## 第 38 章　穿越手册（中）：在 2017 年的条件下重新设计配方 {#ch38 .chapter}

::: goals
- 在 2017 到 2019 年的硬件和数据约束下，为每一个设计决策给出有理有据的选择，涵盖架构、精度与稳定性、显存与并行、需要自己开发的系统、数据，以及后训练；
- 用本书学过的估算工具，判断某个方案在当时的硬件上是否可行。
:::

本章以推理和估算为主，所有数字都是用前面各章的公式算出来的**数量级估计**。

### 38.1 约束回顾，以及一个关键的发现

**约束条件**（第 37 章）：V100 每卡 16 GB 显存（2018 年起有 32 GB 版本），**只支持 FP16**，有效算力约 40 TFLOP/s；DGX-1 的机内拓扑不是全互联（全互联的 NVSwitch 要到 2018 年底）；每卡的跨机带宽约 6.25 GB/s；高质量数据只有几万亿 token；软件栈需要自己搭建。

**关键的发现：算力与带宽之比，与今天差不多。** 第 20 章推导过：用 FSDP 跨机器训练时，每张卡每步处理的 token 数至少要达到 $F/\text{BW}$，才能把通信藏在计算后面。

| | 有效算力 ÷ 每卡跨机带宽 | 每卡每步至少要处理的 token 数 |
|---|---|---|
| H100 | $4\times10^{14}\div5\times10^{10}$ | 约 8,000 |
| V100（DGX-1） | $4\times10^{13}\div6.25\times10^{9}$ | 约 6,400 |

两者的比例相近。也就是说，**今天的大部分并行设计思路，在 2017 年依然适用。** 真正更紧的约束，是 **16 GB 的显存**和 **FP16 的数值范围**。

### 38.2 架构

#### 稠密模型还是 MoE？

**MoE 的优势**：同样的计算量能换来更强的模型（第 8 章），在算力受限的 2017 年尤其有价值。**MoE 在当时的困难**：all-to-all 通信要跨过很慢的网络；DGX-1 的机内拓扑不是全互联；FP16 下路由器容易出现数值问题；工程上很复杂。历史上，GShard（2020）和 Switch Transformer（2021）都是在 **TPU** 上做出来的。

**用第 19 章的方法估算 MoE 的通信能不能藏住。** 以 DeepSeek-V3 的配置为例，看每个 token 经过一个 MoE 层时的情况（只看前向；反向的计算和通信都翻倍，比例不变）：

| 项目 | 计算 | 数值 |
|---|---|---|
| 计算 | 9 个专家（8 个路由专家 + 1 个共享专家），每个专家 $2\times3\times7168\times2048$ FLOP | 约 7.9 亿 FLOP |
| 跨机通信 | 最多发往 4 台机器，V100 只能用 FP16：分发 $4\times7168\times2$ 字节 + 回收同样多 | 约 115 KB |
| **比值** | | **约 6,900 FLOP/字节** |

V100 集群的 $F/\text{BW}$ 约为 6,400 FLOP/字节，两者几乎相等。这意味着**只有在计算和通信几乎完美重叠的情况下**（比如 DualPipe 那样的调度，第 21 章），通信才不会成为瓶颈。如果把每个 token 最多能去的机器数**从 4 台减到 2 台**，比值就会翻倍到约 13,800，余量就充足了（{{fig-ch38-ratio}}）。

**建议：分两代来做。**

| 时间 | 模型 | 理由 |
|---|---|---|
| **第一代（2018 年）** | **稠密模型**，规模在 7B 到 70B 之间，按 Chinchilla 配比训练 | 先把基础设施、数据流水线和整套配方验证一遍，同时交付第一个可用的产品。稠密模型的工程风险最低 |
| **第二代（2019 年）** | **MoE**，最好部署在 DGX-2（NVSwitch 全互联）这样的机器上；每个 token 最多只能发往 2 台机器；专家数量是每台机器 GPU 数的整数倍；每个 token 选的专家数少一些 | 目标是接近 DeepSeek-V3 的计算规模，约 $3\times10^{24}$ FLOP |

#### 各个组件的选择

**只需要知识、不需要特殊硬件的部分，全部直接采用**（第 7 章）：decoder-only 的结构；Pre-norm，配合 RMSNorm；RoPE（角度要用 FP32 计算，第 13 章）；SwiGLU；GQA，可以减少推理时的 KV cache，在 16 GB 的显存下尤其重要；去掉偏置；小模型共享嵌入层。

**专门为 FP16 准备的组件**：**QK-norm 和 z-loss 必须加上**（38.3 节）。

**注意力内核**：要支持长上下文，必须自己写一个 FlashAttention 式的分块注意力内核（第 22 章）。V100 的 Tensor Core 可以通过 WMMA 接口调用，每个 SM 有最多 96 KB 的共享内存，实现起来比在 H100 上难，但可行。历史上，xformers 的内存高效注意力就支持 V100。

**分词器**：字节级 BPE，词表约 10 万，覆盖多种语言。**从第一天起就预留好特殊 token**（对话模板、工具调用、思考过程等），因为分词器一旦确定就很难再改（第 5、24 章）。

**上下文长度**：主体训练用 4K，最后再做长上下文扩展（第 9 章）。

### 38.3 FP16 下的精度与稳定性

**基本方案**：FP16 混合精度，加上动态 loss scaling，再保留一份 FP32 的主权重（第 13 章）。这套方法到 2017 年 10 月才被发表，但穿越者在 1 月就已经知道了。

**FP16 特有的风险**：**激活值溢出**，FP16 能表示的最大值只有 65,504，残差流的数值不断累积、注意力的 logits、MLP 的中间结果，都可能超过这个上限；**梯度下溢**，很小的梯度会直接变成 0（第 13 章的实验）。

**防御措施**（大部分都来自第 12、13 章）：

| 措施 | 针对什么 |
|---|---|
| **QK-norm**，直接给注意力 logits 设一个上限 | 注意力 logits 增长，导致溢出 |
| **z-loss** | 输出层 logits 漂移 |
| logit 软上限 | 双重保险 |
| softmax、归一化、loss、RoPE 都用 FP32 计算 | 关键运算不溢出 |
| 小的初始化，残差分支的输出层按 $1/\sqrt{2L}$ 缩小 | 残差流的数值增长 |
| $\beta_2 = 0.95$，梯度裁剪阈值 1.0 | 防止 Adam 状态过时和单步更新过大 |
| 监控每一步是否溢出、loss scale 的变化、各层激活值的最大值 | 尽早发现问题 |

**在小规模上先验证**：第 12 章讲过，"小模型 + 偏高的学习率"就能复现大模型才会遇到的失稳。在 FP16 下，先用这种方式把所有防御措施都测一遍，再放大规模。

**备选方案**：从 2018 年起，可以在 Google Cloud 上租用支持 bf16 的 TPU，作为对照，或者用来跑某些不稳定的实验。

### 38.4 显存与并行：一个完整的例子

**任务**：在 4,096 张 V100（16 GB）上，训练一个 70B 的稠密模型（80 层，$d = 8192$），序列长度 4K，训练 1.4T token。

**方案**（显存账本见{{fig-ch38-memory}}）：TP = 8（一台 DGX-1V 内部），PP = 8（每段 10 层），DP = 64，配合 ZeRO-1。

| 检查项 | 计算 | 结果 |
|---|---|---|
| 模型状态 | 只用 TP 和 PP 时，$16\times70\times10^9/64 = 17.5$ GB，放不下。加上 ZeRO-1：参数和梯度 $4\Psi/64 \approx 4.4$ GB，优化器状态 $12\Psi/64/64 \approx 0.2$ GB | **约 4.6 GB** |
| 激活值，不做重新计算 | 每层每个 micro-batch 约 $34Tbd/t \approx 143$ MB；每段 10 层，约 1.4 GB；1F1B 下第一个阶段最多同时保存 8 份，约 11.4 GB | 加上模型状态和缓冲区，**超过 16 GB** |
| 激活值，做重新计算 | 只保存每层的输入：每层约 8.4 MB；10 层 × 8 份，约 0.7 GB，再加上正在重新计算的那一层 | **合计约 6 GB，放得下** |
| 全局 batch | 约 400 万 token，即 1,024 条 4K 序列。DP = 64，所以每个副本 $m = 16$ 个 micro-batch | — |
| 流水线气泡 | $(8-1)/(16+7) \approx 30\%$，太高了。改用 $v = 5$ 的交错调度后，约降到 8% | 需要交错调度 |
| 训练时间 | $6\times70\times10^9\times1.4\times10^{12} \approx 5.9\times10^{23}$ FLOP，按每卡 35 TFLOP/s 的有效模型算力（重新计算多出来的部分已包含在效率损失中） | **约 7 周** |

如果在 2018 年换成 32 GB 的 V100，就可以少做或者不做重新计算，省下约 33% 的额外计算。

### 38.5 需要自己开发的系统（按优先级）

| 优先级 | 系统 | 关键内容 | 何时开始 |
|---|---|---|---|
| 1 | **数据流水线**（用 CPU 集群） | 爬虫、正文提取、语言识别、启发式过滤、MinHash 去重、质量分类器 | **2017 年 1 月立即开始**。它只需要 CPU，而且是周期最长的一项 |
| 2 | **训练框架** | FP16 混合精度和 loss scaling；数据并行（基于 NCCL 2 或 MPI，梯度分桶，并与反向传播重叠）；ZeRO-1；Megatron 式的张量并行；1F1B 和交错调度的流水线并行；激活重计算；分布式的异步检查点；健康检查与自动重启 | 2017 年第一季度 |
| 3 | **内核** | 分块注意力（FlashAttention 式）；融合的 RMSNorm、softmax 加交叉熵、SwiGLU；把所有参数打包更新的 Adam | 2017 年第二季度 |
| 4 | **评测框架** | 包括去污染（第 17、30 章） | 2017 年第一季度，与训练框架同步 |
| 5 | **推理引擎** | KV cache、continuous batching、分页管理 KV cache、INT8 量化（P100 和 V100 已经支持 INT8 点积指令）、投机解码 | 2018 年，第一代模型出来之前 |
| 6 | **强化学习基础设施** | 训练与生成分离、沙箱环境、可验证的奖励 | 2018 年下半年 |

**框架选择**：PyTorch 在 2017 年还很年轻，但它是动态图，便于研究，可以用 C++ 和 CUDA 写扩展；TensorFlow 更成熟，而且是使用 TPU 的必经之路。建议**以 PyTorch 为主，加上自己写的 CUDA 扩展**。如果要用 TPU，就再单独维护一套 TensorFlow 代码。

### 38.6 数据

#### 立刻开始

- **抓取和处理 Common Crawl**：按 FineWeb 的配方来做（第 15 章）。当时还没有 trafilatura（2019 年才出现），但有 jusText、boilerpipe 等正文提取工具，也可以自己写。
- **语言识别**：fastText（2017 年已有）。
- **去重**：MinHash 加 LSH，这是 1997 年就有的经典算法。
- **代码**：抓取 GitHub，按许可证过滤，处理 fork，按仓库组织（第 14 章）。
- **数学**：用能保留 LaTeX 的方法提取网页中的数学内容；下载 arXiv 的 LaTeX 源码。
- **书籍**：**尽早开始购买实体书并扫描**，这是合规获取书籍数据的方式。当时已经有可用的 OCR 服务。

#### 质量分类器：自举

一开始用维基百科、教科书等作为正例，训练一个 fastText 分类器（DCLM 的思路，第 16 章）；等第一代 7B 模型出来之后，再用它来给数据打分，也就是 FineWeb-Edu 的做法，进一步提升数据质量。

#### 2017 年独有的机会：建立"干净"的评测集

当时网上还没有 MMLU、GSM8K 这些基准，训练数据也就不可能被它们污染。可以**提前自己出题**，建立一套不公开的评测集，涵盖知识、数学、代码和推理（第 30 章）。

#### 雇人

尽早招募专家标注员，编写 SFT 示范数据、偏好数据和评测题目。

#### 数据规模的规划

不重复的高质量 token 约 3T 到 5T；最好的那部分数据可以重复最多约 4 遍（第 10 章），有效数据量可以达到 10T 左右；第一代 70B 模型按 Chinchilla 配比只需要 1.4T token，完全够用。数据不足的问题，主要出现在第二代。

**配比**（参考 Llama 3）：通用网页约一半，代码约两成，数学和科学约两成（但这部分数据稀缺），其余是书籍和多语言数据。训练的最后阶段，用高质量数据做退火（第 16 章）。

### 38.7 后训练

这一部分以知识为主，算力需求很小，是**穿越者优势最大的环节**。

| 步骤 | 做法 | 依据 |
|---|---|---|
| SFT | 使用预留好的特殊 token 设计对话模板；只对回答部分计算 loss；数据少而精 | 第 24 章 |
| 偏好优化 | **先用 DPO，再迭代**，而不是一开始就上 PPO。DPO 简单、便宜、稳定 | 第 26 章 |
| 推理能力 | 用 GRPO 加可验证奖励（数学、代码）来训练。但要注意：**R1-Zero 的成功，依赖于一个足够强的基座模型**。第一代模型可以先在数学和代码上做 RLVR，再把得到的数据蒸馏给其他模型；真正的突破可能要等到第二代 | 第 27、29 章 |
| 工具使用 | 代码执行沙箱；2017 年已经可以调用 Bing 和 Google 的搜索 API | 第 28 章 |
| 安全 | 制定模型规范，训练模型拒绝真正有害的请求，同时避免过度拒绝，并做红队测试 | 第 31 章 |
| 推理部署 | 长思维链需要高效地服务。在 16 GB 的显存下，GQA 或 MLA、KV cache 量化都格外重要 | 第 33、34 章 |

### 38.8 汇总：2017 年版的配方

| 维度 | 选择 |
|---|---|
| 架构 | 第一代用稠密模型，第二代用 MoE（每个 token 最多发往 2 台机器）；decoder-only、Pre-RMSNorm、RoPE、SwiGLU、GQA、去掉偏置；**加上 QK-norm 和 z-loss** |
| 分词器 | 字节级 BPE，约 10 万词表，从一开始就预留特殊 token |
| 精度 | FP16 混合精度，动态 loss scaling，FP32 主权重，关键运算用 FP32；可以租 TPU 作为 bf16 的对照 |
| 优化器 | AdamW，$\beta = (0.9, 0.95)$，权重衰减 0.1，梯度裁剪 1.0，warmup 加余弦衰减或 WSD |
| 规模 | 先用规模阶梯拟合出自己的 scaling law；第一代按 Chinchilla 配比训练 |
| 并行 | 机内 TP（8），跨机 PP（交错调度），外层 DP 加 ZeRO-1，配合激活重计算 |
| 系统 | 自己开发：混合精度、TP、PP、ZeRO、分块注意力、融合内核、异步检查点、容错 |
| 数据 | 立即开始清洗流水线（MinHash、fastText）；代码、数学和书籍是重点；先建立不公开的评测集 |
| 后训练 | SFT → 迭代 DPO → RLVR/GRPO（等基座足够强时）→ 蒸馏；安全贯穿全程 |

::: keypoints
1. V100 集群的"有效算力 ÷ 每卡跨机带宽"约为 6,400，与 H100 的约 8,000 相近，所以今天的并行思路大多仍然适用；更紧的约束是 16 GB 显存和 FP16 的数值范围。
2. DeepSeek-V3 式的 MoE 在 V100 上每字节通信约有 6,900 FLOP 计算，几乎没有余量；把每个 token 最多去的机器数减到 2 台，比值翻倍。所以第一代做稠密模型，第二代在 DGX-2 等全互联机器上做 MoE。
3. 现代架构的组件只需要知识，可以全部直接采用；FP16 下必须加上 QK-norm、z-loss、FP32 关键运算和完善的溢出监控，并先用"小模型 + 高学习率"验证。
4. 70B 模型在 4,096 张 16 GB 的 V100 上：TP8 + PP8（交错调度）+ DP64 + ZeRO-1 + 激活重计算，每卡约 6 GB，约 7 周训练完 1.4T token。
5. 最先启动的是数据流水线；系统按"训练框架 → 内核 → 评测 → 推理引擎 → 强化学习基础设施"的顺序开发。2017 年可以建立永远干净的私有评测集。后训练以知识为主，是穿越者优势最大的环节。
:::

::: exercises
1. **计算**：把 38.4 节的方案换成 32 GB 的 V100。不做重新计算还放得下吗？如果能，训练时间可以缩短多少？
2. **计算**：一个 MoE 配置：$d = 4096$，每个专家的隐藏层宽 1,408（SwiGLU），每个 token 选 6 个专家，外加 2 个共享专家，每个 token 最多发往 2 台机器，通信用 FP16。算出它的 FLOP/字节比，判断它在 V100 集群上能否把通信藏住。
3. **设计**：写一份在 FP16 下验证训练稳定性的实验计划，包括用多大的小模型、扫描哪些学习率、开关哪些防御措施、观察哪些指标。
4. **规划**：把 38.5 节的 6 个系统画成一张甘特图，标出它们之间的依赖关系，以及哪些可以同时进行。
5. **设计**：为 2017 年设计分词器：词表多大，覆盖哪些语言，预留哪些特殊 token，用什么数据来训练它。
6. **设计**：在 2017 年，为你的公司设计一套不公开的评测集：涵盖哪些能力，每类出多少题，由谁来出，怎样保证它永远不会泄露到训练数据中。
:::
