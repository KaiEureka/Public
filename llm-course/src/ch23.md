## 第 23 章　大规模训练的运维 {#ch23 .chapter}

::: goals
- 量化故障对训练效率的影响，推导检查点的最优保存间隔；
- 说清检查点里要保存什么，以及怎样保存得又快又安全；
- 设计坏卡、慢节点和静默数据损坏的检测与隔离机制；
- 理解作业自动重启的流程、监控体系和值班实践；
- 从几个公开案例中学习经验。
:::

### 23.1 衡量运维的指标：有效训练时间

**有效训练时间占比**（也叫 goodput）= 真正在推进训练的时间 ÷ 总的墙钟时间。

第 18 章讲过，Llama 3 在 1.6 万张卡上训练了 54 天，中断了 466 次，其中 419 次是意外中断，平均约 3 小时一次。尽管如此，他们的有效训练时间仍然**超过了 90%**，而且只有 3 次需要大量人工介入。

每一次故障都会浪费两段时间（{{fig-ch23-timeline}}）：

1. **从上一个检查点到故障发生之间算的东西**，全部作废，需要重新算；
2. **重启所花的时间**：发现故障、替换节点、重新调度、加载检查点、初始化通信。

### 23.2 检查点该隔多久保存一次

记 $\lambda$ 为故障率（每单位时间发生几次故障），$\tau$ 为两次保存检查点之间的间隔，$c$ 为每保存一次检查点训练要停多久，$R$ 为每次故障后重启需要多久。则

$$
\text{损失的时间占比} \approx \underbrace{\frac{c}{\tau}}_{\text{保存检查点的开销}} + \underbrace{\lambda\Big(\frac{\tau}{2} + R\Big)}_{\text{每次故障平均白算 } \tau/2\text{，再加上重启}}.
$$

$\tau$ 越小，保存得越频繁，第一项越大；$\tau$ 越大，故障时白算的越多，第二项越大。对 $\tau$ 求导并令导数为 0，得到**最优的保存间隔**

$$
\tau^* = \sqrt{2c/\lambda}.
$$

这就是 Young（1974）提出的经典公式。

**计算**（估算）：$\lambda$ 为每 3 小时一次。

| 方案 | 每次保存停多久 $c$ | 重启时间 $R$ | 最优间隔 $\tau^*$ | 损失的时间占比 |
|---|---|---|---|---|
| 同步保存，重启慢 | 60 秒 | 10 分钟 | 19 分钟 | **16%** |
| 异步保存，重启慢 | 5 秒 | 10 分钟 | 5.5 分钟 | 8.6% |
| 异步保存，重启快 | 5 秒 | 3 分钟 | 5.5 分钟 | **4.7%** |

<figure id="fig-ch23-tau" data-svg="ch23_tau.svg">
<figcaption>保存间隔与损失的时间占比：每条曲线都有一个最优间隔</figcaption>
</figure>

**结论：保存检查点要快，故障后重启也要快，两者缺一不可（{{fig-ch23-tau}}）。** 而且集群规模越大，$\lambda$ 就越大，问题越严重（见习题 2）。

### 23.3 检查点

#### 要保存什么

要能**准确地接着训练下去**，以下内容一样都不能少：

- 模型参数，包括 FP32 主权重；
- 优化器状态，即 Adam 的 $m$ 和 $v$；
- 学习率调度器的状态，以及当前的步数；
- **数据读取的位置**：已经用过了哪些样本，下一条该读哪一条；
- 各个随机数生成器的状态；
- 如果用 FP16，还有 loss scaling 的缩放因子；
- 配置文件和代码的版本号。

很多团队一开始都会漏掉数据读取的位置。后果是重启之后，有些数据会被重复训练，有些数据则被跳过。405B 模型的完整检查点约为 5.7 TB（第 18 章）。

#### 怎样保存得又快又安全

- **分布式保存**：每张卡只保存自己负责的那一部分（参数分片、优化器状态分片），所有卡同时并行地写入。PyTorch 的分布式检查点（DCP）支持这种方式，而且加载时可以按**不同的并行配置**重新切分，比如换了一种 TP 或 PP 的设置，也能正确加载。
- **异步保存**：先把 GPU 上的状态拷贝到 CPU 的锁页内存里，这只需要几秒钟；之后训练立即继续，由后台线程把数据慢慢写到存储系统中。
- **多级存储**：频繁地把检查点保存到 CPU 内存，或者其他节点的内存里，这样恢复起来最快；隔一段时间再写一次持久化存储。Google 的 Gemini 论文研究过把检查点存在内存中、实现快速恢复的方法。
- **保留策略**：保留最近的若干个检查点，以便遇到 loss 尖峰时可以回退（第 12 章）；再定期长期保存一些，用来做中间评测和事后分析。
- **校验**：保存时计算校验和；定期抽查一个检查点，确认它能被正确加载。

### 23.4 故障有哪些类型

Llama 3 公布了意外中断的原因分布（共 419 次，下面是约数）：

| 原因 | 占比 |
|---|---|
| GPU 故障 | 30% |
| GPU 显存（HBM3）故障 | 17% |
| 软件 bug | 13% |
| 网络交换机或线缆 | 8% |
| 主机维护 | 8% |
| GPU 片上存储（SRAM） | 5% |
| GPU 系统处理器 | 4% |
| 网卡、NCCL 通信超时、**静默数据损坏**、散热、硬盘、电源等 | 各 1% 到 2% |

**约 78% 的意外中断，确认或怀疑是硬件问题。**

还有一些更隐蔽的因素。Llama 3 发现，中午气温高时，GPU 会因为温度升高而自动降频，整体吞吐量会有 1% 到 2% 的波动。第 18 章也提到，全集群的功率会同步大幅波动。

### 23.5 发现和隔离坏节点

#### 开训之前的健康检查

每个作业启动前，先对分配到的节点做一遍快速检查：GPU 诊断（DCGM）、一次小规模的通信测试、确认显存和网卡都正常。有问题的节点直接排除，不让它进入训练。

#### 训练过程中的检测

| 信号 | 说明什么 |
|---|---|
| **NCCL 超时**（看门狗机制） | 集合通信卡住了。第 19 章讲过，只要一个 rank 没有到场，所有 rank 都会一直等下去 |
| **Xid 错误** | NVIDIA 驱动程序报告的错误代码，记录在系统日志里，用来标识各类 GPU 故障 |
| **ECC 错误计数** | 显存的纠错次数在上升，说明这块显存可能快要坏了 |
| 温度过高导致的降频、网卡链路时断时续 | 硬件状态在恶化 |
| **每个 rank 的单步耗时** | 用来发现慢节点 |

**通信记录器**：PyTorch 提供了一个"flight recorder"，记录每个 rank 最近调用过哪些集合通信操作。训练卡死后，可以对比各个 rank 的记录，找出是哪个 rank、在哪一步没有到场。Meta 在 Llama 3 的训练中就用到了这类工具。

#### 慢节点

集合通信的速度取决于最慢的那一个参与者（第 19 章）。一张卡因为过热、PCIe 链路降速或者内存故障而变慢 10%，**整个集群就会跟着慢 10%**。检测的办法是：比较各个 rank 的计算耗时，以及它们在集合通信中等待的时间，找出那个总让别人等它的 rank。

#### 自动处理

一旦发现坏节点：把它从可用节点中移除，用备用节点替换，然后从最近的检查点重启作业。所以集群里通常要**留一部分备用节点**。

**弹性训练**是另一种思路：坏了几个节点，就先减少几份数据并行副本，继续训练，等节点修好再加回来。但在使用张量并行和流水线并行的训练中，这很难实现，所以大多数情况下还是整个作业重启。

### 23.6 静默数据损坏

**静默数据损坏**（silent data corruption，SDC）指硬件算错了，但没有报任何错误，比如运算单元或片上存储中某一位翻转了，而 ECC 没有覆盖到这个位置。

Meta 和 Google 都在 2021 年发表过报告，指出在大规模数据中心里，这种"算错了却不报错"的处理器真实存在。Gemini 的技术报告也提到，在他们的规模下，**大约每一到两周**就会遇到一次影响训练的静默数据损坏。他们用"快速确定性重放"来定位：把出问题的那一步重新算一遍，比对结果，找出算错的硬件。

**对训练的影响**：可能是突然出现 NaN，可能是莫名其妙的 loss 尖峰，也可能是悄无声息的微小偏差，最后这种最难发现。

**检测方法**：

1. **检查 NaN 和 Inf**，以及 loss 和梯度范数是否异常（第 12 章的监控）。
2. **比较数据并行副本之间的参数**：所有数据并行副本在每一步更新后，参数应该**完全一致**。定期对各副本的参数计算校验和并比较，如果某个副本不一致，就说明那里的硬件算错了。这个检查的代价很小，效果却很好（{{fig-ch23-sdc}}）。
3. **重新计算一步**：在另一组硬件上重新算同一步，比对结果。
4. **定期运行"金丝雀计算"**：在每张卡上运行一段已知正确答案的计算，检查结果对不对。

### 23.7 作业的自动重启

故障发生后，自动化系统依次完成（{{fig-ch23-restart}}）：

1. 检测到故障（超时、错误码、心跳中断）；
2. 定位坏节点，把它移除；
3. 补上备用节点，重新调度作业；
4. 拉取镜像，启动进程，初始化 NCCL 通信；
5. 加载最新的检查点，恢复数据读取的位置；
6. 继续训练。

<figure id="fig-ch23-restart" data-svg="ch23_restart.svg">
<figcaption>作业的自动重启流程</figcaption>
</figure>

**重启要快**（23.2 节的 $R$），常见的优化有：提前把容器镜像分发到每个节点上；并行读取检查点；加快通信初始化，在上万张卡的规模下，仅仅是建立 NCCL 通信就可能要花几分钟。

### 23.8 监控与值班

#### 监控

把以下内容放在同一个看板上：**训练指标**，如 loss、梯度范数、注意力 logits 等（第 12 章的清单）；**系统指标**，如 GPU 利用率、功率、温度、ECC 错误计数、网卡错误、存储吞吐量；**效率指标**，如吞吐量、MFU、有效训练时间。

#### 值班

- **分级告警**：明确什么情况自动处理，什么情况需要叫醒人。
- **处理手册**（runbook）：每一类常见问题，都要写好标准的处理步骤。
- **轮值**：基础设施和研究人员都要参与值班，因为有些问题需要研究判断，比如 loss 尖峰要不要回退。
- **训练日志**：记录每一次中断、处理过程和人为决策。Meta 公开的 OPT-175B 日志是很好的学习材料。
- **故障复盘**：重大故障之后，分析根本原因，补充自动化手段。

#### 需要人来做的决策

- 出现 loss 尖峰时，是否回退、是否跳过数据（第 12 章）；
- 发现数据有问题时，是否更换数据；
- 按计划调整配置，比如逐步增大 batch（第 11 章），或者进入长上下文阶段（第 9 章）；
- 定期评测中间检查点，跟踪能力是否在按预期增长（第 30 章）。

### 23.9 公开案例

| 案例 | 规模 | 运维经历 |
|---|---|---|
| **OPT-175B**（Meta，2022） | 992 张 A100，约 2 个月 | 至少 35 次人工重启，替换过 100 多台主机，多次调低学习率。日志完整公开 |
| **BLOOM**（2022） | 384 张 A100，约 3.5 个月 | 平均每周有 1 到 2 张 GPU 故障，配有备用节点 |
| **Llama 3 405B**（2024） | 1.6 万张 H100，54 天 | 466 次中断，有效训练时间超过 90%，只有 3 次需要大量人工介入 |
| **MegaScale**（字节跳动，2024） | 12,288 张 GPU | 训练 175B 模型，MFU 达到 55.2%，有效训练时间超过 90%。论文详细介绍了他们的故障诊断和容错系统 |

::: keypoints
1. 运维的目标是有效训练时间。损失的时间占比约为 $c/\tau + \lambda(\tau/2 + R)$，最优保存间隔是 $\sqrt{2c/\lambda}$。异步保存检查点再加上快速重启，可以把损失从约 16% 压到约 5%。
2. 检查点必须包括参数、优化器状态、调度器状态、数据读取位置和随机数状态。采用分布式保存、异步保存、多级存储，并做校验。
3. 约 78% 的意外中断来自硬件。要在开训前做健康检查，在训练中通过超时、Xid 错误、ECC 计数和每个 rank 的耗时来发现坏节点和慢节点，并自动替换、重启。
4. 静默数据损坏会悄悄地破坏训练。比较数据并行副本之间的参数校验和，是一种代价很小的检测手段。
5. 监控看板要统一，告警要分级，处理手册、轮值、训练日志和故障复盘都不可少。人主要负责研究层面的判断。
:::

::: exercises
1. **推导**：从"损失的时间占比 $\approx c/\tau + \lambda(\tau/2 + R)$"出发，推导出 $\tau^* = \sqrt{2c/\lambda}$，并求出最优间隔下的损失占比。
2. **计算**：如果集群扩大到 10 万张卡，故障率大约变成每小时 2 次（与卡数成正比）。在 $c = 5$ 秒、$R = 5$ 分钟的条件下，最优保存间隔是多少？损失的时间占比是多少？这说明大规模训练还需要什么样的技术？
3. **清单**：列出一个检查点必须包含的全部内容。如果漏掉了数据读取的位置，会造成什么后果？
4. **设计**：设计一个检测静默数据损坏的方案：比较数据并行副本之间的参数校验和。多久检查一次？大约要花多少时间？发现不一致之后怎样处理？
5. **思考**：为什么 NCCL 通信卡死的问题很难排查？通信记录器是怎样帮助定位问题的？
6. **写作**：为"凌晨 3 点出现 loss 尖峰"写一份处理手册，说明每一步做什么、由谁决定、什么情况下要叫醒研究负责人。
:::
