## 第 33 章　推理基础 {#ch33 .chapter}

::: goals
- 说清 prefill 和 decode 两个阶段的计算特点，以及衡量推理服务的几个关键指标；
- 实现 KV cache，算清它的显存开销；
- 理解 continuous batching、PagedAttention、前缀缓存和 chunked prefill；
- 用一个简单的模型估算吞吐量、延迟和每百万 token 的成本；
- 了解主流的推理框架。
:::

为什么推理很重要？一是**成本**：一个被大量使用的模型，上线后在推理上花的计算量，往往远远超过训练（第 10 章）。二是**体验**：用户能直接感受到回答出得快不快。

### 33.1 两个阶段

| 阶段 | 做什么 | 计算特点 |
|---|---|---|
| **Prefill** | 一次性处理全部提示词，算出第一个输出 token | 所有 token 可以并行处理，矩阵乘法很大，**受限于算力**（第 4 章） |
| **Decode** | 每一步只生成一个 token，然后把它接到序列末尾 | 每一步都要读一遍全部的权重，再加上 KV cache，**受限于显存带宽** |

**衡量推理服务的指标**（{{fig-ch33-phases}}）：

| 指标 | 含义 | 主要受什么影响 |
|---|---|---|
| **TTFT**（time to first token，首 token 延迟） | 从发出请求，到收到第一个 token 要等多久 | prefill 的速度，以及排队的时间 |
| **TPOT** 或 **ITL**（每个输出 token 的间隔） | 之后每个 token 隔多久出来一个 | decode 每一步的速度 |
| 总延迟 | TTFT + TPOT × 输出的 token 数 | — |
| **吞吐量** | 每张 GPU 每秒一共能生成多少 token，或者每一美元能生成多少 token | batch 大小、显存利用率 |

### 33.2 KV cache

#### 原理

如果没有缓存，每生成一个新 token，都要把整个序列从头算一遍，包括所有旧 token 的 K 和 V。生成 $n$ 个 token，总的计算量随 $n^2$ 增长。

**KV cache** 的做法是：把每一层、每个 token 已经算好的 K 和 V 保存下来。每一步只为**新的 token** 计算 $q, k, v$，然后用它的 $q$ 去和缓存中所有的 K、V 做注意力：

```python
q, k, v = attn.qkv(ln1(x_new)).split(d, dim=2)                  # 只计算新 token 的 q、k、v
k = torch.cat([cache_k, k], dim=2); v = torch.cat([cache_v, v], dim=2)
cache_k, cache_v = k, v                                         # 把新的 K、V 存进缓存
att = softmax(mask(q @ k.T / sqrt(dh))) @ v                     # 新 token 关注所有已有的 token
```

prefill 时把整段提示词一次性送进去，同时把它们的 K、V 存入缓存；decode 时每一步只送入 1 个新 token。

::: experiment
**在第 6 章的 GPT 上手写 KV cache**（共运行约 1.5 分钟）。

**① 正确性**：用第 6 章训练好的模型做贪心解码，生成 100 个 token。有缓存和没有缓存的两种实现，输出**完全一致**。生成的文本是 "ht the so the shall the shall the shall the…"，不断重复同一个片段。

**② 速度**：用同样的结构，换成 1,024 的上下文长度、$d = 256$（权重是随机的，只用来计时），在 32 个 token 的提示之后生成 $n$ 个 token：

| 生成的 token 数 $n$ | 不用缓存 | 用 KV cache | 加速 |
|---|---|---|---|
| 128 | 1.17 秒 | 0.28 秒 | 4.2 倍 |
| 256 | 3.27 秒 | 0.58 秒 | 5.7 倍 |
| 512 | 13.0 秒 | 1.56 秒 | 8.3 倍 |
| 960 | 50.0 秒 | 2.61 秒 | **19.1 倍** |
:::

不断重复同一个片段，是贪心解码的典型问题（回顾第 1 章的采样和温度），所以实际使用时一般会采样，而不是每一步都选概率最大的 token。速度上，不用缓存时，耗时随 $n^2$ 增长；用缓存后，基本随 $n$ 线性增长。生成得越长，差距越大（{{fig-ch33-kvspeed}}）。

#### 显存开销

$$
\text{每个 token 的 KV cache} = 2 \times L \times n_{kv} \times d_h \times \text{每个数的字节数}\qquad(\text{第 7 章}).
$$

以 Llama 3 70B 为例：$2\times80\times8\times128\times2$ 字节，约 **320 KB/token**。一条 128K token 的序列，仅 KV cache 就要约 **40 GB**。

decode 的每一步要读两样东西：**权重**，读一次，batch 里的所有序列共用；**每条序列自己的 KV cache**，不能共用。所以 batch 越大，KV cache 在读取量中所占的比重就越大。比如 70B 的模型，权重是 140 GB；如果 batch 有 64 条、每条 4K token，KV cache 就有 $64\times4096\times320$ KB，约 84 GB。

### 33.3 Batching

::: experiment
**batch 大小对 decode 的影响。** 在上面那个模型上，让每条序列都已经缓存了 512 个 token，测量一个 decode 步骤的耗时：

| batch 大小 $B$ | 每步耗时 | 总吞吐量 | 每条序列的速度 |
|---|---|---|---|
| 1 | 2.9 毫秒 | 339 token/秒 | 339 token/秒 |
| 4 | 5.1 毫秒 | 779 token/秒 | 195 token/秒 |
| 16 | 17.5 毫秒 | 914 token/秒 | 57 token/秒 |
| 64 | 67.4 毫秒 | 949 token/秒 | 15 token/秒 |
:::

**batch 变大，总吞吐量上升，但每个用户等得更久。这就是吞吐量和延迟之间的取舍。**

在实验所用的 CPU 上，这个小模型的权重只有约 12 MB，读取权重并不是瓶颈，所以吞吐量只提升了约 2.8 倍就饱和了。在 GPU 上运行大模型时，读权重才是主要开销，batch 的收益要大得多：第 4 章的实验 B 显示，每个 token 的成本可以降到原来的 1/16。

#### 静态 batching 与 continuous batching

- **静态 batching**：凑齐一批请求，一起生成，等**整批都结束**了，才接收下一批。先结束的那些序列只能空等，GPU 被浪费掉了。
- **continuous batching**（Orca，Yu 等，2022）：**每一个 decode 步骤**都可以调整这一批的成员：结束的序列立刻离开，新来的请求立刻加入。GPU 的利用率因此大幅提升（{{fig-ch33-batching}}）。这是现代推理系统的标配。

<figure id="fig-ch33-batching" data-svg="ch33_batching.svg">
<figcaption>静态 batching 与 continuous batching</figcaption>
</figure>

batch 最大能开多大，通常取决于显存还能放下多少 KV cache。

### 33.4 PagedAttention：像操作系统一样管理 KV cache

**问题**：早期的系统为每个请求**按最大长度连续地预留**一块 KV cache。但请求最后实际会生成多长，事先并不知道，所以大量预留的空间被浪费，再加上内存碎片，vLLM 的论文（Kwon 等，2023）估计，当时的系统有 **60% 到 80% 的 KV cache 显存被浪费**。

**解决办法**：借鉴操作系统的分页内存管理（{{fig-ch33-paged}}）：

- 把 KV cache 切成固定大小的**块**，比如每块存 16 个 token；
- 用一张**块表**记录每条序列的逻辑位置对应哪个物理块；
- **需要时才分配新的块**，浪费降到 4% 以下；
- 多条序列之间可以**共享**相同的块。比如对同一个提示采样多个回答时，提示部分的 KV cache 只需存一份，等到哪条序列要修改时再复制（写时复制）。

结果是吞吐量比之前的系统提高了 2 到 4 倍。这就是 **vLLM** 的核心技术。

### 33.5 前缀缓存

很多请求都有相同的开头：同样的系统提示、同样的少样本示例、同一段对话历史、同一份文档，以及 Agent 每一轮都会重复发送的上下文（第 28 章）。**前缀缓存**的做法是：把这些共同前缀的 KV cache 保存下来，下次遇到同样的前缀，直接复用，不必再做一遍 prefill。

- **RadixAttention**（SGLang，Zheng 等，2023）用一棵基数树来管理所有缓存的前缀，按"最近最少使用"的原则淘汰旧的缓存；
- 商业 API 的**提示缓存**：命中缓存的输入 token，通常只收原价的一小部分，例如一成左右；
- 对于很长的上下文和多轮对话，还可以把 KV cache 转移到 CPU 内存甚至固态硬盘上。Moonshot 的 Mooncake 架构就是以 KV cache 为中心来设计整个推理系统的。

所以第 28 章建议 Agent 的上下文"只在末尾追加"：这样前面的部分才能一直命中缓存。

### 33.6 调度

- **chunked prefill**（Sarathi-Serve，2024）：一段很长的提示，如果一次性做 prefill，会占用 GPU 好一阵子，这期间其他用户的 decode 都会停下来，TPOT 出现明显的卡顿。解决办法是把长提示切成若干块，和其他用户的 decode 步骤穿插着执行。
- **抢占**：KV cache 的显存不够时，暂停一部分请求：把它们的 KV cache 转移到 CPU 内存，或者直接丢掉，等恢复时再重新计算。
- **按服务等级调度**：比如保证付费用户的 TTFT 不超过某个上限。
- **把 prefill 和 decode 分开部署**：两个阶段的计算特点完全不同，所以干脆放在不同的 GPU 上分别处理，比如 DistServe、Splitwise、Mooncake，以及 DeepSeek-V3 的部署方案（第 8 章）。第 34 章细讲。

### 33.7 成本模型

#### decode：受显存带宽限制

$$
\text{每步耗时} \approx \frac{\text{权重字节数} + B\times\text{每条序列的 KV cache 字节数}}{\text{显存带宽}}, \qquad \text{吞吐量} = \frac{B}{\text{每步耗时}}.
$$

**例子**（估算）：Llama 3 70B，BF16，部署在 8 张 H100 上，用张量并行把模型切到 8 张卡上（总带宽约 26.8 TB/s）。每条序列 4K 上下文，KV cache 为 $4096\times320$ KB，约 1.31 GB。

| batch 大小 $B$ | 每步耗时 | 总吞吐量 | 每条序列的速度 |
|---|---|---|---|
| 1 | $140/26.8 \approx 5.2$ 毫秒 | 约 190 token/秒 | 约 190 token/秒 |
| 32 | $(140+42)/26.8 \approx 6.8$ 毫秒 | 约 4,700 token/秒 | 约 150 token/秒 |
| 64 | $(140+84)/26.8 \approx 8.4$ 毫秒 | 约 7,700 token/秒 | 约 120 token/秒 |
| 256 | $(140+335)/26.8 \approx 17.7$ 毫秒 | 约 14,500 token/秒 | 约 56 token/秒 |

8 张卡一共 640 GB 显存，去掉 140 GB 的权重，还能放下约 380 条 4K 的序列。在 $B = 256$ 时，每步的计算量约为 $2\times70\times10^9\times256 \approx 3.6\times10^{13}$ FLOP，8 张卡大约 9 毫秒就能算完，仍然比 17.7 毫秒的读取时间短，所以瓶颈仍然在显存带宽上。

<figure id="fig-ch33-cost" data-svg="ch33_cost.svg">
<figcaption>decode 的成本模型：batch 越大，总吞吐量越高，每个用户越慢</figcaption>
</figure>

**每百万个输出 token 的成本**（按每卡每小时 2.5 美元，8 卡共 20 美元/小时计算）：$B = 1$ 时，每小时约生成 69 万个 token，约合 **29 美元**每百万 token；$B = 256$ 时，每小时约生成 5,200 万个 token，约合 **0.38 美元**每百万 token。**相差约 75 倍**（{{fig-ch33-cost}}）。

这是理想情况，实际能用到的带宽一般只有峰值的 50% 到 80%。衡量这一点的指标叫 **MBU**（model bandwidth utilization，模型带宽利用率），它在推理中的地位相当于训练中的 MFU。

#### prefill：受算力限制

每个 token 约需 $2N$ FLOP。70B 的模型每个 token 约 $1.4\times10^{11}$ FLOP，8 张卡按 50% 的利用率计算，每秒约 $4\times10^{15}$ FLOP，也就是每秒能处理约 **2.9 万个输入 token**。

**这就是为什么 API 的输入 token 通常比输出 token 便宜好几倍**：输入的 token 可以一大批并行处理，输出的 token 只能一个一个地生成。

### 33.8 推理框架

| 框架 | 特点 |
|---|---|
| **vLLM** | PagedAttention、continuous batching，开源生态中用得最广 |
| **SGLang** | RadixAttention 前缀缓存，结构化输出，调度很强 |
| **TensorRT-LLM** | NVIDIA 官方，内核优化得很深 |
| TGI | HuggingFace 出品 |
| llama.cpp | 在本地 CPU 或消费级显卡上运行，支持各种量化格式 |
| NVIDIA Dynamo | 2025 年发布，面向 prefill 和 decode 分离部署的大规模推理 |

::: keypoints
1. 推理分为 prefill 和 decode 两个阶段。prefill 受限于算力，决定 TTFT；decode 受限于显存带宽，决定 TPOT。
2. KV cache 把 decode 的计算量从随 $n^2$ 增长变成随 $n$ 增长。实验中生成 960 个 token 时快了 19 倍，而且输出与不用缓存时完全一致。Llama 3 70B 每个 token 的 KV cache 约 320 KB，128K 的上下文就要约 40 GB。
3. batch 越大，吞吐量越高，但每个用户的速度越慢。continuous batching 在每一步都更新 batch 的成员。PagedAttention 用分页的方式把 KV cache 的浪费降到 4% 以下，吞吐量提高 2 到 4 倍。
4. 前缀缓存复用相同开头的 KV cache；chunked prefill 避免长提示卡住其他用户；prefill 和 decode 还可以分开部署。
5. 在 decode 阶段，每步耗时约为（权重 + $B$ × KV cache）÷ 带宽。70B 模型在 8 张 H100 上，$B = 1$ 和 $B = 256$ 时每百万 token 的成本相差约 75 倍。输入 token 之所以便宜，是因为 prefill 可以并行处理。
:::

::: exercises
1. **计算**：Llama 3 8B（32 层，8 个 KV 头，$d_h = 128$，BF16），每个 token 的 KV cache 有多大？一张 80 GB 的 H100 放下 16 GB 的权重之后，在 8K 上下文的条件下，最多能同时服务多少条序列？
2. **推导**：从"每步耗时 $= (W + BK)/\text{BW}$"出发，推出吞吐量关于 $B$ 的表达式。$B$ 趋于无穷大时，吞吐量趋向于什么？这说明为了提高吞吐量，最终要优化的是什么？
3. **计算**：同样是 70B 模型、8 张 H100，如果把权重量化成 FP8（70 GB），KV cache 也用 FP8，那么 $B = 64$ 时吞吐量大约变成多少？
4. **思考**：为什么 continuous batching 能大幅提高 GPU 的利用率？用"每个请求的输出长度差别很大"来解释。
5. **设计**：一个客服机器人的每个请求都带着同样的 3,000 token 的系统提示，然后是用户 200 token 左右的问题。前缀缓存能省下多少 prefill 的计算？这对 TTFT 和成本分别有什么影响？
6. **思考**：为什么 API 的输出 token 比输入 token 贵？如果一个应用的输入很长、输出很短（比如总结长文档），它的成本主要花在哪里？
:::
