## 第 19 章　集合通信 {#ch19 .chapter}

::: goals
- 说清 all-reduce、all-gather、reduce-scatter、all-to-all 等通信操作分别做什么，各自用在训练的哪个环节；
- 推导环形 all-reduce 的步骤和通信量，用 α-β 模型估算通信时间；
- 理解树形算法、分层通信和交换机内归约；
- 了解 NCCL 的工作方式；
- 理解怎样让计算和通信重叠，以及通信层面有哪些常见故障。
:::

### 19.1 基本概念

- **rank**：参与通信的每个进程的编号。通常一个进程对应一张 GPU。
- **world size**：参与通信的进程总数，本章记为 $n$。
- **集合通信**：一组进程**一起**完成的数据交换，所有参与者都要调用同一个操作。另一类是**点对点通信**（send 和 recv），只发生在两个进程之间。

### 19.2 基本操作

用 4 张 GPU 来示意（{{fig-ch19-ops}}），$a_i$ 表示第 $i$ 张 GPU 上的数据：

| 操作 | 之前 | 之后 | 用途 |
|---|---|---|---|
| **broadcast** | 只有 GPU 0 上有数据 $a$ | 每张卡都是 $a$ | 分发初始权重 |
| **reduce** | 每张卡各有 $a_i$ | 只有 GPU 0 得到 $\sum a_i$ | 很少单独使用 |
| **all-reduce** | 每张卡各有 $a_i$ | **每张卡都得到 $\sum a_i$** | 数据并行时对梯度求和，张量并行时合并激活值 |
| **reduce-scatter** | 每张卡各有一个完整的向量 | 各卡的向量先求和，结果切成 4 份，**每张卡只拿到其中一份** | ZeRO/FSDP 中的梯度同步（第 20 章） |
| **all-gather** | 每张卡各有向量的一份 | 每张卡都拿到拼好的完整向量 | ZeRO/FSDP 中把切分的参数拼回完整（第 20 章） |
| **all-to-all** | 每张卡上的数据分成 4 份，分别要发给 4 张卡 | 每张卡收到其他所有卡发给它的那一份 | MoE 把 token 发给对应的专家（第 8 章），序列并行 |
| **send / recv** | — | 点对点传输 | 流水线并行中，在相邻的阶段之间传递数据（第 21 章） |

</figure>

**一个关键的恒等关系：all-reduce = reduce-scatter + all-gather。** 先求和并分片，再把各片拼回完整。环形算法正是按这两步来做的。

### 19.3 估算通信时间：α-β 模型

$$
\text{发送一条大小为 } m \text{ 字节的消息，耗时} \approx \alpha + \frac{m}{\beta}.
$$

- **$\alpha$ 是延迟**：每条消息固定的启动开销，与消息大小无关。在 GPU 集群上通常是微秒级。
- **$\beta$ 是带宽**：每秒能传多少字节，见第 18 章的带宽层级表。（本章沿用文献中的写法，用 $\beta$ 表示带宽，与 Adam 的 $\beta_1, \beta_2$ 无关。）

小消息的耗时主要由 $\alpha$ 决定，大消息主要由带宽决定（19.4 节的{{fig-ch19-ab}}）。

### 19.4 环形 all-reduce

把 $n$ 张 GPU 连成一个环，每张卡只向下一张卡发送、从上一张卡接收。把要求和的数据（大小为 $S$ 字节）切成 $n$ 块。

**第一阶段：reduce-scatter，共 $n-1$ 步。** 每一步，每张卡把某一块发给下一张卡；下一张卡把收到的这块加到自己对应的块上。$n-1$ 步之后，每张卡恰好拥有**一块**已经完整求和的数据。

**第二阶段：all-gather，共 $n-1$ 步。** 每张卡把自己已经求和完毕的那一块沿着环传下去，收到的卡直接用它覆盖自己对应的块。$n-1$ 步之后，每张卡都拥有全部的求和结果（{{fig-ch19-ring}}）。

<figure id="fig-ch19-ring" data-svg="ch19_ring.svg">
<figcaption>环形 all-reduce 的 6 步（4 张卡）</figcaption>
</figure>

::: experiment
**用 4 个 CPU 进程手写环形 all-reduce**（PyTorch 分布式 + Gloo 后端，运行约 10 秒）。第 $r$ 张"卡"上的初始数据是 $10^r\times[1, 2, 3, 4]$。

| 阶段 | GPU 0 | GPU 1 | GPU 2 | GPU 3 |
|---|---|---|---|---|
| 初始 | [1, 2, 3, 4] | [10, 20, 30, 40] | [100, 200, 300, 400] | [1000, 2000, 3000, 4000] |
| reduce-scatter 第 1 步 | [1, 2, 3, 4004] | [11, 20, 30, 40] | [100, 220, 300, 400] | [1000, 2000, 3300, 4000] |
| reduce-scatter 第 2 步 | [1, 2, 3303, 4004] | [11, 20, 30, 4044] | [111, 220, 300, 400] | [1000, 2220, 3300, 4000] |
| reduce-scatter 第 3 步 | [1, **2222**, 3303, 4004] | [11, 20, **3333**, 4044] | [111, 220, 300, **4444**] | [**1111**, 2220, 3300, 4000] |
| all-gather 第 3 步之后 | [1111, 2222, 3333, 4444] | [1111, 2222, 3333, 4444] | [1111, 2222, 3333, 4444] | [1111, 2222, 3333, 4444] |

reduce-scatter 结束时，每张卡恰好有一块已经求和完毕（加粗）；all-gather 的 3 步把它们传遍全环。

另用 64 MB 的张量测试：每个进程发送的数据量正好是张量大小的 **1.500 倍**；与 PyTorch 自带的 all_reduce 相比，结果的最大差异是 $1.9\times10^{-6}$。
:::

#### 通信量

每一步每张卡发送 $S/n$ 字节，两个阶段一共 $2(n-1)$ 步，所以

$$
\text{每张卡发送的总量} = \frac{2(n-1)}{n}\,S \approx 2S,
\qquad
\text{耗时} \approx 2(n-1)\,\alpha + \frac{2(n-1)}{n}\cdot\frac{S}{\beta}.
$$

- **带宽那一项几乎不随 $n$ 增长**：GPU 再多，每张卡也只需发送约 $2S$ 的数据。可以证明，这是 all-reduce 在带宽上能达到的最优值。
- **延迟那一项随 $n$ 线性增长**：卡多了以后，小消息会很慢。

<figure id="fig-ch19-ab" data-svg="ch19_ab.svg">
<figcaption>α-β 模型：小消息看延迟，大消息看带宽</figcaption>
</figure>

实验中 $n = 4$，理论值 $2(n-1)/n = 1.5$，与实测一致。结果与 PyTorch 自带实现之间的微小差异，正是第 13 章讲的"浮点加法不满足结合律"：两种算法相加的顺序不同，结果在最后几位上略有差别。

### 19.5 其他算法和优化

#### 树形算法

把 GPU 组织成一棵二叉树，先沿着树往上求和，再沿着树往下广播，延迟项只随 $\log_2 n$ 增长。以 $n = 1024$、$\alpha = 5$ 微秒为例：环形的延迟项约为 $2\times1023\times5$ 微秒，约 10 毫秒；树形的延迟项只有约 0.1 毫秒。

NCCL 使用"双二叉树"，让两棵树各负责一半的数据，这样带宽也能用满。**NCCL 会根据消息大小和拓扑自动选择用环形还是树形。**

#### 分层 all-reduce

利用第 18 章的带宽层级。设有若干台机器，每台 8 张卡，分三步完成：

1. **机器内部做 reduce-scatter**，走 NVLink（450 GB/s）。完成后，每张卡持有 $S/8$ 的部分和。
2. **跨机器做 all-reduce**：每台机器上编号相同的卡组成一组，走自己那条轨道的网卡（50 GB/s）。每组只需处理 $S/8$ 的数据。
3. **机器内部做 all-gather**，走 NVLink。

**估算：对 14 GB 的数据（相当于一个 7B 模型的 BF16 梯度）做 all-reduce，8 台机器共 64 张卡。** 这里只算通信量；单张 80 GB 的卡其实放不下 7B 模型的全部训练状态，这个问题第 20 章讲。

| 步骤 | 每张卡发送的数据 | 链路 | 耗时 |
|---|---|---|---|
| 1. 机器内 reduce-scatter | $\frac78\times14$ GB ≈ 12.3 GB | NVLink 450 GB/s | 约 27 ms |
| 2. 跨机器 all-reduce | $2\times\frac78\times1.75$ GB ≈ 3.1 GB | 网卡 50 GB/s | 约 61 ms |
| 3. 机器内 all-gather | 约 12.3 GB | NVLink 450 GB/s | 约 27 ms |
| **合计** | | | **约 115 ms** |

作为对比，如果全部走 50 GB/s 的网络：$2\times\frac{63}{64}\times14$ GB ÷ 50 GB/s，约 **551 ms**（{{fig-ch19-hier}}）。

#### 交换机内归约

让交换机在转发数据的同时直接完成求和。NVSwitch 上的 NVLink SHARP 和 InfiniBand SHARP 都支持这样做。这样每张卡只需发送一次 $S$、接收一次 $S$，而环形算法里每张卡要发送约 $2S$。

#### all-to-all

每张卡要给其他每一张卡各发一份不同的数据，每张卡发送约 $\frac{n-1}{n}S$。它的速度受限于网络的**对分带宽**：把集群切成两半，两半之间能同时传输的总带宽。这和第 18 章讲的收敛直接相关：上层收敛得越多，跨区域的 all-to-all 就越慢。

所以 MoE 在跨机器时代价很高。DeepSeek 在 2025 年开源了 **DeepEP**，专门优化 MoE 的 all-to-all：同时利用 NVLink 和 RDMA，并且提供两套实现，一套用于训练和处理提示词时追求高吞吐，另一套用于逐 token 生成时追求低延迟。

### 19.6 训练中各环节用到的通信

| 并行方式（第 20、21 章） | 通信操作 | 通信量 | 放在哪里 |
|---|---|---|---|
| 数据并行 | 梯度 all-reduce，或者 reduce-scatter 加 all-gather（ZeRO/FSDP） | 与参数量成正比，每步一次 | 可以跨机器 |
| 张量并行 | 激活值的 all-reduce，或者 reduce-scatter 加 all-gather | **每一层都要做，而且是频繁的小消息** | **必须在一台机器内部** |
| 流水线并行 | 相邻阶段之间的 send/recv | 只传各阶段边界处的激活值 | 可以跨机器 |
| 专家并行 | all-to-all | 与 token 数成正比 | 机器内部最好，跨机器要做特别优化 |
| 上下文并行 | 环形传递 K/V，或者 all-to-all | 与序列长度成正比 | 视情况而定 |

### 19.7 让计算和通信重叠

原理是：通信操作在 GPU 上**另一条执行队列**（CUDA stream，GPU 上可以并发执行的任务队列）上运行，这样它就可以和计算同时进行。

**数据并行中的典型做法**：反向传播是从最后一层往前算的，后面几层的梯度最先算好。把梯度按顺序分成若干"桶"，PyTorch DDP 默认每桶约 25 MB。**一个桶里的梯度一旦全部算好，就立即开始对它做 all-reduce**，同时继续计算前面各层的梯度。理想情况下，等反向传播结束时，通信也差不多做完了（{{fig-ch19-overlap}}）。

**要注意的是**：NCCL 本身也要占用 GPU 的计算单元（SM）来搬运数据、做加法，所以会和计算任务抢资源。DeepSeek-V3 专门拿出 132 个 SM 中的 20 个用于通信，并报告说这已经足以跑满 InfiniBand 和 NVLink 的带宽。

### 19.8 NCCL 是怎样工作的

NCCL 是 NVIDIA 的集合通信库，大规模训练基本都用它。

- **自动探测拓扑**：搞清楚哪些 GPU 之间有 NVLink、走 PCIe 时经过哪些交换芯片、每张网卡离哪张 GPU 最近。
- **建立多条通道**：同时建立多个环或多棵树，每条通道由一组 GPU 计算单元负责，并尽量走不同的网卡，以便把所有链路的带宽都用起来。
- **选择算法**：环形、树形、交换机内归约等。
- **选择传输协议**：小消息用低延迟的协议，大消息用高带宽的协议。
- **衡量指标**：nccl-tests 会报告"总线带宽"（busbw），它等于数据大小 ÷ 耗时 × $2(n-1)/n$。这个数可以直接和链路的硬件带宽比较，用来判断通信有没有跑满。

其他的通信库还有 Gloo（主要用于 CPU，本章的实验就是用它跑的）和 MPI。

### 19.9 通信层面的常见故障

- **卡死**：集合通信要求所有 rank 都参与。只要有一个 rank 没有调用（比如它崩溃了，或者代码里走进了另一个分支），其余所有 rank 都会一直等下去，直到超时报错。
- **调用顺序不一致导致的死锁**：不同的 rank 以不同的顺序调用集合操作，彼此等待对方。
- **慢节点**：一张卡慢了，整个环都会被拖慢。集合通信的速度取决于最慢的那个参与者（第 23 章）。
- **网络链路出错**：网线或光模块出现误码，导致重传和带宽下降。这类问题要靠通信带宽测试来发现（第 18 章的验收测试）。

::: keypoints
1. 基本操作有 all-reduce、reduce-scatter、all-gather、all-to-all 和点对点的 send/recv，其中 all-reduce = reduce-scatter + all-gather。
2. α-β 模型：耗时 = 延迟 + 数据量 / 带宽。环形 all-reduce 中，每张卡发送 $2(n-1)S/n \approx 2S$，这是带宽上的最优值，几乎不随卡数增加；但延迟项随 $n$ 线性增长。树形算法把延迟降到 $\log n$ 量级。
3. 分层通信利用机器内部的高带宽：在 64 张卡上对 14 GB 做 all-reduce，约 115 毫秒；全部走网络则约 551 毫秒。交换机内归约能把通信量再减半。all-to-all 受对分带宽限制。
4. 不同的并行方式使用不同的通信操作。张量并行的通信最频繁，所以必须放在一台机器内部。
5. 用分桶加异步通信，让通信与反向传播重叠进行。NCCL 负责探测拓扑、选择算法和建立多条通道。要警惕卡死、死锁和慢节点。
:::
