第 4 章的结论是：逐元素运算和 softmax 这类计算受限于**显存带宽**，大矩阵乘法受限于**算力**；默认情况下，每个 kernel（内核，即在 GPU 上运行的一个函数）都要先从显存（HBM）读入数据，算完再写回显存。**本章的核心思想是：尽量让数据留在片上的高速存储（SRAM 和寄存器）里，减少与显存之间的往返。**

### 22.1 标准注意力慢在哪里

对每个头，标准实现按以下顺序执行：

1. $S = QK^\top$，把 $T\times T$ 的分数矩阵写入显存；
2. $S = \operatorname{mask}(S)$，从显存读出，加上掩码，再写回；
3. $P = \operatorname{softmax}(S)$，读出，计算 softmax，再写回；
4. $O = PV$，读出 $P$，计算输出。

其中 $S$ 和 $P$ 都是 **$T\times T$ 的矩阵**：

- **显存放不下**：序列长度 $T = 8192$、32 个头、batch 为 1 时，用 BF16 存储，每层的 $S$ 和 $P$ 加起来就要 **8.6 GB**。$T = 131{,}072$、64 个头时，要 4,398 GB。
- **很慢**：mask 和 softmax 这几步，每个元素只做很少的计算，却要在显存和计算单元之间来回搬运 $T^2$ 个数，完全受限于显存带宽。

### 22.2 FlashAttention

FlashAttention 出自 Dao 等（2022），思路是：**永远不把完整的 $T\times T$ 矩阵写入显存。**

1. 把 $Q$ 切成若干块，每块 $B_r$ 行；$K$ 和 $V$ 也切成若干块，每块 $B_c$ 行。
2. 每个 GPU 线程块负责一个 $Q$ 块，把它放在 SRAM 里。
3. 让 $K$、$V$ 的块依次流过 SRAM。每来一块，就在 SRAM 里算出一个 $B_r\times B_c$ 的小分数块，然后立即更新输出。
4. **难点在于 softmax 需要一整行的最大值和总和**，而现在一次只能看到这一行的一部分。解决办法是下面的**在线 softmax**。

#### 在线 softmax：一次只看一块，也能算出正确结果

对 $Q$ 中的某一行，维护三个量：$m$ 是到目前为止见过的分数的最大值；$\ell$ 是到目前为止的 $\sum e^{x - m}$；$o$ 是到目前为止的 $\sum e^{x-m}v$，即还没除以总和的输出。每来一个新的 K/V 块（这一行在这块上的分数为 $x^{(b)}$，对应的值为 $v_j$）：

$$
\begin{aligned}
m_{\text{new}} &= \max\big(m,\ \max_j x^{(b)}_j\big),\\
\ell_{\text{new}} &= e^{m - m_{\text{new}}}\,\ell + \textstyle\sum_j e^{x^{(b)}_j - m_{\text{new}}},\\
o_{\text{new}} &= e^{m - m_{\text{new}}}\,o + \textstyle\sum_j e^{x^{(b)}_j - m_{\text{new}}}\,v_j.
\end{aligned}
$$

所有块都处理完之后，输出 $= o/\ell$。

**为什么是对的？** 每当最大值从 $m$ 变成 $m_{\text{new}}$，之前累积的每一项 $e^{x-m}$ 都只需要乘以 $e^{m - m_{\text{new}}}$，就变成了 $e^{x - m_{\text{new}}}$。所以 $e^{m-m_{\text{new}}}$ 这个系数，就是把之前的累积结果"换算"到新的基准上。最终得到的结果与一次性计算完全一样，**不是近似**（{{fig-ch22-online}} 是一个手算的例子）。这个技巧来自 Milakov 与 Gimelshein（2018）。减去最大值是为了防止指数溢出，这在第 13 章讲过。

#### 反向传播：不保存，重新计算

前向计算结束时，只额外保存每一行的 **logsumexp**，即 $L = m + \log\ell$，每行一个数。反向传播时，利用 $Q$、$K$ 和 $L$，在 SRAM 里分块**重新算出** $S$ 和 $P = e^{S - L}$，而不是从显存中读取保存好的矩阵。这与第 20 章讲的"重新计算"是同一个思路：多做一点计算，换来大量的显存和带宽节省。

#### 核心循环

```python
for i in range(0, T, Br):                          # 每个 Q 块对应 GPU 上的一个线程块
    q = Q[i:i+Br]; m = -inf; l = 0; o = 0
    for j in range(0, T, Bc):                      # 让 K/V 块依次流过 SRAM
        if j > i + Br - 1: continue                # 整块都在"未来"：跳过
        s = mask(q @ K[j:j+Bc].T * scale)          # 只有 Br × Bc 大小
        m_new = max(m, s.max(1))
        p = exp(s - m_new); corr = exp(m - m_new)
        l = corr * l + p.sum(1)
        o = corr * o + p @ V[j:j+Bc]
        m = m_new
    O[i:i+Br] = o / l;  L[i:i+Br] = m + log(l)     # 保存 logsumexp，供反向传播使用
```

::: experiment
**用 numpy 实现分块算法，与标准注意力对比。** $T = 1024$，$d_h = 64$，块大小 $128\times128$，使用因果掩码，双精度：

- 分块算法与标准注意力的最大差异：$8.3\times10^{-16}$（双精度下的舍入误差，说明两者完全一致）；
- 共 64 个 K/V 块对，实际计算了 36 个，因为因果关系跳过了 28 个；
- 任何时刻最多只存在一个 $128\times128 = 16{,}384$ 个数的分数块，而完整的分数矩阵有 1,048,576 个数。
:::

#### 显存节省

除了输出本身，FlashAttention 只需要额外保存每一行的 logsumexp（FP32）：

| 设置 | 标准注意力每层要保存的 $S$ 和 $P$（BF16） | FlashAttention 额外保存的 logsumexp |
|---|---|---|
| $T = 8$K，32 个头 | 8.6 GB | 1 MB |
| $T = 32$K，32 个头 | 137 GB | 4 MB |
| $T = 128$K，64 个头 | 4,398 GB | 34 MB |

第 20 章激活值公式中那个与 $T^2$ 成正比的项（$5n_hT/d$），就是因此而消失的。

#### 为什么计算量不变，速度却快得多

FlashAttention 的 FLOP 数与标准注意力相同，反向传播时因为要重新计算，甚至还多一些。但原来那些受限于显存带宽的步骤（mask、softmax，以及 $T^2$ 级别的显存读写），现在全部在 SRAM 里完成了，整个注意力计算变成了**受限于算力**（第 4 章的 roofline 模型）。

#### 各个版本

| 版本 | 年份 | 改进 | 公布的性能 |
|---|---|---|---|
| FlashAttention | 2022 | 分块计算，加在线 softmax，加反向重新计算 | GPT-2 训练最多提速约 3 倍；显存占用随 $T$ 线性增长，而不是平方增长 |
| FlashAttention-2 | 2023 | 更好地划分各个线程块的工作，减少非矩阵乘法的运算 | 约为第一版的 2 倍，在 A100 上达到峰值的 50% 到 73% |
| FlashAttention-3 | 2024 | 专门针对 H100：异步数据搬运（TMA），让不同的线程组分别负责搬数据和做计算（warp 专门化），支持 FP8 | H100 上 BF16 达到约 740 TFLOP/s（约 75% 的峰值），FP8 接近 1.2 PFLOP/s |

### 22.3 其他常见的融合

| 融合对象 | 不融合时的做法 | 融合之后 |
|---|---|---|
| RMSNorm | 平方、求均值、开方、相除、乘以 $\gamma$，好几次显存往返 | 一个内核，读一次、写一次 |
| SwiGLU | SiLU 和逐元素相乘分别各读写一次 | 一个内核完成 |
| RoPE | 取 cos/sin、做乘法、做加法，各读写一次 | 一个内核完成 |
| 交叉熵 | 先把完整的 logits 写入显存（第 20 章：每条序列约 2 GB） | 与输出层的矩阵乘法融合，分块计算，例如 Liger Kernel |
| 矩阵乘法之后的加偏置、激活函数 | 单独的内核 | 在矩阵乘法的收尾阶段顺手完成（cuBLASLt 等库提供这种功能） |
| AdamW 更新 | 每个参数张量分别启动好几个内核 | 把所有参数打包，用少数几个内核完成更新。PyTorch 的优化器提供了 foreach 和 fused 选项 |

**不必每个都手写**：`torch.compile` 会自动分析计算图，把可以融合的运算合并，并为它们生成 Triton 内核；**CUDA Graphs** 会把一整串内核的调用"录制"下来，之后一次性重放，从而消除 CPU 逐个启动内核的开销。这对内核又小又多的场景尤其重要，比如推理时的逐 token 生成。

### 22.4 Triton：用 Python 写 GPU 内核

**Triton**（Tillet 等，2019，现由 OpenAI 维护）是一种嵌入在 Python 中的 GPU 编程语言。它和 CUDA 的关键区别在于：**CUDA 要求你为每个线程编程，Triton 则让你为一整块数据编程。** 内存访问怎样合并、共享内存怎样分配、怎样调用 Tensor Core，这些细节都交给编译器处理。

下面是一个融合的按行 softmax：

```python
@triton.jit
def softmax_kernel(out_ptr, in_ptr, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)                                    # 每个程序实例处理一行
    offs = tl.arange(0, BLOCK)
    mask = offs < n_cols
    x = tl.load(in_ptr + row * n_cols + offs, mask=mask, other=-float("inf"))   # 这一行只读一次
    x = x - tl.max(x, axis=0)                                 # 以下计算都在寄存器里完成
    num = tl.exp(x)
    tl.store(out_ptr + row * n_cols + offs, num / tl.sum(num, axis=0), mask=mask)  # 只写一次

softmax_kernel[(n_rows,)](y, x, n_cols, BLOCK=triton.next_power_of_2(n_cols))   # 启动 n_rows 个实例
```

如果用 PyTorch 的基本运算（求最大值、相减、取指数、求和、相除）一步步写，每个元素要从显存读五次、写三次；这个内核只读一次、写一次。（PyTorch 自带的 `torch.softmax` 本身已经是融合好的内核，这里只是用 softmax 来演示融合的原理。）

::: experiment
在 CPU 上用 Triton 的解释器模式（`TRITON_INTERPRET=1`）运行上面的内核，它与 `torch.softmax` 的最大差异是 $3.7\times10^{-9}$。解释器模式只能验证结果是否正确，测不了速度。
:::

**更底层的工具**：

- **CUTLASS 和 CuTe**：NVIDIA 用于编写高性能矩阵乘法的 C++ 模板库；
- **ThunderKittens**：斯坦福开发的高性能内核框架；
- **DeepGEMM**：DeepSeek 在 2025 年开源的 FP8 矩阵乘法库，报告在 Hopper 架构上能达到 1,350 TFLOP/s 以上。

要把性能压榨到极致，就需要直接利用 Hopper 架构的新特性：异步数据搬运（TMA）、新的 Tensor Core 指令，以及 warp 专门化。

### 22.5 性能分析：找出时间花在了哪里

#### 工具

- **PyTorch Profiler**：记录每个运算和内核的耗时，生成时间线，可以在浏览器中查看。
- **Nsight Systems**：NVIDIA 提供的全局时间线，能同时显示 CPU、GPU 内核、内存拷贝和 NCCL 通信。
- **Nsight Compute**：深入分析单个内核，告诉你它达到了多少显存带宽、多少算力，在 roofline 图上处于什么位置。

#### 在时间线上找什么

{{fig-ch22-profile}} 画出了下面几种典型问题在时间线上的样子。

1. **GPU 的空闲间隙**：GPU 在等 CPU。常见原因有：CPU 启动内核太慢；数据加载跟不上；代码里有强制同步的操作，比如在训练循环里调用 `.item()` 或打印张量，这会让 CPU 一直等到 GPU 算完。
2. **通信没有和计算重叠**：NCCL 内核和计算内核在时间线上是先后排列的，而不是并行的。
3. **大量很小的内核**：说明需要融合，或者使用 CUDA Graphs。
4. **效率低的矩阵乘法**：矩阵的维度不是 64 或 128 的倍数，或者张量并行切得太细，导致每张卡上的矩阵太小。
5. **受限于带宽的运算占了太多时间**：比如归一化、激活函数等。

### 22.6 提高 MFU 的清单

|---|---|

| 显存够用时，不做或少做重新计算 | 第 20 章 |

| 缩小流水线气泡，让各个阶段的负载均衡 | 第 21 章 |
| 消除 CPU 与 GPU 之间的同步，异步加载数据，使用锁页内存 | 第 22 章 |
| 找出并剔除慢节点 | 第 23 章 |

**一个经验**：优化之前，先用性能分析工具搞清楚时间到底花在了哪里。凭直觉去优化，往往优化错了地方。

::: keypoints
1. 标准注意力要把 $T\times T$ 的 $S$ 和 $P$ 写入显存：$T = 8$K 时每层就要 8.6 GB，而且 mask 和 softmax 都受限于带宽。
2. FlashAttention 用分块计算加在线 softmax，在 SRAM 中完成整个注意力，结果与标准注意力完全一致（实测差异为 $8\times10^{-16}$）。它只额外保存每行的 logsumexp，反向传播时重新计算。FLOP 不变，但速度快得多，显存占用也从随 $T^2$ 增长变为随 $T$ 增长。
3. 其他常见的融合包括 RMSNorm、SwiGLU、RoPE、交叉熵和 AdamW。`torch.compile` 和 CUDA Graphs 可以自动完成大部分融合，并消除内核的启动开销。
4. Triton 让你以"数据块"为单位编写 GPU 内核，底层细节交给编译器。要榨取极限性能，则需要 CUTLASS 等工具和 Hopper 架构的新特性。
5. 先用性能分析工具找到瓶颈，再动手优化。主要看 GPU 的空闲间隙、通信是否与计算重叠、小内核是否太多，以及矩阵乘法的效率。
:::
