## 第 21 章　并行策略（下）：张量、序列、上下文、流水线与专家并行 {#ch21 .chapter}

::: goals
- 说清张量并行怎样切分 MLP 和注意力，为什么它只能放在一台机器内部；
- 理解序列并行和上下文并行（ring attention、Ulysses）；
- 计算流水线并行的"气泡"，了解 1F1B、交错调度、零气泡和 DualPipe；
- 理解专家并行在整体方案中的位置；
- 能为给定的模型和集群设计一套 4D 或 5D 并行方案，并估算显存、通信和气泡。
:::

第 20 章的结论是：卡数很多时，如果只用数据并行或 FSDP，全局 batch 会大到超过临界值，通信的开销也越来越大。所以要把**一个模型副本**切分到多张卡上，让数据并行的份数变少。可以切分的维度有：

| 切分什么 | 名称 | 简称 |
|---|---|---|
| 每一层内部的矩阵 | 张量并行 | TP |
| 归一化等逐 token 计算的激活值，按序列切 | 序列并行 | SP（与 TP 配套使用） |
| 很长的序列本身 | 上下文并行 | CP |
| 不同的层 | 流水线并行 | PP |
| 不同的专家 | 专家并行 | EP |
| 数据 | 数据并行（可以配合 ZeRO 或 FSDP） | DP |

本章记号：$t$、$p$ 分别为张量并行度和流水线阶段数，$m$ 为每步的 micro-batch 数，$v$ 为交错调度中每张卡持有的段数；$d$、$T$、$b$ 同第 20 章。

### 21.1 张量并行

张量并行的经典方案来自 Megatron-LM（Shoeybi 等，2019）。

#### 切分 MLP

MLP 的计算是 $Y = \operatorname{GELU}(XA)\,B$，其中 $A$ 是 $d\times4d$ 的矩阵，$B$ 是 $4d\times d$ 的矩阵。用 $t$ 张卡来切：

1. **第一个矩阵 $A$ 按列切分**（列并行）：GPU $i$ 持有 $A$ 的第 $i$ 份列 $A_i$，计算 $XA_i$，得到隐藏层的第 $i$ 部分。GELU 是逐元素运算，每张卡在自己那部分上单独算就行，不需要通信。
2. **第二个矩阵 $B$ 按行切分**（行并行）：GPU $i$ 持有 $B$ 的第 $i$ 份行 $B_i$，计算 $\operatorname{GELU}(XA_i)\,B_i$，得到一个"部分和"。
3. **最后做一次 all-reduce**：$Y = \sum_i \operatorname{GELU}(XA_i)\,B_i$。

为什么这样切是对的？$A$ 按列切之后，每张卡得到的是隐藏层中互不重叠的一段；$B$ 按行切之后，每张卡正好用自己那段隐藏层去乘 $B$ 中对应的那几行。把各卡的结果加起来，就等于完整的矩阵乘法。**妙处在于中间不需要任何通信**，只在最后做一次 all-reduce（{{fig-ch21-tp}}）。

#### 切分注意力

按**头**来切：每张卡负责 $n_h/t$ 个头的 Q、K、V，相当于对 $W_q, W_k, W_v$ 做列并行；每张卡算完自己那些头的注意力之后，输出投影 $W_o$ 按行切，最后同样做一次 all-reduce。

#### 通信量和取舍

每一层前向计算要做 2 次 all-reduce（注意力之后一次，MLP 之后一次），反向传播再做 2 次。估算通信时间与计算时间之比，按每个 token、每一层来算：每张卡的计算量（前向加反向）约为 $6\times12d^2/t = 72d^2/t$ FLOP；4 次 all-reduce，每次的数据是 $d$ 个 BF16 数，环形算法下每次约收发 $2\times2d$ 字节，共约 $16d$ 字节。于是

$$
\frac{\text{通信时间}}{\text{计算时间}} \approx \frac{16d/\text{BW}}{72d^2/(tF)} = \frac{2}{9}\cdot\frac{t\,F}{d\cdot\text{BW}}.
$$

代入 $t = 8$、$d = 8192$、$F = 4\times10^{14}$ FLOP/s：走 NVLink（450 GB/s）时比值约为 **0.19**，通信只占计算的约两成，而且还能部分重叠；走跨机网络（50 GB/s）时比值约为 **1.7**，通信时间比计算时间还长。

**所以张量并行只能放在一台机器内部**，$t$ 一般不超过 8。像 GB200 NVL72 这样把 NVLink 域扩大到 72 张卡的系统，就允许更大的 $t$。

**收益**：每张卡的参数、梯度和优化器状态都变成原来的 $1/t$，矩阵乘法中涉及的那部分激活值也被切开了。

### 21.2 序列并行

只用张量并行时，LayerNorm 和残差连接这类运算的输入输出，在每张卡上都是**完整的一份**，没有被切开，它们的激活值是重复存储的。

**序列并行**（Korthikanti 等，2022）的做法是：在这些部分**按序列方向切分**，每张卡只处理 $T/t$ 个 token；同时，把原来的 all-reduce 换成"reduce-scatter + all-gather"，通信总量不变（第 19 章）。这样一来，激活值就完全被切开了，每层约为 $34Tbd/t$ 字节。张量并行和序列并行几乎总是一起使用。

### 21.3 上下文并行：处理超长序列

当序列很长时（比如 128K 个 token），即使只有一条序列，它的激活值也放不进一张卡。解决办法是**把序列切开，分给多张卡**。难点在于注意力：每个 token 都需要看到它前面**所有** token 的 K 和 V。

| 方法 | 做法 |
|---|---|
| **Ring Attention**（Liu 等，2023） | 每张卡持有一段 Q、K、V。K 和 V 的块沿着环依次传递，每张卡每收到一块，就算一部分注意力，用"在线 softmax"技巧（第 22 章）把各块的结果正确地合并起来。传递下一块的同时，计算当前这一块 |
| **Ulysses**（DeepSpeed，2023） | 用一次 all-to-all，把"按序列切分"转换成"按头切分"。这样每张卡拿到完整的序列，但只负责一部分头；算完注意力，再用一次 all-to-all 换回来。它的并行度不能超过头的数量 |
| **all-gather 方式**（Llama 3 采用） | 直接 all-gather 所有的 K 和 V，然后各自计算。实现简单 |

**负载均衡**：因果注意力中，序列越靠后的 token 要看的内容越多，计算量也越大。所以通常把序列切成 $2\times\text{CP}$ 块，第 $i$ 张卡分到第 $i$ 块和第 $2\text{CP}-1-i$ 块，一前一后搭配，让每张卡的工作量大致相等（{{fig-ch21-cp}}）。

### 21.4 流水线并行

#### 基本做法

把模型的层分成 $p$ 段，每一段叫一个**阶段**（stage），放在不同的卡上。数据像流水线一样依次流过各个阶段。阶段之间只需要用**点对点的 send/recv** 传递边界处的激活值，数据量小，所以**可以跨机器**。

#### 问题：气泡

如果一次只送一个 batch 进去，那么第一个阶段算的时候，后面的阶段都在等；反向传播时情况相反。卡闲着的这段时间叫**气泡**。解决办法是把 batch 拆成 $m$ 个 micro-batch，让它们接连进入流水线。

**GPipe 调度**（Huang 等，2018）：先让所有 micro-batch 依次做完前向，再依次做反向。{{fig-ch21-gpipe}} 是 $p = 4$、$m = 4$ 的例子，假设一次前向和一次反向都花 1 个单位时间。

#### 改进的调度方式

| 调度 | 做法 | 效果 |
|---|---|---|
| **1F1B**（PipeDream-Flush） | 预热阶段过后，每个阶段交替做一次前向、一次反向 | 气泡与 GPipe 一样，但同时存在的激活值最多只有 $p$ 份，而 GPipe 要存 $m$ 份（{{fig-ch21-1f1b}}） |
| **交错调度**（Megatron，2021） | 每张卡持有 $v$ 段**不相邻**的层。例如 $p = 4$、$v = 2$ 时，GPU 0 负责第 1 段和第 5 段 | 气泡约降到原来的 $1/v$，代价是点对点通信的次数变多 |
| **零气泡**（Qi 等，2023） | 把反向传播拆成两部分：对输入求梯度（B），以及对权重求梯度（W）。B 必须尽快算，好传给前一个阶段；W 可以往后推迟，正好用来填补气泡 | 气泡接近于 0 |
| **DualPipe**（DeepSeek-V3） | 从流水线的**两端**同时送入 micro-batch，并把前向和反向的计算块与 MoE 的 all-to-all 通信精心交叠起来 | 气泡更少，通信几乎完全被计算掩盖。代价是需要存两份参数，但专家并行很大时，多出来的这部分不多 |

**流水线并行的其他问题**：

- **各阶段的负载要均衡**：第一个阶段有嵌入层，最后一个阶段有输出层和 loss，计算量比中间的阶段多。Llama 3 的做法是让首尾两个阶段各少放一个 Transformer 层。
- **与 batch 大小的关系**：每个数据并行副本每一步要处理 $m$ 个 micro-batch，所以全局 batch = DP 份数 × $m$ × micro-batch 大小。$m$ 至少要比 $p$ 大好几倍，气泡才会小。

### 21.5 专家并行

回顾第 8 章：把 MoE 的专家分到不同的卡上，每经过一个 MoE 层，都要做两次 all-to-all，一次把 token 发出去，一次把结果收回来。一种常见的组合是：**注意力层用数据并行或张量并行，MoE 层用专家并行**。专家并行的那一组卡，尽量放在少数几台机器之内。

### 21.6 组合起来：两个公开案例

#### Llama 3 405B（稠密模型，16,384 张 H100）

| 训练阶段 | TP | CP | PP | DP | MFU |
|---|---|---|---|---|---|
| 8K 序列 | 8 | 1 | 16 | 128 | 41% |
| 128K 长上下文 | 8 | 16 | 16 | 8 | 38% |

（在 8,192 张卡、8K 序列时，MFU 是 43%。）

这些并行组在集群中的排列方式，从内到外依次是 **TP → CP → PP → DP**，与第 18 章的带宽层级正好对应（{{fig-ch21-layout}}）：通信最频繁的 TP 放在 NVLink 上；CP 放在较近的机器之间；PP 只需要点对点通信，可以跨机器；DP 每一步只同步一次，最能容忍延迟，所以放在最外层，可以跨 pod。

#### DeepSeek-V3（MoE 模型，2,048 张 H800）

| 维度 | 设置 |
|---|---|
| PP | 16 路，使用 DualPipe 调度 |
| EP | 64 路，跨 8 台机器 |
| DP | 使用 ZeRO-1 |
| **TP** | **不使用** |

论文中说他们没有使用代价高昂的张量并行。他们通过精细的显存优化，比如重新计算 RMSNorm、把部分数据放到 CPU 上，省出了足够的显存。再加上 H800 的 NVLink 带宽本来就被削减过（第 18 章），不用张量并行就更合理了。

**这说明并行方案没有标准答案**，取决于模型结构（稠密还是 MoE）、硬件条件和工程能力。

### 21.7 怎样设计一套并行方案

#### 步骤

1. **TP 放在一台机器内部**（不超过 8）。在显存够用的前提下，越小越好，因为 TP 越大，每张卡的矩阵越小，计算效率越低。对于 MoE 模型，MoE 层优先用 EP，而不是 TP。
2. **如果 TP 加上 FSDP 还是装不下，或者 DP 份数太多导致 batch 太大，就加 PP。** 尽量让各阶段负载均衡，并且保证 $m$ 至少是 $p$ 的 4 倍左右，或者使用交错调度。
3. **序列很长时，加 CP。**
4. **MoE 模型加 EP**，尽量限制在少数几台机器之内。
5. **剩下的卡都用于 DP**，配合 ZeRO-1 或 FSDP。检查全局 batch 是否不超过目标值（第 11 章）。
6. **按带宽层级来摆放**：TP 放在 NVLink 上，CP 和 EP 放在机器内部或同一个 pod 内，PP 跨机器，DP 放在最外层。
7. **估算显存、通信和气泡，然后实际测一遍性能，再反复调整。**

#### 例子：70B 稠密模型，1,024 张 H100，序列长度 8K，目标 batch 约 800 万 token

选择 **TP = 8（一台机器），PP = 4（80 层，每段 20 层），DP = 1024/(8×4) = 32**。

| 检查项 | 计算 |
|---|---|
| 全局 batch | 800 万 token 约为 1,024 条 8K 序列。每个 DP 副本每步处理 32 条，micro-batch 取 1，所以 $m = 32$ |
| 气泡 | $(4-1)/(32+4-1) \approx 8.6\%$。如果用 $v = 5$ 的交错调度，可以降到约 2% |
| 模型状态 | 每张卡的参数和梯度约为 $4\Psi/32 \approx 8.75$ GB；优化器状态再用 ZeRO-1 在 32 个 DP 副本之间切分，约 0.8 GB。**合计约 9.6 GB** |
| 激活值（TP + SP，不做重新计算） | 每层每个 micro-batch 约为 $34\times8192\times8192/8 \approx 285$ MB；每段 20 层，约 5.7 GB；1F1B 调度下，第一个阶段最多同时保存 4 个 micro-batch 的激活值，约 **22.8 GB** |
| 合计 | 约 33 GB，再加上缓冲区，**放得进 80 GB，而且不需要重新计算**，这样还能省下 33% 的额外计算 |

**也可以只用 FSDP**：1,024 张卡，每张卡每步处理 1 条 8K 序列，全局 batch 同样是约 800 万 token。但这时每张卡处理的 token 数只是刚好达到第 20 章算出的约 8,000 这个门槛，通信很难完全藏住；而且一条 8K 序列的激活值约为 182 GB，必须做完整的重新计算。所以在这个规模下，**两种方案都能用，各有取舍**；但如果规模扩大到上万张卡，只用 FSDP 就行不通了。

#### 常用框架

- Megatron-LM（NVIDIA）和 NeMo；
- DeepSpeed（微软）；
- TorchTitan（PyTorch 官方，组合了 FSDP2、TP、PP 和 CP）；
- JAX 生态中的 MaxText：通过 GSPMD，只需要给张量标注"按哪个维度切分"，编译器就会自动插入所需的通信。

::: keypoints
1. 张量并行：MLP 的第一个矩阵按列切、第二个按行切，注意力按头切，每层前向只需 2 次 all-reduce。它的通信与计算之比约为 $\frac29\cdot tF/(d\cdot\text{BW})$，所以必须放在 NVLink 范围内。配合序列并行，可以把激活值完全切开。
2. 上下文并行用 ring attention、Ulysses 或 all-gather 的方式切分长序列，并把序列首尾的块搭配分给同一张卡，以均衡负载。
3. 流水线并行的气泡占比为 $(p-1)/(m+p-1)$。1F1B 降低了激活值显存，交错调度、零气泡和 DualPipe 进一步缩小了气泡。
4. 公开的方案：Llama 3 采用 TP8、CP、PP16、DP，从内到外对应带宽层级；DeepSeek-V3 采用 PP16、EP64、ZeRO-1，不用 TP。
5. 设计流程是：TP 放在机器内，PP 和 CP 按需添加，MoE 加 EP，剩下的用于 DP；然后检查全局 batch、显存、气泡和通信，再实际测量、反复调整。
:::
