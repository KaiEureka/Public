### 34.1 量化

#### 为什么只量化权重就能加速

第 33 章讲过，decode 阶段的瓶颈在于**读取权重**。如果把权重从 BF16（2 字节）压缩成 INT4（0.5 字节），每一步要读的字节数就变成了原来的 1/4，在 batch 较小时，decode 能因此快将近 4 倍。计算时，在内核里把权重临时解压回高精度再做乘法即可，这部分开销很小。

batch 较大时，decode 会逐渐变成受限于算力。这时如果还想加速，就需要**把激活值也量化**，比如用 W8A8（权重和激活值都是 8 位）或 FP8，这样才能用上更快的低精度 Tensor Core（第 4、13 章）。

#### 基本做法：直接舍入

最简单的量化方法叫 **RTN**（round to nearest）：

$$
\text{scale} = \frac{\max\lvert w\rvert}{q_{\max}}, \qquad w_q = \operatorname{round}(w/\text{scale}),
$$

其中 INT8 的 $q_{\max} = 127$，INT4 的 $q_{\max} = 7$。$w_q$ 存成整数，使用时再算 $w_q\times\text{scale}$。

**粒度**：可以每一行（每个输出通道）共用一个 scale；也可以每 32 或 128 个权重为一组，各用一个 scale。组越小，越精确，但存 scale 的开销也越大。

::: experiment
**量化第 6 章的模型。** 对所有的线性层做 RTN 量化，嵌入层保持不变，测量验证集 loss：

| 精度 | 粒度 | 验证集 loss | 每个权重占的位数 |
|---|---|---|---|
| FP32 | — | 1.8894 | 32 |
| INT8 | 每个输出通道 | 1.8895 | 8 |
| INT4 | 每个输出通道 | 1.9077 | 4 |
| INT4 | 每 32 个一组 | **1.8984** | 约 4.5（含 scale） |
| INT3 | 每个输出通道 | 1.9726 | 3 |
| INT3 | 每 32 个一组 | 1.9330 | 约 3.5 |
:::

**INT8 几乎无损**；INT4 开始有损失，**分组可以挽回大部分损失**（{{fig-ch34-quant}}）；位数再往下降，损失会迅速变大。

#### 更好的方法

| 方法 | 思路 |
|---|---|
| **LLM.int8()**（Dettmers 等，2022） | 发现模型规模达到约 6.7B 以后，激活值中会出现少数几个**数值特别大的维度**（离群特征）。做法是把这几个维度单独用 FP16 计算，其余维度用 INT8 |
| **SmoothQuant**（Xiao 等，2022） | 激活值有离群值，很难量化；权重则比较容易量化。于是给每个通道乘上一个缩放系数，把激活值中的"难度"转移一部分到权重上，从而实现 W8A8 |
| **GPTQ**（Frantar 等，2022） | 一列一列地量化权重。每量化完一列，就利用二阶信息（输入数据的协方差）调整**还没有量化的那些列**，补偿刚才产生的误差。这样 3 到 4 位的损失很小，量化 175B 的模型只需约 4 个 GPU 小时 |
| **AWQ**（Lin 等，2023） | 根据激活值的大小，找出**最重要的那一小部分权重通道**，先把它们放大再量化，从而保护它们的精度 |
| **FP8 / FP4** | H100 原生支持 FP8，可以做 W8A8；Blackwell 支持 NVFP4 和 MXFP4（第 13 章）。OpenAI 的 gpt-oss 就是以 MXFP4 格式发布 MoE 权重的，所以 120B 的模型能放进单张 80 GB 的显卡 |
| **KV cache 量化** | 把 KV cache 存成 FP8、INT8 甚至更低的精度。大 batch 和长上下文时，KV cache 往往比权重还大，量化它的收益很明显 |
| **量化感知训练**（QAT） | 在训练时就模拟量化带来的误差，让模型适应低精度。比如 Gemma 3 提供了 QAT 版本（第 29 章） |
| 本地部署的格式 | llama.cpp 的 GGUF，QLoRA 使用的 NF4 等 |

#### 一个值得注意的现象

**训练得越充分的模型，越难量化。** 有研究发现，Llama 3 比 Llama 2 对量化更敏感。Kumar 等（2024）的《Scaling Laws for Precision》也发现，训练 token 越多（即过度训练得越多，第 10 章），训练后再做量化时，损失就越大。一种解释是：每个权重里存储的信息越多，就越经不起精度的损失。

### 34.2 投机解码

#### 思路

decode 受限于显存带宽：大模型每一步都要读一遍全部权重，却只生成一个 token。可是，如果一次送进去 $\gamma + 1$ 个 token，在受带宽限制的情况下，耗时几乎和送 1 个 token 一样，因为权重只需要读一次。所以**投机解码**的做法是（{{fig-ch34-spec}}）：

1. 用一个**便宜的草稿模型**，连续猜出 $\gamma$ 个 token；
2. **大模型调用一次**，同时检查这 $\gamma$ 个 token；
3. 接受其中一部分，被拒绝的位置重新采样。

<figure id="fig-ch34-spec" data-svg="ch34_spec.svg">
<figcaption>投机解码的一轮</figcaption>
</figure>

#### 采样的规则

规则来自 Leviathan 等（2023）和 Chen 等（2023）。设草稿模型在某个位置给出分布 $q$，并从中抽出了 token $x$；大模型在同一位置给出的分布是 $p$。

- **以 $\min\big(1, p(x)/q(x)\big)$ 的概率接受 $x$。**
- 如果拒绝，就从 $\operatorname{normalize}\big(\max(0, p - q)\big)$ 中重新抽一个 token，并丢弃后面所有猜的 token。
- 如果 $\gamma$ 个 token 全部被接受，再从大模型在下一个位置的分布中多抽一个作为奖励。这样，大模型的每次调用至少都能产生 1 个 token。

#### 证明：最终输出的分布恰好是 $p$

记 $\beta = \sum_y \min\big(p(y), q(y)\big)$，它是"草稿被接受"的总概率。输出 token $x$ 的概率由两部分组成：

$$
P(\text{输出 } x) = \underbrace{q(x)\min\Big(1, \frac{p(x)}{q(x)}\Big)}_{\text{草稿猜的是 } x\text{，且被接受}} + \underbrace{(1-\beta)\cdot\frac{p(x) - \min(p(x), q(x))}{1-\beta}}_{\text{草稿被拒绝，重新抽到 } x}
= \min(p(x), q(x)) + p(x) - \min(p(x), q(x)) = p(x).
$$

**结论：输出的分布与直接用大模型采样完全相同，不是近似。** 草稿模型猜得越准，速度越快，但它**永远不会影响输出的质量**。接受率等于 $\beta = \sum\min(p, q) = 1 - \mathrm{TV}(p, q)$，其中 TV 是两个分布之间的总变差距离。

::: experiment
**① 精确性检验。** 两个随机的、各有 10 个取值的分布，按上面的规则执行 20 万次：

| | 10 个取值的概率 |
|---|---|
| 目标分布 $p$ | 0.060, 0.221, 0.000, 0.001, 0.014, 0.124, 0.057, 0.352, 0.046, 0.123 |
| 实际输出频率 | 0.059, 0.221, 0.000, 0.001, 0.015, 0.124, 0.058, 0.353, 0.046, 0.122 |

接受率 0.663（理论值 $\sum\min(p, q) = 0.661$）。
:::

#### 期望加速

设每个草稿 token 被接受的概率都是 $\alpha$，那么大模型每调用一次，期望能产生的 token 数是

$$
E = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha}.
$$

::: experiment
**② 用 bigram 当草稿。** 草稿模型是第 1 章那个只看前一个字符的计数模型，几乎不花计算；目标模型是第 6 章的 GPT。生成 3,000 个字符，采样温度为 1：

| 方式 | 目标模型的调用次数 | 每次调用产生的字符数 | 接受率 | 理论值 $E$ |
|---|---|---|---|---|
| 普通采样 | 3,000 | 1.00 | — | — |
| 投机解码，$\gamma = 2$ | 1,585 | **1.89** | 0.57 | 1.92 |
| 投机解码，$\gamma = 4$ | 1,338 | **2.24** | 0.58 | 2.22 |
| 投机解码，$\gamma = 8$ | 1,249 | **2.40** | 0.59 | 2.36 |

粗略的质量检查：把生成文本的字符频率与普通采样做比较，L1 距离在 0.10 到 0.16 之间；而两次独立的普通采样之间，这个距离是 0.106。
:::

<figure id="fig-ch34-gamma" data-svg="ch34_gamma.svg">
<figcaption>投机解码的期望加速</figcaption>
</figure>

- 实测结果与公式算出的 $E$ 非常吻合（{{fig-ch34-gamma}}）。
- 即使是 bigram 这样粗糙的草稿，也能让目标模型的调用次数减少一半以上。$\gamma$ 再增大，收益很快就递减了，因为连续猜对很多个的概率很低。
- 字符频率的比较中，$\gamma = 8$ 时略高一些，但单次比较的随机波动本来就比较大。**真正保证正确性的，是上面的证明和实验 ①。**

#### 投机解码的变体

| 方法 | 草稿从哪里来 |
|---|---|
| 独立的小模型 | 同一系列中的小模型，比如用 1B 的模型给 70B 的模型打草稿 |
| **Medusa** | 在大模型上额外加几个"预测头"，分别预测后面第 2、3、4 个 token；用树形的注意力一次验证多条候选路径 |
| **EAGLE** 系列 | 训练一个很轻的草稿头，它直接利用大模型内部的隐藏状态来做预测，接受率很高 |
| **MTP**（多 token 预测，DeepSeek-V3） | 训练时就加了预测后续 token 的模块，推理时用它来打草稿。DeepSeek-V3 报告，第二个 token 的接受率在 85% 到 90% 之间，生成速度约提高到原来的 1.8 倍 |
| **从提示中查找** | 直接从提示里复制与当前内容匹配的片段作为草稿。对于修改代码、改写文档这类输出大量重复输入内容的任务，效果特别好 |

**投机解码在大 batch 时收益会变小**：batch 大了以后，decode 越来越受限于算力，"一次多验证几个 token 几乎不额外花时间"这个前提就不成立了。

### 34.3 prefill 与 decode 分离部署

prefill 受限于算力，decode 受限于显存带宽。如果把它们放在同一组 GPU 上，两者会互相干扰：一个长提示的 prefill，会让其他用户的 decode 停顿下来（第 33 章）。**分离部署**的做法是（{{fig-ch34-disagg}}）：用一组 GPU 专门做 prefill，另一组 GPU 专门做 decode；prefill 完成后，通过 RDMA 把 KV cache 传给 decode 那一组；两组可以**分别选择最合适的并行方式和规模**，分别保证 TTFT 和 TPOT 的服务指标。

**代表性的系统**：DistServe（2024）、Splitwise（2024）、Mooncake（Kimi）、NVIDIA Dynamo。

<figure id="fig-ch34-disagg" data-svg="ch34_disagg.svg">
<figcaption>prefill 与 decode 分离部署</figcaption>
</figure>

**DeepSeek-V3 的部署**（第 8 章）：prefill 最少用 32 张 GPU，decode 用 320 张 GPU，两者的专家并行规模不同。DeepSeek 在 2025 年公开过一组线上数据：平均每台 H800 服务器，prefill 阶段每秒处理约 7.37 万个输入 token（含缓存命中），decode 阶段每秒输出约 1.48 万个 token。他们据此估算，理论上的成本利润率高达 545%。

### 34.4 MoE 模型的推理

- **大规模专家并行**：把专家分散到很多张卡上，每张卡只放少数几个专家。这样每个专家都能收到足够多的 token，它的矩阵乘法才能达到较高的效率（第 4 章：矩阵太小，效率就低）。
- **all-to-all 通信**：用 DeepEP 等专门优化过的通信库（第 19 章）。
- **热门专家的负载均衡**：有些专家会被频繁选中，造成负载不均。DeepSeek 的做法是给热门专家**多放几份副本**，并定期根据实际负载重新安排专家的位置。
- **prefill 和 decode 使用不同的专家并行规模**（34.3 节）。

### 34.5 其他常用的手段

- **decode 阶段专用的注意力内核**：batch 小、上下文长的时候，按序列方向把 KV cache 切成多段，并行计算，最后再合并结果（FlashDecoding、FlashInfer 等）；
- **CUDA Graphs**：decode 的每一步都是一串很小的内核，CPU 启动它们的开销不容忽视。把整个 decode 步骤录制成一张图，然后一次性重放（第 22 章）；
- **结构化输出**：用约束解码保证输出符合 JSON 等格式（第 28 章）；
- **长上下文的服务**：KV cache 量化、把 KV cache 转移到 CPU 或硬盘、MLA 和 GQA 这类结构上的改进（第 7、9 章）。

::: keypoints
1. decode 受限于显存带宽，所以只量化权重就能显著加速。实验中，INT8 几乎无损（1.8894 → 1.8895），INT4 分组量化损失很小（1.8984），INT3 损失明显。GPTQ 和 AWQ 改善了低位数量化的精度，SmoothQuant 和 FP8 让激活值也能量化。训练得越充分的模型，越难量化。
2. 投机解码让草稿模型先猜 $\gamma$ 个 token，大模型调用一次就能验证全部。按 $\min(1, p/q)$ 接受，被拒绝时从 $\operatorname{normalize}(\max(0, p-q))$ 中重新抽样，输出分布**恰好**等于 $p$（实测接受率 0.663，理论值 0.661）。
3. 期望每次调用产生 $(1-\alpha^{\gamma+1})/(1-\alpha)$ 个 token。用 bigram 当草稿时，实测 2.24 个，与理论值 2.22 吻合。Medusa、EAGLE、MTP、从提示中查找等变体能提高接受率。大 batch 时收益会下降。
4. prefill 与 decode 分离部署，可以避免两者互相干扰，并让它们分别选择最合适的规模（DeepSeek：32 张卡做 prefill，320 张卡做 decode）。
5. MoE 推理要靠大规模的专家并行、优化过的 all-to-all 和热门专家的副本。其他常用手段还有 decode 专用的注意力内核、CUDA Graphs、KV cache 量化等。
:::
