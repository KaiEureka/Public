### 18.1 带宽层级：本章最重要的一张表

H100 这一代硬件，单方向带宽（{{fig-ch18-bw}}）：

| 连接 | 带宽 | 相对于跨机网络 |
|---|---|---|
| GPU ↔ 自己的显存（HBM） | 3.35 TB/s | 约 67 倍 |
| GPU ↔ 同一台机器的其他 GPU（NVLink） | 450 GB/s | **约 9 倍** |
| GPU ↔ CPU 和网卡（PCIe Gen5 x16） | 约 64 GB/s | 约 1.3 倍 |
| GPU ↔ 其他机器（每张卡一块 400 Gb/s 网卡） | **50 GB/s** | 1 倍 |
| 跨楼栋、跨数据中心 | 更低，延迟也更高 | — |

**机器内部的带宽，大约是跨机器的 9 倍。** 后面所有的并行策略（第 20、21 章）都围绕这一点展开：通信最多的部分放在机器内部，通信较少的部分才跨机器。

### 18.2 一台 8 卡服务器的内部结构

以 HGX/DGX H100 为例（{{fig-ch18-server}}）：

- **NVLink 4**：每张 GPU 有 18 条链路，双向合计 900 GB/s。
- **NVSwitch**：一种交换芯片，让 8 张 GPU 中的任意两张都能以全速直接通信，不需要经过其他 GPU 中转。
- **GPUDirect RDMA**：网卡可以直接读写 GPU 的显存，数据不必先拷贝到 CPU 内存中再发出去。
- **整机功耗**：约 10 kW（DGX H100 的最大功耗是 10.2 kW）。

**更新的形态是整机柜。** GB200 NVL72 把 72 张 Blackwell GPU 和 36 颗 Grace CPU 放进同一个机柜，组成**一个 NVLink 域**，每张 GPU 的 NVLink 带宽为 1.8 TB/s。这样，"高速互联"的范围就从 8 张卡扩大到了 72 张卡，这对 MoE 的专家并行和张量并行非常有利。代价是单个机柜的功耗达到约 120 kW，必须用液冷。

### 18.3 机器之间怎样组网

#### 两种网络技术

| | InfiniBand | RoCE v2（基于以太网的 RDMA） |
|---|---|---|
| 是什么 | 专为高性能计算设计的网络，当前主流是 NDR 400 Gb/s | 在普通以太网上实现 RDMA |
| 优点 | 成熟，延迟低，内置拥塞控制 | 用的是标准以太网设备，供应商多，成本更低 |
| 缺点 | 基本由 NVIDIA 一家供应，价格高 | 需要仔细调优，否则网络拥塞时会丢包 |

**RDMA**（remote direct memory access，远程直接内存访问）是指一台机器可以直接读写另一台机器的内存，不需要经过对方 CPU 的处理，所以延迟低、开销小。

**实例**：Meta 建了两个各 2.4 万卡的集群，一个用 RoCE，一个用 InfiniBand。Llama 3 405B 是在 RoCE 集群上训练出来的，说明两种技术都可以支撑大规模训练。

#### 拓扑：胖树

**胖树**（也叫 Clos 网络）是一种分层的结构：服务器连接到第一层的**叶交换机**，叶交换机再连接到上一层的**脊交换机**，依此类推。如果每一层向上的总带宽等于向下的总带宽，那么任意两台服务器之间都能以满速通信，这叫**无阻塞**或**满对分带宽**。

用 64 口的交换机来算：

- **两层**：每台叶交换机用 32 个口接服务器，另外 32 个口往上接脊交换机。最多可以连接 $64\times32 = 2{,}048$ 个端点。
- **三层**：最多可以连接 $64^3/4 = 65{,}536$ 个端点，大约需要 5,120 台交换机。

#### 轨道优化

把每台服务器的第 0 号 GPU（及其网卡）都接到"第 0 号轨道"的叶交换机上，第 1 号 GPU 都接到第 1 号轨道上，依此类推，这叫**轨道优化**（rail-optimized，见{{fig-ch18-rail}}）。

为什么这样接？训练时，跨机器通信的大多是**各台机器上编号相同的 GPU**（第 20、21 章会讲原因）。它们都挂在同一条轨道上，只需要经过一跳就能到达。如果需要和其他编号的 GPU 通信，就先通过 NVLink 把数据转给本机上编号对应的那张 GPU，再走网络。NVIDIA 的通信库会自动完成这一步。

#### 带宽收敛

如果某一层向上的带宽小于向下的带宽，就叫**收敛**（oversubscription）。收敛可以省下大量交换机和光模块的费用，代价是跨区域的通信变慢。Llama 3 的集群就是这样设计的：每 3,072 张 GPU 组成一个 pod，pod 内部是满带宽的；8 个 pod 之间的连接按 1:7 收敛。

所以，**并行任务在集群里怎样摆放，必须和网络拓扑相匹配**：通信最密集的部分（张量并行）放在一台机器内部，次密集的部分放在一个 pod 内部，通信最少的部分才跨 pod（第 21 章）。

#### 一个省钱的设计：DeepSeek 的萤火二号

DeepSeek 在 2024 年发表了他们的集群论文。萤火二号有约 1 万张 **PCIe 版本**的 A100，采用两层胖树，每台机器的网卡数量也比 DGX 少。他们报告说，这套集群用约一半的成本，达到了 DGX-A100 集群约 80% 的性能，能耗也更低。代价是带宽更小，所以必须在软件上下功夫来弥补，比如自研的通信库，以及后来 DeepSeek-V3 中让计算和通信重叠的设计。

**出口管制**也影响了硬件的选择。美国限制向中国出口 H100 之后，NVIDIA 推出了 H800，它的 NVLink 带宽从 900 GB/s 降到了 400 GB/s（双向）。DeepSeek-V3 正是在 H800 上训练的，这也解释了为什么他们特别重视节省通信。

#### 其他体系

**Google TPU** 用芯片之间的直连链路组成三维环形网络（torus），并配合光交换机来灵活地重新组网。**AWS Trainium** 使用 AWS 自己的 EFA 网络。

### 18.4 存储

| 用途 | 特点 | 常见方案 |
|---|---|---|
| 读取训练数据 | 顺序读取，需要的带宽不算特别高，但要稳定 | 对象存储（如 S3），加上本地 NVMe 缓存 |
| **保存和读取检查点** | **数据量巨大，而且是突发性的**。保存期间训练可能要暂停，所以速度直接影响 GPU 的利用率 | 并行文件系统：Lustre、GPFS、WEKA、VAST；DeepSeek 在 2025 年开源了 3FS |
| 日志、代码、评测结果 | 小文件多 | 普通的网络文件系统 |

**检查点有多大？** 以 405B 的模型为例：BF16 权重约 0.8 TB；加上 FP32 主权重、Adam 的 $m$ 和 $v$（每个参数 12 字节），约 4.9 TB；**合计约 5.7 TB**。

Meta 为 Llama 3 使用的存储系统容量为 240 PB，持续写入带宽约 2 TB/s，峰值约 7 TB/s。即便如此，保存一次检查点仍然需要优化，比如异步保存，以及每张 GPU 只保存自己负责的那一部分（第 23 章）。

### 18.5 供电和散热

#### 功耗估算：16,384 张 H100

| 项目 | 计算 | 功耗 |
|---|---|---|
| 服务器 | 2,048 台 × 约 10 kW | 约 20.5 MW |
| 加上网络与存储（约 10%） | | 约 22.5 MW（IT 设备总功耗） |
| 乘以 PUE（约 1.2） | | **约 27 MW**（整个设施的总功耗） |

**PUE**（power usage effectiveness，电能使用效率）等于数据中心的总用电量除以 IT 设备的用电量，多出来的部分主要花在制冷上，好的数据中心在 1.1 到 1.3 之间。**电费**：$27\ \text{MW}\times8{,}760\ \text{小时}\times0.07$ 美元/kWh，约为**每年 1,700 万美元**。电价因地区差别很大。

#### 散热

风冷的机柜功率一般在 40 kW 左右，大约能放 4 台 H100 服务器；GB200 NVL72 这样约 120 kW 的机柜，必须用液冷。机房的供电和制冷能力，往往是建设集群时的瓶颈，比买到 GPU 还难。

#### 一个特殊问题：功率剧烈波动

训练时，所有 GPU 几乎同时进入计算阶段，又同时进入通信阶段，所以整个集群的功耗会同步地大起大落。Llama 3 的论文提到，整个数据中心的功耗会瞬间波动**几十兆瓦**，这对电网是很大的挑战。缓解的办法包括在软件中插入"平滑负载"，以及使用新一代硬件自带的功率平滑功能。

### 18.6 成本：买还是租

以下是 2024 到 2025 年的市场行情，**只作数量级参考**：

| 项目 | 估算 |
|---|---|
| H100 服务器（8 卡） | 每台约 25 万到 35 万美元 |
| 按每张卡"全包"计算（服务器、网络、存储，不含机房） | 约 4 万到 5 万美元 |
| 16,384 张卡的硬件 | **约 7 亿美元** |
| 网络（网卡、交换机、光模块） | 通常占硬件成本的 10% 到 20%，其中光模块占了很大一部分 |
| 自建机房 | 每 MW 约 1,000 万美元量级，也可以租用现成的机房 |
| 云上租用 H100 | 2025 年大约每卡每小时 2 到 3 美元，比 2023 年的高点下降了很多 |

**怎样选？** **租用**灵活，不用等建设周期，适合需求短期或不确定的情况；但长期来看总价更高，而且很难租到上万张卡、并且全部在同一个高速网络里的规模。**自建**长期成本低，可以按自己的需要定制（比如 DeepSeek 的做法）；但前期投入巨大，建设周期长，还要承担硬件很快过时的风险。

**规模的参考**：Meta 在 2024 年的目标是拥有约 35 万张 H100；据报道，xAI 用了 122 天就建成了一个 10 万卡的集群。

### 18.7 可靠性：规模越大，故障越频繁

Llama 3 405B 在 1.6 万张 H100 上训练了 54 天，期间一共中断了 466 次，其中 419 次是意外中断，**平均约每 3 小时一次**。约 78% 的意外中断，确认或怀疑是硬件问题，排在前面的是 GPU 本身的故障（约 30%）和显存故障（约 17%）。尽管如此，有效训练时间仍然超过了 90%。

第 23 章会专门讲怎样应对这些故障。这里先记住一个规律：**单个部件出故障的概率很小，但部件数量一多，整体出故障的频率就会很高。**{{fig-ch18-fail}} 按 Llama 3 的中断率做了外推。

### 18.8 采购、验收与软件栈

**采购**：提前很久下单，新一代 GPU 的交货周期可能长达数月；选择 GPU 代际，新一代性能更好，但供应少、软件不够成熟；选择供应商，服务器厂商（Supermicro、Dell、HPE 等）或者专门出租 GPU 的云厂商（CoreWeave、Lambda 等）；关注出口管制等政策。

**验收与老化测试**（正式训练之前必须做）：

- 用 GPU 诊断工具（比如 NVIDIA 的 DCGM）测试每张卡的算力、显存和温度；
- 用 nccl-tests 测试**全部节点之间**的通信带宽，找出偏慢的链路和节点；
- 检查网线和光模块的误码率；
- 跑一段时间的满负载老化测试，让早期故障的部件先暴露出来；
- 把坏节点和慢节点替换或隔离掉。**新集群里总会有一些有问题的部件。**

**软件栈**：驱动程序、CUDA、NCCL（NVIDIA 的集合通信库，第 19 章）；容器运行环境；作业调度系统（Slurm 或 Kubernetes）；监控系统（DCGM 加 Prometheus 等）；自动健康检查，即每个作业开始之前，先检查分配到的节点是否正常。

::: keypoints
1. 带宽从近到远依次下降：显存 3.35 TB/s，NVLink 450 GB/s，跨机网络 50 GB/s（均为单方向）。**机器内部的带宽约是跨机的 9 倍**，这决定了后面所有并行策略的设计。
2. 一台 8 卡服务器内部，GPU 之间通过 NVSwitch 全速互联，每张卡配一块 400 Gb/s 网卡。GB200 NVL72 把高速互联的范围扩大到了 72 张卡。
3. 机器之间用 InfiniBand 或 RoCE 组成胖树网络，采用轨道优化接线；上层通常会做收敛来省钱，所以并行任务的摆放要和拓扑相匹配。
4. 存储系统要能快速写入几 TB 的检查点。一个 1.6 万卡的集群约需 27 MW 电力，每年电费约 1,700 万美元，高密度机柜需要液冷。
5. 1.6 万卡规模下，平均约每 3 小时就会发生一次故障。验收测试和自动健康检查是正式训练的前提。
