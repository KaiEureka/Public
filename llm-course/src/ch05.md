## 第 5 章　分词器 {#ch5 .chapter}

::: goals
- 说清文本怎样变成模型能处理的整数序列；
- 理解为什么主流方案是"字节级 BPE"；
- 亲手实现 BPE 的训练和编码；
- 理解词表大小的取舍，以及分词带来的各种怪现象：数不清字母、算术困难、不同语言成本不同。
:::

### 5.1 为什么要分词：三种切法

模型只认识整数。**分词器**（tokenizer）负责两件事：把文本转换成整数序列（**编码**），以及把整数序列还原成文本（**解码**）。每个整数对应的那段文本叫一个 **token**，所有 token 的集合叫**词表**。

切分的粒度有三种选择（{{fig-ch05-split}} 用同一句话做了对比）：

| 切法 | 优点 | 缺点 |
|---|---|---|
| **按字符**（第 1、2 章的做法） | 词表很小，任何文本都能表示 | **序列很长**。模型处理每个 token 都要花约 $2N$ FLOP，序列越长，处理同样的文本就越贵，能放进上下文的内容也越少，生成时要走的步数也越多 |
| **按单词** | 序列短 | 词表会无限膨胀（run、runs、running、人名、拼写错误……）。没见过的词（OOV，out-of-vocabulary）只能统一标成"未知"；run 和 running 之间也没有任何共享 |
| **按子词**（主流） | 常见词整个作为一个 token，罕见词拆成几块，任何字符串都能表示 | 需要一个算法来决定怎样切，也就是本章的 BPE |

<figure id="fig-ch05-split" data-svg="ch05_split.svg">
<figcaption>同一句话的三种切法。子词切分让常见词保持完整，罕见词拆成几个常见片段</figcaption>
</figure>

例如，莎士比亚验证集共 111,540 个字符，用本章训练的、词表大小为 8,192 的子词分词器切分后，只有 31,038 个 token，**序列缩短到原来的约 1/3.6**。

### 5.2 先弄清"字符"是什么：Unicode 与 UTF-8

- **Unicode** 给世界上每个字符分配了一个编号，叫**码点**。例如 `A` 是 U+0041，`中` 是 U+4E2D。目前已分配的字符约有 15 万个。
- **UTF-8** 是把码点转换成字节的规则。英文字母和常见标点占 1 个字节，绝大多数汉字占 3 个字节，emoji 占 4 个字节（{{fig-ch05-utf8}}）。

<figure id="fig-ch05-utf8" data-svg="ch05_utf8.svg">
<figcaption>从字符到字节：英文字母占 1 个字节，é 占 2 个，汉字占 3 个，emoji 占 4 个</figcaption>
</figure>

"孟子見梁惠王"的 UTF-8 字节如下：

```
孟         子         見         梁         惠         王
E5 AD 9F   E5 AD 90   E8 A6 8B   E6 A2 81   E6 83 A0   E7 8E 8B
```

**为什么要在字节上做分词？** 把 256 种可能的字节值作为初始词表，**任何语言、任何 emoji、甚至乱码都能表示，永远不会出现"未知"**。如果以 Unicode 字符作为初始单位，初始词表就要有 15 万个符号。这也呼应了第 1 章的结论：样本空间 $\Omega$ 中的元素，本质上是字节串。

### 5.3 BPE 算法

**BPE**（Byte Pair Encoding，字节对编码）原本是一种压缩算法（Gage，1994），2016 年被 Sennrich 等人用到自然语言处理中。思路非常简单：

> 从 256 个字节开始。在训练语料中找出**出现次数最多的相邻一对 token**，把它们合并成一个新 token，记下这次合并。重复这个过程，直到词表达到预定的大小。

#### 手算一个小例子

假设语料中只有这些词：low 出现 5 次，lower 2 次，newest 6 次，widest 3 次。

| 轮次 | 统计相邻对（按出现次数加权） | 合并 |
|---|---|---|
| 1 | e·s：6 + 3 = **9**，s·t：9，w·e：8，l·o：7，…… | e + s → `es` |
| 2 | es·t：**9**，l·o：7，o·w：7，…… | es + t → `est` |
| 3 | l·o：**7**，o·w：7，…… | l + o → `lo` |
| 4 | lo·w：**7**，…… | lo + w → `low` |

出现次数相同时任选一个即可。到这一步（{{fig-ch05-bpe}}），newest 被切成 n|e|w|est，而训练语料中没有的 lowest 也能切成 low|est。

<figcaption>手算 BPE 的四轮合并（数据同上表）。深色是这一轮新合并出的 token，浅蓝是之前合并出的 token</figcaption>
</figure>

#### 在莎士比亚文本上实际学到的前 15 次合并

在莎士比亚训练集上训练字节级 BPE，前 15 次合并（括号里是合并时这一对出现的次数）：

| 序号 | 合并 | 序号 | 合并 | 序号 | 合并 |
|---|---|---|---|---|---|
| 1 | `' '+'t'` → `' t'`（21,591） | 6 | `' '+'m'` → `' m'`（9,581） | 11 | `' t'+'he'` → `' the'`（7,886） |
| 2 | `'h'+'e'` → `'he'`（16,418） | 7 | `'i'+'n'` → `'in'`（9,531） | 12 | `'n'+'d'` → `'nd'`（7,832） |
| 3 | `' '+'a'` → `' a'`（12,054） | 8 | `' '+'w'` → `' w'`（9,469） | 13 | `':'+'\n'` → `':\n'`（7,662） |
| 4 | `'o'+'u'` → `'ou'`（11,506） | 9 | `'r'+'e'` → `'re'`（8,863） | 14 | `' '+'b'` → `' b'`（7,652） |
| 5 | `' '+'s'` → `' s'`（10,960） | 10 | `'h'+'a'` → `'ha'`（8,723） | 15 | `'i'+'s'` → `'is'`（6,766） |
:::

第 13 次合并 `':\n'` 对应剧本里 "All:" 这样的台词格式。注意，**空格被粘在了单词的前面**：` the`（前面带空格）、`the`（在行首）和 `The` 是三个不同的 token。同一个词，因为位置或大小写不同，会对应完全不同的 token。

#### 编码与解码

- **编码新文本**：按合并被学到的先后顺序来应用，先学到的优先级高，这个顺序叫 **rank**。对每个片段，反复找出相邻对中 rank 最小的那一对并合并，直到没有可合并的对为止。
- **解码**：把每个 token 对应的字节拼起来，再按 UTF-8 还原成文字。

#### 代码

下面是朴素版本，便于阅读（实验中运行的是增量更新的高效版本，见附录 C）：

```python
def train_bpe(words, vocab_size):            # words: {字节序列(tuple): 出现次数}
    merges = {}                               # (a, b) -> 新 token 的 id
    for new_id in range(256, vocab_size):
        pairs = Counter()
        for w, c in words.items():
            for p in zip(w, w[1:]): pairs[p] += c
        if not pairs: break
        best = max(pairs, key=pairs.get)      # 出现次数最多的相邻对
        merges[best] = new_id                 # id 按学到的顺序递增，所以 id 本身就是 rank
        words = {merge(w, best, new_id): c for w, c in words.items()}
    return merges

def merge(w, pair, new_id):                   # 把 w 中出现的所有 pair 替换成 new_id
    out, i = [], 0
    while i < len(w):
        if i + 1 < len(w) and (w[i], w[i+1]) == pair: out.append(new_id); i += 2
        else: out.append(w[i]); i += 1
    return tuple(out)

def encode_word(b, merges):                   # b: 一个预切分片段的字节（见 5.4 节）
    sym = list(b)
    while len(sym) > 1:
        rank, i = min((merges.get(p, inf), i) for i, p in enumerate(zip(sym, sym[1:])))
        if rank == inf: break                 # 没有可用的合并了
        sym[i:i+2] = [rank]
    return sym
```

### 5.4 预切分

如果直接在整段文本上跑 BPE，它会跨越单词和标点做合并，学出 `dog.`、`dog!`、`dog?` 这样各占一个名额的 token，白白浪费词表。

**预切分**（pre-tokenization）的做法是：先用**正则表达式**（一种描述字符串模式的规则语言）把文本切成片段，BPE 只在片段**内部**做合并。GPT-4 和 Llama 3 用的是同一套规则，大致含义是：

1. 英文缩写后缀单独成段：`'s` `'t` `'re` `'ll` 等；
2. 一个单词，前面可以带一个非字母字符，通常是空格；
3. 数字，最多 3 位一组；
4. 一串标点，前面可以带一个空格；
5. 换行和其他空白字符。

效果如下：

```
输入：First Citizen:\nWe know't, we know't. Price: 12345 dollars!
片段：'First' | ' Citizen' | ':\n' | 'We' | ' know' | "'t" | ',' | ' we' | ' know' | "'t" | '.'
      | ' Price' | ':' | ' ' | '123' | '45' | ' dollars' | '!'
```

### 5.5 词表大小

|---|---|---|
| 256（只有原始字节） | 111,540 | 1.00 |
| 512 | 55,963 | 1.99 |

<figure id="fig-ch05-vocab" data-svg="ch05_vocab.svg">
<figcaption>词表越大，每个 token 平均包含的字节越多，序列越短，但增长越来越慢</figcaption>
</figure>

同一句话在两种词表下的切分：

```
V=512 ： To| be|,| |or| not| to| be|:| that| is| the| |q|u|est|ion|.
         M|et|h|in|k|s| the| l|ad|y| d|oth| pr|ot|est| to|o| m|u|ch|.
V=8192： To| be|,| or| not| to| be|:| that| is| the| question|.
         Methinks| the| lady| doth| protest| too| much|.
```
:::

**取舍**：

| 词表变大的影响 | 说明 |
|---|---|
| 好处：序列更短 | 处理同样文本的计算量更少，上下文窗口能装下更多内容，生成需要的步数也更少 |
| 代价：参数更多 | embedding 表和输出层都是 $V\times d$ 的矩阵，$d$ 是模型的向量维度。Llama 3 8B 的 $V = 128{,}256$，$d = 4096$，每个矩阵约 5.25 亿参数，两个合计约 **10.5 亿，占全部 80 亿参数的 13%** |
| 代价：每个 token 更罕见 | $V = 8192$ 时，有 **5,466 个 token 在训练文本里出现不到 10 次**，它们的 embedding 几乎得不到训练。还有不少名额被花在了 ` Northumberland`、`NORTHUMBERLAND` 这样的人名上 |
| 收益递减 | 从 256 到 512，序列长度减半；从 4,096 到 8,192，只缩短了 10%（{{fig-ch05-vocab}}） |

小模型对参数开销更敏感，常用的办法是让输入 embedding 和输出层**共享同一个矩阵**，叫 **tied embeddings**，GPT-2 就是这样做的。

**实际模型的词表大小**：

| 模型 | 词表大小 |
|---|---|
| GPT-2 | 50,257 |
| Llama 2 | 32,000 |
| GPT-4 | 约 10 万 |
| Llama 3 | 128,256 |
| DeepSeek-V3 | 约 12.8 万 |
| Qwen2.5 | 约 15.2 万 |
| GPT-4o | 约 20 万 |
| Gemma | 约 25.6 万 |

词表有越来越大的趋势，主要原因有两个：一是要覆盖多种语言和代码；二是对大模型来说，embedding 在总参数中的占比很小。

### 5.6 多语言：同一个分词器对不同语言并不公平

| 分词器 | 在《孟子》（未参与训练）上，每个汉字需要几个 token | 在英文验证集上，每个 token 平均几个字节 |
|---|---|---|
| 只用莎士比亚训练 | **2.97**，基本就是每个汉字的 3 个字节各占一个 token | 3.59 |
| 莎士比亚 + 唐诗混合训练 | **1.16** | 3.37（变差了） |

这对使用者意味着什么？对同一段中文，以英文为主的分词器切出的 token 数约是照顾了中文的分词器的 2.6 倍（2.97 对 1.16，见{{fig-ch05-zh}}）。于是：

<figcaption>训练语料决定了分词器对哪种语言更“省”：加入唐诗后，中文的 token 数大幅下降，英文只损失一点</figcaption>

- 按 token 计费的 API，费用约为 2.6 倍；
- 上下文窗口能装下的内容只有约 40%；
- 模型还得先学会怎样把字节碎片拼成汉字。

而且词表的名额是共享的：给中文多分一些，英文的压缩率就会下降。**所以，用什么数据来训练分词器，是一个需要认真权衡的决定。** 通常的做法是用一份与预训练数据配比一致的样本来训练。

### 5.7 分词带来的怪现象

#### 数不清字母

用 $V = 8192$ 的分词器切分 strawberry：

```
' strawberry'  →  straw|ber|ry
' Strawberry'  →  St|raw|ber|ry
' STRAWBERRY'  →  S|TR|A|W|BER|RY
```

模型看到的是 token，不是字母。它必须**记住**每个 token 是怎样拼写的，才能回答"strawberry 里有几个 r"这类问题。这就是大模型经常数错字母的根源。同一个词只是大小写不同，就会变成完全不同的 token 序列。

#### 算术

莎士比亚文本里数字很少，所以 ` 1234567` 被切成了 ` |1|2|3|4|5|6|7`：空格单独一个，然后每个数字一个。GPT-4 和 Llama 3 风格的预切分会把数字**从左往右每 3 位一组**切开：1234567 变成 123|456|7。这种分组与数位（个、十、百、千……）对不齐，同一个数位在不同长度的数字里会落在不同的位置，算术就更难学。

也有别的做法：Llama 1/2 把每一位数字都单独切成一个 token；也有研究发现，从右往左按 3 位分组对算术更友好。

#### 故障 token

2023 年，人们发现 GPT-2/3 的词表里有一个 token 是 `SolidGoldMagikarp`，这是一个 Reddit 用户名。它在训练分词器的数据里很常见，所以进了词表；但在训练模型的数据里几乎没有出现过，所以它的 embedding 基本没训练过，模型一遇到它就行为怪异。**教训：分词器的训练数据和模型的训练数据要尽量一致，事后还要检查有没有训练不足的 token。**

#### 提示词末尾的空格

正常文本里，` the` 是一个 token（空格在前）。如果用户的提示词以 `the ` 结尾（空格在后），这个空格就会被单独切出来。这在训练数据中很少见，模型接下来的预测会变差。

#### 切分方式不唯一

同一个字符串可以有很多种切法，比如 the 可以切成 t|h|e、th|e 或者 the，但分词器永远只输出其中一种标准切法。第 1 章的选读框讲过，严格地说，一个字符串的概率应该是所有切法的概率之和，实践中只用标准切法来近似。

### 5.8 特殊 token

有一类 token 不是从普通文本里切出来的，而是由程序专门插入的：

- `<|endoftext|>`：文档结束，也就是第 1 章的 ⟨eos⟩。模型正是靠预测它来决定什么时候停止生成。
- 文档开始标记（BOS）、填充标记（padding）。
- 对话格式标记，比如 `<|im_start|>` 和 `<|im_end|>`，用来标出"这是用户说的、那是助手说的"（第 24 章）。

**安全上要注意**：如果用户输入的文本里恰好包含字符串 `<|endoftext|>`，必须把它当作普通文字来编码，不能转换成特殊 token，否则用户就可以伪造控制信号。

### 5.9 其他算法

- **WordPiece**（BERT 使用）：和 BPE 类似，但选择合并哪一对时，依据的是"合并后对数据似然的提升"，而不是出现次数。
- **Unigram LM**（在 SentencePiece 库中实现）：反过来做，先准备一个很大的词表，再逐步删掉最不重要的 token。
- **SentencePiece**：一个分词工具库，把空格当作普通字符（显示为 ▁）来处理。Llama 1/2 用的就是它的 BPE 模式。
- **不用分词器**：直接在字节上建模，比如 ByT5，以及 Meta 在 2024 年提出的 Byte Latent Transformer（它会动态地把字节分组）。这还是研究前沿。

**当前的主流**：字节级 BPE，加 GPT-4 风格的预切分规则，词表大小在 10 万到 26 万之间。

### 5.10 分词器在整个流水线中的位置

{{fig-ch05-pipeline}} 把一段文本从原始字符到模型输入的过程画了出来。

1. **最先训练，然后冻结。** 在预训练开始前，用一份代表性的数据样本训练分词器。之后不能再改，因为一改，模型的 embedding 就对不上了，只能重新训练，或者做代价很高的适配。所以这是一个**锁定期很长的决定**。
2. **提前把全部语料转成 token。** 整个预训练语料会事先编码成存放 token id 的二进制文件。数据集的规模也按 token 计算，比如"15T token"。
3. **评估分词器时要看**：各种语言和领域（代码、数学）的压缩率；有多少 token 训练不足；编码再解码后能否完全还原原文。

<figure id="fig-ch05-pipeline" data-svg="ch05_pipeline.svg">
<figcaption>一段文本进入模型的过程：预切分 → BPE 切分并查出 id → 查 embedding 表得到向量</figcaption>

::: keypoints
1. 子词切分在"序列长度"和"词表大小"之间取得平衡。在字节上做分词，任何文本都能表示，不会出现未知字符。
2. BPE 从 256 个字节开始，反复合并出现最多的相邻对。编码时按学到的先后顺序应用这些合并。
3. 预切分防止 BPE 跨越单词和标点做合并，主流是 GPT-4 和 Llama 3 用的那套正则规则。
4. 词表越大，序列越短，但参数更多、罕见 token 更多，而且收益递减。主流大模型的词表在 10 万到 26 万之间。
5. 分词器决定了不同语言的成本和效率，也是数不清字母、算术困难、故障 token 这些现象的根源。它一旦确定就很难更改。
:::
