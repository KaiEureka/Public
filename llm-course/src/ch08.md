## 第 8 章　MoE：混合专家模型 {#ch8 .chapter}

- 理解细粒度专家与共享专家的设计；
- 根据配置算出 MoE 模型的总参数和激活参数；
- 知道 MoE 给训练系统和推理系统带来了哪些新麻烦。

### 8.1 动机：把参数量和计算量分开

**稠密模型**（前面各章讲的都是这种）在处理每个 token 时都要用到全部参数，所以每个 token 的计算量约为 $2N$ FLOP。参数越多，模型能储存的知识越多，但每个 token 的计算也越贵。

**MoE**（mixture of experts，混合专家）的想法是：把一个 MLP 换成很多个 MLP，每个叫一个**专家**（expert），每个 token 只选其中少数几个专家来处理。

- **总参数**很大，决定了模型的容量；
- **激活参数**，即每个 token 实际用到的参数，决定了计算量。

第 0 章说 $6ND$ 中的 $N$ 要用激活参数量，原因就在这里。DeepSeek-V3 总共有 6,710 亿参数，每个 token 只激活其中的 370 亿。

**已发表的证据**：

| 工作 | 结论 |
|---|---|
| Switch Transformer（Fedus 等，2021） | 每个 token 的计算量相同时，预训练速度最多比稠密的 T5-Base 快 7 倍 |
| Mixtral 8×7B（2023） | 总参数 467 亿，激活参数 129 亿，在多数基准上达到或超过 Llama 2 70B |
| DeepSeekMoE 16B（2024） | 激活参数 28 亿，用大约 40% 的计算量达到 LLaMA2 7B 的水平 |

**代价**：全部参数都要放在显存里；专家分布在不同的 GPU 上，需要大量通信；系统也更复杂。这些放在 8.7 节讲。

MoE 的思想很早就有了（Jacobs 等，1991）。2017 年 Shazeer 等人在 LSTM 上做出了 1,370 亿参数的稀疏门控 MoE，此后 GShard（2020）和 Switch Transformer（2021）把它带进了 Transformer。

**路由器**（router，也叫 gate）是一个很小的线性层，形状为 $d\times E$，$E$ 是路由专家的数量。对每个 token，计算过程是：

$$
\begin{aligned}
s_i &= \sigma(x\cdot w_i)\ \text{或 softmax} && \text{给每个专家打一个"亲和度"分}\\
S &= \operatorname{top-}k(\{s_i\}) && \text{选出分数最高的 } k \text{ 个专家}\\
g_i &= s_i \Big/ \textstyle\sum_{j\in S} s_j && \text{在被选中的专家之间重新归一化，得到门控权重}\\
y &= \textstyle\sum_{i\in S} g_i\,\operatorname{Expert}_i(x) && \text{每个专家都是一个 SwiGLU MLP}
\end{aligned}
$$

```python
def moe_forward(x, router, experts, k):              # x: (n_tok, d)，这一批里的所有 token
    s = torch.sigmoid(x @ router)                     # (n_tok, E) 亲和度
    topv, topi = s.topk(k, dim=-1)                    # 每个 token 选 k 个专家
    g = topv / topv.sum(-1, keepdim=True)             # 门控权重
    y = torch.zeros_like(x)
    for e, expert in enumerate(experts):              # 按专家处理：把选中它的 token 收集起来一起算
        tok, slot = (topi == e).nonzero(as_tuple=True)
        if len(tok): y.index_add_(0, tok, g[tok, slot, None] * expert(x[tok]))
    return y
```

**路由器是怎样学会分配的？** 专家的输出要乘以门控权重 $g$，而 $g$ 是由路由器的分数算出来的，所以梯度能流回路由器。如果某个专家处理某类 token 效果好，路由器给它的分数就会被推高。没被选中的专家，在这个 token 上收不到梯度。

### 8.3 核心难题：负载均衡

#### 路由坍缩

训练初期，如果某个专家碰巧稍微好一点，它就会被分到更多 token，于是训练得更充分、变得更好，然后又被分到更多 token。这是一个"富者愈富"的正反馈，最终少数专家包揽了大部分 token，其余专家几乎得不到训练。这叫**路由坍缩**。后果有两个：

- **质量上**：大量参数被浪费了；
- **硬件上**：专家分布在不同的 GPU 上（8.7 节），过载的 GPU 成了瓶颈，其他 GPU 只能等着。这种拖慢整体进度的节点叫**掉队者**（straggler）。

#### 专家容量与丢弃 token

早期方案（GShard、Switch）给每个专家设定一个**容量**上限，即每批最多处理多少个 token：

$$
\text{容量} = \text{容量系数} \times \frac{\text{每批 token 数}\times k}{E}, \qquad \text{容量系数通常取 } 1.0\text{–}1.25.
$$

超出容量的 token 会被**丢弃**（token dropping）：这个 token 不经过任何专家，只沿残差连接直接传下去。

#### 辅助损失

Switch Transformer 在训练目标上额外加了一项，专门惩罚负载不均：

$$
\mathcal{L}_{\text{aux}} = \alpha\cdot E\cdot\sum_{i=1}^{E} f_i P_i,
$$

其中 $f_i$ 是这一批中被分给专家 $i$ 的 token 比例（由 top-$k$ 的选择决定，不可导），$P_i$ 是路由器给专家 $i$ 的平均概率（可导）。

- 为什么用 $f$ 乘以 $P$？$f$ 体现的是实际负载，但它来自 top-$k$ 这个离散的选择，无法求导；$P$ 可以求导。两者相乘之后，梯度会把过载专家的 $P$ 往下压。
- 负载完全均匀时 $f_i = P_i = 1/E$，求和等于 $1/E$，$\mathcal{L}_{\text{aux}} = \alpha$。负载越偏，$\mathcal{L}_{\text{aux}}$ 越大。
- $\alpha$ 通常取 0.01。

**这个方法的两难**：辅助损失的梯度会干扰语言建模这个主目标。$\alpha$ 设得太大，模型质量下降；设得太小，又压不住负载不均。这正是 DeepSeek 想要解决的问题。

另外，ST-MoE（2022）提出了 **router z-loss**：惩罚路由器 logits 的 logsumexp 值的平方，防止 logits 过大，以提升训练稳定性。

### 8.4 DeepSeek-V3：不用辅助损失的负载均衡

这个方法来自 Wang 等人 2024 年的论文。做法是给每个专家加一个偏置 $b_i$，**它只用来决定选哪些专家，不参与计算门控权重**：

$$
\begin{aligned}
&\text{选专家：按 } s_i + b_i \text{ 取 top-}k; \qquad \text{门控权重：} g_i = s_i \Big/ \textstyle\sum_{j\in S} s_j \;(\text{用原始分数 } s\text{，不含 } b);\\
&\text{每步训练之后：专家 } i \text{ 过载则 } b_i \leftarrow b_i - \gamma\text{，闲置则 } b_i \leftarrow b_i + \gamma.
\end{aligned}
$$

$b$ 不是靠梯度学出来的，而是按规则调节的，所以它**不会干扰主目标的梯度**。模型的输出始终由学到的亲和度 $s$ 决定，$b$ 只是在专家之间"调剂客流"。DeepSeek-V3 在训练的前 14.3T 个 token 中使用 $\gamma = 0.001$，最后 500B 个 token 设为 0，即停止调节。

此外，DeepSeek-V3 还保留了一个系数极小（$\alpha = 0.0001$）的**序列级**辅助损失，防止在单条序列内部出现极端的不均衡。它在训练和推理时都**不丢弃任何 token**。

### 8.5 细粒度专家与共享专家

这两个设计来自 DeepSeekMoE（2024）。

**细粒度专家。** 把每个专家拆成 $m$ 个更小的专家（隐藏层宽度变为原来的 $1/m$），同时每个 token 选的专家数也乘以 $m$。这样计算量不变，但可选的专家组合数暴增：

- 16 个专家选 2 个：$\binom{16}{2} = 120$ 种组合；
- 每个专家拆成 4 个，变成 64 个专家选 8 个：$\binom{64}{8} \approx 44$ 亿种组合。

组合越多，模型越能为不同的 token 拼出合适的专家组合，专家之间的分工也更精细。

**共享专家。** 设置一个或几个**每个 token 都必须经过**的专家，用来承载通用知识（{{fig-ch08-fine}}）。这样，那些被路由的专家就不必各自重复存储这些通用内容，可以更专注地分工。这是一种设计选择，并非所有模型都采用，比如 Qwen3 的 MoE 就没有共享专家。

### 8.6 参数核算：DeepSeek-V3

DeepSeek-V3 的配置：$d = 7168$，共 61 层，**前 3 层是稠密层，其余 58 层是 MoE 层**。每个专家是隐藏层宽 2,048 的 SwiGLU。

| 部分 | 计算 | 参数量 |
|---|---|---|
| 每个专家 | $3\times7168\times2048$ | 4,404 万 |
| 每个 MoE 层（总量） | $(256 + 1)\times4{,}404$ 万 | 113 亿 |
| 每个 MoE 层（激活量） | $(8 + 1)\times4{,}404$ 万 | 3.96 亿 |
| 58 个 MoE 层 | | 总量 6,565 亿，激活 230 亿 |

再加上注意力（MLA）、前 3 个稠密层和嵌入层，总参数约 6,710 亿，激活参数约 370 亿，与官方数字一致。可以看到，**模型的绝大部分参数都在专家里，但每个 token 只用到其中约 3.5%。**

### 8.7 系统层面的挑战

#### 显存

全部 6,710 亿参数都必须放在显存里。即使用 FP8 存储，光权重就要约 671 GB。训练时还要加上梯度和优化器状态，所以必须把模型切分到大量 GPU 上。

#### 专家并行与 all-to-all 通信

**专家并行**（expert parallelism，EP）是把不同的专家放在不同的 GPU 上。每经过一个 MoE 层，都要做两次 **all-to-all** 通信（{{fig-ch08-a2a}}）：先把每个 token 发到它所选专家所在的 GPU 上（分发），算完之后再把结果发回原来的 GPU（汇总）。all-to-all 的意思是每块 GPU 都要给其他每一块 GPU 发送一份不同的数据（第 19 章）。


第 4 章讲过，跨机器的网络带宽（每块网卡约 50 GB/s）远低于同一台机器内 GPU 之间的 NVLink（900 GB/s），所以通信很容易成为瓶颈。DeepSeek-V3 用了两个办法来应对：


- **限制每个 token 最多只能发往 4 台机器**（节点受限路由）：路由器先给每台机器打分（这台机器上得分最高的 2 个专家的分数之和），选出得分最高的 4 台，再只在这 4 台机器上的专家里选 top-8。所以不会出现“超过 4 台”的情况，代价只是偶尔选不到第 5 台机器上的某个专家，只能退而选次优的；
- 让计算和通信在时间上重叠进行（第 21 章）。

<figure id="fig-ch08-a2a" data-svg="ch08_a2a.svg">
<figcaption>专家并行的 all-to-all 通信：每块 GPU 把手上的 token 按路由结果发往各个专家所在的 GPU（示意）</figcaption>
</figure>

#### 推理

- 只处理一条请求时（batch = 1），每个 token 只需要读取被激活的专家，速度很快。
- 但为了提高吞吐量，实际服务时会把很多请求打包成一个大 batch（第 4 章）：每一步，batch 里的每条请求各自产生自己的下一个 token，这些 token 叠成一个矩阵一起经过模型。batch 里的不同 token 会选中不同的专家，结果每一步几乎所有专家都要被读取一遍；而平均每个专家只分到 batch 里约 8/256 = 1/32 的 token。要让每个专家都分到足够多的 token 来分摊读取权重的开销，整个 batch 必须非常大，专家也要分散到很多卡上。所以 MoE 必须配合超大 batch 和跨多卡的专家并行，才能发挥优势。
- DeepSeek-V3 公布的部署方案是：处理提示词的阶段最少用 4 台机器、32 张 GPU；逐 token 生成的阶段用 40 台机器、320 张 GPU（第 34 章）。

### 8.8 专家学到了什么

人们很容易以为会出现"数学专家""历史专家"这样的分工，但实际情况并非如此。Mixtral 的论文分析发现，**专家的分配没有明显的主题规律**，反而更多与语法、格式有关。例如，Python 代码里的缩进 token 常被分给同一个专家，相邻的 token 也经常被分给同一个专家。

### 8.9 什么时候值得用 MoE

| 场景 | 是否适合 |
|---|---|
| **算力受限，但显存和通信条件充足**（大规模训练、云端高吞吐服务） | 适合。同样的计算量能换来更强的模型 |
| **显存受限**（手机、单卡本地部署） | 不太适合。参数总量太大，放不下 |
| 小规模、低吞吐的场景 | 往往不如同等激活参数的稠密模型划算，因为系统开销太大 |

2024 到 2025 年，最强的开源模型大多是 MoE，例如 DeepSeek-V3、Qwen3-235B、Kimi K2、Llama 4。

::: keypoints
1. MoE 把 MLP 换成很多个专家，每个 token 只选 $k$ 个。总参数决定容量，激活参数决定计算量，$6ND$ 中要用激活参数。
2. 路由器打分，选出 top-$k$，再按门控权重加权求和。梯度通过门控权重流回路由器。
3. 负载均衡是核心难题。辅助损失 $\alpha E\sum f_iP_i$ 有效，但会干扰主目标。DeepSeek 用只影响选择、按规则调节的偏置来做均衡，不干扰梯度，也不丢弃 token。
4. 细粒度专家让可选组合暴增，共享专家承载通用知识。趋势是专家更多、更小，稀疏程度更高。
5. 代价在系统层面：全部参数都要放进显存，每个 MoE 层都要做两次 all-to-all 通信，推理需要大 batch 和大规模部署。
