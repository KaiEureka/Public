# 73.大模型（LLMs）流式输出

#### 什么是流式输出？它为什么对用户体验至关重要？

流式输出（Streaming） 指大语言模型在生成响应时，不是等待整个回答完全生成后再一次性返回给客户端，而是每生成一个 token（或一小批 token）就立即将其推送出去。客户端可以实时地、增量地显示这些文本片段。

对用户体验的重要性：

- 降低首字延迟感知：用户提交请求后，无需等待完整答案，在几百毫秒内就能看到第一个字或词开始出现。这在心理上极大缩短了“等待感”，让交互显得即时和流畅。

- 提供渐进式反馈：即使生成速度较慢（如 20 tokens/s），逐字显示也能让用户实时阅读，跟随模型思路。相比一次性等待数十秒后突然出现整段文本，流式输出更符合人类对话习惯。

- 支持早停与交互控制：用户可以在看到不想要的输出时立即中断生成，节省计算资源并改善体验。这对于聊天、写作辅助等交互式应用尤为重要。

- 模拟真人对话：逐 token 输出模拟了人类“边说边想”的模式，大幅提升对话自然度和产品亲和力。

因此，流式输出已成为现代 LLM 应用的标配，从 ChatGPT 到各类聊天 API 均默认采用此方式。

---

#### 流式输出时，服务端如何将 token 逐个推送给客户端？常用的协议（SSE、WebSocket）对比。

服务端在生成每个 token 后，通过特定协议将其封装并主动推送给客户端。主流协议包括 SSE（Server-Sent Events） 和 WebSocket。

SSE (Server-Sent Events)：

- 基于 HTTP 协议，客户端发起一个普通的 GET 请求（Accept: text/event-stream），服务端保持连接不关闭，并以 `text/event-stream` 格式持续推送数据。

- 每条消息格式为 `data: <json_payload>\n\n`，可以附带 `event:` 和 `id:` 字段。

- 优点：实现极其简单，浏览器原生支持（`EventSource` API），自动重连，穿透代理和防火墙无压力，单向流（服务端→客户端）完美契合流式生成场景。

- 缺点：单向通信（客户端只能通过新建请求来发送数据）；文本格式，二进制支持需 Base64。

WebSocket：

- 全双工通信协议，通过 HTTP 升级握手建立持久连接，之后双方可在任意时间发送数据帧（文本或二进制）。

- 优点：双向通信，支持二进制数据，更低的帧开销和延迟。

- 缺点：需要服务端和客户端都实现 WebSocket 协议；浏览器需手动处理重连；某些网络环境可能屏蔽 WebSocket。

对比与选择：

- 对于典型的 LLM 流式输出（服务端→客户端单向推送），SSE 是更优选择：实现简单，客户端和中间件兼容性好，且足够满足需求。OpenAI、vLLM 等均采用 SSE。

- 若需要客户端也能随时向服务端发送控制指令（如中途修改生成参数、发送中断信号），WebSocket 更合适，但复杂度较高。

实践中，绝大多数 LLM 推理服务的流式 API 均采用 SSE。

#### 在自回归模型中，流式输出的最小推送单位是什么？是 token 还是词块（word）？

最小推送单位通常是单个 token，有时也会以少量 token 的微批次或一个完整词块推送，但以 token 为单位的推送能获得最佳的实时性。

- Token 级别推送：推理引擎每生成一个 token ID，立即将其发送给后处理层。后处理层可以对这个 token 进行 decode 得到文本片段（可能是不完整的 Unicode 字符），并立即推送。这种方式延迟最低，但需要处理不完整字符的问题。

- 词块（word）级别推送：某些实现会在积累了足够形成一个完整词或标点后再推送，以减少碎片化的文本更新，并避免不完整字符。但这会引入少量额外延迟。

- 混合策略：实践中，常用的是 token 级别生成 + 智能拼接：引擎产生 token ID，tokenizer 将其解码为文本，流式层维护一个缓冲区，处理不完整 UTF-8 并尽可能快地发送有意义的最小文本块（如一个完整的词或标点）。但本质上，调度和生成步长仍是单个 token。

因此，从推理引擎角度看，流式推送的最小单位是 token；从客户端接收的文本粒度看，可能是 token 对应的字符片段。核心在于生成与推送的解耦。

---

#### 实现流式输出时，如何保证客户端接收 token 的顺序性和完整性？

流式输出基于可靠传输协议（如 HTTP/1.1 长连接或 HTTP/2 流），其底层 TCP 连接保证了字节流的顺序性和无丢失。因此，只要服务端按正确顺序写入数据，客户端就能按相同顺序接收。

保障措施：

- TCP 的有序性：SSE 和 WebSocket 都依赖 TCP，TCP 保证数据包按发送顺序交付。服务端推送的每个 token 片段会依次到达客户端，不会乱序。

- 消息边界：使用 SSE 的 `data:` 消息边界或 WebSocket 的消息帧，确保每个推送单元是一个完整消息，客户端解析时不会混淆。

- 序列号与确认（应用层可选）：在 WebSocket 或自定义流中，可为每条消息附带递增序列号。客户端检测到序列号跳跃即可发现丢包（尽管 TCP 已保证有序，但可防止应用层处理错误）。对于 SSE，标准允许 `id` 字段用于断线重连后恢复，客户端可在重连时发送 `Last-Event-ID`，服务端据此重传丢失的消息，保证完整性。

- 缓冲与 ACK：服务端可维护发送缓冲区，并仅在收到客户端 TCP ACK 后丢弃已发送数据，但一般内核 TCP 栈已保证。

因此，基于 TCP 的流式输出天然保证顺序性和完整性；SSE 的 `id` 和重连机制进一步增强了应用层鲁棒性。

#### 如果模型输出的 token 经过 tokenizer decode 后形成不完整的 UTF‑8 字符，如何处理？

LLM 的 tokenizer 会将文本切分为子词单元，一个 token 可能对应一个完整字符，也可能只是多字节 Unicode 字符的一部分（如 emoji 的起始字节）。直接 decode 单个 token 可能会产生无效的 UTF-8 字节序列，显示为乱码 `�`。

处理方法：

1. 缓冲与重试解码：维护一个字节或字符缓冲区。每次收到新 token，将其对应的原始字节（或 token 的文本片段）追加到缓冲区。尝试对整个缓冲区进行 UTF-8 解码：
  - 如果解码成功且没有不完整序列，则输出解码后的文本，清空或保留缓冲区。
  - 如果解码失败（遇到不完整多字节序列），则保留缓冲区，等待后续 token 补充完整。将已成功解码的前缀部分输出。

2. 使用安全的流式 tokenizer：HuggingFace 的 tokenizers 提供了 `decode` 的 `skip_special_tokens` 和保留原始字节的方法，以及用于流式的 `decode_async`（部分库支持）。可以将 token 积累到一定程度（如遇到完整词边界）再 decode。

3. 字节级 tokenizer：某些模型（如 GPT-2 之后的很多模型）采用字节级 BPE，每个 token 对应的是一段完整的字节序列，直接拼接即可得到有效 UTF-8，但仍可能出现多字节字符跨 token 的问题，同样需要上述缓冲。

4. 客户端容错：服务端在 SSE 推送时，可先推送已确认安全的字符串片段，对于不完整的末端保留。更简单的方案是服务端只推送 token 文本，不做 decode 保证，由客户端负责累积并处理解码错误。

典型实现（如 vLLM）在流式传输时会维护一个 `previous_text` 和当前文本，智能地只发送新增的可解码部分，避免发送不完整字符。

#### 服务端处理多个并发流式请求时，如何管理每个连接的状态？

服务端需要为每个客户端连接维护独立的生成上下文和连接状态。通常采用异步框架 + 上下文对象来管理。

状态管理要素：

- 请求上下文：每个连接绑定一个唯一请求 ID，包含该请求的生成参数（prompt、温度等）、当前生成序列、以及已推送的 token 游标。

- 连接对象：保存 HTTP 响应流（如 `StreamingResponse` 的句柄）或 WebSocket 连接，用于推送数据。

- 生成器/队列：每个请求关联一个异步队列（如 `asyncio.Queue`）或回调。推理引擎生成新 token 时，将其放入对应请求的队列；服务端协程从队列中取出并推送给客户端。

实现模式（以 Python asyncio + SSE 为例）：

- 使用 FastAPI 的 `StreamingResponse` 结合异步生成器。

- 当请求到达，服务端创建一个 `RequestState` 对象，包含 `asyncio.Queue` 和生成参数。

- 将请求提交给推理引擎（引擎可能运行在独立线程或进程中），引擎在生成 token 时通过回调或放入 `queue.put(token)`。

- FastAPI 的异步生成器函数在一个协程中 `await queue.get()` 获取 token，`yield` SSE 格式的数据。

- 客户端断开连接时，捕获 `CancelledError` 或检查连接状态，取消对应请求的生成并清理资源。

关键点：每个连接的状态完全隔离；使用队列解耦推理生产与网络发送；利用 asyncio 高效管理数千并发连接。

#### 在连续批处理中，多个请求的 token 交错生成，流式输出如何正确分发到对应客户端？

连续批处理中，每次迭代会为 batch 内所有活跃请求各生成一个 token。这些 token 是同时批量产生的，推理引擎迭代结束后，需要将每个新 token 分发到对应请求的流。

分发机制：

- 每次迭代完成后，引擎的输出为一个形状 `[batch_size, vocab_size]` 的 logits 张量，经采样后得到 `batch_size` 个 token ID。

- 引擎维护了一个有序的请求列表（对应 batch 中每个位置的请求 ID）。采样后，遍历列表，将 `(request_id, token)` 对传递给调度器或分发模块。

- 分发模块查找每个 `request_id` 对应的连接上下文（如 `asyncio.Queue`），将 token 放入队列。

- 各请求的流式协程从自己的队列中取出 token，推送给客户端。

具体实现（vLLM 为例）：

- vLLM 使用 `AsyncLLMEngine`，其 `step_async()` 执行一次迭代，返回 `RequestOutput` 列表，每个包含该请求本次生成的一个或多个 token。

- 引擎的调度循环中，每步结束后，将这些输出通过回调或异步生成器传递给每个请求的独立流。

- 服务层（如 FastAPI）在创建请求时，生成一个 `async_generator`，不断从引擎获取属于该请求的输出，并 `yield` 为 SSE 事件。

因此，连续批处理的批量生成与流式分发是通过请求 ID 索引和独立队列实现的，批量产生后即时拆分为独立的流，互不干扰。

#### 流式输出时，如何实现“stop string”检测，并在检测到后立即终止流？

Stop string（如 `"\n\n"`、`"###"`、自定义结束词）的检测需要在 token 序列上实时进行，一旦匹配成功，立即停止生成并关闭流。

检测流程：

1. 维护解码文本缓冲区：每个请求维护一个累积的已生成字符串（或 token 序列）。

2. 每收到新 token：将 token decode 为文本追加到缓冲区，检查缓冲区尾部是否包含任何已配置的 stop string。
  - 可以使用多模式字符串匹配算法（如 Aho-Corasick）高效同时检测多个 stop string。
  - 由于 stop string 可能跨 token 边界，必须使用文本缓冲区而非仅检查最后一个 token。

3. 匹配成功后的处理：
  - 立即将该 stop string 之前的文本（已去除了结束符）作为最终输出的一部分推送给客户端（如果还未推送）。
  - 发送一个结束信号（SSE `[DONE]` 或 WebSocket close frame）。
  - 通知推理引擎停止该请求的继续生成（设置标志，在下次调度时将其标记为完成）。
  - 释放该请求的 KV Cache 等资源。

4. 流关闭：客户端收到结束标记后，视为响应完成。

实现注意：stop string 检测应在文本域进行，因为 tokenizer 可能将 stop string 拆分为多个 token。同时，为了及时性，通常在每次 token 产生后立即检测，而不是累积多个 token 后再检测。如果 stop string 可能被 tokenizer 编码为单个 token，也可在 logits 处理时设置该 token 为不允许生成的（但跨 token 模式仍需文本检测）。

大多数推理框架（vLLM、TGI 等）都内置了 stop string 检测，在生成循环的后处理阶段执行。

#### 如何平衡流式输出的实时性和网络效率？是否需要 token 累积批量发送？

流式输出需要在低延迟和网络效率之间权衡。发送过于频繁（每个 token 立即发送）会增加网络包数量和开销；发送间隔过长则失去实时性。

常见策略：

- Token 级别的立即发送：对于交互式聊天，延迟最为关键，通常每生成一个 token 就立即推送。虽然增加了少量 TCP 包开销，但现代网络和 HTTP/2 多路复用可以承受。这是目前主流的做法。

- 纳秒级微小批累积（Micro-batching）：如果模型生成速度极快（如 >100 t/s），每 token 发送可能导致过于密集的网络 IO，可设定最小发送间隔（如 10ms 或 每 2~3 个 token）。在这段时间内生成的 token 合并为一个 SSE 消息发送。这样既保持了 <50ms 的实时感，又减少了包数量。

- 自适应调整：根据生成速度和网络状况动态调整。当生成速度快时，适当累积；慢时，立即发送。

- Nagle 算法配合：操作系统 TCP 栈默认可能会启用 Nagle 算法（合并小包），对实时性有负面影响。流式服务通常设置 TCP_NODELAY 以禁用 Nagle，确保小包立即发送。

- HTTP/2 和 SSE 的优势：HTTP/2 支持多路复用，多个流式响应共享一个 TCP 连接，头部压缩等，大幅降低了每个 SSE 消息的额外开销。

结论：绝大多数应用采用每 token 立即推送 + 禁用 Nagle 以获得最佳实时性；对于极高生成速度，可加轻度累积（如每 5~10ms 发送一次累积的 token），用户体验无明显差异但网络效率更好。

#### 写出基于 asyncio 的流式 LLM 推理服务伪代码，处理生成和传输。

以下伪代码展示了一个基于 FastAPI + asyncio + 模拟推理引擎的流式聊天服务。

```python
import asyncio
import uuid
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from typing import AsyncGenerator

app = FastAPI()

# 模拟推理引擎：一个全局协程，实际可能为独立线程
class InferenceEngine:
    def __init__(self):
        self.requests = {}  # request_id -> asyncio.Queue

    async def add_request(self, prompt: str) -> str:
        req_id = str(uuid.uuid4())
        self.requests[req_id] = asyncio.Queue()
        # 启动异步生成任务
        asyncio.create_task(self._generate(req_id, prompt))
        return req_id

    async def _generate(self, req_id: str, prompt: str):
        # 模拟自回归生成 token
        for i in range(100):  # 最多生成 100 token
            await asyncio.sleep(0.01)  # 模拟生成延迟
            token = f"tok_{i}"  # 实际为 token ID 或文本片段
            if req_id in self.requests:
                await self.requests[req_id].put(token)
            else:
                break  # 请求已取消
        # 生成结束，放入结束标记
        if req_id in self.requests:
            await self.requests[req_id].put(None)  # None 表示结束

    def cancel_request(self, req_id: str):
        if req_id in self.requests:
            del self.requests[req_id]

engine = InferenceEngine()

# 流式 SSE 生成器
async def generate_stream(req_id: str) -> AsyncGenerator[str, None]:
    queue = engine.requests.get(req_id)
    if not queue:
        yield "data: error\n\n"
        return
    try:
        while True:
            token = await queue.get()
            if token is None:
                break
            # 发送 SSE 格式数据
            yield f"data: {token}\n\n"
    except asyncio.CancelledError:
        # 客户端断开连接
        engine.cancel_request(req_id)
        raise
    yield "data: [DONE]\n\n"

@app.post("/chat")
async def chat(prompt: str):
    req_id = await engine.add_request(prompt)
    return StreamingResponse(
        generate_stream(req_id),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "Connection": "keep-alive"}
    )
```

代码说明：

- 推理引擎为每个请求分配一个 `asyncio.Queue`，并在后台任务中生成 token，逐个放入队列。

- FastAPI 路由创建 `StreamingResponse`，其中 `generate_stream` 是异步生成器，持续从队列获取 token 并 yield SSE 数据。

- 当客户端断开，协程被取消，通过 `CancelledError` 处理清理请求。

- 生成结束放入 `None`，流发送 `[DONE]` 后关闭。

实际应用中，推理引擎部分会被替换为 vLLM 的 `AsyncLLMEngine` 或类似的高性能引擎，但核心的队列解耦与流式传输模式保持不变。

#### 前端如何良好地展示流式 LLM 输出，包括 Markdown 渲染、代码块增量？

流式输出的前端展示需要处理增量文本更新、Markdown 解析以及代码块的特殊处理，以保证用户看到平滑且正确格式化的内容。

关键技术与策略：

1. 维护完整文本缓冲区\
   前端接收到 SSE 的每个 token 文本片段后，追加到一个完整的响应字符串中。这个字符串是不断增长的，代表了当前已生成的全部文本。

2. 增量渲染 Markdown\
   对整个缓冲区进行 Markdown 渲染，并更新显示区域。但不能简单全量重新渲染，否则会导致光标跳动和性能问题。常见做法：
  - 使用支持增量更新的 Markdown 库（如 `react-markdown` 配合 `remark` 或 `marked`），每次将新文本附加到已有内容，只重新渲染变化的部分。
  - 或者将原始 Markdown 直接显示在文本编辑器中（如代码编辑器风格），由用户自行查看渲染后的效果，但主流聊天界面通常实时渲染。

3. 代码块的处理\
   代码块是 Markdown 的特殊结构，以 ````` 为边界。流式到达时可能不完整：
  - 如果检测到当前处于未闭合的代码块内，可以暂时不渲染为代码块，而是显示为普通文本，直到代码块结束。
  - 或者单独将代码块区域提取出来，使用等宽字体展示，待闭合后再应用语法高亮。
  - 更优方案：将 Markdown 解析为抽象语法树（AST），遇到未闭合的代码块时，前端只渲染代码块前缀部分，内部内容增量追加并应用代码样式。

4. 光标跟随与自动滚动\
   内容增长时应自动滚动到底部，让用户始终看到最新输出。使用 `scrollIntoView` 或保持滚动条在底部。

5. 防止 XSS\
   使用安全的 Markdown 渲染器（如 `DOMPurify` 净化），避免恶意脚本注入。

6. 停止生成时的处理\
   如果用户点击停止或模型输出结束，前端应立即刷新最后一次渲染，确保所有内容正确闭合（如补全代码块边界）。

总结：前端利用字符串缓冲区和增量 Markdown 渲染器，配合代码块状态机，可以实现流畅的流式 Markdown 显示，用户体验类似 ChatGPT。

#### 使用 SSE 进行流式输出时，如何处理连接中断和重连？

SSE 内置了自动重连机制，并且可以通过 `Last-Event-ID` 实现断点续传，但需要服务端配合。

处理机制：

1. 浏览器端自动重连\
   `EventSource` API 会在连接中断后自动尝试重新连接（默认间隔约几秒）。重连时会发送 `Last-Event-ID` HTTP 头，其值是最近接收到的 `id` 字段。

2. 服务端支持 `id` 和 `Last-Event-ID`
  - 服务端在每条 SSE 消息中附加 `id: <序列号>`。序列号可以是对应 token 的序号或偏移量。
  - 当重连请求到达，服务端解析 `Last-Event-ID`，找到该请求中断前已发送的最后一个 token 位置，并从该位置之后的 token 开始推送。这要求服务端能够缓存已生成的 token 序列（至少缓存最近的 token）或能够根据序列索引重新生成（不现实）。常见实现：服务端维护每个请求的生成历史，客户端重连后，服务端先发送 `id` 和对应数据，客户端跳过已接收的消息。

3. 自定义重连策略\
   如果使用自定义 SSE 客户端（如 `fetch` + `ReadableStream`），需要手动实现重连：
  - 在流断开时，重新发起请求，并携带 `Last-Event-ID`。
  - 客户端维护接收到的最大 `id`，丢弃重复数据。

4. 服务端清理与过期\
   为避免服务端无限期缓存，可以设置超时时间。如果客户端长时间未重连（如 30 秒），服务端清理该请求的缓存，客户端重连后可能无法恢复，只能重新发起完整请求。

5. 连接中断的检测\
   客户端通过 `EventSource.onerror` 或 `fetch` 的 `reader.cancel` 检测中断，并触发重连逻辑。

最佳实践：在 LLM 流式服务中，通常不实现复杂的重连续传，因为生成的内容具有实时性和上下文依赖，重连后重新发送完整请求更简单且可靠。但对于超长输出，可以通过客户端缓存已接收文本，重连后发送已接收长度提示给服务端，由服务端跳过已生成部分继续推送新 token（如果引擎支持断点续生成）。

#### 在 vLLM 或 TGI 中，如何开启流式输出？配置哪些参数？

vLLM：

- 启动 OpenAI 兼容服务器：


#### 流式输出中的“首个 token 延迟”（TTFT）受哪些因素影响？如何优化？

TTFT (Time To First Token) 是从请求发出到客户端收到第一个 token 的时间。它直接影响用户感知的响应速度。

影响因素：

1. 模型加载与初始化（首次请求）：若模型尚未加载到显存，冷启动会显著增加 TTFT。可通过预热或持久化模型避免。

2. Prompt 长度（Prefill 时间）：prefill 阶段需要一次处理整个 prompt，其计算量与 prompt 长度成正比。长 prompt 导致高 TTFT。

3. 模型大小与计算速度：模型参数量越大，计算越慢；量化可减少计算时间。

4. 并发请求与调度：在连续批处理中，新请求可能需要等待当前 batch 执行完才能加入（或等待资源）。高并发下调度延迟增加。

5. 网络延迟：客户端与服务端之间的 RTT。

6. 输入处理：tokenization、截断等预处理开销。

优化方法：

- 使用推测解码：草稿模型或 Medusa 头在 prefill 时就开始生成候选 token，可能隐藏部分 TTFT，但主要优化后续 token 延迟。对 TTFT 优化有限。

- 分块预填充（Chunked Prefill）：将长 prompt 分成多个 chunk 与 decode 混合，这样第一个 chunk 很快完成，可以提前开始解码，显著降低 TTFT（vLLM 支持）。

- 前缀缓存（Prefix Caching）：如果请求有共同前缀，复用已计算的 KV Cache 直接跳过 prefill，TTFT 降为接近单 token decode 延迟。

- 量化与内核优化：使用 FP8/INT8 加速 prefill 计算。

- 动态批处理调度优化：优先调度新请求的 prefill（与 decode 混合），避免长时间等待。

- 减少预处理开销：预编译 tokenizer 或缓存编码结果。

- 边缘部署：将模型部署在离用户更近的节点，降低网络延迟。

总结：TTFT 的关键瓶颈在 prefill 和调度。采用前缀缓存、分块预填充和高效的混合批处理是当前最优实践。

#### 多模态模型输出时，流式输出如何同时推送文本和可能的图像占位？

多模态模型（如 GPT-4o, LLaVA）可能生成交错的文本和图像（或特殊标记）。流式输出需要定义一种协议来标识媒体片段。

常见做法：

1. 特殊 Token 或标记\
   模型在生成文本过程中，在需要插入图像的位置输出一个特殊 token（如 `<image>` 或 `<|image|>`）。流式输出时，服务端将这个特殊标记作为普通文本推送，或者可以将其封装为特定事件类型。

2. SSE 事件类型的区分\
   使用 SSE 的 `event:` 字段来区分消息类型：
  - `event: text` -> 文本块
  - `event: image` -> 图像 URL/Base64 数据或占位符
  - 前端根据不同事件类型在 UI 中分别渲染文本和图像。\
    例如：

```plain text
event: text
data: 这是描述文字

event: image
data: {"url": "data:image/png;base64,...", "alt": "图片描述"}
```

3. 文本内嵌标记 + 延迟加载\
   服务端推送文本时，遇到图像占位符（如 `[IMG: generating...]`），先显示占位文本。当图像生成完成后，再通过另一个事件更新该占位符为实际图像或 URL。

4. 多部分流（Multipart Streaming）\
   类似于 HTTP multipart，但实现较复杂。SSE 更简单通用。

5. 客户端解析特殊标记\
   如果图像是以 token 序列生成（如扩散模型），服务端可能积累这些 token，一旦解码出一幅完整图像，就发送图像事件，并暂停文本流。

关键点：需要前后端约定统一的事件格式，使文本和图像能够在时间线上交错显示，保持流式体验。OpenAI 的多模态流式 API 目前采用特殊标记嵌入文本，配合前端解析。

#### 当使用推测解码时，流式输出行为会有什么变化？如何对外保持一致？

推测解码（包括 Medusa）在内部一次验证多个 token，会批量产生多个 token，而标准自回归一次只产生一个 token。这可能导致流式输出出现“突发”行为：客户端可能在一段时间内没有 token，然后一次收到多个 token。

行为变化：

- 在标准流式中，token 产生间隔大致均匀。

- 在推测解码中，草稿阶段不产生输出（全部为候选），验证阶段一次性接受多个 token，这些 token 会在极短时间间隔内一起交付给流式模块，随后是下一轮草稿+验证的间隔。因此，流式输出会呈现批次性：一组 token 快速连续推送，然后停顿，再下一组。

- 从客户端看，接收 token 的节奏变得不规则，可能略微影响“逐字出现”的细腻感。

对外保持一致的方法：

- 加入平滑发送机制：在推理引擎内部，将验证后接受的多个 token 暂存，然后以模拟自回归的速度（根据平均每 token 延迟）逐个释放给流式层。但这会人为增加延迟。

- 客户端归一化：客户端接收 token 时不做任何假设，只是按到达顺序渲染。实际体验中，只要整体速度提升，短暂的 burst 对用户影响不大，因为文本仍在快速涌现。

- 透明处理：不对流式层做特殊处理，直接批量推送。这是最常见的做法，因为推测解码带来的总加速远大于流式不平滑的微小缺陷。

总结：推测解码会使流式输出产生 token 的突发到达，但这对于终端用户是透明的或可接受的。为保持 API 行为一致，服务端无需特殊处理，继续以 token 为单位推送即可。

#### 在流式过程中，如果模型输出需要进行后处理（如敏感词过滤），应在哪个环节处理，如何避免增加延迟？

后处理应尽量靠近 token 生成侧，在推送到客户端之前完成，且不能阻塞生成循环。

处理环节与策略：

1. Token 级别即时过滤\
   每生成一个 token，立即将其 decode 为文本，并与已积累的文本缓冲区结合，检查是否出现敏感词。如果检测到：
  - 立即替换或屏蔽敏感部分。
  - 若需要完全停止生成（如触发安全策略），立即通知引擎终止该请求。\
    由于检测通常在 CPU 上进行（快速字符串匹配），可以在推理引擎的每次迭代后、流式推送前执行，延迟几乎可忽略（微秒级）。

2. 异步处理\
   如果后处理较复杂（如调用外部审核 API），应采用异步方式，不阻塞推理主循环。可以将 token 送入一个处理队列，由后台任务处理后再推送；但这会引入额外的延迟。更优方法是预判风险，在生成前通过 prompt 工程降低不安全输出概率。

3. 延迟敏感的缓冲\
   可以设定一个极小的缓冲窗口（例如 2-3 个 token），在此窗口内检查是否形成敏感词，如果没形成，立即发送最早的 token；如果形成，则替换后发送。这平衡了实时性和安全性，额外延迟仅为两三个 token 的生成时间，通常 < 100ms。

4. 在客户端进行后处理\
   将敏感词过滤放在客户端，服务端只提供原始 token 流。但这可能无法防止服务端资源浪费（不安全内容仍被生成），适用于对延迟要求极高且信任客户端的场景。

结论：最佳实践是在服务端生成循环内，以极低开销的字符串匹配即时过滤，在 token 推送前完成，不显著增加延迟。

#### 如何设计 API 使流式输出能够同时返回 token 的对数概率？

要在流式输出中携带 token 的对数概率（logprobs），需在 SSE 事件的数据中包含相应信息。

设计方案：

1. 扩展 SSE 数据字段\
   每个 SSE 消息的 JSON 负载不仅包含 `token` 文本，还包含该 token 的 logprob、候选 token 及其 logprobs 等。例如：

```json
{
  "token": "你好",
  "logprob": -0.12,
  "top_logprobs": [
    {"token": "你好", "logprob": -0.12},
    {"token": "您好", "logprob": -1.5},
    ...
  ],
  "text": "你好"   // 累积文本
}
```

这与 OpenAI 的流式 API 返回的 `choices[0].logprobs` 结构类似。

2. logprobs 的计算时机\
   在模型输出 logits 并采样得到 token 后，立即计算所选 token 的对数概率（`log_softmax` 后的值），以及如果需要，计算 top-k 候选的概率。这些信息与 token 绑定。

3. 对推理引擎的要求\
   推理引擎在采样后需保留 logits（或直接计算 logprobs），并在分发 token 时附带这些统计量。vLLM、TGI 等引擎均支持 `logprobs` 参数，开启后会自动在输出中包含。

4. API 参数\
   类似 OpenAI，在请求中通过 `logprobs=True` 和 `top_logprobs=5` 开启。服务端在流式响应的每个 data 块中包含这些字段。

5. 性能考虑\
   计算 top-k logprobs 需要在 logits 上做排序，对于大词表（如 128k）有一定开销。可使用高效的 top-k 算法，并仅在用户请求时启用，避免不必要的计算。

实现示例（OpenAI 兼容）：

```plain text
data: {"id":"cmpl-...","object":"text_completion.chunk","created":...,"model":...,"choices":[{"index":0,"text":"你好","logprobs":{"tokens":["你好"],"token_logprobs":[-0.12],"top_logprobs":[{"你好":-0.12,"您好":-1.5,...}]}}]}
```

这样客户端即可在流式接收 token 的同时获得每个 token 的概率信息。

#### 解释在 gRPC 双向流或 WebSocket 下实现 LLM 流式调用的优势。

gRPC 双向流和 WebSocket 提供了不同于 HTTP SSE 的流式调用方式，具有以下优势：

1. 双向通信
  - 客户端可以在接收 token 流的同时，随时向服务端发送控制消息，例如中止生成、调整采样参数（如 temperature）、注入新的系统指令等。这在交互式创作、对话式 AI 中非常有用。
  - SSE 是单向的，客户端若需中止只能关闭连接，无法优雅地发送“停止”信号让服务端提前释放资源。

2. 多路复用与并发
  - gRPC 基于 HTTP/2，原生支持多路复用，可以在一个 TCP 连接上同时处理多个流（例如多个并行生成请求），减少连接开销。
  - WebSocket 也支持全双工，但需要应用层自己管理多路复用。

3. 低延迟与二进制帧
  - WebSocket 的消息帧开销比 SSE 文本格式更小，支持二进制传输，对于需要发送大量 token 或媒体数据的场景更高效。
  - gRPC 使用 Protocol Buffers 序列化，结构紧凑，解析效率高。

4. 强类型契约
  - gRPC 通过 `.proto` 定义服务接口，生成强类型客户端/服务端代码，减少出错，适合大型系统集成。
  - WebSocket 消息格式需自定义，易产生歧义。

5. 流控与背压
  - gRPC 和 WebSocket 底层 TCP 具有流控机制，可以自然实现背压：如果客户端处理慢，服务端发送缓冲区满，会自动减速。gRPC 还有应用层流控。

适用场景：

- 需要双向实时交互或精确控制时，使用 gRPC 双向流或 WebSocket 更优。

- 仅需服务端推送的简单场景，SSE 更简便。

#### 流式输出中如何将“系统提示”、“用户输入”和“助手回复”以流式事件形式区分？

在多轮对话中，或需要区分消息角色时，可以通过 SSE 的 `event` 字段或消息中的 `role` 字段来标识不同部分。

方案：

1. 使用 SSE `event` 类型\
   服务端在推送不同角色内容时，设置不同的 `event` 名称：
  - `event: system` → 系统提示内容
  - `event: user` → 用户输入回显或生成过程中的用户中断
  - `event: assistant` → 助手回复（默认流式输出）\
    这对于区分同一连接中的多个角色消息非常清晰。

2. 在数据 JSON 中包含 `role` 字段\
   类似 OpenAI Chat Completion 流式，每个 chunk 的 `choices[0].delta` 中包含 `role`（仅在第一个 chunk 中指定 `role: "assistant"`），后续 chunk 不包含 `role`。前端根据首 chunk 的角色分配消息框。

3. 多阶段流\
   对于复杂的多步骤对话（如工具调用），服务端可以在一个流中依次发送多种事件：
  - 先发送 `event: thought` 内部思考
  - 再发送 `event: tool_call` 工具调用
  - 最后发送 `event: answer` 最终回答

4. 实现细节\
   在服务端生成循环中，根据当前生成的阶段，设置对应的 SSE event 或 JSON 字段。例如，在开始生成助手回复时，先发送：

```plain text
event: assistant
data: {"role": "assistant", "content": ""}
```

1. 然后后续 token 均发送 `event: assistant` 或省略 event 使用默认助手角色。

这样前端可以基于事件类型构建清晰的多角色对话界面，实现类似 ChatGPT 的显示效果。

#### 如果生成过程中出现错误（如显存不足），如何在流式通道中优雅地通知客户端？

在流式响应中，如果发生不可恢复的错误，必须通知客户端，同时保证连接正常关闭。可以通过定义特殊的 SSE 事件或错误数据结构来实现。

实现方式：

1. SSE `error` 事件\
   服务端发送一个 `event: error` 的 SSE 消息，数据中包含错误码和错误信息：

```plain text
event: error
data: {"code": "out_of_memory", "message": "显存不足，请稍后重试。"}
```

然后服务端主动关闭连接。\
客户端监听 `error` 事件并展示相应提示。

2. 在常规数据中附加错误字段\
   在最后一次数据推送中包含 `"error"` 字段（类似于 OpenAI API 在非流式中的错误处理）。但这不如专用错误事件显眼。

3. 发送 HTTP 错误状态码（如果可能）\
   若错误发生在流建立之前，直接返回 500 错误；如果流已经开始，则通过上述 SSE 事件告知。

4. 客户端检测连接关闭\
   如果服务端意外断开而没有发送错误事件，客户端应检测到连接关闭，并视为“生成中断”，显示通用错误提示。可通过 `EventSource.onerror` 或 `fetch` 的 `reader.closed` 实现。

5. 提供重试或恢复建议\
   错误数据中可以包含 `retry_after` 或 `request_id` 以便客户端重试或联系支持。

注意点：

- 在关闭连接前，确保错误事件被成功发送，可能需要短暂延迟或同步刷新。

- 对于部分生成结果（已推送的 token），客户端可以选择保留显示，并附加错误标记。

- 服务端需正确清理该请求的资源（释放 KV Cache 等），防止泄漏。

优雅错误处理示例（Python 伪代码）：

```python
try:
    for token in generate():
        yield f"data: {json.dumps({'token': token})}\n\n"
except MemoryError:
    yield f"event: error\ndata: {json.dumps({'error': 'out_of_memory'})}\n\n"
finally:
    yield "data: [DONE]\n\n"
```

这样客户端就能在流中收到明确的错误通知，而非突然断开。
