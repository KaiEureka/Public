# 68.大模型（LLMs）PagedAttention

#### PagedAttention 是如何借鉴操作系统分页思想来管理 KV Cache 的？

PagedAttention 将操作系统的虚拟内存分页机制引入到 LLM 推理的 KV Cache 管理中。其核心类比是：

- 虚拟地址空间 → 逻辑 KV 序列（每个请求的 token 序列）

- 物理内存 → GPU 显存（存储所有请求的 K、V 张量）

- 页（Page） → 固定大小的 KV 块（如每个块包含 16 个 token 的 K 和 V）

- 页表（Page Table） → 块表（Block Table），记录逻辑块到物理块的映射关系

传统方法为每个请求预分配一段最大长度的连续显存，就像早期操作系统为进程分配连续物理内存，极易产生内部碎片（未使用的预留空间）和外部碎片（释放后的不连续空洞），导致显存利用率低下，无法支持高并发。

PagedAttention 借鉴分页思想，将 KV Cache 划分为大量固定大小的小块，需要时按需分配，不使用时释放回收，实现了：

- 按需分配，动态增长：无需预分配最大长度，只需随着 token 生成逐步申请物理块，显存利用率大幅提高，接近物理极限。

- 无外部碎片：任何空闲块均可分配给任何请求，回收后又能立即用于其他请求，消除了外部碎片。

- 内存共享：多个请求可以共享相同的物理块（如相同前缀的 prompt 或 beam search 的公共部分），只需在各自块表中指向同一物理块，配合写时复制（COW）或引用计数，进一步节省显存。

- 弹性调度：连续批处理可以随时加入新请求或换出老请求，块级别的释放与分配保证了系统的动态弹性。

因此，PagedAttention 实现了接近零浪费的显存管理，使 LLM 推理服务能够支持更大的 batch 和更长的序列，是 vLLM 等系统吞吐飞跃的关键。

#### 在 PagedAttention 中，KV Cache 被划分为固定大小的“块”（block），请描述块的分配与映射过程。

物理块：在 GPU 显存中预先分配一个大块内存池，将其均匀切分为固定大小的物理块。例如，块大小 `block_size = 16` 个 token，则每个块存储某个注意力头（或所有头）的 16 个 token 的 K 或 V 张量。对于所有层和所有头，通常会统筹管理，但逻辑上可以按层/头独立分配。

分配过程（以请求生成为例）：

1. 请求初始化（Prefill 阶段）
  - 当新请求到达，系统根据其 prompt 长度估算需要的物理块数量：`num_blocks = ceil(prompt_length / block_size)`。
  - 从空闲块池中分配 `num_blocks` 个物理块，分配给该请求的 KV Cache。这些物理块在显存中可能不连续。
  - 建立一个块表（Block Table），长度为最大可能的逻辑块数，记录了逻辑块索引到物理块索引的映射。
  - 在 prefill 过程中，随着 prompt token 被处理，生成的 K 和 V 按顺序写入这些物理块。第一个逻辑块写入 token 0..15，第二个写入 16..31，依此类推，最后一个块可能未填满（存在少量内部碎片）。

2. Decode 阶段动态追加
  - 每生成一个新 token，序列长度增加 1。如果当前最后一个物理块已满（即已存储 `block_size` 个 token），则从空闲池再分配一个新的物理块，并将其索引追加到该请求的块表末尾。
  - 新 token 的 K、V 写入这个新块的起始位置（偏移 0）。后续 token 继续填充该块，直至再次满并分配下一块。

3. 映射关系
  - 逻辑序列位置 `pos`（从 0 开始的 token 索引）对应的逻辑块号为 `block_id = pos // block_size`，块内偏移为 `pos % block_size`。
  - 通过块表查得物理块号 `physical_block = block_table[block_id]`，则该 token 的 K、V 数据位于该物理块内存区域的偏移 `offset * head_dim` 处。

4. 释放
  - 请求完成或被抢占时，其所有物理块被标记为空闲，回收到空闲池，块表销毁。

这种按块动态分配与映射的机制，完全消除了预分配连续长序列的必要性。

#### 画出 PagedAttention 中逻辑 KV 序列到物理块的映射表，并解释注意力计算时如何根据映射表读取 KV。

我们可以用示意图来描述映射关系。假设物理块大小为 4（简化），共有 8 个物理块，编号 0~7。请求 A 的序列长度为 10，请求 B 的序列长度为 6。

逻辑到物理映射表：

```plain text
请求 A (seq_len=10):
逻辑块0 (token 0-3)  -> 物理块 2
逻辑块1 (token 4-7)  -> 物理块 5
逻辑块2 (token 8-9)  -> 物理块 7 (仅用前2个位置)

请求 B (seq_len=6):
逻辑块0 (token 0-3)  -> 物理块 0
逻辑块1 (token 4-5)  -> 物理块 3 (仅用前2个位置)
```

块表可表示为数组：

A.block_table = [2, 5, 7]

B.block_table = [0, 3]

注意力计算时如何读取：

在 Decode 阶段，每个请求需读取其全部历史 KV。对于请求 A，计算其第 10 个 token（新 token）的注意力时，需要访问 token 0~9 的 K、V。

- 确定逻辑块范围：0..2。迭代每个逻辑块 `blk_idx`：
  - 查块表得物理块号 `phy = A.block_table[blk_idx]`。
  - 计算该块内有效 token 数：若 `blk_idx < last_idx` 则满块（4），否则为剩余 token（对于块2是 2）。
  - 加载该物理块的 K、V 数据，从偏移 0 开始，读取 `有效长度 * head_dim` 个元素。

在 GPU 内核中，这些操作通过传入块表和请求的上下文信息（序列长度）实现，循环加载非连续的物理块地址。由于块大小固定，可以高效实现向量化访问，每个物理块内部是连续内存，无需逐 token 的 scatter/gather 操作。

#### 使用 PagedAttention 后，如何解决因预分配固定最大长度造成的显存浪费？

传统方式为每个请求分配大小为 `max_seq_len` 的连续显存，例如最大 2048 token 的 KV Cache。但实际请求长短不一：

- 短请求（如 20 token）浪费了 2028 个 token 的未使用空间（内部碎片极大）。

- 释放时留下的空洞大小不同，无法被新请求完美复用，产生外部碎片。

PagedAttention 从根本上解决了这一问题：

消除内部碎片：

不再预分配固定最大长度，而是以小块（如 16 token）为单位按需分配。短请求仅占用极少块（如 20 token 占 2 块，最后一个块有 12 个空位，内部碎片仅为 12/16，远小于之前的上千浪费）。内部碎片仅限于每个请求的最后一个物理块的部分空间，总浪费与块大小成正比，与最大长度无关。

消除外部碎片：

所有物理块大小相同，回收后的块直接并入空闲池，任何请求都能使用。不存在因长度不一导致的“无法利用的空洞”。显存被组织为统一的块池，所有分配和释放都是块粒度的，天然无外部碎片。

统计效果：

在真实负载下，传统方案的显存利用率通常不足 50%，而 PagedAttention 可将利用率提升到 90% 以上，相同显存下可支持数倍的并发请求，直接转化为系统吞吐的成倍增长。

#### 当序列长度动态增长超过已分配的物理块时，PagedAttention 如何重新分配或扩展？

在 decode 阶段，每生成一个新 token 可能会触发块的扩展。PagedAttention 采用惰性按需分配策略：

1. 检测是否满块：每次追加新 token 时，检查当前序列最后一个逻辑块内的 token 数是否已达 `block_size`。若未满，直接将新 K、V 写入该块的下一个空闲位置，无需新块。

2. 分配新块：若最后一个块已满，从空闲物理块池中分配一个新物理块。这个块可能是之前被其他请求释放的任意空闲块。

3. 更新块表：将新物理块索引追加到该请求的块表末尾（例如 `block_table[num_blocks] = new_phy_block`），同时请求的逻辑块计数加 1。

4. 写入数据：新 token 的 K、V 被写入这个新块的起始位置（偏移 0）。

空闲块不足时：

如果空闲池没有可用块，调度器必须抢占某些请求（换出到 CPU 内存）或直接拒绝新请求。被换出的请求的物理块被释放，供其他请求使用。当资源恢复时，被抢占的请求可以重新分配物理块并从 CPU 拷贝回 KV 数据（或重计算）恢复执行。

因此，PagedAttention 通过动态扩展块表，以块为单位平滑增长，完全避免了传统方案中“空间不足需整体搬迁”的笨重操作。

#### PagedAttention 如何处理多个序列共享相同前缀的 KV Cache 块？这种共享对吞吐的提升有多大？

共享机制（例如 parallel sampling 或 beam search）：

- 当多个序列源自同一个 prompt（如对同一 prompt 生成多个候选回复），它们的 prompt 部分是相同的。PagedAttention 可以为这些序列共享同一组物理块来存储 prompt 的 K、V。

- 实现方式：为每个序列维护独立的块表，但将 prompt 部分的逻辑块映射到相同的物理块。同时，使用引用计数跟踪每个物理块被多少序列共享。

- 当某个序列需要修改共享块（追加新 token 导致写操作）时，采用写时复制（Copy-on-Write, COW）：先将共享的物理块复制到一个新分配的块，然后修改新块，原共享块引用减一。但通常 prompt 的 KV 是只读的，真正需要 COW 的情况较少；decode 阶段生成不同 token 后，各个序列会产生各自独有的新块。

对吞吐的提升：

- 显存节约：假设 batch 中有 32 个请求共享同一 prompt，传统方式需要存储 32 份完整的 prompt KV。PagedAttention 只需 1 份。以 prompt 长度 1024 token 为例，每个请求可节省约 1024 * 2 * d_model * layers 字节的显存，释放出的空间可容纳更多请求，提高并发数。

- 吞吐增益：更大的 batch size 直接提升 GPU 利用率和总 token/s。理论上，如果 batch 全部由相同 prompt 驱动，显存可支撑的并发度翻倍，吞吐接近翻倍。在混合负载中，前缀共享也能带来 10%~30% 的吞吐提升，具体取决于请求的相似度。

- 减少 prefill 计算：vLLM 还会利用共享前缀跳过重复的 prefill 计算（prefix caching），不仅省显存，还省算力，进一步降低首 token 延迟。

因此，PagedAttention 的块级共享机制使系统在并行采样、多轮对话等场景下具有极大的内存和性能优势。

#### 解释 vLLM 中“块表”（block table）的数据结构，并在 GPU 上如何传递以进行内核计算。

块表数据结构：\
在 vLLM 中，块表是一个二维整数张量，形状为 `[num_requests, max_num_blocks_per_req]`，存储物理块索引。对于每个请求，其块表的一行记录了该请求的逻辑块号到物理块号的映射，未使用的槽位填充为 `-1` 或无效值。每个请求的实际逻辑块数由 `seq_lens` 跟踪。

例如：

```plain text
block_table = [
    [2, 5, 7, -1, -1],  # 请求0：3个逻辑块
    [0, 3, -1, -1, -1], # 请求1：2个逻辑块
]
```

伴随的还有 `context_lens`（已生成序列长度，即 token 总数）等元数据。

GPU 传递方式：

- 在每次 decode 迭代前，CPU 调度器更新块表（如追加新块、释放块），然后将块表作为 PyTorch 张量拷贝到 GPU。

- GPU kernel（如 `paged_attention_kernel`）接收该块表以及 `seq_lens`、`block_size` 等参数。

- 在 kernel 中，每个线程块负责一个请求（或一个注意力头）的计算。它读取对应请求的块表行，根据 `seq_len` 计算需要迭代的逻辑块数。对于每个逻辑块 `i`，通过 `block_id = block_table[request_idx][i]` 获取物理块索引，然后计算该物理块的基地址（`base + block_id * block_size * head_dim * element_size`），从该地址加载该块的 K 或 V 数据。

- 因为物理块在显存中是连续存储的，加载一个块内部的数据是合并访问的，非常高效。非连续的块之间通过多次索引跳转，但每个块内是完全顺序的，避免了随机 gather 开销。

优化点：块表通常常驻 GPU，或在每次迭代前通过异步拷贝（`cudaMemcpyAsync`）更新增量。vLLM 还支持将块表置于统一虚拟内存（UVA）中，CPU 可见，便于动态修改。

#### 物理块大小（block size）如何选择？对显存利用率和计算效率有何影响？

物理块大小（每块包含的 token 数）是一个重要的超参数，需要在内部碎片、块表开销、计算效率之间权衡。

- 内部碎片：平均每个请求的最后一个块有 `block_size/2` 的期望浪费。块越大，内部碎片越多，显存利用率越低。例如，block_size=128 可能造成每个请求 ~64 token 的浪费；block_size=16 则仅 ~8 token。

- 块表开销：块越小，块表行数（最大逻辑块数）越大，块表本身占用内存和传输开销增加。同时，注意力 kernel 需要循环更多次（每次加载一个块），循环开销和索引计算也增加。

- 计算效率：较大的块可以更好地利用内存合并访问和 Tensor Core 的 tile 尺寸。块内连续区域大，向量化加载效率更高；循环次数少，kernel 启动和指令开销降低。但过大的块在 batch 中不同请求的长度差异大时，可能导致负载不均（某些块只部分填充，GPU 线程束利用率下降）。

- 实践经验：vLLM 默认 `block_size = 16`（或 32）是一个平衡点，既保持内部碎片在可接受范围（几%），又维持了较高的 kernel 效率。对于内存非常充裕或面向极长序列的场景，可适度增大块尺寸以减少循环开销。

影响总结：

| 块大小 | 内部碎片 | 块表大小 | Kernel 循环次数 | 推荐场景 |
| --- | --- | --- | --- | --- |
| 小 (8) | 低 | 大 | 多，开销较高 | 显存极度受限，短请求多 |
| 中 (16/32) | 中 | 中 | 平衡 | 通用，vLLM 默认 |
| 大 (64/128) | 高 | 小 | 少，单块效率高 | 长序列为主，显存充裕 |

#### 在 PagedAttention 的内核实现中，如何高效处理非连续内存中的 KV 块？是否需要 gather 操作？

PagedAttention 内核不需要昂贵的逐元素 gather/scatter 操作，而是通过按块索引 + 块内连续加载来实现高效率。

实现方式：

1. 两层循环：外层循环遍历逻辑块，通过块表获得物理块地址；内层循环在该物理块内部顺序加载 K/V 元素。

2. 地址计算：对于给定的物理块号 `p`，块数据的起始地址为 `base_addr + p * block_bytes`。块内第 `i` 个 token 的第 `j` 个 head_dim 元素的地址为 `base_addr + p * block_bytes + i * head_dim * element_size + j * element_size`，完全连续。

3. 向量化加载：由于块内 token 的 K/V 存储是连续的，可以使用 `float4` 或 `uint4` 等宽向量化加载指令（如 CUDA 的 `cuda::memcpy_async` 或 PTX 的 `cp.async`），一次加载多个字节，充分利用内存带宽。非连续仅存在于块之间，而块切换只发生在逻辑块边界，次数有限。

4. 无随机 gather：传统的基于索引列表的 gather 操作（如根据 token 位置数组随机访问）会导致大量非合并内存访问，效率极低。PagedAttention 通过固定块大小和连续块内存储，将非连续访问限制在粗粒度的块级别，块内始终保持合并访问，极大提升了显存带宽利用率。

具体 kernel 伪代码：

```python
for log_block in range(num_blocks):
    phy_block = block_table[req_idx][log_block]
    offset = phy_block * block_size * head_dim
    # 加载整个块的 K（或每次加载 tile）
    for t in range(block_size):
        # 这里的加载在块内是连续的
        k[log_block*block_size + t] = load(base_K + offset + t*head_dim)
```

由于这些加载的模式可预测且连续，GPU L1 缓存和合并访问单元可以有效工作。此外，vLLM 在 FlashAttention 的基础上实现了 `flash_attn_with_kvcache`，将分页式加载融合进分块注意力计算中，进一步减少了额外的中间缓冲。

结论：PagedAttention 高效处理非连续 KV 块的秘密在于“以块为单位的连续加载”，避免了逐 token 的随机 gather，实现了接近连续缓存的带宽利用率。

#### 比较 PagedAttention 与传统的连续 KV Cache 存储在显存碎片和利用率上的改善。

传统连续 KV Cache 存储：

- 为每个请求预分配一段大小为 `max_seq_len * 2 * num_layers * num_heads * head_dim * dtype_size` 的连续显存。

- 内部碎片：每个请求实际使用的长度远小于最大长度时，大量预分配空间闲置。例如最大 2048，平均 200 token，浪费超 90%。

- 外部碎片：请求结束释放后，留下不同大小的空闲段。新的请求可能无法找到恰好合适的连续块，导致内存空洞，利用率进一步降低。

- 灵活性差：无法动态增加长度，若生成超过预分配最大值则溢出失败；无法实现零拷贝的块共享。

PagedAttention：

- 按固定大小的块分配，块内连续，块之间可以不连续。

- 内部碎片：仅在每个请求的最后一个块中存在，平均约 `block_size/2` 个 token 的浪费。若 block_size=16，平均浪费 8 token，相比数千的预分配近乎可以忽略。

- 外部碎片：完全消除。所有空闲块等大同构，可被任意请求使用，回收后直接合并到池，无任何空洞问题。

- 显存利用率：可从传统方案的 30~50% 提升至 90% 以上。vLLM 论文中报告，在相同负载下，显存可支撑的请求数提高了 2~4 倍。

- 额外收益：支持前缀共享，进一步节省显存；支持抢占换出换入，实现过载下的弹性调度。

定量比较（假设条件：模型 13B，max_seq_len=2048，块大小=16，平均请求长度 300 token）：

- 传统方案：每请求固定占用约 2.6 GB，64 GB 显存最多可并发 24 个请求，利用率约 `(300/2048)≈14.6%`，浪费严重。

- PagedAttention：每请求实际占用与长度成正比，约为 `300/2048 * 2.6 GB ≈ 0.38 GB`，加上少量碎片，64 GB 可支撑约 150+ 请求，利用率达 80% 以上。

因此，PagedAttention 从根本上重构了 KV Cache 的存储管理，将显存利用率推向极致，是大模型推理服务实现高吞吐低延迟的关键技术。

#### 使用 PagedAttention 后，prefill 阶段如何分配物理块？与 decode 阶段有何不同？

Prefill 阶段的物理块分配：

- 在请求进入时，调度器根据其 prompt 长度 一次性估算并分配足够容纳整个 prompt 的物理块数量：`num_blocks = ceil(prompt_length / block_size)`。

- 从空闲块池中取出对应数量的物理块，分配该请求，并初始化块表（前 `num_blocks` 个条目填入物理块号，后续为 `-1`）。

- 在 prefill 计算过程中，生成的 K、V 张量按 token 顺序写入这些物理块。最后一个块可能未满，形成少量内部碎片，后续 decode 会在该块上继续填充。

- Prefill 阶段需要一次性分配多块，但只占用与实际 prompt 长度成正比的块数，没有预分配最大长度的浪费。

Decode 阶段的物理块分配：

- 每次生成一个新 token，按需追加。若当前最后一个物理块已满（token 数达到 `block_size`），则从空闲池再分配 一个 新物理块，并将其索引追加到块表末尾。

- 若未满，则直接写入该块的下一个空闲位置，无需新块。

- Decode 分配是惰性的、增量式的，每次最多 1 个块，显存占用随序列增长平滑上升。

核心区别总结：

| 阶段 | 分配时机 | 分配数量 | 特征 |
| --- | --- | --- | --- |
| Prefill | 请求开始时 | 根据 prompt 长度一次性多块 | 块数固定或分块预填充逐步分配 |
| Decode | 每次 token 生成后需要时 | 每次最多 1 块 | 惰性动态增长 |

这种分离使得长 prompt 和长生成各自得到优化：prompt 不会浪费 decode 预留的空间，decode 也不会因为预先分配过长而耗尽显存。

#### 在连续批处理中，PagedAttention 如何支持新请求加入时块的分配和旧请求完成时块的回收？

新请求加入时的块分配：

- 调度器在每轮迭代结束后，从等待队列取请求。首先计算其所需初始块数（基于 prompt 长度）。

- 检查空闲物理块数量是否足够。若足够，立即分配这些块，构造块表，并将请求加入运行集。然后该请求参与后续 prefill（可能分块）和 decode。

- 若空闲块不足，调度器可能延迟该请求、触发抢占（换出一些运行请求的块），或拒绝请求（流量控制）。

旧请求完成时的块回收：

- 当请求生成 EOS 或达到最大长度，标记为完成。调度器在迭代结束后，遍历该请求的块表，将所有被引用的物理块释放回空闲池。

- 对于共享块（如来自相同前缀），采用引用计数机制：每个物理块维护一个引用计数，当块被分配给新请求或共享时计数增加；当请求完成且不再需要该块时计数减一；当计数归零时，该块才真正回收为空闲。

- 被回收的块立刻可供其他请求使用，无需等待整体批次结束。

连续批处理的配合：

- PagedAttention 的块分配和回收是操作极快的纯逻辑操作（修改块表和空闲链表），没有数据搬运。因此可以在每次迭代之间无缝进行，不增加明显的调度延迟。

- 这种动态的、细粒度的显存管理是连续批处理能维持高 batch 饱和度的基础：资源一旦释放立刻复用，新请求得以快速注入。

#### 解释 PagedAttention 中的“copy-on-write”机制在并行采样（如 beam search）中的应用。

在并行采样或 beam search 中，一个 prompt 会产生多个候选序列。这些序列最初共享 prompt 的 KV Cache，但在 decode 过程中各自走向不同的 token，形成分叉。

PagedAttention 使用写时复制（Copy-on-Write, COW）来管理这种共享与分叉：

1. 初始共享：当从同一 prompt 启动多个采样序列时，它们的块表中，prompt 部分的逻辑块指向相同的物理块。每个物理块的引用计数设为序列数（例如 `num_samples`）。

2. 分叉点：在 decode 阶段，所有序列都从 shared prompt 开始生成第一个 token。由于每个序列生成的 token 不同，它们需要将新 token 的 K、V 写入各自独立的物理块。对于 prompt 部分，它们只读共享块，不会修改。

3. 写时复制触发条件：如果某个序列需要修改一个共享块（例如，在分块预填充中后续写满了该块？但实际 prompt 块在 prefill 后不会再被修改，除非有极特殊的设计）。在标准 decode 中，共享块始终只读，因此通常不需要真正触发 COW。真正需要 COW 的场景是：当某个序列需要在原本共享的逻辑块范围内插入或修改 KV（如某些回溯策略），或者当块内未满但需要写入导致影响其他序列时。但 PagedAttention 中，每个序列的逻辑块一旦被填满并共享，后续写入只会发生在新的独立块上。因此，COW 更多是一种防御性机制，确保万一有共享块被写入时，先拷贝再修改，避免污染其他序列。

4. 实现：当检测到要对一个 `ref_count > 1` 的物理块进行写操作时，分配一个新物理块，将原块数据拷贝过去，将请求的块表对应项指向新块，原物理块引用计数减一（可能归零回收），然后写入新块。

应用收益：COW 使得并行采样的显存开销接近单个序列加上每个额外序列的差异部分，而非完整的 `num_samples` 倍。这在需要大量采样（如评估时生成多个答案）时节省极为可观的显存。

---

#### 如果用 PagedAttention 实现多个并行生成的序列（如多个采样），它们的物理块如何共享和分歧？

共享部分：

- 所有序列共享 prompt 的物理块（完全相同）。这些块的引用计数 = 采样数。

- 在 prompt 处理完毕后，每个序列的块表最初完全相同（全部指向共享块）。

分歧过程（Decode 阶段）：

- 第一轮 decode：每个序列各自生成 token_1，但此时它们各自需要一个新物理块来存储 token_1 的 K、V。因为 token_1 不同，不能共享，所以为每个序列分配独立的物理块，并追加到各自的块表中。此时引用计数：prompt 块仍然是 `num_samples`（只读）；各序列自己的新块引用计数为 1。

- 第二轮 decode：若上一步分配的块未满（如 block_size=16，则新块还有 15 个空位），则每个序列继续在自己的这个块中追加 token_2，仍不共享。若某序列的块满了，则再分配一个独立块。

- 因此，从分叉点开始，每个序列产生的 KV 都写入各自完全独立的物理块中，不再共享。这自然形成“共享前缀 + 私有后缀”的物理块布局。

块表管理：调度器为每个序列维护独立的块表，初始相同，之后各自扩展。当某个序列完成时，将其私有块回收，同时 prompt 共享块的引用计数减一；只有当所有采样序列都完成，prompt 共享块才被回收。

无需特殊同步：因为生成过程中，各序列写入的物理块是完全隔离的（COW 保证了写入安全），因此可以完全并行地执行，没有任何锁竞争。这相比传统需要完整拷贝 KV Cache 的方案，性能和显存优势巨大。

#### 如何评估 PagedAttention 的内存节省效果？用 13B 模型，分析最大 batch size 的提升。

评估方法： 比较相同显存预算下，使用传统连续分配和 PagedAttention 所能支持的最大并发请求数（max batch size），同时考虑平均序列长度和长度分布。

13B 模型假设：

- 参数：13B，d_model = 5120，层数 L=40，头数 h=40，头维度 d_head=128。

- 数据类型：FP16（2 bytes）。

- 单个 token 的 KV Cache 大小（每层）：`2 * h * d_head * 2 bytes = 2 * 40 * 128 * 2 = 20480 bytes ≈ 20 KB`。

- 40 层总计：`40 * 20 KB = 800 KB / token`。

- 显存预算：假设 GPU 显存 80 GB，其中模型权重约 26 GB (13B * 2 bytes)，剩余给 KV Cache 和其他开销约 54 GB。

传统连续分配（预分配 max_length=2048）：

- 每个请求固定预分配：`800 KB * 2048 = 1638.4 MB ≈ 1.6 GB`。

- 最大并发请求数：`54 GB / 1.6 GB ≈ 33.75`，即约 33 个请求。

- 即使平均请求长度仅 300 token，显存利用率仅为 `(300/2048) ≈ 14.6%`，大量浪费。

PagedAttention（block_size=16）：

- 每 token 占用 800 KB 固定，物理块大小 16 token = `16 * 800 KB = 12.8 MB`。内部碎片平均半个块（8 token），即约 6.4 MB 浪费/请求，相比于显存占用，比例极低。

- 以平均长度 300 token 为例，每请求平均占用 `300 * 800 KB + 碎片 ≈ 240 MB + 6.4 MB ≈ 246.4 MB`。

- 最大并发：`54 GB / 0.246 GB ≈ 219`，理论可支持 200+ 请求。

- 相较于传统的 33 请求，提升约 6~7 倍。即使考虑调度开销和块表，实际提升通常在 3~5 倍。

考虑长度分布的影响：若混合长短请求，PagedAttention 优势更大，因为短请求不会占用过多空间，空闲块能被立即复用，整体显存利用率可达 90% 以上。

#### PagedAttention 对注意力内核的修改是否会引入额外计算开销？通常可以忽略吗？

确实引入了少量额外开销，但经过精心设计后，在 decode 阶段几乎可以忽略；在 prefill 阶段略明显，但仍远小于其带来的吞吐收益。

额外开销来源：

1. 块表查询：每次计算注意力时，kernel 需要根据逻辑块索引从块表加载物理块地址。这需要额外的寄存器、共享内存带宽或常量内存读取。块表通常较小，可以缓存在 L1/共享内存中，一次加载后反复使用。

2. 块循环开销：传统连续缓存可一次加载整个 KV 序列；PagedAttention 需要循环处理每个块，增加了循环计数、地址计算和跳转指令。

3. 非连续访问造成的潜在性能损失：虽然物理块内部连续，但块与块之间地址不连续。如果 GPU 内存子系统预取不佳，可能在块边界出现流水线断流。不过通过异步拷贝预取（`cp.async`）提前加载下一块，可以有效隐藏延迟。

4. 内核复杂度：为了实现分页，内核逻辑比简单的连续版本更复杂，可能增加指令缓存压力。

量化评估：

- Decode 阶段（主要瓶颈是内存带宽）：PagedAttention kernel 的实测延迟与理论带宽极限非常接近，表明非连续加载的额外开销已被预取和指令重叠充分隐藏。vLLM 的数据显示，其在 A100 上的 decode 吞吐与理想的连续缓存内核相差在 5% 以内，可视为基本无额外开销。

- Prefill 阶段（计算密集）：使用分块的 FlashAttention 变体，非连续加载使得计算与数据搬运的重叠略复杂，但配合分块预填充（Chunked Prefill），额外开销也在 10% 以内。考虑到显存节省带来的更大 batch size，系统净吞吐反而大幅提升。

结论：PagedAttention 引入的额外计算开销在高效实现下可被有效掩盖，属于可忽略的微幅代价，而其带来的显存利用率革命性提升和弹性调度能力是绝对超值的。

#### 当模型有 GQA 或多头时，PagedAttention 块中存储的 KV 头组织方式是否需要调整？

需要根据 GQA/MQA 的特性调整物理块的内部布局，以最大化内存带宽利用和计算效率。

标准 MHA 的布局：

- 一个物理块包含 `block_size` 个 token，对于 每个头 独立存储 K 和 V。如果物理块按层划分，通常在该层的所有头连续存储。例如，布局可能是 `[token_0: head_0...head_h, token_1: head_0...head_h, ...]`，或者按头分组 `[head_0: token_0...token_b, head_1: ...]`。

- vLLM 等实现通常采用按头分组的布局：一个块内，同一个头的所有 token 的 K 连续存储，然后下一个头的 K，再是 V 同样组织。这样做是因为注意力 kernel 以头为单位并行，每个线程块处理一个头，这样访问连续，避免交叉访问。

GQA/MQA 的调整：

- GQA 下 KV 头数 `g` 远小于 Q 头数 `h`。物理块同样可以按 KV 头 分组存储。例如，对于 `g=8`，有 8 个 KV 头，每个 KV 头服务一组 Q 头。块内布局为 `KV_head_0: token_0..token_b, KV_head_1: ...`。

- 在注意力计算时，kernel 根据 Q 头索引找到对应的 KV 头，然后加载该 KV 头的物理块数据。由于多个 Q 头共享同一 KV 头，这些 Q 头的线程块可以复用同一份 K、V 块数据，大大减少了 HBM 读取总量，这本身就是 GQA 的优势。PagedAttention 的分页机制与此完美兼容：只需按照 KV 头数而不是 Q 头数来划分和组织物理块，存储量自然减少。

- 不需要额外调整块大小，只是块内部各头的存储量减少（因为头数少）。分页机制仍然以 token 块为单位分配，块内元数据、地址计算与 MHA 一致，只是每个头的维度或头数变了。

结论：PagedAttention 的块组织方式与 GQA/MQA 天然协调：通过减少 KV 头数，物理块的总字节数减少，同样显存下可以容纳更多块，进一步提升并发。内核实现需正确映射 Q 头到 KV 头并共享块加载。

#### 为什么有些框架（如 TGI）也有类似分页的机制？与 vLLM 的 PagedAttention 有何异同？

TGI（Text Generation Inference） 也采用了分页或类分页思想来管理 KV Cache，称为 Paged KV Cache 或 块缓存。其动机与 vLLM 相同：解决预分配连续缓存导致的显存浪费和碎片。

相同点：

- 都将 KV Cache 划分为固定大小的块，按需分配和释放，消除预分配浪费。

- 支持动态 batch 和连续批处理，利用块映射表实现逻辑到物理的转换。

- 都支持前缀共享和写时复制（在并行采样中）。

主要差异：

| 维度 | vLLM (PagedAttention) | TGI (HuggingFace) |
| --- | --- | --- |
| 内核实现 | 自研高度优化的 CUDA kernel（paged_attention_kernel），专为分页设计，与 FlashAttention 深度集成 | 基于 PyTorch 或优化较少的 kernel，部分使用 torch.scatter 或循环实现非连续读取，效率低于 vLLM 自研 kernel |
| 块粒度与管理 | 块大小较小（默认 16/32），极其细致的显存控制；块表在 GPU 上传递 | 早期版本块较大或采用不同粒度，优化程度略低 |
| 与调度器的耦合 | 紧密耦合，支持连续批处理、抢占、分块预填充等高级特性 | 也支持连续批处理，但整体架构和优化深度略逊 |
| 社区与专有性 | vLLM 专注推理性能，开源社区活跃，已被多家云服务采用 | TGI 是 HuggingFace 官方推理解决方案，与 HF 生态集成更好，更易用 |
| 前缀缓存 | 通过块哈希自动实现 prefix caching（automatic prefix caching） | 也支持，但实现细节有差异 |

总结：TGI 的类分页机制在概念上与 vLLM 的 PagedAttention 类似，但 vLLM 的内核优化更激进，因此在极限吞吐和延迟上通常略胜一筹；TGI 则在 HuggingFace 生态的兼容性和易用性上有优势。两者共同推动了分页式 KV 缓存管理成为行业标准。

#### PagedAttention 是否适用于 encoder‑decoder 模型中的交叉注意力 KV 缓存？

适用，但需要将分页管理扩展到 encoder 输出缓存。

在 encoder-decoder 模型（如 T5、Whisper）中，除了 decoder 的自注意力 KV Cache，还有 交叉注意力（cross-attention）的 KV 缓存，其 K、V 来自 encoder 的最终输出（对所有输入 token 的编码）。这些 encoder K、V 在整个 decoder 生成期间是静态只读的。

PagedAttention 的适配：

- 将 encoder 输出的 K、V 同样组织为固定大小的物理块，建立encoder 块表。不同请求的 encoder 输入长度不同，故 encoder 块数不同。

- 在 decoder 的交叉注意力计算时，kernel 根据请求的 encoder 块表和该层交叉注意力的 K、V 存储布局，加载对应块的 K、V 数据。

- 共享潜力：如果多个请求共享相同的 encoder 输入（例如批量翻译同一句话），它们的 encoder KV 块可以共享，大幅节省显存。

- 内存管理：encoder 块在请求的生命周期内始终存在（只读），直到请求完成才释放。同样采用引用计数，可跨请求共享。

与纯 decoder 的区别：

- 需要维护两套块表：一套用于 decoder 自注意力（动态增长），一套用于 encoder 交叉注意力（静态）。

- 内核需要支持双路分页加载：自注意力从 decoder 块表读，交叉注意力从 encoder 块表读。这增加了内核参数和逻辑复杂度，但原理完全一致。

- Prefill 阶段需要为 encoder 处理分配块并写入，之后 decoder 方可开始。

结论：PagedAttention 完全可以推广到 encoder-decoder 模型，通过独立管理 encoder KV 块实现了统一的分页缓存架构。当前 vLLM 的实验性支持已经在做此类扩展。

#### 当使用 FlashAttention 结合 PagedAttention 时，如何在内核中实现分页查询？

vLLM 等框架将 FlashAttention 的分块计算 与 PagedAttention 的分页加载 融合，形成 `flash_attn_with_kvcache` 等高效内核。

融合原理：

- FlashAttention 本身循环加载 K、V 块（沿序列长度分块）到 SRAM，与 Q 块计算。在支持连续 KV Cache 时，K、V 块的地址是连续递增的。

- 要实现分页，内核在每次加载 K、V 块之前，通过块表将逻辑块索引转换为物理块地址，然后从该物理地址加载连续的 `block_size` 个 token 的 K、V。

- 具体步骤：
  1. 确定本轮需要处理的逻辑序列范围，计算起始逻辑块号和块内偏移。
  2. 通过 `block_table` 获得对应的物理块号 `p`，计算出该物理块的 K、V 数据起始指针 `K_ptr = base + p * block_bytes + offset_in_block`。
  3. 使用 `cp.async` 或类似异步指令，将 `block_size` 长度（或剩余长度）的 K、V 从 HBM 预取到 SRAM。
  4. 执行 FlashAttention 的标准循环：在 SRAM 中计算 QK^T、online softmax、更新输出。
  5. 逻辑序列递增，如果跨越块边界，则更新物理块号指针，继续预取下一块。

优化细节：

- 为了避免在每个块都计算块表，可以一次性将当前请求的整个块表条目预加载到寄存器或共享内存中。

- 物理块内部连续，与 FlashAttention 原本的分块连续性假设完全兼容，因此只要解决了地址映射，循环体几乎不需要改动。

- 由于分页导致的非连续，预取距离可能需要调整，确保在需要数据前发出加载请求，隐藏延迟。

因此，结合的关键就是在 FlashAttention 的外层循环中加入一次“地址重映射”，将逻辑连续变为物理块内连续、块间跳转的访问模式。 这种融合让分页管理和高效注意力计算结合得天衣无缝。

#### 如何保证 PagedAttention 分配和释放块的并发安全性（多线程环境）？

在推理服务中，CPU 端的调度器和内存管理器可能被多个线程访问（如同时接收新请求、处理完成回调）。必须确保物理块池的分配和释放是线程安全的。

典型实现方案（以 vLLM 为例）：

1. 全局块池由锁保护：使用 `BlockTable` 或 `CpuGpuBlockAllocator` 类，内部维护 `free_blocks` 列表（或栈），以及每个物理块的引用计数。所有分配（`allocate`）和释放（`free`）操作都使用互斥锁（`std::mutex` 或 Python 的 `threading.Lock`）串行化，或者使用无锁队列（如 `boost.lockfree`）提升性能。

2. 请求级的隔离：每个请求对象持有自己的块表（逻辑块到物理块映射），分配和释放由调度器在单个调度线程中集中处理。vLLM 的调度循环是单线程的（或在持有 GIL 的 Python 线程中），逐次进行决策，从而避免了多线程直接竞争块池。异步事件通过消息队列通知调度线程。

3. 引用计数的原子操作：对于共享物理块，引用计数需要原子更新。可以使用 C++ 的 `std::atomic<int>` 或 Python 的 `multiprocessing.Value`。当引用计数降为 0 时，将块回收到空闲池，回收操作需要加锁或通过无锁结构。

4. CUDA 操作的同步：在释放物理块之前，必须确保 GPU 上已经没有任何未完成的 kernel 正在使用该块。vLLM 通过等待 CUDA stream 完成（`cudaStreamSynchronize`）或使用事件来保证安全释放。

5. Python GIL 的作用：在 vLLM 早期版本，由于大量逻辑在 Python 层且 GIL 保护，某些操作天然串行。但为避免性能瓶颈，核心分配器常用 C++ 实现，并通过细粒度锁或无锁结构提供并发安全。

总结：通过集中式调度器 + 互斥锁保护空闲池 + 原子引用计数 + GPU 同步，PagedAttention 的分配与释放可保证在多线程环境下正确且高效地运行，不会出现数据竞争或泄漏。
