# 123.大模型（LLMs）服务化部署（API 设计、负载均衡）

#### 请设计一个 LLM API 的请求和响应数据结构，需要考虑流式输出。

设计 LLM API 的数据结构，需要在 丰富性、可扩展性和通用性之间找到平衡。以下是一个以 OpenAI Chat Completions API 为蓝本，并针对流式输出进行增强的设计。

请求数据结构 (Request)

```json
{
  "model": "my-llm-v2",                 // 必填：模型名称或ID
  "messages": [                          // 必填：对话消息列表
    {
      "role": "system",                  // 角色：system, user, assistant, tool
      "content": "你是一个有用的助手。"
    },
    {
      "role": "user",
      "content": "你好，请解释一下量子计算。"
    }
  ],
  "stream": true,                        // 是否启用流式输出
  "max_tokens": 2048,                    // 最大生成token数
  "temperature": 0.7,                    // 采样温度
  "top_p": 0.9,                          // 核采样参数
  "stop": ["\n", "###"],                 // 停止词
  "frequency_penalty": 0.0,
  "presence_penalty": 0.0,
  "logit_bias": { "12345": -100 },       // 调整特定token的概率
  "user": "user-123",                    // 终端用户标识（用于监控和限流）
  "metadata": {                          // 可选的透传元数据
    "session_id": "sess-456",
    "trace_id": "trace-789"
  }
}
```

设计要点：

- `messages` 列表完整保留对话历史，使模型能理解上下文。`role` 字段严格区分角色，这是实现多轮对话的基础。

- `stream` 字段是控制流式输出的开关，简单明了。

- 采样参数 (`temperature`, `top_p`) 与标准定义一致，便于用户控制生成多样性。

- `metadata` 允许客户透传自定义信息，方便日志关联和审计。

非流式响应数据结构

```json
{
  "id": "chatcmpl-9a7b8c",              // 本次请求唯一ID
  "object": "chat.completion",           // 对象类型
  "created": 1723456789,                 // 时间戳
  "model": "my-llm-v2",                 // 实际使用的模型
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "量子计算是一种利用量子力学原理... (完整回答)"
      },
      "finish_reason": "stop"           // stop, length, content_filter, tool_calls
    }
  ],
  "usage": {                             // token 使用量统计
    "prompt_tokens": 25,
    "completion_tokens": 150,
    "total_tokens": 175
  }
}
```

流式响应数据结构

当 `stream=true` 时，服务端以 Server-Sent Events (SSE) 格式推送一系列数据块。每个数据块是一个独立的 JSON 对象，包含增量更新信息。

```plain text
data: {"id":"chatcmpl-9a7b8c","object":"chat.completion.chunk","created":1723456790,"model":"my-llm-v2","choices":[{"index":0,"delta":{"role":"assistant","content":"量子"},"finish_reason":null}]}\n\n
data: {"id":"chatcmpl-9a7b8c","object":"chat.completion.chunk","created":1723456791,"model":"my-llm-v2","choices":[{"index":0,"delta":{"content":"计算"},"finish_reason":null}]}\n\n
...
data: {"id":"chatcmpl-9a7b8c","object":"chat.completion.chunk","created":1723456795,"model":"my-llm-v2","choices":[{"index":0,"delta":{},"finish_reason":"stop"}],"usage":{"prompt_tokens":25,"completion_tokens":150,"total_tokens":175}}\n\n
data: [DONE]\n\n
```

流式数据结构设计要点：

- 使用 `delta` 而非 `message`，表示增量内容。首个 chunk 可包含 `role`，后续只包含 `content` 的片段。

- 每个 chunk 都带有 `finish_reason`，在非结束时为 `null`，结束时为 `"stop"` 或 `"length"`。

- 最后一个 chunk 可携带 `usage` 信息，避免额外的非流式调用。

- 末尾用 `data: [DONE]` 标记流结束，这是 SSE 的常见实践。

这种设计使得客户端可以逐字渲染回复，显著提升用户体验，同时保持与 OpenAI 生态的兼容性，方便接入现有工具和框架。

#### LLM API 的流式输出是如何实现的？常用哪种协议或技术？

LLM API 的流式输出，其核心在于将模型生成 token 的过程与 HTTP 响应传输解耦，使得服务端可以一边生成 token，一边将已生成的 token 通过网络推送给客户端，而不必等待全部生成完毕。

实现原理：在传统的非流式模式下，LLM 必须生成完整个序列后，才将结果打包成一个 JSON 响应返回。流式模式则不同：模型自回归地生成每个 token 时，服务端立即将其包装成一个事件（event），写入到 HTTP 响应体中，并立即刷新缓冲区（flush），客户端就可以逐条接收并处理这些事件。

常用协议/技术：Server-Sent Events (SSE)

SSE 是 W3C 标准，是一种基于 HTTP 的轻量级推送协议，非常适合 LLM 的流式输出。

- 工作原理：
  1. 客户端发送一个常规 HTTP GET/POST 请求，并在请求头中指定 `Accept: text/event-stream`。
  2. 服务端收到请求后，返回一个 `Content-Type: text/event-stream` 的响应头，并保持连接不关闭。
  3. 服务端通过该持久连接，不断向客户端推送以 `data:` 开头的文本行。每行代表一个事件。
  4. 事件之间用空行 `\n\n` 分隔。
  5. 当生成结束时，服务端发送一个特殊事件（如 `data: [DONE]\n\n`）并关闭连接。

- 为什么选择 SSE：
  - 简单：基于纯文本和 HTTP，实现和调试都非常容易。任何支持 HTTP 的库都可以轻松消费。
  - 单向推送：非常契合 LLM 生成（服务端→客户端）的单向数据流。
  - 自动重连：SSE 规范支持浏览器自动重连，增强了鲁棒性。
  - 广泛支持：OpenAI, Anthropic, Google 等几乎所有 LLM 提供商的流式 API 都基于 SSE。

- 其他可选技术：
  - WebSocket：全双工通信，适合需要客户端频繁向服务端发送数据的场景（如语音对话）。但用于纯文本生成时，其复杂性高于 SSE，不如 SSE 轻量。
  - gRPC 流：基于 Protocol Buffers，性能极高，适合内部微服务之间的流式通信。但对于公网 API，兼容性和调试便利性不如 HTTP+SSE。

服务端实现关键点：

1. 确保 HTTP 响应头 `Content-Type` 和 `Transfer-Encoding: chunked` 正确设置。

2. 在生成每个 token 后，立即调用 `response.write()` 并 `flush()`，避免框架缓冲导致客户端长时间无响应。

3. 异常处理：生成过程中若发生错误，应通过 SSE 事件发送错误信息，然后关闭连接。

#### 如何设计一个兼容 OpenAI API 格式的模型服务？

设计兼容 OpenAI API 的服务，不仅是为了方便用户迁移，更是为了无缝融入已有庞大的 AI 应用生态（如 LangChain, LlamaIndex, AutoGPT 等）。其核心是实现一个 API 网关/适配层，将 OpenAI 格式的请求转换为你后端模型可以理解的格式，并将模型输出转换回 OpenAI 格式。

架构设计：

```plain text
客户端（OpenAI SDK） -> 兼容API网关 -> 路由/调度 -> 推理引擎（vLLM/TGI） -> 模型
```

关键实现步骤：

1. 接口定义与路由：完全实现 OpenAI API 的核心端点，如 `/chat/completions`、`/completions`、`/embeddings`、`/models`。API 网关需要能够准确解析 OpenAI SDK 发送的请求格式，包括其复杂的参数体系。

2. 请求转换（适配层）：这是最核心的部分。将 OpenAI 格式的请求体转换为后端推理引擎能接受的格式。例如：
  - 将 `messages` 列表（带有 `system`/`user`/`assistant` 角色）拼接成特定格式的 Prompt 字符串，或者直接映射为你模型微调时使用的 ChatML 格式。
  - 将 `temperature`, `max_tokens` 等参数映射到推理引擎的配置项。
  - 对于 `stop` 词、`logit_bias` 等高级参数，需要在推理引擎中找到对应的功能实现或进行后处理。

3. 后端推理引擎集成：选择高性能的推理引擎，如 vLLM, TensorRT-LLM, Hugging Face TGI。这些引擎提供了高性能、内存高效的推理能力，并常内置了 OpenAI 兼容的 API 服务器（如 vLLM 的 `--api-key` 模式），可以直接作为后端，极大简化开发。

4. 响应转换与流式兼容：
  - 非流式：将推理引擎返回的完整文本，封装为标准 OpenAI 响应 JSON。
  - 流式：监听推理引擎的 token 生成事件，将其逐个封装为 SSE `data: {...}` 块，包含 `id`, `object`, `choices[0].delta.content` 等字段。第一个块需包含 `role`，最后一个块需设置 `finish_reason`，并在末尾发送 `[DONE]`。

5. 模型列表与兼容性：实现 `/models` 端点，返回一个包含你部署模型名称和 ID 的列表，让客户端 SDK 能自动发现可用模型。

6. 高级特性兼容：OpenAI API 还包括 `function calling` (Tools)、`logprobs` 等特性。如果后端模型和引擎支持，应当在兼容层实现这些功能；否则，可以返回一个明确的错误信息。

使用 vLLM 等已有框架是实现此目标的最快路径，因为它已经内置了完整的 OpenAI 兼容服务器。对于需要定制或统一多个异构后端的平台，则需要自研一个更复杂的网关层。

#### 什么是请求队列和批处理（Batching）？如何提升 GPU 利用率？

LLM 推理是计算密集型任务，GPU 是昂贵的核心资源。请求队列和批处理是提升 GPU 利用率、增大系统吞吐量的核心技术。

请求队列：当多个用户同时发送请求时，所有请求首先进入一个调度队列，而不是立即被处理。调度器根据一定的策略（如 FCFS 先来先服务、优先级队列、最大等待时间等）从队列中取出请求，组批后发送给 GPU 进行推理。队列起到了削峰填谷、平滑负载的作用。

批处理：将多个独立的推理请求组合成一个批次（Batch），一次性送入 GPU 进行计算。GPU 的并行架构使得处理一个批次的时间远小于单独处理每个请求的时间总和。批处理能显著提升吞吐量。

提升 GPU 利用率的关键挑战：LLM 自回归生成的特性使得传统批处理面临巨大困难。

- 请求长度不一：有些请求只需要生成几个 token，有些则需要长篇大论。在传统批处理中，整个批次必须等到所有请求都生成完毕才能释放，导致 GPU 大部分时间在等待长请求而处于空闲状态。

- 流水线气泡：一个请求的生成过程包括多个迭代，不同请求可能同时处于推理的不同阶段，如何将它们高效地组合在一起是一项挑战。

解决方案：连续批处理（见下一题）

为了提升 GPU 利用率，在架构上通常这样做：

1. 使用高性能推理引擎（vLLM, TensorRT-LLM），利用其 PagedAttention 和连续批处理技术。

2. 设置合适的调度策略：动态地将新请求插入到正在运行的批次中（`continuous batching`）。

3. 合理配置 `max_batch_size` 和 `max_num_seqs` 参数，平衡吞吐与延迟。

4. 使用量化（INT8/INT4）和分页注意力，降低单个请求的显存占用，使得在相同硬件上能同时处理更多请求。

通过这些技术，GPU 利用率可以从传统静态批处理的 30-50% 提升到 90% 以上，吞吐量实现数倍的增长。

#### 连续批处理（Continuous Batching）的原理和优势是什么？

连续批处理（Continuous Batching），也称作 In-flight Batching 或 Iteration-level Batching，是当前主流 LLM 推理引擎（vLLM, TGI, TensorRT-LLM）实现高吞吐的核心技术。

原理：它打破了传统静态批处理“必须等整个批次处理完才能处理下一批”的限制。在连续批处理中，推理过程被分解为逐个 token 的迭代。在每次迭代（生成一个 token）结束时，调度器都有机会重新调整处理中的请求组合。

- 动态插入新请求：当一个新请求到达时，不会等到当前批次全部完成，而是直接在下一个迭代开始时，将其插入到正在运行的请求组中。

- 即时释放已完成请求：当一个请求完成生成（即遇到 EOS token）时，它会被立即从当前批次中移除，其占用的 GPU 显存和计算槽位被立刻释放，供其他等待中的请求使用。无需等待同批次中的其他“慢请求”。

核心优势：

- 极高的 GPU 利用率：GPU 几乎总是满负荷运行。不会因为等待慢请求而让计算核心闲置。新请求可以填补那些已完成请求释放出的计算空间。

- 低延迟与高吞吐并存：与静态批处理相比，它在不增加延迟的前提下，将吞吐量提升了数倍甚至一个数量级。

- 有效应对变长生成：完美解决了生成任务中不同请求长度差异巨大的痛点。

实现要点：连续批处理需要精细的内存管理，因为动态地插入和移除请求会导致显存碎片。PagedAttention 技术正是为此而生，它通过分页机制管理 KV Cache，实现了零碎片的动态内存分配和回收。

#### 负载均衡在 LLM 服务中的常用策略有哪些？

当 LLM 服务由多个模型实例（多个 GPU、多个节点）支撑时，负载均衡器负责将海量 API 请求智能地分发到各个后端实例，以确保系统整体的高可用、低延迟和资源利用率。常用策略分为以下几类：

一、通用反向代理层策略

在入口层，使用 Nginx, Envoy 等通用代理即可实现基础负载均衡。

- 轮询：最简单地轮流分发。

- 最少连接：将请求发给当前活跃连接数最少的后端，适合处理长短连接混合的场景。

- IP 哈希：基于客户端 IP 进行哈希，保证来自同一用户的请求始终落到同一个后端。这对需要会话保持（如利用显存缓存来加速重复 Prompt）的场景非常有用。

二、LLM 专用调度策略

在推理引擎层面，调度器需要做出更智能的决策，因为每个请求的计算成本（Prompt/生成长度）差异巨大。

- 最少 token 数：将新请求发送到当前累积待处理 token 总数最少或 KV Cache 占用最低的实例。这能最直接地平衡 GPU 的计算和显存压力。

- 基于前缀匹配的亲和性调度：如果负载均衡器能感知到请求 Prompt 的相似性，它可以将具有相同系统提示词的请求调度到同一个实例上。vLLM 等引擎支持 Prefix Caching，可以复用相同前缀的计算结果和 KV Cache，从而极大加速推理。这种调度策略能最大化 Prefix Caching 的收益。

三、高级容错与弹性策略

- 健康检查：代理定期探测后端实例的 `/health` 端点，自动剔除不健康或过载的实例。

- 速率限制与排队：当所有实例都达到其最大并发限制时，在负载均衡层进行排队或直接返回 503（服务暂时不可用）。

- 权重路由：为不同算力的实例（如 A100 和 H100）设置不同的权重，以更合理地分配负载。

- 金丝雀发布与流量镜像：当新模型版本上线时，先分配少量流量（如 5%）进行验证，稳定后再逐步增大流量比例。同时，可将生产流量复制一份发给新版本来评估其效果。

#### 如何设计一个支持多模型、多版本的统一推理平台？

设计这样的平台，核心目标是将模型管理与推理服务解耦，实现灵活、高效的部署和迭代。

整体架构：

```plain text
客户端 SDK / API -> 统一网关 -> 模型路由与调度层 -> 推理引擎池 (vLLM/TGI) -> 模型仓库（存储）
```

核心组件设计：

1. 模型注册中心：一个元数据数据库，存储所有已注册模型的信息，包括：
  - 模型唯一 ID（如 `llama-3-70b-instruct`）
  - 版本号（如 `v1`, `v2`, `production`, `canary`）
  - 模型文件在对象存储（如 S3）中的路径
  - 运行配置（所需 GPU 类型、显存、推荐批处理大小等）
  - 模型类型（LLM, Embedding, Reranker）

2. 统一推理网关：
  - 接收所有 API 请求，解析请求中的 `model` 参数。
  - 根据路由表，将请求映射到负责该模型/版本的具体推理服务实例组。
  - 负责认证、限流、日志记录等公共功能。

3. 模型路由器与版本策略：
  - 支持灵活的版本指向策略：`production` 标签指向最稳定的版本，`latest` 指向最新版本，也支持用版本哈希直接访问。
  - 支持流量分发：将特定百分比的流量分配给金丝雀版本，实现平滑上线。

4. 推理引擎池与自动化运维：
  - 模型不是直接运行在裸机上，而是容器化后由 Kubernetes 等进行编排。
  - 可以水平自动伸缩。例如，当发现负责某个热门模型的推理服务负载过高时，自动增加 Pod 数量；冷门模型长时间无请求时，可以将实例缩容到 0，以节省算力。
  - 模型版本更新时，采用滚动更新或蓝绿部署，保证服务不中断。

5. 存储与模型分发：
  - 所有模型文件集中存储在高性能共享存储（如 Ceph, MinIO）或对象存储中。
  - 当一个新的推理 Pod 启动时，通过 Init Container 或预加载机制，从存储中快速拉取模型文件到本地 SSD 或加载到 GPU 显存中。

这种平台设计将开发、运维和业务需求完美分离，极大地提升了模型迭代速度和资源利用效率。

#### 什么是“冷启动”问题？如何通过模型预加载或保活机制缓解？

冷启动是指当一个LLM推理服务实例（容器/Pod）被新创建或长时间无请求后被唤醒时，需要将庞大的模型文件从磁盘加载到 GPU 显存的过程。这个过程极其耗时（从数十秒到数十分钟不等），期间服务无法响应任何请求，导致请求超时或失败。

缓解策略：

1. 模型预加载：这是最根本的解决方案。不要等到请求来了再加载模型，而是在服务实例启动的过程中，就把模型加载好，只有当模型加载完成并处于“Ready”状态后，才将其注册到负载均衡器上，开始接收流量。在 Kubernetes 中，这可以通过 `startupProbe` 结合一个健康检查 API 来实现。

2. 实例保活：对于访问频率不高但不可或缺的模型，使用“保温”机制避免其缩容到零。例如：
  - 设置 Kubernetes 的 HPA（水平自动伸缩）最小副本数为 1，即使没有流量也保留一个实例常驻。
  - 实现一个定时 Ping 机制，每隔一段时间（如 5 分钟）向推理服务发送一个简单的请求，确保其活跃状态。
  - 尽管这会浪费一些空闲资源，但对于需要保证低延迟的高优先级应用是必需的。

3. 延迟缩容：在自动缩容策略中，设置较长的缩容冷却时间。这样，即使在业务高峰期过后，服务实例也会再保留一段时间（如 30 分钟），以应对即将到来的新请求。

4. 模型预热（Warmup）：在模型加载完成后，立即发送一些模拟请求数据，将模型的计算图和相关内存“预热”到一个合适的状态。这可以避免真实用户请求首次命中时出现异常高的延迟。

5. 快速加载技术：优化模型加载速度本身。例如，使用更快的 GPU 显存（如 HBM）和更高效的序列化/反序列化框架；在磁盘到 GPU 的传输路径上使用 GPUDirect Storage 等技术，绕过 CPU，加速模型加载。

#### 如何对 LLM API 进行限流和鉴权？

这是保护 LLM 服务免受滥用、进行成本控制和商业化运营的基础。

一、鉴权

鉴权的目的是回答“你是谁？”和“你能做什么？”。

- API Key 机制：最常用的方式。为每个用户或应用分配唯一的、复杂的 API Key。用户在请求头中携带此 Key（如 `Authorization: Bearer YOUR_API_KEY`）。服务端在网关层验证 Key 的有效性，并将其映射到相应的用户账号和权限策略。

- 多级权限控制：一个用户可能有多个 Key，每个 Key 授予不同的权限，如只读、可访问特定模型、可进行微调等。权限策略可以在网关层统一实施。

- 动态密钥轮换：提供 API 让用户可以自助创建、删除、轮换 API Key，降低密钥泄露风险。

二、限流

限流的目的是回答“你可以用多快？”和“总量可以用多少？”。复杂的 LLM 服务通常需要多维度、分层次的限流。

- 基于 Token 的精确限流：LLM 的成本与 Token 数强相关。最合理的限流不是基于“请求次数”，而是基于 Token 的吞吐量（如 TPM, Tokens Per Minute）。实现时，在网关层解析请求和响应的 `usage` 字段，利用令牌桶算法进行精确控制。

- 多维限流策略：
  - 用户级限流 (Per-User)：对单个用户的 TPM、RPM (Requests Per Minute) 或 TPD (Tokens Per Day) 进行限制。这保证了公平性，防止个别用户的突发流量影响到其他人。
  - 模型级限流 (Per-Model)：对整个集群上某个模型的总体吞吐量设置上限，以保护后端推理服务不过载。
  - 并发限流：使用信号量限制同时处理的请求数，防止等待队列无限增长导致雪崩。

- 友好的限流反馈：当请求被限流时，不要简单地断开连接，而是返回 HTTP 429 (Too Many Requests) 状态码。同时在响应头中提供 `Retry-After`（秒数），告诉客户端何时可以重试。如果可能，将超出限流额度的请求放入一个具有超时和最大长度的等待队列，而非直接拒绝。

- 技术实现：可以在 API 网关（如 Kong, Envoy）中通过插件实现，也可以使用独立的分布式缓存（如 Redis）来存储限流状态，以保证多实例下的状态一致性。

通过精细的鉴权和多维限流，可以实现对 LLM API 服务的商业化管控，保障服务质量，并为不同的服务套餐（SLA）提供技术支撑。

#### 在 API 网关层面，可以为 LLM 调用提供哪些增值功能？

API 网关是 LLM 服务的总入口，它的作用远不止于简单的请求转发。在 LLM 场景中，它可以成为一个强大的“增值服务层”，为上层应用和运维团队提供关键能力。

1. 精细化、基于 Token 的计费与成本归因\
   LLM 的商业本质是按 Token 计费。网关可以精准地解析请求和响应，提取 `usage` 中的 `prompt_tokens`、`completion_tokens` 和模型名，实现多维度的计费：

- 按量计费：为不同的 API Key 或用户账户设置单价，进行实时扣费或记录账单。

- 成本归因：即使是对内服务，网关也能将每个部门、每个项目的 LLM 调用成本精确统计，打破了以往“一刀切”的资源共享模式，实现成本透明化。

2. 高级缓存策略

这是提升用户体验和降低成本的利器。

- 语义缓存：网关可以集成向量数据库，对请求进行语义去重。如果两个请求表述不同但意图相同，网关可以直接返回缓存的答案，无需再次调用昂贵的 LLM。命中率哪怕只有 5%-10%，在巨大体量下都能节省可观的推理成本。

- 前缀缓存感知路由：对于 Chat 类应用，所有请求的 System Prompt 部分是高度一致的。API 网关如果能感知到这种前缀，就可以将与具有相同 System Prompt 的请求路由到同一个后端实例。这能最大化利用 vLLM 等推理引擎的 Prefix Caching 特性，大幅减少重复计算。

3. 安全防护与合规审计

LLM 应用面临着独特的攻击风险。

- Prompt 注入检测：在请求到达模型之前，网关可以部署一个轻量级的安全模型或规则引擎，对用户输入进行扫描，识别并拦截潜在的 Prompt 注入攻击（如“忽略之前所有指令...”），保护模型的行为基线不被篡改。

- 内容安全过滤：对用户输入和模型输出进行双向的内容审核，过滤掉涉黄、涉暴、涉政等违规内容，确保生成内容的安全合规，并留下审计日志。

4. 请求/响应改写与多模型路由

- 格式兼容：网关可以将内部私有模型的 API 格式，动态翻译为 OpenAI 标准格式，让下游应用无痛切换。

- 智能路由：根据请求的复杂度和用户级别，将简单问题路由到 7B 小模型，复杂问题路由到 70B 大模型，实现成本和性能的最佳平衡。

- 负载均衡与降级：当一个模型集群整体过载时，网关可以将部分非关键请求自动降级到备用的小模型，或者在队列中等待，而不是直接返回错误。

#### 如何设计模型服务的健康检查和自动扩缩容策略？

LLM 推理服务的健康状态和资源消耗模式与传统 Web 服务截然不同，其核心是 GPU 显存和计算队列。

健康检查设计

健康检查必须能区分“服务已启动”和“服务已准备好处理请求”。

- 就绪探针：后端推理实例的 API 应提供一个 `/health` 或 `/ready` 端点。该端点在被调用时，不仅检查进程是否存在，更要检查模型是否已完全加载到 GPU 显存中，并且推理引擎是否已完成初始化。只有当这些都完成后，才返回 200 OK。这是决定一个 Pod 能否加入负载均衡的关键。

- 存活探针：需要一种机制来检测“僵尸”实例——进程存活但推理卡死。存活探针可以是一个简单的“心跳”，也可以更严格：如果一个实例连续多次（如5次）请求都超时或返回内部错误，Kubernetes 应将其视为不健康并重启。

自动扩缩容策略

LLM 实例的扩缩容应以 GPU 显存或计算饱和度 为核心指标，而不是 CPU 或普通内存。

- 扩容指标：
  - KV Cache 使用率：这是最精准的指标。当 GPU 显存中可用 KV Cache 块的数量低于阈值时，说明并发能力即将饱和，需要扩容。
  - 请求队列长度/等待时间：当推理请求的平均排队等待时间超过设定的延迟目标时，触发扩容。
  - GPU 利用率/吞吐量：当 GPU 计算核心的利用率持续接近 100% 时，也是一个扩容信号。

- 缩容策略：
  - 冷却时间：必须设置足够的缩容冷却时间（如 5-10 分钟），避免在流量波动时频繁销毁和创建实例，这会导致反复的模型加载（冷启动）。
  - 保护策略：如果预测到定时的高峰流量，可以提前预热并禁止在高峰期间缩容。

- 实现手段：Kubernetes 的 HPA 目前难以直接基于 GPU 显存等自定义指标进行扩缩容。通常需要借助 KEDA 或自研 Controller，通过 Prometheus 采集精细指标，并根据这些指标定义弹性伸缩规则。

#### 对于需要低延迟的场景，如何选择或部署模型服务架构？

追求低延迟（交互式应用如语音助手、搜索等）意味着必须将 TTFT 和 TPOT 这两个指标压到极低。核心策略是“多管齐下”，从架构、模型和调度层面进行优化。

1. 模型选择是第一步

选择一个参数规模适合、延迟可接受的模型至关重要。

- Mixture-of-Experts (MoE)：这类模型总参数量巨大，但单次推理激活的参数量较小。如果能在显存中放下所有专家（或者通过快速交换），它能在提供大模型能力的同时，保持相对较低的延迟。

- 量化模型：使用 INT8 或 INT4 量化的模型。这不仅能大幅降低显存占用（允许更大的 batch size 或 KV Cache），还能减少内存带宽压力，显著加速推理。

2. 推理引擎与部署环境优化

- 选择高性能推理引擎：必须使用 vLLM, TensorRT-LLM 等对低延迟高度优化的框架。它们通过算子融合、内核优化和 PagedAttention 等技术，将推理效率推向极致。

- 利用推测解码：在生成阶段，用一个极轻量的小模型快速生成候选 token，再由大模型并行验证。这能将生成延迟降低约 2-3 倍。

- 硬件选择：使用具有大显存带宽和高计算能力的顶级 GPU（如 NVIDIA H100），并确保模型部署在单机甚至单卡上，避免跨机通信带来的不可控延迟。

3. 优化请求调度与缓存

- 尽力避免排队：这是保证低延迟的关键。调度策略应从“最大化吞吐”转为“优先保证延迟”。这意味着需要预留更多冗余算力，保持较低的 GPU 利用率水位，以随时应对突发请求。

- 充分利用 Prefix Caching：对于具有固定 System Prompt 的对话应用，将请求调度到可以复用其前缀的实例上，可以极大地降低 TTFT。

- 客户端优化：在请求 API 时，`best_of` 等需要多次采样的参数绝对不能用，因为它会成倍增加延迟。流式输出 (Streaming) 必须开启，以降低用户的感知延迟。

#### 请描述一个基于 Kubernetes 的 LLM 服务部署方案。

这是一个典型的、生产级的 Kubernetes 部署方案，充分利用了云原生的声明式管理、自动调度和弹性能力。

1. 基础设施与部署对象

- 节点池：创建一个专门的 GPU 节点池（例如，由配备 NVIDIA A100 或 H100 的机器组成），并打上相应的标签和污点（Taint），确保只有 LLM 推理服务才能调度到这些昂贵的节点上。

- Deployment 或 LeaderWorkerSet：
  - 对于单卡能放下的模型，使用标准的 Deployment 管理多个相同的 Pod 副本。
  - 对于需要跨多张 GPU 的张量并行或流水线并行的模型，使用 Kubernetes 的 LeaderWorkerSet 或其他自定义资源（如 PyTorch Job 的变体）来管理一组关系紧密的 Pod。

2. 核心配置

- 资源请求与限制：在 Pod Spec 中，必须精确声明所需的 GPU 资源：

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

- 只有声明了资源，调度器才能正确地将 Pod 分配到有可用 GPU 的节点上。

- 健康探针：配置一个 `readinessProbe`，定期调用模型的 `/health` 端点，确保模型加载完成后 Pod 才被标记为 Ready，从而接入服务。

- 模型分发：
  - Init Container + 共享存储：最简单的方案。使用一个 Init Container 将模型文件从对象存储（如 S3）拷贝到一个 `emptyDir` 卷（或基于 SSD 的 PVC）中，然后主容器加载模型。每次 Pod 启动都要拷贝，可能较慢。
  - Persistent Volume Claim (PVC) + ReadOnlyMany：对于更大的模型，提前将模型拷贝到一个共享的 PVC（如基于 NFS 或高性能并行文件系统）中，Pod 启动时直接只读挂载。启动速度快，但对存储系统有要求。
  - Container 镜像内嵌模型：将模型文件直接打包到 Docker 镜像中。这是最快的启动方式，但镜像体积会非常庞大。

3. 网络与服务暴露

- Service：创建一个 Kubernetes `Service` (ClusterIP 类型)，负责在部署的多个 Pod 副本之间进行负载均衡。

- Ingress/Gateway：如果需要对外暴露服务，创建一个 `Ingress` 或 API Gateway 资源，将外部流量路由到内部的 `Service`，并在这一层实现认证、限流和路由等功能。

#### 如何处理长文本请求导致的 GPU 显存溢出问题？

长文本请求的显存压力主要来自 Prefill 阶段的巨大 KV Cache 分配。处理这个问题的核心策略是“分解压力”和“妥协交换”。

1. 强制限制与预处理\
   这是最基础的防线。必须在 API 层面或推理引擎配置中，设置一个硬性的 `max_input_tokens` 限制。对于超长的用户输入，API 服务可以拒绝，或利用模型自身对长文本进行摘要，压缩到可接受的长度后再进行推理。

2. 前置分块与检索增强生成 (RAG)

这是处理超长文本的“银弹”。不要在推理时直接处理整个长文档。在预处理阶段，将长文本分割成大量小块，存入向量数据库。推理时，只检索与用户问题最相关的片段作为上下文。这从根本上解决了显存溢出的问题，是成本效益最高的方案。

3. 推理引擎的内置优化

高性能推理引擎提供了多种技术来应对此问题：

- 分块 Prefill：将长 Prompt 切分成多个小块，逐块进行 Prefill，并将每个块的计算结果（KV Cache）与之前块的计算结果合并。这削平了显存占用的峰值。

- Prefix Caching：如果多个请求共享相同的长 System Prompt，引擎可以复用已计算的 KV Cache，避免重复计算和存储。

- 量化 KV Cache：将 KV Cache 量化为 INT8/FP8，直接将其显存占用减半。

4. 模型架构层面的支持

- 对于需要原生支持超长上下文的模型（如 128K），通常会使用 GQA/MQA 和 滑动窗口注意力 等技术，从底层减少 KV Cache 的大小。

#### 什么是服务器端 KV 缓存共享？它如何影响负载均衡？

服务器端 KV 缓存共享是指在推理服务实例（如 vLLM Pod）内部或实例组之间，通过特定的机制复用之前请求的 KV Cache。

当前的主流形式是 Prefix Caching：

- 当一个请求的 Prompt（比如 System Prompt）与之前某个请求完全相同时，推理引擎能够识别出这个“前缀”，并直接复用已存储在 GPU 显存中的、该前缀对应的 K 和 V 张量。

- 这样做的巨大好处是：跳过了 Prefill 阶段的计算，使首个 token 的生成时间 (TTFT) 几乎降为零，并且节省了大量重复计算和显存。

对负载均衡的影响：

KV Cache 共享引入了一种强烈的亲和性负载均衡需求。

- 问题：如果使用轮询或最少连接数等无状态策略，可能会将两个具有相同长 System Prompt 的对话，分发到两个不同的后端实例上。这样一来，两个实例都需要各自计算一遍 System Prompt 的 KV Cache，完全浪费了缓存复用的机会。

- 解决方案——会话亲和性或前缀感知路由：我们需要在 API 网关或负载均衡器上，引入基于 Prompt 前缀的路由功能。例如，可以计算请求中 `messages[0].content`（即 System Prompt）的哈希值，然后根据这个哈希值，将所有相同 System Prompt 的请求，固定路由到同一组后端实例上。

这种“有状态”的负载均衡策略，可以最大限度地发挥 KV Cache 共享的威力，但也要求我们的基础设施具备更高级的调度和流量管理能力。

#### 如何设计一个支持多租户的 LLM 服务平台？

多租户平台的设计核心是 “逻辑隔离与资源保障”。我们需要在同一个物理集群上，为不同团队、不同业务线（即租户）提供相互独立、安全可靠、成本可度量的 LLM 服务。

1. 租户模型与隔离

- 软隔离：通过应用层的逻辑划分。为每个租户创建独立的 API Key / Workspace。所有资源（如模型、工具、Prompt）都与该 Workspace 绑定。用户在访问时，通过 API Key 进行身份认证和权限校验。这是最轻量、最主流的模式。

- 硬隔离：为高安全需求或高SLA要求的租户，提供独立的物理计算资源。例如，在 Kubernetes 中为该租户独占一个 Node Group，其上只部署该租户的推理服务实例。这保证了绝对的性能和安全性，但成本较高。

2. 多维度配额管理与限流

这是实现资源公平使用的核心。必须能够为每个租户设置细粒度的配额，包括：

- 请求速率：每分钟/每天的 API 请求次数（RPM/RPD）。

- Token 吞吐量：每分钟/每天的 Token 处理量（TPM/TPD），这是更贴近 LLM 成本的指标。

- 并发度：租户可以同时处理的请求数量上限。\
  当租户用量达到配额上限时，系统应返回 429 状态码，而非直接导致其服务中断。

3. 计量、计费与成本归因

平台需要有一个强大的数据管道，实时收集每个 API 请求的详细元数据（租户ID、使用的模型、消耗的 Token 数、延迟等），并将其写入时序数据库或数据仓库。基于这些数据，平台可以实现：

- 用量仪表盘：让租户可以直观地查看自己的使用情况。

- 成本分摊：精确地将底层 GPU 集群的成本，按 Token 用量分摊到每个租户乃至每个部门。

4. 可插拔的安全与治理策略

允许平台管理员或租户自身，为其应用配置安全策略，例如：

- 内容审核：为特定租户开启敏感词过滤或 Prompt 注入防护。

- 数据隐私：为部分租户开启“事后不记录日志”的选项。

- 这些策略应该在 API 网关层以插件的形式被动态执行。

#### 如何监控 LLM API 的首 token 延迟和吞吐量？

LLM 服务的性能监控与传统 Web 服务不同，需要聚焦于两个核心指标：TTFT（首Token延迟）和TPOT（每输出Token时间）。

1. 在 API 网关层进行精确统计

由于 LLM API 通常以流式（SSE）方式响应，传统的反向代理（如 Nginx）只能监控到请求总时长，无法感知到首 Token 的生成时间。因此，我们需要在自研的 API 网关中编写专门的 SSO 解析逻辑。

统计逻辑：

- 网关在发送完请求体后，立刻记录一个时间戳 `T_start`。

- 当网关从推理引擎收到第一个 `data: {...}` 流式事件，并且该事件的 `choices[0].delta.content` 字段有效时，记录第二个时间戳 `T_first_token`。`TTFT = T_first_token - T_start`。

- 当网关收到 `data: [DONE]` 事件时，记录 `T_end`。

- `吞吐量（Tokens Per Second, TPS）` = 本次请求生成的总 Token 数 / (`T_end` - `T_first_token`)。

网关将这些精确的延迟指标，连同 Token 消耗、请求 ID 等元数据一起，发布到 Prometheus 等监控系统。

2. 基于 OpenTelemetry 的分布式追踪

在复杂链路中，仅仅监控网关是不够的。我们需要利用分布式追踪来定位瓶颈。

- 在 API 网关、调度器、推理引擎等关键环节，都集成 OpenTelemetry 的 SDK。

- 为每一个请求生成唯一的 Trace ID，并在整个调用链路中传递。

- 通过在代码中手动添加 Span，我们可以清晰地看到请求花费在网络传输、队列等待和模型计算等各个阶段的时间。这对于定位是网络问题、排队问题还是模型推理慢的问题至关重要。

#### 在部署多个模型副本时，如何处理不同 GPU 节点间的负载不均？

负载不均是异构集群和 LLM 请求特性下必然出现的问题。不同 GPU 节点可能有微小的性能差异（如功率限制、散热），而不同 LLM 请求的计算量（Prompt/生成长度）差异巨大。处理此问题的关键在于动态、智能的调度，而非静态分配。

1. “最少Token数”调度策略

基于负载均衡器的智能调度，是解决此问题最直接的手段。

- 与其用“最少请求连接数”来评判实例负载，不如用 “待处理/正在生成的 Token 总数” 来衡量。这个指标直接反映了实例的计算和显存压力。

- 负载均衡器（或自定义的调度网关）需要实时从每个后端推理实例获取其当前 Token 负载。在分发新请求时，总是选择当前负载最轻的实例。这可以最大程度地平衡各节点的压力。

2. 推理引擎内部动态调整

在连续批处理框架下，推理引擎本身具有一定的“削峰填谷”能力。

- 如果某个节点上的生成长度普遍较短，该节点会很快完成并释放资源，调度器自然会将更多的新请求分配给这个“高周转率”的节点。

- 系统应避免“超大批量积压”：如果一个请求的生成长度极长，可能会在该节点上形成“长尾效应”，阻塞后续请求。虽然连续批处理可以动态插入，但若积压过多，仍需调度器将新请求引导至其他更空闲的节点。

3. 处理异构 GPU 性能差异

如果集群中存在不同型号的 GPU（如 A100 和 H100），解决负载不均需要更主动的策略。

- 权重路由：在负载均衡器上，为不同性能的节点设置不同的权重。H100 的权重设为 2，A100 的权重设为 1。这样 H100 会承担大约两倍于 A100 的流量，从根本上避免了将同等流量分给不同性能节点导致的不均衡。

#### 什么是“Speculative Decoding”？如何作为服务提供？

推测解码（Speculative Decoding） 是一种利用“小模型‘起草’、大模型‘审核’”的方式来加速 LLM 生成的算法。它能在不改变生成质量的前提下，将推理延迟降低约 2-3 倍。

工作原理：

1. 草案生成：一个轻量级的“草稿模型”（Draft Model），以自回归方式快速生成连续的 K 个候选 token。

2. 并行验证：将 Prompt 和这 K 个候选 token 一起，一次性输入给大型“目标模型”（Target Model）。目标模型通过一次前向传播，就能并行地验证所有 K 个 token。它输出自己的概率分布，并逐个检查草稿模型生成的 token 是否符合其“期待”。

3. 接受或拒绝：目标模型会采纳其认为正确的候选 token。一旦某个候选 token 被拒绝，目标模型会基于自己的预测生成一个新 token，并丢弃后续所有草稿。这个过程循环往复。

如何作为服务提供：

将推测解码集成到 LLM 服务中，对 API 使用者是完全透明的。

- 部署架构：推理引擎（如 vLLM）可以将草稿模型和目标模型部署在同一个 GPU 进程中。草稿模型通常非常小（如 0.5B），与 70B 的目标模型相比，其显存和计算开销几乎可以忽略不计。通过共享显存或高效的 IPC 机制，两个模型可以低延迟地交互。

- API 透传：API 网关和接口设计无需做任何改变。用户发送的仍然是标准的 Chat Completions 请求。推理服务内部自动启用推测解码优化，对用户来说，只是感觉到生成速度变快了，首 Token 延迟 (TTFT) 和每 Token 延迟 (TPOT) 都显著下降。

工程挑战：推测解码的效果高度依赖于草稿模型的质量和与目标模型的对齐程度。如果草稿模型与目标模型行为差异过大，大部分候选 token 都会被拒绝，反而导致效率下降。因此，如何选择一个好的草稿模型并进行对齐是关键。

#### 如何保障模型推理服务的安全性，防止提示注入或越狱？

LLM 推理服务的安全攻防是持续演进的，需要构建一个纵深防御体系，在系统的不同层面部署安全措施。

1. 模型内置安全对齐（第一道防线）

这是最基础的防御。模型自身需要经过安全微调和 RLHF，具备拒绝回答有害问题的能力。这是应对各类攻击的“内功”。

2. API 网关：安全前置过滤器（第二道防线）

在用户请求到达模型之前，在 API 网关层进行拦截。

- 输入净化与注入检测：部署一个或多个轻量级安全模型，专门用于检测用户输入中的恶意模式。
  - 注入攻击检测：识别并拦截诸如“忽略之前的指令”、“你现在是 DAN 模式”等企图覆盖系统提示的 Prompt。
  - 有害内容过滤：识别并拦截包含暴力、色情、仇恨言论等违规内容的提问。

- 输出安全审查：模型生成的内容在返回给用户之前，同样需要经过输出过滤器的审查。这个过滤器可以检测并屏蔽模型生成的违规内容，防止“越狱”成功后有害信息的传播。

3. 严格的权限隔离与沙盒机制（第三道防线）

对于有能力调用外部工具（Function Calling）的 Agent，必须构建严格的权限边界。

- 最小权限原则：Agent 调用的工具（如数据库、邮件服务）应使用独立的、权限受限的专用账户。

- 参数白名单与校验：对于模型生成的工具调用参数，必须在执行侧进行严格的格式校验和范围过滤，绝不能直接将模型输出拼接成 SQL 命令或 Shell 命令执行。

- 沙箱执行：高风险代码（如模型生成的 Python 代码）必须在隔离的沙箱容器或虚拟机中运行，防止其对宿主机造成危害。

4. 持续的对抗性测试（红队测试）

防御体系需要不断迭代。定期组织红队攻击，使用最新的攻击手法（如多模态注入、代码隐写、多轮语言切换等）对服务进行渗透测试。将发现的薄弱环节反馈给模型训练和安全策略团队，形成“发现-修复-验证”的闭环。

#### 当模型更新版本时，如何设计平滑的切换或灰度发布策略？

大语言模型的权重文件动辄数十 GB，模型服务的切换不是简单的代码更新，而是一个有状态的、涉及到 GPU 显存资源蓝绿置换的复杂过程。粗糙的更新会导致服务中断、请求超时和资源争抢。平滑发布策略是保障模型服务高可用的关键。

策略一：金丝雀发布 (Canary Deployment)

这是最主流的、风险最低的发布方式。

- 原理：新旧版本模型同时运行，但新版本只接收一小部分流量。

- 实现：
  1. 创建一个新的 Deployment 或 Rollout 对象，部署新版本的模型服务 Pod。所有 Pod 启动并完成模型加载后，都注册到同一个 API 网关后端。
  2. 在 API 网关或 Ingress 层，配置流量路由策略。将带有特定 Header（如 `X-Canary: true`）的请求，或随机抽取 5% 的生产流量，路由到新版服务。
  3. 密切监控新版服务的核心指标（TTFT, TPS, 回答质量, 错误率）。如果一切正常，逐步将流量比例从 5% -> 25% -> 50% -> 100%。
  4. 如果新版本出现问题，可以立即将流量比例调回 0%，实现秒级回滚，完全不影响旧版本服务。

策略二：蓝绿部署 (Blue-Green Deployment)

适用于需要快速、完整切换的大版本更新。

- 原理：维护两套完全独立的、规模相同的生产环境（Blue为旧版，Green为新版）。新版环境部署、测试、预热完毕后，通过修改负载均衡器的指向，将 100% 的生产流量一次性切换到 Green 环境。

- 优势：切换迅速，且旧环境（Blue）保留，一旦出现问题，可以立刻切回，回滚速度极快。

- 挑战：资源开销巨大。在切换期间，需要同时运行两套完整的生产集群，对 GPU 等昂贵资源是一种浪费。

策略三：滚动更新 (Rolling Update)

对于某些场景（如模型微调后的快速迭代），可以使用 Kubernetes 原生的滚动更新策略，但需要精细配置。

- 关键配置：
  - `maxSurge`: 1。先启动一个新版 Pod，等待其完成模型加载并通过健康检查。
  - `maxUnavailable`: 0。确保在更新过程中，没有旧版 Pod 被提前终止，保证整体容量不下降。
  - 当新版 Pod Ready 后，一个旧版 Pod 才会被终止。这个过程以逐个替换的方式进行，直到所有 Pod 都更新完毕。

- 风险：整个集群会短暂地处于新旧版本并存的状态，需要确保 API 网关的负载均衡策略能正确处理这种情况。并且，如果新版 Pod 启动后立刻崩溃，`maxUnavailable: 0` 策略也会阻止更新继续进行，需要人工介入。
