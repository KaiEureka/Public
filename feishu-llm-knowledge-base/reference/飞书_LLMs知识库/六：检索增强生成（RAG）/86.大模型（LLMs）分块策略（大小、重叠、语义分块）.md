# 86.大模型（LLMs）分块策略（大小、重叠、语义分块）

#### 为什么在 RAG 中需要对文档进行分块？分块对检索和生成有什么影响？

在 RAG 系统中，分块是将长文档切割成若干较小片段的核心预处理步骤。这并非可有可无的工程细节，而是由嵌入模型的技术限制、检索的精准度需求、以及生成模型的上下文效率三者共同决定的。

直接原因：嵌入模型存在最大输入长度。无论是早期的 512 token，还是现在的 8192 token，模型一次只能将一个有限长度的文本片段映射为一个向量。如果不分块，一整本 200 页的手册根本无法生成一个单一的、有意义的向量表示。硬截断则会导致后面部分的信息完全丢失。

对检索的影响：分块策略直接决定了检索的“命中精度”和“信息完整度”。分块太大，比如将一个章节作为一块，那么这一块会包含多个不同的子主题。当用户查询只与其中某一段相关时，这个块虽然会被检索到，但其向量是多个主题的平均，相似度分数可能不高，容易被其他无关的短块挤掉。即使被检索到，整个长块丢给生成模型，也会引入大量噪音，让模型难以聚焦。分块太小，比如每块只有一个句子，又会导致信息碎片化。一个完整的概念被拆散到多个块中，检索时可能只能找回其中一两块，导致上下文断裂，生成模型看到的是支离破碎的信息，无法还原全貌。

对生成的影响：分块质量直接决定了 LLM 能否输出准确、完整的答案。理想的分块应该是“自包含”的，即每一块尽可能包含一个完整的、独立的信息单元。这样，检索模块将最相关的几块提供给 LLM 时，LLM 不需要额外脑补块与块之间的关系，就能基于清晰、完整的上下文给出答案。相反，如果块边界随意切割，一句话被拦腰截断，LLM 看到的就是无法理解的半句话，轻则回答质量下降，重则产生幻觉。

因此，分块是信息粒度的艺术，它在“语义完整性”和“检索精准度”之间进行权衡，是决定 RAG 系统性能上限的关键环节。

#### 固定大小分块（如每块 512 token）与基于段落/句子分割有何优劣？

固定大小分块和基于语义边界（如段落、句子）的分割，代表了两种不同的设计哲学。前者追求工程上的极简和可控，后者追求信息上的完整和自然。

固定大小分块：

- 优点：实现极其简单，只需按 Token 数或字符数机械切割，计算成本极低。它产生的块大小均匀，这非常有利于批量处理，比如将块填充到相同长度进行高效的 GPU 推理。由于大小可控，可以精确估算每个块消耗的存储和计算资源，也更容易控制最终给 LLM 的上下文长度。

- 缺点：最大的问题是无视信息的自然边界。它常常在句子中间、甚至词语中间进行切割，将一个完整的概念强行拆散。比如，一段严谨的法律定义可能被切到两个块中。被切碎的信息在嵌入后，其语义是模糊的、不完整的，检索质量会大打折扣。即使用了重叠策略来缓解，也无法从根本上解决信息单元的断裂。

基于段落/句子分割：

- 优点：它遵循文档的自然结构，以段落、句子作为最小切割单元。这意味着每个块大概率是一个相对完整的思想、论点或事实陈述。这样的块在嵌入后，其向量表示更聚焦、更清晰，因此检索的信噪比很高。当它们作为上下文喂给 LLM 时，LLM 也更容易理解，因为它看到的是人类作者原本就组织好的逻辑片段。对于长段落，可以设定一个最大长度阈值，在超过阈值时再寻找次级边界，比如句号。

- 缺点：实现更复杂，需要依赖于文档的格式标记或 NLP 工具来识别句子和段落边界。它产生的块大小不均匀。极短的段落（如一个单行引用）可能信息量不足，而超长的段落（如一段密集的代码注释）又可能超出模型长度限制。当面对格式混乱、没有清晰段落标记的文档（如 OCR 文本、抓取的网页）时，这种策略可能会失效，退化为某种不可控的长块。

实践中的选择：大多数成熟的 RAG 框架采用的一种融合策略，即递归分块。它先尝试用段落分隔，发现段落还是太长，就递归地用句子分隔，句子还太长就用词，但绝不把一个词切开。这本质上是“以语义优先，但用固定大小作为最终兜底”的策略。

#### 如何根据文档类型（论文、代码、对话、合同）选择合适的分块大小？

文档类型决定了信息组织的内在逻辑，因此分块策略必须“因材施教”。

- 学术论文：论文的结构性极强，分为标题、摘要、章节、段落。信息密度大，且逻辑严谨。分块应尽量保持这种结构。
  - 策略：以段落为主，但必须为每个块注入层级标题作为上下文前缀（例如“2. 相关工作 > 2.1 向量检索模型”）。块大小可以适中偏大（如 800-1200 token），以确保完整的论证逻辑不被切断。同时，可以单独为图表和其标题生成一个摘要块，供检索。

- 代码：代码的语义不依赖于自然语言的段落，而是依赖于函数、类、模块这些逻辑单元。且代码对精确符号匹配的要求远高于自然语言。
  - 策略：使用代码感知的分块器，基于抽象语法树（AST）进行切割，将每个函数、类作为一个独立的块。块大小可以很小（如一个几十行的函数），因为函数的职责通常是单一的。同时，为代码块生成一个专门的、用自然语言描述其功能的文本块用于向量检索，而将原始代码作为元数据保留。这比直接嵌入代码文本效果更好。

- 对话（如客服记录、剧本）：其信息围绕角色和轮次组织。孤立的单轮对话往往信息不完整，需要上下文才知道在说什么。
  - 策略：以“连续若干轮对话”为一个块，而不是以句子。例如，将同一个用户的一个问题与客服的后续回答打包在一起。或者使用滑动窗口，窗口大小为几轮对话，步长为一轮，这样每个块都包含了局部的对话上下文。

- 合同/法律文件：语义极其依赖长程依赖和精确的指代关系（如“甲方”、“乙方”）。条款之间的引用必须被保留。
  - 策略：分块时要极其保守，块大小可以很大（如 2000 token），以确保一个完整的条款及其子项在同一块内。对于合同中反复出现的定义，可以在每个块的元数据或前缀中重复注入这些关键定义，以减少检索时的歧义。这是一个非常适合进行“上下文增强”的领域。

#### 分块重叠（overlap）的作用是什么？典型的重叠比例是多少？过大或过小的重叠会带来什么问题？

分块重叠是在切割文本时，让相邻的两个块共享一小段相同的内容。它是解决固定大小分块所导致的“信息断裂”问题的一种有效但相对笨拙的补偿机制。

作用：重叠的核心目的是保证跨块边界的语义连续性。当检索系统单独取回一个块时，这个块的开头和结尾因为有重叠，往往包含了相邻块的上下文，使得它更容易被独立理解。它不会因为被切在边界而丢失关键的开头词或结尾词。比如，一个句子被切在了中间，前半句在块A的末尾，后半句在块B的开头。如果块A和块B有重叠，那么块A的末尾就会包含这个句子的完整部分，或者块B的开头会包含，从而保证至少有一个块是完整的。

典型重叠比例：通常设置在块大小的 10% 到 25% 之间。对于 512 个 Token 的块，重叠 50-128 个 Token 是常见的范围。

- 重叠过小：会失去保护作用，切割边界依然可能导致信息碎片化，一个关键的词组可能被切成两半，导致没有任何一个块包含完整的词组，检索时直接漏掉。

- 重叠过大：会带来严重的副作用。首先，索引中会充斥着大量高度重复的信息，导致存储和计算资源浪费。更重要的是，它会破坏检索结果的多样性。一次查询可能召回 Top K 个结果，其中好几个都是几乎相同、只是稍有偏移的重叠块。它们霸占了结果列表，排挤了其他不同主题的相关信息，导致生成模型只能看到单一的信息来源，产生偏见。

因此，重叠是一个需谨慎使用的技术。它不能替代合理的分块策略。许多先进的系统通过语义分块来根治切割问题，从而避免或大幅减少对重叠的依赖。

#### 语义分块是什么？如何利用句子嵌入或相似度聚类将文档分为语义连贯的块？

语义分块是一种自适应的分块技术，它不依赖固定的 Token 数或标点符号，而是试图理解文本的语义转折点，在主题发生切换的地方自然地设置块边界。其目标是让每个块内部讨论的是同一件事，块与块之间则相对独立。

基本原理：文档的语义可以通过句子级别的嵌入向量来量化。一个连贯的段落中，相邻句子在向量空间中是彼此接近的。而当一个话题结束，另一个话题开始时，句子之间的语义距离会显著增大，形成一个“凹陷”。语义分块的核心，就是找出这些凹陷，并在那里下刀。

实现方法：

1. 句子拆分与嵌入：将整篇文档拆分为单个句子。使用一个轻量级的句子嵌入模型，为每个句子生成一个向量。无需使用昂贵的超大模型，all-MiniLM-L6-v2 这类模型就足够捕捉句间的语义差异。

2. 计算相邻句子的相似度：计算所有相邻句子对（如 `sent_1` 和 `sent_2`，`sent_2` 和 `sent_3`）的余弦相似度，得到一个一维的相似度序列。

3. 识别断点：分析这个相似度序列。那些明显低于局部平均水平的相似度值，就是潜在的断点。可以采用以下方法进行更鲁棒的判定：
  - 阈值法：设定一个固定阈值（如 0.5），相似度低于此值即断。
  - 滑动窗口法：计算一个窗口内的平均相似度，当某对句子的相似度远低于窗口平均时（如低于 2 个标准差），则认为是断点。这种方法能更好地适应文档不同部分的密度变化。

4. 合并与边界调整：将断点之间的所有句子合并成一个块。为了避免块太小或太大，通常会设定最小和最大块大小的约束。如果合并后的块超出了最大长度，则在块内寻找次一级的边界进行再次分割。

实践中的挑战：这种方法在结构良好、主题分明的文章上表现很好。但在意识流、呓语或主题来回跳跃的文本上，相似度序列会非常混乱，找不到清晰的断点。因此，一个健壮的系统通常会将语义分块作为首选，但在找不到明确语义边界时，会平滑降级到固定大小分块，形成一个“混合”策略。

#### 实现语义分块的常见算法：基于相邻句子的余弦相似度，如何确定块边界？

基于相邻句子余弦相似度的语义分块算法，其核心在于如何从一连串的相似度数值中，自动化地、鲁棒地识别出那些代表“话题转移”的边界点。下面详细描述其算法流程。

第一步：构建句向量与相似度数组。\
使用分句工具将文档拆分为句子列表 `S = [s1, s2, ..., sn]`。通过句子嵌入模型，得到每个句子的向量 `V = [v1, v2, ..., vn]`。计算所有相邻句子的余弦相似度，得到一个数组 `Sim = [sim(v1, v2), sim(v2, v3), ..., sim(vn-1, vn)]`。

第二步：识别异常低点作为候选边界。\
一个好的边界点应该是它前后的句子“不相似”。简单的做法是设定一个全局阈值，如 0.3，低于此值的直接标记为边界。但全局阈值往往过于僵化，无法适应文档中语义密度的变化。一种更鲁棒的做法是相对阈值法：维护一个滑动窗口，计算窗口内相似度的均值 `μ` 和标准差 `σ`。对于窗口中心的点 `i`，如果 `Sim[i] < μ - β * σ`（β 是调节因子，如 1.5），则将 `i` 标记为候选边界。滑动窗口可以平滑局部波动，识别出相对于其局部环境而言的“突变点”。

第三步：应用分块大小约束。

纯粹基于语义断点可能会导致块的大小极不均匀，出现只有一句话的超小块，或依然是数页之长的超大块。因此，必须引入工程约束。

- 最大块长度约束：设置一个上限 `MAX_LEN`（如 1024 Token）。当从上一个边界到当前边界之间的累计 Token 数超过 `MAX_LEN` 时，即使下一个句子的语义相似度很高，也必须强制执行切割。此时，我们不再依赖语义边界，而是寻找距离 `MAX_LEN` 最近的一个“次级语义边界”（如相似度相对较低的点）进行切割。这确保了块大小永远可控。

- 最小块长度约束：设置一个下限 `MIN_LEN`（如 256 Token）。如果从上个边界到当前边界太短，即使遇到了一个很强的语义断点，也先不切割，而是将它和后续的句子暂时合并，直到超过 `MIN_LEN` 或遇到更强的强制切割条件。这防止了碎片的产生。

第四步：合并句子生成最终块。\
根据确定好的边界索引，将 `S` 中的句子合并，形成最终的文本块列表。

算法的优点：它完全是自适应的，无需预先设定固定的块大小，能产出语义质量极高的块。算法的挑战：对嵌入模型质量有依赖；对于没有清晰逻辑结构的文本，自动识别的边界可能不稳定；计算所有句子的嵌入和相似度会引入额外的预处理开销。

#### 递归分块（Recursive Character Text Splitter）的工作原理：如何处理不同层级的分隔符？

递归分块是目前使用最广泛、鲁棒性最好的文本分割方法之一，其核心思想是模仿人类阅读长文档时，先看章节，再看段落，最后才看句子的层次化思维，通过递归地尝试不同粒度的分隔符，来实现既尊重语义边界，又确保块大小可控的目的。

工作原理：\
递归分块接受一个由用户定义的分隔符层级列表。这个列表是按照语义粒度从大到小排列的，例如：`["\n\n", "\n", "。", ".", " ", ""]`。

1. 顶层切割：算法首先使用列表中的第一个分隔符（如双换行 `\n\n`）来切分整个文本，试图得到一系列段落。如果切分后得到的所有片段长度都小于预设的最大块大小，算法就结束了。

2. 递归处理：如果某个片段（比如一个很长的段落）的长度仍然超过最大值，算法就会递归地调用自身，用下一个层级的分隔符（如单换行 `\n`）来继续切割这个长片段。这个过程会层层递进，不断尝试用更细粒度的分隔符进行拆分。

3. 终极兜底：当列表中的所有分隔符都用完了，但某个片段（可能是一个超长的句子或一个巨大的表格）依然超出最大长度，算法就使用最后一个空字符串分隔符 `""`，强制按照字符或 Token 数量进行机械切割。

4. 块合并：在切割后，算法通常会尝试将小的片段与相邻片段进行合并，直到合并后的块大小接近但仍小于最大块大小。这可以避免产出大量极小的碎片。

处理不同层级分隔符的关键：

这种策略之所以强大，在于它完美地平衡了“语义完整性”和“长度可控性”。它总是优先尝试最大粒度的分隔符，以期在最大程度上保持文档的逻辑结构（如段落不被切断）。只有当逻辑单元本身太大时，它才“迫不得已”退而求其次，转向更细粒度的切割，最终确保没有一块会超过硬性长度上限。这使得它在面对结构良好的文档（如论文、合同）时，能产出高质量的段落级块；而在面对混乱无序的文本（如OCR结果）时，也不会崩溃，而是能平滑地降级到句子级甚至字符级切割，保证系统的健壮性。

递归分块不进行任何复杂的语义计算，仅通过规则就实现了一种务实、高效且可解释的分块效果。

#### 对于包含表格、代码块的文档，分块策略需要做哪些特殊处理？

表格和代码块具有与叙事性文本截然不同的信息结构，如果混在普通文本中一起切割，很容易导致信息被破坏，严重影响检索质量。

表格的特殊处理：

表格的语义在于其二维结构，每一行代表一个实体，每一列代表一个属性。如果将其切成碎片，数字和列名的对应关系就丢失了，对后续的 LLM 而言毫无意义。

- 表格识别与隔离：首先，需要用解析器识别出文档中的表格区域。

- 独立成块：一个完整的表格，如果大小合适，可以作为一个独立的块。

- 大型表格的处理：如果一个表格过大（超过最大块 Token），不能简单地拦腰切断。应该采用行/列感知的切割。例如，在切割时保证表头被完整保留，然后与一部分行组成一个块，下一个块依然是同一个表头，再带领后续的行。这样每个块都是一个包含完整列名的、可独立理解的结构。

- 线性化与摘要：将其转换为 LLM 更友好的格式，如 Markdown 表格，或更高级的，将其转换为一系列陈述句（如“产品A的销售额在2023年Q3为100万”）。也可以生成一个表格的摘要文本块用于向量检索，而将原始数据保留给 LLM 使用。

代码块的特殊处理：

代码的语义依赖于其语法结构。

- 代码感知解析：不能依赖标点或空格。必须使用基于抽象语法树（AST）的工具来解析代码，识别出函数、类、方法等逻辑单元。每个单元可以作为一个候选块。

- 上下文注入：一个独立的函数，如果缺少了其所在的类名或顶部的导入语句，对 LLM 来说可能难以理解。在分块时，需要为每个代码块注入其“头文件”信息，比如类签名、关键导入等。

- 混合表示：向量检索应主要基于代码的自然语言描述（如 docstring）进行。如果代码缺少注释，可以预先使用 LLM 为每个代码块生成一个简短的摘要，然后将这个摘要的向量用于检索。检索命中后，再将原始代码块作为上下文提供给 LLM。

---

#### 分块大小与 embedding 模型的上下文窗口之间应保持什么关系？

分块大小与嵌入模型上下文窗口之间是一个明确的“小于”关系，但从工程和语义角度看，需要追求一个更佳的匹配点，而不是简单地塞满窗口。

绝对约束：块大小必须严格小于嵌入模型的最大输入长度。这是硬性要求，超出部分会被 API 直接截断，或在本地模型上导致运行时错误，从而导致信息丢失。

实践中的最佳匹配：不应将窗口填满。如果模型上下文窗口为 8192，分块大小就设为 8100，这是一种虽然可行但并不总是最佳的做法。原因在于，嵌入模型的性能在其声称的最大窗口附近可能存在不均一性，部分模型在边界处对长文本的语义聚焦能力会下降。

信息密度与维度匹配：嵌入模型将一个文本块压缩为一个固定维度的向量。如果文本块很长且信息稠密，压缩过程就会有信息损失，向量的区分度变差。如果文本块很短，语义聚焦，但与模型的典型训练样本长度分布不符，也可能得到次优的向量表示。因此，选择块大小时，需考虑模型的典型输入长度。例如，OpenAI 的 text-embedding-ada-002 模型，在 512 Token 左右的文本上已经能产生质量非常高的向量。

检索与生成的双重视角：即使嵌入模型可以处理 8000 Token 的块，也应该从 RAG 最终目的出发来思考。一个巨大的块可能包含了多个主题，导致检索时命中的精度很低。即使被检索到，如此大的块也会消耗掉大量的 LLM 上下文窗口，挤占了融合其他来源信息的可能性。因此，分块大小的最终确定，需要在一个具体的 RAG 系统上进行端到端的实验。通常，一个几百到一千多 Token 的块，能够在语义聚集度和上下文信息量之间找到一个较好的平衡点。它的上限由嵌入模型窗口决定，但实际值由下游任务决定。

#### 过小的分块可能导致上下文信息丢失，过大的分块可能稀释语义，如何通过实验找到最佳大小？

寻找最佳分块大小，本质上是一个超参数调优问题，但它不能仅仅通过查看检索的相似度分数来判定，而必须采用一种端到端、以生成质量为最终评判标准的实验方法。

实验设计思路：

首先，必须认识到“最佳”是动态的，它取决于你的文档类型、嵌入模型、以及用户查询的典型模式。没有放之四海皆准的“最佳大小”。

实验步骤：

1. 准备代表性测试集：准备一个包含不同用户查询意图的测试集（如 50-100 个问题），并且拥有一个包含这些查询答案的、具有代表性的文档库。为每个问题标注好理想答案所依据的原始文档片段（ground truth）。

2. 选择评估指标：放弃以检索的相似度分数或召回率作为唯一指标。而应采用生成质量指标。
  - 自动指标：使用 RAGAS 等 RAG 评估框架，可以自动计算生成答案的忠实度（答案是否源于提供的上下文）和答案相关性（答案是否切题）。
  - 人工或 LLM 评估：将不同分块策略下 RAG 系统生成的最终答案，连同其参考上下文，交给一个强模型（如 GPT-4）进行打分，比较哪个更准确、更完整。这是目前最可靠的评判方式。

3. 执行分块实验：
  - 粗扫：以较大的步长（如 128, 256, 512, 1024, 2048）进行粗扫，快速定位性能较好的区间。
  - 精调：在表现最好的区间附近（例如 512 和 1024 之间），用更小的步长（如 128）进行细调。
  - 同时，也要对不同策略（固定大小、递归、语义）进行对比。

4. 分析曲线：
  - 当块从极小的值开始增大时，生成质量通常会上升，因为信息变完整了。
  - 在某个点，质量达到峰值，然后开始缓慢下降。下降点就是你的文档中典型独立信息片段的平均大小。超过这个点，单个块中开始混入噪音。
  - 观察下降曲线是否平缓。如果平缓，说明系统对块大小不那么敏感；如果陡峭，说明你的文档结构非常清晰，一旦块太大就显著破坏了检索的信噪比。

5. 结合实际约束：实验得出的最佳块大小还需结合实际成本约束。一个 512 大小的块和一个 1024 大小的块，如果生成质量相差在 1% 以内，从成本（更大的块消耗更多 Token）和延迟角度，选择 512 的可能是更经济的选择。

通过这种端到端、生成导向、数据驱动的实验方法，才能为你的特定 RAG 应用找到最优的分块大小，而不是盲目套用通用经验值。

#### 多级分块：什么是“小块检索 + 大块上下文”策略？简述其在 RAG 中的应用。

多级分块，尤其是“小块检索 + 大块上下文”策略，是一种将检索的最优粒度与生成所需的最优上下文解耦的设计。它认识到这两者所需的信息片段大小往往不一致：检索需要一个语义高度聚焦的小片段来确保匹配精度，而生成则往往需要一个更大的、包含充分背景信息的上下文来产出完整、准确的答案。

策略实现：

此策略通常需要构建两套并行的索引，或者在索引中存储两种粒度的块。

1. 小块索引：将文档按较小粒度切割，例如以段落、句子甚至固定 256 Token 的小块。这些小块语义集中、噪音少，能非常精准地被检索到，提高了检索的相似度区分度和命中率。

2. 大块上下文：在检索命中小块后，系统不直接将这个小块返回给 LLM，而是利用预先建立的映射关系，找到这个小块所属的原始大块。这个大块可以是原本的整个章节、固定 1024 Token 的大块，或者是包含该小块及其周围的扩展上下文。最终，将这个更大的上下文作为生成模型的输入。

在 RAG 中的应用：

这种策略在答案需要综合上下文的场景中效果显著。例如，用户问“某某条约的第三条款具体内容是什么？”，一个很小的块可能只包含第三条款本身。但如果生成模型只看到这一条款，可能缺少“某某条约”的背景，导致无法正确引用或解释。利用小块检索可以精准定位到条款，然后通过映射取出包含条约前言和后续条款的大块，LLM 便能在完整语境下给出更清晰的回答。

实现上，常见做法是：在分块时，为每个小块记录其所属的父文档ID或大块ID。检索时，利用向量索引搜出最相关的小块，再根据这些ID去检索对应的全文或大块，最后将这些大块去重后作为上下文。这本质上是一种检索重映射，它同时保证了检索的精准度和生成的完整性。

#### 分块策略对检索评分（相似度分数）的影响：为什么块太小可能使相似度计算不可靠？

分块策略直接影响检索评分，也就是查询向量与文档块向量之间的相似度分数。这个分数是决定哪个块被召回、以什么顺序呈现的关键。块的大小如果选择不当，会使得这个分数失真，导致看似相关但实则无用的结果排在前列。

块太小为何不可靠：

当块太小（例如只有一句话或十几个 token）时，其包含的语义信息非常局部和稀疏。一个短小的块可能只表达了某个完整概念的一个侧面。想象一个查询：“苹果公司 2023 年第四季度财报亮点”。一个极小块的文本块可能是：“营收同比增长 2%”。从字面看，这似乎非常相关，相似度分数可能极高。但它单独存在时，缺失了至关重要的上下文：是哪个公司？哪个季度？什么业务？这个小块由于自身信息不完整，它的向量表示在嵌入空间中可能处于一个模糊地带，容易与其他不相关的、但具有类似用词的短文本发生误匹配，从而得到一个虚高的相似度分数。

相似度计算的可靠性依赖于信息的完整性和区分度。一个合格的文本块应该包含足够的上下文，使其语义能够被独立理解。例如，对于上例，一个合适的块可能是：“苹果公司 2023 年第四季度财报显示，其总营收为 1195.75 亿美元，同比增长 2%。”这样的块，其语义明确、独特，在向量空间中的位置就非常清晰。与查询的相似度分数会真实地反映其相关性，而不是由模糊匹配产生的噪声。

因此，过度切割会导致“高相似度、低信息量”的垃圾结果泛滥，严重降低检索质量。好的分块策略要确保每个块在语义上是自包含的。

#### 如何评估分块策略的优劣？除了最终 RAG 性能，有哪些中间指标？

评估分块策略不能只等待最终的 RAG 答案，而需要设置一系列中间指标，快速、低成本地迭代。

中间指标：

1. 检索命中率与 MRR：对于一个标注好的问答数据集（包含每个问题的标准答案块ID），可以纯粹评估检索阶段的性能。指标包括 Recall@K（前 K 个结果中包含标准答案块的比例）和 MRR（平均倒数排名，即标准答案块在结果列表中的排名的倒数平均值）。这能快速反映分块是否能将正确答案从知识库中“捞”出来。

2. 块的语义完整性得分：这是一个需要借助强模型或人工评估的指标。随机抽取一批块，判断它们是否构成一个独立的、完整的信息单元。计算“完好块”的比例。这个指标直击分块的核心质量。

3. 块大小分布的合理性：统计所有块的大小的分布，关注其均值和方差。是否存在大量极小碎片（< 50 Token）或超大块（> 模型上限）？一个健康的分布应该相对集中，且没有越界。

4. 上下文冗余度：如果使用了重叠策略，可以通过计算所有块的总 Token 数除以原始文档的总 Token 数，得到一个膨胀系数。这个系数越高，说明索引中的冗余信息越多，存储和计算浪费越大。

与最终 RAG 性能的结合：

最终的 RAG 评估仍然不可或缺，指标如答案的忠实度（Faithfulness）和相关度（Answer Relevance）。通过中间指标，可以快速淘汰掉有明显缺陷的分块方案（如产生了大量碎片），然后再将少数几个表现良好的方案投入昂贵的端到端 RAG 评估中。这种分层评估方法能最大化迭代效率。

#### 在分块过程中，如何保留文档结构元数据（如标题层级、章节）？这些元数据如何利用？

在分块过程中保留文档的结构元数据，是让 RAG 系统从“信息检索”升级到“知识理解”的关键。这些元数据包含了文档的逻辑骨架。

保留方式：

在文档解析阶段，就需要识别出各级标题、章节、页眉页脚等结构。分块时，不是简单地输出一个文本字符串，而是为每个块创建一个结构化的对象，包含以下字段：

- `content`: 块的文本内容。

- `metadata`: 一个字典，记录了 `source` (来源文件)、`page_number`、`chapter_title`、`section_headers` (从一级到当前级的所有标题列表) 等。\
  具体的实现技术通常是“上下文增强”：在为块生成嵌入向量之前，将它的关键元数据注入到文本内容的前面。例如，块的文本内容变为：

```plain text
[文档标题: 《2024年AI发展报告》]
[章节: 3. 技术突破 > 3.1 大语言模型]
文本内容: 2024年，LLM在推理能力上取得了显著进展...
```

这样，嵌入向量就“记住”了这个块的背景信息。

元数据的利用：

1. 提升检索精准度：如果用户查询“AI报告里关于大语言模型的进展”，带有元数据的块向量因为包含了“报告”、“大语言模型”等关键词，其语义会更接近查询，更容易被命中。

2. 实现元数据过滤：在向量搜索时，可以添加硬性的过滤条件，例如 `metadata["year"] == 2024`。这在回答诸如“根据2024年的报告...”这类问题时至关重要。

3. 为LLM提供丰富上下文：在将块喂给 LLM 时，可以将其元数据以清晰的结构化格式（如 Markdown 标题）展现，或者将层级标题作为前缀。这让 LLM 能像人阅读报告一样，知道当前信息在文档中的位置，从而更好地理解内容的范围和可信度，并能在答案中进行准确的引用。

#### 如何处理长文档中的跨块实体指代（如“如上所述”）？分块是否会破坏指代解析？

分块是必然会被坏文档中长距离的指代关系的。“如上所述”、“该产品”、“他”等指代词，一旦与它所指的对象分在了不同的块中，检索系统单独召回的这个块就会变得难以理解，给 LLM 造成困惑。

问题的本质：分块割裂了文本的线性阅读流。当信息被检索出来时，它是碎片化的。

处理策略：

1. 上下文增强 (Context Enrichment)：这是最常用的方法。在将文档分块后，系统不是直接存储原始的块内容，而是对文本进行一次指代消解或上下文替换的预处理。例如，一个 LLM 被用来重写文本，将模糊的代词替换为具体的实体名称。将“该产品在2024年销量增长了20%”重写为“Acme AI Chatbot 在2024年销量增长了20%”。这样，每个块就变得更自包含。这种操作可以在分块前进行，也可以在分块后进行。

2. 检索后的上下文扩展：在检索阶段，一旦命中了一个块，系统不直接返回这个块，而是像前面提到的“大块上下文”策略一样，返回包含该块的一个更大的上下文窗口（例如前后各几个句子或段落）。这利用了原始文档的局部连贯性，大概率能将指代的前文包含进来。这是工程上最简单、最鲁棒的解决方案。

3. 利用元数据注入：如果文档中使用了大量的“如上所述”来引用上级标题或前面章节的结论，可以在分块时，通过分析文档结构，将这些被引用的“上文”直接作为元数据注入到文本块的前缀中。例如，一个块的前面被自动加上“（接上一节：LLM的三大挑战包括成本、幻觉和延迟）”。

分块是否破坏指代解析？

是的，它会严重破坏。但这通常被看作是一个预处理和检索策略的问题，而不是通过完美分块能解决的。所以，工程上接受分块对指代的破坏，然后通过检索阶段的上下文扩展和预处理阶段的指代消解来修复这个问题。

#### 滑动窗口分块在流式文档或时间序列文本中的应用。

滑动窗口分块是一种动态生成重叠块的方法，非常适合于信息密度均匀、没有明显主题边界的流式数据，比如演讲稿、对话记录、程序日志或实时字幕。

工作原理：

与固定大小分块不同，它不是在文档上切出一个个互不重叠的区间，而是设置一个窗口大小和一个滑动步长。例如，窗口大小为 512 个 Token，步长为 256 个 Token。算法从文档开头开始，提取前 512 个 Token 作为第一个块。然后，窗口向后滑动 256 个 Token，产生第二个块，它与第一个块有 256 个 Token 的重叠，以此类推。

在流式文档中的应用优势：

1. 平滑语义过渡：在连续对话或演讲中，话题是逐渐演变的，没有硬性的“段落”边界。滑动窗口避免了在任意点硬性切割，使得每个窗口内的信息都是流畅的。这种策略能较好地保留局部上下文。

2. 信息冗余保证鲁棒性：由于高度重叠，任何一个特定的信息点都会出现在连续的多个块中。这意味着即使某个块的向量由于偶然原因没有被检索到，它旁边的重叠块依然有机会被命中，从而提高了召回率。

3. 适合时间序列文本：在处理按时间排序的文本（如日志）时，滑动窗口可以自然地创建一个“事件上下文”。每次向前滑动一步，窗口就包含了最新的事件以及它发生之前的背景事件。这在“发生了什么”以及“为什么发生”的查询中非常有价值。

挑战：

最大的挑战是索引膨胀。高度重叠导致相同的内容被存储和索引了多次，存储成本和计算成本都成倍增加。此外，它可能导致检索结果的多样性降低，因为大量高度相似的窗口块会互相竞争有限的 Top K 名次。因此，滑动窗口通常应用于那些信息本身是流式的、且无法被清晰地结构化的数据源上。

#### 对比 LangChain 中不同 splitter（Character, Token, Sentence, Semantic）的实现原理和适用场景。

LangChain 提供了丰富的文本分割器，每种都针对不同的文本特性和应用场景。

- CharacterTextSplitter：
  - 原理：最简单的分割器。它使用单个字符（如换行符 `\n` 或空格 `" "`）作为分隔符，将文本切割成块。
  - 适用场景：适用于格式简单、标记清晰的文本，如日志文件、CSV 数据。它不能理解语言结构，只是机械切割，通常作为其他高级 Splitter 的兜底方案，或用于特定格式数据的精确控制。

- TokenTextSplitter：
  - 原理：不依赖自然语言的分隔符，而是直接使用模型的 Tokenizer，根据 Token 数量来切割文本。这确保了每个块的 Token 数严格精确，不会超出模型窗口。
  - 适用场景：适用于对 Token 数目有严格限制的模型，且对文本结构要求不高。它的缺点是可能在不恰当的地方切断文本。

- SentenceTransformersTokenTextSplitter / NLTKTextSplitter：
  - 原理：这是基于句子的分割器。它使用 NLTK 或 spaCy 等 NLP 库，先识别出文档中的句子边界，然后试图将尽可能多的完整句子打包进一个块中，确保不会在句子中间切开。
  - 适用场景：这是最通用的选择之一，适用于大多数结构良好的自然语言文本，如文章、博客、报告。它在“保持句子完整性”和“控制块大小”之间取得了良好的平衡。

- SemanticChunker：
  - 原理：它的核心是前面提到的语义分块。它通过对句子进行嵌入，计算相邻句子的余弦相似度，在相似度出现骤降的“话题转折点”处创建块边界。
  - 适用场景：适用于对语义完整性要求极高的场景，如学术论文、法律合同。它能够自适应地找到信息密度变化的边界，产出的块质量最高。缺点是计算开销大，且对无清晰主题结构的文本（如闲聊对话）可能效果不佳。

- RecursiveCharacterTextSplitter：
  - 原理：这是 LangChain 的默认推荐。它结合了层级分隔符的思想。它维护一个分隔符列表（如 `["\n\n", "\n", ".", " ", ""]`），优先用能保持最大语义结构的分隔符（如段落）切割，如果切出来的块还太大，就递归地用下一级分隔符（如句子）去切割那个大块，以此类推。
  - 适用场景：通用性最强。几乎适用于所有文档类型，因为它能自适应地在“保持结构”和“控制大小”之间找到平衡。它通常是项目的首选。

#### 在分块时进行文本清洗（去除噪音、特殊字符）的时机和方式，是否影响语义完整性？

文本清洗是 RAG 数据预处理中的必要一环，但清洗的时机和程度至关重要。不当的清洗会破坏语义完整性，反而损害检索效果。

清洗的时机：

清洗可以在两个时机进行，各有优劣。

1. 分块前清洗：对原始文档进行一次性的全量清洗。优点是一次处理、成本低，能避免在成千上万的块上重复操作。缺点是可能移除了某些对特定块上下文有用的信息。适用于全局噪音（如页眉页脚、水印）的处理。

2. 分块后清洗：针对每个文本块进行单独的精细清洗。优点是可以根据块的局部上下文进行处理，比如移除该块中由于切割产生的孤立、无意义的句子片段。缺点是计算开销大。适用于处理分块过程本身引入的噪音（如句子开头多余的空格）。

清洗的方式及对语义的影响：

- 安全的清洗（提升语义密度）：移除多余的空白符、标准化 Unicode 字符、修复常见的 OCR 错误、移除页眉页脚等模板化噪音。这些操作通常不会破坏文本的主干语义，反而能让文本更干净，使嵌入模型生成的向量更聚焦。

- 需谨慎的清洗（可能扭曲语义）：移除所有标点符号（会导致句子边界丢失）、删除低频词（可能移除关键术语）、强行将所有文本转小写（可能混淆专有名词和缩写）。这些操作会破坏自然语言的语法结构，可能改变句子的原意，导致嵌入质量下降。

- 破坏性的清洗（绝对避免）：使用正则表达式盲目删除任何包含数字或特殊字符的文本，这可能会抹去关键数据（如金额、日期、代码片段）。

最佳实践：采用一种“轻量级、保守型”的清洗策略。核心目标是消除那些对语义无贡献、甚至干扰嵌入模型的“信号噪音”，而不是去改写或“美化”文本。清洗后，应进行抽样人工检查，确保关键信息没有被误伤。

#### 多语言文档的分块：中英文混合时，应选择哪种分块粒度？

多语言混合文档的分块，最大的挑战在于中英文在字符集、词法、句法和信息密度上的巨大差异，不存在一个同时完美的单一粒度。需要采用一种鲁棒的中立策略，或者增加预处理步骤。

为什么固定字符数或词数会失效：

- 一个中文字符通常就代表一个语素，而一个英文单词需要多个字符组成。按字符数切割，对英文会切得非常碎，而对中文可能恰好。

- 按词切割，需要可靠的多语言分词工具，而这对于中英夹杂、各种缩写和术语混用的文本来说，难以做到 100% 准确。

推荐策略：

1. 统一采用 Token 级别分块：\
   这是目前最有效、最普适的方法。直接使用目标嵌入模型的 Tokenizer，根据 Token 数量（如 512 tokens）来切割文本。因为无论源语言是什么，Tokenizer 都会将其统一转换为模型的内部表示。这确保了所有块的语义容量在模型看来是基本一致的，从而避开了不同语言在字符层面的差异。

2. 语言检测与自适应分隔符：\
   如果采用递归分块，可以先用语言检测模型识别出当前段落的主语言。然后根据语言选择不同的分隔符列表。对于中文，可以使用 `["。", "！", "？", "\n", "，", " ", ""]`；对于英文，可以使用 `["\n\n", "\n", ".", " ", ""]`。这种方法在文档内部语言切换时效果很好。

3. 语义分块：\
   使用强大的多语言嵌入模型（如 `multilingual-e5-large`），采用基于相邻句子相似度的语义分块。由于语义分块完全依赖于向量空间的距离，而一个好的多语言模型已经将不同语言的语义对齐到了同一个空间中，因此这种方法天然具有语言无关性。它自动在“语义转折点”切割，不论那是个中文句子还是英文句子。

4. 避免混合语言的极小碎片：\
   在实际应用中，最好保持一个块内的语言相对一致。如果切割点恰好切在一个中文句子和一个英文句子之间，就让它们各为一个块，而不是硬把它们合并。这需要分块器对语言边界有一定的感知。

#### 图像和表格的“分块”如何处理？是转换为文本块还是单独索引？

图像和表格蕴含着极其丰富且关键的信息，它们的处理方式与纯文本截然不同，通常采用一种多模态转换与多级索引相结合的策略。

处理的核心思路：不能将它们与普通文本一起切割。它们应该被识别出来，作为一个独立的、特殊的“块”来处理，其内容需要先被转换成 LLM 可以理解和检索的文本形式。

图像的处理：

1. 转换为文本（Captioning）：使用一个多模态大模型（如 GPT-4V）为图像生成详细的文字描述。这个描述文本会被用来生成向量并参与检索。

2. 建立关联与注入：在原始文档中，图像附近的文本（如标题、上下文段落）往往与图像强相关。可以将这些上下文文本与 Caption 拼接在一起，形成一个综合文本块进行嵌入。同时，该块的元数据中存储图像的 URL 或 Base64 编码。

3. 检索与生成分离：当检索命中这个块时，系统将 Caption 和原始上下文文本提供给 LLM 作为理解背景。如果 LLM 具有多模态能力，还可以同时将原始的图像数据作为输入的一部分，使 LLM 能“看到”原始图像。

表格的处理：

表格的处理粒度更细，因为它具有二维结构。

1. 完整表格线性化：将表格转换为 LLM 更友好的格式，如 Markdown 表格或 CSV 字符串。

2. 表格的语义分块：如果表格很大，需要分块。最佳方式是行感知分块。核心原则是：切割行，但重复表头。即每一块都包含完整的表头信息，再加上连续的一部分数据行。这样，每一块都是一个独立的、可被理解的小表格。

3. 表格摘要与独立索引：为整个表格或每个逻辑行生成一个自然语言的摘要或陈述句（如“Acme 公司 2024 年 Q3 的营收为 100 万，同比增长 20%”）。将这些摘要文本进行向量化用于检索，当命中后，再将对应的完整表格块或原始表格数据提供给 LLM。这比直接对线性化的表格进行向量检索的效果要好得多。

总之，图像和表格的“分块”，本质上是一个先理解、再翻译（转成文本）、然后按语义索引的过程，最终在生成时再根据情况决定是提供文本还是提供原始多模态数据。
