# 92.大模型（LLMs）重排序（Reranker）

#### 1. Reranker 在 RAG 流程中的位置和作用是什么？为什么不能只依赖初检索？

在 RAG 流程中的位置：

Reranker（重排序模型）位于 RAG 管道的检索阶段之后、生成阶段之前，是一个连接“粗筛”与“精读”的关键中间层。典型的 RAG 数据流是：

```plain text
用户查询 → 初检索（粗筛）→ 候选文档集（Top N） → Reranker（精排）→ 精选文档集（Top K） → 提示组装 → LLM 生成
```

在这个流水中，初检索负责从海量文档库中快速、高召回地捞出一个较大的候选池（例如 50~200 个文档）；Reranker 则对这个候选池进行二次精细排序，从中挑出与查询最相关的少数文档（例如前 3~5 个）送入生成模型。

核心作用：

Reranker 的本质任务是弥补初检索模型在精细语义区分能力上的不足，从而在保证召回的前提下，最大化最终的准确率。它通过更强的模型和更复杂的交互计算，重新评估每个候选文档的真实相关性。

为什么不能只依赖初检索：

初检索（无论是稀疏的 BM25 还是稠密的向量检索）受限于其架构和效率要求，不得不做出精度上的妥协。

- 双塔模型的局限性：主流的稠密检索采用双塔结构，查询和文档在编码时完全独立，交互仅发生在最终向量的单点内积上。这种“浅交互”无法捕捉查询词与文档词之间的复杂关系（如否定、限定、词序、局部匹配等）。一个初筛模型可能因为文档整体语义相近而打出高分，却忽略了关键细节。例如，对于查询“不含咖啡因的咖啡”，初筛可能返回大量关于“咖啡的好处”的文档，因为它们在整体语义上相近，但忽略了“不含咖啡因”这一关键限定。

- 单向量表示的瓶颈：将长文档压缩为单个固定维度向量，会导致信息稀释，尤其会丢失关键实体的精确匹配信号。

- 效率和精度的取舍：初检索要求在毫秒级内从百万、亿级文档中完成搜索，因此必须使用高效的近似最近邻算法和较浅的编码器，这不可避免地牺牲了部分精度。

因此，Reranker 是 RAG 系统中以计算换精度的关键组件。它承接初检索的高召回，产出高精度，保证最终输入到 LLM 的上下文既相关又精炼，极大提升了答案质量和系统效率。

#### 重排序模型通常采用什么架构？Cross-encoder 与 Bi-encoder 的核心区别。

重排序模型目前最主流的架构是 Cross-encoder（交叉编码器），它与初检索常用的 Bi-encoder（双塔编码器） 形成了鲜明的互补。

Bi-encoder（双塔模型）：

- 架构：拥有两个独立的编码器塔（或共享权重），分别对查询和文档进行编码，输出各自固定长度的向量。相关性分数通过计算两个向量的余弦相似度或内积得到。

- 工作方式：文档向量可以离线预先计算并建库，查询时只需实时编码查询向量，然后通过 ANN 快速搜索。查询和文档在编码过程中完全独立，没有交互。

- 特点：速度极快，适合大规模检索；但交互性弱，语义区分能力有限。

Cross-encoder（交叉编码器）：

- 架构：通常基于 BERT 等 Transformer 编码器，将查询和文档拼接成一个完整的序列输入：`[CLS] query [SEP] document [SEP]`。模型通过多层自注意力机制，让查询的每个 Token 与文档的每个 Token 进行充分的、全对全的交互。

- 工作方式：无法预先计算文档向量，必须在推理时为每一对 `(query, document)` 完整地运行一次前向传播，在 `[CLS]` 向量之上接一个线性分类头，输出一个相关性分数。

- 特点：精度极高，能捕捉复杂的语义匹配关系；但计算开销大，无法用于海量文档的初筛。

核心区别总结：

| 维度 | Bi-encoder (双塔) | Cross-encoder (交叉编码器) |
| --- | --- | --- |
| 交互方式 | 分别编码，向量内积交互（浅交互） | 拼接后联合编码，Token 级自注意力交互（深交互） |
| 推理速度 | 极快，可离线预计算文档向量 | 慢，每次查询-文档对需完整前向计算 |
| 存储成本 | 低，仅需存储文档向量 | 无法预存，无需考虑 |
| 检索精度 | 较低，容易忽略细节 | 极高，能精准判断相关性 |
| 在RAG中的角色 | 初筛器（负责高召回） | 精排器（负责高精度） |

正是由于这种架构上的根本差异，才决定了 Cross-encoder 成为 Reranker 的首选。它用昂贵的实时计算，换取了 Bi-encoder 无法企及的排序精度。

#### 为什么 Cross-encoder 排序更准确但计算开销更大？推理时的输入形式是什么？

为什么排序更准确：

Cross-encoder 的准确性优势源于其全交互的注意力机制。在 Bi-encoder 中，查询和文档的表示是在彼此“不知情”的情况下生成的，向量内积是唯一的信息交汇点。这是一种极度压缩的交互，会丢失大量细粒度匹配信号。而在 Cross-encoder 中，查询和文档被拼接送入同一个 Transformer 网络。自注意力机制让模型能够：

- 精确捕捉局部匹配：查询词“苹果”可以直接注意到文档中的“iPhone”，理解二者在当前上下文中的关联。

- 理解词序和限定关系：对于“除了苹果之外的水果”，模型能通过注意力关注到“除了”这个否定词，以及它与“苹果”的关系，从而避免错误匹配。

- 建模复杂的句法结构：模型可以学习到哪些查询词对应文档中的哪些片段，以及它们之间是因果关系、并列关系还是转折关系。

- 动态评估相关性：不同于提前压缩的固定向量，Cross-encoder 可以根据查询的不同，动态地关注文档中不同的部分，实现“定制化”的相关性评估。

这种深度、上下文相关的交互，使得 Cross-encoder 在判断相关性时，更像一个“阅读理解”模型，而非简单的“向量对比”。

为什么计算开销更大：

开销大的根本原因在于无法预计算。对于每一个查询，Reranker 必须将它与每一个候选文档分别拼接，然后完整地执行一次 Transformer 前向传播。这个计算成本与候选文档数量成正比。而 Bi-encoder 的文档向量是离线计算好的，在线只需一次查询编码和快速的内积运算。

推理时的输入形式：

典型的输入格式如下（以 BERT 架构为例）

```plain text
[CLS] 查询文本 [SEP] 文档文本 [SEP]
```

- `[CLS]`：这是 BERT 预留的用于分类任务的聚合 Token。经过多层 Transformer 处理后，其对应的最终隐藏状态向量会被送入一个单层线性分类器，输出一个标量作为相关性分数。

- `[SEP]`：用于分隔查询和文档，帮助模型区分两个不同的文本段。

- 输入的文本通常会进行截断，以符合模型的最大长度限制（如 512 Token）。优先保留查询的完整性，并在必要时截断文档的尾部。

整个流程就是：对每一对 `(query, doc)`，构造这样一个序列，送入模型，取 `[CLS]` 输出，计算得分，然后对所有候选文档按得分降序排列。

#### 常用的 Cross-encoder 重排序模型有哪些（如 Cohere Rerank, bge-reranker）？它们的特点。

当前，重排序模型领域百花齐放，既有强大的商业 API，也有高质量的开源选择。

1. Cohere Rerank

- 类型：商业 API 服务。

- 特点：目前公认的顶级性能之一，尤其在指令遵循和复杂语义理解上表现出色。它专为重排序任务优化，而非简单的文本相似度。其 API 设计友好，支持多语言，能直接返回排序后的文档及其相关性分数。最大的优势是零部署成本，即调即用，且持续更新。缺点是需要网络，有数据隐私顾虑，且存在调用成本。

2. bge-reranker 系列 (BAAI)

- 类型：开源模型。

- 代表：`bge-reranker-base`, `bge-reranker-large`, `bge-reranker-v2-m3` 等。

- 特点：中文和英文表现均非常出色，尤其是最新版在多项基准上接近商业 API 水平。它基于 XLM-RoBERTa 等架构，通过大量多阶段训练获得。优势是完全本地化部署，零数据泄露风险，且可通过微调适配特定领域。`bge-reranker-v2-m3` 是一个基于多语言模型的轻量版本，在速度和精度上达到了更好的平衡。

3. cross-encoder/ms-marco 系列

- 类型：开源模型。

- 代表：`cross-encoder/ms-marco-MiniLM-L-6-v2`, `cross-encoder/ms-marco-MiniLM-L-12-v2`。

- 特点：由 Microsoft 等基于 MS MARCO 数据集训练的经典系列。它们将知识从大模型蒸馏到 TinyBERT 或 MiniLM 架构，实现了极快的推理速度。虽然绝对精度可能略低于最新的顶尖模型，但它们是性价比和速度的王者，非常适合对延迟敏感的在线服务。

4. 多语言与领域特定模型

- mixedbread-ai/mxbai-rerank 系列：支持多语言的开源模型，体积小巧。

- 领域微调模型：许多团队在特定领域（如法律、医学）数据上对上述基础模型进行微调，得到领域专用的高精度 Reranker。

特点对比：

| 模型 | 精度 | 速度 | 部署 | 适用场景 |
| --- | --- | --- | --- | --- |
| Cohere Rerank | 极高 | 快（API） | 零成本，即用 | 通用高精场景，无隐私顾虑 |
| bge-reranker | 极高 | 中等 | 需GPU | 中英文高精场景，本地部署 |
| ms-marco-MiniLM | 较高 | 极快 | 需少量GPU | 延迟敏感、高吞吐在线服务 |
| 领域微调模型 | 领域内最高 | 依基座而定 | 需GPU和标注数据 | 特定垂直领域 |

选型时，需要在精度、速度、部署成本和数据隐私之间做出权衡。

#### 如何在 RAG 管线中部署 Reranker？初检索返回 N 个候选，Reranker 从中选出 Top K 的逻辑。

部署 Reranker 是 RAG 系统从“能检索到”到“检索得准”的关键一跃。其核心逻辑是：对初筛候选集逐一精细打分，重新排序后截取最优。

部署步骤与逻辑：

1. 初检索候选集生成：\
   混合检索器（稠密+稀疏）对用户查询 $q$ 执行搜索，返回一个相对较大的候选文档集合 D={d1,d2,...,dN}，其中 $N$ 通常为 50~200。这个阶段的目标是高召回率。

2. 候选集预处理：\
   对每个候选文档，提取其用于重排序的文本字段。这通常是文档的一段摘要或与查询最相关的分块，而不是全文。因为 Cross-encoder 有最大输入长度限制（如 512 Token），需要对超长文档进行截断。最佳实践是保留文档的开头部分或与查询关键词最相关的局部片段。

3. 构建 Batch 并执行推理：\
   将查询 $q$ 与每一个候选文档 $d_i$ 的文本拼接，构建成一系列输入对：`[CLS] q [SEP] d_i [SEP]`。为了提升效率，将它们打包成 mini-batch，在 GPU 上进行批量并行推理。Reranker 模型为每个文档 $d_i$ 输出一个标量得分 $s_i$。

4. 根据得分重排序并截取：\
   得到所有候选文档的得分后，系统根据 $s_i$ 从高到低对文档进行降序排列。然后，根据预设的 K（通常为 3~10，最终提供给 LLM 的上下文数量），截取排名前 $K$ 的文档作为最终的精排结果。

5. 与下游生成模型对接：\
   将这 Top K 个高质量的文档，按照特定的格式（如 `[文档1标题] 内容 [文档2标题] 内容`）拼接到生成模型的 Prompt 中，供 LLM 进行答案生成。

工程优化要点：

- 去重：如果多个候选块来自同一篇父文档，在送入 LLM 前可以只保留得分最高的一个块，或合并它们的上下文，避免冗余。

- 异步与流水线：Reranker 的推理可以与后续的生成步骤流水线化，即不等所有文档评分完成，就可以开始对先评完的高分文档进行生成前的准备工作。

- 缓存：对于高频查询，可以将其重排序后的 Top K 结果直接缓存，完全绕过后续的推理。

#### 分析 Reranker 对延迟和吞吐的影响，如何平衡精度和效率？

引入 Reranker 会显著增加 RAG 管道的端到端延迟，并降低系统的最大吞吐量。理解其开销来源，并采取相应的优化策略，是工程部署的关键。

延迟与吞吐的影响分析：

- 延迟：系统的总延迟 = 初检索延迟 + Reranker 推理延迟 + 生成延迟。Reranker 推理延迟是新增的主要部分。它等于 Cross-encoder 模型处理一个 mini-batch（大小为 N）的时间。这个时间与 N 成正比。如果 N=100，一个中等的模型可能需要 50~200 毫秒，这可能是初检索延迟的数倍。

- 吞吐：Reranker 的推理是计算密集型的，会大量占用 GPU 或 CPU 资源。每个查询都需要消耗固定的计算量，这导致系统的并发处理能力下降，最大 QPS 受限。

平衡精度和效率的策略：

1. 限制候选集大小（N）：这是最直接有效的方法。不要贪多，将 N 控制在 50~100 范围内。通过离线实验，绘制 N 与最终 Recall@K 的曲线，找到 Recall 增长的饱和点。超过这个点，增加 N 带来的精度提升微小，而延迟和成本线性增长。

2. 模型选型与加速：
  - 轻量化模型：在对精度要求不是极度苛刻的场景，优先使用 `cross-encoder/ms-marco-MiniLM-L-6-v2` 这类蒸馏小模型，而不是大型的 `bge-reranker-large`。推理速度可以快 5-10 倍。
  - 模型量化：使用 ONNX Runtime 或 TensorRT 对模型进行 INT8 量化，在几乎不损失精度的情况下大幅提升推理速度。

3. 预过滤与异步化：
  - 快速预过滤：在送入 Reranker 前，先用一个极快的、基于规则或浅层模型的过滤器筛掉明显不相关的文档（如 BM25 分数过低的），进一步缩小 N。
  - 异步非阻塞：将 Reranker 推理与后续流程解耦。对于允许稍高延迟的交互，可以异步执行重排序。

4. 结果缓存：对高频查询的重排序结果进行缓存。如果用户查询命中缓存，则完全跳过 Reranker 推理，实现零额外延迟。

5. 动态调整策略：根据查询的复杂度动态决定是否启用 Reranker 或调整 N。对于简单、意图明确的查询，可以使用较小 N 甚至跳过 Reranker；对于复杂、模糊的查询，则启用完整管道。

通过这些策略，可以在保持大部分精度收益的同时，将 Reranker 引入的额外延迟和成本控制在可接受范围内，实现精度与效率的最佳平衡点。

#### 多阶段排序：能否使用多个 Reranker 级联（粗排 → 精排）？何时需要？

多阶段排序（Cascading Rerankers）是在极端重视精度、且对延迟和成本有承受能力的场景下，采用的一种“层层筛选”策略。它使用多个不同复杂度、不同速度的排序模型，像漏斗一样逐步缩小候选集。

实现方式：

一个典型的三阶段排序管道如下：

1. 第一级（粗筛）：混合检索（稠密+稀疏），从百万级文档中召回 Top N1，如 N1=200。

2. 第二级（轻量精排）：使用一个速度极快、高度优化的轻量级 Cross-encoder（如蒸馏后的 MiniLM），对 N1 个文档进行重排序，筛选出 Top N2，如 N2=50。这一级主要用于快速去除大部分明显不相关的文档。

3. 第三级（重量精排）：使用一个参数量大、精度极高的强力 Cross-encoder（如 `bge-reranker-large` 或 Cohere API），对 N2 个文档进行最终的精细排序，选出最终的 Top K，如 K=5，送入 LLM。

何时需要：

- 对排序精度有极致要求：例如在医疗文献、法律判例检索中，排错一个文档都可能导致严重后果，需要最强力的模型进行最终把关。

- 候选集质量参差不齐：如果初筛结果的噪声很大，轻量精排可以作为“清道夫”，为重量精排创造一个更干净、更小的输入空间，让昂贵的算力聚焦在最难辨别的候选上。

- 拥有充足的计算资源和预算：多阶段排序成本高昂，需要部署和维护多个模型，延迟也会叠加。只有在业务核心、有明确 ROI 的场景下才值得投入。

关键设计点：

多阶段排序的核心在于各级模型的能力和速度的梯度要拉开。如果两级 Reranker 的性能高度相关，级联的边际收益就会很小。通常，轻量级模型注重速度（如基于蒸馏的4层模型），重量级模型注重精度（如24层的大模型），二者形成互补。

#### 重排序模型的训练数据如何构造？正负样本通常来自哪里？

训练一个高质量的重排序模型，关键在于构造能教会模型区分“真正相关”和“看似相关但实际无关”的训练数据。

正样本的构造：

正样本是“查询-相关文档”对。来源主要有：

- 人工标注：请领域专家为查询标注最相关的文档。这是质量最高的数据，但成本极其昂贵，通常只用于微调或最终评测。

- 用户点击日志：这是工业界最宝贵的正样本来源。对于一个查询，用户点击的文档可以被认为是正相关文档。但需要注意位置偏差和点击噪音。

- 现有问答/检索数据集：利用 MS MARCO、Natural Questions 等公开数据集，其中已经包含了大量标注好的“问题-相关段落”对。

- LLM 合成：使用强大的 LLM（如 GPT-4）根据文档内容生成可能的相关问题，构成“合成查询-文档”对。这是目前快速扩充高质量训练数据的有效方法。

负样本的构造：

负样本的挖掘比正样本更为关键，特别是 难负样本。它们是那些与查询在字面或浅层语义上有些相似，但实际并不相关的文档。来源包括：

- BM25 挖掘：使用 BM25 检索出字面匹配但人工标注为不相关的文档。这是经典的难负样本来源。

- 当前模型的混淆文档：使用当前性能最好的 Reranker 或初检模型，对文档进行打分，将那些模型给出虚高分数但实际不相关的文档作为难负样本。这种方法能直接针对当前模型的弱点进行迭代优化。

- 随机负采样：从文档库中随机抽取文档。由于绝大多数文档与查询无关，随机采样可提供大量的“简单负样本”。

- 跨批次负采样：在一个训练批次内，将其他查询的正文档作为当前查询的负样本。这种方法高效，但可能引入假负样本。

训练数据构造的关键点：

- 正负样本比例：通常在 1:3 到 1:7 之间。

- 混合难度：训练数据中应同时包含简单负样本（让模型快速收敛）和难负样本（提升模型的精细辨别力）。

- 数据多样性：确保训练数据覆盖多种查询类型、文档长度和领域。

#### 重排序模型是否容易过拟合于训练集分布？如何评估其在零样本领域的泛化能力？

是的，重排序模型，尤其是在特定的、有限的标注数据集上微调的模型，非常容易过拟合于训练集的查询风格、文档特征和相关性判断标准。这种过拟合会导致模型在它未见过的、分布差异大的新领域或新任务上性能急剧下降。

过拟合的表现：

- 领域过拟合：在医疗数据上微调的模型，可能学会“处方”、“诊断”等词是高相关性的强信号。当它被用于法律文书检索时，这些信号可能完全失效。

- 查询风格过拟合：如果训练集全是短关键词查询，模型可能不擅长处理长问句查询。

- 标注偏差：模型可能学习到标注员的个人偏好，而不是真实的客观相关性。

评估零样本泛化能力：

零样本泛化能力是指模型在不经过新领域训练的情况下，直接在新领域数据集上的表现。评估方法包括：

1. 使用标准化的多领域评测基准：\
   BEIR (Benchmarking IR) 是评估检索和重排序模型泛化能力的最权威基准。它包含了 18 个来自不同领域的数据集，如金融、新闻、问答、生物医学等。评估一个 Reranker 在 BEIR 上所有数据集的平均性能（如 nDCG@10），而不是仅仅看它在某个单一数据集（如 MS MARCO）上的表现，是衡量其泛化能力的金标准。

2. 构造领域外测试集：\
   企业应根据自己的业务，构建一个或多个与训练数据来源完全不同的“野生”测试集。这包括真实的用户查询和人工标注的答案。在这个测试集上评估模型性能，是最贴近实际效果的泛化能力检验。

3. 分析性能下降的幅度：\
   将模型在训练领域测试集上的得分，与在零样本领域测试集上的得分进行对比。一个泛化能力强的模型，这两个得分之间的差距应该较小。

缓解过拟合、提升泛化性的方法：

- 多领域混合训练：在训练时，混合来自多个不同领域的数据集，迫使模型学习通用的相关性特征。

- 数据增强：使用 LLM 对查询进行重写、回译、引入噪音等，增加训练数据的多样性。

- 正则化与参数高效微调：使用 Dropout、权重衰减等正则化技术。采用 LoRA 等参数高效微调方法只训练少量参数，能一定程度上保留基座模型的通用能力，降低过拟合风险。

#### 轻量级 Reranker 的设计：如何使用蒸馏、量化或小模型来加速重排序？

在延迟敏感的在线服务中，标准 Cross-encoder 的推理速度是不可接受的。轻量级 Reranker 的设计目标是在大幅降低计算开销的同时，尽可能地保留排序精度。主要技术路径包括模型蒸馏、量化和直接使用小模型。

1. 模型蒸馏：

这是最核心的轻量化技术。用一个高精度但慢速的大型教师模型，去教导一个结构小巧、快速的学生模型。

- 流程：
  - 准备无标签数据：收集一批用户查询，用教师模型为每个查询的候选文档预测相关性分数。
  - 训练学生模型：学生模型（如 TinyBERT, MiniLM）使用相同的输入，学习去拟合教师模型给出的软标签（分数分布），而不是硬标签（0/1）。

- 优点：可以将 24 层 BERT 的教师模型的知识，成功迁移到仅 4 到 6 层的 MiniLM 学生模型上，实现速度提升 5-10 倍，而精度仅损失几个百分点。`cross-encoder/ms-marco-MiniLM-L-6-v2` 正是这一技术的经典产物。

2. 模型量化：

将模型参数从高精度（FP32）转换为低精度（INT8）表示，以降低计算和内存需求。

- 方式：
  - INT8 量化：通过 TensorRT、ONNX Runtime 等工具对模型进行静态或动态量化。推理时使用 INT8 核心进行计算，速度可提升 2-4 倍，模型体积缩小 4 倍。

- 优点：这是一种“黑盒”优化，无需重新训练模型，可以直接对任何已训练好的模型应用。精度损失通常非常小。

- 注意：量化对硬件（如支持 INT8 指令集的 CPU/GPU）有要求，且极低比特（如 INT4）的量化可能导致精度显著下降。

3. 直接设计和使用小模型：

- NAS（神经架构搜索）：通过算法自动搜索出在给定延迟和精度约束下最优的微型模型结构。

- 小型预训练模型：直接使用 TinyBERT、MobileBERT 等专门为边缘或实时场景设计的预训练模型，在其上进行重排序任务的微调。

工程实践中的组合策略：

一个常见的极致优化流水线是：

1. 选择一个小体量的学生模型（如 4层MiniLM）作为基座。

2. 使用业务领域的大模型作为教师，通过蒸馏训练该学生模型，确保领域精度。

3. 对蒸馏后的学生模型进行 INT8 量化。

4. 使用高性能推理引擎（如 ONNX Runtime 或 TensorRT）进行部署。\
   通过这种“蒸馏+量化+推理优化”的组合拳，可以将 Reranker 的推理延迟从数百毫秒降低到十毫秒以内，使其可以流畅集成到对延迟要求极高的在线 RAG 服务中。

#### 如何将 Reranker 与混合检索结合？是否有统一的框架？

将 Reranker 与混合检索结合，本质上是把混合检索输出的高质量候选池，交给 Reranker 进行最终的精细排序。这是一个经典的多阶段排序架构，业界已有成熟的统一框架和最佳实践。

结合模式：

混合检索负责高召回，Reranker 负责高精度，两者在管道中前后衔接。

1. 混合检索生成候选池：用户查询被同时送入稠密检索和稀疏检索，两路结果通过 RRF 或分数融合，生成一个统一的相关文档候选集 $C$，大小为 N（如 50~200）。这个候选集已经初步结合了语义和关键词的优势，质量高于任何单一路径。

2. Reranker 精排：将候选集 $C$ 中的每一个文档与查询进行拼接，送入 Cross-encoder 模型，逐一计算精细相关性分数。根据新分数重新排序，从中选出最终的 Top K（如 3~10）个文档，提供给下游生成模型。

统一框架：

目前许多现代向量数据库和检索框架已经将混合检索与重排序集成在统一 API 中。例如：

- LlamaIndex：提供了 `HyDE`、`Reciprocal Rerank Fusion` 等模块，可以轻松将多种检索器与各种 Reranker（如 Cohere, bge-reranker）组合。

- LangChain：通过 `EnsembleRetriever` 组合不同检索器，并使用 `ContextualCompressionRetriever` 或 `LLMChainExtractor` 等实现重排序。

- Weaviate：在内部支持混合搜索，并可通过 `rerank` 模块集成 Cohere 等外部 Reranker。

- Milvus：从 2.3 版本开始支持混合搜索，并在 2.4 版本中引入了内置的 Reranker 框架。

这些框架的共性在于：将检索器、融合器和重排序器视为可插拔的组件，通过配置文件或几行代码即可构建完整的检索-精排管道。开发者无需从头实现复杂的协调逻辑。

关键注意事项：

- 去重：混合检索融合时，同一文档可能来自稠密和稀疏两路。RRF 已经自然处理了排名信号累加，但在送入 Reranker 前，需要按文档 ID 去重，避免重复计算。

- 候选集大小：混合检索的召回数量 $N$ 需要合理设置。过大则 Reranker 开销过高，过小则可能遗漏关键文档。通常 $N$ 设为 50~200 之间，具体取决于 Reranker 速度和延迟预算。

- 分数归一化：如果混合检索阶段是分数融合，则其输出的分数可能已经归一化。Reranker 的分数与之无关，可以独立计算，不需要再做归一化。

因此，混合检索 + Reranker 已成为高性能 RAG 系统的标配架构。它就像一个“粗选-精选”的流水线，最大化利用不同模型的互补优势。

#### Reranker 的 prompt 相关性：是否可以在 Reranker 中加入任务指令以提高准确性？

是的，现代的重排序模型（尤其是基于指令微调的模型）已经支持在输入中加入任务指令，以引导模型更准确地理解排序目标和上下文。这与指令微调 Embedding 模型的思路一脉相承。

加入任务指令的方式：\
对于支持指令的 Cross-encoder，输入不再是简单的 `[CLS] query [SEP] document`，而是变成：

```plain text
[CLS] 任务指令 [SEP] query [SEP] document [SEP]
```

例如，在医疗检索场景中，指令可以是：“判断以下文档是否包含与患者症状相关的诊断信息”。

为什么能提高准确性：

- 任务感知：指令明确告知模型当前排序的具体目标和领域，使其能够调整内部注意力，关注与指令相关的语义特征。例如，“用于检索”和“用于问答”可能需要不同的相关性标准。

- 领域自适应：通过指令注入领域知识（如“优先考虑最新发表的文献”或“只关注安全性相关的段落”），可以快速定制化 Reranker 的行为，而不需要重新微调模型。

- 多任务处理：一个支持指令的 Reranker 可以服务于多个不同的下游应用，只需切换指令即可。

实际应用：

- Cohere Rerank API 直接支持 `prompt` 参数，允许用户传入自然语言指令。

- bge-reranker-v2-m3 等开源模型在训练时引入了指令微调，可以接受任务前缀。

- 在自定义微调 Reranker 时，可以在训练数据中加入多样化的指令，让模型学会根据指令动态调整。

注意事项：

- 指令应该简洁、明确，避免引入歧义。

- 指令的长度会占用模型的最大输入窗口，需要在指令详细度和文档截断长度之间平衡。

- 目前并非所有 Cross-encoder 都原生支持指令，使用时需查阅模型文档。

总之，将任务指令引入 Reranker，是提升其准确性和灵活性的重要手段，尤其在需要处理多任务、多领域的复杂 RAG 系统中。

#### 对多语言文档的 Reranking，模型需要多语言支持吗？有哪些多语言 Reranker？

是的，处理多语言文档的 Reranking 需要模型具备多语言理解能力。如果用仅支持英文的 Reranker 去排序中文文档，其性能会严重下降，因为模型无法理解文本内容，只能依赖表面的词汇重叠。

为什么需要多语言支持：

Cross-encoder 的底层是预训练语言模型。如果该模型只在英文语料上训练，它的词表和语义空间都是英文的，对中文、日文等其他语言的分词和语义理解能力几乎为零。它将中文文本视为未登录词（UNK），相关性判断完全失效。因此，必须使用多语言预训练模型作为基座。

多语言 Reranker 模型：

- bge-reranker-v2-m3 (BAAI)：这是目前最出色的开源多语言 Reranker 之一。它基于 XLM-RoBERTa 架构，支持超过 100 种语言，在中文和英文上表现均非常强劲。训练时使用了多语言数据，能很好地处理跨语言和混合语言场景。

- Cohere Rerank 商业 API 也支持多语言，底层模型经过多语言训练，可以直接处理多种主流语言。

- mixedbread-ai/mxbai-rerank 系列：也提供了多语言版本，体积小巧，适合轻量级部署。

- 多语言 MiniLM 系列：如 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` 虽然主要用于文本相似度，但也可以作为 Reranker 的基座进行微调。

使用时的考量：

- 语言识别与路由：如果文档库包含多种语言，可以在 Reranker 之前通过语言检测，将查询和文档的语言信息作为指令的一部分注入，或根据不同语言选择专门的 Reranker。

- 跨语言场景：支持多语言的 Reranker 能够处理用户用一种语言查询、检索另一种语言文档的跨语言检索。它的多语言语义空间已经对齐。

- 微调：如果有大量特定领域多语言数据，可以在通用多语言 Reranker 上进行微调，以进一步提升领域内性能。

因此，多语言 Reranker 是构建国际化 RAG 系统不可或缺的组件。

#### Reranker 如何处理超长文档？常见的截断策略或段落选取方法。

Reranker 模型通常有严格的输入长度限制（如 512 或 8192 个 Token）。当候选文档的长度超出这一限制时，必须进行截断或段落选取。这并非简单的丢弃，而是需要尽可能保留与查询最相关的部分。

常见策略：

1. 简单头部截断：\
   直接保留文档的前 `L` 个 Token（`L` 为模型最大长度减去查询长度和特殊 Token）。这种方法最简单，但假设文档的开头部分包含最重要信息，这在很多文档（如新闻、论文摘要）中是成立的，但可能丢失正文中关键的细节。

2. 与查询相关的动态滑动窗口：\
   先使用一个轻量级的算法（如 BM25 或稠密检索）对文档进行分段，找到与查询最相关的一个或多个段落。然后，以这些段落为中心，截取一个固定长度的窗口。也可以将多个相关段落拼接，但总长度不超过限制。这种方法更智能，能最大化保留信号。

3. 滚动分块，分别评分后取最大值：\
   将长文档按固定步长切分为多个有重叠的块（Chunk）。将每个块与查询独立送入 Reranker 打分。然后，取所有块得分的最大值作为整篇文档的最终得分。这种方法保证了不会因为截断而漏掉文档中间的关键信息，但计算开销增加了数倍。

4. 摘要注入：\
   如果系统在索引阶段就为每篇长文档生成了摘要，那么可以直接使用摘要作为 Reranker 的输入。因为摘要已经高度概括了文档的核心内容，信息密度极高。这是一种非常高效的策略。

最佳实践：

- 优先使用智能截断：利用初检时命中的分块位置，直接将该分块及其周围上下文作为 Reranker 的输入。这是 RAG 中最常见的做法，因为检索时的分块已经是最相关的候选片段。

- 结合元数据：文档的标题、小标题等信息可以作为前缀注入，为 Reranker 提供全局背景。

- 动态策略：根据文档长度和类型自动选择截断方式。对于极长的文档，结合摘要和关键片段。

通过精心的截断设计，可以极大限度地降低长文档带来的信息丢失风险，保证 Reranker 的精度。

#### 评估 Reranker 的指标：除了精度提升，还应关注排序质量（如 nDCG, MRR）？

评估 Reranker 不能只看最终答案的准确率，因为 Reranker 的直接产出是一个排序列表，而非最终答案。因此，必须使用排序质量评估指标，同时也要衡量其对下游任务的影响。

关键排序质量指标：

1. nDCG@K：归一化折损累计增益。这是评估排序质量最全面、最常用的指标。它考虑了两个因素：相关文档是否排在前面，以及相关文档的相关度等级（例如 0-4 级）。它通过折损函数对排名靠后的结果进行惩罚，并对分数进行归一化。在评估 Reranker 时，通常报告 nDCG@10。

2. MRR：平均倒数排名。它只关心第一个相关文档出现的位置。对于许多问答任务，用户只关心第一个正确的答案，MRR 非常直观。MRR 值越高，说明 Reranker 把正确答案排在最前面的能力越强。

3. MAP：平均精度均值。它综合考虑了所有相关文档的排名和精度。MAP 对排序列表中每个相关文档的位置都给予奖励，比 MRR 更全面，但对多重相关文档的场景敏感。

4. Recall@K：虽然这是检索指标，但在重排序后同样重要。它衡量经过 Reranker 后，前 K 个结果中是否包含了足够的相关文档。我们希望 Reranker 不会漏掉在初检中被召回的相关文档（即 Recall 不降）。

5. Precision@K：衡量前 K 个结果中相关文档的比例。在 Reranker 后，我们期望这个指标比初检有大幅提升。

与下游任务联合评估：

除了上述独立的排序指标，还应评估 Reranker 对最终 RAG 系统的影响：

- 生成答案的正确率/忠实度：将 Reranker 精选的文档提供给 LLM 后，评估生成的答案是否正确、是否忠实于提供的上下文。

- 端到端延迟：Reranker 带来的额外延迟有多大，是否在可接受范围内。

- 吞吐量：Reranker 对系统并发处理能力的影响。

一个全面的评估报告应同时包含排序指标（nDCG, MRR）和下游任务指标，以充分证明 Reranker 的价值。

#### 对比基于 LLM 的 Reranker（如用 GPT-4 进行成对比较）与专门 Cross-encoder 的优劣。

随着大语言模型的崛起，使用 GPT-4 等强大模型直接进行重排序成为一种新兴方案。它与传统的专门 Cross-encoder 在原理、效果和成本上差异显著。

基于 LLM 的 Reranker：

- 工作原理：通过提示工程，让 LLM 对一组候选文档进行排序。可以一次性输入所有文档并要求输出排序，或者进行成对比较。常用方法包括：点式（直接打分）、列表式（输出排序列表）、成对比较（两两比较后综合排序）。

- 优势：
  - 推理能力极强：GPT-4 等模型具有强大的常识推理和复杂语义理解能力，能捕捉到传统 Cross-encoder 难以学习的深层逻辑关系。
  - 零样本泛化：无需任何训练数据，开箱即用，对新任务和新领域的适应性极好。
  - 可解释性：可以通过 Chain-of-Thought 让模型同时输出排序理由。

- 劣势：
  - 成本极高：调用 GPT-4 API 进行大规模排序的费用远高于运行一个本地 Cross-encoder。
  - 延迟高：API 调用的网络延迟和生成延迟都较大，难以满足实时在线服务的需求。
  - 一致性问题：LLM 的输出可能不稳定，相同输入多次结果可能不同，且可能产生幻觉或位置偏差。
  - 上下文窗口限制：一次输入的候选文档数量受限于 LLM 的上下文窗口，且长文档会急剧增加成本。

专门 Cross-encoder：

- 工作原理：基于 BERT 类模型，通过大规模文本对训练，专门学习文本相关性匹配任务。

- 优势：
  - 极致的效率和成本：本地化部署，推理速度快，单位计算成本远低于 LLM。
  - 性能稳定：专门为排序任务优化，输出稳定，可重复性高。
  - 易于优化：可以进行量化、蒸馏、TensorRT 加速等极致工程优化。

- 劣势：
  - 泛化能力有限：需要标注数据微调，在零样本新领域可能不如 LLM。
  - 推理能力弱：对于需要复杂世界知识或逻辑推理的排序任务，能力不及 LLM。

适用场景：

- 离线评估、高价值少量排序、需要深度推理时：可选用基于 LLM 的 Reranker，例如用 GPT-4 对最重要的查询进行精细排序，或生成训练数据。

- 在线实时服务、大规模排序、成本敏感场景：专门 Cross-encoder 是唯一实际可行的选择。

两者常以级联形式合作：用 Cross-encoder 进行快速粗精排，将缩小后的顶尖候选集（例如 Top 10）送给 LLM 进行最终决策和推理，兼顾效率与智能。

#### 重排序中的位置偏差：Reranker 是否会对靠前的候选更偏好？

位置偏差是指模型在评估文档相关性时，受到文档在输入列表中位置的影响，而不仅仅是其内容。对于 Cross-encoder 而言，它处理的是单个查询-文档对，理论上不存在列表位置偏差，因为每对都是独立评估的。

为什么 Cross-encoder 没有位置偏差：\
Cross-encoder 的输入是 `[query, document]`，每次只对一个文档打分。它没有“看到”其他候选文档，因此不知道任何文档在初检列表中的排名。所有文档都在公平的起跑线上。这与生成式 LLM 的列表重排序有本质不同。

但 Cross-encoder 可能存在另一种“伪位置偏差”：

如果使用滚动分块策略对长文档取最大分数，那么文档中越靠前的段落被选为相关段落的概率可能更高（因为截断策略可能偏好开头）。这是一种文档内部位置偏差，而非列表位置偏差。

在模型微调阶段可能引入偏差：

如果训练数据中，正样本主要来自初检的前几名（例如只标注了前 10 个结果），模型可能学会对那些看起来“更有可能被选为正样本”的特征（如某些关键词密度）产生偏好，但这种偏差不是来自位置本身。

缓解位置偏差的措施（主要针对使用 LLM 列表重排序时）：

- 在提示中随机打乱候选文档的顺序，让 LLM 意识到位置并不重要。

- 使用成对比较（Pairwise）而非列表排序，并多次比较取平均。

- 对于 Cross-encoder，不需要特别处理，因为它本身无此问题。

因此，纯粹的 Cross-encoder 重排序不受初检排名影响，这也是它相对于某些启发式融合方法（如加权分数）的一大优势。

#### 如何在线更新 Reranker 以适应动态变化的文档库？

动态文档库会不断有新文档加入、旧文档更新或删除。Reranker 本身是一个评分模型，它不直接存储文档索引，因此更新相对简单。但为了保持其排序质量，需要关注模型和输入特征的时效性。

更新策略：

1. 模型定期重训或微调：\
   当文档分布发生显著变化（如新领域、新术语大量涌现）时，原有的 Reranker 可能无法准确评估新文档的相关性。此时需要：
  - 收集新一批的标注数据（可通过用户点击日志、LLM 合成等方式）。
  - 在原有模型基础上进行增量微调，或使用新旧混合数据重新训练。
  - 对于轻量级模型，这种更新可以频繁进行（如每周）。

2. 特征时效性注入：\
   如果文档有发布时间或时效性要求，可以在 Reranker 的输入中显式加入时间信息作为特征。例如，将发布日期文本化后拼入输入，或者使用指令：“优先考虑 2024 年之后的文档”。这样，即使模型不重新训练，也能动态地根据时效性调整偏好。

3. 模型热切换：\
   部署新的 Reranker 模型时，应支持无中断的热切换。线上同时存在新旧两个模型服务，流量逐步切换，待新模型稳定后下线旧模型。

4. 文档质量监控与反馈闭环：\
   收集最终生成答案的用户反馈（点赞/踩、停留时间），间接反映 Reranker 排序质量。将负面案例沉淀为新的训练样本，持续优化模型。

与初检索的协同更新：

Reranker 的候选集来自初检索。当初检索的索引发生重大更新（如重新分块、更换 Embedding 模型）时，Reranker 也应随之重新评估或微调，因为输入的分布可能已经改变。

总之，Reranker 的在线更新是一种模型运维闭环，重点在于数据的持续采集和模型的快速迭代，以保证其与动态知识库的匹配度。

#### 在安全领域，Reranker 是否可以用来过滤有害或不相关的内容？

完全可以，而且这是 Reranker 的一个重要安全应用方向。它可以作为内容安全管道中的最后一道“精密过滤器”，在内容呈现给用户或 LLM 之前，拦截有害信息。

应用方式：

1. 训练专门的安全 Reranker：\
   在标注数据中，将“有害、违规、无关”内容标记为负样本，将“安全、相关”内容标记为正样本。训练出的 Reranker 能够为文档输出一个“安全性/相关性”分数。在检索后，设置一个安全阈值，低于该阈值的文档直接丢弃。

2. 多目标融合：\
   一个 Reranker 可以同时输出多个分数：相关性分数和安全性分数。通过加权融合，确保返回的内容既相关又安全。

3. 作为 LLM 的安全护栏：\
   在 RAG 中，即使检索到的文档包含有害内容，如果在送入 LLM 之前经过 Reranker 过滤，就可以在上下文窗口外就消除风险。这比依赖 LLM 自身的安全对齐更可靠、更可控。

4. 实时政策适配：\
   当内容安全政策发生变化时（如新增违规类别），可以通过微调或修改 Reranker 的训练数据快速适应，而不需要重新训练整个生成模型。

优势：

- 高效：Reranker 的推理速度远快于 LLM，可以在高吞吐场景下实时过滤。

- 可控：安全标准可定制，可解释性强，便于审计。

- 独立：安全模块与生成模块解耦，降低单点风险。

注意：

- Reranker 本身并非绝对可靠，需要持续迭代和对抗测试。

- 对于极其隐蔽的恶意内容，仍需多级防御。

因此，安全 Reranker 是构建可信 RAG 系统的重要工具，它将内容审核从“事后补救”提前到了“事前拦截”。

#### 如果初检索的召回很低，Reranker 是否能弥补？其作用边界在哪里？

结论先行：Reranker 无法弥补初检索的召回失败。它的作用边界在于：只能从给定的候选集中挑选最好的，而不能召回候选集之外的相关文档。

原理解析：\
Reranker 是一个“精排器”，不是“检索器”。它没有建立索引，不具备从海量文档库中搜索文档的能力。它只能接收初检索提交的候选集 $C$，并在这个集合内部进行重新排序。如果某个相关文档没有被初检索召回（即不在集合 $C$ 中），那么 Reranker 就永远“看不到”它，也就无法将其提升至 Top K。

初检索召回低的原因：

- 词汇不匹配（查询用词与文档用词完全不同），BM25 失效。

- 语义鸿沟过大，稠密检索的 Embedding 模型无法理解。

- 分块策略不当，信息被切碎。

这些根本性缺陷导致相关文档根本没有进入候选池。Reranker 无法解决“找不到”的问题，它只能解决“找到了但排不上去”的问题。

Reranker 的作用边界：

Reranker 的价值体现在提升精度上。当且仅当初检索的召回率足够高（例如，相关文档已经在 Top 200 内），Reranker 才能发挥其作用，将这些相关文档从候选池的中下游“捞”到前列，从而提高最终提供给 LLM 的上下文质量。如果初检索的召回率很低（例如，相关文档在 Top 500 之外），Reranker 将无力回天。

最佳实践：

- 先优化初检索的召回：确保混合检索、查询重写、分块等策略能够将核心文档稳定地召回在 Top 100-200 内。

- 用 Reranker 解决“排序不准”问题：当初检索的 Recall 已经达标（例如 Recall@100 > 0.95），但 Precision 或 nDCG 不够高时，引入 Reranker。

- 监控管道各阶段指标：分别监控初检索 Recall@N 和最终输出 Recall@K，以定位性能瓶颈是在召回还是在精排。

因此，Reranker 不是万能的，它必须建立在高召回初检索的基础之上。只有“捞得足够多”，Reranker 才有“精选”的原料。

#### 使用 Reranker 时，初检索的召回数量 N 如何影响最终质量？最佳 N 的确定方法。

初检索召回的候选集大小 $N$ 是 Reranker 管道中最重要的超参数之一，它直接决定了精度、延迟和成本的平衡点。

N 对最终质量的影响：

- N 过小（如 N=10）：初检索可能遗漏核心相关文档，导致 Reranker 失去精选的基础。即使 Reranker 再强，也无法补救漏网之鱼。最终质量受限于初检索的 Recall@10。

- N 过大（如 N=500）：初检索的高 Recall 提供了充足原料，但 Reranker 需要处理的文档数量大增。这会带来更高的计算延迟、GPU 成本和 API 费用。而且，当 N 超过一定阈值后，新增的文档大多是“噪音”，Reranker 的边际收益急剧下降。

- 存在最优区间：通常，从 N=1 开始，最终质量（如 nDCG@10）随 N 增大而快速上升；当 N 达到某个临界点（例如 50~100）后，上升趋势趋于平缓，甚至因引入过多噪音而略有下降。

最佳 N 的确定方法：

1. 离线实验：
  - 使用一个代表性的查询集和对应的标注答案。
  - 保持 Reranker 不变，改变初检索的召回数量 $N$（例如 10, 20, 50, 100, 150, 200）。
  - 绘制 N vs. 最终检索质量（如 nDCG@10） 曲线。
  - 同时记录 N vs. Reranker 推理总延迟 曲线。

2. 寻找帕累托最优：
  - 在 “nDCG vs. 延迟” 图上，找到那个拐点：继续增大 N，nDCG 的提升微乎其微，而延迟却线性增长。这个拐点就是最佳 N。

3. 考虑成本预算：
  - 如果使用付费 API Reranker（如 Cohere），还需要计算成本。根据预算上限，反推可承受的最大 N。

4. 动态设置：
  - 对于不同类型的查询，设置不同的 N。例如，简单查询用较小的 N（30），复杂长尾查询用较大的 N（100）。可以通过查询意图分类器实现。

经验法则：

- 对于追求高精度的离线场景，N 可设为 100-200。

- 对于在线实时服务，N 通常设为 30-100。

- 许多系统采用 N=50 作为默认值，能够在延迟和精度之间取得良好平衡。

最终，N 的选择是在你的具体硬件、模型和业务指标上跑出来的，而不是抄某个固定数字。通过科学的离线实验，可以找到最适合自己系统的最佳 N。
