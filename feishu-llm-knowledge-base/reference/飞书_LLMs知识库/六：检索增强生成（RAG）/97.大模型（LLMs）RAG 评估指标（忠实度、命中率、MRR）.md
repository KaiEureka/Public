# 97.大模型（LLMs）RAG 评估指标（忠实度、命中率、MRR）

#### RAG 系统评估通常分为哪几个层面？检索评估、生成评估、端到端评估。

RAG 系统的质量评估不能只盯着最终答案的对错。因为 RAG 是一个由检索和生成两大环节串联而成的管道，任何一个环节出问题都会导致最终答案失败。一个优秀的评估体系必须是分层、多维度的，通常包含三个核心层面：检索评估、生成评估、以及端到端评估。

检索评估——关注“喂给模型什么”

检索是 RAG 的第一道工序，它决定了后续生成的天花板。检索评估不关心最终的答案是什么，只关心从知识库中捞出的文档是否真正相关，以及它们的排序是否合理。核心指标通常包括：

- 命中率：衡量所有相关文档中，有多少被成功召回了。它检查的是检索的“完整性”。

- MRR：衡量第一个相关文档出现在结果列表中的平均位置。它检查的是检索的“精准性”和“便利性”。

- NDCG@K：更全面地衡量排序质量，考虑相关文档的排名位置和相关度等级。\
  如果检索评估得分很低，说明知识库建设、分块策略、嵌入模型或检索算法存在问题。此时去调试生成部分是徒劳的。

生成评估——关注“模型消化了之后产出什么”

生成评估假设检索已经提供了正确的文档，专注于评估大语言模型利用这些文档生成答案的质量。核心指标包括：

- 忠实度：这是最重要的指标。它衡量生成的答案是否完全基于检索到的上下文，有没有凭空编造事实。这是对抗幻觉的关键。

- 答案相关性：衡量生成的答案是否切实回答了用户的问题，有没有答非所问。

- 信息覆盖率：衡量答案是否完整覆盖了上下文中与问题相关的所有关键信息点。

端到端评估——关注“整个系统作为一个黑盒好不好用”

端到端评估不关心内部是检索错了还是生成错了，只从用户视角评判最终输出。它结合了客观指标和主观体验，包括：

- 整体正确率：人工或自动评判答案的整体对错。

- 用户满意度：通过 A/B 测试、用户点赞/踩、停留时间等业务指标来衡量。

- 任务成功率：在 Agent 式 RAG 中，评估整个多步任务是否完成。

- 延迟与成本：系统的响应速度和资源消耗，这是决定系统能否上线的重要工程指标。

这三个层面缺一不可。只做端到端评估，发现问题后无法定位根因；只做检索评估，无法保证最终答案的质量。一个成熟的 RAG 评估体系，必须在这三个层面都建立基线、进行监控和迭代优化。

#### 什么是忠实度？在 RAG 中如何定义和量化忠实度？

忠实度的定义

忠实度是 RAG 系统最核心的质量指标之一。它衡量的是大模型生成的答案，其内容是否可以从给定的上下文文档中直接推导或验证。一个忠实度高的答案，意味着模型就像一个严谨的新闻发言人，所说的每一句话都有文件依据，而不是靠自己脑补。反过来，忠实度低的答案，就是模型在“一本正经地胡说八道”，产生了幻觉。

为什么忠实度如此重要

RAG 的初衷就是通过引入外部知识来抑制幻觉、提升可信度。如果模型拿到相关文档后，依然无视其内容、凭空编造事实和数字，那么整个 RAG 管道就彻底失败了。在所有评估维度中，忠实度通常是第一道红线：忠实度不达标，答案正确率再高也不可信任，因为用户无法分辨哪句话是真实依据，哪句是凭空捏造。

如何量化忠实度

量化忠实度是一个精细的自然语言理解任务，目前主流方法分为三类：

1. 基于蕴含关系的方法：这是最常用、最成熟的自动评估手段。首先，将生成的答案拆解为一个个独立的原子事实。然后，使用一个在自然语言推理（NLI）数据集上微调过的模型（如 RoBERTa），逐一判断每个原子事实是否可以被检索到的上下文“蕴含”。如果上下文蕴含该事实，则认为它是忠实的；如果上下文无法支持甚至与该事实矛盾，则认为它不忠实。最终计算被蕴含的事实占总事实的比例，得到忠实度分数。

2. 基于问答验证的方法：这种方法不直接判断蕴含关系，而是采用一种更巧妙的思路：如果答案中的某个信息确实是来自上下文，那么根据这个信息构造的问题，应该也能从上下文中找到相同的答案。系统会从答案中生成一系列问题，然后让模型仅根据上下文来回答这些问题，最后比较原答案和新答案的一致性。

3. 基于 LLM 作为评判者的方法：直接使用一个强大的 LLM（如 GPT-4）来进行忠实度打分。提示词精心设计，要求 LLM 逐句检查答案是否得到上下文支持，并输出结构化的理由和分数。这种方法灵活性最高，但成本也最高，且其本身的判断也可能存在偏见。

在实践中，通常是“蕴含评估器”和“LLM 评判者”两者结合，前者用于大规模自动化回归测试，后者用于高价值的最终审核和争议案例的人工仲裁。

#### 如何评估生成答案是否忠实于检索到的上下文？常用的自动指标（如 entailment 比率）是什么？

评估生成答案的忠实度，本质上是在做细粒度的事实核查。这项工作不能依赖简单的词重叠（如 ROUGE），因为一个句子完全可以和上下文使用完全不同的词汇，但意思相同；或者使用完全相同的词汇，但通过拼接和扭曲产生虚假陈述。我们需要的是对“陈述是否得到证据支持”的语义判断。

核心自动指标：蕴含比率

“蕴含比率”是忠实度评估中应用最广、最经典的自动指标。它的工作流程如下：

1. 答案分解：将待评估的生成答案，分解为一组最小、独立的“原子事实”。每个原子事实都是一个简短的、包含单一信息的陈述句。例如，“爱因斯坦出生于1879年的德国乌尔姆市”可以被分解为两个原子事实：“爱因斯坦出生于1879年”和“爱因斯坦出生于德国乌尔姆市”。

2. 逐条验证：将每一个原子事实作为“假设”，将检索到的所有上下文拼接起来作为“前提”。送入一个自然语言推理（NLI）模型（如 RoBERTa-Large fine-tuned on MNLI）。NLI 模型会输出三种标签之一：`entailment`（蕴含，即上下文支持该事实）、`contradiction`（矛盾，即上下文与该事实冲突）、`neutral`（中立，即上下文不涉及该事实，无法判断）。

3. 比率计算：统计所有被标记为 `entailment` 的原子事实数量，除以原子事实总数，得到的就是“蕴含比率”。这个比率直接代表了答案中有多大比例的事实是有据可查的。

为什么这个指标有效？

NLI 模型经过大量数据训练，能够捕捉到词汇层面的同义表达、逻辑蕴含和矛盾关系，而不只是字面匹配。它能够判断“苹果发布了新手机”是否在语义上得到“Apple 公司推出了下一代 iPhone”的支持。这种能力是忠实度评估所需要的，也是 n-gram 匹配完全无法比拟的。

其他辅助指标

- 矛盾率：如果某些原子事实被标记为 `contradiction`，这是一个非常危险的信号，说明模型不仅在编造，而且在编造与事实相反的信息，这比信息缺失危害更大。

- 基于问答的指标（QAGS 等）：通过“答案-问题-再回答”的闭环，评估信息的一致性。如果从答案中提取的问题，用原文能够回得到相同的答案，则说明该信息是忠实于原文的。

注意事项

自动 NLI 模型并非完美，它在处理需要复杂推理、领域专有知识或长文档时准确率会下降。因此，对于高风险的医疗、法律等场景，建议定期用“蕴含比率”进行全量自动化扫描，发现异常案例后，再由人工或昂贵的 GPT-4 进行二次复核。

#### 命中率如何计算？它度量了什么？在 RAG 中为何重要？

命中率的定义与计算\
命中率，通常指 Recall@K，衡量的是“对于一批用户问题，在检索器返回的前 K 个文档片段中，平均包含了多少个真正相关的文档”。它的计算公式非常直接：\
`Hit Rate = (所有查询中，其相关文档在 Top-K 结果中被找到的查询数量) / (总查询数量)`。\
更精确的 Recall@K 则是：对于每个查询，计算 `(Top-K 结果中相关文档的数量) / (该查询总共拥有的相关文档数量)`，然后将所有查询的这个值取平均。

它度量了什么

命中率度量的是检索系统的查全率。它的关注点非常纯粹：正确答案有没有被捞进来？ 它不关心正确答案是排在第1位还是第10位，也不关心捞进来的除了正确答案之外还有多少垃圾信息。它只管“不漏掉”。一个命中率为 0.9 的检索器，意味着对于 90% 的用户问题，至少有一篇能够回答它的文档出现在了前 K 个结果里。

在 RAG 中为何重要

命中率是 RAG 系统的生命线。原因极其简单：如果检索器根本没有把相关文档“喂”给大模型，那么大模型再聪明，也是巧妇难为无米之炊，注定无法正确回答这个问题。这是 RAG 系统最大的失败模式——不是回答错了，而是根本没有机会回答对。因此，命中率通常是大语言模型 RAG 管道优化时最先被关注、也最重要的指标。一旦命中率不达标，后续所有关于生成质量的讨论都失去了意义。这也是为什么在系统调试时，我们会用大量精力去优化分块策略、嵌入模型、查询重写、HyDE 等技术，这些技术的首要目标都是为了提升这个 KPI。

命中率的局限

命中率虽然重要，但它只看“有没有”，不看“在哪里”。如果一个系统把正确答案召回了，但排在了第 80 位，而你的下游生成模型只接收前 5 个文档作为上下文，那么这个第 80 位的正确答案对生成来说就是不可见的。因此，命中率必须和 MRR 或 nDCG 等排序质量指标结合使用，才能全面地评估一个检索系统。

#### MRR（Mean Reciprocal Rank）的定义和计算公式，为什么它关注第一个相关文档的排名？

MRR 的定义与计算公式\
MRR 是信息检索领域衡量排序质量的一个经典指标，它专门关注第一个相关文档出现在结果列表中的排名位置。对于一组查询，MRR 的计算公式为：\
`MRR = (1/|Q|) * Σ (1 / rank_i)`，其中 `|Q|` 是查询总数，`rank_i` 是第 i 个查询的第一个相关文档在结果列表中的排名（从 1 开始）。\
例如，用户问了三个问题，系统对这三个问题的返回结果中，第一个相关文档分别排在第 1 位、第 3 位和第 10 位。那么 MRR 就是 `(1/1 + 1/3 + 1/10) / 3 ≈ 0.48`。

为什么关注第一个相关文档的排名

这个指标的设计背后，有着深刻的产品哲学。它模拟了用户在使用搜索引擎时的经典行为模式：用户极度缺乏耐心，通常只会浏览搜索结果列表的最前面几条，然后点击第一个看起来相关的链接。如果第一页翻完还没找到想要的信息，用户很可能就会关闭页面、修改查询词，或者直接放弃。

因此，对于一个 RAG 系统，如果它的下游生成模型只接收检索结果的前 3 或前 5 个文档作为上下文，那么正确的文档无论排在第 8 位还是第 100 位，对这个生成模型来说都是“不可见的”，效果等同于没有被检索到。MRR 精确地捕捉了这种“可见性”需求。它惩罚那些将正确答案“藏”在后面的系统，并奖励那些能将正确答案直接“举”到用户眼前的系统。一个高 MRR 的系统，意味着用户和下游生成模型都能在最高优先级的位置获得他们需要的关键信息。

MRR 与命中率的关系

命中率回答的是“相关文档在不在结果列表里”，而 MRR 回答的是“如果在，它排得有多靠前”。一个有高命中率但低 MRR 的系统，就像一个把关键文件随便塞在资料堆某个角落的助手——文件确实在这里，但你就是找不到。因此，优化 RAG 系统时，在命中率达到基本满意水平后，下一个核心优化目标通常就是提升 MRR，这通常需要引入重排序模型。

#### 比较 Hit Rate 与 MRR：它们分别强调检索的什么方面？何时更应关注 MRR？

关注维度的根本差异

- 命中率强调检索的完整性。它回答的问题是：“所有正确答案中，有多少个被我的检索系统成功覆盖了？” 它只关心“有没有”。

- MRR强调检索的精准性与便利性。它回答的问题是：“第一个能用的正确答案，排在结果列表的多靠前位置？” 它关心的是“好不好找”。

一个直观的类比：把你的检索系统想象成一个私人图书管理员。你问他一个问题，命中率很高意味着他确实把你需要的书都从书库里搬出来了，但可能随意地堆在了你面前的地板上。MRR 很高则意味着他不仅找对了书，而且每次都把最重要的那本直接放在了你的右手边，你一伸手就能拿到。两者都重要，但服务的体验层次不同。

何时更应关注 MRR

在以下三种典型场景中，MRR 的重要性会超过命中率：

1. 上下文窗口极其有限：如果你的 RAG 管道设计为只将检索结果的 Top-1 或 Top-3 文档送给大模型生成答案，那么 MRR@1 或 MRR@3 就是决定性指标。因为排在第 4 位及以后的相关文档，对生成答案没有任何贡献。此时，光有命中率毫无意义，必须追求 MRR。

2. 用户对首屏信息的依赖极强：在设计面向终端用户的 FAQ 机器人或智能搜索时，系统可能直接展示检索结果的标题和摘要给用户，而不是让大模型进行二次总结。在这种情况下，MRR 直接决定了用户能否在第一眼就看到想要的答案，是影响用户满意度的关键 UX 指标。

3. 系统已经完成了召回优化：当你的系统命中率已经达到 0.9 以上，再往上提升遇到瓶颈或边际成本极高时，优化重心就应该果断转向 MRR。通过引入重排序模型等手段，将那些已经召回的正确答案从底部挪到顶部，能带来更显著的业务价值提升。

总结：命中率是基础，MRR 是上层建筑。在项目初期，先确保命中率达到一定水位；在项目优化期，集中精力提升 MRR。

#### 除了 MRR，还有哪些排序质量的指标？如 nDCG、MAP 的解释及适用场景。

除了 MRR，nDCG 和 MAP 是另外两个评估排序质量的关键指标。它们各自从不同角度、不同颗粒度衡量着检索结果的优劣。

nDCG：考虑多级相关度和排名的综合指标

- 解释：nDCG 是一个更全面、更精细的排序指标。它有两层核心思想：第一，文档的相关度可以是分等级的，而不是简单的“相关/不相关”（例如，完美答案 > 部分相关 > 有点关系 > 不相关）；第二，一个高度相关的文档，应该被排在尽可能靠前的位置，如果排在后面，它的价值应该被“折损”。nDCG 的计算首先根据文档的等级分数和位置计算出一个折损累计增益，然后将其与理想的排序情况（即完美排序下的最大得分）进行比较，得到归一化的分数。分数越接近 1，排序越完美。

- 适用场景：nDCG 特别适用于你的 RAG 系统有精细的文档质量分级的场景。例如，在电商客服 RAG 中，你可以将“包含标准答案的文档”标记为 3 分，“包含相关政策的文档”标记为 2 分，“只包含部分关键词的文档”标记为 1 分。nDCG 能够很好地反映系统是否将 3 分文档排在了最前面。如果你的评估数据只标记了“相关/不相关”，使用 nDCG 的优势就无法充分发挥，此时 MRR 或 MAP 可能更直观。

MAP：平均精度均值，衡量所有相关文档的排序

- 解释：MAP 也是一个对排序位置敏感的指标，但它和 MRR 不同。MRR 只关心“第一个”相关文档的位置，而 MAP 关心“所有”相关文档的位置。它首先为每个查询计算一个平均精度（AP），计算方法为：从排序列表的顶部向下遍历，每碰到一个相关文档，就计算并记录下当前位置的精度（例如，到当前位置为止，相关文档的比例），最后将所有相关文档位置的精度值取平均。MAP 就是所有查询 AP 的平均值。

- 适用场景：MAP 特别适用于需要对多个相关文档进行综合评估的场景。例如，用户的问题是“列出导致项目失败的主要原因”，答案需要综合 3 篇文档里的信息。此时，我们希望不仅第一篇相关文档排在前面，其他两篇相关文档的排名也尽可能靠前。MRR 对这种情况不敏感（因为它只看到了第一个文档），而 MAP 会奖励那些将所有相关文档都排在靠前位置的系统。

简单对比总结：如果你只关心第一个正确答案在哪里，用 MRR；如果你关心所有正确答案排得怎么样，并且它们有优劣之分，用 nDCG；如果你关心所有正确答案排得怎么样，但不区分它们的优劣，用 MAP。

#### 如何衡量答案相关性？它是否等同于忠实度？

答案相关性的定义

答案相关性衡量的是生成的答案在多大程度上切题、合适、并且回答了用户提出的问题。一个相关性的答案，首先必须能回应用户的核心意图。例如，用户问“如何重置密码？”，生成的答案却是关于“密码安全策略”的长篇介绍，即使这段文字 100% 忠实于检索到的文档，它也是不相关的，因为它没有帮用户解决实际问题。相关性关注的是“答案是否满足了用户的提问需求”。

与忠实度的区别

答案相关性和忠实度是两个正交的、完全不同的维度。忠实度衡量的是“答案是否基于给定的上下文”，它把上下文当作唯一真理，检查答案中有没有编造的内容。相关性衡量的是“答案是否回应了查询”，它把用户意图当作评判标准。这四种情况都有可能发生：

1. 高忠实度 + 高相关性：这是最理想的情况。答案基于文档，并且完美回答了问题。

2. 高忠实度 + 低相关性：答案的内容在文档中都能找到，但文档本身就跑题了（检索失败），导致生成的答案虽然不胡说，但答非所问。这是典型的检索质量问题。

3. 低忠实度 + 高相关性：答案很精准地解决了用户问题，但内容完全是模型自己编的。这是最危险的幻觉，看似完美，实则是谎言。

4. 低忠实度 + 低相关性：答案是乱七八糟的瞎编，与问题和文档都没关系。这是最差的失败情况。

如何评估答案相关性

评估答案相关性通常需要依赖强大的语言模型作为评判者，因为“是否切题”是一种复杂的语义判断，很难用简单的 n-gram 匹配来评估。常用的方法是：

- LLM 作为评判者：将用户的问题和生成的答案一起送入 GPT-4，要求它从多个维度（如：是否直接回答了问题？是否遗漏了关键点？是否包含了无关信息？）给出 1-5 分的相关性评分。通过精心设计的提示词和少量示例，可以获得相当可靠的相关性评估。

- 基于问答的评估：将生成的答案作为上下文，重新构造一个问题（如“这个回答是在解决什么用户问题？”），然后判断这个重构出的问题与原始用户问题在语义上是否一致。

因此，答案相关性和忠实度共同构成了生成质量的一体两面。一个可靠的 RAG 系统，必须在这两个维度上都达到高标准。

#### 上下文相关性怎么评估？有哪些自动评估信号？

上下文相关性的定义

上下文相关性衡量的是检索系统返回给大模型的文档块，在多大程度上与用户查询相关，并且不包含冗余的噪音。它的评估对象是检索管道，而不是最终生成的答案。一个上下文相关性高的检索器，能够精确地只将那些对回答问题有帮助的文档放入上下文窗口，而不会塞进一堆无关、过时或者重复的“垃圾信息”。

为什么需要单独评估上下文相关性

即使最终的答案忠实于上下文，但如果上下文本身充满了噪音，大模型就需要在垃圾堆里找金子，这会极大地降低答案的质量、增加推理成本，甚至可能被错误信息误导。单独评估上下文相关性，可以帮助我们将检索环节的问题（上下文不干净）和生成环节的问题（模型不理解上下文）分离开来，实现精准的故障定位。

自动评估信号与方法

评估上下文相关性主要依赖以下几种自动信号：

1. 信号一：上下文排除率。这是一个强有力的“减法”信号。具体做法是，将检索到的上下文中的每个句子，依次移除，然后观察移除后对生成答案忠实度的影响。如果移除某个句子后，答案的忠实度或正确率没有下降，说明该句子对回答问题是无关的。无关句子被识别出的比例越高，说明上下文相关性越差。

2. 信号二：LLM 作为相关性评判者。直接将用户查询和检索到的每一篇文档块送入 GPT-4，要求它对文档块进行 1-3 级的相关性打分（如“直接相关”、“部分相关”、“不相关”）。然后统计相关文档的比例，以及不相关文档的数量。这种方法直接、准确，是最常用的自动评估手段。

3. 信号三：基于嵌入的相似度分布。将用户查询和所有检索到的文档块分别进行向量嵌入，然后计算它们之间的余弦相似度。一个高质量的检索结果，其相似度分布应该呈现出一个明显的“高分头部”和“快速下降的长尾”。如果大部分文档的相似度分数都很低且差异不大，说明这次检索可能没有找到真正相关的内容，上下文相关性很差。

4. 信号四：信号-噪声比。将文档块中与查询直接相关的实体、短语、数字的占比，与无关内容的占比进行比较。可以通过规则匹配或 NLI 模型来识别相关片段。

通过这些自动信号，可以在不依赖人工标注的情况下，对线上每次检索的上下文质量进行大规模、持续的监控和评估。一旦发现上下文排除率突然升高，或 LLM 评判的无关文档比例增加，就可以快速触发告警。

#### 在 RAG 评估中，如何获得参考答案？人工标注 vs LLM 标注的利弊。

获得高质量的参考答案是整个 RAG 评估体系的基石。参考答案的可靠性，直接决定了所有自动化指标（如忠实度、答案正确率）的可信度。目前，获取参考答案主要有两条路径：人工标注和使用 LLM 自动标注。两者各有利弊，在实际生产中通常是组合使用。

人工标注：高成本的金标准

- 优势：质量上限最高。对于需要专业领域知识（如医疗、法律）、复杂推理或细微语言判断的任务，经过严格培训的人类专家所标注的答案是最终的金标准。他们的判断具有权威性和可解释性，能够捕捉到模型无法理解的业务逻辑和伦理边界。

- 劣势：成本极高、速度慢、难以大规模扩展。不同标注员之间存在主观差异，需要设计复杂的标注规范和一致性校验流程。对于快速迭代的模型开发来说，人工标注的周期往往跟不上模型更新的步伐。

- 适用场景：系统最终上线前的质量终审、高风险领域的核心评测集构建、对 LLM 标注结果的争议仲裁。

LLM 标注：高效率的主力军

- 优势：速度快、成本低、可无限扩展、一致性高。可以一次性生成大量参考答案，迅速构建一个覆盖广泛、数量可观的评估数据集。对于事实型、定义明确的任务，GPT-4 等强大模型的标注质量已经非常接近甚至在某些方面超过普通人工标注员。它是支撑 RAG 系统快速迭代实验的基础。

- 劣势：存在模型偏见和幻觉风险。LLM 生成的“参考答案”可能本身就是错误的，或者带有其训练数据中的偏见。用它生成的答案来评估它自己或另一个模型时，可能会形成“裁判和运动员是一伙”的回音壁效应，掩盖真实的问题。对于需要深层专业知识或复杂价值判断的案例，其可靠性仍存疑。

- 适用场景：开发迭代阶段的日常自动评测、大规模测试集的初始构建。

最佳实践：多层次、交叉验证的标注体系

一个成熟的 RAG 评估团队，通常会采用以下策略：

1. 用 LLM 生成初版答案：快速构建一个覆盖面广的评估集。

2. 人工抽检与校准：对 LLM 生成的答案进行随机抽检，由领域专家审核其质量，修正错误。同时，用高质量的专家标注来微调一个专门用于评估的 LLM 评判者，提升其打标的准确性。

3. 建立黄金评测集：将少量经过专家反复校验、确定无误的高价值问答对，作为“黄金评测集”。这套评测集的参考答案完全由人工确保质量，用于对系统进行最终、最权威的评估。

4. 对抗性动态更新：定期将线上用户反馈为“差”的、以及模型回答出错的案例，经人工分析后补充进评测集，让评测基准保持时效性和挑战性。

#### 什么是 RAGAS？它提供了哪些 RAG 评估指标，各自的计算逻辑。

RAGAS（Retrieval Augmented Generation Assessment）是一个专门为 RAG 系统设计的、开源的自动化评估框架。它的核心目标是用尽量少的、或者完全不需要人工标注的数据，来全方位量化 RAG 管道的质量。RAGAS 的理念是“分层评估”，它将 RAG 系统拆解为检索和生成两个核心环节，并针对每个环节定义了专门的、可自动计算的指标。

RAGAS 提供的主要指标及其计算逻辑如下。

一、检索环节的指标

1. 上下文召回率（Context Recall）
  - 衡量什么：检索到的上下文文档中，是否包含了回答用户问题所需的全部关键信息。
  - 计算逻辑：RAGAS 首先会利用 LLM 从参考答案（或从检索到的上下文中）中提取出回答该问题所需的一组关键句子或信息点。然后，逐一检查这些信息点是否能在检索到的上下文中找到对应的证据。最终得分 =（能够被上下文支撑的信息点数量）/（信息点总数）。这个指标关注检索的“完整性”。

2. 上下文精确率（Context Precision）
  - 衡量什么：检索到的上下文文档中，有多少是真正相关的，而不包含大量无关噪音。
  - 计算逻辑：RAGAS 会要求 LLM 对检索结果中的每一个文档块进行相关性判断（相关/不相关）。然后，计算相关文档的比例，并且该指标对排名靠前的相关文档给予更高权重。具体来说，它会计算一个加权精确率，排名越靠前的相关文档，其精确率得分越高。这个指标关注检索的“信噪比”。

二、生成环节的指标

3. 忠实度（Faithfulness）
  - 衡量什么：生成的答案是否完全基于检索到的上下文，有没有凭空编造事实。
  - 计算逻辑：这是 RAGAS 最核心的指标之一。它首先将生成的答案分解为一组独立的、简短的“陈述句”。然后，对每个陈述句，利用 LLM 判断它是否可以从提供的上下文中直接推导出来。最终得分 =（被上下文蕴含的陈述句数量）/（陈述句总数）。得分越高，幻觉越少。

4. 答案相关性（Answer Relevancy）
  - 衡量什么：生成的答案是否切实回应了用户的问题，有没有答非所问。
  - 计算逻辑：RAGAS 会反向操作——让 LLM 根据生成的答案，反推出一些“这个答案可能是为了回答什么问题而生成的”。然后，计算这些反推出来的问题与用户原始问题之间的语义相似度。最终得分是所有反推问题与原始问题相似度的平均值。如果答案跑题了，反推出来的问题就会和原始问题差异很大，得分就会很低。

5. 上下文利用率（Context Utilization）
  - 衡量什么：检索到的上下文在生成答案时，是否被充分且有效地利用了。
  - 计算逻辑：将上下文中的每个句子逐一移除，观察移除该句子后，生成的答案在忠实度上是否发生变化。如果移除某句后忠实度明显下降，说明该句是生成答案所需的关键信息。最终得分 =（被判定为“必要”的句子数量）/（上下文总句子数）。这个指标用来检测检索结果是否过于冗余，或者模型是否没有充分利用关键信息。

RAGAS 的这些指标共同构成了一个完整的评估矩阵，开发者可以通过几行代码，快速诊断出 RAG 系统的短板是在检索端还是在生成端。

#### 如何使用 LLM 作为评判器来评估 RAG 输出的忠实度和相关性？提示词怎么写？

使用大语言模型作为评判器，是当前自动化评估 RAG 输出质量最主流、最灵活的方法。它的核心思想是：给一个强大的 LLM（如 GPT-4）提供详细的评估标准和待评估的文本，让它模拟人类专家的思维过程，输出一个结构化的质量分数和判断理由。

一、评估忠实度的提示词设计

评估忠实度的目标是判断生成的答案是否严格基于给定的上下文，而不是模型自己的知识。提示词的设计必须让 LLM 扮演一个“严苛的事实核查员”。

一个高质量的忠实度评估提示词应包含以下要素：

- 角色设定：明确 LLM 的身份，如“你是一个严谨的事实核查专家”。

- 任务描述：清晰地说明任务，如“请逐句检查‘生成的答案’中的每一个事实陈述，判断它是否可以从‘给定的上下文’中直接推导或验证。”

- 判定标准：给出明确的分类指导。例如：
  - “Yes”：答案陈述完全可以从上下文得出。
  - “No”：答案陈述与上下文矛盾，或上下文完全没有提及。
  - “Partly”：答案陈述部分得到上下文支持，但添加了额外的推测或信息。

- 输入格式：将上下文和答案用清晰的标记分隔，如 `[上下文]...[/上下文]` 和 `[答案]...[/答案]`。

- 输出格式：要求 LLM 以结构化的方式输出，最好是 JSON 格式，包含每个句子的判定结果（Yes/No/Partly）、理由、以及最终的整体忠实度分数（如 0-100%）。

示例提示词片段：

```plain text
[系统]
你是一个严格的事实核查员。请根据[上下文]中提供的信息，核查[答案]中的陈述是否属实。

[判定规则]
- 如果陈述的内容可以在[上下文]中找到明确依据，判定为 "Yes"。
- 如果陈述的内容与[上下文]矛盾，或[上下文]完全没有提及，判定为 "No"。

[输出格式]
请以JSON格式输出，包含以下字段：
- "verdicts": 一个列表，每个元素包含 "statement" (陈述句), "verdict" ("Yes"或"No"), "reason" (理由)。
- "faithfulness_score": 判定为 "Yes" 的陈述数量除以总陈述数量。

[上下文]
{retrieved_documents}

[答案]
{generated_answer}
```

二、评估答案相关性的提示词设计

评估答案相关性的目标是判断生成的答案是否切实回应了用户的问题。提示词需要 LLM 扮演一个“严格的用户”，判断答案是否满足了自己的信息需求。

提示词的关键要素：

- 角色设定：如“你是一个正在使用AI助手获取信息的用户。”

- 任务描述：如“请评估‘生成的答案’在多大程度上直接、准确、完整地回答了‘用户的问题’。”

- 评估维度：引导 LLM 从多个维度打分，如：
  - 直接性：答案是否直面问题，而不是绕弯子？
  - 完整性：答案是否涵盖了问题的所有核心方面？
  - 无冗余：答案中是否包含了与问题无关的信息？

- 评分标准：给出一个 1-5 分的评分量表，并详细描述每个分数的含义。

- 输出格式：要求给出分数和详细的评分理由。

关键提示词工程技巧：

1. 要求思维链：在给出最终判定前，先让 LLM 写出它的分析推理过程。这能极大提高最终判定的准确性。

2. 提供少量示例：在提示词中提供一到两个高质量的示例（带有正确标签和理由），能帮助 LLM 更好地理解任务标准。

3. 降低温度：将温度参数设在 0.2 以下，使 LLM 的输出更确定、更稳定。

4. 多模型交叉验证：对于高风险评估，使用不同家族的强大模型分别打分，取平均值或投票结果。

#### 在缺乏真实标注的情况下，能否用对比方法评估 RAG 系统的质量？

完全可以。在缺乏人工标注的“参考答案”时，评估 RAG 系统质量的核心范式从“与标准答案对比”转变为“不同系统版本之间的横向对比”。这种方法虽然无法给出“系统达到了85分”这样的绝对指标，但可以非常可靠地告诉你“系统A是否显著优于系统B”，这对于模型选型、策略迭代等工程决策来说，价值极高。

几种常用的对比评估方法：

1. AB 测试与成对比较：\
   对于同一个用户问题，同时运行两个版本的 RAG 系统（例如，版本A使用HyDE检索，版本B使用基础检索），得到两个答案。然后，将它们交给 LLM 评判者或人类评估员进行“盲测”。评判者不知道哪个答案来自哪个系统，只被要求回答：“综合考虑准确性、相关性和流畅度，哪个答案更好？还是平手？”通过积累大量这样的成对比较结果，可以计算出系统的胜率。这是最直接、最公平的对比评估方式。

2. 基于参考文档的自动评估：\
   即使没有问答对的标注，但你通常有构建 RAG 系统的知识库文档。此时，你可以利用 LLM 从这些文档中自动生成一批“合成问题”。因为问题是根据特定文档生成的，所以你知道这篇文档就是它的“标准答案上下文”。用这批合成问题去测试你的 RAG 系统，虽然无法评估真实性（因为文档本身就是答案），但可以非常有效地评估检索的命中率和生成答案的忠实度（因为你知道答案应该基于哪篇文档）。

3. 消融实验与指标趋势分析：\
   这不是直接对比答案优劣，而是对比不同系统在无标注自动指标上的趋势。例如，系统A和系统B在相同测试集上进行评估，虽然你没有忠实度的真实值，但你可以观察到，系统A在 RAGAS 的忠实度得分上，是否一致地、显著地高于系统B。如果这种趋势在大量测试样本上稳定出现，那么可以推断系统A在抗幻觉能力上有所提升。

4. 对抗性测试与边界案例挖掘：\
   主动构造一些“陷阱”问题。例如，问一个在你知识库中明确不存在、或者存在矛盾信息的问题。然后对比不同系统在这些对抗性查询上的表现：系统A是否会编造答案，还是诚实地回答“不知道”？系统B在处理矛盾信息时，是否会同时报告两种说法？这些边界表现是衡量系统鲁棒性的黄金标准。

结论：缺乏标注不意味着无法评估。通过“成对比较”、“合成数据构建”、“指标趋势分析”和“对抗性测试”的组合拳，可以构建一个强大的、无需人工标注的相对评估体系，足以驱动系统的持续迭代。

#### 如何评估检索的召回率（Recall@k）？在开放域 RAG 中，为什么 Recall@k 往往比 Precision 更重要？

一、如何评估 Recall@K

Recall@K 衡量的是“在所有真正相关的文档中，检索系统成功找回了多少个，并且这些被找回的文档排在了前 K 位”。评估步骤通常如下：

1. 构建查询集与标注：准备一组用户查询，并为每个查询人工标注或通过高权威来源确定其“相关文档集合”。这个标注集是评估的基础。

2. 执行检索：用每个查询去检索系统，得到返回的 Top-K 文档列表。

3. 计算单次查询的 Recall@K：对于单个查询，`Recall@K = |Top-K 结果中属于相关文档集合的文档数量| / |该查询的全部相关文档集合大小|`。

4. 计算总体 Recall@K：对所有查询的 Recall@K 值取平均。

这个过程衡量的是系统“捞回”正确信息的能力。

二、为什么在开放域 RAG 中 Recall@K 往往比 Precision 更重要

在开放域 RAG 场景中，召回率通常被赋予比精确率更高的优先级。这是由 RAG 的系统架构和任务目标共同决定的。

1. RAG 的“生成器”具有强大的噪声过滤能力：在 RAG 管道中，检索只是第一步，它的输出是给下游 LLM 阅读的。LLM 具有极强的语义理解能力，它能够像一位经验丰富的编辑，从一堆混杂着相关和无关片段的材料中，识别出真正有价值的信息。因此，将一些无关文档送入 LLM 的成本，通常远低于因漏掉关键文档而导致 LLM 无法回答问题的代价。宁可多给一些材料，也不能让关键信息丢失。

2. 上下文窗口的巨大容量：现代大语言模型的上下文窗口已经达到百万 Token 级别。这允许 RAG 系统在检索时，适当扩大召回范围，容纳一些不太精准但可能包含有用信息的文档。系统可以容忍一定程度的精确率下降，因为有足够的窗口去消化和处理这些信息。

3. “相关信息”的定义在生成时可能会变化：一个文档在检索阶段可能因为与查询词不完全匹配而被判定为“不相关”（即精确率受损），但在后续的生成过程中，它可能包含对丰富答案至关重要的背景信息。因此，过早地、过于严格地追求精确率，可能会扼杀掉这些潜在的、有价值的上下文。

4. 用户体验的容错边界：用户面对一个因为信息缺失而显得单薄、错误的答案（低召回导致），其负面体验远大于面对一个内容详尽但稍有冗余的答案（低精确导致）。前者是“无能”，后者顶多是“啰嗦”。

因此，在 RAG 系统的优化顺序中，通常第一步是穷尽手段将 Recall@K 做到极致（通过优化分块、嵌入、混合检索等），然后在此基础上，再引入重排序模块去提升精确率。先确保“拿到”，再优化“拿得精”。

#### 端到端评估时，如何区分是检索模块的问题还是生成模块的问题？

当一个 RAG 系统输出了一个糟糕的答案时，我们面临的核心诊断问题是：到底是检索阶段没有提供好的素材（检索失败），还是生成阶段没有用好素材（生成失败）？这需要一套系统化的故障定位流程。

区分方法：逐层排除与对比实验

1. 使用“黄金上下文”进行消融实验：\
   这是最根本、最权威的定位方法。对于一批测试问题，由人工标注出“如果模型看到这些文档，就一定能正确回答”的黄金上下文。然后，用这些黄金上下文替换掉检索模块的输出，直接喂给生成模型。如果此时生成的答案质量依然很差（如出现幻觉或答非所问），那问题一定出在生成模块本身。反之，如果换上黄金上下文后答案变得完美，那么就确凿无疑地证明是检索模块出了问题，它没能找回这些关键文档。

2. 分层指标追踪：\
   在系统上线后，每个查询的日志中都应记录下分层指标。
  - 查看检索指标：首先检查这次查询的命中率、MRR 等。如果这些指标很低，几乎可以肯定问题出在检索。例如，正确答案的文档根本没有出现在 Top-K 结果里。
  - 查看生成指标：如果检索指标看起来正常，相关文档已经被召回，那么就应聚焦于生成指标。例如，使用 RAGAS 计算生成的忠实度分数。如果忠实度很低，说明模型在生成时出现了幻觉，没有忠实于已给到的上下文，这显然是生成模块的问题。

3. 引入“上下文相关性”作为中间裁判：\
   这个指标专门评估检索到的文档与查询的相关性。如果答案失败，而上下文相关性得分很高，说明检索给的是对的，但模型理解或生成出了错。如果上下文相关性得分很低，说明检索本身就是失败的。

4. 分析模型的“引用”行为：\
   如果你的 RAG 系统要求模型在生成答案时提供引用（例如，引用来源文档的编号），那么可以通过分析这些引用来快速诊断。如果模型的引用是准确的，但答案依然错误，可能是推理错误。如果模型完全不引用，或者引用的是不相关的文档，则可能是检索文档质量差，或者模型选择了错误的文档作为依据。

诊断流程总结：

输出质量差 → 检查上下文相关性 → 相关性低则检索失败 → 相关性高则检查忠实度 → 忠实度低则生成失败 → 忠实度高但答案错则推理失败。

通过这套流程，可以像经验丰富的医生一样，对 RAG 系统的“病症”进行精准分诊，从而有针对性地去优化检索管道、调整分块策略、或微调生成模型。

#### 人工评估 RAG 系统时，应遵循怎样的准则来保证一致性？

人工评估是 RAG 质量评估的金标准，但也最容易受到评估者主观差异、疲劳和理解偏差的影响。为了保证评估结果的可靠性和一致性，需要建立一套严格的评估准则和执行流程。

核心准则与流程：

1. 制定极其详尽的评分规范（Rubric）：\
   不能只给出“好、中、差”这样的模糊标准。评分规范必须将每个评估维度（如忠实度、相关性、流畅度）进行分数量化，并为每一个分数层级提供具体的、反例式的定义。
  - 示例：对于忠实度，1-5 分的标准可能是：
    - 5分：答案中的所有事实陈述都能在上下文中找到精确的原文支持。
    - 3分：答案的核心事实正确，但包含了一些无法从上下文验证的推测性描述。
    - 1分：答案的核心事实与上下文直接矛盾，或大部分内容完全虚构。\
      规范中应包含大量的正面和反面示例，让评估员明确知道每一种情况的边界。

2. 实施双重盲评与仲裁机制：\
   每一条评估样本都应被随机分配给至少两位互不知晓对方身份的评估员。如果两位评估员给出的分数差异小于 1 分，通常取平均值；如果差异超过 1 分，说明该样本可能存在歧义或难以判断，应由更资深的第三位评估员进行最终仲裁。这种机制能有效消除个人偏见。

3. 进行一致性校准培训与测验：\
   在正式评估开始前，必须组织所有评估员参加校准会议。在会上，他们需要共同为一批样例打分，并公开讨论各自的打分理由，直到团队对评分标准达成共识。之后，通过一个“校准测验”，只有测验通过（即其评分与专家组标准一致）的评估员，才能正式上岗。

4. 采用“成对比较”替代部分绝对打分：\
   当需要比较两个系统版本（如系统A vs. 系统B）的优劣时，让评估员直接给出“A更好、B更好、平手”的比较判断，往往比让他们对每个系统独立给出一个1-5的绝对分数更容易、更一致。因为相对判断比绝对尺度更符合人类的直觉。

5. 任务分解与轮转：\
   将评估任务进行分解。例如，一个人专门评估忠实度，另一个人专门评估答案相关性，而不是让同一个人同时评估所有维度。这有助于评估员保持专注，减少认知负荷。同时，定期轮换评估员评估的测试批次，避免某个评估员长期评估特定类型的查询而产生系统性偏差。

6. 设置质量控制与休息机制：\
   在评估任务中随机插入一些“黄金标准题”（已知正确答案的题目），监测评估员的判断是否与标准一致。如果出现显著偏差，立即让该评估员休息或进行重新校准。强制设置休息时间，避免疲劳效应导致评估质量下降。

人工评估不是简单的“找人看一遍”，而是一个需要精心设计、严格控制的科学实验过程。只有这样，才能从昂贵的人工成本中，萃取出真正有价值的、可重复的评估数据。

#### 分析 RAG 评估中常见陷阱：如检索到但未使用的上下文是否应算命中？

在 RAG 评估中，最经典的陷阱之一就是对“命中”的定义模糊不清。一个常见的困惑是：如果一个正确答案所在的文档被检索系统“成功召回”了（即它出现在了 Top-K 列表中），但由于它排在第 50 位，而你的生成器只取前 5 篇文档来阅读，导致这个文档实际上没有被模型“看到”和“使用”。那么，它应不应该被算作一次成功的检索命中？

这个问题的答案取决于你评估的目的和层级。

- 如果你评估的是检索模块本身：那么应该算作命中。因为检索模块的工作就是“从海量数据中找出可能相关的文档”，它已经成功完成了这个任务。此时计算出来的指标，是检索模块的理论最大能力。在单独优化检索算法（如嵌入模型、ANN 索引参数）时，就应该使用这种定义下的指标。

- 如果你评估的是端到端 RAG 系统的效果：那么不应该算作命中。因为对于下游的生成模块来说，这个文档是不可见的。最终生成的答案并没有从这个被深埋的文档中获益。如果在端到端评估中将其计为命中，会造成“检索性能虚高”的假象，掩盖了“检索结果未被有效利用”的真实问题。

另一个相关陷阱：生成模型的“选择性无视”

还有另一种更隐蔽的情况：正确答案就在模型看到的前几篇文档里，但模型在生成时不知为何，选择了无视它，或者基于另一篇不相关的文档编造了答案。从评估角度看，检索和上下文都是好的，但答案错了。此时，如果不做精细分析，很容易误判为是生成模型的推理失败。但深入分析可能会发现，是上下文中的信息过于碎片化或相互矛盾，导致模型无法正确提取关键信息。这说明，我们对“上下文质量”的评估，除了看“命中”，还需要看“信噪比”和“信息组织的清晰度”。

如何避免这些陷阱：

1. 分层评估，明确定义：在报告指标时，必须明确你评估的是哪个阶段。检索阶段用“理论命中率”，端到端阶段用“有效命中率（即被模型实际参考的文档命中率）”。

2. 引入“上下文利用率”指标：通过分析生成的答案具体引用了哪部分上下文，来计算上下文利用率，从而揭示模型是否真正“吸收”了关键信息。

3. 分析引用日志：如果你使用了支持引用的生成模型，分析其引用日志是发现“选择性无视”问题的最直接方法。

#### 如何评估 RAG 系统的时延、吞吐和成本？定义性能相关的 KPI。

评估 RAG 系统的性能，不仅要看它回答得准不准，还要看它回答得快不快、贵不贵。这是决定系统能否从 demo 走向大规模生产的关键。性能评估主要围绕三个核心 KPI 展开：时延、吞吐和成本。

1. 时延（Latency）

- 定义：衡量系统处理单个请求的快慢。通常关注两个关键时延：
  - 首Token时间（TTFT）：从用户发送请求到收到第一个生成 Token 的时间间隔。这个指标直接影响用户体感的“响应速度”，是交互流畅性的关键。
  - 生成总时间：从请求发起到完整答案生成完毕的总耗时。对于长文本生成任务，这个指标也很重要。

- 评估方法：在模拟生产环境的负载下，使用压测工具（如 Locust）发送请求，记录并统计上述时延的均值（Avg）、中位数（P50）、P95 和 P99。P95/P99 的时延能反映系统的长尾问题，对保障用户体验至关重要。

2. 吞吐（Throughput）

- 定义：衡量系统在单位时间内能处理多少请求。常用指标包括：
  - 每秒查询数（QPS）：系统每秒钟能成功处理并完成的查询请求数量。
  - 每秒生成Token数（TPS）：系统每秒钟能生成的有效输出 Token 总量。在按 Token 计费的商业模型中，这个指标比 QPS 更能反映系统的产出效率。

- 评估方法：逐步增加并发请求数，测量系统在不同负载下的 QPS/TPS，同时监测其时延变化。最终需要找到系统的吞吐拐点，即随着负载增加，时延开始急剧恶化的那个点，并将其作为系统的最大服务容量。

3. 成本（Cost）

- 定义：处理单个或单位数量请求所消耗的资源。这需要根据部署方式定义不同的成本 KPI：
  - API 成本：如果使用付费 API（如 GPT-4），成本直接体现为每百万输入/输出 Token 的价格。KPI 是每次查询平均成本。
  - 硬件成本：如果私有化部署，成本体现在 GPU 等硬件的折旧、电费和运维上。KPI 可以是每百万生成 Token 的GPU小时消耗。

- 评估方法：在吞吐测试的基础上，记录每次请求消耗的 Token 数量，并结合 API 单价或硬件时租来计算成本。

性能评估的协同优化

这些性能指标不是孤立的，它们之间存在着内在的关联。例如，为了提高生成质量，可能会增加上下文长度（成本上升、时延增加）或增加检索路数（时延增加）。一个成熟的 RAG 系统运维，需要建立一套性能监控仪表盘，持续追踪这些 KPI，并能够在“质量、速度、成本”的不可能三角中找到业务的最优平衡点。例如，对于 VIP 用户，可以牺牲一点成本换取最低的时延和最复杂的检索管道；对于免费用户，则使用轻量级的方案。

#### 多轮对话 RAG 的评估有何特殊性？需要额外考虑哪些指标？

多轮对话 RAG 的评估，远比单轮问答复杂。因为此时系统的行为不再是一个孤立的“问-答”对，而是一系列在时间上连续、逻辑上递进的交互。评估不仅要看每一轮的答案质量，更要看系统对整个对话历史、上下文指代和意图演变的处理能力。

多轮对话评估的特殊性

1. 历史依赖与指代消解：用户的问题常常是省略的、指代不明的，必须结合历史才能理解。评估必须覆盖系统是否能正确解决这些指代。例如，用户先问“张三多大了？”，接着问“那他住哪？”。评估不能只看第二轮答案是否正确，还要看系统是否将“他”准确消解为了“张三”。

2. 状态维护与记忆一致性：在多轮交互中，模型必须在隐性状态中记住对话过程中被确认的事实、用户的偏好、以及已完成的任务。评估需要检查模型是否会出现“失忆”或前后矛盾。例如，前面已经确认了用户的航班日期，后面推荐酒店时却又问了日期。

3. 对话连贯性与自然度：评估生成的回复是否顺畅地衔接了对话历史，像一个真人在交谈，而不是一堆孤立的、虽然正确但听起来很生硬的答案片段。这包括了对语气、情感和对话节奏的把握。

需要额外考虑的评估指标

1. 指代消解准确率：专门构造一个包含大量指代和省略的测试集，精确评估系统将口语化短查询解析为独立、完整检索查询的能力。

2. 对话状态追踪准确率：评估系统是否能在每一轮对话中，正确更新并维护一个包含关键槽位（如目的地、时间、预算）的“状态表”。可以将系统生成的状态表与人工标注的理想状态表进行对比。

3. 信息冲突处理能力：设计用户在后续对话中否定或修改之前提供的信息的场景。评估系统是否能正确处理这种“冲突更新”，并基于最新信息重新给出建议。

4. 主动引导与澄清能力：当用户意图不明时，系统是否能主动发起澄清式提问？当对话陷入僵局时，系统是否能提供有用的引导选项？这属于更高级的对话能力评估。

评估方法：

多轮对话的评估更依赖LLM 作为评判者。可以编写复杂的提示词，将整个对话历史一次性提供给评判 LLM，要求它从上述多个维度对最后一轮的回复进行综合打分。同时，也需要构建专门的对抗性测试集，模拟各种复杂的对话流转场景。单轮评估的那些忠实度、相关性指标依然适用，但必须将它们放在“结合对话历史”的前提下去评判。

#### 在领域特定的 RAG 系统中，如何构建评估基准？需要哪些领域专家参与？

构建一个高质量的领域特定 RAG 评估基准，是决定该系统能否在严肃商业场景中真正“可用”的前提。通用评估基准无法覆盖领域知识、术语和业务逻辑的独特性，因此必须量身定制。

一、构建评估基准的流程

1. 业务场景梳理与任务定义：由产品经理和业务负责人主导，明确 RAG 系统需要解决的核心业务问题有哪些。例如，一个法律 RAG 可能聚焦于“法条检索”、“案例分析”和“合同条款审查”。将这些任务转化为具体的评估维度。

2. 领域数据集构建：这是工作量最大、也最核心的环节。
  - 真实文档库：使用脱敏后的真实业务文档作为检索库。
  - 查询集构建：由领域专家（如律师、医生、工程师）基于他们的日常工作经验，编写一套高质量的、能反映真实用户需求的查询问题集。这是基准的灵魂。查询集应覆盖常见问题、边界问题和长尾疑难问题。
  - 黄金参考答案与证据标注：对于查询集中的每个问题，由领域专家亲手撰写一份或多份标准答案，并且明确标注出在文档库中，回答该问题所依据的“黄金证据片段”。这一步为后续的自动化评估（如忠实度、命中率）提供了无可争议的评判依据。

3. 评估指标定制：由算法工程师和领域专家共同确定。除了通用的忠实度、相关性外，可能需要定义领域特有指标。例如，医疗 RAG 可能需要评估“诊断建议的合规性”和“药品禁忌症覆盖的完整性”；法律 RAG 可能需要评估“关键法条的召回率”和“法律风险提示的准确性”。

二、需要哪些领域专家参与

- 领域业务专家（核心标注员与标准制定者）：他们是评估基准质量的决定性力量。他们负责撰写领域查询、制定标准答案、标注证据片段，并定义专业的评估维度。他们的判断是评估的“金标准”。

- 领域数据工程师：负责从原始的业务数据库中提取、清洗、脱敏和整理文档，构建出用于评估的高质量知识库。

- 产品经理：在业务需求和模型能力之间架设桥梁，确保评估基准能够衡量模型是否真正解决了业务痛点，而不仅仅是学术指标上的好看。

- 算法工程师（评估基准的用户）：从模型可评估性的角度提供反馈，确保标注的数据和定义的指标能够被自动化评估框架有效地使用。

三、迭代与维护

领域评估基准不是一成不变的。随着业务发展、法规更新和模型能力进化，它需要持续的迭代。

- 定期更新：定期邀请领域专家审查和更新查询集、标准答案和文档库。

- 失败案例注入：将线上收集到的、系统回答错误的真实用户案例，经过专家分析后，不断补充进评估基准中，使其始终保持挑战性和时效性。

- 对抗样本构建：由专家刻意构造一些包含矛盾信息、模糊表述或逻辑陷阱的查询，来测试系统的鲁棒性和边界。

总结：构建一个领域评估基准，本质上是一次深入的产学研结合。它的核心资产不是代码，而是由领域专家精心标注的、承载着宝贵业务知识的高质量评测数据集。这个数据集的水平，直接决定了整个 RAG 系统质量迭代的上限。

#### 忠实度评估中，如何检测“幻觉”（编造不存在于上下文中的信息）？

在忠实度评估中，检测“幻觉”就是识别出答案中那些无法从给定上下文中找到直接依据的陈述。这是对抗生成模型“一本正经地胡说八道”的前沿阵地。目前主流的方法已经从简单的词匹配进化到了复杂的语义验证。

检测方法：

1. 原子事实分解与NLI（自然语言推理）验证：\
   这是最经典、最可靠的方法。
  - 分解：将需要评估的生成答案，分解为一组最小的、独立的“原子事实”或“信息点”。例如，“爱因斯坦于1879年出生于德国乌尔姆市”可以被分解为三个事实：“爱因斯坦是一位物理学家”、“他出生于1879年”、“他出生于德国乌尔姆市”。
  - 验证：将每一个原子事实作为“假设”，将所有检索到的上下文拼接成“前提”。使用一个在蕴含识别任务上微调过的 NLI 模型，判断该原子事实是否被上下文“蕴含”。如果模型预测为“中立”或“矛盾”，则该事实被标记为“幻觉”。
  - 综合评分：最终，答案的忠实度得分 = 被蕴含的原子事实数量 / 原子事实总数。幻觉率 = 1 - 忠实度得分。

2. 基于问答一致性的闭环检测：\
   这是一种更巧妙、不需要显式标注“支持事实”的方法。
  - 问题生成：基于生成的答案，让一个 LLM 自动提出一系列细节性问题。例如，如果答案声称“2024年诺贝尔物理学奖授予了John Hopfield”，那么就生成问题：“2024年诺贝尔物理学奖授予了谁？”
  - 封闭式再回答：将这些生成的问题，连同原始上下文，再次交给同一个 LLM，要求它仅根据上下文来回答这些问题，而不是用自己的知识。
  - 一致性比对：将新生成的答案与原答案进行比对。如果两者在关键事实上不一致（例如，新答案说“上下文并未提及具体获奖者”，或者提到了另一个名字），那么原答案中的该事实陈述就极有可能是“幻觉”。这是一个非常漂亮的零样本检测方法。

3. LLM 作为直接评判者：\
   直接利用 GPT-4 等强大模型的推理能力。提示词设计为：“请逐句检查【答案】中的每个陈述，判断它是否可以在【上下文】中找到明确依据。如果有任何编造、推测或与上下文矛盾之处，请指出并判定为幻觉。” 这种方法最为灵活，可以捕捉到很多 NLI 模型难以处理的隐含逻辑谬误和细微的事实扭曲，但其本身也可能存在偏见。

与检索评估的关联：

幻觉检测也与检索环节紧密相关。如果一个答案的大部分内容都被判定为“上下文不支持”，但你又发现这部分内容实际上是模型正确的参数化知识（即它说的是对的，只是上下文里没有），这说明问题出在检索环节——相关的文档没有被成功召回。因此，对幻觉的深入分析，往往能反向揭示出检索系统的覆盖盲区。
