# 88.大模型（LLMs）表格与多模态文档处理

#### 为什么表格数据对传统 RAG 构成挑战？直接用文本表示表格会丢失哪些信息？

表格是人类表达结构化信息最密集的形式之一。它之所以对传统 RAG 构成巨大挑战，是因为 RAG 的核心——文本嵌入模型和生成模型——都是为处理线性、连续的叙事文本而设计的，而表格的本质是二维的、关系型的、视觉导向的。

直接将表格“拍平”成纯文本，会丢失三个层次的关键信息：

- 空间与结构信息：表格的行列对齐、单元格的视觉分组，是帮助人类快速理解数据归属关系的核心线索。当表格被线性化为一串文本时，“北京”和“100万”之间的行列关联就变成了靠逗号或空格分隔的两个词，模型必须从零推断它们的关系，这增加了认知负担，也容易出错。这种平面结构的丧失，是信息丢失中最根本的一种。

- 层级与语义关系：真实世界的表格远不止简单的二维网格。多层表头会构成“大类-小类”的层次分类体系；合并单元格则承载着“一个值跨越多个子类别”的语义。这些复杂的层级信息在纯文本流中几乎不可能被完好地表达，模型只能看到一个被拉平后的字符串，无法还原其内部的语义层级。

- 数值的物理意义与可比性：表格中大量的数字并非孤立，它们有着特定的单位、量纲和物理意义。它们共同表达着一种对比、趋势或分布关系。例如，一个销售表的核心是“各产品在不同地区的销售额对比”。文本化后，数字和表头分离，模型需要先艰难地重建数字与语义的绑定关系，才能进行推理和比较，这个过程极容易产生幻觉。

因此，简单的文本表示会让表格从“高度结构化的知识库”退化为“一堆有关联但难以解析的文本片段”，使得 RAG 系统的检索和生成两个环节都受到严重损害。

#### 有哪些表格序列化方式（CSV、Markdown 表格、JSON、HTML），哪种对 LLM 最友好？为什么？

常见的表格序列化格式主要有 CSV、Markdown 表格、JSON、HTML 四种。它们对 LLM 的友好程度，取决于其结构开销、语义清晰度以及模型训练数据中的出现频率。

| 格式 | 友好度 | 关键优势 | 主要缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| CSV | 低 | 结构极简，Token 开销最小 | 无法表达多级表头、合并单元格；所有列语义等同，LLM 难以区分表头和数据行 | 仅适合无任何合并的、最简单的单表头表格 |
| JSON | 中 | 能完美表达任意复杂的层级关系和结构 | 结构性 Token（{}[]"）开销巨大，数据内容易被淹没；LLM 有时在处理深层嵌套结构时性能下降 | 需要精确机器读取的结构化数据；或作为 API 输出 |
| HTML | 中 | Web 原生，能表达合并单元格（rowspan/colspan）等复杂结构 | Token 冗余度极高，大量标签占据了宝贵的上下文窗口；LLM 需要“透过”标签来理解数据 | 前端展示；或需要精确复刻复杂表格结构时 |
| Markdown 表格 | 最高 | 在结构开销、可读性和功能之间取得了最佳平衡。能表达基本的列对齐和简单的表头层级；大量出现于 LLM 的训练数据（GitHub README、技术文档） | 无法直接表达复杂的单元格合并和多层表头 | RAG 和 LLM 交互的首选 |

Markdown 表格胜出的根本原因：

- 训练数据的亲和性：LLM 的训练语料（特别是代码和技术文档）中包含了海量的 Markdown 表格，这使得模型对这种格式的理解最为自然和精准。

- 结构直觉化：Markdown 表格使用 `|` 分隔列，用 `---` 分隔表头和数据，这种视觉化的结构接近于人类阅读表格的习惯，模型能轻易地将文本表示与二维布局关联起来。

- Token 效率：相比 HTML 和 JSON，Markdown 表格的 Token 开销极低。在 LLM 的上下文窗口中，这一点至关重要。

最佳实践：对于绝大多数 RAG 场景，应首选 Markdown 表格。如果遇到 Markdown 无法表达的复杂合并单元格，可以在 Markdown 表格内部或旁边，用自然语言显式地补充说明这种合并关系，例如在表头添加注释。

#### 如何从图像或 PDF 中精确提取表格结构（单元格位置、合并单元格、行列关系）？

从非结构化文档中精确提取表格结构，是一个从“看见”到“理解”的过程，需要专门的技术。传统方法依赖视觉线条，而现代方法则转向基于语义的端到端模型。

传统计算机视觉方法：

这种方法分三步：检测表格区域、识别行列线和分析结构。它依赖图像中的水平与垂直线条来定位单元格，适用于线条清晰、格式规整的表格。但局限性极强：对于无线条表格、仅靠色块区分行列的表格，或者线条断裂、弯曲的扫描件，几乎完全失效。

现代深度学习模型方法：

这是目前工业界的主流，直接在图像上预测表格的逻辑结构，不再依赖于物理线条。其代表模型如百度的 SLANet、Google 的 Table Transformer、微软的 TableNet 等。它们能够同时完成两个任务：检测出每个单元格的精确位置；并推断出任意两个单元格之间是否存在“同一行/同一列”的逻辑关系。因此，即使表格没有线条，模型也能根据文本的对齐规律重建其行列结构。对于合并单元格，模型通常会预测单元格的起始行/列和跨行/列的数量，从而完整记录其合并信息。

处理流程：

1. 使用表格检测模型从文档图像中定位出所有表格的边界框。

2. 将每个表格区域裁剪并送入表格结构识别模型。

3. 结构识别模型输出每个单元格的坐标、内容以及它的行列逻辑关系（如 rowspan=2, colspan=3）。

4. 将逻辑结构转换为 Markdown、HTML 或 JSON。

对于 PDF 文件，可以先用 PyMuPDF 获取页面上每个文本片段的精确坐标和字体信息，然后利用这些坐标信息辅助模型判断单元格归属，这比单纯基于图像的识别更为精准。

#### 对于复杂表格（多层表头、跨行跨列），转换为文本后应如何描述以保持语义？

复杂表格的语义在于其层级结构和数据归属关系。转换为文本时，如果强行将其拍平，必然导致信息丢失。更好的策略是进行“语义增强”或“逻辑拆分”。

策略一：转换为结构化 Markdown + 显式注释。\
在 Markdown 表格中，使用空行、缩进或特殊符号来模拟层级。例如，一个有两层表头的表格，可以将第一层表头作为一个合并后的分组标题，用类似 Markdown 注释的方式在表前显式声明合并关系。例如：“`（注：以下表格中，‘2023年’为跨‘Q1-Q4’的表头）`”。然后在表格体内部，通过重复或缩进等方式来保持可读性。这种方式的优点是保留了表格的整体性，LLM 对 Markdown 的理解较好。

策略二：拆分为多个规范子表。

将一个复杂的多层级表格，依据其顶层分类，拆解为多个扁平、独立的三范式表格。每个子表只含单层表头，表名则包含了其完整的层级路径。例如，原表为“销售数据 > 2023年 > Q1/Q2/Q3/Q4”，可以拆分为：

- “销售数据_2023年_Q1”

- “销售数据_2023年_Q2”

- ...\
  每个子表都是简单的行列结构。这种方式最干净，能最大化地利用向量嵌入和检索的效率，但拆解后需要在外部的索引元数据中维持它们之间的关联。

策略三：自然语言描述 + 表格内容。

将表格的复杂结构信息，用一段精炼的自然语言文本显式地描述出来，然后将这段描述作为该表格块的“元数据”或“前导文本”一起嵌入。例如：“该表格是一个两层表头结构，第一层表头为‘2023年’和‘2024年’，分别跨越四列。2023年下又分为Q1-Q4四个季度。” 随后再附上拍平后的数据。这样，即使表格数据本身丢失了层级，前导文本也能为 LLM 提供清晰的解读钥匙。

在实践中，策略一和策略三常常结合使用，能够最大程度地保留复杂表格的语义完整性。

#### 表格表示与 embedding：能否直接对表格生成向量？有哪些专用的表格嵌入模型？

可以直接对表格生成向量，而且效果远超简单的文本拍平。专用的表格嵌入模型通过设计特殊的输入结构和预训练任务，能够编码表格的结构、文本和数值等多维信息。

专用表格嵌入模型：

- TAPAS (Table Parser)：Google 提出的经典模型。它会在输入文本中添加特殊的 Segment Embeddings 来区分表头、数据单元格和位置信息（如行/列 ID），使模型能直接感知表格的二维结构。TAPAS 常用于先检索相关表格，再进行答案抽取，但它本身不直接输出句向量。

- Table-GPT 或 Table-BERT 系列：这类模型通常对表格的每一行或每个单元格生成一个向量，并设计预训练任务（如预测被掩盖的单元格内容、判断一个句子是否属于该表格）来学习表格的联合表示。其输出的行/列向量可以用于下游检索或分类任务。

- 现代多模态模型：如 GPT-4V、CLIP 等，可以直接将表格区域作为图片输入，利用视觉能力理解其结构，实现对表格内容的“视觉嵌入”。这种方法无需线性化表格，最接近人类看图表的模式。

实现方案：在实际 RAG 系统中，如果想直接对表格生成向量，可以：

1. 将表格转换为 Markdown 格式。

2. 在 Markdown 表格前后，显式加入用自然语言表达的“表格描述”和“列名解释”。

3. 使用一个支持长文本的通用嵌入模型（如 `text-embedding-3-large`）对这个增强后的文本块进行编码。这是目前成本最低、效果最好的折中方案。

#### 如何实现针对表格的精准检索：使查询能定位到特定单元格或行列？

实现对表格的精准单元格级检索，需要一种比“把整个表格作为一个向量”更细粒度的索引策略。

策略一：单元格级索引（Cell-level Indexing）。\
将表格的每一个单元格，都单独作为一个独立的文档块进行索引。在嵌入时，不仅包含单元格自身的值，还要融合其完整的语义上下文，包括所属表头、行列号、表名和所在章节等。例如，一个单元格的嵌入文本是：“`表格：2023年销售数据；行名：北京；列名：Q3；值：150万`”。这样，当用户查询“北京 Q3 的销售额”时，查询向量会与这个单元格的语义上下文高度匹配，从而实现精准定位。缺点是索引量会显著膨胀。

策略二：行列摘要索引（Row/Column Summary Indexing）。\
对表格的每一行和每一列分别生成一个摘要向量。例如，为“北京行”生成一个向量，其文本为：“`2023年北京销售数据：Q1: 100万, Q2: 120万, Q3: 150万, Q4: 200万`”。查询时，首先通过语义匹配找到最相关的行或列，然后在检索后处理阶段，再从元数据中解析出所需的具体单元格数据。这种方法比单元格索引更节省空间，但精度稍低。

策略三：检索后处理 (Post-Retrieval Processor)。

整个表格块被检索到后，不直接提供给 LLM，而是先经过一个轻量级的文本到 SQL 的翻译器。将用户的查询意图转换为 SQL 语句，直接在检索到的表格数据上执行精确查询，最后将查询结果交给 LLM 进行答案生成。这种方式最精确，完全排除了模糊匹配的风险，但对查询的鲁棒性和 SQL 翻译器的准确度要求较高。

在实践中，策略一（单元格级索引）配合策略三（后处理） 是构建高精度表格问答系统的黄金组合。

#### 在 RAG 中，表格的上下文增强：除了表格本身，是否需要附带表名、标题和周围段落？

是的，不仅需要，而且这是提升表格检索和生成质量的关键一步。一个脱离上下文的表格，其数据意义往往是模糊的，甚至容易被误解。

上下文增强的必要性：

- 表名和标题：提供了表格的全局主题和身份（ID）。在检索时，包含表名的查询能极大地提高命中率。

- 周围段落：文档中引用表格的上下文（如“如下表所示，...”、“从表2中可以观察到...”）是理解表格数据的“前理解”。它解释了作者为何创建这个表格，以及期望读者从中读出什么。这些信息对于 LLM 正确解读数据至关重要。

- 脚注和注释：通常包含关键的界定信息，如数据来源、单位说明、统计口径、异常值解释等。丢失脚注会导致数据被错误解读。

增强方式：

1. 文本融合嵌入：在构建索引块时，将表格的标题、周围的引用段落、脚注等内容，与表格的线性化文本拼接成一个完整的文本块，一起送入嵌入模型生成向量。这使得检索时，表格数据的全局上下文和局部数据能够被联合匹配。

2. 元数据注入：将表名、标题层级等关键信息，作为结构化元数据与表格的向量块一同存储。检索时，可以利用这些元数据进行精准过滤（如“只检索标题为‘销售数据’的表格”）。

3. LLM 上下文注入：在最终将检索到的表格块提供给 LLM 时，将上述元数据和上下文文本，以清晰的结构化格式（如“`[表名: 2023年财报] [来源: 第3页]`”）放在表格内容的前面。这为 LLM 提供了理解表格所必需的全部背景信息。

因此，一个完整的表格 RAG 块应该是：“`全局上下文 + 表格结构描述 + 表格数据 + 脚注`”的复合体。

#### 多模态文档处理：当文档包含文本、图像、表格时，如何构建统一的索引和检索框架？

构建统一的多模态文档索引，核心在于将物理布局不同的信息，映射到一个统一的语义空间中，同时保留各自的模态特性和在文档中的逻辑位置。

统一索引框架：

这是一个“区域识别 -> 分类处理 -> 统一表示 -> 关联元数据”的管道。

1. 文档布局分析：使用布局识别模型（如 LayoutLM、Surya），将文档页面分割为不同区域，并标记其类别：“正文段落”、“标题”、“表格”、“图片”、“图表说明（Caption）”。

2. 分类处理（Modality-Specific Processing）：
  - 文本区域：保持原样，进行常规分块。
  - 表格区域：使用表格结构识别模型提取，并转换为 Markdown 文本。
  - 图片区域：提取图片文件，并用多模态模型生成详细的 Caption 描述。

3. 统一表示（Unified Chunking）：\
   将处理后的结果，统一抽象为一种通用的“文档块”结构。每个块包含：
  - `content`：用于生成向量的主文本内容。对于图片块，是 Caption；对于表格块，是 Markdown 文本。
  - `modality`：标识该块是“文本”、“表格”还是“图片”。
  - `metadata`：包含来源、页码、位置、层级标题等。
  - `payload`：存储原始数据。对于图片，是图片的存储路径；对于表格，是原始表格的 JSON 或 Markdown 表示。

4. 关联元数据 (Contextual Linking)：通过页面的布局信息，将图表与其 Caption、正文引用段落进行物理关联，并在元数据中建立双向链接。

检索与生成策略：

- 检索时，查询向量与所有块的 `content` 向量进行匹配，实现跨模态的统一检索。

- 生成时，根据召回块的 `modality` 类型，动态组装上下文。将文本块和表格块的 Markdown 直接注入 Prompt。如果 LLM 具备多模态能力，还可以根据图片块的 `payload` 路径，将原始图片数据作为输入的一部分，使模型能直接“看图说话”。

#### 图像在 RAG 中如何处理？描述方法（captioning）与直接图像 embedding 的多模态检索对比。

在 RAG 中处理图像，主要有两条技术路径：将其“翻译”为文本，或将其嵌入到多模态向量空间中。

| 方法 | 核心思想 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Captioning | 使用多模态模型（如GPT-4V）将图像内容翻译成一段详尽的自然语言描述，然后将这段描述文本用于后续的文本检索和生成。 | 与现有文本RAG管道完全兼容，无需改动架构；生成的描述是可解释、可编辑的；可以生成多种粒度的描述（简要说明、详细描述、针对特定问题的描述）。 | 信息丢失不可避免，尤其是图像的细节、风格和不可言说的视觉信息；描述的准确性依赖于模型能力；无法处理需要直接进行图像匹配的任务。 |
| 多模态Embedding | 使用CLIP等多模态模型，直接将图像编码为一个向量，与文本向量存入同一向量空间。检索时，查询文本与图像向量进行跨模态相似度匹配。 | 保留了图像最原始的视觉特征；可以实现精细的视觉匹配，如“蓝色条纹衬衫”的图片；检索阶段即可实现跨模态对齐。 | 生成阶段如何处理？ 检索到了图片向量，但后续的生成模型大多是文本模型，无法直接消费图片向量。通常仍需对召回的图片进行Captioning或直接调用多模态LLM来生成最终答案，增加了流程复杂性。 |

最佳实践：混合策略。

在实际的高质量多模态 RAG 中，两者不是二选一，而是互补的。

1. 索引时：同时为一张图片生成 Caption 文本，并提取其 CLIP 图像向量。两者都存储为索引的字段。

2. 检索时：进行混合检索，部分权重来自用户查询与 Caption 文本的语义匹配，另一部分来自用户查询与图像向量的跨模态匹配，从而更全面地召回相关图片。

3. 生成时：如果最终使用的生成模型是多模态的，则同时提供 Caption 和原始图像数据，让模型做出最准确的判断。如果模型仅支持文本，则提供之前生成的高质量 Caption 作为图像的“代言人”。

#### 使用多模态 LLM（如 GPT-4V）直接对文档图片进行问答，这种方法能取代传统的解析+检索吗？

多模态 LLM 在文档理解上展现了强大的能力，但它是否能够取代传统的“解析+检索”管道，答案是否定的，至少在可预见的未来，两者是互补而非替代关系。它们在本质上面向不同的问题场景和规模。

传统解析+检索（RAG）的不可替代性：

1. 大规模文档库的必然选择：当面对一个包含数万份、总页数达百万级的文档库时，将整个知识库全部作为图片输入给多模态 LLM 是不可能的。一是上下文窗口根本无法容纳，二是推理成本将是天文数字。RAG 的“先检索、后生成”模式是处理大规模知识库的唯一经济可行的方式。

2. 知识更新与管理：对于企业 RAG 而言，知识库是不断更新的。传统管道只需重新解析新文档、增量更新索引即可。而每次更新都让 LLM 重新“看”一遍所有文档图片是不现实的。RAG 的索引提供了知识版本管理和溯源的能力，这是直接问答做不到的。

3. 精确的结构化数据提取与审计：对于需要高度精确的结构化数据提取（如财务报表、合同条款），传统管道的表格识别、规则解析等方法，其结果具有确定性和可审计性。而多模态 LLM 直接“看图说话”时，无法保证 100% 的数值准确，也难以追溯它是从图片的哪个位置推导出答案的。

多模态 LLM 的独特优势与最佳定位：

它的巨大价值体现在 RAG 管道鞭长莫及的“长尾”和“精度”环节。

- 解析工具的增强和补充：它可以用于为复杂的图片、图表生成高质量的 Caption，执行布局分析，或者在传统 PDF 解析失败时作为兜底方案进行全页识别。

- 对检索到的精准上下文进行深度理解：在 RAG 管道召回 Top K 个相关的文档块后，多模态 LLM 可以同时消费这些块（包括其中的图像和表格），进行复杂的跨模态推理，生成最终的答案。它负责的是“最后一公里”的深度思考，而不是全程的“记忆和检索”。

结论：未来最强大的文档处理系统，将是 “传统解析+检索”为躯体，“多模态 LLM”为大脑的混合架构。躯体负责海量知识的消化、组织和调度，大脑负责在聚焦的范围内进行深度的理解和创造。试图用大脑取代整个消化系统，既不经济，也不可靠。

#### 文档中的图表（Chart）如何提取数据并进行问答？能否反向转换为表格数据？

图表（Chart）是数据的可视化表达，常见类型包括柱状图、折线图、饼图等。在 RAG 中处理图表的理想方式，不是简单地将它视为一张图片去描述，而是将其反向工程为底层的结构化数据，从而能进行精确的数值问答。

提取图表数据的技术路径通常分为两步。首先利用计算机视觉模型对图表进行分解，识别出图表类型、坐标轴、图例、数据系列以及具体的数值映射。例如，可以使用基于目标检测和关键点回归的模型（如 DePlot、ChartQA 的视觉模块）定位图表的各个组件，然后根据坐标轴刻度和数据标记的位置反推出原始数值。如果图表是 PDF 中矢量图形绘制的，还可以通过解析矢量指令直接提取数据点，这比视觉方法更准确。第二步是将提取出的数据点重新组织为结构化表格，将图例条目映射为列名，将 X 轴的类别或数值映射为行索引，填充对应的 Y 值。这样，一张“2023年各季度销售额柱状图”就被转换成了一个“季度-销售额”的二维表格。

这种反向转换之所以重要，是因为它能将图表的不可量化视觉信息转化为精确的数字，为问答提供坚实基础。当用户问“2023年 Q3 销售额最高的是哪个产品”时，系统可以精准地从表格中检索出最大值对应的行，而不是依赖多模态模型从图片中“读出”一个可能有偏差的近似答案。如果无法完整提取，作为降级方案，可以调用多模态 LLM 生成详细的图表描述，但需要注明其数值可能存在估算误差。

在实际管道中，图表处理模块通常是布局分析的下游。当布局模型检测到一个区域为“图表”时，它会被送入专用的图表解析器，输出的表格数据和描述文本共同作为该区域的索引内容，表格数据同时存入元数据供精确查询。

#### 多模态 embedding 模型（如 CLIP, ImageBind）如何助力文档中图文匹配和检索？

多模态 embedding 模型，如 CLIP，通过将图像和文本映射到同一个高维向量空间，实现了跨模态的语义对齐。在文档处理中，这意味着我们可以直接衡量一个文本查询与一张文档图片（或其中的某个区域）的语义相似度，而无需先将其转换为文本。

这项能力在文档检索中带来了两方面的显著提升。首先是弥补了纯文本解析的遗漏。许多文档中的信息天然适合图像表示，例如公司 Logo、产品照片、复杂的流程图或无法被正确 OCR 的手写签名。传统的文本 RAG 会完全丢失这些信息。而使用 CLIP 为这些图像区域生成向量后，用户查询“包含公司 Logo 的合同页面”时，就能通过跨模态匹配直接定位到相关图像块，这是文本检索做不到的。其次，它可以充当文本检索的质量增强器和验证器。当文本解析结果不可靠时（如扫描件 OCR 质量差），可以同时依赖文本向量和页面图像的 CLIP 向量进行混合检索，两者相互补充，提高召回率。

在实现上，典型的模式是为每页文档或其中的每个图片区域计算一个 CLIP 图像向量，存储在向量库中。对于文本查询，使用 CLIP 的文本编码器生成查询向量，直接与图像向量进行相似度搜索。这可以与传统的文本-文本检索并行进行，结果通过融合排序后提供给 LLM。ImageBind 等更先进的模型进一步扩展到音频、深度图等模态，但目前文档处理最成熟的仍是图文对齐。需要注意的是，CLIP 对文档图像的细粒度文本理解可能不如 OCR+文本嵌入，所以它更适合作为宏观的、视觉层面的补充，而不是完全替代文本检索。

#### 布局感知（Layout-aware）的文档分块：如何利用坐标和顺序信息提升检索质量？

传统的固定大小分块完全忽视了文档的视觉布局，常常将标题与其下的段落割裂，或在多栏排版中产生阅读顺序混乱。布局感知的分块则试图利用 PDF 解析或布局分析得到的坐标信息，恢复文档的逻辑结构，让每个分块都尽可能成为一个语义自包含的单元。

实现布局感知分块的核心是构建一棵“文档布局树”。首先使用布局模型或 PDF 解析器识别页面上的各个元素，如标题、段落、表格、图片，并获取它们精确的边界框坐标。然后，依据坐标进行空间聚类和排序：先按照从上到下、从左到右的阅读顺序对元素排序，再通过分析坐标的 X 轴分布检测出“栏”的存在。对于同一栏内的元素，根据 Y 坐标自然排序；不同栏则按照栏的左右顺序，读完一栏再读下一栏。

在排序完成后，进行“上下文合并”。一个关键的启发式规则是：一个元素如果被标记为“标题”，那么它应该与其后续的非标题元素合并为一个块，直到遇到下一个同级或更高级的标题。这样，标题与其说明的文本就被紧密绑定在一起。同样，表格的标题和脚注也会被合并进表格块中。对于无法明确识别的文本块，可以根据坐标邻近性进行合并，并设定一个最大块大小作为兜底。

这种布局感知的分块显著提升了检索质量。一方面，由于每个块都包含了完整的标题上下文，其向量表示更加精确和独特，检索时更容易命中。另一方面，当 LLM 接收到这样的块时，它看到的是带有清晰层级和完整背景的信息，避免了割裂感。在工程上，可以利用 PyMuPDF 等库获取文本块的坐标，结合 spaCy 等 NLP 工具进行标题识别，自行实现一套布局感知分块逻辑，也可以直接使用 Unstructured 等专门为此设计的开源库。

#### 在文档问答中，如何将文本检索结果和表格检索结果融合后输入生成模型？

文档中同时包含文本和表格，两者的检索通常是分开进行的，因为它们的嵌入空间和检索特征差异很大。如何将来自不同“模态”的结果公平、有效地融合，是决定最终生成质量的关键一步。

最直接的融合发生在检索结果层面，即“分数融合”。一种常用的方法是倒数排名融合（Reciprocal Rank Fusion, RRF）。它的思想很简单：不关心各个检索器的绝对分数（因为文本相似度和表格相似度的分数尺度完全不可比），而是只看每个结果在其各自检索列表中的排名。RRF 为每个结果计算一个融合分数，等于 `1 / (k + rank)`，其中 `k` 是一个常数（通常取 60）。然后将来自文本和表格检索的结果根据这个融合分数重新排序，选出最终的 Top K。这种方法无需任何训练，对不同的检索后端非常鲁棒，在实践中效果很好。

更精细的融合是在重排序层面。可以将双路粗筛的结果合并去重后，送入一个 Cross-Encoder 重排序模型进行统一的精细打分。这个重排序模型将查询与每个候选片段（无论是文本块还是 Markdown 表格）拼接后联合编码，从而能更准确地判断其语义相关性，天然解决了跨模态的分数对齐问题。

在向生成模型输入时，顺序也很重要。通常不是将所有文本块和表格块随机摆放，而是根据它们在原文中的逻辑位置进行排序后提供给 LLM。例如，将一个段落的文本块、紧随其后的表格块、以及之后的另一个文本块按照页面阅读顺序排列，这能为 LLM 还原出最接近原始文档的上下文流，极大提升其理解能力。在 Prompt 中，还可以为不同类型的块加上清晰的标记，如 `[文本段落]` 和 `[表格数据]`，帮助 LLM 区分信息源。

#### 多模态 RAG 的索引设计：是用统一向量空间还是多索引分治？

多模态 RAG 的索引设计面临一个根本抉择：是将所有模态（文本、图像向量、表格向量）强行映射到同一个向量空间，还是分而治之，为每种模态构建独立的专门索引。

统一向量空间的理想很丰满。如果存在一个完美的多模态嵌入模型，能够将文本段落、图片、表格都精准地映射到同一个语义空间，那么检索就变得无比简单：只需一个查询向量，就能跨模态地找到所有相关信息。CLIP 等模型在图文对齐上迈出了一大步，但对于富含结构化信息的表格，目前仍缺乏完美的统一模型。强行使用可能导致某种模态的表达能力被削弱。例如，将 Markdown 表格用 CLIP 文本编码器编码，虽然可行，但其对表格行列结构内在语义的捕捉能力，远不如专门的文本嵌入模型。统一空间最大的吸引力在于其简洁性和天然的跨模态关联能力。

多索引分治是目前更务实、更强大的方案。它为文本、图像、表格分别构建专用的索引。文本使用强语义文本嵌入模型，图像使用 CLIP 视觉编码器，表格则可以使用经过表格数据微调的特殊嵌入模型，甚至直接采用单元格级索引。查询时，系统并行地在三个索引中检索，得到三个各自最优的结果集，然后通过结果融合（如 RRF 或加权求和）来生成最终的 Top K 列表。这种方案的优点是每个索引都可以针对其数据特性进行极致优化，不牺牲任何精度。缺点是需要维护多个检索管道和融合逻辑，工程复杂度较高。

在工程实践中，通常推荐多索引+混合重排序的架构：用多索引保证各个模态的召回率，然后用一个强大的多模态重排序模型（或直接使用多模态 LLM）在精排阶段进行深度融合。这是当前在技术能力和工程可控性之间找到的最佳平衡。

#### 处理幻灯片（PPT）时，如何组织每页的文本、图像、表格，使检索粒度合理？

幻灯片文档与普通文章不同，其信息天然被组织为单页的离散单元，每页内部又包含标题、文本框、图片、表格等丰富的视觉元素。处理 PPT 的核心挑战在于，如何将这些碎片化的视觉元素，重新组织成既有足够上下文、又不会过于庞大的检索单元。

最合适的检索粒度通常是页级上下文块，而非单个文本框。一张幻灯片之所以被设计成一页，就是因为它上面的所有元素共同表达了一个单一的主题。因此，将一页 PPT 解析后，不应将标题、各个分点文本框、图片描述分别独立索引，而应按照阅读顺序（通常是自上而下、分栏时自左而右）将它们拼接成一个完整的大文本块。每个文本框或图片的内容之间用换行或特殊符号分隔。同时，为这个块注入这页 PPT 的标题作为前缀，以及可能存在的章节标题。这样，一个块就包含了这一页的完整语义，检索时不会因为碎片化而丢失上下文。

对于图片，同样需要生成 Caption，并将其描述文本按顺序插入到大文本块中。如果图片本身有重要的视觉信息需要被直接检索，可以额外为它单独建立一条图像向量索引，并在元数据中关联回它所属的页面块。对于表格，应将其转换为 Markdown 格式后插入。如果表格复杂无法用 Markdown 表达，可以将其作为独立的子块，但仍与页面主块在元数据上强关联。

这种以“页面上下文”为基本单元的策略，既能保证检索到的信息足够完整，又能利用幻灯片本身的结构（页）来控制块的大小，非常自然。当用户查询命中一个 PPT 页面时，LLM 得到的是类似于阅读一页幻灯片的完整体验，可以准确地回答问题。如果某些页面内容过多，也可以进一步拆分为“标题+主体内容”和“附注”两部分，但必须保留清晰的关联关系。

#### 如何评估表格检索的准确性？常用指标和基准数据集有哪些？

评估表格检索的准确性，与评估普通文本检索有许多共通之处，但需要特别关注表格的结构特性。核心指标仍然是召回率（Recall@K）和平均倒数排名（MRR）。Recall@K 衡量的是包含标准答案的表格是否出现在检索结果的前 K 个之中，这是最基本的准入指标。MRR 则关注标准答案表格在结果列表中的具体排名，排名越靠前，MRR 越高。对于表格问答系统，还可以使用 精确匹配率（Exact Match, EM） 和 F1 分数，衡量从表格中提取的答案字符串与标准答案的匹配程度。但 EM 对格式特别敏感，因此很多时候会用更鲁棒的 F1。

在基准数据集方面，有几个代表性的选择。WikiTableQuestions 是一个经典的表格问答数据集，包含来自维基百科的表格和人工编写的问题，答案往往涉及多行推理和聚合操作。TabFact 专注于表格事实验证，任务是基于表格判断一个自然语言陈述的真假，这要求模型同时理解表格和陈述。SQA (Sequential QA) 类似，需要多步推理。近年来，TableBench 等大型基准试图覆盖更多样化的表格类型和查询意图。对于自建的 RAG 系统，最好的评估是基于自身业务文档构造测试集：抽取真实文档中的表格，为它们编写典型的用户查询，并标记出包含正确答案的表格块 ID 以及具体的答案单元格。这种定制化测试集对衡量系统在生产环境下的表现最具指导意义。评估时，应将检索与最终的生成答案联合评估，因为检索的最终目的是为了生成正确的答案，而不只是为了召回正确的表格。

#### 对于包含金融或科学数据表的文档，需要特殊的数值理解能力，RAG 如何增强？

金融和科学数据表中的信息往往以数值为核心，查询也常常涉及比较、求和、趋势分析等定量操作。这对 RAG 系统提出了远超简单文本匹配的需求，必须增强其数值理解能力。

增强策略可以从数据预处理和查询执行两个层面入手。在数据预处理阶段，当解析并线性化表格时，不仅输出原始的 Markdown 表格，还要对数值进行语义增强。例如，识别出货币单位（美元、人民币）、量级（百万、亿）、百分比等，并将其标准化和显式化。可以把“¥1,200万”显式地改写为“1200万人民币”。对于跨行或跨列的数据，可以自动计算预聚合值（如小计、总计），并将这些聚合值作为新的数据行追加到表格中，或作为表格摘要的一部分。更重要的是，为每个数值单元格生成一个包含完整上下文的“陈述句”，例如“2023年 Q3 Acme 公司的收入为 150 万美元，环比增长 20%”。这些陈述句极大地增强了嵌入向量的语义信息，使数值查询能被精准定位。

在查询执行阶段，可以利用外部工具来弥补 LLM 自身算术能力的不足。当 RAG 检索到相关表格后，不直接将其全部丢给 LLM，而是先用一个轻量级的 Text-to-SQL 引擎，根据用户查询在检索到的表格上执行精确的聚合计算。例如，用户问“2023年总收入最高的产品是哪个？”，系统可以自动将 Markdown 表格转换为 SQLite 内存表，执行 `SELECT product, SUM(revenue) FROM table WHERE year=2023 GROUP BY product ORDER BY 2 DESC LIMIT 1`，然后将精确的查询结果交给 LLM 生成自然语言答案。这种“先检索、再结构化查询、后生成”的模式，从根本上解决了 LLM 在处理精确数值计算时容易出幻觉的问题，是金融和科学领域 RAG 系统的必备能力。

#### 表格的语义分块与普通文本分块有何不同？能否按行、列块进行检索？

表格的语义分块与文本分块有着本质的区别。文本的语义单元是句子或段落，沿着一维线性展开；而表格的语义单元则是行列交织的二维单元格集合，其“语义”同时体现在行的记录完整性和列的属性分组上。

因此，表格的语义分块不能简单地按 Token 数切割，而是要沿着其逻辑维度进行。常见的分块方式有三种：

- 单元格级分块：为每个单元格创建一个索引块，内容为其本身的数值以及从表头和行头注入的完整上下文。这种方式可以实现极致的精准检索，比如直接回答“北京 Q3 的销售额是多少”。代价是索引量会膨胀。

- 行级分块：将表格的每一行作为一个独立的数据记录进行索引。块的内容是该行所有列的值，并显式带上表头作为键。这适合“找人”或“找事件”的查询，能完整保留一条记录的所有属性。

- 列级分块：将表格的每一列（通常与表头结合）作为一个独立的语义向量，适合“找属性”或“找趋势”的查询。例如，单独为“温度”这一列生成一个摘要向量，方便回答“温度是如何变化的”这类问题。

在实践中最常用的混合策略是：以行级分块为主，辅以列级摘要和全局表格向量。每个行块独立索引，用于精确召回。同时，为每列和整个表格生成描述性向量，用于广域的语义匹配。这样做既保持了记录完整性，又提供了宏观的检索入口。按行、按列进行检索是完全可行的，并且是提升表格问答精度的重要手段。这种多维分块和检索，正是表格 RAG 区别于纯文本 RAG 的核心所在。

#### 使用 LLM 进行表格事实性校验：如何检测表格中的矛盾或错误数据？

在 RAG 知识库的构建和维护中，利用 LLM 对表格数据进行事实性校验，是提升数据质量和系统可靠性的重要一环。这通常发生在文档解析后、索引构建前，作为一种数据清洗和验证的后处理步骤。

校验可以分为两类：内部一致性校验和外部事实校验。内部一致性校验不依赖外部知识，只检查表格自身逻辑是否自洽。例如，可以检测“小计”行是否等于各分项之和，百分比列的各项加起来是否接近 100%，不同层级的合计值是否存在冲突。这类任务非常适合 LLM，因为它们需要理解表格的语义结构和进行简单算术，将表格转换为其所理解的格式后，LLM 可以指出“根据您的数据，Q1 至 Q4 的总和与给出的全年总计不符”。

外部事实校验则需要交叉验证。例如，表格声称“公司成立于 1910 年”，LLM 可以凭借其内部知识判断这个年份是否合理，或者调用搜索引擎进行核实。更高级的做法是，在受控的企业环境中，将提取出的关键数据点与数据库中的权威记录进行比对，LLM 在此扮演数据匹配和对齐的角色。

实现上，可以设计一个专门的校验 Prompt，输入是线性化的表格，要求 LLM 逐条检查并列出发现的不一致之处。校验结果可以作为该表格的“置信度”标签写入元数据，或直接生成告警供人工复核。需要注意的是，LLM 本身也可能产生幻觉，因此其校验结果最好作为筛选器或辅助提示，最终决策仍需人工或确定性规则来把关。这种校验机制对于金融、法律等对数据准确性要求极高的领域，是 RAG 系统能够落地的关键一环。

#### 在低延迟要求下，多模态文档的解析和检索如何优化流水线？

在实时性要求高的 RAG 应用中，多模态文档处理极易成为延迟瓶颈。优化需要贯穿解析、嵌入、检索和生成的全流程，采取“避免、加速和缓存”的组合策略。

解析环节：核心是异步化和预计算。绝不能让用户请求触发实时解析。在文档进入知识库时，就应通过离线管道完成所有繁重的解析工作，包括布局分析、OCR、表格识别等。可以将解析任务推入消息队列，由专门的 GPU 工作池处理，结果存入对象存储。在检索时，只访问已解析好的结构化文本和元数据。对于必须实时处理的场景，对解析模型进行量化（如使用 ONNX Runtime 部署轻量级 OCR），并严格设置超时和降级策略（解析失败则仅使用可提取的文本层）。

嵌入与索引：使用高效的向量库和近似最近邻搜索。将基础索引常驻内存，使用 IVF_PQ 等压缩索引以减少内存占用和加速搜索。对于已知的热点查询，可以实施语义缓存，将查询向量和结果存储起来，命中时直接返回，完全绕过检索和生成环节。

检索与生成：采用多级检索漏斗。第一级用极快的轻量级方法（如 BM25 关键词匹配）进行粗筛，将候选集从百万级缩小到百级；第二级用向量相似度进行精排；如果候选集仍较大，第三级用 Cross-Encoder 进行最终排序。最后，将少量高相关度块送给 LLM 生成答案。流式输出也能改善用户体感，让模型边生成边返回结果。

在整个流水线中，缓存是提升低延迟体验的最有效手段。可以对不同层级的结果进行缓存：解析结果的缓存、查询嵌入的缓存、查询结果的缓存。这样，随着系统的运行，重复或相似查询的响应延迟会趋近于零。最终，一个精心优化的多模态 RAG 系统，可以在几百毫秒内完成从用户提问到返回包含图文表信息的精确答案。
