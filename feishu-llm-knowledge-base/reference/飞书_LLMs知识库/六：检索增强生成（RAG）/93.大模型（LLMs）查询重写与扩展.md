# 93.大模型（LLMs）查询重写与扩展

#### 为什么在 RAG 中需要对用户原始查询进行重写或扩展？

在 RAG 系统中，用户的原始查询通常不是检索的最优形式，直接使用它进行检索往往会导致效果不佳。查询重写与扩展的核心目的，就是弥合用户信息需求的表达方式与文档库中相关内容的表述方式之间的鸿沟，从而提升检索的召回率和精确率。

具体原因包括以下几个方面：

信息缺失与模糊性：用户在提问时，尤其是在对话或多轮交互中，常常会使用省略、指代或依赖上下文背景。例如，用户先问“张三多大了？”，接着问“那他住哪？”。第二个查询如果直接检索“那他住哪”，几乎不可能找到任何有效文档。重写的任务就是将其还原为“张三的住址”。

词汇与语义鸿沟：用户的用词习惯和文档作者往往不同。用户可能用口语化、非专业的表述，而文档是正式的书面语。例如，用户搜索“怎么让自己更开心”，而相关文档的标题可能是“提升个人幸福感的方法”。如果只靠字面匹配的稀疏检索，这个查询就会漏掉这篇文档。重写可以引入同义词、近义词、上下位词，或者用生成模型直接生成更贴近文档措辞的查询版本。

查询的粒度与意图不匹配：用户输入的查询可能过于简短宽泛（如“人工智能”），也可能过于冗长复杂（如一段包含多个子问题的描述）。重写可以根据检索系统的特性，将宽泛查询具体化，或将复杂查询分解为多个独立的具体查询，再分别检索。

多模态与元数据需求：有时用户查询中隐含了对文档类型、时间、来源的需求。例如，用户说“给我看看最新的官方政策”，虽然没有直接说“2024年 白皮书”，但通过重写可以显式地加上时间过滤和文档类型偏好。

因此，查询重写与扩展是 RAG 系统中连接“用户真实意图”与“系统可检索表达”的关键桥梁，它直接决定了检索结果的相关性和最终答案的质量。

#### 查询重写的常见方法有哪些？列举至少三种（基于规则、基于同义词、基于生成模型）。

查询重写的方法从简单到复杂，可以根据场景和资源选择。常见的三种方法为：

1. 基于规则的方法：

这是最快速、成本最低的重写方式。它不涉及任何机器学习模型，仅依靠预定义的规则或模板对查询进行变换。

- 同义词替换：通过维护一个领域同义词表，将查询中的关键词替换为它的同义词或标准化形式。例如，将“血压高”替换为“高血压”。此方法简单高效，但需要人工构建和维护词表，无法处理复杂的语义改写。

- 拼写纠错与规范化：修复常见的用户拼写错误，统一大小写、全半角、日期和数字格式。

- 模板填充：对于特定业务场景（如客服、订单查询），使用固定的重写模板，将用户查询中的实体提取出来，填充到结构化的查询模板中。

- 停用词移除与关键词提取：去除查询中无信息量的功能性词汇，保留核心关键词。

2. 基于同义词或知识图谱的方法：

这类方法利用外部词汇资源或知识图谱来扩展查询，比简单同义词表更丰富。

- 基于 WordNet：对于英文，可以利用 WordNet 查找查询词的同义词集、上位词、下位词，将其作为查询扩展词。

- 基于知识图谱：对于包含实体的查询，可以链接到知识图谱（如 Wikidata、企业知识图谱），找到该实体的别名、相关实体、属性。例如，查询“苹果 CEO”，可以通过图谱扩展出“蒂姆·库克”、“Apple Inc.”。

- 基于词嵌入的扩展：使用预训练的词嵌入模型（如 Word2Vec, GloVe）找到与查询词最相似的 K 个词进行扩展。这能捕捉语义层面的相似性，但可能引入噪音，需要结合语境。

3. 基于生成模型的方法（最先进）：

利用强大的 LLM 来自动完成查询重写，是目前最主流、效果最好的方法。它通过精心设计的 Prompt，让 LLM 理解对话历史、用户意图，并生成多个独立、完整、适用于检索的查询。

- 少样本提示：在提示中给出一两个查询重写的例子，然后要求 LLM 对当前查询进行重写。

- 零样本指令：直接向 LLM 下达清晰的指令，例如：“你是一个查询改写助手。请将用户的对话查询改写为一个独立的、简洁的、用于搜索引擎检索的查询。如果用户有对话历史，请根据历史消解指代。”

- 生成多个改写版本：可以让 LLM 生成多个语义相同但表述不同的查询版本，然后并发检索，合并结果，以最大化召回率。

这三种方法并非互斥，而是可以在一个系统中组合使用。例如，先通过规则进行基础的实体识别和纠错，再通过 LLM 进行深层的语义改写和对话消解。

#### 如何利用 LLM 对查询进行重写以更好地匹配文档的表述方式？写出提示词思路。

利用 LLM 进行查询重写的核心是构建一个清晰、结构化的提示词（Prompt），为模型设定角色、任务、上下文、约束和输出格式。以下是设计思路和示例。

设计思路：

1. 角色设定：明确告诉 LLM 它是谁。例如：“你是一个专业的查询改写助手，负责为搜索引擎生成最佳的查询词。”

2. 任务描述：清晰地定义它需要做什么。核心是将用户口语化的、依赖上下文的问题，改写成一个独立、精准、关键词丰富的检索查询。

3. 上下文提供：提供可用的多轮对话历史，让 LLM 能够理解指代和省略。

4. 改写原则与约束：
  - 自包含：改写后的查询必须脱离对话历史也能独立理解。
  - 提取核心实体与意图：将对话中提到的关键实体（人名、地名、专有名词）显式地补充进去。
  - 文档化表述：使用更正式、更贴近书面文档的关键词，而非口语词。
  - 去除噪音：去除礼貌用语、语气词等对检索无用的成分。
  - 简洁性：查询不宜过长，保留对检索最有用的信息。

5. 输出格式：可以要求输出一个或多个改写版本，并使用特定的标记分隔。

提示词示例（用于多轮对话）：

```plain text
你是一个专业的查询改写助手。你的任务是根据用户的对话历史，将用户当前的问题改写为一个或两个独立、简洁的搜索引擎查询。

[对话历史]
用户：你知道张三吗？
助手：张三是一位著名的计算机科学家。
用户：那他今年多大了？

[改写原则]
1. 将省略和指代替换为具体实体（如人名、地名）。
2. 使用适合文档检索的关键词和正式表述。
3. 改写后的查询必须脱离对话历史也能独立理解。
4. 只输出改写后的查询，不要解释。

[输出格式]
改写查询1：...
改写查询2：... (可选)
```

LLM 的输出将是：“改写查询1：张三 年龄”。这个查询可以直接用于 BM25 或向量检索，大大提高了命中相关文档的概率。

更高级的做法：

可以结合用户的意图，让 LLM 生成多个不同角度的重写查询。例如，如果用户意图是“比较”，则生成“A vs B 对比”、“A 和 B 的区别”等。此外，可以同时生成针对稀疏检索的关键词查询，和针对稠密检索的、更接近自然语言的句子查询。

#### 查询扩展（Query Expansion）与查询重写（Query Rewriting）的区别是什么？各适用于什么场景？

查询扩展（QE）和查询重写（QR）都是优化原始查询的技术，但它们在处理粒度、方法哲学和适用场景上存在显著区别。

核心区别：

| 维度 | 查询扩展 (Query Expansion) | 查询重写 (Query Rewriting) |
| --- | --- | --- |
| 目标 | 增加召回：向原查询中添加相关的词项或短语，以召回更多潜在相关的文档。 | 提升精度与召回：将原查询转化为更准确、更贴近文档表达形式的新查询，甚至替代原查询。 |
| 操作方式 | 在原查询基础上做加法，保留原查询的全部或大部分信息，然后附加扩展词。 | 进行重构，可能删除、替换、重组原查询中的成分，生成一个或几个全新的查询。 |
| 输出 | 一个增补过的查询字符串，通常是在原查询词基础上连接扩展词，或生成一个带权重的查询词集合。 | 一个或多个全新的、独立的查询字符串。 |
| 技术 | 同义词/词嵌入扩展、伪相关反馈、基于词表的规则扩展。 | 基于 LLM 的生成、基于规则的模式转换、基于意图分类的模板改写。 |
| 对原查询的依赖 | 强依赖，原查询是核心，扩展只是辅助。 | 弱依赖，新查询可能完全抛弃原查询的措辞，只保留语义。 |

适用场景：

- 查询扩展适用于：
  - 初检召回率低：对某些长尾、罕见的查询，可能只有极少数字面匹配文档，需要通过同义词、上下位词扩展来增加命中。
  - 弥补词汇不匹配：当领域内存在大量同义不同词的表达时，通过扩展来覆盖这些表达。
  - 稳健性优先：不希望对原查询进行大幅改动，以防引入语义偏移，只做安全的补充。
  - 稀疏检索（如 BM25）：由于 BM25 严重依赖字面匹配，查询扩展是其提升召回率的关键手段。

- 查询重写适用于：
  - 对话系统：必须依赖多轮历史来消解指代和省略，生成一个独立的查询。
  - 查询意图复杂或模糊：用户输入是长句或口语化问题，需要提炼为精准的检索关键词。
  - 最大化检索质量：追求最高的检索精度和排序质量，可以接受一定的计算开销，使用 LLM 生成最佳查询。
  - 稠密检索：由于稠密检索本身有语义泛化能力，更需要的往往不是盲目增加词项，而是生成一个更聚焦、语义更清晰的句子进行向量检索。

在实践中，两者常常可以结合使用。例如，先用 LLM 重写查询，再对重写后的查询进行关键词扩展，结合两者优势。

#### 在对话式 RAG 中，如何利用对话历史来消解指代和省略，生成独立的检索查询？

对话式 RAG 的核心挑战之一是多轮交互中的上下文依赖性。用户的当前问题往往包含大量指代词（“他”、“那个”、“上次的方案”）和省略（“价格呢？”）。如果不做处理直接检索，几乎不可能命中相关文档。利用对话历史生成独立的检索查询，是保障检索质量的必要前提。

解决方案：基于 LLM 的对话查询重构。

这是目前最主流、效果最好的方法。它是一个专门的预处理步骤，发生在检索之前。流程如下：

1. 维护对话状态与历史：系统保存当前会话的完整历史，包括用户和助手的所有消息。为了节省 Token，可以只保留最近 N 轮，或使用对话历史摘要。

2. 构造专用提示词：编写一个专门用于消解指代和生成独立查询的提示词。这个提示词会明确告知 LLM 它当前的任务。

3. 提示词关键要素：
  - 提供对话历史：将原始的历史对话按顺序提供给 LLM。
  - 明确当前问题：单独标记出“当前用户问题”。
  - 给出消解指令：清晰地告知 LLM 需要完成的操作，如“请将省略和指代替换为具体实体”、“生成一个不依赖对话历史也能理解的独立查询”。
  - 提供示例（少样本）：在提示中给出一两个消解指代的正确示例，能极大提升模型的遵从度。

示例：

```plain text
[对话历史]
用户：帮我查一下2024年诺贝尔物理学奖得主是谁。
助手：2024年诺贝尔物理学奖授予了John Hopfield和Geoffrey Hinton。
用户：那他的主要贡献是什么？

[指令]
请根据对话历史，将用户的最后一个问题改写为一个独立的、完整的检索查询。

[正确的改写示例]
用户：上次说的那个产品，它的价格是多少？
历史：助手推荐了“智能手表A”。
改写查询：智能手表A 价格

现在，请改写：
改写查询：
```

LLM 输出应为：“John Hopfield 主要贡献” 或 “Geoffrey Hinton 主要贡献”。

实现架构：

这个查询重构模块通常部署为一个微服务或函数，在 RAG 检索管道的入口处被调用。它具有以下特征：

- 低延迟要求：不能显著增加端到端响应时间，因此需要选用推理速度快的轻量级 LLM。

- 专用性：专门为消解指代和查询重写而微调或精心提示，不承担其他任务。

- 可缓存：对于相同的历史前缀，可以缓存其状态。

通过这样一个前置的重构步骤，对话系统就能将口语化、碎片化的多轮交互，转化为一个个清晰明确的检索查询，从而大幅提升复杂对话场景下的 RAG 性能。

#### 基于用户意图分类的查询重写：如何根据意图选择不同的重写策略？

不同的用户查询意图，需要不同的检索策略和查询形式。对查询意图进行分类，并据此选择针对性的重写策略，可以显著提升检索的精准度。

意图分类与对应的重写策略：

1. 事实型查询：
  - 特征：询问一个明确的事实、实体属性或定义。如“谁是美国总统？”、“水的沸点是多少？”。
  - 重写策略：实体聚焦与精确化。将查询重写为最核心的关键词组合，强调精确匹配。可以提取出核心实体，为其添加别名或标准名称。对于稀疏检索，生成简短的关键词查询；对于稠密检索，生成一个包含实体的简明句子。
  - 示例：查询“告诉我们关于苹果公司最新的那个手机” -> 重写为 “苹果公司 最新手机 型号”。

2. 解释型/概念型查询：
  - 特征：询问概念、原因、过程。如“什么是机器学习？”、“如何制作面包？”。
  - 重写策略：语义扩展与释义。为查询生成多个不同措辞的版本，以覆盖文档中可能出现的同义表达。可以加入“定义”、“解释”、“概述”、“教程”等引导词。
  - 示例：查询“如何让自己更开心” -> 重写为 “提升幸福感的方法”、“保持积极心态的技巧”。

3. 比较型查询：
  - 特征：要求对比两个或多个实体。如“iPhone 15 和 三星 S24 哪个好？”。
  - 重写策略：分解与组合。一方面生成一个包含两个实体的组合查询（“iPhone 15 对比 三星 S24”），另一方面可以生成两个独立的、针对各自实体的查询。
  - 示例：查询“iPhone 15 和 S24 哪个拍照好” -> 重写为 “iPhone 15 拍照评测”、“三星 S24 拍照评测”、“iPhone 15 S24 相机对比”。

4. 导航型/元数据查询：
  - 特征：用户想找特定类型的文档，如“2024年的财报”、“最新的官方政策文件”。
  - 重写策略：注入元数据约束。在查询中显式添加文档类型、时间、来源等词。如“2024 年度财报 filetype:pdf”。
  - 示例：查询“给我看看最新的政策” -> 重写为 “2024 年 官方政策 文件”。

实现方式：

- 微调意图分类器：在领域数据上训练一个轻量级的文本分类模型，在线时快速判断查询意图。

- 基于 LLM 的一体化重写：将意图分类与重写合并，通过 Prompt 让 LLM 同时输出意图类别和对应的重写查询。这更为灵活。

通过这种“先分类，后重写”的策略，检索系统不再是千篇一律地处理所有查询，而是能“因材施教”，最大化检索的准确率。

#### 多轮对话中的查询重构：如何将“那他的年龄呢？”转为“张三的年龄”？

将多轮对话中高度依赖上下文的查询（如“那他的年龄呢？”）重构为独立查询（如“张三的年龄”），这个过程的核心是指代消解和实体链接。

实现方法：

最有效的方式是通过少量样本提示或微调一个 LLM 来专门完成这个任务。这个 LLM 需要理解对话历史，并具备提取关键实体和意图的能力。

以提示工程为例：

设计一个包含以下要素的 Prompt：

1. 角色指令：告知 LLM 它的任务是将口语化的、依赖历史的用户问题，转化为一个独立的、完整的检索查询。

2. 对话历史：提供原始的历史消息。为了使 LLM 聚焦，历史可以经过简化，去除不必要的客套话。

3. 当前问题：明确标记出需要重构的用户消息。

4. 消解规则：用自然语言说明需要执行的操作，例如：“如果用户问题中包含‘他’、‘她’、‘它’、‘那个’等词，请根据对话历史，将这些词替换为具体的人名、地名或物体名。”

5. 输出格式：要求只输出重构后的查询，不做任何解释。

示例 Prompt：

```plain text
你是一个对话上下文消解专家。请根据“对话历史”，将“当前用户问题”改写为一个不依赖历史、可以独立理解的检索查询。

[对话历史]
用户：我想了解张三。
助手：张三是一位著名的计算机科学家，主要贡献在人工智能领域。
用户：那他今年多大了？

[消解规则]
将“他”替换为对话历史中最后提到的相关人名。

[输出]
张三 的 年龄
```

通过这种提示，模型能够将“那他的年龄呢？”准确重构为“张三的年龄”。

更为工程化的方案：

- 微调一个指代消解模型：如果拥有大量领域内的对话数据，可以微调一个轻量级的序列到序列模型，专门用于这项任务。其输入是对话历史和当前问题，输出是重构后的查询。这种方式比通用 LLM 提示更稳定、更快速。

- 结合实体识别：使用 NER 工具预先提取对话历史中的所有实体及其类型。在重构时，将最近的同类型实体填充进去。例如，当前问题提到“他”，最近出现的人名是“张三”，就将“他”替换为“张三”。

无论哪种方式，这个重构步骤都应该作为 RAG 管道中检索之前的必经环节，确保进入检索系统的查询是清晰、自包含的。

#### 查询扩展中加入伪相关反馈（Pseudo Relevance Feedback）：如何从初检索结果中提取关键词并扩展查询？

伪相关反馈（PRF）是一种经典的查询扩展技术。它的核心思想是：假设初检索排在前列的结果是相关的，然后从这些“伪相关”文档中自动提取出与原始查询相关的关键词，再将这些词加入到原始查询中，形成一个新的扩展查询进行第二次检索。

实现步骤：

1. 执行初检索：使用用户原始查询 $Q_0$ 进行检索，得到前 $N$ 个结果（通常 N=10∼20），作为伪相关文档集 $D_{top}$。这个阶段假设排名靠前的文档大概率是相关的。

2. 文本提取与预处理：从这些伪相关文档的文本或摘要中，提取出所有词汇。进行分词、词干提取、停用词移除等预处理。

3. 关键词打分与选取：这是核心。需要对每个候选词项计算一个分数，以衡量它对原始查询主题的代表性。常用的打分方法有：
  - Rocchio 算法：通过向量空间模型，计算一个能区分伪相关文档和整个文档集平均向量的方向向量，选择该方向上最显著的词项。
  - TF-IDF / BM25 统计：在伪相关文档集中，计算每个词项的平均 TF-IDF 分数。分数高的词意味着它在该文档子集中频繁出现，且对整个文档库是罕见的，很可能是主题相关的。
  - 基于语言模型的 KL 散度：比较伪相关文档集的语言模型与整个文档集语言模型的差异，选取差异最大的词作为扩展词。

4. 查询扩展与重检索：选择得分最高的 $M$ 个词（$M$ 通常为 5~30），将它们与原始查询词组合。最简单的组合是使用逻辑“OR”连接，或者为原始查询和扩展词赋予不同的权重（如原始查询词权重更高）。使用这个扩展后的查询 $Q_{new}$ 再次进行检索，得到最终结果。

优缺点与改进：

- 优点：全自动，不需要外部知识库，可以有效捕捉领域特有的同义和关联词汇，提升召回率。

- 缺点：极易受到“查询漂移”的影响。如果初检索的结果中混入了不相关的文档（例如，查询是“苹果”，初检索召回了大量“苹果公司”的文档，但用户本意是水果），那么从中提取的关键词就会严重偏向错误主题，导致第二次检索结果完全偏离用户意图。

如何在 RAG 中应用：

- PRF 通常更适合在稀疏检索（BM25）上使用，以弥补其词汇不匹配的缺陷。

- 可以与稠密检索结合：先用稠密检索保证初检结果的质量，降低 PRF 引入噪音的风险，然后再用 PRF 扩展查询，进行 BM25 二次检索，融合结果。

- 一个现代的改进是 基于生成模型的 PRF：不直接提取关键词，而是将初检的前几篇文档内容作为 Prompt 的一部分，让 LLM 直接生成相关的扩展查询。

#### 如何避免查询重写导致语义偏移或引入噪声？有哪些质量检查手段？

查询重写虽然强大，但始终存在风险：改写后的查询可能偏离用户的原始意图，或者引入不必要的噪音，反而降低了检索质量。确保重写质量需要多层次的检查和保障。

避免语义偏移和噪音的策略：

1. 在设计阶段进行约束：
  - 保守的重写策略：对于高风险场景，重写应以“补充”为主而非“替换”。保留原始查询的全部信息，只进行指代消解和核心实体补充，不做大幅度的措辞改变。
  - 高质量的 Prompt 工程：在提示词中明确要求 LLM “保持原始语义不变”、“不要引入新的或不相关的实体”、“如果无法确定，保留原样”。提供反面示例。
  - 指令微调：如果使用微调模型，训练数据中必须包含大量保持语义不变的改写对，并且要惩罚引入噪音的改写。

2. 过程中的质量检查：
  - 语义相似度校验：计算原始查询和重写后查询的向量余弦相似度。如果相似度过低（如 < 0.8），则可能发生了语义偏移，应丢弃或降低重写版本的权重。
  - 基于 LLM 的自我验证：使用同一个 LLM 进行验证。Prompt 为：“原始查询是A，重写后的查询是B。请判断B是否保持了A的核心意图？只回答‘是’或‘否’。” 如果答案为“否”，则回退到原始查询。
  - 实体一致性检查：如果原始查询中有明确的实体（如人名、日期），重写后这些实体必须仍然存在，或者被正确替换。

3. 检索后的效果评估：
  - 多版本融合：同时使用原始查询和重写查询进行检索，通过 RRF 或分数加权融合结果。这样即使重写版本偏移，原始查询仍然可以提供安全垫。
  - 监控检索质量指标：上线后，持续监控重写查询带来的 Recall@K 和 nDCG 变化。如果发现某些类型的查询指标下降，及时分析并调整重写策略。

最佳实践：始终将原始查询作为基线。重写查询应该被视为提升性能的“增强器”，而不是完全替代品。通过多版本检索和语义校验，可以在提升检索效果的同时，有效控制风险。

#### 并发查询多个重写版本，然后合并结果，这种做法有何优势及成本？

并发查询多个重写版本，是一种用计算资源换取检索鲁棒性和高召回率的策略。它利用 LLM 生成同一查询的多个不同表述，然后对每个表述分别执行检索，最后合并所有结果。

优势：

1. 最大化召回：单个重写查询可能存在偏向或不完整，而多个版本从不同角度覆盖了用户意图。例如，原始问题是“如何让我变得更快乐”，版本1可能是“提升幸福感的方法”，版本2可能是“保持积极心态的技巧”，版本3可能是“改善情绪的科学建议”。这些不同表述能命中不同措辞的相关文档，大大降低了遗漏的风险。

2. 提高鲁棒性：如果某一个重写版本质量不佳（如引入噪声或语义偏移），其他高质量的版本仍然能提供稳定的检索结果。通过融合，系统不会因为一次糟糕的重写而性能崩溃。

3. 覆盖多意图：用户的查询有时隐含多个子意图。生成多个版本可以显式地将这些子意图拆分开来。例如，“我想了解A和B”可以生成“A的特点”、“B的特点”、“A和B的对比”。

4. 适应不同检索器的特性：可以生成适合不同检索器的版本。一个简短的关键词版本给 BM25，一个更自然的句子给稠密检索，各取所长。

成本与挑战：

1. 检索成本倍增：这是最主要的代价。生成 N 个版本意味着需要执行 N 次检索（或至少 N 次向量搜索），检索时间、计算资源和 API 调用费用都成倍增加。

2. LLM 调用成本：生成多个版本需要 LLM 的额外调用，增加了首Token延迟和 Token 消耗。

3. 融合复杂性与噪音风险：合并多个结果列表需要更多的融合计算。同时，如果某个版本召回了大量不相关文档，可能会在融合后挤占高相关文档的排名。

工程优化：

- 并发执行：所有版本的检索完全并发，总延迟约等于最慢的一次检索时间。

- 共享粗筛结果：可以先由最快的版本进行初检，然后将融合结果共同送入一个精排模型。

- 选择性启用：不是所有查询都需要多版本检索。可以通过意图分类，只对复杂、模糊或关键任务启用。

并发查询多个重写版本，本质上是一种“用计算换质量”的策略。在对检索质量要求极高的场景（如关键业务决策），它是非常有效的手段。

#### 在工具使用或 API 检索的 RAG 中，查询重写如何将自然语言转换为结构化查询？

在工具使用或 API 检索的 RAG 场景中，用户的自然语言查询需要被转换为机器可执行的、结构化的 API 调用或工具参数。这个转换过程本身也是一种高级的查询重写，它将“模糊的意图”转化为“精确的指令”。

实现路径：

1. 基于 Function Calling 的重写：\
   现代 LLM 已具备强大的 Function Calling 能力。系统预定义好一组工具或 API 的函数签名（包括函数名、描述、参数名和参数类型）。当用户输入自然语言查询时，LLM 并不直接输出重写后的文本，而是输出一个符合函数签名的 JSON 对象，例如 `{"name": "search_products", "arguments": {"keyword": "无线耳机", "max_price": 500}}`。这本质上是一种高度结构化的查询重写。模型的提示中包含了所有可用工具的描述，它能够自动选择最合适的工具并填充参数。

2. 基于意图分类与槽位填充：\
   对于无法直接使用 Function Calling 的模型或场景，可以采用经典的 NLP 管道。首先，对用户查询进行意图分类（例如，是“产品搜索”、“订单查询”还是“售后投诉”）。然后，针对该意图，使用命名实体识别和槽位填充技术，提取出关键信息（如产品名、日期、订单号）。最后，将这些信息填入预设的结构化查询模板中，例如 `SELECT * FROM orders WHERE order_id = '...' AND status = '...'`。

3. 基于 LLM 的 Text-to-SQL：\
   当工具是关系型数据库时，查询重写变成了 Text-to-SQL 任务。将用户的自然语言问题，连同数据库的 Schema 描述（包含表名、字段名、字段类型和示例值）一起送入 LLM，要求其生成一条对应的 SQL 查询语句。这是目前最强大的结构化查询重写方式，不仅能进行简单过滤，还能进行聚合、连接等复杂操作。

4. 面向 API 的自然语言重写：\
   如果工具是 RESTful API，而 LLM 不支持原生 Function Calling，则可以让 LLM 直接生成 API 请求的 URL 和参数。例如，提示：“用户的请求是‘查一下北京明天的天气’，请将其转换为天气API的查询URL。API格式为 `/weather?city=<城市>&date=<日期>`。”

质量保障：

结构化重写必须确保参数的正确性和安全性。通常会在执行前进行语法校验（如 JSON/URL 格式校验）和参数白名单过滤，避免注入攻击和非法参数。对于关键操作，还需要用户二次确认。

#### 子查询分解：如何将复杂问题分解为多个子问题，然后分别检索？

子查询分解（Sub-query Decomposition）是解决复杂多跳推理问题的关键技术。它将一个需要综合多份信息才能回答的复杂问题，拆解为一系列更简单、更易于检索的子问题，然后分别检索、汇总结果，最后生成答案。

分解方法：

1. 基于 LLM 的逐步分解：\
   使用一个强大的 LLM（如 GPT-4）并设计专门的提示词，将复杂问题分解为检索顺序。提示词可以要求 LLM：“请将以下复杂问题分解为多个简单的、可以独立检索的子问题。按照需要回答的顺序排列。”例如，对于问题“2023年奥斯卡最佳影片的导演的妻子是谁？”，LLM 会分解为：
  - 子问题1：2023年奥斯卡最佳影片是什么？
  - 子问题2：这部影片的导演是谁？
  - 子问题3：这位导演的妻子是谁？\
    这三个子问题可以顺序执行，也可以将不依赖其他结果的子问题并行执行。

2. 基于图的检索与推理：\
   对于极度复杂的问题，可以构建一个思维图或状态图。将每个子问题的检索结果作为新的上下文，用于生成下一个子问题，或者修正原有的分解计划。这种动态交互式分解比静态的一步分解更强大。

3. 少样本提示与 CoT 结合：\
   在提示中给出一个或两个复杂问题分解的示例，引导 LLM 学会分解模式。同时，要求 LLM 在分解前先写出它的推理计划（Chain-of-Thought），这能显著提高分解的合理性和准确性。

检索与结果合并：

- 串行执行：适用于有严格先后依赖关系的子问题。

- 并行执行：对于相互独立的子问题，可以并发检索，降低总延迟。

- 迭代执行：检索到第一个子问题的结果后，将其反馈给 LLM，让它判断是否需要调整后续子问题，或者是否需要进一步的检索。

检索完成后，系统会将各个子问题的检索结果（通常是文档片段）按照原始问题的逻辑顺序组织起来，和原始问题一起送入最终的生成模型，得到综合性的答案。

子查询分解能够将模型的复杂推理能力与检索系统的高效查找能力深度结合，是解决多跳问答的利器。

#### 查询重写的延迟分析：引入 LLM 重写会显著增加响应时间，如何优化？

引入 LLM 进行查询重写，会直接在 RAG 管道的入口处增加一个 LLM 推理步骤，这确实会显著增加端到端的响应延迟，尤其是在在线服务中。这种延迟主要由模型推理时间、网络传输时间和排队等待时间组成。

优化策略：

1. 模型侧优化：
  - 使用轻量级专用模型：不要使用巨无霸模型进行重写。训练或蒸馏一个专门的重写小模型（如 LLAMA-7B, T5-small），仅需几十毫秒即可完成推理，延迟远低于通用大模型。
  - 本地化部署与推理加速：将重写模型部署在本地 GPU 集群，消除网络延迟。使用 TensorRT-LLM、vLLM 等高性能推理框架，并应用 INT8 量化、FlashAttention 等技术，将推理时间压缩到极致。
  - 投机解码：如果使用大模型，可以采用投机解码技术，用小模型快速生成候选 token，再由大模型验证，降低平均延迟。

2. 管道优化：
  - 预测性缓存：对高频查询及其重写结果进行缓存。用户查询进来，先查缓存，命中则直接使用缓存的重写结果，跳过模型推理。
  - 异步解耦与流式处理：将查询重写与后续的检索步骤解耦为异步任务。在等待重写结果的同时，可以先用原始查询进行预检索。当重写完成后，再进行第二次检索，二者结果合并。对于流式输出，可以在后台异步完成重写，先返回基于原始查询的结果，再用重写后的结果进行补充和更正。
  - 选择性启用：不是所有查询都需要重写。训练一个轻量级的路由器（Router），判断当前查询是否需要重写。对于简单、明确的查询，直接跳过重写步骤。

3. 重写策略优化：
  - 限制生成长度：在 Prompt 中明确限制 LLM 输出的最大 Token 数，防止模型生成冗长的解释。
  - 批量重写：如果系统负载允许，可以将短时间内聚集的多个查询打包成一个 Batch，同时进行重写推理，提升 GPU 利用率和吞吐量。

通过上述方法，可以将 LLM 重写的额外延迟控制在数十毫秒内，使其在实际在线服务中可行。

#### 是否有专门训练的查询重写模型，而非依赖通用 LLM？

是的，专门训练的查询重写模型不仅存在，而且在很多场景下比通用 LLM 更优。这些专用模型参数量小、推理快、领域专注度高，是工程化部署的理想选择。

专用模型的类型：

1. 基于序列到序列的神经重写模型：\
   最经典的是使用 T5 或 BART 等 Seq2Seq 架构，在大量“用户查询-重写查询”对上进行微调。训练数据可以来自人工标注、用户点击日志（将用户的点击文档对应的查询作为重写目标）或通过大模型蒸馏而来。这些模型经过训练，可以将对话式、口语化的查询直接转换为关键词或标准检索查询。例如，Google 在其搜索中使用了类似的查询重写技术。

2. 用于对话消解的专用模型：\
   在多轮对话中，有专门用于指代消解和省略恢复的模型。它们通常基于预训练的对话模型，在特定的多轮对话数据集上进行微调，输入是对话历史与当前问题，输出是独立的查询语句。这种模型比通用 LLM 更适合处理口语化的、碎片化的对话历史。

3. 查询扩展的专用模型：\
   像 Doc2Query 这样的模型，虽然是用于文档扩展，但它的反向思路被应用于查询扩展。可以训练一个模型，输入用户查询，输出一系列相关的扩展词项。这些词项可以直接追加到原查询后用于 BM25 检索。

优势：

- 低延迟与低成本：参数量小，推理速度极快。

- 领域专用：可以针对特定领域（如电商、法律）的数据进行微调，学习该领域特有的术语和改写模式，效果远超通用 LLM。

- 稳定与可重复：确定性输出，不会像 LLM 那样产生随机性或幻觉。

实现路径：

可以先用通用 LLM 生成大量的查询重写对，以此作为“伪标注”数据，然后蒸馏出一个轻量级的 T5 或 MiniLM 学生模型，经过验证后部署上线。

#### 如何评估查询重写的质量？有哪些自动指标和人工标准？

评估查询重写质量，需要从多个维度综合衡量，确保改写后的查询既保留了原意，又提升了检索效果。评估分为自动指标和人工标准两个层面。

自动指标：

1. 检索性能指标：\
   这是最核心的评估方式。将原始查询和重写后的查询分别送入检索系统，对比它们的检索结果质量。
  - Recall@K：重写后查询的召回率是否高于原始查询。
  - nDCG@K / MRR：重写后查询的排序质量是否更优。\
    这是任务导向的评估，直接衡量重写对下游任务的价值。

2. 语义相似度指标：\
   计算原始查询向量与重写查询向量的余弦相似度。
  - 过高（如 > 0.95） 可能意味着改写不足，没有带来新信息。
  - 过低（如 < 0.8） 则可能发生了语义偏移。\
    一个理想的重写查询应该在语义上和原查询高度相关，但措辞又有足够差异。

3. 词汇重叠度指标：
  - Jaccard 相似度：衡量原查询与重写查询的词项集合的重叠度。期望是部分重叠，但又有新增的、有信息量的词项。
  - BERTScore：基于上下文嵌入的相似度评估，能更好地捕捉语义等价性。

4. 查询特异性与长度指标：
  - 长度变化：重写后查询通常应该比原始查询更长、更具体。
  - 实体密度：关键实体是否被正确保留并显式地补充。

人工标准：

1. 意图保持度：人工评估重写后的查询是否完整、准确地保留了用户的核心意图。

2. 独立可理解性：在多轮对话重写中，评估生成的查询是否脱离了历史也能被独立理解，指代和省略是否被正确消解。

3. 信息增益：重写是否增加了有助于检索的、合理的上下文或关键词，而非无关噪音。

4. 流畅性与可读性：查询是否自然流畅。

最佳评估实践：结合自动指标和人工抽检。先通过自动指标（如 Recall@K）快速筛选出性能不佳的重写案例，再对它们进行人工分析，找出问题根源（如意图偏移、噪音引入）。

#### 在领域特定 RAG 中，查询重写如何融入领域术语和知识？

领域特定 RAG（如医学、法律、金融）的核心挑战之一是术语的准确性和概念的映射。通用查询重写模型往往不了解这些领域的专业表达，因此必须进行领域适配。

融入领域术语与知识的方法：

1. 构建领域知识增强的提示词：\
   如果使用 LLM 进行重写，可以在 Prompt 中注入领域知识。例如，在指令中说明：“在改写时，请将‘心脏病’的标准医学术语映射为‘冠状动脉粥样硬化性心脏病’。如果用户提到‘心梗’，请改写为‘急性心肌梗死’。”也可以提供一个简短的领域术语表作为上下文。

2. 基于领域数据微调重写模型：\
   收集或构造该领域的查询重写对。这些数据可以来自：
  - 领域专家的标注。
  - 该领域搜索引擎的点击日志。
  - 从领域文献中提取的同义词、缩写、全称映射关系，然后通过规则生成训练对。\
    使用这些数据微调一个轻量级的 Seq2Seq 模型，使其学会领域特有的重写模式。

3. 结合知识图谱进行实体和概念映射：\
   在重写管道中集成一个领域知识图谱。系统首先对原始查询进行实体识别，然后链接到知识图谱中的标准实体，获取其实体的官方名称、缩写、相关属性。这些标准化的信息直接被注入到重写后的查询中。例如，用户查询“吃点布洛芬行吗”，系统将其重写为“布洛芬 适应症 用法用量”，其中“布洛芬”就是标准化的药物实体。

4. 使用检索增强的重写：\
   先对原始查询进行一次初检，从领域文档库中找回最相关的几篇文档。将这些文档的标题或摘要作为上下文，提供给 LLM，要求它基于这些专业文献的措辞来重写查询。这使得重写结果与领域文档的表述方式高度对齐。

通过这些方法，领域特定的 RAG 系统能够将用户的日常用语精准地映射到专业文档的语言空间，显著提升检索的准确率。

#### 查询重写能否纠正用户查询中的事实错误？这样做是否合适？

这是一个涉及安全、伦理与产品定位的复杂问题。技术上，LLM 可以在重写时“纠正”明显的事实错误（例如，用户问“爱因斯坦发明了电灯吗？”，重写为“电灯的发明者”），但这种做法在大多数情况下并不合适，且风险极高。

技术可行性：

LLM 拥有庞大的参数化知识，能够识别出许多常见的事实错误，并在重写时进行“修正”。它可以生成一个更符合事实的查询，从而检索到更准确的文档。

为什么这样做不合适：

1. 剥夺用户的修正权与知情权：如果用户本身对某个事实存在误解，一个负责任的系统应该引导他发现真相，而不是在背后悄悄修改他的问题，然后给他一个他可能无法理解的答案。这会造成困惑。

2. 错误纠正本身可能出错（幻觉）：LLM 的知识是有限的且可能过时，它自己的“纠正”也可能是错误的。如果系统自以为是地修改了一个正确的查询，用户将得到一个完全错误的答案，而他却毫不知情，信任将荡然无存。

3. 违背用户意图：用户可能并不是在陈述事实，而是在进行反问、假设、引用或测试。例如，“有人说地球是平的，你怎么看？”如果系统重写为“地球是球形的科学证据”，就彻底丢失了用户对话的语境。

合适的做法：

查询重写应只做“意图澄清”和“表述优化”，而不是“事实修正”。当系统检测到用户查询中可能包含事实错误时，最佳实践是：

- 保持原查询不变，确保检索结果能反映用户的原始表述。

- 在生成回答的阶段，通过检索到的权威文档，礼貌地指出事实并提供正确的信息。例如：“关于电灯的发明者，普遍认为是爱迪生，他改进了电灯并使其商业化。”

- 或者，生成一个并行的探索性查询，比如在后台同时搜索“电灯发明者”，但其结果用于生成答案时的补充说明，而不是替代用户的主查询。

总之，重写阶段应扮演“忠实的传话人”，而非“知识的仲裁者”。

#### 对比查询扩展中的“关键词提取 + 同义词替换”与“用 LLM 生成变体”的优劣。

这两种方法代表了传统 NLP 与现代生成式 AI 在查询扩展上的两条路径。

| 维度 | 关键词提取 + 同义词替换 | 用 LLM 生成变体 |
| --- | --- | --- |
| 原理 | 基于规则、词典或统计特征。先提取核心关键词，再通过词汇资源查找同义、上下位词进行替换或增补。 | 基于深度学习，输入原始查询，使用生成模型直接生成多个语义相同但表述不同的完整查询句子。 |
| 优势 | 速度快、成本极低：无需 GPU，可在 CPU 上快速完成。<br>可控性高：可以精确控制扩展哪些词、扩展多少个。<br>可解释：每个扩展词的来源清晰。 | 语义理解强：能进行抽象、释义和语境化改写，而不仅仅是词级别的替换。<br>灵活度高：能处理复杂句式、否定、多义词消歧。<br>语言流畅：生成的查询自然流畅。 |
| 劣势 | 召回天花板低：只能处理词级别，无法应对句式结构差异和深层次的语义鸿沟。<br>词表维护成本高：需要根据领域不断更新同义词表。<br>易引入噪音：多义词的盲目替换可能改变原意。 | 成本高、延迟大：需要 GPU 推理，耗时较长。<br>可解释性差：无法解释为何生成某个变体。<br>可能产生幻觉：可能生成与原意偏离的查询。 |
| 适用场景 | 对延迟极度敏感、资源受限、领域封闭且词汇表相对固定的场景。 | 对检索质量要求极高、需要深层次语义匹配、能够接受计算开销的通用或复杂场景。 |

实践中，两者常常结合：

先用规则方法进行稳健的实体替换和拼写纠错，然后将结果输入一个轻量级的、经过蒸馏的生成模型，在保证基础准确性的同时，进行更深层的语义改写。

#### 在多语言 RAG 中，查询重写能否实现跨语言检索？如将中文查询改写为英文关键词。

完全可以，这是查询重写在多语言 RAG 中的一个重要应用——跨语言查询翻译与改写。

实现机制：

- 直接翻译重写：提示 LLM：“请将以下中文查询改写为适合英文文档检索的英文关键词。” LLM 会利用其多语言能力，直接将中文查询翻译并重写为英文检索词。例如，“最新的可再生能源技术” -> “latest renewable energy technologies”。

- 多语言关键词生成：更强大的做法是，让 LLM 同时生成中、英两种语言的查询，然后分别在不同语言的索引中进行检索，最后合并结果。这能最大化跨语言的信息覆盖。

- 利用多语言嵌入模型的对齐能力：将中文查询通过多语言 Embedding 模型直接生成英文语义空间的向量，然后用这个向量去检索英文文档库。这本质上是跨语言检索，无需显式的文本重写，但它依赖于 Embedding 模型的跨语言对齐质量。结合查询重写，可以同时利用翻译后的文本进行 BM25 检索，多路融合。

优势：

- 打破了语言壁垒，使用户可以用自己最熟悉的语言，检索全球的文档库。

- 重写后的查询更贴近目标语言的文档表述习惯，提高了检索的准确率。

挑战与优化：

- 专有名词与缩写：需要确保人名、地名、专业术语被正确翻译，或保留源语言形式。

- 领域适配：不同语言的领域术语可能并不完全对应，重写时需要结合领域知识库进行映射。

- 延迟：跨语言重写增加了推理步骤，需要通过模型优化来控制。

#### 如何防止查询重写使查询变得过于宽泛或偏离用户本意？

防止查询重写后变得宽泛或发生语义偏移，是一个质量控制的持续过程，需要在重写策略、模型设计、后处理验证和反馈闭环等多个层面设置防线。

核心策略：

1. 在 Prompt 与训练中施加约束：
  - 明确指令：在重写提示中强调“保持原始查询的核心意图不变”、“不要添加不相关的信息”、“重写后的查询应该是一个更精确的检索版本，而不是一个更泛泛的话题”。
  - 反面示例：提供将查询错误地泛化或偏移的示例，并指出其问题，让模型学会规避。
  - 限制生成长度：过于冗长的重写往往容易离题。

2. 后处理验证与过滤：
  - 语义一致性检验：计算原始查询与重写查询的向量余弦相似度。如果相似度低于一个安全阈值，则丢弃重写版本，回退到原始查询。
  - 关键词实体校验：检查原始查询中的关键实体（特别是专有名词、数字、日期）在重写查询中是否仍然存在。如果关键实体丢失，说明可能发生了漂移。

3. 检索结果侧的双重校验：
  - 双路检索融合：同时使用原始查询和重写查询进行检索，将两路结果通过 RRF 等融合排序。这样即使重写版本偏离，原始查询的检索结果仍能提供安全垫。
  - 重排序模型把关：最终的检索结果会经过一个精排模型。如果重写导致召回了大量宽泛文档，精排模型会因其相关性低而将其排到后面，从而减弱其负面影响。

4. 迭代优化与反馈闭环：
  - 建立一个离线的评估集，定期对重写模型的表现进行回归测试。
  - 收集线上用户对最终答案的反馈（点赞/踩）。如果一个回答被踩，回溯分析是否是因重写导致检索结果偏离，并将这些案例作为新的训练数据，持续微调模型。

通过这种多层次的防御，可以最大程度地保证重写后的查询既精准又忠实于用户的初衷。

#### 能否将查询重写与 embedding 模型结合，生成重写后的查询嵌入直接检索？

可以，而且这一思路正在被许多前沿的 RAG 系统采用。它的核心是：不显式生成文本形式的查询，而是让模型直接生成一个更“理想”的查询向量，用于在向量空间中检索。

实现方式：

1. 基于指令的 Embedding 模型：\
   使用指令微调的 Embedding 模型（如 Instructor-XL, BGE-M3），在查询时，将重写的逻辑以“指令”的形式注入。例如，查询的输入变成：“为以下用户问题生成一个用于检索相关文档的向量表示，请重点关注其中的人名和日期：<用户问题>”。模型会根据指令，在生成向量时动态地调整其语义表示，使其更贴近检索目标。这相当于在向量空间中完成了一次隐式的重写。

2. 基于生成模型的查询向量生成：\
   训练一个专门的模型，输入是原始查询（可能加上对话历史），输出不是一个重写后的文本，而直接是一个固定维度的稠密向量。这个模型在训练时，被优化为使得输出的向量能够最大化与相关文档的相似度，最小化与不相关文档的相似度。这类似于一个端到端的检索模型。

3. 多向量融合：\
   使用一个 LLM 生成多个文本形式的重写查询，然后分别用 Embedding 模型将它们编码为向量，最后将这些向量进行加权平均或 Pooling，形成一个融合后的综合查询向量。这种方法比单次文本重写更鲁棒。

4. 基于 LLM 的检索器（如 ColBERT 的变体）：\
   一些模型直接使用生成式 LLM 来生成文档的向量表示，这可以看作是最彻底的“生成式检索”，绕过了传统的查询-文档分塔架构。

优势：

- 消除了解码的延迟：直接生成向量，省去了文本生成（自回归解码）的步骤，速度更快。

- 更强的特征融合：模型的内部状态可以直接用于生成向量，信息保留更充分。

挑战：

- 训练复杂：端到端的向量生成模型需要精心设计损失函数和大量训练数据。

- 可解释性差：无法看到重写后的文本，出了问题难以调试。

总之，将查询重写与 Embedding 模型深层结合，代表着 RAG 检索模块的进化方向，即从“显式文本改写”走向“隐式语义映射”，以更高的效率实现更精准的检索。
