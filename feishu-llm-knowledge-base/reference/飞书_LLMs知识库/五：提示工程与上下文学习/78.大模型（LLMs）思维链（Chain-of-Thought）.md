# 78.大模型（LLMs）思维链（Chain-of-Thought）

#### 什么是思维链提示？写出一个标准的 CoT 示例，展示推理步骤。

思维链提示是一种专为增强大语言模型复杂推理能力而设计的提示技术。其核心是在少样本示例或指令中，显式地展示从输入到最终输出之间的一系列中间推理步骤（即“思维链”），从而引导模型在面对新问题时也模仿这种逐步推导的过程，而非直接输出最终答案。

通过将隐性推理过程外化为自然语言序列，CoT 将原本需在模型内部一步完成的“黑盒映射”，分解为多个可被自回归生成逐段处理的简单步骤，大幅提升了多步逻辑、数学计算和常识推理等任务的准确性。

标准 CoT 示例（数学应用题）：

```plain text
问题：小明有 5 个苹果，他给了小红 2 个，然后又买了 3 个苹果。小明现在有多少个苹果？
答案：6

问题：一个农场有 12 只鸡和 8 只兔。每只鸡有 2 条腿，每只兔有 4 条腿。农场总共有多少条腿？
答案：
```

上面的 prompt 仅有输入-输出对，是标准少样本。CoT 版本则会在答案前插入推理步骤：

```plain text
问题：小明有 5 个苹果，他给了小红 2 个，然后又买了 3 个苹果。小明现在有多少个苹果？
推理：小明最初有 5 个苹果，给出 2 个后剩余 5 - 2 = 3 个。再买 3 个，总共 3 + 3 = 6 个。
答案：6

问题：一个农场有 12 只鸡和 8 只兔。每只鸡有 2 条腿，每只兔有 4 条腿。农场总共有多少条腿？
推理：
```

模型将续写：

```plain text
鸡的总腿数：12 只 × 2 = 24 条腿。
兔的总腿数：8 只 × 4 = 32 条腿。
总腿数：24 + 32 = 56 条腿。
答案：56
```

通过提供包含推理链的示例，模型学会了在生成最终答案前展开中间计算，从而显著提升准确性。

#### CoT 为什么能提升复杂推理任务的性能？它的理论基础或直觉是什么？

CoT 提升复杂推理性能的原因可从计算、认知和模型机制等多个角度理解：

1. 增加有效计算深度

自回归模型每生成一个 token 都经过一次完整的前向传播。将推理过程拆解为多个中间步骤，等同于为最终答案分配了更多的计算量和“思考时间”。每个推理步骤的输出都成为下一步的条件，使得模型能够逐步构建通往正确答案的逻辑路径，避免了在单步内完成复杂映射的困难。

2. 分解问题，化繁为简

复杂推理任务通常需要多步逻辑操作。CoT 将原问题分解为一系列简单的子问题（如逐步算术运算、事实检索、逻辑推理），每个子问题对模型而言更容易解决。这种分解降低了问题的认知负荷，提高了正确率。

3. 引导注意力与信息流

生成的推理链在 Transformer 中形成了清晰的信息路径。后续 token 可通过注意力直接引用前序推理步骤中提取的关键信息和中间结果，避免了在隐藏状态中“默默”记忆所有中间量的困难。显式的中间变量提高了信息传递的效率。

4. 激活预训练中的推理模式

大规模预训练语料中包含大量带有推理过程的文本（如数学解题、论证、教程）。CoT 提示通过示例激活了这些潜伏的推理模式，使模型更可能生成符合逻辑的文本序列。它本质上是通过上下文学习“唤醒”模型内在的逐步推理能力。

5. 错误纠正与自校准

在推理链的生成过程中，模型有时能自我检测到前后矛盾，并在后续步骤中修正。虽然并非完全可靠，但比单步预测有更多机会纠正错误。

理论基础：CoT 可被视作一种上下文内程序执行。研究指出，Transformer 在上下文学习中能隐式构建线性模型或梯度下降步骤。CoT 将这种隐式学习拓展为显式的、可读的计算轨迹，使得模型能够在“思维纸”上逐步执行算法。

#### CoT 与标准少样本提示的核心区别在哪里？为什么“让我们一步一步思考”有效？

核心区别：

- 标准少样本提示：仅提供输入-输出对 `(x_i, y_i)`。模型被期望直接从输入映射到输出，中间推理过程完全在隐藏状态内完成，属于“黑盒”模式。

- 思维链提示：提供输入-推理链-输出三元组 `(x_i, reasoning_i, y_i)`。模型被明确要求生成中间推理步骤，将解题过程外化。这改变了任务的形式，从“给出答案”变为“展示推导过程并给出答案”。

为什么“让我们一步一步思考”有效？

这句话是零样本 CoT 的经典触发器。其有效性来源于以下几点：

1. 激活推理模式：经过指令微调的大模型已经将“逐步思考”等短语与详尽、结构化的回答方式关联起来。该短语作为一个强信号，促使模型采用不同于默认简洁回答的生成策略，即展开分析过程。

2. 引导输出格式：它暗示模型应该生成一个分步的、带有推导的响应。模型会倾向于模仿这种结构，导致实际输出中包含推理步骤，从而享受到 CoT 带来的计算和逻辑分解的好处。

3. 增加回答前的计算量：模型在生成“步骤”文本时，实际上在进行额外的计算和注意力操作，为最终的答案准备了更丰富的上下文表征。这些中间生成的 token 充当了辅助变量。

4. 普适性与简洁性：不需要针对每个任务手工设计示例，一句简单的话就能激发出强大的零样本推理能力，极大地降低了使用门槛。

因此，“让我们一步一步思考”起到了“零样本思维链开关”的作用，是提示工程中极富价值的发现。

#### CoT 是否在所有任务类型上都能带来提升？在哪些任务上可能无效甚至有害？

CoT 并非万能，其效果高度依赖任务特性。

提升显著的任务：

- 多步数学推理（如 GSM8K）：涉及多步数值计算，分解步骤至关重要。

- 符号推理（如最后一个字母拼接）：需要按步骤执行算法。

- 常识推理（如 StrategyQA）：需要检索多个背景知识并综合。

- 逻辑谜题与规划：需要推导链条。

无效或有害的任务：

- 简单任务：如基础情感分析、短文本分类、简单事实检索。对这些任务，CoT 引入冗长的推理过程不仅浪费 token，还可能产生无关的“过度思考”，引入噪声甚至幻觉，导致错误答案。例如，对“这部电影很棒，情感是什么？”生成一段分析后仍可能输出正确标签，但增加了延迟和成本，且如果分析中出现偏差反而可能带偏最终判断。

- 依赖直观或模式快速匹配的任务：某些语言流畅性任务、语法判断，模型无需推理，直觉即可正确。CoT 的显式分析可能扰乱这种直觉。

- 对格式要求极其严格的任务：如果任务期望输出必须是特定格式（如 JSON），CoT 可能导致模型在推理文本中迷失，难以抽取最终答案。

- 常识极度简单的任务：如果问题过于简单，推理步骤可能是空洞的赘述，无实质帮助。

结论：CoT 适用于需要非平凡推理深度的任务。使用前应评估任务复杂度：若零样本或标准少样本已近完美，则无需 CoT；若涉及多步逻辑，CoT 往往能带来质的飞跃。可通过小规模实验快速判断。

#### 自动 CoT（Auto-CoT）是如何避免手动编写示例的？简述其自动生成推理链的流程。

手动为每个任务编写高质量推理链费时费力。Auto-CoT 的核心思想是让 LLM 自己为示例生成推理链，从而自动化少样本 CoT 的构建过程。

Auto-CoT 的主要流程：

1. 示例聚类（问题多样性保证）
  - 将未标注的示例问题（只有问题，无答案）全部编码为向量。
  - 使用 K-Means 聚类，将问题划分为若干簇。每个簇代表一种问题类型或主题。
  - 从每个簇中选取一个代表性问题（如最靠近簇中心的那个）。

2. 零样本触发推理链生成
  - 对每个选出的代表性问题，使用零样本 CoT 提示（如“让我们一步一步思考”）让 LLM 生成推理链和答案。
  - 具体做法：构造 prompt `[问题]\n让我们一步一步思考：`，模型将返回推理过程及最终答案。

3. 构建少样本示例集
  - 将生成的 `(问题, 推理链, 答案)` 组合作为示例。
  - 由于问题来自不同簇，这些示例自然具有多样性，覆盖了不同类型的推理模式。

4. 最终推理
  - 将这些自动生成的示例与新的测试问题组合成少样本 CoT prompt，交给 LLM 进行推理。

优势：

- 无需人工标注推理链，全自动。

- 聚类保证了示例的多样性，避免了单一类型示例带来的偏差。

- 可以轻松扩展到大批量任务。

注意事项：

- 零样本生成的推理链可能包含错误，这些错误会作为示例传播。Auto-CoT 可通过生成多条推理链并投票（自洽性）或利用简单启发式规则（如答案是否合理）进行筛选，过滤掉低质量示例。

- 对于需要外部知识的任务，LLM 零样本生成的推理链质量可能受限，仍不如人工编写。

Auto-CoT 使得 CoT 的大规模应用成为可能，是自动化提示工程的重要里程碑。

#### 零样本 CoT 与少样本 CoT 的效果差异及适用场景。

| 维度 | 零样本 CoT | 少样本 CoT |
| --- | --- | --- |
| 提示方式 | 仅添加“让我们一步一步思考”或类似指令，不提供示例 | 提供多个包含推理链的完整示例 |
| 效果差异 | 在多数推理任务上明显优于零样本无 CoT，但通常弱于精心设计的少样本 CoT，尤其在需要特定格式或复杂推理模式时 | 通常更强，因为示例直接展示了期望的推理风格、步骤粒度和输出格式 |
| 适用场景 | 快速原型验证、没有标注示例、任务相对通用、或需要极简 prompt 的场合。极其方便，一句指令即可激活推理能力 | 追求最高性能、任务格式特殊（如特定逻辑推导模板）、需要严格控制推理质量时。示例可固化任务规范 |
| 稳定性 | 对指令措辞稍敏感（不同的“逐步思考”表述效果可能不同） | 示例若覆盖全面，性能稳定；但示例选择不当可能引入偏差 |
| 成本 | Prompt 短，推理成本相对低 | Prompt 较长，推理成本稍高（输入 token 多） |
| 示例依赖 | 零依赖 | 强依赖示例质量与多样性 |

选择指南：

- 如果没有标注的推理链，或者想快速测试 CoT 对某任务的提升幅度，先用零样本 CoT。

- 如果追求上线性能，或需要定制推理过程（例如必须按“法律→事实→结论”格式推导），则投入精力构建少样本 CoT。

- 两者可以结合：用零样本 CoT 自动生成一批推理链，人工或自动筛选后，作为少样本示例使用（类似 Auto-CoT 的思路）。

#### CoT 推理链的长度、细节程度对最终答案正确性的影响。

推理链的长度和细节程度对正确性具有倒 U 型或递增收益影响，需要适度控制。

影响分析：

- 过短或过于简略的推理链：跳过关键中间步骤，导致信息不完整，模型可能无法正确完成逻辑跳跃，错误率较高。这与直接给出答案的效果接近，未能充分发挥 CoT 优势。

- 适度详细、完整的推理链：包含必要的中间计算和逻辑推导，能显著提升准确性。每一步都是对前一步的验证和基础，形成稳固的推理阶梯。

- 过于冗长或冗余的推理链：
  - 收益递减：额外的非必要细节可能无益，但通常不会明显降低准确率（强模型可忽略冗余）。
  - 潜在危害：可能引入无关信息或离题内容，增加模型“走神”或产生幻觉的风险。对弱模型，过长的上下文可能导致注意力分散，丢失关键信息。
  - 效率问题：生成过长推理链浪费 token，增加延迟和成本，并可能挤占上下文窗口，减少可用于示例的空间。

最佳实践：

- 以任务必要步骤为准：推理链应包含解题所需的所有逻辑环节，不跳过，也不铺陈。

- 风格精炼：使用清晰、直接的数学表达式或简洁的自然语言，避免修辞性废话。

- 在示例中示范理想长度：少样本 CoT 中，示例的详细程度直接教会模型以何种粒度进行推理。通过调整示例，即可控制生成链的长度。

- 自洽性（Self-Consistency）辅助：即便推理链较长，结合采样多个推理路径并投票，可以抵消个别路径冗余带来的错误。

因此，推理链的设计追求的是必要且充分的信息量，均衡准确度与效率。

#### 思维链中的错误传播：当中间步骤出错时，最终答案是否一定错？如何缓解？

在 CoT 中，推理是串行生成的。中间步骤出错极大概率导致最终答案错误，因为后续步骤往往基于前面的中间结果。这就是错误传播（Error Propagation）。错误可能是计算错误、逻辑跳跃错误或事实引用错误。

是否一定错？

不一定绝对。存在少数情况模型在后文中进行了自我修正（例如“等一下，我重新算一下”），但这不是稳定属性，不能依赖。绝大多数情况，一个关键中间错误会直接导致答案偏离。

缓解措施：

1. 自洽性（Self-Consistency）\
   生成多条独立的推理链（可通过设置较高温度采样获得多样性），然后取出现次数最多的最终答案。即便个别链出错，多数正确的链仍能主导投票结果。这是最有效、最常用的方法。

2. 验证与回溯提示\
   在指令或示例中加入验证步骤，例如“检查每一步计算的正确性”、“如果发现错误请纠正”。这提示模型在生成过程中进行自我监控和修正。

3. 最小化步骤间的依赖\
   设计推理格式时，尽量让每一步的计算独立可验证。例如，将大问题拆分为多个并列子问题，分别求解后再汇总，减少错误级联。

4. 外部工具辅助\
   对数学计算，可让模型生成计算表达式而非直接算出数值，然后由外部计算器（如 Python 解释器）得出精确结果，再返回给模型继续推理。这彻底消除了算术错误传播。

5. 更强大的模型\
   更大、更强的模型在推理时的自我纠错能力略强，但这并非根本解决方案。

6. 优化示例\
   在少样本 CoT 中，提供展示了“发现错误并纠正”的示例，教会模型这一行为模式。

综上所述，错误传播是 CoT 的内在弱点，必须通过集成投票、工具使用和自验证机制来增强可靠性，不能寄望于单次推理的完美正确。

#### 如何设计 CoT 提示，使得模型不仅给出答案，还能输出可验证的推理过程？

为了让推理过程可验证（甚至可执行），需要从提示设计上对模型的输出进行结构化和形式化约束。

设计方法：

1. 强制结构化输出格式\
   在指令中明确要求推理过程遵循特定的标记和字段，例如：

```plain text
你必须按以下格式输出：
推理步骤：
1. [第一步推理]
2. [第二步推理]
...
最终答案：[答案]
```

使用 XML 标签、Markdown 标题或 JSON 也有效。结构化使程序能自动解析出推理和答案，便于后续验证。

2. 要求生成可执行代码或表达式\
   对于数学或逻辑问题，可要求模型输出 Python 代码或数学表达式，而非纯自然语言推理。例如：

```plain text
对于每个数学问题，生成 Python 代码进行计算，用 print() 输出结果。
```

生成的代码可由外部解释器执行，结果精确可验证。这也是 PAL（Program-Aided Language）模型的核心思想。

3. 引用来源与事实基础\
   对于问答任务，要求模型在推理中明确引用前提条件或已知事实。例如：“根据给定的段落 2，我们可知...”。这使推理过程可被溯源，验证其事实依据。

4. 加入验证步骤作为必需环节\
   在提示模板中固定包含一个“验证”步骤，强制模型在得出最终答案前检查自己的推理。例如：

```plain text
推理：...
验证：检查上述推理是否有误，并给出验证结果。
最终答案：...
```

这虽不能完全杜绝错误，但提供了自我质疑的机会，并输出了验证轨迹。

5. 使用少样本示例示范可验证推理\
   示例中的推理必须严格遵循上述格式，模型会模仿这种带验证的结构。

6. 结合外部知识库或工具\
   提示模型在需要事实时调用搜索工具，在需要计算时调用计算器，将推理过程与外部可靠信息结合，使其步骤根基扎实，更可验证。

通过这些设计，CoT 输出从自由文本转变为包含明确逻辑、可被自动检查的透明推理记录，极大提升了模型在关键应用中的可信度和实用性。

#### 比较 CoT 与 Self-Consistency 的组合使用方式，能带来多大提升？

CoT 与 Self-Consistency 的组合是当前提升 LLM 推理准确率最经典、最有效的方式之一，它的威力来自于把“思考深度”和“思考广度”结合起来。

组合方式的具体运作

标准的 CoT 是一次生成一条推理路径，然后给出最终答案。这里面有个隐患：模型在每一步生成时都有一定概率出现小偏差，尤其是算术计算、逻辑跳步或事实引用错误。一个步骤错了，后面就会沿着错误方向越走越远。Self-Consistency（自洽性）的解决办法是：不把鸡蛋放在一个篮子里。我们在解码时故意设置较高温度（比如 0.7 甚至 0.8），并让模型独立生成多条推理链（例如 10 条、20 条），然后统计每条链得出的最终答案，选择出现频率最高的那个作为最终输出。

这种做法本质上是一种“多数投票”集成。它背后的直觉是：对于真正困难的问题，模型并不是完全不会，而是它的“思考”存在波动。让模型多思考几次，如果大多数思考路径都收敛到同一个答案，那么这个答案很可能是正确的；如果路径分散在不同答案上，说明问题确实超出了模型的稳定推理能力，此时即使选多数答案，也应当谨慎对待。

具体提升幅度

在 GSM8K（小学数学应用题）这类典型基准上，不加 Self-Consistency 的 CoT 准确率大概在 60%–70%（视模型而定）。加上 Self-Consistency 并采样 10 条路径，准确率可以提高到 75%–85%；采样 40 条甚至能达到 80%–90%。对于某些符号推理任务（如日期理解、字母拼接），提升幅度同样显著，经常有 8–15 个百分点的绝对提升。

需要注意的是，提升并非线性增长。从 1 条到 5 条的边际收益最大，5 条到 20 条收益递减，20 条以上逐渐饱和。此外，对于本身简单、模型已经几乎不会错的任务，Self-Consistency 几乎没有帮助，反而白白浪费计算资源。

工程上的代价与实用策略

这种组合的最大代价是推理成本成倍增加：生成 10 条路径相当于 10 次推理。因此在实际系统中必须做取舍：

- 对延迟敏感的场景（如实时对话），可以只用单次 CoT，并通过流式输出改善用户体验。

- 对精度敏感但延迟可接受的后台批处理（如试卷批改、数据分析），可以启用 Self-Consistency。

- 可以采用自适应策略：先用单次 CoT 生成答案，同时输出模型的置信度（如平均 token logprob），若置信度低于阈值，再触发额外的采样投票。这样兼顾了效率与准确率。

总结

CoT + Self-Consistency 组合将“一次深思”变为“多次深思后投票”，在不改变模型本身的情况下，借助计算量换取准确率，是 LLM 推理能力的最强实用技巧之一。

#### 在代码生成或数学证明任务中，CoT 需要怎样适配？

代码生成和数学证明都属于对准确性要求极高、输出具有严格形式约束的任务。直接将通用 CoT 套用过来，往往效果不佳，必须进行专门的适配。

代码生成任务的 CoT 适配

代码生成通常以函数签名和文档字符串为输入，输出可执行的程序。CoT 在这里的价值在于：让模型先理清逻辑，再动手写代码，而不是一气呵成地输出可能漏洞百出的程序。

适配要点：

1. 用结构化注释作为推理链：推理步骤可以用高层级的伪代码或注释形式呈现。例如，先写“# 步骤1: 遍历列表，找到最大值”，然后写出对应代码；接着“# 步骤2: 检查边界条件”，再写出代码。这样既实现了 CoT 的分步推导，又不破坏代码的语法。

2. 展示“思路-代码-测试”的完整流程：在少样本示例中，不仅给出最终代码，还要展示开发者是如何从题目要求出发，逐步推导出算法、编写代码、并且用简单用例跑一遍验证的。这样模型在生成时，也会模仿这种“思考-实现-自测”的闭环。

3. 结合可执行环境：这是最关键的一步。可以遵循 PAL（Program-Aided Language）范式，让模型生成的推理部分本身就是可执行的 Python 脚本。推理链即代码，最后直接运行得到精确结果，完全避免人工计算错误。例如数学题中不再用自然语言“12+34=46”，而是生成 `result = 12 + 34` 并由 Python 执行。

数学证明任务的 CoT 适配

数学证明要求逻辑严密，每一步都必须有依据，且不能有隐藏的跳跃。

适配要点：

1. 强制采用严谨的逻辑模板：少样本示例必须展示“已知条件 → 引用定理 → 推导结论”的固定模式。比如“由条件A，根据勾股定理得…”“因为…且…，由反证法假设…，矛盾，故原命题成立”。这种模板化能大幅减少模型“瞎编”的空间。

2. 分情况讨论的清晰展开：证明中常有分支情况，示例应展示如何用“情况1：…；情况2：…”的方式逐一处理，并在最后总结。

3. 嵌入自我验证步骤：要求模型在给出完整证明后，附加一个“验证”段落，检查每一步是否有逻辑漏洞，或者用具体数值代入验证。这种元认知提示能提升正确性。

4. 使用 LaTeX 或符号化表达：对于有公式的证明，引导模型使用 LaTeX 格式，不仅清晰，而且便于渲染和后续处理。需要注意的是，某些符号在 tokenization 时会被拆分，可能影响模型理解，需进行针对性测试。

共性适配原则

- 使用明确的标签（`<thinking>`, `<code>`, `<proof>`）将推理与最终输出分隔开，便于后处理提取。

- 示例必须完美无误：代码和证明中的示例如果有任何细微错误，都会被模型当作“正确答案范本”模仿，后果严重。

- 能调用外部工具时决不依赖模型自己的计算或知识，因为幻觉在这类任务中代价极高。

#### CoT 是否只适用于大型模型？小模型能否受益？其最小有效参数量大约是多少？

CoT 并非天生排斥小模型，但它的有效性与模型规模有非常强的关联。目前的主流结论是：CoT 是一种涌现能力，存在比较明显的规模门槛。

为什么小模型用 CoT 效果差

小模型（比如 1B–7B 参数）在生成长文本时容易出现几种问题：

- 逻辑连贯性差：模型容易在推理中途“忘记”最初的条件或目标，产生前后矛盾的步骤。

- 错误累积严重：小模型对每一步的准确性掌控更弱，一步错便步步错，而且缺乏自我纠错能力。

- 重复和退化：在长序列生成时，小模型容易陷入重复循环或者生成无意义内容，完全破坏推理链。\
  因此，对于小模型，强行加入 CoT 示例往往非但无益，反而可能因为生成了一条表面像样实则错漏百出的推理链，导致最终答案比直接猜测更差。这种现象在实验中被反复观察到：小模型在 CoT 下准确率可能反而下降 5–10 个百分点。

规模门槛大概在哪里

多项研究指出，CoT 开始展现正面效果的参数量拐点大致在 60B–100B 左右。例如，在 Google 的实验中，8B 参数的模型 CoT 没有帮助；62B 开始出现微弱提升；540B 的 PaLM 则从 CoT 中获得了巨大增益。OpenAI 的 GPT-3（175B）以及后续的 GPT-3.5/GPT-4 都是 CoT 的绝佳施展平台。

不过，这个门槛并不是绝对的。经过高质量指令微调的中等规模模型（例如 LLaMA-2-13B-Chat），在特定任务上也能从 CoT 中受益，尤其是当推理步骤被设计得非常简短、结构化时。这种受益更多来自于微调过程中对“逐步输出”格式的学习，而非真正的深度推理能力涌现。

让小模型部分受益的工程手段

如果必须在资源受限的小模型上使用 CoT，可以尝试以下方法：

- 任务专有微调：用大量人工或高质量自动生成的 CoT 数据对小模型进行微调，将推理能力“蒸馏”进去。此时 CoT 不再依赖上下文学习，而是成为了模型已学会的生成模式。

- 压缩推理链长度：将推理步骤压缩到极致，例如只用关键算式或关键词，避免生成大段自然语言。

- 结合外部工具：让小模型只负责输出调用工具的指令（如 calculator），把最易出错的算术部分外包，从而提升整体可靠性。

结论

原生 CoT 是巨型模型的“特权”。小模型若要在推理任务上受益，通常需要借助微调或工具增强，而不能仅靠添加“让我们一步一步思考”这类提示。

#### 思维链与“分治”思想的联系：如何用 CoT 解决多步规划问题？

CoT 与分治（Divide and Conquer）在哲学层面高度一致：都是将一个复杂、难以直接求解的大问题拆解为若干个更小、更易处理的子问题，逐个击破，再组合结果。CoT 所做的，正是将这种内在的解题策略外化为显式的自然语言步骤。

CoT 如何体现分治思想

在 CoT 的推理链中，模型通常会不自觉地执行以下阶段，这些阶段直接对应分治策略：

1. 问题理解和重述：将用户输入的目标用自己的话重新表述一遍，这相当于明确“我们要解决什么”。

2. 分解子问题：识别出完成目标需要满足哪些条件，或者需要先计算出哪些中间量。比如“为了知道总价，需要先分别计算商品价格和运费”。

3. 逐个求解子问题：对每个子问题独立进行推理或计算。这期间可能会产生多条并行的推理线，或者顺序依赖的步骤链。

4. 合并与得出结论：将各个子问题的答案汇总，形成最终答案。例如“商品总价 85 元，运费 10 元，优惠减 15 元，最终支付 80 元”。

用 CoT 解决多步规划问题的具体方法

以“安排一个包含多项约束的旅行行程”为例，CoT 的应用可以这样设计：

1. Prompt 设计：少样本示例中，展示如何将一个复杂的旅行规划问题分解为“时间约束检查 → 交通方式选择 → 景点顺序安排 → 餐饮休息时间插入 → 预算汇总”等多个子阶段。每一步都有清晰的输入和输出状态描述。

2. 状态追踪：让模型在推理中显式维护一个“当前状态”，例如“目前已用时间：6小时，剩余预算：500元，当前位置：A景点”。每进行一步决策，都更新这个状态。这可以借助 Markdown 表格或固定格式的文本来实现。

3. 回溯与备选方案：对于可能出现冲突的规划任务，可以引导模型在发现冲突时进行“如果…否则…”的分支推理，甚至模拟“撤销上一步决策，尝试另一选项”的回溯过程。虽然 LLM 并非真正的搜索算法，但通过精心设计的示例，它可以模仿这种回溯行为。对于更复杂的情况，Tree of Thoughts (ToT) 框架提供了更系统化的搜索树，其本质也是分治的扩展。

实际应用中的局限与增强

纯 CoT 在处理需要长距离依赖和大规模状态维护的规划任务时，仍可能因为模型注意力限制而丢失早期信息。此时可以通过以下方式增强：

- 将规划任务与外部记忆或数据库结合，将中间状态持久化到上下文之外。

- 使用 ReAct 模式，在推理过程中穿插实际的工具查询（如查询交通 API 获取真实时间），使推理建立在可靠数据之上。

小结

CoT 是分治思想在 LLM 推理中的自然映射。通过让模型自言自语地拆解问题、逐步求解，它将原本可能被压缩在隐层的一次性映射，变成了人类可读、可调试、可验证的显式计算过程。对于多步规划，关键在于维护清晰的状态和分阶段的目标。

#### 如何在 CoT 中引入外部工具（如计算器、搜索引擎）以实现更准确的推理？

LLM 的固有短板在于精确数值计算和实时知识获取，这恰好是外部工具的长处。将工具集成进 CoT，相当于给了模型“手臂和眼睛”，让它可以去操作精确的工具，而不只是在大脑里空想。

集成模式

1. 标记化工具调用：在 CoT 推理链中，当模型遇到计算或查询需求时，不直接输出结果，而是生成一个约定格式的工具调用指令。例如：

```plain text
我需要计算总价，调用计算器：
<tool name="calculator">85 * 1.1 + 12</tool>
```

外部编排系统检测到这个标签后，暂停生成，调用相应工具，把结果（如“105.5”）以特定格式注入对话上下文，模型再继续推理。这种模式的关键在于：

标签格式必须简单且不易与正常文本混淆。

示例必须清晰展示这种中断和继续的流程。

2. ReAct 循环（Thought-Action-Observation）：这是目前最经典的工具集成范式。模型生成一个“Thought”（推理步骤），然后是一个“Action”（要调用的工具和参数），系统执行后返回“Observation”（工具结果），模型再基于此继续下一个Thought。整个循环可以多次执行，直到得出最终答案。少样本示例中需要包含完整的 TAO 循环演示。

3. 程序辅助推理（PAL）：对于数学题，直接将推理过程用 Python 代码表达。模型生成完整的 Python 脚本，由解释器执行，得到的结果就是精确答案。这样完全把容易出错的算术部分交给了计算器，模型只负责将自然语言问题翻译为代码。这也是 CoT 的一种特殊形式。

4. 搜索引擎集成：当需要实时或大量事实信息时，模型生成搜索查询（如 `search("2024年诺贝尔物理学奖得主")`），系统调用搜索引擎 API，将返回的摘要片段以 Observation 形式返回，模型再基于这些权威信息继续推理，极大减少幻觉。

工程实现关键点

- 编排系统：需要一个中间层（如 LangChain、Semantic Kernel）负责解析模型输出，判断是否有工具调用，执行调用，并将结果格式化后重新提交给模型。

- 容错与重试：工具调用可能因为格式错误、超时或返回异常而失败。编排系统需要具备解析容错（如用正则提取关键信息）、超时处理、自动重试以及错误信息反馈给模型（让模型知道调用失败并尝试其他方法）的能力。

- 安全沙箱：尤其是执行代码时，必须在严格的沙箱环境中运行，防止注入攻击和对宿主系统的破坏。

- 成本控制：每次工具调用都会增加延迟，搜索 API 可能还有费用。在提示中应训练模型只在必要时才调用工具，而不是每步都调。

效果评估

引入工具后，CoT 在数学计算准确率上可以从 60%-70% 飞跃到近乎 100%（算术部分）。在知识问答上，结合搜索的 CoT 可以显著提高事实准确性和时效性。这种“LLM作为大脑，工具作为四肢”的模式已经成为构建可靠 Agent 的核心架构。

#### 为什么 CoT 容易产生“幻觉推理”，即推理听起来合理但本质错误？

幻觉推理是 CoT 面临的最隐蔽也最棘手的问题之一。它指的是模型生成了一条读起来非常流畅、逻辑自洽、甚至让非专业人士信服的推理链，但实际上其中包含事实错误、逻辑谬误或无根据的假设。

根本原因剖析

1. 语言模型的本质是统计拟合，而非逻辑推理器\
   模型的训练目标是预测下一个 token，它学会的是“在类似语境下，人们通常会这样接着写”。因此，当它被提示进行推理时，它会从训练数据中检索出最像“推理”的语言模式来生成文本。这种模式匹配优先于真实逻辑运算。一条推理链在统计上越“像正确的推理”，就越容易被模型输出，不管它实际是否正确。

2. 错误传播的滚雪球效应\
   CoT 是自回归生成，前一步的输出成为后一步的输入。一旦某个步骤生成了一个貌似合理但实质错误的陈述（例如“因为利率下降，所以债券价格下跌”——而实际上应该是负相关），后续的推理都会基于这个错误的前提展开。模型会极其自信地沿着错误路径继续推导，因为它不断在上下文中看到自己刚刚生成的“事实”，并将其当作可靠依据。

3. 缺乏真值校验机制\
   人类在推理时，会在脑内对每一步进行快速的真假判断，如果发现不合理会退回重想。LLM 没有这种内在的验证器。它无法判断自己生成的“1915 年爱因斯坦发表了广义相对论”是否正确（实际上是 1915 年），只要这个句子在语言上成立，它就会继续下去。而且它常常会编造出看起来有模有样但完全虚构的引用、数据和理论。

4. 过度泛化与错误类比\
   模型可能把在某个领域内正确的推理模式（如数学归纳法）错误地移植到另一个不适用该模式的领域（如历史分析），从而生成一套听起来很专业、但实际上逻辑不成立的论证。这种类比错误对非专业读者极具迷惑性。

5. 注意力衰减与上下文遗忘\
   在非常长的推理链中，早期的约束条件、已知事实可能因为距离太远而不再被模型有效关注，导致后期的推理脱离了初始条件，变得虽然局部连贯但全局错误。

如何缓解

- 自洽性：多生成几条路径投票，降低单条幻觉路径被采纳的几率。

- 外部工具：用计算器、搜索引擎等提供客观真值，切断幻觉传播。

- 强制验证步骤：在推理链末尾要求模型自我检查，尽管不能根除，但能部分纠正错误。

- RAG（检索增强生成）：提供可靠的外部文档作为推理基础，减少模型对内部“记忆”的依赖。

- 提示中展示不确定性：在示例中加入“我不太确定，但…”或者“查证后…”这样的表达，使模型在不确定时不那么武断。

#### 思维链的格式化：使用编号、项目符号还是自然段落？哪种更有效？

格式化看似是表面问题，实则对模型推理质量有不可忽视的影响。格式直接决定了模型如何组织其“思维结构”，以及后续如何被解析和验证。

三种格式对比

1. 编号列表（1. 2. 3.…）
  - 优势：强制步骤分明，顺序清晰。尤其适合需要严格前后依赖关系的任务，如数学计算、流程操作。编号隐含“第一步做完再做第二步”的顺序约束，能有效减少模型跳步或遗漏。同时也便于程序解析（按编号切分步骤）。
  - 劣势：对于并列关系强或思路需要灵活跳转的任务，强制编号可能会限制模型的自然表达，显得生硬。
  - 实验证据：在 GSM8K 等数学推理任务上，使用编号列表的 CoT 准确率通常最高。

2. **项目符号（- 或 ）*
  - 优势：适合展现并列的观点、原因或选项，没有严格顺序要求，灵活度较高。
  - 劣势：缺乏显式的顺序信息。如果任务本身需要先后步骤，项目符号可能导致模型忽略依赖关系，造成逻辑松散。
  - 适用场景：头脑风暴、优缺点分析、多项条件列举等。

3. 自然段落
  - 优势：最接近人类的书写习惯，阅读流畅，适合需要解释、论述的复杂推理。它能容纳更细腻的因果连接词（“因此”、“然而”），让推理读起来更自然。
  - 劣势：步骤边界模糊，模型可能不自觉跳步，或者把好几步揉在一个长句里。对后处理提取答案也较困难。
  - 风险：自然段落的自由度更高，也意味着模型更容易跑偏、加入无关内容，或者产生冗长重复。

哪种更有效？

综合研究和工程实践，对于绝大多数需要精确推理的任务，编号列表通常表现最好且最稳定。原因在于它强加了一个结构化的思维框架，帮助模型约束生成长度、减少歧义、保持步骤完整。项目符号和自然段落在特定任务中也有用武之地，但风险略高。

设计建议

- 一旦选定某种格式，必须在所有少样本示例中保持一致。格式不一致会让模型感到困惑。

- 可以混合使用：例如在编号步骤内部用自然语言详细描述，或使用子编号（1.1, 1.2）。这在复杂任务中尤其有效。

- 应进行小规模 A/B 实验，测试不同格式在具体任务上的准确率和稳定性，以数据驱动决策。

#### 在 CoT 中，如何控制模型生成简练的推理路径，避免冗长和重复？

冗长的推理不仅浪费 token 和时间，还会增加错误概率，因为无关信息可能引入噪声或让模型“分心”。控制推理长度需要从示例、指令、参数和微调等多方面入手。

1. 示例是最好的老师

少样本示例中推理链的详尽程度会直接成为模型模仿的对象。如果示例里的推理简洁明了，每步只说关键信息，模型也会倾向于简洁；如果示例啰嗦，模型就跟着啰嗦。因此，精心编写甚至反复修剪示例的推理链是首要工作。

2. 显式指令与格式约束\
   在 prompt 中加入明确的长度控制指令，例如：“请用不超过 3 步的推理给出答案”或“每步推理只用一句话”。对于指令微调过的模型，这类要求通常能被较好地遵守。也可以强制输出结构，如固定提供三个 `Step` 槽位，模型便会倾向于填满但不溢出。

3. 解码参数调节

- 适当降低 `temperature`（如 0.2–0.4）可以减少模型发散和重复。

- 设置 `repetition_penalty` 防止同一句话或短语反复出现。

- 限制 `max_tokens` 直接截断过长生成，但要注意不能截断关键推理步骤。

4. 后处理裁剪

如果推理仍然偏长，可以训练一个轻量级的摘要模型对推理链进行压缩，或者用规则提取关键句。但这会引入额外延迟和复杂度。

5. 针对性微调（知识蒸馏）

如果任务固定且对延迟极度敏感，可以用一组精心编写的“简洁推理”数据对模型进行微调，从根本上改变模型的生成风格。微调后的模型即使不加强约束也能输出精炼的推理。

平衡点

简洁不等于缺失信息。过度压缩可能导致关键步骤被省略，反而降低准确率。需要在验证集上绘制“推理长度 vs 准确率”曲线，找到准确率开始下降的临界长度，作为最优简洁度参考。

#### 多模态 CoT：如何让视觉-语言模型展现思维链？

多模态 CoT 将纯文本的逐步推理扩展到包含视觉信息的场景，例如回答关于图片的复杂问题、解读图表、或根据图像进行规划。这对模型的要求比纯文本 CoT 更高。

核心挑战

- 模型需要同时处理视觉和文本两种模态，并在它们之间建立精细的对应关系。

- 视觉信息往往是非结构化的，需要模型自行从中提取关键要素。

- 长推理链加上图像特征，对上下文窗口和计算资源是双重压力。

实现路径

1. 分阶段的推理模板\
   将推理过程明确分成“视觉观察”和“逻辑推理”两个阶段，用固定标签分隔。例如：

```plain text
视觉观察：
- 图中有一个红绿灯，显示为红灯。
- 一辆白色汽车停在停止线前。

推理：
由于是红灯，汽车必须停车等待。所以这辆车的当前状态是停车等待。

答案：停车等待
```

这种模板强制模型先进行客观描述，再进行推理，减少了跨越模态直接猜答案的风险。

2. 少样本示例中融入视觉定位\
   示例要展示如何引用图像的具体区域。虽然模型不一定能输出精确坐标，但可以用自然语言定位，如“在图像左上角的菜单栏中”、“表格的第三行第二列”。这要求模型具备一定的空间语义理解能力。

3. 训练数据增强\
   对于开源多模态模型（如 LLaVA 系列），可以构建包含详细推理链的指令数据集进行微调。数据集格式通常为：`图像 + 问题 + 推理链文本 + 最终答案`。微调能让模型内化多模态逐步推理的生成模式，效果远优于单纯的上下文学习。

4. 借助外部视觉工具\
   可以调用目标检测、OCR、图像描述等外部模型，先将图像转化为结构化的文本描述或实体列表，再让纯文本 LLM 基于这些结构化信息进行 CoT 推理。这种“多工具流水线”模式降低了端到端多模态模型的训练难度，在生产环境中更可控。

5. 流式交互与可视化\
   在多模态 CoT 的展示中，可以结合前端技术，在模型提到图像某个区域时高亮该区域，或者在推理步骤中插入缩略图，让用户直观看到模型的“注意焦点”。这既是功能，也是增强用户信任的手段。

当前局限与展望

多模态 CoT 尚处于快速发展期。目前顶尖的闭源模型（如 GPT-4V）已经具备不错的多模态 CoT 能力，开源模型则需要通过高质量微调数据来追赶。随着视觉编码器与语言模型对齐技术的进步，多模态 CoT 将成为智能助手、自动驾驶、医疗影像解读等领域的关键技术。

#### CoT 对推理时间成本的影响：生成更长的推理链带来延迟，如何权衡？

CoT 显著增加了输出 token 的数量，推理链的长度往往是最终答案的几倍甚至十几倍。在自回归解码中，总生成时间大约与总 token 数成正比，所以 CoT 会直接拉长用户的等待时间。如何平衡准确率提升与延迟增加，是工程部署中的核心决策。

成本量化

假设一个简单问题直接回答需要 20 token，耗时 0.2 秒；启用 CoT 后推理链有 150 token，总 token 变为 170，耗时变成了 1.7 秒。延迟增加了 8 倍多。对用户来说，从“秒回”变成了“等一下”，体验影响显著。

权衡策略

1. 任务分流\
   不是所有请求都需要 CoT。可以训练一个轻量级分类器或者用简单的规则（如问题长度、是否包含“计算”“推理”等关键词）判断问题复杂度。简单问题直接回答，复杂问题启用 CoT。这在客服和对话系统中非常实用。

2. 控制推理链长度\
   如第 17 问所述，通过示例、指令和参数把推理链控制在完成任务所需的最短长度。少写一句废话，就少一分延迟。

3. 流式输出缓解心理等待\
   虽然物理总时长没变，但流式输出让用户能立刻看到模型开始“思考”，不断有文字涌现，心理等待感远低于盯着空白屏幕等几秒。对于 CoT，流式还能让用户看到推理过程，增加透明度和可信度。

4. 选择性使用 Self-Consistency\
   在延迟敏感的在线服务中，用单次 CoT；在离线批处理或对精度有极致要求的场景（如合同审查），再打开 Self-Consistency。两者可以根据请求优先级或用户等级动态切换。

5. 推理加速技术\
   采用模型量化（INT8/INT4）、FlashAttention、推测解码（Speculative Decoding）等技术，直接降低每 token 的生成延迟，使 CoT 的额外时间在绝对数值上变小，更容易被接受。

6. 预计算与缓存\
   对于高频问题的推理链，可以提前生成并缓存，用户请求时直接返回缓存的推理和答案，延迟等同于简单查询。

寻找最优平衡点

建议在产品环境中绘制“延迟—准确率”帕累托曲线：用不同的推理链长度上限、是否启用 CoT、是否启用自洽性等配置，测得对应的平均延迟和准确率，选择在延迟预算内准确率最高的配置。这个最优解会随着模型能力、硬件性能和业务需求的变化而动态调整。

#### 如何评估 CoT 生成的推理质量？除了最终答案正确率，还有哪些指标？

仅凭最终答案的对错来评估 CoT 是片面的。一个“蒙对”但推理完全错误的答案在测试中会被算作正确，而一个思路全对但最后一步笔误的推理则被算作错误。我们需要更细粒度的评估体系来真正衡量推理质量。

核心评估维度

1. 推理正确性（Process Correctness）\
   逐步骤检查推理链是否逻辑正确、计算无误、引用的前提真实。可以人工标注，也可以用强模型（如 GPT-4）作为评判器，给定标准答案和推理链，逐条判断。指标可以细分为：
  - 步骤级准确率：正确步骤数 / 总步骤数。
  - 完全正确率：整条推理链没有任何错误的样本比例。

2. 逻辑连贯性与一致性\
   推理步骤之间应该存在合理的逻辑关系（因果、递进、转折等），而不是生硬拼接。可以用自然语言推理（NLI）模型自动检查相邻步骤是否存在蕴含或矛盾关系。连贯性得分低的推理链通常存在断裂或跳跃。

3. 事实忠实度（Faithfulness）\
   推理链中陈述的事实是否忠实于给定的上下文或已知的世界知识，而不是模型凭空编造。可检测幻觉率，即每百步推理中包含不实信息的步骤数。尤其在基于文档的问答中，忠实度是生死线。

4. 简洁性与冗余度\
   好的推理应当直击要害。可以测量推理链长度与“最小必要推理长度”的比值，或者通过专家评分来评判是否包含无关信息。冗余不仅浪费资源，还可能降低可读性并引入噪声。

5. 鲁棒性与稳定性\
   对同一问题的不同问法、示例顺序打乱、无关背景信息注入等扰动，推理链是否仍保持正确。计算多次运行的标准差或最差情况准确率，能反映模型推理的稳定程度。

6. 可验证性\
   推理链是否包含足够的信息让人类或自动系统验证其正确性。例如，是否明确引用了数据来源、公式编号、法律条文等。可验证性高的推理更值得信赖。

7. 与人类专家推理的吻合度\
   在某些领域（如医学、法律），可以请专家评估模型推理与人类专家推理思路的相似度和合理性。这是衡量模型是否真正“像专家一样思考”的重要参考。

自动化评估方法

- LLM-as-a-Judge：用高级 LLM 依据评测标准对推理链进行打分，成本低于人工标注，且可大规模执行，但需警惕裁判模型自身的偏见和误差。

- 基于规则和工具：对算术步骤，可以用计算器验证；对引用，可以比对知识库；对格式，可用正则检查。这种方法客观准确，但覆盖范围有限。

构建评估体系的意义

多维度评估不仅让我们知道模型“考了多少分”，更让我们洞察“它是怎么思考的”，从而有针对性地改进提示、微调数据，或定位模型的系统性缺陷。这是 LLM 推理能力从“能用”走向“可靠”的必经之路。
