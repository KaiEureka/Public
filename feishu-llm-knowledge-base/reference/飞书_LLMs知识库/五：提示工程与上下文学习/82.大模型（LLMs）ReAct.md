# 82.大模型（LLMs）ReAct

#### ReAct（Reasoning + Acting）框架的核心思想是什么？它如何结合推理与行动？

ReAct 框架的核心思想是让大语言模型在解决复杂任务时，不再仅仅依赖内部参数化知识进行孤立推理，而是将推理（Reasoning） 与行动（Acting） 紧密交织在一起。模型被允许在生成最终答案的过程中，随时向外部世界发起操作（如搜索、查询数据库、调用计算器），并将从外部环境返回的观察结果（Observation）直接作为新的上下文，指导后续的推理和行动。

这种结合方式模仿了人类解决复杂问题时的典型行为：我们不会凭空冥想，而是会“思考一步，然后查一下资料，根据查到的信息再思考，再行动，如此循环”。ReAct 将 LLM 视为一个智能代理，它拥有一个与外部环境交互的接口。每一轮中，模型首先产出一个思考（Thought），分析当前状态、明确需要什么信息或下一步计划；接着产出一个行动（Action），精确指定要调用的工具及其参数；然后系统执行该行动，将返回的观察（Observation）注入对话上下文；模型基于观察再次进入思考，如此反复，直到得出最终答案。

这种“推理-行动-观察”循环的优势在于：

- 实时获取最新、最准确的信息，弥补 LLM 内部知识的截止日期限制和领域覆盖不足。

- 通过外部工具辅助精确计算和操作，克服 LLM 在算术、逻辑执行上的弱点。

- 通过观察反馈自我纠错，当行动返回无效信息或模型发现推理矛盾时，可以调整策略，重新行动，提升鲁棒性。

- 提供可解释的推理-行动轨迹，用户可以清晰地看到模型每一步的思考过程以及从何获取的信息，增强可信度。

因此，ReAct 不是简单的“LLM+工具调用”，而是一种将工具使用有机融入复杂推理过程的动态交互框架，为构建真正能够“思考并行动”的智能 Agent 奠定了基础。

---

#### 描述 ReAct 的典型循环：思考 → 行动 → 观察 → 思考...

ReAct 的典型工作循环是一个迭代的、交替的序列，直到模型认为已经掌握了足够信息来回答用户问题。这个循环可以分解为以下阶段：

1. 思考（Thought）：模型分析当前状态，包括原始问题和已经积累的观察历史。它思考当前还缺少什么信息，下一步应该做什么来推进解决。思考是内在推理，不直接改变外部环境。例如：“我需要找出2023年诺贝尔物理学奖得主的出生地。首先我得知道他/她是谁，我需要搜索获奖者名字。”

2. 行动（Action）：基于思考，模型决定采取一个具体的行动，并给出行动的参数。行动是显式的、可被解析的指令，用于调用外部工具。例如：`Search[2023年诺贝尔物理学奖得主]`。行动空间通常是预定义的，如搜索、查找数据库、调用计算器等。

3. 观察（Observation）：这是从外部环境返回的结果。系统执行模型指定的行动，并将结果以文本形式返回给模型。例如，搜索引擎返回一段摘要：“2023年诺贝尔物理学奖授予皮埃尔·阿戈斯蒂尼、费伦茨·克劳斯和安妮·吕利耶...” 观察被直接注入到对话上下文中，作为下一步推理的事实基础。

4. （循环）再次思考：模型阅读观察结果，更新自己的理解。它可能从观察中提取出所需的关键信息（如得奖者姓名），然后继续思考下一步：现在有了名字，还需要他们的出生地。于是生成新的思考，接着再次发起行动（如搜索“皮埃尔·阿戈斯蒂尼 出生地”）。这个循环持续进行，模型可能进行多轮搜索，逐步逼近最终答案。

5. 终止与最终答案（Final Answer）：当模型认为已经收集到足够的信息，或者任务已经完成时，它会生成一个特殊的“最终答案”行动，或直接输出最终回答。例如：`Final Answer: 皮埃尔·阿戈斯蒂尼出生于法国...`。

这种交替循环使 LLM 能够动态地根据外部信息调整推理方向，而不是一早就定下整个计划。它具有极强的适应性和鲁棒性，因为每一步行动都是基于最新的全部历史做出的。

#### 在 ReAct 中，推理步骤（Thought）和行动步骤（Action）如何交替进行？请画出流程图。

在 ReAct 中，推理和行动严格交替，形成“思考→行动→观察→思考→行动→观察”的链条。模型生成的内容只包含 Thought 和 Action，而 Observation 由外部环境注入。具体交替流程如下：

（此处为描述性流程图）

```plain text
开始
 │
 ↓
[用户问题]
 │
 ↓
┌──────────────────────────────────────┐
│  LLM 生成                             │
│  Thought: "我需要先做...，因为..."     │
│  Action: Search[查询词]                │
└──────────────┬───────────────────────┘
               │  调用搜索工具
               ↓
┌──────────────────────────────────────┐
│  外部环境返回                          │
│  Observation: "搜索结果摘要..."        │
└──────────────┬───────────────────────┘
               │  注入上下文
               ↓
┌──────────────────────────────────────┐
│  LLM 继续生成                          │
│  Thought: "根据搜索结果，我得知..."      │
│  Action: Search[进一步查询]             │
└──────────────┬───────────────────────┘
               │  调用搜索工具
               ↓
               ...（重复循环）
               │
               ↓
┌──────────────────────────────────────┐
│  LLM 生成                              │
│  Thought: "我已获得足够信息，可以回答。" │
│  Action: Finish[最终答案]               │
└──────────────┬───────────────────────┘
               │
               ↓
            结束
```

在这个流程中，Thought 总是先于 Action 出现，因为它负责分析并决定下一步行动。每轮仅包含一对 Thought 和 Action（或者仅 Action，如果模型不需要显式思考）。Observation 是由系统在 Action 执行后插入的，模型不能跳过 Observation 直接产生新的 Thought。这种严格的交替确保了外部信息被及时整合，避免了模型在缺乏事实依据时凭空推理。

#### ReAct 与纯推理方法（如 CoT）相比，优势在哪些任务上？为什么？

ReAct 相对于纯推理方法如 CoT（思维链）的优势，集中体现在那些依赖实时、准确外部知识或需要与动态环境交互的任务上。

优势任务类型：

1. 知识密集型问答（开放域QA）：CoT 依赖模型内部存储的参数化知识，这些知识可能过时、不完整或包含错误。ReAct 可以通过搜索行动实时获取最新、权威的信息，确保答案的事实准确性。

2. 多步推理与组合问题（如多跳问答）：例如，“2023年奥斯卡最佳影片的导演的妻子是谁？”这类问题需要先查最佳影片，再查导演，最后查配偶。CoT 可能一步到位地编造答案（幻觉）。ReAct 可以通过多轮搜索逐步获取每步所需的事实，每一步都建立在真实观察之上，逻辑链条牢固。

3. 事实核查与验证任务：需要确认某个声称是否属实。ReAct 可以通过搜索相关的可靠来源，比对信息，给出有据可查的判断。CoT 只能基于内部知识判断，不可靠。

4. 需要外部工具精确计算的任务：如数学计算、单位换算。CoT 自身的算术能力经常出错。ReAct 可以调用计算器行动获取精确数值，从根本上消除算术错误。

5. 动态信息查询：如天气、股价、体育比分。这些信息是 CoT 的内部知识完全无法覆盖的（时效性），ReAct 通过搜索行动可以获取实时数据。

为什么有优势？

根本原因在于 ReAct 将 LLM 的角色从“知识库+推理机”转变为了“推理协调器”。LLM 不再需要记忆所有事实，而是专注于分析问题、制定信息检索策略、并根据检索到的信息进行综合推理。它利用了外部知识源的动态性和精确性，显著减少了因知识缺失或过时导致的幻觉。同时，行动的“观察”为推理提供了真实可靠的锚点，使得每一步推理都有据可查，整个解题过程的可靠性和可解释性都远高于纯内部推理。

#### 行动（Action）通常包含哪些类型？如搜索、计算器、API 调用等。

在 ReAct 框架中，行动（Action）是模型与外部世界交互的接口。行动空间的设计取决于具体应用场景，但通常包括以下几类：

1. 信息检索类：
  - 搜索（Search）：最核心的行动，调用搜索引擎（如 Google、Bing API）获取与查询词相关的网页摘要。参数为搜索查询字符串。
  - 查找（Lookup）：在已搜索到的某个特定结果页面内进行精确定位，模拟人类点击链接查看详情的行为。参数通常是结果序号和查询关键词。
  - 数据库/知识库查询（Query）：用结构化查询语言（如 SQL、SPARQL）查询内部数据库或知识图谱，获取精确的结构化信息。

2. 精确计算类：
  - 计算器（Calculator）：调用数学计算引擎（如 Python eval）执行数学表达式，返回精确数值结果。参数为数学表达式。
  - 单位/货币转换：调用专门的转换 API。

3. 程序执行类：
  - 代码解释器（Code Executor）：执行一段代码（通常是 Python），返回标准输出或错误信息。用于数据分析、绘图、算法运行等。
  - 终端命令：在安全沙箱中执行 Shell 命令，用于文件操作、运行脚本等。

4. 事务性操作类：
  - API 调用：调用第三方服务 API，如发送邮件、创建日程、下单、控制智能家居设备等。行动参数包含 API 名称和所需 JSON 参数。
  - 数据库写入：执行 INSERT/UPDATE 等操作，改变外部系统状态。

5. 任务控制类：
  - 完成/结束（Finish）：表示任务已经解决，后面跟随最终答案文本。
  - 澄清（Ask User）：当信息不足或不确定时，向用户提问以获取澄清。

6. 环境交互类（在具身智能或游戏 Agent 中）：
  - 移动、拾取、使用物品等物理或模拟环境中的动作。

在典型的 ReAct 实现中，每种行动都有严格的文本格式，例如 `Search[query]`、`Calculator[expression]`、`Finish[answer]`，以便外部解析器准确识别和执行。良好的行动空间设计应在“功能完备性”和“避免模型滥用”之间取得平衡。

#### 如何设计 ReAct 的少样本提示，让模型学会何时思考、何时行动？

ReAct 的行为模式（交替生成 Thought 和 Action）是通过精心设计的少样本提示（Few-Shot Prompt）教会模型的。提示中需要展示完整的“思考→行动→观察→思考...”轨迹，让模型从示例中归纳出这种交互范式。

设计要点：

1. 选择覆盖核心行为模式的示例：应包含 2~4 个完整的 ReAct 轨迹示例。这些示例需要覆盖不同的行动类型（搜索、查找、完成）和推理场景（需要多步搜索、遇到死胡同需要调整策略、信息足够时停止）。例如：
  - 示例1：展示如何通过多轮搜索逐步获取事实。
  - 示例2：展示搜索结果不相关时如何重新构造查询。
  - 示例3：展示直接使用计算器获取数值。

2. 严格格式规范：在每个示例中，清晰标注 `Thought`、`Action`、`Observation` 的边界。Observation 通常由系统注入，但在示例中必须展示其作为文本的一部分，让模型理解外部信息将如何出现以及如何利用它。

3. Thought 的内容训练：Thought 应该展示分析当前状态、评估已有信息、规划下一步的过程。好的 Thought 会解释为何选择某个 Action，例如：“我需要知道苹果公司的 CEO，搜索一下。” 而不是无意义的空话。示例应示范多样化的 Thought 模式：有时是分解问题，有时是检查信息完整性，有时是对观察进行推理。

4. Action 的参数化展示：示例中 Action 的格式必须完全一致（如 `Search[...]`），且查询内容要具体、合理。通过示例教会模型如何构造有效的搜索查询（使用关键词而非完整问句，引用已知实体等）。

5. 错误恢复示例：包含一个动作失败或返回无关信息时的恢复示例。例如，搜索返回了错误实体，Thought 分析出搜索词有歧义，然后提出更精确的搜索。这教会模型灵活调整。

6. 终止条件展示：示例明确展示何时停止行动并给出最终答案。Thought 会表达“现在我已掌握所需全部信息”，然后 Action 为 `Finish[答案]`。

示例结构片段：

```plain text
问题：2022年冬奥会在哪里举办？
Thought：我需要搜索2022年冬奥会举办地。
Action：Search[2022年冬奥会举办地]
Observation：2022年冬奥会在中国北京举行...
Thought：搜索结果显示是北京，我可以直接回答。
Action：Finish[2022年冬奥会在中国北京举行。]
```

通过这样贴近真实、格式统一、覆盖边界情况的少样本提示，模型能够快速掌握 ReAct 的语法和策略，学会何时深入思考、何时果断行动、何时优雅终止。

#### ReAct 如何缓解幻觉？观察（Observation）在其中扮演什么角色？

幻觉（Hallucination）是 LLM 凭空编造事实的根本缺陷。ReAct 通过引入外部行动和观察，从机制上大幅缓解了幻觉问题。

缓解机制：

1. 用外部事实替换内部知识：幻觉的根源是模型仅依赖其参数记忆。在 ReAct 中，模型被训练（或提示）为不依赖记忆直接回答，而是将外部工具返回的观察作为权威事实来源。每一步推理的关键依据都必须来自最近的 Observation，而不是模型“觉得”或“记得”的内容。这从根本上切断了内部幻觉的生存空间。

2. 多步验证与交叉比对：ReAct 可以执行多次搜索，从不同来源获取信息，然后在 Thought 中对这些信息进行比对。如果不同来源的信息一致，答案的置信度就很高；如果矛盾，模型可以进一步深入调查，而不是轻易采信单一的内部猜测。

3. 事实链的可追溯性：ReAct 产生的最终答案，其背后的每一个事实性陈述都可以追溯到某个具体的观察。这使得整个回答变成了有根有据的引证，而不是黑箱输出。这种可追溯性本身对用户来说就是一种信任保证，也便于后续审核。

4. 强制“看到再回答”：ReAct 的动作循环隐含了“先查后说”的纪律。模型被训练为在没有执行搜索并得到相关观察前，不应当生成最终答案。这避免了 CoT 中常见的“流畅地编造”的陷阱。

观察的核心角色：

观察是 ReAct 对抗幻觉的锚点和事实基础。

- 锚点：它把模型的推理锚定在真实的外部数据上，防止推理漂移到虚构空间。每一次 Thought 都是基于前一次的 Observation 展开的，而不是基于模型自己的想象。

- 事实基础：最终答案中的每一个事实，都应该能在先前的 Observation 中找到直接依据。用户甚至可以回溯到具体的搜索轮次去核实。这就好像写论文时必须标注参考文献一样，强制要求证据先行。

- 纠错触发器：当观察返回意外或矛盾信息时，它会触发模型的反思性 Thought，促使模型调整错误的假设或修正搜索策略，而不是在错误的幻觉路径上越走越远。

因此，ReAct 不靠提升模型内部知识精度来减少幻觉，而是通过架构设计，将 LLM 从一个“知识库”转变为一个“信息检索与综合者”，让事实准确性由外部系统保证。

#### 如果行动返回了无效或噪声信息，ReAct 如何从这种错误中恢复？

外部环境并非总是可靠的。搜索可能返回不相关的结果，API 可能超时，计算器表达式可能有语法错误。ReAct 具备从这些常见错误中恢复的机制。

恢复机制：

1. 基于无效观察的反思性思考：当模型收到一个不理想或无效的观察时（例如“未找到相关结果”或错误信息），下一个 Thought 是关键。少样本示例应教会模型此时不要慌张或放弃，而是分析可能的原因并调整策略：
  - 调整查询：“这个搜索词太宽泛了，让我试试更具体的关键词。”
  - 更换工具：“搜索引擎没找到，也许我可以换个内部知识库查询。”
  - 分解问题：“完整的句子没搜到，让我搜其中的人名试试。”
  - 检查行动格式：“可能是计算表达式写错了，让我检查并重试。”

2. 重试与退避：模型可以再次执行相同或类似的动作。这类似于程序中的重试逻辑。系统也可以预设最大重试次数，防止无限循环。

3. 利用部分信息：如果搜索返回了一些信息，但不完全相关，模型不会全盘丢弃，而是可以尝试从噪声中提取有用片段。Thought 会体现这种辨别：“虽然大部分内容不相关，但其中提到了一个关键名字，让我顺着这个查。”

4. 向用户求助：如果多次尝试均失败，模型可以采取 `AskUser` 行动，将模糊点或困难反馈给用户，请求人类提供更明确的指引。这是一种高情商的降级处理。

5. 回溯与尝试备选路径：ReAct 的思考-行动历史为回溯提供了可能。模型可以在 Thought 中提及“也许我一开始的假设不对”，然后尝试一条完全不同的搜索路径，而不是在死胡同里反复重试。这类似于思维树中的回溯。

在少样本提示中教授恢复：

这是关键。示例必须包含遭遇糟糕观察后成功恢复的案例，否则模型会不知所措。示例会明确展示遇到“无结果”时如何重新措辞查询，遇到“无关摘要”时如何发现其中的蛛丝马迹并深入。通过这些“困难模式”示例，模型学会将观察视作反馈信号，并动态调整行为。

因此，ReAct 的鲁棒性不仅来自于 LLM 的推理能力，还来自于其利用观察作为反馈信号进行闭环调整的架构优势。它不像纯推理方法那样一旦方向错误就无可挽回，而是可以在执行过程中不断根据环境反馈修正航向。

#### 分析 ReAct 与 Toolformer 这类工具使用模型的异同。

ReAct 和 Toolformer 都是让 LLM 使用外部工具的先进方法，但它们在训练方式、行动集成粒度、推理与行动的耦合度上有显著区别。

相同点：

- 都赋予 LLM 调用外部工具的能力（如搜索、计算器）。

- 都通过特殊标记或格式来定义工具调用，使其可被外部解析器识别和执行。

- 都旨在弥补 LLM 在知识时效性、计算精度等方面的不足。

核心区别：

| 维度 | ReAct | Toolformer |
| --- | --- | --- |
| 基本思想 | 以“推理-行动-观察”循环为框架，行动服务于复杂推理过程。 | 在语言模型的文本生成中，自主决定在任意位置插入工具调用，以获取更准确的 token。 |
| 训练方式 | 主要通过上下文学习（Few-Shot Prompting），无需微调模型参数。适用于已有强大指令遵循能力的模型。 | 必须通过自监督微调，让模型学习在何时、如何调用工具。训练数据由模型自身生成和筛选。 |
| 行动粒度与位置 | 行动在固定的“思考-行动”节拍中出现，通常是完整的、高层次的（如搜索整个查询）。行动和普通文本泾渭分明。 | 工具调用可以嵌入在任意位置，甚至是一个句子中间，更细粒度（如仅对某个生僻词查词典）。行动是与普通文本混合生成的。 |
| 推理深度 | 强调显式的多步推理（Thought），行动是推理链中的一环。适用于复杂的、需要多步信息检索的任务。 | 重点在优化 token 预测，不一定包含显式的深度推理链。可能只是简单的“查一下这个事实，然后继续写”。 |
| 交互性 | 是一种交互式框架，模型在生成过程中会暂停，等待外部环境返回结果后再继续。这要求运行时支持“暂停-恢复”执行。 | 生成工具调用标记后，理论上是继续生成的，但实际实现中也需要暂停并注入结果。但其设计更偏向于自包含的文本生成。 |
| 适用模型 | 主要适用于已对齐的对话模型或指令模型。 | 从基座模型开始微调，因此可以内化工具使用习惯，使之成为模型能力的一部分。 |

总结：

ReAct 是一种显式的、循环式的代理推理框架，工具是它获取信息并验证思路的手段，强调整个推理过程的透明和可控。Toolformer 则是一种隐式的、自监督的工具集成方法，致力于让模型自身学会在需要时无缝调用工具，提升文本生成的事实准确性。两者可以结合：用 Toolformer 的方法微调一个擅长使用工具的基座模型，然后用 ReAct 的提示框架引导该模型在复杂任务中进行多步交互式推理。

#### 在 ReAct 中，如何处理行动依赖？能否并行执行多个行动？

行动依赖和并行性是在将 ReAct 扩展到更复杂场景时必须考虑的问题。

处理行动依赖：

在标准的 ReAct 循环中，行动是顺序执行的，每一步的 Action 都基于之前所有 Thought 和 Observation。这种串行模式天然处理了依赖关系：如果一个行动依赖前一个行动的结果，模型必须等到前一个行动的 Observation 返回后，才能在下一个 Thought 中分析并产生新 Action。这符合人类的一般解决问题逻辑，顺序保证了因果关系的正确。

但如果任务中有些行动没有依赖关系，顺序执行就会浪费时间。例如，需要同时查询“北京天气”和“上海天气”，两次搜索之间没有依赖。此时，如果模型能够识别出无依赖关系，就可以并行发起行动以提高效率。

并行执行多个行动：

让模型在单轮中生成多个独立的 Action 是实现并行的关键。需要修改提示模板和解析器来支持“多行动”输出。

- 提示设计：可以在少样本示例中展示模型在同一轮 Thought 后，输出多个 Action。例如：

```plain text
Thought：我需要同时获取北京和上海的天气来比较。
Action 1: Search[北京天气]
Action 2: Search[上海天气]
```

- 或者使用列表格式。

- 系统执行：外部解析器识别到多个 Action 后，将它们同时派发给相应的工具，并将所有结果收集起来。返回的 Observation 也应结构化，指明对应哪个行动的结果，例如：

```plain text
Observation 1: 北京天气...
Observation 2: 上海天气...
```

- 后续的 Thought 就可以同时基于这两个结果进行推理。

挑战：

- 结果对齐：确保返回的观察能与模型发起的行动正确对应，避免混淆。

- 依赖误判：模型可能错误地认为两个行动无依赖而要求并行，但实际上有隐含依赖，导致其中一个行动使用了过期假设。训练模型准确判断依赖关系是关键。

- 复杂度增加：并行行动会使提示模板和解析逻辑变得复杂，也要求工具后端支持并发处理。

目前，一些高级 Agent 框架（如 LangChain 的 ReAct 实现或 AutoGPT）已经支持一定程度的并行工具调用。实际应用中，可以设计为：默认顺序执行，仅当模型通过特定语法（如 `Actions: [act1, act2]`）明确请求并行时，才触发并行执行。这种按需并行的方式兼顾了性能与安全。

#### ReAct 的停止条件是什么？如何判断推理和行动已经足够并给出最终答案？

ReAct 的停止条件是模型自身基于当前积累的观察和推理，判断已经掌握了足够信息或任务已无法继续推进，从而主动生成最终答案。停止判断本质上是模型通过上下文学习习得的一种元认知能力。

停止条件的常见形式：

1. 显式“完成”行动：模型在 Thought 中分析得出“信息已足够，可以回答”，然后输出一个特殊的 Action 类型，如 `Finish[最终答案]` 或 `Answer[答案]`。这是最标准、最明确的停止方式。外部解析器检测到此类 Action 后，即终止循环，提取答案返回给用户。

2. 达到最大步数限制：为防止无限循环，系统会预设一个最大循环次数（如 10 轮 Think-Act-Observe）。当达到该上限时，即使模型没有主动 Finish，系统也会强制终止，并可能要求模型基于当前已有信息给出最佳答案，或返回一个“无法完成”的提示。

3. 连续无进展检测：如果模型连续若干轮都在重复类似的无效行动（如反复搜索无结果且不改变策略），系统可以判定陷入死循环，提前终止，并要求模型总结已有信息给出答案，或直接返回部分结果。

4. 模型置信度表达：在某些实现中，模型可以在 Thought 中表达对当前答案的置信度。当置信度超过预设阈值时，即可视为满足停止条件。这需要模型在训练或提示中具备评估自身不确定性的能力。

如何训练/提示模型学会停止：\
在少样本示例中，必须清晰展示“何时应该停止”。示例应包含这样的模式：当 Thought 总结出“根据以上信息，我已知晓全部所需事实”或“经过多轮搜索，未能找到更多信息，基于现有信息可以给出最佳答案”，然后紧接着 `Finish[答案]`。同时，示例也应包含负面案例：明明信息不足却过早停止，或者信息已够却继续无效搜索，以此教给模型判断的边界。

因此，ReAct 的停止既依赖于模型从示例中归纳出的“足够感”，也依赖于系统设定的安全边界，二者共同确保任务在恰当的时候结束。

#### 在实现 ReAct 时，如何解析模型输出以提取“Thought”和“Action”？常用的解析技术。

ReAct 的实现依赖于可靠地从 LLM 的生成文本中分离出 Thought 和 Action。模型输出通常是自由文本，需要解析器将结构提取出来。

常用解析技术：

1. 正则表达式（Regex）解析：最常用的方法。如果提示模板强制要求了固定的格式，如：

```plain text
Thought: [思考文本]
Action: [行动类型][行动参数]
```

解析器可以用正则表达式分别匹配 `Thought:` 和 `Action:` 字段，提取出思考内容、行动类型和参数。例如，匹配 `Action:\s*(\w+)\[(.*?)\]` 来获取行动名和参数。正则方法简单高效，但对格式偏差敏感。一旦模型输出多了一个空格或换行，可能导致匹配失败。因此，需要编写容错性较强的正则，或对文本进行预处理（如合并多余空格、统一大小写）。

2. 结构化输出（JSON 模式）：利用现代 LLM 支持 JSON 模式输出的能力，可以直接要求模型以 JSON 格式返回 Thought 和 Action，例如：

```json
{"thought": "...", "action": {"type": "Search", "query": "..."}}
```

然后使用标准 JSON 解析器提取。这种方法从根本上解决了格式不稳定的问题，但对提示设计要求高，且在某些开源模型中可能不如文本格式稳定。此外，JSON 输出会增加一些 token 开销。

3. 特定分隔符 + 字符串分割：在提示中要求模型使用特殊分隔符（如 `### Thought`、`@@Action`），然后通过简单的字符串分割和搜索来定位各字段。这种方法的鲁棒性介于正则和 JSON 之间。

4. LLM 自解析（后处理）：如果原始输出格式混乱，可以再调用一次 LLM，将混乱的原始输出和格式要求作为提示，让 LLM 重新输出结构化的 Thought 和 Action。这相当于一个“格式化器” LLM 调用，可以挽救很多解析失败的情况，但增加了成本和延迟。

5. 错误处理与重试：无论采用哪种解析方法，都必须配备健壮的错误处理。如果解析失败，系统可以：
  - 返回特定的错误提示给模型，要求其“重新按格式输出”。
  - 截取模型输出中明显包含 Thought 和 Action 的部分重试解析。
  - 使用历史成功解析的上下文作为引导。

实践中的最佳做法：优先尝试 JSON 模式（如果模型和平台支持），因为其确定性最高。如果不支持，则使用带有强容错机制的正则表达式，并辅以重试逻辑。同时，在少样本示例中严格统一格式，降低模型输出偏差的概率。

#### ReAct 用于多步问答、事实验证、交互式任务的效果对比。

ReAct 在不同类型的任务上效果差异明显，这源于各任务对“外部信息依赖度”和“推理深度”的不同要求。

1. 多步问答（Multi-hop QA）：

这类问题需要整合多个来源的信息才能回答，如“2023 年奥斯卡最佳影片的导演的妻子是谁？”。ReAct 在这类任务上效果卓越。模型可以像侦探一样，一步步搜索、提取实体、再搜索、再链接，最终拼凑出完整答案。相比 CoT，ReAct 的每一次推理都基于真实的搜索结果，避免了在多步推理中因一步记忆错误而全盘皆输的雪崩效应。实验数据表明，在 HotpotQA 等多跳问答基准上，ReAct 的准确率远超纯 CoT，且幻觉率大幅降低。其优势在于将复杂问题分解为有序的信息检索步骤，每一步都扎实有据。

2. 事实验证（Fact Verification）：

任务要求判断一个声称（Claim）是否真实，并给出证据。ReAct 表现同样突出，因为它本质上就是“搜索证据→评估证据→得出结论”的循环。模型可以针对声称中的关键实体进行搜索，获取多个来源，然后进行交叉比对和逻辑推理，最后给出“支持”、“反驳”或“信息不足”的判断。这个过程生成的可追溯证据链，是事实验证任务所必须的。ReAct 在此类任务上的准确率和证据召回率均优于单纯依赖内部知识的模型，因为它能将最新、最可靠的外部信息作为判断依据。

3. 交互式任务（如对话式推荐、客服）：

交互式任务的特点是用户意图可能不明确，需要多轮澄清和动态决策。ReAct 在这类任务上的价值在于它的“动态调整”能力。它可以将用户的每一轮输入都视作一个 Observation，然后思考（Thought）用户可能的需求，接着采取 Action（如查询商品数据库、计算价格、询问用户偏好），再将结果返回给用户。这种“思考-行动”循环完美契合了对话的交互本质。相比预设流程，ReAct 能更灵活地处理非线性的对话跳转和突发情况。它的效果优于固定脚本，但对提示设计和行动空间设计的要求更高，需要涵盖所有可能的对话动作。

总结：ReAct 在需要深度、顺序化信息检索和推理的任务（多步问答、事实验证）中，相较纯推理方法有质的飞跃。在交互式任务中，它提供了强大的动态决策框架，使对话系统更加智能和灵活。但在简单的事实型问答中，ReAct 的多次调用可能显得过于“笨重”，此时轻量级的 RAG 或直接回答反而更高效。

#### 如何将 ReAct 与 RAG 结合，让模型自主决定何时检索？

将 ReAct 与检索增强生成（RAG）结合，相当于为 LLM 装上了一个“检索行动”，让它能够自行判断什么时候需要查找外部知识库，以及如何查找。这比单纯的 RAG（每次请求都无条件检索）更智能、更高效。

结合方式：

1. 将“检索”定义为 ReAct 的一个 Action：在 ReAct 的行动空间中，增加一个 `Retrieve[查询语句]` 行动。当模型思考后认为需要从知识库获取信息时，就发起这个行动。系统执行该行动时，调用 RAG 管道，将查询语句转换为嵌入向量，从向量数据库中检索相关文档片段，并将这些片段作为 Observation 返回给模型。

2. 多轮、可迭代的检索：与一次性检索不同，ReAct 允许模型进行多轮检索。如果第一轮检索到的文档不够充分，模型可以在 Thought 中分析原因，然后构造一个更精确的查询，再次发起 `Retrieve`。这实现了迭代式 RAG，能显著提升复杂问题的召回率和准确率。

3. 与搜索行动互补：可以同时设置 `Search`（互联网搜索）和 `Retrieve`（内部知识库检索）两个行动。模型可根据问题类型自主决定：对于时效性问题用 `Search`，对于企业内部文档问题用 `Retrieve`。这种工具选择的自主性让 Agent 更加智能。

4. 基于置信度的自适应检索：模型可以在 Thought 中自评对当前问题的了解程度。如果“我很清楚这个答案”，则直接回答，不触发检索；如果“我对这个领域不太确定，需要查一下资料”，则触发 `Retrieve`。这避免了不必要的检索调用，降低了成本和延迟。

实现示例：

在少样本提示中，加入类似下面的轨迹：

```plain text
问题：公司最新的年假政策是什么？
Thought：这是公司内部政策，我需要查询内部知识库。
Action：Retrieve[年假政策]
Observation：[检索到的相关文档片段...]
Thought：根据文档，员工入职满一年享有5天年假...信息足够，可以回答。
Action：Finish[根据公司政策...]
```

优势：ReAct + RAG 结合，赋予了模型“信息获取的主动性”，既避免了无关检索造成的上下文噪音和成本，又通过迭代检索提升了对复杂问题的覆盖。这使得知识密集型应用的效率和质量达到了一个更好的平衡点。

#### 在 ReAct 中引入“工作记忆”：如何在长周期任务中维护重要信息？

ReAct 在多轮交互中，所有的 Thought、Action、Observation 都直接累积在提示的上下文窗口里。对于长周期、多步骤的任务，这会导致上下文过长、重点信息被淹没，模型可能遗忘早期的重要发现。因此，需要引入“工作记忆”机制，将关键信息提炼并持久化。

工作记忆的实现方式：

1. 结构化笔记（Scratchpad）：在提示中专门开辟一个“笔记”区域，要求模型在每轮或每隔几轮，将当前已知的关键事实、约束条件、子任务完成状态总结到笔记中。这个笔记区域不参与 Thought-Action 循环，而是作为固定的背景信息始终存在于上下文里。例如，可以这样定义：

```plain text
[工作笔记]
- 关键实体：巴黎，人口216万
- 已确认：需要比较2020年和2022年数据
- 待解决：尚未找到2022年GDP数据
```

模型可以在 Thought 中决定更新笔记，然后调用一个 `UpdateNote[新内容]` 行动，由系统将内容追加或合并到笔记区。

2. 分层摘要：当上下文超过一定长度时，可以触发一个后台线程，使用一个更便宜、更快的 LLM 对历史对话进行摘要，压缩早期的详细观察，只保留关键事实和决策点。摘要后的文本可以替换掉原来的详细历史，从而释放上下文空间。这类似于操作系统的内存分页，将“冷”数据换出到摘要中。

3. 外部记忆存储：使用外部数据库或键值存储来维护工作记忆。模型可以执行 `SaveMemory[主题][内容]` 和 `FetchMemory[主题]` 行动，主动将重要信息存入外部记忆，在需要时再读取。这不仅可以跨多轮会话保持信息，还能让记忆持久化。

4. 图结构记忆：对于复杂任务，可以用图（如 GoT）来组织记忆。实体和关系被存储为图节点和边，模型通过扩展子图来推进推理。这比线性笔记更擅长捕捉交叉依赖。

优势与注意：

引入工作记忆后，ReAct 不再受限于有限的上下文窗口，能够处理更长、更复杂的任务，并保持信息的一致性。但需要注意更新笔记的时机和内容质量，避免模型陷入记“流水账”或遗漏关键信息的误区。提示中需要示范如何精炼总结，以及何时应该更新笔记。

#### ReAct 的推理路径是否可解释？如何向用户展示其决策过程？

ReAct 的推理路径天然具有极高的可解释性，这正是它相对于端到端黑盒模型的核心优势之一。模型每一步的 Thought、Action 和 Observation 共同构成了一条清晰的决策轨迹，可以完整地向用户呈现。

可解释性的来源：

- Thought 作为内部独白：Thought 直接揭示了模型在每一步的“内心想法”：它为什么需要某个信息，它对当前观察的解读，它认为下一步应该怎么做。这使得用户不仅能知道“答案是什么”，还能理解“模型是如何一步步想到这个答案的”。

- Action 作为可审计的操作：每个 Action 都明确记录了模型调用了什么工具以及用什么参数。这让用户可以审计模型的行为是否恰当，比如搜索查询词是否合理。

- Observation 作为证据来源：最终答案所依赖的事实，都来自这些观察。用户可以回看观察，核实信息的真实性和来源，这与引用文献的原理相同。

向用户展示决策过程的方式：

1. 流式渲染思考链：在 UI 中，将 Thought 和 Action 以折叠或侧边栏形式展示。默认可能只显示最终答案，但用户可以点开“查看推理过程”，查看每一步的详细轨迹。类似 OpenAI ChatGPT 的“Thinking”界面。

2. 可视化图表：对于复杂的多步推理，可以用流程图或时序图来展示思考-行动链条，用不同颜色区分 Thought、Action 和 Observation。这让抽象的推理过程变得直观。

3. 证据溯源高亮：在最终答案中，将每个关键事实与其来源的 Observation 进行关联（类似参考文献角标）。用户可以点击角标直接跳转到当时的搜索轮次和观察内容，验证真伪。

4. 调试视角：为开发者提供更详细的视图，包括模型原始输出、解析结果、工具调用耗时、重试次数等，帮助分析性能瓶颈和错误原因。

应用价值：这种可解释性在医疗、金融、法律等需要严格问责的领域至关重要。它让用户不再是盲目信任 AI 的输出，而是能够理解、质疑、核实 AI 的推理过程，从而建立更深层次的信任。它也为模型开发者提供了调试和优化系统的最直观手段。

#### 比较 ReAct 与 Plan-and-Solve 策略的异同。

ReAct 和 Plan-and-Solve（P&S）都是增强 LLM 推理能力的先进策略，但它们在规划与执行的时序关系上存在根本差异。

相同点：

- 都旨在解决复杂多步任务，超越了简单的单步回答。

- 都利用 LLM 的推理能力来引导问题求解过程。

- 都可以结合外部工具，尽管 P&S 更侧重于推理，工具使用不是其核心。

核心区别：

| 维度 | ReAct | Plan-and-Solve |
| --- | --- | --- |
| 规划与执行时序 | 交织进行，没有全局预设计划。每一步行动都基于上一步的观察动态决定。 | 先制定完整的全局计划（Plan），然后按计划逐步求解（Solve）。计划阶段和执行阶段是分离的。 |
| 灵活性 | 极高。能灵活应对执行中的意外和观察反馈，随时调整方向。 | 较低。一旦计划制定，后续主要按计划执行，调整计划需要额外机制。对意外情况的处理能力较弱。 |
| 推理透明度 | 每步思考-行动-观察都实时可见，推理路径细致。 | 可看到初始计划和每一步的执行结果。推理路径更结构化，但可能缺少动态调整的细节。 |
| 对错误和噪音的鲁棒性 | 强。因为观察反馈可以被立即用于调整策略，甚至完全转向。 | 较弱。如果计划本身有误，或者执行中发现新问题，可能需要重新规划，成本高。 |
| 计算开销 | 可能更高，因为每步都需要 LLM 重新评估整个状态并生成新动作。步骤数可能更多。 | 可能更高效，一旦计划制定好，执行步骤可以快速进行，甚至部分步骤可以自动化。但复杂问题可能因计划不周而失败。 |
| 典型应用 | 信息探索、多步问答、交互式任务、需要动态调整工具使用的场景。 | 数学应用题、结构化推理、任务分解明确且环境变化少的场景。 |

形象比喻：

- ReAct 像是一个探险家，在丛林里走一步看一步，根据遇到的情况随时决定下一步方向。他依靠灵活应变来找到出路。

- Plan-and-Solve 像是一个工程项目经理，开工前先画好完整的图纸（计划），然后施工队按图索骥。如果图纸完美，施工就高效；如果现场有变化，则需要改图。

融合趋势：许多现代 Agent 框架结合了二者优点。例如，可以先进行一个高层次 Plan（计划），然后在每个子任务内部使用 ReAct 循环进行灵活执行。这种“全局计划+局部灵活执行”的模式兼顾了效率和适应性。

#### 在代码辅助任务中，ReAct 如何与代码解释器结合？

在代码辅助任务中，ReAct 与代码解释器的结合形成了一种强大的“试错-验证-修正”循环，使得模型能够像人类程序员一样编写代码、运行测试、并根据错误信息进行调试。

结合机制：

1. 定义代码相关行动：在 ReAct 的行动空间中，专门增加一个 `Execute[代码]` 或 `Run` 行动。当模型认为需要测试一段代码或执行计算时，就调用此行动。系统后端在安全沙箱中执行该代码，并将标准输出（print 内容）、返回值和错误堆栈信息作为 Observation 返回给模型。

2. 典型循环模式：
  - 编写代码：模型在 Thought 中分析需求，然后在 Action 中生成一段 Python 代码，可能是草稿或测试片段。
  - 执行并观察：系统执行代码，返回 Observation。如果代码有错误，Observation 会包含完整的 Traceback。如果没有错误，Observation 会显示输出和返回值。
  - 分析反馈并修正：模型基于 Observation 进行 Thought。如果出错，它会分析错误原因（例如 NameError、TypeError），并决定如何修改代码。然后再次调用 `Execute` 运行修正后的代码。这个循环可以持续进行，直到代码通过测试或达到预期输出。
  - 整合与回答：当代码调试成功后，模型将正确的代码段和运行结果通过 `Finish` 返回给用户。

3. 与搜索行动互补：在代码辅助中，ReAct 还可以结合 `Search` 行动。当模型不确定某个 API 用法或遇到无法解决的 bug 时，它可以先搜索相关文档或 stackoverflow，然后根据搜索结果来修复代码。这完美模拟了程序员“写代码 → 报错 → 查资料 → 修改”的工作流。

4. 多文件与项目管理：更进一步，ReAct 可以通过文件操作行动（如 `WriteFile[path, content]`、`ReadFile[path]`）来管理多文件项目。它可以先生成项目结构，再逐个编写文件，然后执行测试，形成完整的软件开发流程。

优势：

- 将代码生成的“静态”过程转变为“动态”调试闭环，大幅提升复杂代码的正确率。

- 利用代码解释器的精确执行，完全消除了模型在思维链中进行心算或模拟代码运行时所产生的不确定性错误。

- 通过观察真实的错误信息，模型能够像人类一样进行有针对性的调试，而不是盲目猜测。

- 整个编程和调试过程被完整记录，形成可解释的开发日志。

#### ReAct 中的行动空间设计：是固定集合还是开放式？各自的利弊。

行动空间定义了 ReAct 智能体可以执行的操作集合。其设计有两种基本范式：固定集合（封闭式）和开放式。

固定集合：

- 定义：预先定义一组数量有限的、明确的行动类型，如 `Search`、`Lookup`、`Calculator`、`Finish`。每种行动有严格的参数格式。模型被训练/提示只能从这个集合中选择行动。

- 优点：
  - 可控性高：系统行为完全可预测，不会有意外操作。
  - 安全性好：可以精确审计和限制模型能做什么，防止滥用（如执行任意代码）。
  - 解析简单：行动类型和参数格式固定，用正则或简单分类器就能可靠解析。
  - 模型学习成本低：明确的少样本示例即可教会模型。

- 缺点：
  - 灵活性差：无法应对设计时未预见的新需求。面对新工具或新任务，必须修改代码、更新提示。
  - 扩展性受限：每增加一个新工具，都要重新设计提示和解析逻辑。

开放式（动态生成）：

- 定义：模型可以生成任意格式的行动描述，例如自然语言指令，或一个通用的 `Tool[工具名][参数JSON]` 形式。行动不是从预设列表中选择，而是由模型自由生成。解析器或一个中间层负责理解并路由到实际工具。

- 优点：
  - 极度的灵活性：模型可以“发明”新的行动来应对新颖任务，例如组合多个原子工具或创建宏。
  - 工具生态自适应：当工具库动态更新时，无需强制修改提示，模型可通过描述使用新工具。
  - 更通用：适合开放域的、需要大量不同 API 的 Agent 场景。

- 缺点：
  - 解析困难和易出错：模型可能生成无法执行或格式错误的行动，导致失败率高。
  - 安全性风险高：模型可能生成危险操作（如 `DeleteFile`），如果没有严格沙箱，后果严重。
  - 行为不可控：模型可能滥用工具，或产生意料之外的连锁行动。
  - 学习难度大：需要通过大量示例或微调来教会模型如何合理构造各种行动。

实际应用中的趋势：\
多数生产环境采用受限的开放式设计。行动类型是固定的（以保证安全），但参数可以是自然语言或结构化 JSON。例如 `API[api_name][JSON_params]`，这里 api_name 可以是一个较长的可扩展列表，但需要注册。或者采用 “工具选择 + 参数生成” 的两步模式：模型先决定使用哪个工具（封闭选择），然后为该工具生成自由的参数。这平衡了灵活性和可控性。例如 OpenAI 的 function calling 就是这种设计的典范。

#### 如何防止 ReAct 陷入思考-行动的死循环？可以设置哪些保护机制？

ReAct 的迭代特性使其有可能陷入无效的循环，例如反复执行相同搜索却无结果，或在 Yes/No 问题上反复纠结。必须设置多层保护机制。

保护机制：

1. 硬性步数限制（Max Steps）：最基础的保护。设定一个绝对上限（如 10 轮 Thought-Action-Observe）。一旦达到，系统强制终止循环，并要求模型基于现有信息给出最佳答案，或者直接返回“无法完成”。这防止了无限消费 Token。

2. 动作重复检测与惩罚：监控最近的 Action 历史。如果模型连续 N 次（如 3 次）执行完全相同或高度相似的 Action（如相同的搜索查询），说明模型可能陷入了思维定势。可以采取以下措施：
  - 在 Observation 中注入一条系统警告：“你似乎已重复此操作多次，请尝试不同的方法或接受当前信息。”
  - 直接阻止该 Action 的执行，返回一条假观察，引导模型换思路。
  - 强制调用 `Finish` 行动。

3. 无效行动计数与超限：统计无效 Action 的数量（如搜索返回空结果、代码执行报错）。如果无效行动占比超过阈值，表明当前策略可能失效，系统可以介入，建议模型重新评估整体方案或直接向用户求助。

4. 语义循环检测：比字面重复更高级。定期将最近的 Thought 序列交给一个轻量级监控 LLM 或语义相似度模型分析，判断模型是否在相同的话题点上打转，而没有实质推进。如果发现语义循环，可触发反思提示。

5. 时间限制：设置一个总的处理时间上限（如 60 秒）。超时则强制终止，并尝试从已有的部分结果中拼凑回答。

6. 反思触发器：在提示中内置一个“元认知”机制。例如，每经过 3 轮，系统会在 Observation 末尾附加一个反思问题：“请简要评估目前进展：我们是否更接近答案了？是否需要改变策略？” 这迫使模型定期进行自我审视，避免机械循环。

7. 最终保底策略：当强制终止后，系统不会直接丢弃所有信息。它可以将收集到的全部观察和模型生成的思考历史，作为提示输入给一个“总结器”模型，该模型的任务是：“尽管任务未完全解决，请基于以下信息给出一个目前能做到的最佳回答。” 从而提供一个保底的、有信息量的输出。

通过以上多层防御，可以有效遏制 ReAct 的无效循环，确保计算资源被用在刀刃上，并保障系统最终总能给用户一个合理的回应。

#### ReAct 的 token 消耗通常很大，如何通过压缩历史或总结来优化？

ReAct 的每次循环都会显著增加上下文的长度，因为 Thought、Action 和 Observation 不断累积。长上下文不仅大幅增加 token 成本，还可能降低模型在长文本上的推理质量。优化势在必行。

优化策略：

1. 历史压缩（上下文窗口滑动与摘要）：当历史长度超过一个预设阈值时，不直接将完整历史删除（这会丢失重要信息），而是对早期轮次进行摘要。可以使用一个轻量级、快速的 LLM 或通过精心提示让主模型自身在适当时机生成对历史的压缩总结。摘要只保留“为达成目标，到目前为止已获得的关键事实、已确认的决策和未解决的子问题”。然后用这段摘要替换掉早期的详细对话历史，从而释放上下文空间。这个“压缩-替换”过程可以周期性进行。

2. 观察内容精炼：外部工具返回的观察（如搜索摘要）往往包含大量冗余或无关文本。可以在 Observation 返回给模型之前，先用一个小的摘要模型或规则进行精炼，只保留与当前问题最相关的句子。或者，在行动设计时，要求工具返回结构化且精炼的数据，而不是长篇大论的网页全文。例如，搜索引擎返回的 snippets 通常比全文更适合直接注入。

3. 选择性记忆（工作笔记）：如前所述，引入“工作笔记”区域。模型被训练将重要的中间成果（如提取的关键实体、计算出的中间数值、已验证的假设）主动保存到笔记中。而冗长的、过程性的思考（如“让我试试这个查询”）在几轮后便不再重要，可以被安全地移除或压缩。这样，上下文只保留精华，丢弃过程噪声。

4. 分层提示设计：将提示分为不可变的“系统指令和少样本示例”、半固定的“工作笔记”、以及动态的“最近N轮历史”。当需要压缩时，只压缩“最近N轮历史”的早期部分，更新“工作笔记”。系统指令和示例保持不变，保证行为稳定。

5. Token 高效的工具定义：精心设计 Action 和 Observation 的格式，使其尽可能简洁。使用缩写、固定字段名，避免冗长的自然语言描述。例如，用 `Obs[1]: ...` 代替 `Observation 1: ...`。节省的每个 token 在长循环中都会积累成可观的成本优势。

6. 模型内缓存（KV Cache 优化）：从工程角度，利用推理引擎的前缀缓存功能。由于每次循环的上下文只有最后部分变化，前半部分的 Key-Value 缓存可以被复用，从而减少重复计算，间接降低延迟和计算成本。但这不影响 token 数量，仅加速推理。

通过历史压缩、观察精炼和结构化记忆的组合，ReAct 的 token 消耗可以得到有效控制，使其在长周期复杂任务中保持经济可行，同时又不牺牲推理所需的上下文连贯性。

#### 训练模型专门进行 ReAct 式推理，是否比依赖提示更鲁棒？怎么做？

依赖少样本提示（few-shot prompting）让模型遵循 ReAct 模式，是一种快速且无需训练的冷启动方法。但它的鲁棒性受限于模型基础指令遵循能力、提示设计的稳定性以及上下文窗口内的偏差积累。相比之下，通过训练（微调）让模型专门掌握 ReAct 式推理，能带来更深层次的鲁棒性提升，但也要克服一些新的挑战。

为何训练更鲁棒？

1. 行为内化与一致性：通过训练，ReAct 的“思考-行动-观察”交替模式被编码进模型参数。模型不再需要每次从少样本示例中重新“阅读并模仿”这一格式，而是像学会了语法一样自然地产出符合规范的序列。这大大降低了因为提示模板微小变动或上下文过长而导致的格式错误、遗忘行为模式等脆弱性。

2. 更优的策略学习：训练数据可以包含大量多样化的推理轨迹，包括成功路径、从错误中恢复的路径、高效信息检索策略以及何时该停止的决断。模型可以从中学习到更普遍、更优的行动选择策略，而不仅仅是模仿提示中的几个固定例子。例如，它可能学会针对不同类型的问题，自主调整搜索查询的详细程度，或者学会在遇到矛盾信息时优先信任权威来源。

3. 降低提示成本与上下文占用：少样本提示会占用大量宝贵的上下文窗口，限制模型可处理的任务复杂度。训练后的模型不再需要这些示例，释放出的上下文可以用于更长的工作记忆和更复杂的多步交互。

4. 对干扰和对抗输入的抵抗力更强：训练可以使模型对工具返回的噪声、无关信息甚至是恶意注入的内容具备更好的辨别力和鲁棒性，因为它在训练时已经见过类似的反面案例，并学会了相应的处理策略。

如何进行训练（微调）？

1. 构建大规模、高质量的 ReAct 轨迹数据集：这是最关键的一步。数据来源可以包括：
  - 人工标注：专家在模拟环境中执行任务，记录完整的 Thought-Action-Observation 序列。
  - 现有最强模型（如 GPT-4）生成：用少样本提示让顶级模型在大量任务上产生轨迹，然后由人工或自动化规则筛选出高质量、正确、高效的轨迹。
  - 自我对弈与回溯：让模型在环境中自行探索，将成功的轨迹加入数据集，甚至可以从失败的轨迹中截取正确的前缀部分作为训练数据。
  - 数据增强：对现有轨迹中的 Action 参数进行变换（如同义词替换、查询改写），并生成对应的模拟 Observation，扩充数据集。

2. 定义清晰的损失函数与训练目标：训练时，通常只计算模型生成部分（Thought 和 Action）的损失，忽略由环境注入的 Observation 部分（通常用特殊标记区分）。可以引入强化学习（RL）来直接优化任务成功率，但纯粹的监督微调（SFT）已经能带来巨大提升。更高级的是使用 RLHF 或直接偏好优化（DPO），让模型学习人类更偏好的推理风格（简洁、高效、安全）。

3. 课程学习与多任务训练：从简单任务开始，逐步增加任务长度和复杂度。将使用不同工具（搜索、计算器、数据库）的任务混合训练，使模型获得通用的工具使用和推理能力。

4. 迭代式自我改进：用训练好的模型产生新数据，再用这些数据重新训练，逐步提升模型能力，形成数据飞轮。

结论：训练模型进行 ReAct 推理，比纯粹依赖提示在鲁棒性、效率和策略最优性上都有质的飞跃。虽然初期需要投入数据构建和计算资源，但对于追求长期稳定、高性能的 Agent 系统而言，这是必由之路。目前先进模型（如 GPT-4 经过指令微调后）已经表现出很强的 ReAct 能力，这正是大规模训练的结果。

#### 在安全敏感环境中，如何限制 ReAct 的行动范围，防止危险操作？

在安全敏感环境（如金融、医疗、基础设施控制）中部署 ReAct 智能体，对其行动范围进行严格限制是生死攸关的要求。核心原则是最小权限原则和纵深防御。

限制行动范围的机制：

1. 封闭的、受限的行动空间：这是第一道防线。只向模型暴露一组经过严格审计的安全行动。不提供任何通用目的的行动（如“执行任意 Shell 命令”或“调用任意 API”）。每个行动都应是功能单一、参数明确、易于审计的。例如，在银行客服系统中，只允许 `QueryBalance`、`TransactionHistory`、`TransferFunds(amount, to_account)`，且后者需要有金额和次数限制。

2. 参数校验与白名单：对模型生成的行动参数进行严格的后端校验。例如，如果行动是 `Search[query]`，可以对 query 进行关键词过滤，防止模型搜索敏感或违规内容。如果是 `API[api_name][json_params]`，必须校验 `api_name` 是否在预注册的安全清单中，并对 `json_params` 的每个字段进行类型、范围和格式验证，拒绝任何不符合预期 Schema 的调用。

3. 沙箱与虚拟化执行环境：对于必须执行的代码或命令，必须在一个隔离的、资源受限的沙箱环境中进行。沙箱应限制网络访问、文件系统写入权限、系统调用等，确保即使模型生成恶意代码，也无法造成实际危害。例如，代码解释器通常在一个临时的 Docker 容器中运行，任务结束后销毁。

4. 权限分级与用户确认（Human-in-the-Loop）：对不可逆或高风险操作，强制执行人工确认。模型可以提出行动意图（如 `RequestApproval[Action: ...]`），但系统不会自动执行，而是将其呈现给授权用户，待用户批准后才由系统执行。这适用于转账、删除数据、发送邮件等操作。

5. 速率限制与预算控制：限制单位时间内模型可以执行的总行动次数、特定行动的次数、或涉及的成本（如 API 调用费用）。这可以防止模型因陷入循环或恶意攻击而耗尽资源或造成经济损失。

6. 审计日志与异常检测：记录模型的每一次 Thought 和 Action，建立完整的不可篡改的审计轨迹。同时，引入一个并行的安全监控模型或基于规则的异常检测系统，实时分析日志。一旦检测到危险模式（如尝试调用未授权的 API、生成可疑代码），可以立即中断任务，并通知管理员。

7. 模型自身的安全对齐与提示约束：在系统指令和微调中，反复强调安全边界和禁止事项。例如：“你绝对不能执行任何修改系统设置的操作。在转账前必须获得用户明确批准。” 尽管这不是技术上的强制措施，但能从源头上降低模型产生危险意图的概率。

通过这种多层立体防护，可以将 ReAct 智能体的能力“关进笼子里”，使其在强大功能与安全保障之间取得平衡。

#### ReAct 能否处理需要长期规划和行动序列的任务，如“预订酒店+会议”这样的多步事务？

能，但这需要将 ReAct 与更高层次的规划机制相结合，因为原生 ReAct 更擅长动态响应，而非长程严格规划的严格执行。

原生 ReAct 的不足：

对于“预订酒店+会议”这类事务，它需要遵循严格的商业流程：查询酒店 → 选择酒店 → 查询空闲会议室 → 预订二者 → 发送确认邮件。步骤之间有严格的依赖关系，且需要满足多个约束（日期、地点、预算）。原生 ReAct 在每一步都重新审视整个状态，它可能在前几步游刃有余，但随着步骤增加，容易在上下文长度膨胀中丢失总体目标或早期约束，也可能在行动选择上做出次优决策（例如过早预订了不可退款的酒店，导致后续会议时间不符）。

使 ReAct 胜任长程规划任务的方法：

1. 引入高层次计划（Plan）作为全局约束：在开始执行前，先让 LLM 基于任务要求生成一个分步计划。这个计划被存储在“工作记忆”或系统提示中，始终可见。后续的每一轮 ReAct 循环，模型除了进行动态思考外，还需对照计划，检查当前步骤是否在按计划推进，以及是否需要修改计划。这相当于给 ReAct 装上了一个“指南针”。

2. 组合使用“宏观 ReAct”与“微观 ReAct”：使用分层架构。上层是一个“规划智能体”，它以较慢的频率运行，负责任务分解、监控进度和处理重大异常（如酒店售罄）。它通过调用下层多个专门的“执行智能体”来完成子任务（如“酒店预订智能体”、“会议安排智能体”）。每个执行智能体内部可以用 ReAct 循环来完成各自子任务的具体信息检索和操作。这样，长序列被拆解成了多个短序列，由全局规划协调。

3. 状态机与 ReAct 结合：将整个事务流程建模为一个状态机，每个状态代表一个阶段（如“搜索酒店”、“选择酒店”、“确认预订”）。ReAct 在每个状态内部进行相对自由的探索和决策，但状态之间的跳转由规则或上层逻辑严格控制。这确保了整体流程不会偏离正轨，同时保留了在每个阶段内的灵活性。

4. 持久化工作记忆与外部任务列表：在上下文中维护一个结构化的任务清单（Todo List），明确列出“已完成”、“进行中”、“待处理”的子任务。ReAct 的思考过程会显式地引用和更新这个任务列表，确保不遗漏任何步骤。

5. 事务性行动的幂等性与回滚设计：在设计行动空间时，让关键事务性操作支持幂等性和回滚。例如，预订酒店可能有 `PreBook`（暂时锁定）和 `Confirm` 两个行动，这为 ReAct 提供了犯错和回溯的空间。如果后续步骤发现冲突，可以回滚之前的预锁，而不是直接承受损失。

通过上述增强，ReAct 可以从一个“灵活应变但可能短视”的探险家，升级为一个“既有大局观又灵活执行”的项目经理，从而胜任长程、多步的事务性任务。

#### 如何评估一个 ReAct 系统的性能？除了任务成功率，还要看行动效率、准确率等。

评估 ReAct 系统需要从效果、效率、可靠性和质量四个维度进行综合衡量，单一的任务成功率是片面的。

1. 效果指标

- 任务成功率（Success Rate）：最核心的指标，指成功完成任务目标的比例。需明确定义成功的标准（如最终答案正确、事务操作正确完成）。

- 部分完成度：对于复杂任务，评估关键步骤的完成情况。例如，酒店虽预订成功但会议未安排，计为部分成功。

2. 效率指标

- 平均行动步数（Average Steps）：完成任务平均需要的 Think-Act-Observe 循环次数。步数越少，效率越高。应区分有效步数和无效（重试、纠错）步数。

- Token 消耗（Token Cost）：完成任务平均消耗的总 token 数。这是衡量计算成本的关键，直接影响 API 费用和延迟。

- 墙钟时间（Latency）：端到端任务完成时间。并行行动可以降低延迟，但对 token 成本无影响。

- 行动效率比（Action Efficiency Ratio）：成功步数 / 总步数，衡量模型行动的目的性。

3. 准确性指标

- 最终答案的事实准确率（Factual Accuracy）：与标准答案或外部事实源对比的正确率。特别关注幻觉率。

- 工具调用准确性（Tool Call Accuracy）：生成的 Action 格式正确、参数合理的比例。这反映模型对工具的掌握程度。

- 信息检索精度/召回率：模型发起的搜索行动是否高效地获取了相关且全面的信息。

4. 鲁棒性与可靠性指标

- 错误恢复率（Error Recovery Rate）：在遇到无效观察或工具报错后，最终仍能成功完成任务的比例。

- 死循环/超时率：因陷入循环或超出步数/时间限制而强制终止的比例。应越低越好。

- 对提示和环境的敏感性：在略微改变提示模板或工具返回格式时，性能的波动幅度。

5. 过程质量指标

- 推理逻辑合理性：由人类或更强的模型评估 Thought 的逻辑质量，是否清晰、必要、无冗余。

- 可解释性与可追溯性：最终答案中的事实是否能清晰地回溯到某轮 Observation。缺乏溯源的答案可能隐含幻觉风险。

- 安全合规性：在安全敏感场景下，是否存在越权行动、泄露信息等违规记录。

评估方法：结合自动化评测（对数学、代码等有明确标准答案的任务）和 LLM-as-judge（对开放式任务的过程质量评估），并在必要时引入人工评估。建立一个多样化的、涵盖不同难度和领域、包含许多边界情况的基准测试集（Benchmark），才能全面公平地衡量 ReAct 系统的性能。

#### 多智能体 ReAct：多个 ReAct Agent 如何协同工作？

多智能体 ReAct 是将复杂的全局任务分解给多个各司其职的 ReAct 智能体，它们通过通信和协调共同完成任务。这是一种从“单兵作战”到“团队协作”的扩展。

协同架构：

1. 层级式（Manager-Worker）：一个“管理者”智能体（Manager）负责接收总任务，制定高层计划，并将子任务分配给专门的“工人”智能体（Worker）。Manager 本身可能也是一个 ReAct Agent，其行动是“委派任务”。Worker 是专注特定领域的 ReAct Agent（如“搜索专家”、“代码专家”），它们接收子任务，在其内部执行完整的 ReAct 循环，完成后将结果汇报给 Manager。Manager 整合结果，决定下一步计划或直接生成最终答案。这是最清晰、最可控的模式。

2. 对话式/辩论式（Debate/Collaboration）：多个平等的 ReAct 智能体围绕同一个问题，各自独立或半独立地进行探索。它们可以共享一个公共的“公告板”（Blackboard）来发布自己的发现（Observation 或 Conclusion）。一个智能体可以看到其他智能体的发现，并在此基础上进一步推理或提出质疑。或者，它们以“圆桌会议”的形式，每一轮每个智能体都发表一个 Thought 或 Action，然后由“主席”或投票机制决定下一步集体行动。这适合需要多视角、创造性或辩证推理的任务。

3. 流水线式（Pipeline）：任务被分解为固定阶段，每个阶段由一个 ReAct 智能体负责。前一个智能体的最终输出（包括其收集的所有上下文）作为输入传递给下一个智能体。每个智能体在自己的阶段内进行灵活的 ReAct 探索，但上下游之间的交接是结构化的。

协同中的关键机制：

- 通信协议：定义智能体之间如何交换信息。可以是结构化的 JSON（包含意图、内容、证据），也可以是自然语言。结构化更可靠，自然语言更灵活。

- 共享记忆与私有记忆：每个 Worker 应有自己的私有记忆（其内部的 ReAct 历史）。同时，团队应有一个共享的全局工作记忆（如任务列表、已知关键事实），Manager 负责维护，所有 Worker 可读。

- 冲突解决：当不同智能体的发现或结论冲突时，需要有升级和裁决机制。通常由 Manager 负责仲裁，或触发专门的“验证”智能体进行事实核查。

- 动态任务分配：Manager 可以根据 Worker 的当前负载、专长和以往表现，动态分配新任务，实现负载均衡。

多智能体 ReAct 能指数级提升系统处理复杂、大规模任务的能力，但协同开销、通信冗余和死锁风险是其主要挑战。良好的架构设计和清晰的通信协议是成功的关键。

#### 如果外部工具不可靠或延迟高，ReAct 的行为如何调整？

外部工具的不可靠性（返回错误、噪声）和高延迟是现实部署中的常见挑战。ReAct 智能体需要有弹性的应对策略，而不是预设工具总是完美和即时的。

针对不可靠工具的调整：

1. 预期失败并规划备选：在 Thought 阶段，模型应表现出对失败可能性的意识。少样本示例中可以加入：“让我搜索一下 X。如果没找到，我会尝试搜索 Y。” 这使模型将工具调用看作一个试探，而不是必然成功。

2. 主动验证与交叉检查：对于关键信息，不要仅信任单一工具的一次返回。模型可以在 Thought 中计划：“我会从两个不同来源确认这个事实。” 如果第一次搜索返回可疑信息，可执行另一次搜索来验证。

3. 降级与回退策略：当首选工具连续失败时，模型应能主动降级到次优方案。例如：“搜索引擎似乎故障了，让我用内部知识库查询试试，虽然数据可能旧一点。” 或者，如果计算器不可用，它可以尝试用思维链进行估算（并明确说明是估算）。

4. 向用户澄清或求助：当所有尝试均失败，模型不应无限循环，而应触发 `AskUser` 行动，向用户说明困难并请求人工指导。这是最高情商的错误处理方式。

针对高延迟工具的调整：

1. 异步行动与并行化：这是对抗延迟最有效的手段。如第 10 问所述，模型应被训练成识别无依赖的行动，并将其并行发起。系统在后台同时执行多个缓慢的工具调用，结果返回后一并注入上下文。这大大压缩了墙钟时间。

2. 提供进度反馈（流式输出）：对于耗时任务，模型可以在 Thought 中生成进度描述（“正在等待查询结果...”），并通过系统将这种中间状态流式推送给用户，避免用户面对长时间的沉默，提升体验。

3. 设置超时与快速失败：系统为每个工具调用设置严格的超时时间（如 5 秒）。一旦超时，系统自动生成一个“超时”观察返回给模型，而不是无限等待。模型需要从少样本中学会如何应对这个特殊观察，并采取备选方案。

4. 缓存与预取：对于读多写少的外部工具（如搜索引擎、百科 API），可以建立缓存层。相同的查询直接返回缓存结果，显著降低平均延迟。更高级地，Manager 智能体可以基于对任务的理解，在用户提问前就预取可能需要的背景知识。

通过内建对失败和延迟的预期与处理机制，ReAct 系统才能真正从“温室中的演示”走向“现实世界的可靠部署”。

#### ReAct 的自我纠错能力：观察到错误后，如何调整后续推理？

自我纠错是 ReAct 框架的核心优势之一。它不将错误视为终结，而是视作信息，并以此为基础动态调整策略。

纠错过程：

1. 错误识别：错误通过 Observation 显现。这可能是一个工具返回的错误信息（如 `Error: Division by zero`），一个与预期不符的输出，一个空结果，或者是一个与自己先前知识或逻辑链相矛盾的观察。

2. 归因分析（关键 Thought）：观察到错误后，下一个 Thought 的核心任务是诊断错误的根源。模型会被提示去思考：
  - “我的行动格式错了吗？”（解析错误）
  - “我的查询词是否太具体/太模糊/有歧义？”（搜索策略错误）
  - “我之前的假设（某个事实为真）是否错误？”（前提错误）
  - “这个计算为什么会溢出？哦，我用了错误的数据类型。”（逻辑/实现错误）\
    少样本示例对培养这种归因能力至关重要，应展示模型如何从不同错误中分别定位原因。

3. 策略调整：基于归因，模型在下一步 Action 中执行修正。
  - 格式修正：重新按照正确格式生成 Action。
  - 参数调整：修改搜索关键词（更泛化、更具体、使用别称、修正拼写错误），或修改计算表达式。
  - 改变方法：如果一种搜索策略反复失败，则完全换一种信息获取方式，比如从“搜索整个问题”变为“分解实体分别搜索”。
  - 修正前提：如果发现最初的事实假设错误，模型会在 Thought 中明确承认错误，并基于正确的前提开启一条全新的探索路径。这相当于思维图中的回溯。
  - 降级处理：如果因为工具能力限制而无法获取精确值，模型可能转而寻求近似解或向用户说明。

4. 避免重复错误：在调整策略后，模型不仅修正了当前错误，还通过归因学到了一个临时教训（在其上下文窗口内）。它可以避免在后续步骤中重蹈覆辙，比如它可能会记住“这个词有歧义，未来查询需要加限定词”。

自我纠错的鲁棒性边界：LLM 的自我纠错不是万能的。它受到模型自身能力和上下文窗口的限制。如果错误模式太复杂、需要深度逻辑推导才能定位，或模型持续受到确认偏差的影响，纠错可能失败。因此，自我纠错应与外部硬性检查（如代码执行）和超时/步数限制相结合，形成多重保障。

#### ReAct 与强化学习中的 Actor-Critic 是否有概念上的映射？

ReAct 与强化学习（RL）中的 Actor-Critic（演员-评论家）架构在概念上存在深刻且富有启发性的类比，尽管 ReAct 目前主要是通过提示或监督学习实现的。

概念映射：

| ReAct 组件 | Actor-Critic 组件 | 映射关系 |
| --- | --- | --- |
| 智能体 (LLM) | Actor (策略网络) | 二者都是决策核心，负责在当前状态下生成动作（Action）。LLM 基于上下文（状态）输出 Thought 和 Action 序列。 |
| Thought 的内部独白 | Critic 的价值评估 (隐式) | ReAct 的 Thought 除了规划下一个 Action，还经常包含对当前状态、已获信息质量的评估（“这还不够”，“这个来源可靠”）。这种自我评估功能，相当于一个隐式的 Critic，在内部对当前策略和状态价值做出判断。但它是文本化的，而非数值化的价值函数。 |
| 与环境的交互 (Action -> Observation) | 与环境的交互 (Action -> Reward, Next State) | 二者都通过执行动作从外部环境获取反馈。ReAct 得到的是 Observation（文本），RL 得到的是 Reward（数值）和下一个状态。Observation 可被视为一种丰富的信息奖励信号。 |
| 完成任务/获得最终答案 | 获得累积奖励 | 任务成功相当于获得一个大的正奖励。ReAct 目前通常只在最后有成功/失败的二元信号，而 RL 有细粒度的即时奖励。 |

关键区别与启示：

1. 奖励信号的缺失：标准的 ReAct 没有显式的数值奖励。它的“Critic”评价是模糊的、基于语言的。这导致策略优化只能依赖最终结果的监督信号，中间步骤的优劣无法被精细优化。这正是 RL 可以增强 ReAct 的地方。

2. RL 增强 ReAct 的路径：
  - RL Fine-tuning (RLHF/PPO)：我们可以用 RL 来微调 ReAct 策略。任务成功给予正奖励，步数过多或无效行动给予负奖励。Critic 可以是一个独立训练的价值网络（或 LLM 本身加一个价值头），专门学习预测当前状态（上下文）下采取某行动的长期价值。Actor（LLM）则根据 Critic 的反馈优化策略，学会选择更高效、更可能成功的行动序列。
  - Process Reward Model：训练一个模型对每个 Thought-Action 对进行打分（如是否合理、是否推进了任务）。这个分数作为即时奖励，引导 Actor 学习更优的中间推理步骤，而不仅仅是最终答案。

3. Advantage Actor-Critic (A2C) 在 LLM 中的应用：已经有一些研究将 A2C 架构应用于微调 LLM 推理。Critic 评估每个生成步骤的质量，Actor 则生成下一个 token。这种方法有望培养出自我纠错能力更强、推理效率更高的 ReAct 式模型。

因此，ReAct 可以视为一种“语言化的 Actor-Critic”雏形。未来的发展必然是二者深度融合：用 RL 的精确奖励信号来训练 LLM 内部那个目前还很模糊的“Critic”，让其学会评估自身推理过程的价值，从而实现更高效的探索与学习。这是实现能自我改进的 Agent 的关键路径。

---

#### 你认为 ReAct 是通往通用人工智能 Agent 的关键一步吗？还需突破哪些？

ReAct 框架无疑是将 LLM 从被动的文本生成器转变为主动的智能 Agent 道路上的里程碑式的一步，但它本身尚不构成 AGI，而是一个极其重要的原型和方法论基础。

为什么是关键一步：

- 统一了推理与行动：它首次将 LLM 的高级推理能力和外部工具的精确执行能力在单个循环中无缝融合，是“神经”与“符号”系统结合的典范。这让 Agent 既能“想”又能“做”。

- 提供了可解释、可交互的决策框架：ReAct 的 Thought-Action-Observation 轨迹让 Agent 的决策过程透明化，这是人类对 AGI 进行信任、监督和干预的基本前提。

- 证明了“动态自校正”的可行性：它的闭环特性使得 Agent 可以根据环境反馈灵活调整，展现出初步的自我纠错和适应能力，这是智能体的核心标志。

- 催生了丰富的多模态 Agent 应用：ReAct 已成为众多 Agent 框架（LangChain、AutoGPT等）的事实标准交互模式，极大地推动了 Agent 技术的发展。

迈向 AGI Agent，ReAct 还需突破的关键瓶颈：

1. 从反应式到前瞻性的长期规划与分层抽象：当前 ReAct 基本是“走一步看一步”的反应式。AGI 需要能制定长期、抽象的计划，进行分层次思考（目标-策略-战术-执行），并能根据环境变化优雅地重新规划。这需要将 ReAct 与强大的分层规划器、世界模型深度结合。

2. 从语言反馈到统一的多模态、可执行反馈：ReAct 的观察目前主要是文本。AGI 需要能无缝处理视觉、听觉、物理交互等多模态反馈，并能将这些反馈转化为统一的语义理解和行动指令。具身智能是重要发展方向。

3. 从依赖外部奖励到内在动机与持续学习：当前 ReAct 是为一次任务优化。AGI 需要有内在好奇心、主动探索未知、从连续的经验流中持续学习和技能积累的能力。这需要将 ReAct 与元学习、持续学习、好奇心驱动的强化学习等结合，让 Agent 在“生存周期”内越用越聪明。

4. 资源感知与策略性资源分配：AGI 必须意识到自己的计算成本（Token、时间），并能在“花更多时间深思”与“快速给出不错答案”之间做出最优权衡。它需要学会“元认知调控”，在简单问题上不浪费资源。

5. 价值对齐与可解释性治理框架：能力越大，安全与对齐的挑战越大。我们需要一套超越当前“提示约束”的治理框架，让 Agent 不仅行动安全，其内部思考过程（Thought）也符合伦理和规范。可解释性和可审计性需要达到能说服社会监管的程度。

6. 从孤立智能体到协作智能体的社会性：人类智能是社会性的。AGI Agent 应能自然地与人类、与其他 AI 进行高效协作，理解隐含的社交契约，进行谈判、教学和协调。多智能体 ReAct 只是这个方向的起点。

总结：ReAct 是打造 AGI Agent 的完美起点和基础架构，因为它抽象出了智能体与环境交互的最基本循环。但它就像一颗聪明的种子，要长成参天大树（AGI），还需要在长期规划、持续学习、多模态融合、高效资源利用和深度价值对齐等“养分”上取得根本性突破。ReAct 为我们指明了方向：将强大的语言模型与外部世界紧密连接，形成交互闭环。所有未来的突破，都将在这一闭环的基础上展开。
