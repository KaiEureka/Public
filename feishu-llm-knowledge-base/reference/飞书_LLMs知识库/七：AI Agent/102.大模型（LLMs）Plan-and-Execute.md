# 102.大模型（LLMs）Plan-and-Execute

#### 什么是 Plan-and-Execute 范式？它与 ReAct 的根本区别是什么？

Plan-and-Execute 是一种将复杂任务的规划和执行显式分离的 Agent 架构范式。它首先由一个“规划器”对任务目标进行全局分解，生成一份结构化的、包含一系列有序子任务或步骤的“行动计划”，然后将这份计划交给一个“执行器”去逐步执行。这种范式的核心理念是“谋定而后动”，强调在动手之前先构建全局蓝图，以保证最终产出的结构完整性和逻辑一致性。

它与 ReAct 的根本区别在于对“规划”和“执行”的时空关系的处理。

ReAct 将规划和执行高度融合，形成一个实时的、步进的“思考-行动-观察”闭环。它不在行动前制定完整计划，而是每走一步都根据最新的环境反馈来决定下一步怎么走。这赋予它极大的灵活性和动态应变能力，但也使其容易在长程任务中迷失方向，缺乏对全局的掌控。

Plan-and-Execute 则将规划和执行严格分离，先完成规划，再按部就班执行。这种分离带来了几个关键优势：第一，它对最终产出有更强的全局控制和结构保证，特别适合格式严格、步骤明确的复杂任务；第二，它允许在执行前对计划进行审核和修正，高风险场景下可由人类把关；第三，执行过程相对简单、可预测，降低了在每一步都进行复杂推理的成本。其劣势在于对动态变化的适应能力较弱，当环境变化导致初始计划失效时，需要额外的重规划机制来补救。

简单类比，ReAct 像一位经验丰富的即兴爵士乐手，在舞台上根据现场氛围和同伴的演奏实时创造旋律，灵活但不确定；而 Plan-and-Execute 像一位建筑工程师，在施工前必须先完成详细的设计蓝图，然后严格按照图纸建造，确保最终的大楼稳固且符合预期。

#### Plan-and-Execute 的典型流程：先由 Planner 生成完整计划，再由 Executor 逐步执行。

一个完整的 Plan-and-Execute Agent 工作流程，可以清晰地划分为两个宏观阶段和若干个关键环节，形成一个从“战略制定”到“战术执行”的完整闭环。

阶段一：规划

1. 接收任务与上下文：系统接收到用户的原始复杂目标，以及相关的背景信息（如用户画像、环境状态、可用工具列表等）。

2. Planner 生成计划：一个专门的、被提示为“战略规划师”的 LLM 被调用。它的输入是原始任务和上下文，输出是一份结构化、有序的、可执行的“行动计划”。这份计划将复杂目标分解为一系列逻辑依赖的子任务。计划中的每一步通常包含：步骤编号、子目标描述、需要执行的动作类型、动作所需的参数、以及该步骤所依赖的前置步骤。

3. 计划审核与确认：这是一个可选的、但极为重要的步骤。系统将生成的计划呈现给用户或一个独立的审核模块。用户可以在此阶段对计划进行审查、修改或确认。这能有效避免因规划错误导致后续大量无效的执行，尤其在高风险操作中不可或缺。

阶段二：执行

1. Executor 逐步执行：Executor 按顺序读取计划中的每一步。对于每一步，它根据子目标描述和动作类型，执行相应的操作。这可能是调用一个工具（如搜索、计算、代码执行）、生成一段文本，或者向用户发起一个澄清式提问。

2. 局部推理与状态更新：Executor 在执行每一步时，并非完全机械。它通常需要进行小范围的局部推理，例如，将上一步工具返回的结果填入下一步动作的参数中。Executor 还会维护一个“任务状态”，记录已完成的步骤、关键中间结果和当前进度。

3. 观察与评估：每一步执行完毕后，Executor 会评估该步的结果。它需要判断该步是否成功，结果是否满足该子目标的完成标准。

4. 异常处理与重规划触发：如果某一步执行失败，或者结果与预期存在重大偏差，Executor 会将该异常连同当前的任务状态，反馈给 Planner。Planner 被再次调用，基于最新的信息进行“增量重规划”或“全局重规划”，生成一个新版本的计划，替换或追加到原有计划中。然后执行器从更新后的断点继续执行。

5. 任务完成与交付：当计划中所有步骤都已成功完成，或者满足终止条件时，Executor 执行一个最终的整合步骤，将所有子任务的成果组装成用户所需的最终产出。

这个流程通过将“规划”和“执行”解耦，使得系统在结构性和灵活性之间找到了一个优秀的平衡点。

#### 如何设计 Planner 的提示模板，让它输出一个结构化、可执行的计划？

Planner 是整个 Plan-and-Execute 系统的战略大脑。其提示模板的设计，直接决定了生成计划的质量和可执行性。设计目标是引导模型进行严谨、全面、结构化的思考，而不仅仅是罗列一串动作。

核心设计要素

1. 角色设定与目标明确化：必须首先为模型设定一个高度具体的战略规划专家角色，并清晰地定义它的使命。例如，“你是一位资深的项目规划师，你的任务是为给定的用户目标，制定一份详尽、可执行的行动计划。”

2. 注入任务分解的元原则：在提示中明确指导模型如何进行高质量的分解。例如：“请遵循以下原则进行任务分解：① 自顶向下，先识别核心里程碑，再细化具体动作；② 每个子任务必须是一个原子操作，可以被一个工具调用或一个生成动作完成；③ 明确标注子任务之间的逻辑依赖关系；④ 确保所有子任务加在一起，能够完整地实现总目标，不遗漏关键步骤。”

3. 强制要求结构化的输出格式：这是实现自动执行的关键。必须要求模型以固定的、可被程序解析的格式输出计划。最常用的是 JSON，因为它可以清晰表达层级和属性。要求输出的 JSON 数组中，每个对象包含 `step_id`、`goal`、`action_type`、`parameters`、`depends_on`、`expected_outcome` 等字段。这为后续的 Executor 提供了明确的执行指令。

4. 提供高质量、多样化的少样本示例：抽象的指令不如鲜活的例子有效。在提示中提供 1-2 个完整的、从高维目标到详细计划的示例，展示如何正确处理依赖关系、如何将模糊意图转化为具体的工具调用，以及如何覆盖边界情况和失败的应对策略。示例是最好的老师。

5. 注入对可用工具的理解：Planner 在制定计划时，必须清楚地知道 Agent 有哪些工具可用。因此，提示中需要包含所有可用工具的详细描述（名称、功能、参数 Schema）。这使规划不会天马行空，而是建立在可实现的基础之上。

示例提示词片段

```plain text
[系统] 你是一个世界级的任务规划师。你的职责是将一个复杂的用户目标，拆解成一个有序的、可执行的JSON计划。

[任务分解原则]
1. 自顶向下：先识别核心里程碑，再逐步细化每个里程碑下的具体动作。
2. 最小动作：每个子任务应该是一个原子操作。
3. 明确依赖：清晰地指出哪些任务是其他任务的前置条件。
4. 完整覆盖：确保所有子任务完成后，总目标可以被完美达成。

[可用工具]
- search(query): 搜索互联网信息。
- calculator(expression): 计算数学表达式。

[输出格式]
请严格以JSON列表格式输出你的计划，每个元素包含以下字段：
- "step": 步骤编号 (整数)
- "goal": 本步骤要达成的子目标 (字符串)
- "action": 需要执行的具体动作 (字符串)
- "depends_on": 依赖的步骤编号列表 (列表)

[示例]
...

[现在请处理]
总目标：{用户输入}
计划：
```

通过这种精心设计的提示，LLM 能够生成一份既高屋建瓴又脚踏实地、且能被机器自动调度执行的行动计划。

#### 计划的表达格式：自然语言列表、JSON、还是可执行脚本？各自的优缺点。

计划的表达格式是 Planner 和 Executor 之间的接口语言。格式的选择直接决定了系统的自动化程度、健壮性和可调试性。

一、自然语言列表

这是最直接、最简单的方式，计划以“1. 2. 3.” 的编号列表呈现，步骤描述使用自然语言。

- 优点：非常灵活，易于人类阅读和理解，LLM 生成起来也毫无障碍。适合快速原型开发和人类参与的半自动化流程。

- 缺点：机器解析极其困难且脆弱。从中精确提取动作类型和参数需要复杂的正则或 NLP 模型，且模型输出的微小格式偏差都可能导致解析失败，不适合全自动的 Executor。

二、JSON

这是目前工业界最主流、最推荐的结构化表达格式。

- 优点：解析极其简单、可靠。通过 `JSON.parse()` 即可转化为程序可直接使用的数据结构。它可以清晰地表达层级、参数、依赖关系等复杂信息。LLM 已经能够非常成熟地生成符合指定 Schema 的 JSON。

- 缺点：相比自然语言，可读性稍差。生成 JSON 会消耗更多 Token。对 LLM 生成格式的准确性要求较高，但现代模型已能很好满足。

三、可执行脚本

这是最极致的“Plan-as-Code”思想，计划本身就是一段 Python 或 JavaScript 代码。

- 优点：表达力极强，可以自然地处理循环、条件分支、异常处理等复杂逻辑。计划本身就是可执行的，无需额外的解析器。支持复杂的工具编排。

- 缺点：对 LLM 的代码生成能力要求极高，容易产生语法错误或逻辑 bug。存在严重的安全风险，必须进行严格的沙箱隔离。对人类的可读性和可审计性较差。

选择指南

在实际工程中，推荐以 JSON 作为首选。它在“结构化可执行”和“可读易调试”之间取得了最佳平衡。对于需要极高确定性和安全性的场景，可以在 JSON 之上，由后端的编排引擎来确保执行逻辑的严谨性。可执行脚本则更适用于研究性或对灵活性要求极高的沙箱环境中。

#### Executor 在执行每一步时，是否需要进行局部推理？还是机械执行？

Executor 的核心职责是忠实地执行计划，但这并不意味着它是一个完全机械、不懂变通的机器人。高质量的 Executor 在执行每一步时，需要一定程度的局部推理，但它绝不应进行改变整体计划的“全局推理”。

需要局部推理的场景

1. 动态参数填充：这是最常见的推理需求。计划中的某一步可能被定义为“搜索关于 X 的信息”，而 X 的具体值需要依赖前一步的执行结果。Executor 必须能读取上一步的输出，提取出 X 的值，填入当前步骤的参数中。这要求 Executor 具备上下文理解和参数映射的能力。

2. 结果评估与完成度判断：计划中每个子任务有一个“完成标准”。Executor 执行完一个动作后，需要判断动作的结果是否达到了这个标准。是成功、部分成功还是失败？这需要基于对结果文本的语义理解，而非简单的状态码检查。

3. 格式适配与细微调整：当工具返回的结果格式与下一步期望的输入格式不完全匹配时，Executor 可以进行微小的、无损核心语义的格式转换。

禁止全局推理

Executor 的权限边界是：绝不能对计划本身进行修改、调整顺序或决定跳过某个步骤。这种改变整体规划的决策，必须由更高层级的 Planner 通过“重规划”来完成。如果将全局推理权下放给 Executor，就会模糊 Plan-and-Execute 的边界，使其退化为 ReAct，失去其结构性和可控性的优势。

实现方式

Executor 通常由一个被精心提示的 LLM 来担任。提示词中会明确其职责范围：基于“总体计划”、“已完成的步骤及其结果”、“当前待执行的步骤”，生成执行该步骤所需的具体动作指令，并根据执行结果更新任务状态。

因此，一个优秀的 Executor 是一个“戴着镣铐的舞者”，在给定的计划框架内进行智能的、局部的最优执行。

#### 如果执行过程中遇到意外或错误，Plan-and-Execute 如何应对？是否支持重新规划？

处理意外和错误，是区分一个脆弱的线性脚本与一个健壮的自主 Agent 的关键。Plan-and-Execute 对错误的应对，主要依赖于其“重规划”机制，而非放弃或崩溃。

错误的捕获与评估

当 Executor 执行某一步骤时，可能会遭遇多种意外：

- 工具执行错误：如 API 超时、返回错误码、参数不合法。

- 逻辑性失败：工具执行成功，但返回的结果与预期完全不符，例如搜索返回了大量无关信息，使得该子目标无法达成。

Executor 捕获到这些异常后，会将其封装成一个结构化的“失败报告”，其中包含失败的步骤、原始意图、执行的动作以及详细的错误或异常观察。这份报告不是直接抛给用户，而是作为一次“升级求助”，发送给 Planner。

重新规划的机制

接到失败报告后，Planner 会被重新激活，执行一次“重规划”。这次重规划的上下文，除了原始的用户目标外，还包含了所有已经成功完成步骤的摘要，以及最新的失败报告。Planner 基于这些丰富的信息，生成一份修改后的计划。

重规划有两种粒度：

1. 增量重规划：仅对失败步骤及其后续受影响的依赖步骤进行局部调整。例如，将失败的步骤替换为一个替代方案，但保持整体计划结构不变。这是最常见的重规划形式，高效且针对性强。

2. 全局重规划：当失败揭示了原始计划的核心假设有误时，Planner 会推翻大部分甚至全部剩余计划，基于全新的理解生成一份截然不同的计划。

新计划生成后，Executor 从断点（或根据新计划的指示）继续执行。这个“执行-失败-评估-重规划”的闭环，使得 Plan-and-Execute 系统在面对复杂、不确定的环境时，具备了宝贵的韧性。

#### 动态重新规划：在 Plan-and-Execute 中，如何判断是否需要更新计划？

动态重新规划赋予 Agent 在动态环境中自我修正的智慧。但重规划本身有成本，不恰当或过于频繁的重规划反而会降低系统效率和稳定性。因此，如何准确判断“触发时机”至关重要。

触发条件的设计

重规划的触发不应是简单的是非判断，而应是一个基于多维信号的决策矩阵。

1. 子任务执行失败：这是最强、最明确的触发信号。当 Executor 多次尝试执行某个步骤（或其替代方案）后，仍无法达到其完成标准时，必须触发重规划。这避免了在同一个地方反复碰壁。

2. 环境信息的实质性变化：在执行过程中，Agent 可能通过观察获得了一个全新的、颠覆性的信息。这个信息可能与之前的核心假设矛盾，或者揭示了一条更优的路径。例如，在做旅行规划时，突然搜索到目标目的地发生自然灾害，这就触发了全局重规划的必要性。

3. 计划的内在一致性被破坏：当执行某个子任务的结果，使得后续步骤的依赖条件无法满足时，就会产生计划冲突。例如，原计划步骤 5 依赖于步骤 2 生成的一个数字在 100 以内，但步骤 2 实际结果是 150。这个冲突一旦被 Executor 检测到，就应立即触发重规划。

如何避免“抖动”

频繁的、无意义的重规划会导致系统“抖动”，无法稳定推进任务。需要设置抑制机制。

- 设置最小重规划间隔：规定在一次重规划后的 N 个执行步内，除非遇到任务失败，否则不再触发新的重规划。给新计划一个稳定执行的机会。

- 引入成本-收益评估：在执行重规划前，让 Planner 自己进行一次快速的元认知评估：“投入额外的 Token 和延迟来重新制定计划，预计会带来多大的质量提升？”只有当预期收益明确高于其成本时，才启动重规划。

- 锁定核心路径：将计划中已经过验证、且执行顺利的核心主干路径锁死，不允许轻率修改。重规划应更多发生在不确定的、探索性的外围分支上。

通过精细的触发和抑制机制，动态重规划才能成为系统稳定可靠的保障，而非混乱的根源。

#### Plan-and-Execute 与分层 Agent 架构的关系：高层的 Planner 和低层的工具执行器如何交互？

Plan-and-Execute 是分层 Agent 架构最经典、最直观的实现形式。在这种架构中，高层的 Planner 和低层的 Executor 通过定义清晰的接口进行交互，实现了“战略”与“战术”的完美分离。

交互关系与职责分离

- 高层 Planner：是系统的“大脑”，负责战略制定。它接收宏观任务目标，进行全局分解，生成详细的行动计划（JSON 列表）。在出现异常时，它接收 Executor 的升级报告，进行重规划。它不关心底层工具的具体调用细节。

- 低层 Executor：是系统的“手脚”，负责战术执行。它接收 Planner 的输出——一份结构化的行动计划。它按照计划顺序，逐步执行每个步骤。在执行时，它会进行必要的局部推理（如动态参数填充），调用具体的工具，收集执行结果。

交互协议

两者之间的交互通过清晰定义的消息协议来完成，实现了解耦。

1. 下发的消息（计划）：Planner -> Executor。格式为一份结构化的 JSON 计划，包含所有步骤及其元数据。这是 Executor 的行动依据。

2. 上报的消息（状态与异常）：Executor -> Planner。正常执行时，Executor 上报步骤完成状态和关键结果。异常时，上报一份包含失败步骤、失败原因和当前状态的“重规划请求”。

3. 共享的上下文（黑板）：Planner 和 Executor 可以共享一个公共的“任务状态黑板”。Executor 实时更新当前进度、已获取的关键信息和中间产物。Planner 在进行重规划时，可以直接读取这块黑板，获取当前任务的全貌，而不需要 Executor 逐一报告。

这种交互模式的价值

这种分层架构使得系统的各个部分可以独立演化、独立测试。例如，你可以只升级 Executor 的工具调用逻辑，而无需修改 Planner 的规划策略。你也可以在同一个 Planner 下，为不同任务切换不同的 Executor。它完美体现了软件工程中“高内聚、低耦合”的设计原则，是构建复杂、可靠 Agent 系统的不二法门。

#### 比较 Plan-and-Execute 与 BabyAGI、AutoGPT 这类任务驱动 Agent 的异同。

Plan-and-Execute 是一种 Agent 架构范式，而 BabyAGI、AutoGPT 等则是这一范式早期经典的工程实现，它们共同推动了 Agent 从理论走向现实。

相同之处

1. 任务驱动的自主性：它们都是为了完成用户给定的一个开放式的复杂目标，而自动进行任务分解和执行的。

2. 核心逻辑相似：它们都遵循“创建任务列表 -> 按优先级执行任务 -> 根据结果动态添加新任务”这一核心循环，这与 Plan-and-Execute 的“规划-执行-重规划”逻辑一脉相承。

3. 依赖 LLM 进行决策：它们都使用大语言模型作为规划、推理和决策的核心大脑。

关键区别

1. 规划与执行的结构化程度
  - Plan-and-Execute：强调显式的、一次性的全局规划。在行动前生成一份结构完整、逻辑清晰、包含依赖关系的计划。执行过程相对严格，按部就班。
  - BabyAGI / AutoGPT：更倾向于一种动态的、涌现式的任务管理。它们维护一个任务列表，执行完一个任务后，根据结果由 LLM 决策生成新的后续任务，插入到任务列表中。这个过程更加动态和启发式，缺乏一个强约束的全局蓝图。它们的“计划”是在执行过程中不断生长和演化的。

2. 重规划机制
  - Plan-and-Execute：有一个清晰的、从 Executor 到 Planner 的“升级-重规划”机制。当执行遇到重大障碍时，会主动触发一次结构性的重规划。
  - BabyAGI / AutoGPT：其动态任务列表本身就具有重规划的性质。当某个方向走不通时，LLM 在生成后续任务时会自然地避开它。这是一种隐性的、非结构化的调整，而不是一次显式的、全面的重规划。

3. 适用场景与可控性
  - Plan-and-Execute：更适合处理结构清晰、步骤可预见的复杂任务，如撰写长篇报告、执行标准业务流程。它的可控性和可预测性更强。
  - BabyAGI / AutoGPT：更适合于高度开放、探索性强、路径未知的任务，如“创建一个自动化的市场情报系统”。但它们的行为也更不稳定，更容易陷入无效循环。

Plan-and-Execute 可以看作是 BabyAGI/AutoGPT 这些早期探索的经验总结和架构升华，它吸收了它们的核心思想，但通过更严谨的规划抽象，解决了它们行为不稳定、难以预测的痛点。

#### 在复杂任务（如软件工程、旅行规划）中，Plan-and-Execute 为何能比 ReAct 更高效、更易管理？

在软件工程、旅行规划这类结构复杂、约束多、对最终产出有严格要求的任务中，Plan-and-Execute 的架构优势会被急剧放大，展现出远超 ReAct 的效率和管理性。

一、全局一致性与结构性保证

- 软件工程：开发一个功能模块，需要遵循严格的架构设计、接口定义和编码规范。Plan-and-Execute 可以在规划阶段就生成详细的技术方案，明确模块划分、数据流和依赖关系。这确保了最终代码的结构清晰、逻辑自洽。而 ReAct 边走边看，很容易写出逻辑混乱、结构松散的代码。

- 旅行规划：一个行程需要满足时间、预算、交通接驳、景点开放时间等一系列硬约束。Plan-and-Execute 可以先出全局行程表，一次性校验所有约束，避免出现“预订了无法衔接的航班”这种致命错误。ReAct 的逐步探索则极易陷入局部最优，而忽略了全局冲突。

二、管理与协作的效率

- 可审计与可干预性：Plan-and-Execute 生成的详细计划，本身就是一份完美的沟通文档。在软件工程中，技术负责人可以在编码前审查开发计划；在旅行规划中，用户可以提前看到完整行程并提出修改。这种“事前审批”比 ReAct 的“事后检查”要高效和安全得多。

- 任务的并行分解：全局计划可以清晰地识别出哪些子任务没有依赖关系。在软件工程中，不同模块的开发可以并行分配给不同 Agent；在旅行规划中，机票和酒店的预订可以同时进行。而 ReAct 的串行模式则难以实现这种并行优化。

- 执行的可预测性：Plan-and-Execute 的执行过程是透明的，每一步都可追踪。这使得对复杂任务的进度管理和成本估算成为可能。ReAct 的探索轨迹则充满了不确定性，难以进行有效的项目管理。

三、成本控制

ReAct 的每一轮交互都需要 LLM 进行复杂的推理，导致 Token 消耗高、延迟大。对于步骤繁多的大型任务，这个成本极高。而 Plan-and-Execute 将一个复杂任务分解为一系列简单步骤后，执行这些步骤所需的推理成本可以大大降低。简单步骤甚至可以用更便宜的模型或规则来完成，只有在规划和重规划时才调用昂贵的强大模型。这使得处理复杂任务的成本更加可控。

总而言之，当任务的复杂度和对最终产出的结构性要求超过某个阈值后，Plan-and-Execute 的“谋定而后动”哲学在效率、可控性、质量和成本上都展现出了压倒性的优势。它是解决复杂工程问题的利器。

#### 计划粒度：如何决定计划的详细程度？是抽象高层步骤还是精细到具体操作？

计划粒度的选择，是 Plan-and-Execute 系统设计中最核心的权衡之一。它直接决定了计划的灵活性、可执行性、以及后续执行器进行局部推理的复杂度。粒度过粗会导致执行器无从下手，需要大量的自主决策，从而退化为类似ReAct的即兴执行；粒度过细则使计划变得冗长、脆弱，对动态环境的适应力下降，且增加了规划的难度和成本。

决定粒度的核心因素

1. 执行器的能力边界：这是决定粒度的首要因素。执行器是一个能够进行复杂局部推理的LLM，还是一个只能机械执行简单指令的规则引擎？如果执行器本身具备较强的推理能力，那么计划粒度可以适当放粗，将“如何做”的细节留给执行器去自主决策；反之，如果执行器能力较弱，计划就必须精细到每一步具体操作，以减少其犯错的可能。

2. 任务的确定性与结构化程度：对于那些步骤明确、流程固定的任务（如合同审核、标准报表生成），可以采用更精细的粒度，将每一步操作和期望输出都定义清楚。这样做能保证执行的一致性和结果的可预测性。而对于探索性强、路径不确定的任务（如市场情报收集、开放域研究），粗粒度的计划更为合适，它只定义里程碑和子目标，而将实现路径的选择权留给执行器，从而保留了应对未知情况的灵活性。

3. 工具的原子性与复杂度：如果系统提供的工具都是简单、原语级的（如`search`、`calculator`），那么计划步骤通常会比较细，接近于具体的工具调用。如果工具本身就是复合的、高层次的（如`generate_report`、`analyze_sentiment`），那么计划步骤就可以更粗，因为一个工具调用就能完成大量工作。

4. 错误成本与安全要求：对于高风险、高成本的步骤（如资金转账、发送批量邮件），计划粒度必须精细到足以进行人工或规则审核的程度。模糊的抽象步骤是不可接受的。而对于低风险的信息查询，则可以给予执行器更大的自由度。

最佳实践：分层粒度策略

在实践中，通常不采用单一的全局粒度，而是采用分层粒度策略，让计划在不同层级上展现出不同的详细程度。

- 顶层计划：由Planner生成，面向人类审核和全局调度。这一层的粒度较粗，描述的是“做什么”（子目标、里程碑），而非“具体怎么做”。例如，“步骤1：收集市场数据；步骤2：分析竞争对手；步骤3：生成报告”。

- 底层展开：Executor在接收到一个粗粒度的子任务后，如果发现自己无法一步完成，可以在执行时进行一次轻量级的“局部规划”，将该子任务进一步分解为一系列更细粒度的原子操作，然后逐步执行。这种“动态细化”结合了全局计划的结构性和局部执行的灵活性。

通过这种分层粒度的设计，Plan-and-Execute系统得以在“结构性”和“灵活性”之间取得最佳平衡。

#### 计划中的依赖关系管理：后续步骤依赖前面步骤的结果，计划中如何体现和传递？

依赖关系是计划的灵魂。没有依赖关系，一系列子任务就只是一盘散沙；有了清晰的依赖关系，它们才能构成一个逻辑有序、可被高效执行的行动图谱。在Plan-and-Execute中，依赖关系的体现和传递涉及计划的“静态定义”和执行的“动态数据流”两个层面。

一、在计划中静态体现依赖关系

Planner在生成计划时，必须显式地定义任务之间的依赖关系。这通常通过在计划的每个步骤中包含一个 `depends_on` 字段来实现。这个字段是一个列表，包含了当前步骤执行前必须完成的步骤编号。

例如，一个JSON格式的计划步骤可以这样定义：

```json
{
  "step": 3,
  "goal": "基于收集到的信息，生成分析报告",
  "action": "generate_report",
  "parameters": {
    "data": "{{step1_output}}",
    "strategy": "{{step2_output}}"
  },
  "depends_on": [1, 2]
}
```

这种静态定义使得Executor在调度时，能够准确地判断哪些任务已经就绪（其所有依赖项都已完成），哪些任务还需要等待。它也是实现任务并行化的基础：所有`depends_on`为空或依赖项已全部完成的步骤，可以并行执行。

二、执行时动态传递依赖数据

仅仅知道“步骤3依赖步骤1和2”是不够的，步骤3在执行时还需要步骤1和2产生的具体数据。这是动态数据流要解决的问题。

1. 上下文变量传递：最直接的方法是让Executor在执行过程中维护一个“任务状态”或“上下文变量池”。当一个步骤执行完毕，它产生的重要结果（如搜索得到的实体、计算出的数值）会被以键值对的形式存入这个变量池（例如：`context["step1_output"] = ...`）。后续步骤在执行时，会从这个变量池中读取所需的值，动态填充到自己的参数中。

2. 模板化参数引用：在计划的参数定义中，可以使用模板语法来引用前面步骤的输出。如上例中的 `"data": "{{step1_output}}"`。Executor在实例化该步骤时，会解析这个模板，从上下文变量池中提取对应的值进行替换。这使得计划本身就定义了数据流。

3. 隐式依赖与数据流：有时步骤之间的依赖不是显式的步骤编号，而是语义上的“需要上一步的结果”。Executor的局部推理能力在这里发挥作用：它可以根据上下文的语义和当前步骤的意图，智能地选择使用哪个历史结果。但这需要Executor有较强的理解能力，风险也更高。

通过“静态依赖声明”和“动态上下文传递”的结合，Plan-and-Execute系统能够优雅地管理复杂的任务编排，确保数据在步骤间正确、高效地流动。

#### Plan-and-Execute 的并行执行：无依赖的子任务能否并行执行以提高效率？

绝对可以，而且并行执行是Plan-and-Execute范式相较于ReAct等串行范式的一个重大工程优势。将复杂任务分解为带有依赖关系的有向无环图，其核心目的之一，就是识别出可以同时进行的独立分支，从而大幅缩短端到端任务的墙钟时间。

如何实现并行执行

1. 依赖图分析：Planner生成的计划，本质上是一个任务依赖图（通常是DAG）。Executor（或一个专门的调度器）在准备执行时，首先会分析这个图。它会找出所有`depends_on`列表为空、或其所有依赖项都已经完成且成功的“就绪”步骤。

2. 异步任务调度：系统将所有就绪的步骤同时提交给执行层。在现代Agent框架中，这通常通过异步I/O、协程或多线程来实现。例如，一个需要同时查询“北京天气”和“上海天气”的步骤，会被打包成两个独立的工具调用任务，并发地发送给后端。

3. 结果收集与同步：调度器等待所有并行任务完成（或超时/失败）。当所有并发任务都返回结果后，调度器会将这些结果更新到全局上下文变量池中，并解锁那些依赖这些结果的新步骤，开始下一轮调度。

实际案例

考虑一个“撰写A公司与B公司竞品分析报告”的任务。计划中可能包含以下步骤：

- 步骤1: 收集A公司产品信息

- 步骤2: 收集B公司产品信息

- 步骤3: 收集市场整体趋势（无依赖）

- 步骤4: 基于步骤1、2、3的结果进行对比分析

在这个计划中，步骤1、2、3之间没有任何依赖关系，完全可以并行执行。系统可以同时发起三次搜索，等待它们全部返回后，再启动步骤4。这比先查A、再查B、最后查C的串行模式要快得多。

挑战与注意事项

- 资源限制：并行任务数必须受限于系统的资源上限（如API并发限制、GPU显存）。无限制的并行可能导致资源耗尽或触发外部服务的速率限制。

- 错误隔离：一个并行任务的失败，不应无差别地取消其他所有任务。调度器应能优雅地处理部分失败，只将受影响的任务标记为失败，并允许其他成功的并行任务继续。

- 依赖关系的准确性：这是并行执行安全性的基础。如果Planner错误地判断两个任务没有依赖，而实际上它们有隐性的数据依赖，那么并行执行就会出错。这要求Planner对任务的逻辑理解非常准确。

并行执行是Plan-and-Execute从“能完成任务”迈向“能高效完成任务”的关键一步。

#### 如何评估生成的计划质量？除了可执行性，还需考虑优化性（步骤最少、资源最省）。

一份高质量的“行动计划”，不仅是“能做对”，更应该是“能高效、优雅地做对”。评估计划质量，需要跳出“最终任务是否完成”的结果导向，深入到计划本身的逻辑结构、资源编排和鲁棒性之中。

评估维度与指标

1. 正确性与完整性

- 逻辑正确性：计划中的步骤顺序是否符合现实世界的逻辑？依赖关系是否准确无误？

- 目标覆盖度：计划完成后，是否能完整、无遗漏地达成用户的总目标？是否涵盖了所有的硬性约束和必要条件？

2. 优化性与效率

- 步骤最少化：计划是否以最精简的步骤完成了任务？是否存在不必要的冗余或迂回？例如，两个可以合并的搜索操作是否被设计成了两个独立步骤。

- 资源最省：计划是否优先选择了低成本的工具和数据源？例如，在能通过内部知识库回答时，是否避免了昂贵的外部搜索API调用？

- 并行化程度：计划是否最大化了可并行执行的任务，以减少总体的端到端延迟？

- 工具选择的最优性：在每个步骤中，所选择的工具是否是完成该子目标的最优选择？是否存在“用牛刀杀鸡”的情况？

3. 鲁棒性与容错性

- 异常处理：计划中是否预见了关键步骤可能失败的情况，并设计了备选方案或降级策略？

- 适应性：计划的结构是否过于刚性，以至于在环境发生微小变化时就会整体失效？一个高质量的计划应该有一定的弹性。

评估方法

1. 基于LLM的专家评判：设计一个评估提示词，让一个强大的LLM扮演“规划评审专家”的角色。将生成的计划与原始任务目标一同输入，要求它从上述几个维度进行量化打分（如1-5分），并给出详细的评分理由。这是目前最全面、最灵活的评估方式。

2. 模拟/沙箱执行评估：在一个模拟环境中，反复执行这个计划（可以注入随机扰动），统计其最终的任务成功率、平均完成步数和资源消耗。这是最客观的评估，但成本较高。

3. 与最优基线对比：对于标准任务，可以人工设计一份“最优计划”作为黄金基线。评估生成的计划与基线在结构、步骤数、资源选择上的相似度。

通过这套多维度的评估体系，我们可以引导Planner不仅仅追求“能做对”，更追求“做得巧”。

---

#### 在 Plan-and-Execute 中，LLM 的 Planner 是否可以利用外部知识或过去的经验来优化计划？

绝对是必须的，而且这是让Planner从一个只会凭空想象的“新手”成长为一个经验丰富的“专家”的关键。Planner的优化能力，正是通过持续吸收外部知识和积累自身经验来实现的。

利用外部知识

在生成计划之前或期间，Planner可以主动地、或由系统被动地注入外部知识，以制定更合理、更专业的计划。

1. 检索增强规划：Planner在接收到任务后，可以先调用一个检索工具（如内部知识库、维基百科），搜索与任务相关的“最佳实践”、“案例模板”或“标准作业流程”。例如，在制定一个“软件开发项目计划”时，它可以先搜索“敏捷开发标准流程”，然后将这些专业的方法论融入到自己生成的计划中。这使得它的计划不是凭空捏造，而是有领域知识支撑的。

2. 实时环境感知：Planner可以调用API来获取当前的真实环境状态，而不是依赖模型内部可能过时的知识。例如，在制定旅行计划时，它可以实时查询天气、航班状态和酒店空房情况，并基于这些实时信息来优化路线和选择。

利用过去的经验

这需要与Agent的长期记忆系统深度集成。

1. 检索历史成功计划：当遇到一个新任务时，Planner首先去长期记忆库中，通过语义相似度检索过去执行成功的类似任务计划。它将检索到的历史计划作为“少样本示例”或“参考模板”，注入到自己的规划提示词中。这类似于人类专家在遇到新问题时，会先回想自己或同事之前解决类似问题的方案，然后进行适配。

2. 吸收反思教训：更重要的是，Planner可以从过去的失败中学习。Reflexion等反思机制产生的“经验教训”被存储在长期记忆中。当Planner准备生成一个涉及“社交媒体分析”的计划时，它会检索到一条历史教训：“在进行社交媒体分析时，不要只依赖一个数据源，要交叉验证。” Planner会将这条教训融入新计划，主动加入“交叉验证”的步骤，从而避免重蹈覆辙。

通过这种方式，Plan-and-Execute系统就具备了持续学习和自我进化的能力，其规划质量会随着经验的积累而不断提高。

#### 如何将 Plan-and-Execute 与记忆结合：执行结果存入记忆，供未来计划参考。

这是赋予Agent持续成长能力的关键一步。通过将Plan-and-Execute与长期记忆系统深度结合，Agent不仅能解决眼前的任务，还能从中“学习”，让过去的成功经验和失败教训成为未来解决问题的宝贵财富。

一、执行结果的持久化

当一个Plan-and-Execute任务执行完毕（无论成功或失败），其完整的执行轨迹——包括初始计划、每一步的执行动作、工具返回的观察、以及最终的结果——都会被序列化并存入长期记忆库。存储时通常包含以下信息：

- 任务摘要：原始用户目标的一段简洁文本描述。

- 计划的结构化副本：例如，JSON格式的计划本身。

- 执行轨迹：完整的ReAct式日志，用于深度分析和复盘。

- 结果与反馈：任务成功/失败标签，以及任何用户或系统的反馈信号。

二、利用记忆优化未来计划

当新任务到来时，Planner不再是孤立地思考，而是会积极主动地从记忆库中检索相关信息，用于优化当前的规划。

1. 检索相似任务计划作为模板：Planner首先使用新任务的文本描述，去向量数据库中检索最相似的几个历史成功任务。它将这些历史任务的计划作为宝贵的“参考案例”，在提示中展示给LLM，并指令：“请参考以下类似任务的成功计划，为新任务生成一份计划。”这能极大缩短规划时间，并提升计划的质量和可行性。

2. 检索失败案例的教训以避免重蹈覆辙：Planner同时检索与新任务相关的失败案例及其“反思教训”。它会得到这样的信息：“上次做竞品分析时，因为没有对搜索结果的时效性进行限制，导致获取了过时信息。这次规划时，应该主动加入时效性约束。”这使得Planner能够主动规避已知的陷阱。

3. 检索执行过程中的关键中间产物：有时，新任务可能直接需要以前任务产生的某个中间结果。例如，用户问：“根据上次的市场分析报告，再帮我做一份销售策略。” Planner会从记忆中检索出“上次市场分析报告”的文本，将其作为已知上下文，直接基于它来规划新任务，而不是从头开始。

这种与记忆的深度融合，将Plan-and-Execute从一次性的工具升级为一个能够积累经验、持续进化的学习系统。

#### 多轮 Plan-and-Execute：当任务由多个阶段组成，如何分阶段规划和执行？

现实世界中的复杂任务，往往无法在单一轮次的规划中完美解决。它们通常具有多个存在显著上下文鸿沟的阶段。对这类任务进行分阶段规划和执行，是保持系统可控性和结构性的关键。

实现机制：增量式规划

当任务被识别为跨越多个宏观阶段时，Planner不应尝试一次性规划所有细节，而应采用“增量式规划”的策略。

1. 第一阶段规划：Planner首先只对第一阶段进行详细规划，生成一个可执行的JSON计划。对于后续阶段，它只生成一些抽象的、占位符式的里程碑描述，而不展开具体步骤。例如，对于一个“开发一个Web应用”的任务，第一阶段计划是“搭建开发环境、设计数据库模型”，而后续的“实现前端页面”和“部署上线”则仅作为高层目标被列出。

2. 执行与状态收集：Executor执行第一阶段计划，完成该阶段的所有子任务。执行完毕后，它会生成一份详细的“阶段完成报告”，其中包含了所有已完成工作的成果、产生的关键数据和文件、以及当前项目的状态快照。

3. 基于新状态的后续规划：触发第二阶段的规划。此时，Planner的输入不仅包括原始的总目标，更包括了第一阶段生成的“阶段完成报告”。这使得它能够基于最新的、最真实的项目进展来规划第二阶段。例如，它在规划前端页面时，已经知道了数据库的具体表结构。

4. 循环直到任务完成：这个“规划->执行->报告->再规划”的循环会持续进行，直到项目的所有宏观阶段都完成。

关键好处

- 降低单次规划复杂度：避免了要求模型一次性生成一个包含数百个步骤的超长计划。

- 提高计划的准确性：后续阶段的规划是基于前阶段真实的、非预期的产出进行的，避免了基于过时或错误假设进行规划的风险。

- 保持上下文窗口可控：每次规划都只需要加载当前阶段的详细上下文，而不是整个项目的完整历史。

这种分阶段、增量的方式，使得Plan-and-Execute能够胜任超长周期的、持续演化的大型项目。

#### Plan-and-Execute 的局限性是什么？在高度不确定的环境下是否仍然适用？

Plan-and-Execute范式虽然强大，但并非银弹，它的结构性既是其最大优势，也是其最根本的局限所在。

主要局限性

1. 对动态环境的脆弱性：Plan-and-Execute的核心假设是，可以在行动前制定一个相对稳定的蓝图。但在环境瞬息万变的情况下（如实时股票交易、多智能体博弈），预设计划可能迅速过时。它需要依赖重规划机制来补救，但如果环境变化太快，重规划的频率和成本将高到不可接受。

2. 初始规划的冷启动问题：当面对一个全新的、毫无先验知识的领域时，Planner可能因缺乏必要的信息而无法做出任何有价值的规划。它需要一个探索性的“信息收集”阶段，而这本身就更适合使用ReAct等灵活范式来完成。

3. 处理高度抽象和模糊的目标：如果用户目标本身就是模糊的（如“让我变得更健康”），Planner无法直接将其分解为具体的步骤，因为它不了解用户的具体情况、偏好和约束。此时需要与用户进行多轮澄清对话，而ReAct的交互式模式更为擅长。

在高度不确定环境下的适用性

在高度不确定的环境中，Plan-and-Execute单独使用是低效且脆弱的，但它可以作为混合架构中的高层战略指导。

1. “粗粒度计划 + ReAct执行”的混合模式：这是最成功的融合方案。Planner只负责生成一个高层次的、抽象的计划，定义任务的大阶段和里程碑，但不规定具体实现路径。在每个阶段内部，由ReAct Agent进行灵活的、动态的探索和执行。这样，既有了总体方向的把握，又保留了应对不确定性的能力。

2. 作为备选方案的生成器：Planner可以被用来生成多个可能的行动计划，而不是一个。然后由一个ReAct Agent在执行过程中，根据环境反馈动态地在这些备选计划之间切换。

3. 利用重规划实现适应性：在不确定性较高的环境中，可以适当提高重规划的灵敏度，允许Planner在接收到关键新信息时，更频繁地修正计划。将重规划视为一个常态化的适应手段，而非异常处理。

因此，Plan-and-Execute的未来不在于取代ReAct，而在于与ReAct等灵活范式深度融合，形成“战略上藐视，战术上重视”的强大混合智能体。

#### 如何处理计划中的模糊步骤？是否应让 Executor 自主澄清？

在执行过程中遇到模糊步骤，是Plan-and-Execute系统面临的常见挑战。一个模糊的步骤描述，如“分析数据并给出建议”，对于人类可能是容易理解的，但对Executor来说却是无法直接执行的。处理这种模糊性，需要Executor具备自主澄清和局部规划的能力。

应对策略

1. Executor的局部规划能力：Executor不应是一个机械的执行者，而应具备一定的局部推理和规划能力。当接收到一个模糊的步骤时，它首先会尝试进行“局部展开”——自己在内心（或通过一次轻量级的LLM调用）将这个模糊目标分解为一系列具体的原子操作，然后逐步执行。例如，对于“分析数据”，它可能自我分解为：1) 读取数据文件，2) 计算关键统计指标，3) 与历史数据对比，4) 生成图表，5) 撰写分析摘要。这个过程完全在Executor内部完成，无需向上反馈。

2. 向用户或Planner请求澄清：如果模糊步骤的意图过于宽泛，以至于Executor无法确定其真正的子目标，或者存在多种可行的、但路径完全不同的实现方式，Executor应主动发起一个澄清式提问。这个提问可以发送给用户（如果设计如此），也可以像错误升级一样，作为一条“澄清请求”消息发送给Planner。Planner会基于更全局的视角，返回一条更具体的指令。

3. 利用上下文和记忆自动消歧：Executor会结合整个任务的上下文、用户画像、以及长期记忆中相关的历史信息，来自动推断模糊步骤的最合理意图。例如，如果用户画像是“高级数据分析师”，那么“分析数据”就意味着进行复杂的统计建模；如果用户画像是“市场专员”，则可能只意味着绘制一些销售趋势图。

设计权衡

将澄清能力放在Executor端，能减少与用户或Planner的交互轮次，提高效率，但也增加了Executor做出错误决策的风险。因此，一种稳妥的设计模式是：Executor先进行自主澄清尝试，如果它对自己生成的局部计划有高置信度（例如，LLM自我评估的得分），就继续执行；如果置信度低，则触发升级，请求外部帮助。这结合了局部智能与全局控制。

#### 能否使用代码生成作为计划？即 Plan 就是一段程序，执行器是代码解释器。

绝对可以，这正是“Plan-as-Code”的前沿思想。它将 Agent 规划的形式从模糊、易歧义的自然语言，升级为精确、可执行、可验证的代码。在这种范式下，Planner 不再是生成一份人类阅读的计划文档，而是生成一个可以由机器直接执行的程序脚本。

优势

1. 极高的精确性与确定性：代码的语义是确定且无歧义的。这从根本上消除了自然语言计划中常见的模糊性和误解。

2. 原生支持复杂逻辑：循环、条件分支、异常处理（try-catch）、函数调用等复杂控制流，是编程语言与生俱来的能力，而用自然语言描述则极其繁琐且不可靠。这使得“计划”能够应对复杂的、动态的任务编排。

3. 可验证与可测试：生成的计划（代码）可以像普通软件一样被静态分析、单元测试和集成测试。一个被验证为有效的“计划函数”，可以被封装成模块，在不同的任务中反复调用。

4. 高效的错误处理与恢复：代码中的`try-catch`块可以提供结构化、可编程的错误处理逻辑，远比自然语言的“如果失败则尝试…”要可靠。

实现方式与挑战

Planner被要求直接生成Python代码，该代码调用预定义好的工具函数（如`search(query)`、`calculator(expr)`等）。生成的代码被送入一个安全的沙箱化代码解释器（如Docker容器中的Python解释器）执行。

核心挑战：

- LLM代码生成可靠性：这要求Planner有极高的代码生成准确率，否则一个微小的语法错误就会导致整个计划崩溃。

- 安全风险：生成的代码可能包含恶意或危险的操作。必须在一个严格隔离、权限最小化的沙箱中执行，并对所有外部调用进行审计。

- 可审计性与透明度：一段逻辑复杂的代码对人类审查员来说，不如自然语言计划那样一目了然。这给人工审核和信任带来挑战。

- 错误定位与恢复：当代码执行失败时，LLM需要能够根据错误日志，自行生成“代码补丁”来修复错误（即重规划），这要求LLM具备强大的调试能力。

结论：Plan-as-Code代表了Agent规划从“艺术”走向“工程”的终极形态。虽然在可靠性和安全性方面仍有挑战，但它在需要高确定性和复杂逻辑的场景中展现出了巨大的潜力，是Plan-and-Execute范式的最终演化方向之一。
