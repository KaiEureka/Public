# 105.大模型（LLMs）Agent 框架（LangChain Agent、AutoGen）

#### LangChain 的 Agent 抽象是如何设计的？AgentExecutor 的作用是什么？

LangChain 的 Agent 设计哲学是将大语言模型的推理能力与外部工具执行解耦，并通过一个统一的执行环境将它们编排在一起。这种抽象的核心是“Agent（智能体）”和“AgentExecutor（执行器）”的分离。

Agent 抽象

在 LangChain 中，Agent 并不是一个具体的类，而是一个逻辑概念，它的核心职责是决策。Agent 负责接收输入和历史上下文，然后输出一个结构化的“行动指令”。这个行动指令包含两个关键信息：要调用哪个工具，以及用什么参数。Agent 本身不执行任何操作，它只负责“想”和“决策”。LangChain 支持多种类型的 Agent，如 OpenAI Functions Agent、ReAct Agent 等，它们的主要区别在于如何构造提示、解析输出以及进行决策，但它们都遵循同一套抽象接口。

AgentExecutor 的作用

AgentExecutor 是 LangChain Agent 架构中真正的运行引擎，它负责实现“思考-行动-观察”的循环。AgentExecutor 将 Agent（决策大脑）和 Tools（执行手脚）连接起来，形成一个闭环。它的核心职责包括：

1. 循环控制：它运行一个死循环，不断地调用 Agent 进行决策。当 Agent 返回一个表示“任务完成”的最终答案时，执行器终止循环并将结果返回给用户。

2. 工具执行与观察注入：当 Agent 决定调用某个工具时，AgentExecutor 负责解析出工具名和参数，实际执行该工具，并捕获其返回结果。然后，它将这个结果格式化为一个“观察”文本，注入回对话上下文，供 Agent 进行下一轮思考。

3. 安全与边界控制：AgentExecutor 负责强制执行最大步数限制、处理工具调用超时和错误。这些边界控制是防止 Agent 陷入无限循环或产生错误的关键。

4. 提示词构造与上下文管理：它负责将系统提示、对话历史、工具描述和用户输入组装成完整的 Prompt，发送给 LLM。

通过这种 Agent 与 AgentExecutor 的分离，LangChain 实现了决策与执行的解耦，开发者可以灵活地替换不同的决策策略（Agent 类型），而无需改变执行层的逻辑。

#### LangChain 中的 Agent 类型有哪些？OpenAI Functions Agent、ReAct Agent、Structured Chat Agent 的区别和适用场景。

LangChain 提供了多种 Agent 类型，以适应不同模型的能力和任务需求。它们的核心区别在于：如何构造提示、如何解析模型输出、以及如何利用模型特定能力。

1. OpenAI Functions Agent

这是专为 OpenAI 的 Function Calling 能力设计的 Agent。它不依赖传统的“Thought/Action”文本解析，而是利用模型原生支持的 `tools` 参数和 `tool_calls` 响应格式。

- 工作机制：提示中包含了工具的定义（JSON Schema）。模型直接输出一个结构化的 `tool_calls` 对象，包含函数名和参数。AgentExecutor 解析这个对象，执行工具，并将结果以 `role: "tool"` 的消息返回。

- 优点：极其可靠、无歧义，因为模型被专门训练来输出这种格式。支持并行工具调用。

- 适用场景：在使用 OpenAI 最新模型（GPT-3.5-turbo-0613 及更高版本）时，这是首选方案。适用于所有需要工具调用的通用场景。

2. ReAct Agent

这是最经典、最通用的 Agent 类型。它通过提示工程，引导模型生成“Thought（思考）”、“Action（行动）”、“Observation（观察）”的文本序列。

- 工作机制：提示词中包含一个详细的模板，告诉模型如何以这种交替格式输出。AgentExecutor 解析文本，提取出最新的 Action 指令，执行工具，然后将结果作为 Observation 追加回对话历史。

- 优点：模型无关，可以在任何支持指令遵循的 LLM 上使用，包括开源模型。其 Thought 过程完全透明，便于调试。

- 缺点：依赖于文本解析，格式错误可能导致执行失败。不支持原生并行调用。

- 适用场景：使用非 OpenAI 模型、需要高度可解释性的推理过程、或需要精细控制思考步骤的复杂多步任务。

3. Structured Chat Agent

这是一种支持多参数工具的高级 Agent，它将工具的参数 Schema 编码到提示中，允许模型在一次调用中为工具提供复杂的、结构化的输入。

- 工作机制：它的提示词包含了工具的参数 Schema 描述。模型可以生成包含结构化动作的文本，如 `Action: Search` 然后换行后跟 `Action Input: {"query": "...", "source": "web"}`。

- 优点：能够处理需要复杂参数的工具，比简单的单参数 ReAct Agent 能力更强。

- 适用场景：当你有多个工具，且它们的输入参数结构复杂（例如，需要嵌套对象或数组）时，这个 Agent 比基础的 ReAct Agent 更胜任。

#### 在 LangChain 中，如何定义一个 Tool？需要实现哪些接口？

在 LangChain 中，工具（Tool）是 Agent 与外部世界交互的唯一接口。一个设计良好的工具，能让 LLM 准确理解其功能和使用方式。

核心接口与定义方式

定义 Tool 最经典的方式是继承 `BaseTool` 类，并实现其核心方法。同时，LangChain 也提供了 `@tool` 装饰器，用最简洁的方式将普通函数封装为 Tool。

无论哪种方式，一个 Tool 的定义都包含以下几个关键部分：

1. `name` (str)\
   工具的唯一标识符。LLM 在决策时，会用这个名称来指定要调用的工具。名称应简洁、描述性强，最好使用动词-名词结构，如 `search_documents`、`calculator`。

2. `description` (str)\
   这是最重要的字段。它是 LLM 理解该工具功能、适用场景和参数含义的唯一依据。一个好的描述必须包含：

- 功能说明：工具做什么。

- 使用场景：什么时候应该用这个工具，而不是其他工具。

- 参数描述：清晰的语义和格式要求。

- 能力边界：这个工具不能做什么。

3. `args_schema` (Pydantic BaseModel)\
   定义工具输入参数的结构化 Schema。使用 Pydantic 模型来精确描述每个参数的类型、是否必需、以及描述信息。这使得 LLM 能够生成符合格式的参数，并且 LangChain 可以自动校验。

4. `_run` 或 `_arun` 方法\
   工具的核心执行逻辑。`_run` 是同步执行方法，接收参数，执行实际操作，并返回一个字符串结果。这个返回的字符串就是 LLM 下一次思考时看到的“观察”。

示例代码片段

```python
from langchain.tools import BaseTool
from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    query: str = Field(description="搜索关键词")

class CustomSearchTool(BaseTool):
    name: str = "search_web"
    description: str = "用于搜索互联网信息。当需要最新资料或时事时使用。"
    args_schema: type[BaseModel] = SearchInput

    def _run(self, query: str) -> str:
        # 这里是实际的搜索逻辑
        result = call_search_api(query)
        return result
```

通过这样严谨的定义，LLM 就能够像查阅 API 文档一样理解并使用我们的工具。

#### LangChain Agent 的工具选择机制：模型如何决定调用哪个工具？提示是如何构造的？

LangChain Agent 的工具选择，本质上是 LLM 在阅读了一段精心构造的提示词后，进行的一次“意图分类”和“槽位填充”的联合推理。其核心在于提示词的构造。

提示词的构造逻辑

当 AgentExecutor 准备调用 LLM 时，它会将以下所有信息组装成一个庞大的提示。

1. 系统级指令（前缀）：这部分在提示的最开头，定义了 Agent 的行为准则。例如：“你是一个智能助手。你可以使用以下工具来帮助回答用户问题。请严格遵循 Thought/Action 格式。”

2. 工具描述（核心）：所有可用工具的 `name` 和 `description` 被清晰地列出。每一条工具描述都像一篇微型 API 文档，详细阐述了该工具的功能、使用场景和参数要求。这是 LLM 进行选择的唯一依据。例如：

```plain text
你可以使用以下工具：
search_web: 用于搜索互联网信息，参数 query: 搜索关键词。
calculator: 用于计算数学表达式，参数 expression: 数学表达式。
```

3. 对话历史：当前会话中的所有消息，包括用户的问题、模型之前的思考、执行的动作以及工具返回的观察。

4. 格式指令（后缀）：这部分定义了 LLM 应该如何输出它的决策。对于 ReAct Agent，它会强制要求模型以 `Thought: ...` 和 `Action: ...` 的格式输出。对于 Functions Agent，则要求输出合法的函数调用 JSON。

模型如何决策

当 LLM 接收到这个庞大的提示后，它会逐 Token 地生成响应。在其内部，自注意力机制会同时处理所有信息。模型的“决策过程”是隐式完成的：它会将用户问题、对话历史的语义，与每个工具的 `description` 进行匹配。如果它判断用户的意图最符合某个工具的能力描述，并且它能够从对话历史中提取出该工具所需的参数，那么它就会选择这个工具，并按照格式指令生成相应的 Action。

例如，如果用户问“帮我算一下 123 乘以 456”，模型会将这句话与 `calculator` 工具的描述进行高权重匹配，因为该描述中提到了“计算数学表达式”。同时，它会从用户的话中提取出 `123 * 456` 作为参数。

这个过程是完全端到端的，LLM 在一次前向传播中同时完成了工具选择和参数提取。

#### AutoGen 的核心理念是什么？它的多 Agent 对话模式与传统 Agent 框架有何不同？

AutoGen 的核心理念是：将多 Agent 协作建模为对话驱动的计算图。它不试图让单个超级 Agent 完成所有事情，而是通过定义多个具有不同角色和能力的 Agent，让它们在结构化的对话中相互协作，共同解决复杂任务。

与传统 Agent 框架的核心区别

传统 Agent 框架（如早期 LangChain Agent）通常以单 Agent 为中心，其工作模式是“思考-行动-观察”的自我循环。即使需要多个工具，也是由一个 Agent 在内部进行串行或并行的调用。这种模式类似于一个人独自完成所有工作。

AutoGen 则转向多 Agent 对话协作。它将任务解决过程转变为多个 Agent 之间的对话流。这带来了几个根本性的改变：

1. 从单体思考到群体协作：复杂任务被自然地分解。一个 Agent 作为“规划者”分解任务，另一个 Agent 作为“执行者”调用工具，还有 Agent 作为“批评者”审查结果。它们在对话中传递信息，形成高效的协作网络。

2. 对话本身即是工作流：Agent 之间的对话不仅仅是通信，更是任务的调度和执行机制。一个 Agent 向另一个 Agent 发送消息，可以是委派一个子任务、请求一个信息、或者提供反馈。这种模式非常灵活，开发者可以自定义复杂的对话流。

3. 支持人类作为一等公民：AutoGen 原生地支持将人类用户作为一个特殊的 Agent（`UserProxyAgent`）嵌入到对话循环中。人类可以在任何节点介入，提供指导、批准操作或回答问题。这使得人机协同变得极其自然和强大。

4. 灵活的对话模式：AutoGen 提供了 `GroupChat` 和 `Manager Agent` 两种核心协调机制，前者模拟自由讨论，后者提供层级控制。这种灵活性允许开发者根据任务的确定性和复杂度选择最合适的协作模式。

总结而言，AutoGen 将 AI 从“单兵作战”的助手，升级为“团队协作”的同事，通过对话将智能进行连接和放大。

#### AutoGen 中如何定义 Agent 的角色和能力？UserProxyAgent 和 AssistantAgent 的职责。

在 AutoGen 中，每个 Agent 都是一个独立的实体，其角色和行为由一套精心设计的配置定义。这些配置共同构成了 Agent 的“个性”和“能力”。

定义 Agent 的核心参数

1. `name`：Agent 的唯一标识符，在对话和日志中使用。

2. `system_message`：这是最关键的部分，是一个用自然语言书写的、高度定制的系统提示。它定义了 Agent 的角色、专长、职责、行为准则以及与其它 Agent 的交互方式。这就像为每个 Agent 编写了一份专属的“员工手册”。

3. `llm_config`：指定驱动此 Agent 的大语言模型，包括模型名称、API 密钥等。AutoGen 支持为团队中的不同 Agent 分配不同的 LLM，以实现成本与性能的最优组合。

4. `code_execution_config`：如果 Agent 需要执行代码，可以为其配置代码执行环境（如 Docker 容器），并提供执行结果。

5. `function_map` / `tools`：为 Agent 注册可调用的工具函数。这使得 Agent 可以通过生成函数调用来执行特定操作，如搜索网络、读写文件等。

两个核心角色的职责

1. `AssistantAgent`：这是典型的“思考者”和“执行者”。它由 LLM 驱动，负责理解任务、生成计划、编写代码、调用工具和进行推理。它不直接与外部世界交互，而是通过发送消息（如建议调用某个函数）来驱动系统。它的角色类似于团队中的“技术专家”。

2. `UserProxyAgent`：这是人类用户或外部系统在 Agent 对话中的“全权代表”。它的核心职责是执行 `AssistantAgent` 提出的、需要与现实世界交互的操作。当 `AssistantAgent` 建议执行一个工具调用或一段代码时，`UserProxyAgent` 会实际去执行它，并将执行结果返回给对话。它也可以代表人类用户向 `AssistantAgent` 发起初始提问或提供反馈。它的角色类似于“项目经理”与“环境交互接口”的结合。

两者的协作模式非常清晰：`UserProxyAgent` 代表用户提出需求，`AssistantAgent` 负责思考和规划，并请求 `UserProxyAgent` 去执行具体操作，`UserProxyAgent` 执行后将结果反馈给 `AssistantAgent`，如此循环，直至任务完成。

#### 在 AutoGen 中，GroupChat 和 GroupChatManager 如何协调多 Agent 对话？

GroupChat 和 GroupChatManager 是 AutoGen 实现复杂多 Agent 协作的核心机制，它们提供了一种去中心化但可控的对话协调方式。

GroupChat：一个共享的对话空间

`GroupChat` 可以被理解为一个容纳了所有参与者的“聊天室”。所有 Agent 的消息都发送到这个共享空间中，每个 Agent 都能看到完整的对话历史。这为去中心化的、自发的协作提供了基础。

GroupChatManager：聪明的会议主持人

`GroupChatManager` 是一个特殊的 Agent，它负责管理 `GroupChat` 的进行。它的核心职责不是参与内容讨论，而是决定在每一轮中，由哪位 Agent 来发言。它扮演了“聪明的会议主持人”的角色。

协调机制

`GroupChatManager` 的发言权管理机制是其精髓。在每一轮对话中，它都会根据预设的 `speaker_selection_method` 来决定下一轮的发言人。

1. `auto` (默认)：`GroupChatManager` 自身也会调用 LLM。它会分析当前的对话历史，判断下一步最需要哪种角色的输入来推进任务。例如，如果上一个发言者提出了一个需要代码执行的问题，`GroupChatManager` 可能会选择 `AssistantAgent` 或 `UserProxyAgent` 作为下一个发言者。这种智能调度使得对话能聚焦于任务本身，效率很高。

2. `round_robin`：Agent 按照一个预定义的顺序轮流发言。这种方式简单可控，适合流程固定的任务。

3. `random`：随机选择下一个发言者，用于某些需要探索性的场景。

4. `manual`：由人类用户来决定下一个发言者。

特色：允许发言者指定下一个发言者\
除了 `GroupChatManager` 的集中调度，AutoGen 还有一个独特的机制：一个 Agent 在结束自己的发言时，可以直接指定下一个发言者。这通过发送一个特殊的系统消息来实现，例如“接下来，请由产品经理Agent来评审这个设计”。这种方式使得 Agent 之间可以进行更直接、更高效的协作，实现任务流的自动传递。

`GroupChat` 和 `GroupChatManager` 的组合，为多 Agent 协作提供了一种既灵活又可控的协调范式。

#### 比较 LangChain Agent 和 AutoGen 在架构灵活性、易用性和可扩展性方面的异同。

LangChain Agent 和 AutoGen 是当前构建 LLM Agent 的两大主流框架，但它们的核心理念和设计哲学截然不同，导致在灵活性、易用性和可扩展性上各有侧重。

架构灵活性

- LangChain Agent：灵活性体现在其对底层 LLM 和工具的高度抽象和可替换性。它是一个庞大的生态，你可以通过简单的配置，灵活地切换不同的 LLM 提供商、不同的 Agent 类型、不同的记忆组件和检索器。这种灵活性使它成为快速集成和实验各种 AI 组件的理想平台。

- AutoGen：灵活性则体现在多 Agent 协作模式的深度定制上。它不强求单一的 Agent 架构，而是允许开发者像导演一样，设计 Agent 之间的对话流、角色和交互协议。你可以构建层级式、分布式、辩论式等任意复杂的协作拓扑。它的灵活性在于对“协作流程”的塑造。

易用性

- LangChain Agent：对于单 Agent 的简单任务，LangChain 提供了开箱即用的封装，能够快速启动。但当任务变复杂，需要精细调试时，其背后大量的自动 prompt 拼装和隐式逻辑会让调试变得非常困难，开发者很难看清“模型到底看到了什么”。

- AutoGen：概念模型更加清晰和直观。将 Agent 定义为不同的角色，通过对话来协作，这非常符合人类对团队工作的直觉。开发者可以清楚地看到每个 Agent 的 System Prompt 和它们之间的通信历史，调试过程更加透明和直接。

可扩展性

- LangChain Agent：其生态优势使其具有极强的“横向扩展”能力。因为它的核心是对各种组件的标准封装，你可以轻松地将 LangChain 的检索器、记忆组件、以及庞大的工具和模型库，与 LangGraph（用于复杂工作流）等框架集成。

- AutoGen：其可扩展性体现在“垂直深入”上。一旦你接受了它的多 Agent 对话理念，你可以通过增加 Agent 数量、细化角色分工、优化对话协议，来无限地提升系统解决超复杂任务的能力。其扩展性是沿着“团队协作复杂度”这个维度展开的。

总结：LangChain Agent 是一个工具集成和模型调度的超级平台，适合“我需要快速接入很多工具和模型”的场景。AutoGen 则是一个多 Agent 协作的导演工作室，适合“我需要一个团队来完成一项复杂的、多步骤的任务”的场景。

#### 什么是 LangGraph？它如何支持构建有状态、多步骤的 Agent 工作流？

LangGraph 是 LangChain 生态中的新一代框架，它专门用于解决构建有状态、多步骤、带有循环和条件分支的复杂 Agent 工作流的问题。

LangGraph 的核心思想

LangGraph 将 Agent 的工作流抽象为一个有向循环图。图中的“节点”代表一个计算步骤（例如，调用 LLM、执行一个工具、进行一个判断），而“边”则代表从一个步骤到下一个步骤的流程。这个抽象完美地匹配了像 ReAct 这样的循环范式，也支持更复杂的、非线性的多 Agent 交互。

如何支持复杂工作流

1. 状态图：LangGraph 将整个工作流的状态（包括对话历史、中间变量等）封装在一个共享的 `State` 对象中。每个节点函数接收这个 `State`，并返回一个更新后的 `State`。这使得数据在整个复杂工作流中的传递变得清晰可控。

2. 节点与边：开发者通过定义不同的节点（Node）来封装各种任务逻辑。例如，一个 `call_agent` 节点用于调用 LLM，一个 `execute_tool` 节点用于执行工具。然后，通过添加边（Edge）来定义任务流转。除了普通的边，还有条件边，它允许根据上一步的输出状态，动态地决定下一步跳转到哪个节点。例如，如果 LLM 的决策是“调用工具”，就走向工具节点；如果是“最终答案”，就走向结束节点。

3. 内置循环与持久化：由于图本身可以是循环的，LangGraph 自然支持 Agent 的“思考-行动-观察”循环。更重要的是，LangGraph 提供了强大的检查点和持久化功能。它能自动保存每个步骤完成后的图状态。这意味着，当工作流因意外中断后，可以从最近的检查点恢复运行，而不是从头开始。这对于长时间运行的高成本任务至关重要。

与传统 LangChain Agent 的对比

传统的 `AgentExecutor` 是一个黑盒的、固定的循环。开发者很难介入其内部流程。而 LangGraph 将这个黑盒打开了，变成了一张透明的、可完全由开发者定制的“工作流蓝图”。这使得你可以构建任意复杂的 Agent 拓扑，比如在调用 LLM 之前强制进行输入安全检查，或者在得到最终答案后强制进行事实性校验。

因此，LangGraph 是 LangChain 从“简单自动化”走向“复杂、可靠的生产级 Agent 应用”的关键一步。

#### LangSmith 在 Agent 调试和追踪中的作用是什么？

LangSmith 是 LangChain 官方推出的全生命周期 DevOps 平台，专门用于 LLM 应用的开发、调试、测试和监控。对于行为复杂、难以预测的 Agent 而言，LangSmith 提供了至关重要的可视化能力。

核心作用

1. 端到端的执行追踪与可视化：这是 LangSmith 最核心的功能。每当你的 Agent 运行一次任务，LangSmith 都会记录下完整的“执行轨迹”。这份轨迹包含了与 LLM 的每一次交互、每一步的思考（Thought）、调用的每一个工具、工具返回的观察、以及最终的结果。它将这些信息以清晰的、层级展开的 UI 展示出来。开发者可以一目了然地看到 Agent 的完整决策链路：它在哪一步选择了哪个工具？它传给工具的参数是什么？它如何根据工具返回的结果进行下一步思考？

2. 强大的调试能力：当 Agent 的行为不符合预期时，开发者不再需要对着终端日志大海捞针。在 LangSmith 的界面中，可以直接查看任何一次调用的完整 Prompt 和响应。更重要的是，你可以将一次失败的执行轨迹一键添加到测试集中，或者基于此创建一个新的实验，快速迭代你的 Prompt 或代码。

3. 自动化测试与评估：LangSmith 允许开发者创建和运行自动化测试流水线。你可以将历史执行的轨迹作为黄金基准，然后在新版本 Agent 上重放相同的输入，通过 LLM 或自定义指标来比较输出的质量。这为 Agent 的持续集成和迭代提供了量化依据。

4. 实时监控与反馈分析：在应用上线后，LangSmith 可以实时收集所有执行轨迹和用户反馈。开发者可以监控关键指标（如成功率、延迟、成本），并对特定类型的失败案例进行聚合分析。这为线上系统的稳定运行和持续优化提供了数据支持。

总之，LangSmith 为 Agent 的开发过程带来了如同传统软件开发中“日志、断点调试、单元测试、性能监控”一样的能力，是将 LLM Agent 从“实验性原型”推向“生产级应用”的关键基础设施。

#### 在 AutoGen 中，如何实现人类参与（Human-in-the-Loop）的交互模式？如何配置？

Human-in-the-Loop 是 AutoGen 的核心设计理念之一，它将人类用户无缝地嵌入到多 Agent 对话流中，使其成为协作网络中的一个一等公民。这通过 `UserProxyAgent` 及其配置来实现。

实现机制

`UserProxyAgent` 是代表人类用户在对话中的代理。它的核心职责是执行 `AssistantAgent` 提出的、需要与现实世界交互的操作，并代表人类用户向其他 Agent 提问或提供反馈。其交互模式的关键配置在于 `human_input_mode` 参数，它决定了人类在对话中的介入程度。

`human_input_mode` 的三种模式

1. `"ALWAYS"`：这是最高级别的介入模式。每当 `UserProxyAgent` 收到一条来自其他 Agent 的、期待回复的消息时，它都会暂停并等待人类用户从终端输入实际的回复内容。这适用于需要对每一步决策都进行人工把控的极高风险场景，例如，AI 生成的每一封对外邮件都需经人工确认后发送。

2. `"TERMINATE"`：这是最常用的模式。`UserProxyAgent` 在大多数情况下会自动处理来自其他 Agent 的消息，例如自动执行代码或确认请求。只有当对话状态达到一个“终止条件”时（例如，`AssistantAgent` 发送了一条包含 "TERMINATE" 关键词的消息），它才会停下来，将最终结果呈现给人类用户，并询问用户是否同意终止任务。这种模式在“自动化执行”和“关键节点人工审核”之间取得了极佳的平衡。

3. `"NEVER"`：此模式下，`UserProxyAgent` 完全自主运行，永远不会主动请求人类输入。它仅根据预设的逻辑和其他 Agent 的消息来自动响应。适用于完全自动化的、低风险的批处理任务。

配置示例

```python
from autogen import UserProxyAgent

user_proxy = UserProxyAgent(
    name="user_proxy",
    human_input_mode="TERMINATE",  # 在TERMINATE时请求人类介入
    max_consecutive_auto_reply=10,  # 最大自动回复次数，防止死循环
    code_execution_config={
        "work_dir": "coding",
        "use_docker": False,        # 是否使用Docker沙箱
    },
    system_message="你是一个代表人类用户的代理，负责执行代码和请求。"
)
```

人类介入的具体场景

1. 请求批准：`AssistantAgent` 可以在消息中明确要求人类批准。例如，在生成一个投资组合后，它会发送“TERMINATE”，`UserProxyAgent` 便会暂停并将方案呈现给用户，由用户决定是否接受。

2. 澄清与提问：当 `AssistantAgent` 需要更多信息时，它可以向 `UserProxyAgent` 发送一个包含具体问题的消息。如果 `human_input_mode` 为 "ALWAYS"，用户将直接看到问题并回答。

3. 异常与错误处理：如果 `AssistantAgent` 的代码执行失败，`UserProxyAgent` 会收到错误报告，并可以自动将其反馈给 `AssistantAgent` 进行修正。在 "TERMINATE" 模式下，如果修正多次失败，它会请求人类介入判断。

通过这种灵活的人类参与模式，AutoGen 将 AI 的高效与人类的智慧完美结合，构建出既强大又可控的智能系统。

#### LangChain 的 Memory 模块如何与 Agent 集成？ConversationBufferMemory、SummaryMemory 等的使用。

LangChain 的 Memory 模块为 Agent 提供了跨轮次对话的上下文维护能力。没有记忆，Agent 就是一条只有七秒记忆的鱼，无法处理多轮交互。

集成机制

LangChain 的 Memory 模块与 Agent 的集成主要通过 `AgentExecutor` 来实现。`AgentExecutor` 在初始化时接受一个 `memory` 对象。在每次调用 Agent 时，它都会将当前会话的交互消息自动读入和写出到记忆中。

常用 Memory 类型及其使用场景

1. `ConversationBufferMemory`\
   这是最简单、最直接的内存形式。它将对话中的所有 Human 和 AI 消息都完整地保存在一个列表中，并将整个列表作为上下文注入到下一次 LLM 调用的提示中。它的优点是信息无损，缺点是 Token 消耗会随着对话增长而线性增加，最终导致成本过高或超出模型上下文窗口。它适用于非常短期的、对话轮次可控的场景。

2. `ConversationSummaryMemory`\
   为了解决 Buffer Memory 的无限膨胀问题，Summary Memory 会使用一个独立的 LLM 调用来对历史对话进行实时摘要。每当历史消息达到一定长度，它就会被压缩成一段简短的摘要文本，存储在记忆中。这使得记忆的大小相对恒定，不受对话轮次影响。但它会丢失细节，且摘要过程本身有成本。

3. `ConversationBufferWindowMemory`\
   这是 Buffer 和 Summary 的折中方案。它只保留最近 K 轮（一个窗口）的完整交互历史。这既保留了对最近上下文的精确记忆，又避免了 Token 的无限增长。它适用于需要最近几轮上下文、但对更早历史不敏感的场景，如客服对话。

4. `VectorStoreRetokenMemory`\
   这是一种更高级的记忆形式。它不存储对话的顺序文本，而是将历史对话内容进行 Embedding 后存入向量数据库。当 Agent 需要回忆时，它会用当前的用户查询作为检索词，从向量库中检索出最相关的几段历史记忆，并将其注入上下文。这种方式可以精准地从海量历史中找到相关信息，信息密度高，但实现复杂度和成本也更高。

如何选择\
选择哪种 Memory 取决于你的任务对历史信息的需求是精确（Buffer）、概括（Summary）还是相关（VectorStore）。在实际项目中，常常会组合使用，例如用 `ConversationBufferWindowMemory` 维护最近对话，同时用 `ConversationSummaryMemory` 维护早期的摘要。

#### AutoGen 的代码执行器（Code Executor）是如何工作的？支持哪些沙箱环境？

代码执行能力是 AutoGen 强大功能的核心之一，它允许 `AssistantAgent` 直接生成并执行 Python 代码，然后将运行结果反馈到对话中，形成一个强大的、自动化的纠错和迭代闭环。

工作原理：生成-执行-反馈的闭环

1. 生成：`AssistantAgent` 在推理过程中，如果判断需要代码来解决问题（如进行复杂计算、数据处理、绘图），它会生成一段完整的 Python 代码，通常包裹在 Markdown 代码块（`python ...`）中。

2. 转发与执行：`UserProxyAgent` 收到包含代码的消息后，会触发它的代码执行模块。它将代码提取出来，发送给配置好的代码执行器。

3. 执行与结果捕获：代码执行器在一个隔离的环境中运行这段代码。它捕获代码的标准输出、标准错误和最终返回值。

4. 反馈与迭代：执行结果（无论是成功输出还是错误日志）会被格式化后，作为一条新的消息发送回对话历史。`AssistantAgent` 会阅读这些反馈。如果代码运行出错，它会像一个经验丰富的程序员一样，分析错误信息，尝试修正代码，并再次生成。这个“生成-执行-纠错”的循环可以自动重复，直到代码成功运行。

支持的沙箱环境

代码执行的安全性至关重要，因此 AutoGen 支持多种执行环境，从最安全到最便捷依次为：

1. Docker：这是生产环境的首选。AutoGen 会在指定的 Docker 镜像中创建一个隔离的容器来执行代码。容器拥有独立的文件系统、网络和进程空间。代码执行完成后，容器可以被立即销毁。这提供了最高级别的安全性，能有效防止恶意代码或错误的 `rm -rf /` 对宿主系统造成破坏。

2. 本地命令行 (Local)：代码直接在宿主系统的子进程中执行。这种方式速度最快，成本最低，但安全性极低。它只适用于完全可信的代码生成环境或本地开发调试，绝不能用于处理不可信的外部输入。

3. Jupyter Kernel：AutoGen 可以连接到一个 Jupyter Notebook 内核来执行代码。这种方式支持交互式编程，非常适合数据分析和探索性任务。

4. 自定义执行器：开发者可以通过实现 `CodeExecutor` 接口，接入自己的代码执行服务，例如内部的云函数平台。

配置示例

```python
code_execution_config = {
    "executor": "autogen.coding.DockerCommandLineCodeExecutor",
    "timeout": 60,  # 代码超时时间（秒）
    "work_dir": "workspace",
    "image": "python:3.11-slim",
}
```

通过这种设计，AutoGen 的 Agent 不仅会“说”代码，还能真正“跑”代码，并基于结果进行反思，极大地提升了其在编程、数据科学等领域的实用性。

#### 如何使用 LangChain 实现一个能够自主搜索互联网的 Agent？需要哪些工具和链？

构建一个能够自主上网的 Agent，需要赋予它两种核心能力：理解任务并制定搜索计划的能力，以及执行搜索和浏览网页的能力。这涉及到工具的配置和 Agent 的组装。

所需的核心工具

1. `WebSearchTool` 或 `TavilySearch`：这是最核心的工具，用于根据查询关键词去搜索引擎获取一系列相关网页的 URL、标题和摘要。Tavily 是一个专门为 AI Agent 设计的搜索 API，它返回的结果更结构化，便于 LLM 处理。

2. `WebBrowserTool` 或 `ScrapeTool`：搜索工具只返回摘要，信息量有限。当 Agent 判断需要深入阅读某个具体网页时，就需要这个工具。它能接收一个 URL，抓取该页面的完整 HTML 内容，并提取出核心的纯文本返回给 Agent。

实现步骤

1. 定义工具：首先，将上述搜索和浏览功能封装成 LangChain 的 `Tool` 对象。对于搜索，可以使用 `TavilySearchResults` 或 `DuckDuckGoSearchRun`。对于网页抓取，可以使用 `AsyncHtmlLoader` 和 `Html2TextTransformer` 的组合，或封装好的 `WebBaseLoader`。

2. 创建 Agent：选择适合处理多步复杂任务的 Agent 类型，如 `create_openai_functions_agent` 或 `create_react_agent`。Functions Agent 调用更可靠，是首选。

3. 配置提示词：在 Agent 的 System Prompt 中明确其工作流程。例如：“你的任务是回答用户的问题。你可以使用搜索工具来获取信息。如果搜索结果的摘要不够详细，请使用网页浏览工具打开具体链接阅读全文。你必须基于找到的真实信息来回答，不要编造。”

4. 组装并执行：将 LLM、工具列表和 Prompt 组合起来，创建 `AgentExecutor`。然后调用 `executor.invoke`，传入用户的问题。

Agent 的典型工作流程

1. 分析问题：Agent 收到“帮我查一下2024年诺贝尔物理学奖得主是谁”，它的 Thought 会分析：“需要最新信息，应该用搜索工具。”

2. 执行搜索：它调用 `WebSearchTool`，传入查询“2024年诺贝尔物理学奖得主”。

3. 分析结果：它收到搜索结果摘要，如“2024年诺贝尔物理学奖授予John Hopfield和Geoffrey Hinton...”。它可能在 Thought 中判断：“信息已足够明确，可以回答。”

4. （可选）深入浏览：如果信息不足或需要更多细节，它会调用 `WebBrowserTool` 并传入一个搜索结果的 URL，阅读完整文章。

5. 生成答案：基于收集到的信息，它生成最终答案返回给用户。

通过这个流程，Agent 就具备了自主上网探索和研究的能力。

#### 在 AutoGen 中，Agent 之间如何传递结构化数据（如 JSON）而不仅仅是文本？

虽然 AutoGen 中的 Agent 通信看起来是自然语言对话，但其底层机制完全支持并鼓励传递结构化数据。这种能力使得 Agent 之间的协作可以像微服务架构一样精确和高效。

传递结构化数据的方法

1. 在消息文本中直接嵌入 JSON

这是最直接、最简单的方法。一个 Agent 生成 JSON 字符串，并将其作为消息内容的一部分发送。接收方 Agent 可以依靠其 LLM 的解析能力，从文本中理解这段 JSON。但这种方法存在风险：LLM 在长对话中可能忘记或在引用时出错。

2. 利用函数/工具调用机制传递结构化参数

这是最可靠、最标准的方法。在 AutoGen 中，Agent 被配置为可以注册一系列可调用的工具函数。当一个 Agent 需要请求另一个 Agent 执行某个操作并传递结构化参数时，它会生成一个符合函数签名的结构化调用。这类似于 OpenAI 的 Function Calling。接收方 Agent 的代码执行器会处理这个调用，将 JSON 参数安全、无歧义地传递给实际的函数。这是实现 Agent 间确定性数据交换的核心机制。

3. 通过共享的外部记忆或文件系统

对于需要跨多轮对话、多个 Agent 引用的关键数据（例如，一份项目需求文档、一份数据库 Schema），Agent 可以将其写入到一个共享的“工作空间”或外部存储（如文件系统、Redis）中。然后，它只将数据的存储路径或唯一标识符作为消息发送给其他 Agent。接收方 Agent 在需要时，通过路径去读取完整数据。这是处理大规模、持久化数据的最佳方式。

4. 利用 `description` 字段明确数据类型\
   在 Agent 的 `system_message` 或工具函数描述中，可以明确规定该 Agent 能够接受和输出的数据结构。例如，在“产品经理 Agent”的描述中写明：“本 Agent 输出的需求文档必须是包含 `title`, `description`, `acceptance_criteria` 三个顶级字段的 JSON 对象”。这种约定俗成强化了协作的确定性。

通过这些方法，AutoGen 的 Agent 不仅能够进行自由的智能对话，还能像精密仪器一样进行严格的结构化数据交换，从而胜任软件开发、数据分析等需要高精度协作的复杂任务。

#### 对比 LangChain 的 create_openai_functions_agent 和 create_react_agent 的内部实现原理。

这两个函数是 LangChain 中创建 Agent 的两种主要方式，它们分别代表了两种不同的决策和执行范式，其内部实现原理也截然不同。

`create_openai_functions_agent`：模型原生调用

这是一种专为 OpenAI 优化、极其可靠的 Agent 实现。

- 提示构造：它不依赖复杂的文本指令，而是将工具的定义转换为 OpenAI API 所需的 `tools` 参数（即一个 JSON Schema 列表）。同时，它会注入一个简洁的 System Prompt，引导模型在需要时调用工具。

- 模型调用与决策：它直接利用 OpenAI 模型的 Function Calling 能力。模型在生成时，如果判断需要工具，其响应会直接包含一个 `tool_calls` 对象，这是一个结构化的列表，每个元素包含 `id`、`function.name` 和 `function.arguments` (JSON 字符串)。这个决策过程是模型被专门训练过的，因此极其精确，几乎不会出现格式错误。

- 输出解析与执行：`AgentExecutor` 接收到响应后，直接检查 `message.tool_calls` 是否存在。如果存在，它遍历列表，将 `arguments` 解析为 JSON，调用对应的工具，并将工具返回的结果封装成 `role: "tool"` 的消息，与 `tool_call_id` 一一对应地追加回对话历史，供模型进行下一轮推理。

- 停止条件：当模型的响应不再包含 `tool_calls`，而是包含普通的文本消息时，`AgentExecutor` 将其视为最终答案，停止循环。此实现原生支持并行工具调用。

`create_react_agent`：文本解析驱动

这是一种更通用、模型无关的 Agent 实现，通过提示工程来模拟决策过程。

- 提示构造：它将所有工具的描述格式化为一段纯文本，并与一个复杂的 ReAct 格式模板拼接。模板包含严格的指令和示例，要求模型以 `Thought: ... \nAction: ... \nAction Input: ...` 的固定格式输出。

- 模型调用与决策：它向 LLM 发送构造好的文本 Prompt。模型以自然语言生成的方式，按照模板格式输出它的“思考”和“行动决定”。

- 输出解析：这是关键而脆弱的一步。`AgentExecutor` 必须使用正则表达式或特定解析器，从模型生成的自由文本中，精确地提取出最新的 `Action` 和 `Action Input`。这一步极易因为模型输出的微小格式偏差（如多一个空格、换行）而失败。

- 执行与停止：解析成功后，执行工具，并将结果以 `Observation: ...` 的格式追加回文本。循环直到模型输出包含一个 `Final Answer:` 的 Action，解析器提取出最终答案并停止。

核心对比

| 特性 | Functions Agent | ReAct Agent |
| --- | --- | --- |
| 决策机制 | 模型原生 Function Calling | 提示工程+文本解析 |
| 可靠性 | 极高，结构化输出 | 较低，依赖文本解析 |
| 模型兼容性 | 仅OpenAI特定模型 | 任何支持指令遵循的LLM |
| 可解释性 | 无显式的"思考"过程 | 有透明的Thought文本 |
| 并行调用 | 原生支持 | 不支持 |

#### 如何在 AutoGen 中实现多个 Agent 的角色扮演（如客户和客服）？

在 AutoGen 中实现角色扮演，是通过为不同 Agent 注入高度定制化的 System Prompt 来实现的。这些提示赋予了每个 Agent 截然不同的“身份”、“背景故事”、“专业知识”和“行为准则”，使它们能够像演员一样在对话中扮演各自的角色。

实现步骤

1. 定义客服 Agent：创建一个 `AssistantAgent`，其 System Prompt 被设计为经验丰富的客服。例如：“你是‘云享商城’的高级客服‘小云’。你专业、耐心、永远以客户为中心。你的知识库包含了所有退换货政策和产品详情。当客户的问题不在你知识范围内时，请礼貌地引导他们转接人工客服。”

2. 定义客户 Agent：创建另一个 `AssistantAgent`，其 System Prompt 被设计为有特定需求的客户。例如：“你是一位叫‘李明’的客户。你刚刚收到了一件在‘云享商城’购买的衬衫，但发现尺码偏大。你对电子产品也很感兴趣。你的目标是解决退货问题，并咨询一下新款耳机的信息。你的语气可以有些焦急，但保持礼貌。” 在这个提示中，我们不仅定义了角色，还植入了模拟对话的“剧本”和“目标”。

3. 启动和管理对话：
  - `UserProxyAgent` 作为代表：使用一个 `UserProxyAgent`，它是代表我们（开发者）的“眼和手”，可以执行代码或作为对话的发起者。
  - 初始化 GroupChat：将客服 Agent、客户 Agent 和 `UserProxyAgent` 放入同一个 `GroupChat`。
  - 设置初始消息：通过 `UserProxyAgent` 发送一条初始消息来触发整个角色扮演流程。例如，`user_proxy.initiate_chat(manager, message="李明：你好，我刚收到货，但衬衫太大了，我想退货。")`。
  - Agent 自动对话：`GroupChatManager` 会管理发言权。客服 Agent 会基于其专业的 Prompt 进行回复，客户 Agent 则会根据其“人设”和“目标”继续推进对话，如进一步询问电子产品。它们会像真人一样完成一个完整的客服对话场景。

关键技巧

- 明确目标：在客户 Agent 的 Prompt 中设定一个或多个“隐藏目标”，可以让角色扮演更具目的性和测试性。

- 风格注入：在 Prompt 中明确语言风格（如“口语化”、“使用emoji”、“专业严肃”），能极大提升角色扮演的真实感。

- 利用记忆：如果需要基于历史对话进行更复杂的角色扮演，可以为 Agent 配置 LangChain 的 Memory 或 AutoGen 的 `Teachability` 模块。

通过这种方式，AutoGen 可以模拟各种复杂的交互场景，用于客服培训、剧情生成、甚至是对新产品的压力测试。

#### LangChain 的 Callback 系统如何用于监控 Agent 的每一步行动？

LangChain 的 Callback 系统是一个强大的、贯穿其所有模块的事件监听和钩子机制。它允许开发者在 Agent 运行的几乎每一个关键节点插入自定义的逻辑，而无需修改 Agent 的核心代码。这为日志记录、监控、调试和成本追踪提供了极大的便利。

Callback 系统的工作原理

LangChain 的大多数核心组件（LLMs, Chains, Tools, Agents）在执行过程中，会在特定时机触发预定义的事件。开发者可以创建一个回调处理器（Callback Handler），在其中实现对应这些事件的处理函数。然后将这个处理器传递给 AgentExecutor。AgentExecutor 在运行时，会在事件发生时调用处理器中相应的函数。

监控 Agent 每一步行动的关键事件

一个用于监控 Agent 的典型回调处理器会关注以下几个核心事件：

1. `on_llm_start` / `on_llm_end`：
  - 触发时机：在 Agent 每次调用 LLM 之前和之后。
  - 监控信息：可以记录发送给 LLM 的完整 Prompt 序列，以及 LLM 返回的原始响应和 Token 消耗。这是分析 Agent “思考”过程的第一手资料。

2. `on_tool_start` / `on_tool_end` / `on_tool_error`：
  - 触发时机：在 Agent 每次调用一个工具之前、成功之后、或出现错误之后。
  - 监控信息：可以记录工具的名称、传入的输入参数、工具执行后的输出结果，以及如果出错时的详细错误信息。这是分析 Agent 行动合理性的关键。

3. `on_agent_action` / `on_agent_finish`：
  - 触发时机：当 Agent 做出一个决策（要调用某个工具）时，以及当 Agent 决定结束任务并返回最终答案时。
  - 监控信息：`on_agent_action` 事件能捕获到 Agent 选择的具体 Action 和输入参数，这是在 LLM 输出之后、工具执行之前的重要中间状态。`on_agent_finish` 则记录了最终返回给用户的完整输出。

代码示例 (概念性)

```python
from langchain.callbacks import StdOutCallbackHandler

# StdOutCallbackHandler 是一个内置的处理器，可以将所有事件打印到控制台
# 这在开发调试阶段极其有用
executor = AgentExecutor(agent=agent, tools=tools, callbacks=[StdOutCallbackHandler()])

# 你可以创建自定义处理器
class MyMonitorHandler(BaseCallbackHandler):
    def on_llm_end(self, response, **kwargs):
        print(f"LLM调用结束，消耗Token: {response.llm_output['token_usage']}")

    def on_tool_error(self, error, **kwargs):
        print(f"工具调用出错: {error}")

executor = AgentExecutor(agent=agent, tools=tools, callbacks=[MyMonitorHandler()])
```

通过 Callback 系统，开发者可以像拥有一个透明的仪表盘一样，实时掌握 Agent 的内部运行状态，从而进行高效的调试和性能优化。

#### 这些框架如何处理工具调用的错误？如何自定义异常处理和重试逻辑？

工具调用是 Agent 与现实世界交互的接口，而现实世界充满了不确定性，错误是常态。LangChain 和 AutoGen 都提供了处理工具调用错误的机制，但理念和实现方式有所不同。

LangChain 的错误处理

LangChain 的 `AgentExecutor` 有一个核心参数 `handle_parsing_errors`，它决定了当模型输出的格式无法被解析时（例如 ReAct Agent 输出了错误格式的 Action），系统的行为。

- 默认行为：如果解析失败，`AgentExecutor` 会抛出异常，导致整个任务中断。

- `handle_parsing_errors=True`：这会启动一个自动修复机制。当解析失败时，`AgentExecutor` 会将解析错误信息格式化后，作为一个“观察”注入回对话历史，并再次请求 LLM。这给了模型一个自我修正的机会。模型会看到“你上次的输出格式不正确，请修正并重试”这样的提示，然后尝试生成正确格式的输出。

- 自定义处理函数：开发者可以传入一个函数，它接收错误信息并返回一个自定义的字符串，作为反馈给模型的“观察”。这提供了最大的灵活性。

对于工具执行期间的错误（如网络超时、API 返回错误），LangChain 的默认行为是将错误信息直接作为工具的返回结果，传递给 LLM。LLM 看到错误信息后，可能会在下一轮思考中决定重试、更换参数或使用其他工具。

AutoGen 的错误处理

AutoGen 的错误处理更加结构化，并且与代码执行深度绑定。

1. 代码执行错误：这是 AutoGen 最擅长处理的错误。当代码执行器运行代码失败时，它会自动捕获 stdout、stderr 和退出码，并将这些信息作为一条格式化的错误消息，自动发送给生成该代码的 `AssistantAgent`。`AssistantAgent` 会解读错误信息，并尝试修复代码后重新生成。这个“生成-执行-纠错”循环可以自动进行多次。

2. 工具调用错误：对于通过 `function_map` 注册的自定义函数，如果在执行中抛出异常，开发者需要在函数内部捕获异常，并将其转换为一个包含明确错误信息的字符串返回。AutoGen 会将这个返回的字符串作为观察，发送回调用方 Agent。Agent 会根据错误内容进行后续决策。

自定义重试逻辑\
在 LangChain 中，最灵活的重试机制是使用 `handle_parsing_errors` 和工具内部的 `try-except` 来构造错误信息，引导模型去“重试”。在 AutoGen 中，可以配置 `max_consecutive_auto_reply` 来限制自动回复和纠错的轮数，防止无限循环。还可以在 Agent 的 System Prompt 中加入重试策略的指引。

#### 在 LangChain Agent 中，什么是“Chain-of-Thought”提示？如何定制 Agent 的提示模板？

Chain-of-Thought 提示是引导 LLM 在给出最终答案前，先输出一系列中间推理步骤的技术。在 LangChain Agent 中，它被内化到 Agent 的提示模板中，成为 Agent 思考过程的核心。

LangChain Agent 中的 CoT 提示

在 ReAct Agent 的提示模板中，CoT 体现为强制性的 `Thought:` 步骤。这不是建议，而是必须遵守的格式。模型被训练或被提示为在每一次行动前，都必须先写下它的思考过程。这个思考过程就是 CoT，它包含了模型对当前状态的分析、下一步行动的规划、以及选择该行动的理由。这种机制极大提升了复杂推理任务的准确性。

如何定制 Agent 的提示模板

定制提示模板是微调 Agent 行为的核心手段。LangChain 提供了多种方式来修改 Agent 的提示。

1. 使用预定义的 Hub 提示：LangChain 的 Hub 上有很多社区分享的、针对不同场景优化过的提示模板，可以直接拉取使用。

```python
from langchain import hub
prompt = hub.pull("hwchase17/react")
```

2. 创建自定义的 PromptTemplate：这是最灵活的方式。你可以创建一个新的 `PromptTemplate` 或 `ChatPromptTemplate`，然后将其传递给 Agent 的构造函数。你需要遵循对应 Agent 类型（如 ReAct, Functions）的变量约定，确保模板中包含 `{tools}`, `{input}`, `{agent_scratchpad}` 等必要变量。

3. 修改 Agent 的 `get_full_inputs` 或相关方法：对于更高级的定制，你可以继承 Agent 类，覆写其方法。但实践中，修改提示模板已经能满足绝大多数需求。

示例：定制 ReAct 提示

```python
from langchain.agents import create_react_agent
from langchain_core.prompts import PromptTemplate

custom_react_prompt = PromptTemplate.from_template("""
你是一个世界级的智能助手。你可以使用以下工具来解决问题：

{tools}

请严格遵循以下格式：
Question: 用户的问题
Thought: 你应该思考要做什么
Action: 要执行的动作，必须是 [{tool_names}] 中的一个
Action Input: 动作的输入
Observation: 动作执行的结果
... (这个 Thought/Action/Action Input/Observation 可以重复 N 次)
Thought: 我现在知道最终答案了
Final Answer: 对原始问题的最终答案

记住！在你生成最终答案时，务必提供详细可靠的依据，并注明信息来源。
开始！
Question: {input}
Thought: {agent_scratchpad}
""")

agent = create_react_agent(llm=llm, tools=tools, prompt=custom_react_prompt)
```

通过在定制提示中注入业务规则、安全准则或思考步骤，开发者可以精确地引导 Agent 的行为。

#### AutoGen 的“Teachability”功能是什么？它如何让 Agent 从交互中学习？

AutoGen 的 "Teachability" 是一个赋予 Agent 长期学习和适应能力的强大功能。它使得 Agent 可以从与用户或其他 Agent 的交互中获取新知识、记住用户的偏好和修正自己的错误，并将这些学习成果应用到未来的对话中。

Teachability 的工作机制

Teachability 本质上是一个与 Agent 绑定的、轻量级的记忆和学习管理系统。它主要由以下几个步骤组成：

1. 知识提取与触发：当一个交互会话结束，或者当用户在对话中明确表示“记住这个”时，Teachability 会被触发。它会分析整个对话历史，提取出有价值的信息，例如新的概念、事实性知识、用户的个人偏好，或者用户对 Agent 错误回答的纠正。

2. 记忆存储与管理：提取出的知识不是被简单地追加到某个日志文件中，而是被语义化地存储。Teachability 会将每条知识生成一个向量（Embedding），然后存入一个专用的向量数据库中（如 ChromaDB）。同时，它还会存储知识的原始文本和时间戳等元数据。这种存储方式支持后续的高效语义检索。

3. 知识的检索与应用：当 Agent 开始一个新的对话时，Teachability 会在后台静默地工作。它会将当前用户的查询和对话上下文进行向量化，然后从记忆中检索出最相关的几条历史知识。这些知识会被精心地格式化，并作为一条无声的“提示”注入到 Agent 的系统消息中。Agent 能看到这些提示，但用户看不到。例如，检索到的记忆可能是：“（记忆：用户偏好简洁的代码注释，使用中文）”。

它如何让 Agent “学习”？

- 用户教学：用户可以直接教 Agent。“记住，我们的服务器地址是 10.0.0.1”。Teachability 会存储这条信息。下次 Agent 需要连接到服务器时，这条记忆就会被检索出来，Agent 就能知道正确的地址。

- 错误纠正：当 Agent 回答错误被用户纠正后，Teachability 会存储“用户更正”这一事实。下次遇到类似问题时，Agent 会优先参考被纠正后的信息。

- 偏好学习：用户说“下次生成代码时，别用类，用函数实现”。Teachability 会记住这个偏好，并在未来生成代码时自动应用。

配置 Teachability

启用 Teachability 非常简单，在创建 Agent 时将其添加即可。

```python
from autogen import ConversableAgent, teachability

agent = ConversableAgent(
    name="teachable_agent",
    llm_config={"config_list": [{"model": "gpt-4", "api_key": "..."}]},
    teach_config=teachability.Teachability(
        verbosity=0,  # 0 (静默), 1 (简要), 2 (详细日志)
        reset_db=False, # 是否重置记忆库
        recall_threshold=1.5, # 检索记忆的阈值
    )
)
```

Teachability 为 AutoGen 的 Agent 装上了真正的“长期记忆”和“学习能力”，让它们不再是每次都从零开始，而是能够随着使用时间的增长变得越来越智能、越来越个性化。
