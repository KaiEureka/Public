# 99.大模型（LLMs）工具使用（Function Calling）及 Schema 定义与参数提取

#### 什么是 Function Calling？它在 LLM Agent 中扮演什么角色？

核心定义

Function Calling（函数调用）是大语言模型的一项关键能力，它允许模型在生成文本的过程中，不是直接输出最终答案，而是输出一个结构化的、包含函数名和参数的 JSON 对象，用以“请求”外部系统执行一个具体的操作。这个操作可以是查询数据库、调用 API、运行代码、搜索互联网，或者任何其他可以被程序化执行的功能。

从本质上讲，Function Calling 是赋予大语言模型“行动能力”的接口。它让模型从一个只能进行文字交流的“聊天机器”，进化为一个能够主动与外部世界进行交互、获取实时信息、并产生实际影响的“智能 Agent”。

在 LLM Agent 中的核心角色

Function Calling 是 Agent 实现从“思考”到“行动”的枢纽，扮演着三个不可替代的角色。

1. 连接语言与行动的桥梁：大语言模型的核心能力是处理非结构化的自然语言，而外部世界运行在结构化的 API、数据库查询和代码逻辑之上。Function Calling 凭借其精确定义的 JSON Schema，将模型模糊的意图翻译成了机器可精确执行的指令。例如，用户说“帮我查一下明天北京的天气”，模型通过 Function Calling 并不会直接生成天气预报，而是输出 `{"name": "get_weather", "parameters": {"city": "北京", "date": "2024-05-21"}}`。这个 JSON 对象就是桥梁，它的一头连接着用户的自然语言意图，另一头连接着能够获取天气数据的代码函数。

2. 实现动态、按需的知识与能力获取：LLM 的参数化知识是静态的，存在截止日期，也无法涵盖所有领域。Function Calling 让模型可以突破这一限制。当模型判断需要最新信息或执行特定操作时，它可以主动“调用”工具来满足需求。这使得 Agent 具备了动态扩展能力：它可以随时接入新的 API 来获取股价、调用计算器进行精确算术、或者查询企业内部的客户数据库。Agent 不再是一个被训练后就固化的系统，而是一个能够按需学习和使用新工具的开放平台。

3. 支持复杂任务的规划与执行：单个工具调用往往只能完成一个原子操作。但通过多轮 Function Calling，Agent 可以实现对复杂任务的自主规划与逐步执行。例如，用户要求“帮我预订一张下周五从北京到上海的高铁票，并发送确认邮件”。Agent 的规划器会将其分解为：① 调用“查询列车时刻表”工具；② 分析结果并选择最优车次；③ 调用“预订车票”工具；④ 获取预订结果后，调用“发送邮件”工具。在这一系列动作中，每一步都由一次 Function Calling 驱动，模型在获取到上一步的返回结果后，会继续推理下一步的动作。这个过程展示了 Function Calling 作为 Agent “行动闭环”的核心驱动作用。

结论：Function Calling 是 LLM 从“能说”到“能做”的质变点。它把模型的推理能力，通过结构化的工具接口，拓展到了广阔的物理世界和信息世界，是现代 Agent 框架的基石。

#### 描述 LLM 工具调用的一般流程：从用户输入到执行工具再到整合结果的完整链路。

完整链路概述

LLM 工具调用是一个涉及用户、大模型、应用程序后端和外部 API 等多个参与方的协同过程。其完整链路通常包含五个关键环节，形成一个从“理解意图”到“交付答案”的闭环。

第一步：意图识别与工具选择

流程从用户输入一个自然语言查询开始。应用程序后端会将这个查询与系统预设的、所有可用工具的详细描述（即工具的 JSON Schema 列表）一同发送给 LLM。LLM 被提示分析用户意图，并判断是否需要调用某个工具来满足该意图。如果需要，它会从工具列表中选择最合适的一个或多个工具。这个决策过程完全是 LLM 基于其对自然语言和工具描述的理解完成的。

例如，当收到查询“查一下公司最新的企业内训课程有哪些？”，LLM 会分析出“查询”和“最新”等关键意图，并根据工具描述锁定到一个名为 `search_courses` 的函数，而不是一个 `get_weather` 或 `send_email` 的函数。

第二步：参数提取与指令生成

一旦选定了工具，LLM 接下来会根据该工具定义的参数 Schema，从用户的自然语言查询中提取出所需的具体参数值。这个过程非常巧妙，模型需要理解参数的类型和语义描述，并在查询中寻找对应的信息。如果查询中信息不全，某些先进的实现还可以让模型生成一个反问，向用户请求缺失的必填参数。

最终，模型会输出一个结构化的、符合工具 Schema 定义的 JSON 对象，通常被称为“工具调用请求”。该请求包含了明确的 `function_name` 和 `parameters` 键值对。例如：`{"name": "search_courses", "arguments": {"category": "企业内训", "sort_by": "latest"}}`。

第三步：后端验证与执行

LLM 生成的工具调用请求会被应用程序后端拦截和解析。后端首先会执行一系列关键的安全和逻辑校验：

- Schema 验证：检查生成的 JSON 是否符合工具定义的 Schema，参数类型是否正确，必填参数是否都已提供。

- 安全沙箱与权限控制：检查此次调用是否在用户的权限范围内，是否存在注入攻击的风险。

- 业务逻辑校验：进行一些模型无法完成的业务规则检查。

验证通过后，后端会正式调用实际的函数或 API，并将从 LLM 接收到的参数传入。函数执行其内部逻辑，例如查询数据库、运行 Python 代码、或调用第三方 API。执行完成后，函数会返回一个原始结果。

第四步：结果处理与上下文整合

工具返回的原始结果（例如，一个包含课程列表的 JSON 数组，或一个“操作成功”的状态码）通常不能直接展示给用户。应用程序后端需要先对其进行格式化，将其转换为更适合 LLM 理解的文本摘要。例如，将一个复杂的 API 返回 JSON 清洗掉无关的元数据，只保留核心信息。

然后，这个处理过的“工具响应”文本会被作为新的上下文消息，追加到与 LLM 的对话历史中。它被标记为一个特殊的角色，如 `tool` 或 `function`，并附带上该次工具调用的唯一 ID。

第五步：生成最终答案

最后，后端将包含有工具响应文本的完整对话历史再次发送给 LLM。模型现在拥有了来自外部工具的真实、结构化的信息。它会被提示基于这些新信息，来生成一个流畅、准确、直接回答用户原始问题的最终答案。例如，它可能会根据返回的课程列表 JSON，生成一个格式清晰、附带简要说明的课程推荐清单。

这个五步链路形成了一个完整的智能循环，让 LLM 能够通过标准化的接口，无缝地接入和利用整个数字世界的能力。

#### 如何为工具定义一个清晰的 JSON Schema？应该包含哪些关键字段？

核心原则

定义一个清晰的工具 JSON Schema，其目标是为 LLM 提供一份“精确到无歧义”的函数使用说明书。模型必须仅凭这份描述，就能准确理解函数的功能、适用场景、以及如何正确地组装参数。一个模糊或错误的 Schema 是导致工具调用失败的根源。

关键字段与定义规范

一个高质量的工具 JSON Schema 通常包含以下关键字段，每个字段都有其明确的职责和撰写规范。

1. `type: "function"`\
   这是顶层字段，用于声明此对象描述的是一个可供调用的函数。

2. `function.name`\
   函数的唯一标识符。命名应遵循清晰、简洁、易于模型理解的原则。

- 最佳实践：使用动词-名词结构，如 `search_products`、`create_order`、`get_weather_forecast`。避免使用缩写、技术黑话或过于宽泛的名称。一个好的函数名本身就能传递其功能。这会让模型在进行“意图匹配”时更准确。

3. `function.description`\
   这是决定模型能否在正确场景下选择该工具的最关键字段。

- 核心要求：必须是详细的、角色清晰的描述，解释函数的功能、在什么情况下使用、以及它与其他类似函数的区别。

- 撰写技巧：要描述函数的“能力边界”，而不仅仅是重复其名称。例如，对于 `search_courses`，一个不好的描述是“搜索课程”，一个好的描述是“根据课程类别、关键词、开课时间等条件，从公司内部培训平台搜索相关的课程信息。当用户想找培训课程、了解课程详情或查询课程安排时使用。此函数无法用于报名或取消课程，相关操作请用其他函数。”

- 关键信息：描述中应隐含地告诉模型，此函数能解决用户的哪些问题，以及不能解决哪些问题。这能极大减少误调用。

4. `function.parameters`\
   这是定义参数的核心部分，本身也是一个遵循 JSON Schema 规范的对象。它必须精确描述每个参数的格式、类型和约束。

- `type`：定义参数的顶级类型，最常用的是 `"object"`，因为大多数函数需要多个参数。

- `properties`：一个对象，其键是参数名，值是另一个描述该参数的对象。
  - `type`：参数的数据类型，如 `"string"`, `"number"`, `"boolean"`, `"array"`, `"object"`。
  - `description`：此字段是重中之重。必须提供参数的语义描述、它的作用，并且尽量给出值的示例或格式要求。例如，对于 `city` 参数，描述可以是：“需要查询天气的城市名称，使用标准中文全称，如‘北京’、‘上海’。不要使用拼音或缩写。”
  - `enum`：如果参数的值是一个固定的集合，必须使用此字段列出所有可能的值。这能极大提高模型输出合法参数值的概率。

- `required`：一个字符串数组，列出所有必须由模型提供的参数名称。对于没有出现在此数组中的参数，模型会视其为可选。

- `additionalProperties`：通常建议设置为 `false`，以防止模型“脑补”出 Schema 中不存在的参数。

示例：一个清晰的 Schema 片段

```json
{
  "type": "function",
  "function": {
    "name": "search_restaurants",
    "description": "根据用餐需求，搜索符合要求的餐厅。适用于用户想找餐厅、询问美食推荐、或预订餐位前的信息查询。",
    "parameters": {
      "type": "object",
      "properties": {
        "cuisine": {
          "type": "string",
          "description": "菜系类型，如‘川菜’、‘日料’、‘意大利菜’。",
          "enum": ["川菜", "粤菜", "日料", "意大利菜", "烧烤", "不限"]
        },
        "price_range": {
          "type": "string",
          "description": "人均消费预算。",
          "enum": ["经济实惠", "中等", "高档"]
        },
        "location": {
          "type": "string",
          "description": "用户偏好的区域或地标，例如‘三里屯’、‘国贸’、‘西湖边’。"
        },
        "max_results": {
          "type": "integer",
          "description": "最多返回的餐厅数量，默认为5。"
        }
      },
      "required": ["location"]
    }
  }
}
```

通过这样一份精确到参数值格式和示例的 Schema，LLM 能够像一个熟练的 API 调用者一样，生成准确、合法的参数。

#### 设计工具描述时有哪些最佳实践？如何让 LLM 准确理解工具的功能和使用场景？

核心问题

工具描述是连接 LLM 和外部世界的唯一文档，其质量直接决定了 Agent 工具调用的成功率。LLM 无法像人类开发者那样去阅读源代码或参考示例，它完全依赖于你在 JSON Schema 的 `description` 字段中提供的信息。一个糟糕的描述会导致模型在需要时忽略该工具，或者生成了错误的参数。

最佳实践

1. 明确的“能力范围”陈述，而非简单的功能罗列

在描述函数整体时，不要只说“这是一个搜索工具”，而是要清晰地定义它能做什么，以及更重要的是，它不能做什么。这能帮助模型在多个功能相似的工具之间做出精准的选择。

- 好的示例：“此工具用于从内部产品库中搜索商品信息。它可以按名称、类别、价格区间进行查询。请注意，它不能用于查询订单信息或处理售后请求，相关功能请使用 `query_orders` 或 `create_ticket` 工具。”

- 坏的示例：“一个搜索工具。”

2. 提供详尽的参数语义、格式和示例

这是让 LLM 生成正确参数的最关键之处。对每个参数，必须将你的隐含知识显式化。

- 描述语义：解释此参数代表现实世界中的什么，而不仅仅是技术名称。

- 定义格式：明确说明期望的数据类型、结构、甚至正则表达式。例如，`date` 参数应描述为“日期，格式为 ‘YYYY-MM-DD’，例如‘2024-05-20’”。

- 提供具体示例：在描述文本中直接给出值的示例。这比任何格式说明都更有效。例如，“城市名称，使用标准中文全称，如‘北京’、‘上海’。不要使用拼音或缩写。”

- 使用 `enum` 字段：当参数值是一个有限的集合时，务必使用 `enum` 字段列出所有合法值。这能将模型生成错误值的概率降到最低。

3. 建立语义清晰的函数命名体系\
   一个词能达意的函数名本身就承担了大部分描述工作。遵循统一、清晰的命名规范，如动词-名词结构（`get_`, `search_`, `create_`, `update_`, `delete_`），可以让模型在第一时间就从“名字”上理解其基本功能，便于在大规模工具列表中进行快速筛选。

4. 注入场景化指导，引导模型决策\
   在整体描述或特定参数描述中，加入与用户场景相关的指导。例如，对于一个 `get_weather` 工具，可以描述为：“当用户查询‘明天天气’、‘这周周末会下雨吗’等问题时使用。注意，如果用户只问‘天气真好’，那是感叹，不需要调用。” 这种场景化的正反示例，能极大降低误触发的几率。

5. 明确定义副作用与幂等性\
   对于会改变系统状态的操作（如创建订单、发送邮件），必须在描述中明确其“副作用”。同时，告知模型该操作是否幂等（重复调用是否安全）。例如，对于 `send_email` 的描述：“此操作将立即向指定地址发送一封邮件。注意：此操作不可逆，且重复调用会导致收件人收到多封相同邮件。请在调用前与用户确认。”

6. 使用 `required` 字段和 `additionalProperties: false`\
   严格且清晰地定义哪些参数是必须的，哪些是可选的。将 `additionalProperties` 设置为 `false`，可以防止模型自行添加幻觉参数。

通过将这些实践融入到工具 Schema 的设计中，你相当于为 LLM 编写了一份无师自通的 API 文档。这份文档的质量，直接决定了你的 Agent 是工具使用的专家，还是只会乱按按钮的门外汉。

#### 参数提取：LLM 如何从自然语言中识别并填充函数所需的参数？常见的参数解析方法。

核心机制

LLM 从自然语言中提取参数，并非运行一个独立于生成之外的 NER 模型，而是其强大的指令遵循和上下文学习能力的直接体现。它是通过“阅读”函数的 JSON Schema，特别是其中的参数描述，来理解需要哪些信息，然后在生成函数调用 JSON 时，从对话历史中“检索”并填充这些值。

这个过程是端到端发生的：模型在决定调用某个函数的同时，就已经在组织它的参数了。其能力来源于预训练期间对海量结构化与非结构化数据的对齐学习。

常见的参数提取与解析方法

1. 模型原生提取与结构化输出

这是目前最主流、最可靠的方法。整个提取和填充过程完全由 LLM 在一次前向传播中完成。

- 工作原理：应用程序将工具的 JSON Schema 与用户查询一同发送给 LLM。现代 LLM（如 GPT-4, Claude）经过专门的指令微调，能够直接输出一个符合预期 JSON 格式的函数调用指令。该输出不仅包含了所选函数，也包含了所有提取并填充好的参数。

- 优势：速度快，延迟低，上下文理解更精准，因为提取和决策是同时进行的。

- 解析：后端程序收到这个结构化的输出后，可以直接用 `JSON.parse()` 解析，获取参数键值对，进行下一步处理。

2. 多阶段提取策略（适用于复杂场景或较旧模型）

在某些情况下，可能需要更精细的控制。

- 分离式提示：设计一个特定的提示词，要求模型先“列出从用户输入中提取的实体”，然后再“将这些实体映射到函数参数”。这种方法更灵活，可以加入复杂的转换逻辑，但延迟更高。

- 工具特定提示：为每个工具设计一个专门的“参数提取”提示模板。对于无法处理复杂 Schema 的模型，这种方式可能更有效。

- 后处理修正：使用规则或小型模型对 LLM 提取的参数进行二次校验和修正。例如，用正则表达式检查日期格式，或根据实体库进行实体链接。

3. 处理信息缺失与用户澄清

高级 Agent 在提取参数时，如果发现缺少某个必填参数，且该参数无法从上下文推断，它不应去“猜测”一个默认值。最佳实践是，模型应生成一个“澄清”回应，直接向用户提问，请求提供缺失的信息。例如：“为了帮您搜索餐厅，请告诉我您偏好的区域是哪里？” 这通常通过在系统提示中明确指令来实现。

4. 模糊与消歧处理

当查询中存在歧义时（例如，“我要去苹果”），模型需要结合上下文或自身知识进行消歧。提示策略可以引导模型：“如果信息不明确，请优先根据对话历史推断。如果仍无法确定，请列出可能的解释并向用户确认。”

结论：随着模型能力的发展，模型原生提取因其简洁、高效和低延迟，已成为绝对主流。其他方法更多地被用作针对特定边界情况的补充和增强。因此，工程的重心应放在如何编写最优的 JSON Schema 和系统提示，以最大化模型原生的提取能力。

#### 复杂参数类型（嵌套对象、数组、枚举）的 Schema 如何定义？LLM 能正确生成这些复杂结构吗？

核心回答：绝对可以。现代 LLM（如 GPT-4、Claude 3 系列）在处理复杂的、嵌套的 JSON Schema 方面表现出惊人的能力，能够准确地生成包含多层嵌套对象和数组的复杂参数。这得益于它们在大规模代码和 JSON 数据上的训练。

Schema 定义方法

对于嵌套对象、数组和枚举，可以严格按照 JSON Schema 规范进行定义。

1. 嵌套对象\
   当参数需要结构化的子属性时，使用 `"type": "object"` 来定义，并在其内部使用 `properties` 进行描述。可以无限嵌套。

```json
"shipping_address": {
  "type": "object",
  "description": "用户的收货地址。",
  "properties": {
    "province": { "type": "string", "description": "省份，如'浙江'。" },
    "city": { "type": "string", "description": "城市，如'杭州'。" },
    "detail": { "type": "string", "description": "详细街道地址。" },
    "zip_code": { "type": "string", "description": "邮政编码。" }
  },
  "required": ["province", "city", "detail"]
}
```

2. 数组\
   当参数需要一个列表时，使用 `"type": "array"` 定义，并用 `items` 指定数组中每个元素的 Schema。

```json
"items_to_order": {
  "type": "array",
  "description": "用户要购买的商品列表。",
  "items": {
    "type": "object",
    "properties": {
      "product_id": { "type": "string", "description": "商品的唯一ID。" },
      "quantity": { "type": "integer", "description": "购买数量。" }
    }
  }
}
```

3. 枚举\
   如前所述，使用 `enum` 关键词直接列出所有合法值。

```json
"payment_method": {
  "type": "string",
  "enum": ["wechat", "alipay", "credit_card"],
  "description": "支付方式。"
}
```

LLM 生成复杂结构的准确性

现代 LLM 在这方面非常可靠，原因如下：

- 训练数据的覆盖：它们的预训练语料包含了海量的 JSON 数据和代码，因此对这类结构化信息的语法和逻辑有深刻的理解。

- 上下文学习能力：一个清晰、无歧义的 Schema 本身就是最强的“提示”。模型能够像编译器解析语法一样，精细地遵循 Schema 的层级和类型定义。

- 原生 JSON 模式支持：许多高级 API（如 OpenAI 的 JSON Mode）保证模型输出是合法的 JSON，这从根本上解决了格式错误的问题。

但仍有挑战与注意事项：

- Schema 的复杂度不能无限增加。如果嵌套过深（例如超过 5 层），或者同一层级有数十个属性，模型的注意力可能会分散，导致遗漏字段或生成错误的层级关系。

- 描述至关重要。对于复杂的嵌套结构，必须在每一个层级的 `description` 中都给出清晰的解释和示例。不能让模型去猜测某个深层嵌套对象的业务含义。

- 长尾歧义。在极其罕见或定义模糊的复杂场景下，模型的输出仍可能不符合预期。因此，后端的 Schema 校验步骤依然是必不可少的。

结论：你可以放心地使用嵌套对象、数组和枚举来精确描述业务所需的复杂数据结构。只要 Schema 本身定义清晰、描述到位，现代 LLM 足以成为合格的“结构化数据生成器”。

#### 如何处理可选参数和默认值？Schema 中如何表达，LLM 应如何决策是否提供？

核心回答：处理可选参数和默认值是工具设计中的精细活，它关系到模型在信息不足时的行为——是去“猜测”一个值，还是“诚实地”省略它。最佳实践是引导模型倾向于省略，而将默认值的赋权交给后端逻辑。

在 Schema 中表达可选参数和默认值

- 可选参数：在定义参数的 `required` 数组时，不将该参数名加入数组，即可将其标记为可选。

- 默认值：目前，标准的 LLM 工具调用 JSON Schema 本身没有一个专门的 `default` 字段。因此，你必须在参数的 `description` 字段中，用自然语言来传达默认值的信息。

示例：

```json
"max_results": {
  "type": "integer",
  "description": "最多返回的餐厅数量。如果用户没有明确指定，请勿猜测，直接省略该参数。系统后端默认为5。"
}
```

LLM 应如何决策是否提供

这是关键。你应该通过提示词和描述策略，明确地训练模型的行为模式。

最佳实践：引导模型“宁缺毋滥”

- 在系统提示中设定全局规则：可以加入一条指令：“当调用工具时，对于可选参数，除非用户在当前对话中明确提供了该信息，否则不要自行添加该参数。”

- 在参数描述中给出具体指引：如上述 `max_results` 的例子，直接告诉模型在用户没提及时“直接省略该参数”。这比依赖模型自己的“常识”要可靠得多。

为什么这样做？

- 避免臆测偏差：如果用户只是说“帮我找附近的餐厅”，模型自行填入 `max_results: 3`，而你的后端默认是 10，可能就错过了用户更想要的选择。把默认值的决定权留在服务器端，可以保证业务逻辑的一致性。

- 简化后端校验：后端可以更容易地判断：参数存在，说明是用户的明确意图；参数不存在，则安全地使用默认值。

- 区分“未提及”与“明确设为”：这种设计模式能完美区分“用户未提及”和“用户明确要求某个值（即使与默认值相同）”这两种情况。如果用户明确要求了某个和默认值一样的值，模型会生成该参数，后端可以据此进行特殊的业务处理（例如，记录用户偏好）。

一个需要模型“主动提供”的特殊情况：\
当省略某个可选参数可能会导致工具执行一个危险或不恰当的默认行为时，你应该反其道而行之。例如，如果 `file_deletion` 工具有一个 `confirm` 参数，默认为 `false`（即不确认就删除）。此时，应该要求模型“当用户表达删除意图时，务必提供 `confirm: true` 作为安全确认”。这种逻辑最好通过系统提示来强制实施。

结论：处理可选参数的精髓，在于将“默认值”的逻辑从模型端剥离，回归到可控的后端代码中。让模型扮演一个忠实的“信息收集者”，而不是一个爱脑补的“决策者”。

#### 一个 LLM 调用可能涉及多个工具，如何设计提示让模型选择正确的工具并提取参数？

核心问题

当你的 Agent 拥有数十个功能各异的工具时，确保模型在每次调用中都能精准地选择出正确的工具，并为其提取参数，是系统设计的一大挑战。这本质上是要求模型在一个有限的上下文窗口内，完成一次高精度的“意图分类”和“槽位填充”联合任务。

提示设计策略

1. 核心提示：角色、职责与基本规则

系统提示的开头应奠定全局基调。需要明确告知模型：“你是一个智能助手，你的职责是帮助用户完成他们的请求。你可以通过调用一系列工具来获取信息或执行操作。请仔细阅读用户的问题，并根据下面提供的工具列表，选择最合适的工具来完成任务。你必须只从下面提供的工具列表中选择，不要使用任何未列出的工具。”

2. 工具描述的质量是基石\
   如前所述，每个工具的 `name` 和 `description` 必须极其精确，特别是要阐明其“能力边界”。当两个工具功能相似时，必须在描述中清晰地指出它们的区别和使用场景。

3. 注入“思考链”指导（Chain-of-Thought）

为了防止模型在复杂任务中“跳步”或选错工具，可以在提示中注入一个隐性或显性的思考链指导。

- 隐式：在系统提示中加入：“在选择工具之前，请先在内心分析：用户的核心需求是什么？要完成这个需求，需要哪些信息？这些信息中哪些是已知的，哪些是缺失的？哪一个工具能够最有效地填补这个信息缺口？”

- 显式：要求模型在输出工具调用前，生成一段思维链文本（取决于 API 是否支持）。这段文本可以清晰地展示它的推理逻辑，便于调试。

4. 利用少样本示例进行场景化教学

对于特别容易混淆的、或者需要复杂参数组合的工具集，提供一到两个高质量的少样本示例是极其有效的。示例应覆盖“单工具调用”、“多工具并行调用”和“基于上一步结果进行后续调用”等不同场景。好的示例能将抽象的工具描述具象化，让模型精准领悟在不同语境下的正确选择。

5. 明确定义“无法处理”的回退策略

工具集不可能覆盖所有用户问题。必须告诉模型，当它找不到任何合适的工具来处理用户请求时应该怎么做。例如，在提示中规定：“如果没有任何工具能够满足用户请求，请礼貌地解释你目前的能力限制，并向用户提供你所支持的操作列表。”

组合运用

一个健壮的、多工具的选择与提取系统，不是靠某一个神奇的提示词，而是靠高质量的工具 Schema、清晰的系统指令、以及精心设计的场景示例三者共同作用的结果。其中，Schema 负责定义“是什么”，系统指令负责约束“怎么做”，示例负责展示“在具体场景下如何做”。这三者共同构成了模型进行准确决策的全部上下文。

#### 并行工具调用（Parallel Function Calling）是怎么实现的？LLM 如何返回多个工具调用请求？

核心回答

并行工具调用是一项高级能力，它允许 Agent 在同一轮对话中，对多个相互之间没有依赖关系的工具同时发起调用。这极大地减少了完成复杂任务所需的串行交互轮次，从而显著降低了端到端延迟，提升了用户体验。

实现机制

并行工具调用的实现，不是客户端的行为，而是由 LLM 的能力和 API 设计共同决定的。

1. LLM 的决策与生成

当 LLM 分析用户请求时，如果它判断完成该任务需要的信息可以同时从多个独立的来源获取，它就会决定发起并行调用。例如，对于“帮我查一下北京和上海未来三天的天气”，模型会识别出查询“北京天气”和“上海天气”是两个互不依赖的独立任务。在生成响应时，它不会输出一个工具调用，而是输出一个包含多个工具调用对象的数组。例如：

```json
[
  {"name": "get_weather", "arguments": {"city": "北京", "days": 3}},
  {"name": "get_weather", "arguments": {"city": "上海", "days": 3}}
]
```

每个对象都是一个独立、完整的工具调用指令。

2. API 层面的支持\
   这需要 API 的支持。在原生支持并行调用的 API 中，LLM 的响应结构本身就允许在 `tool_calls` 字段中包含一个列表。如果 API 本身不支持这种结构，就需要通过提示工程来模拟。例如，可以定义一个新的函数，其参数是一个由所需子调用组成的数组。但这需要更复杂的解析逻辑，且效果不如原生支持。

3. 后端的并行执行与结果聚合

应用程序后端接收到这个包含多个调用请求的数组后，立即执行一个并行（或并发）操作：

- 它同时启动多个异步任务，分别执行每个独立的函数调用。

- 等待所有任务完成后，将所有函数返回的结果收集起来。

- 将每个函数的结果分别封装为一条 `tool` 角色的消息，并附上对应的 `tool_call_id`。

- 最后，将这一批包含所有工具结果的对话上下文，再次发送给 LLM，让它综合所有信息，生成最终的总结性回答。

关键前提：无依赖性

并行调用必须严格遵守一个前提：所有被并行的调用之间，绝对不能存在相互依赖关系。例如，你不能并行执行“调用 A 获取用户 ID”和“调用 B 根据用户 ID 查询订单”，因为 B 的输入依赖于 A 的输出。这种依赖关系必须由 LLM 自身在规划时正确识别。一个错误的并行规划，会导致其中一个调用因参数缺失而失败。

结论：并行工具调用将 Agent 的效率提升到了一个新的水平。它依赖于 LLM 强大的任务分解和依赖分析能力，以及底层 API 和应用程序框架的完美配合。

#### 工具调用中的错误处理：当工具返回错误或超时，Agent 应如何反应？重试、修正参数还是换工具？

核心问题

工具调用失败是真实环境中的常态，原因多种多样：网络超时、API 权限不足、参数格式错误、业务逻辑拒绝等。一个脆弱的设计会让 Agent 在此刻“死机”，而一个鲁棒的、全面的错误处理策略，则是 Agent 可靠性的基石。

错误处理策略

当工具返回错误时，Agent 的反应不应是单一的，而应是根据错误类型和上下文，从一系列策略中进行智能选择。

1. 错误信息的标准化与传递\
   后端在执行工具调用失败时，不应简单地向 LLM 返回一个 `Error: true`。必须将原始的错误信息进行清洗和标准化，构造成一段信息丰富的、对 LLM 友好的文本。例如，将 HTTP 500 的堆栈信息翻译为：“工具 `search_database` 执行失败，原因是服务器内部错误。这可能是一个临时故障，稍后重试可能会成功。” 这段文本会作为 `tool` 角色的消息，返回给 LLM，作为其下一步推理的依据。

2. LLM 的智能响应策略

LLM 在接收到错误信息后，可以展现出几种层次的“智能”应对：

- 策略一：智能重试。如果错误信息表明这是一个临时性故障（如“连接超时”），模型可以决定以完全相同的参数再次发起调用。但必须设定最大重试次数，防止无限循环。

- 策略二：参数修正。如果错误信息是“参数错误：城市名‘北竟’不存在”，模型能够利用其常识推理能力，自动将参数修正为“北京”，并再次发起调用。这是 LLM 强大纠错能力的体现。

- 策略三：降级与替代方案。如果一个工具反复报错，模型应转向尝试功能相似的工具。例如，`search_database` 不可用，可以尝试 `search_file_system` 或 `ask_user` 等替代方案。

- 策略四：优雅失败与用户沟通。如果以上所有尝试均告失败，或者错误表明任务不可为（如“权限不足”），模型应停止尝试。它需要综合所有失败的尝试，生成一段清晰的、有同理心的回复，向用户解释失败的原因、它尝试了哪些方法，并提供可能的替代建议或请求人工介入。

3. 系统级的兜底与保护机制

不能完全依赖 LLM 的自我纠错，系统本身也必须设定保护网。

- 全局超时与步数限制：为整个任务设置一个硬性的时间或步数上限，防止 Agent 在错误处理循环中消耗过多资源。

- 全局异常捕获与日志：所有层的异常都应被捕获、记录，并可用于后续的系统审计和优化。

- 强制终止策略：当检测到同一个工具调用连续失败超过 N 次，系统可以强制终止该分支，并向 LLM 注入一条系统指令，要求其立即改变策略。

结论：工具调用的错误处理不是一个事后补丁，而应被设计为一个贯穿前后端、融合系统级健壮性与 LLM 智能决策的分层体系。正是这种对异常情况的周全考虑，才让 Agent 从玩具变成了值得信赖的生产力工具。

#### 如何安全地执行 LLM 生成的工具调用？沙箱、权限控制、输入校验的必要性。

LLM 生成的工具调用，本质上是将一段由非确定性系统产生的、完全不可信的文本，直接映射为对宝贵数据和关键系统的操作指令。如果不加任何防护，这就等于将你家的门禁密码交给了每一位访客。因此，安全地执行工具调用，不是可选的额外保障，而是系统的生命线。

一、沙箱机制：隔离与限权

沙箱是执行 LLM 生成代码或高风险操作的首道防线。它的核心思想是创建一个与真实系统环境完全隔离的、受限的执行空间。

- 代码执行沙箱：当 Agent 需要运行 LLM 生成的代码时，绝不能在宿主服务器上直接执行。必须将其放入一个隔离的容器（如 Docker、gVisor）或微虚拟机（如 Firecracker）中。这个沙箱应被剥夺所有非必要的网络访问、文件系统写入权限和系统调用。执行完毕后，整个沙箱环境立即销毁。这确保了即使模型生成了恶意的 `rm -rf /` 命令，其破坏力也仅限于沙箱内部，无法波及真实系统。

- 行动权限沙箱：对于非代码的 API 调用，沙箱体现为后端对每个工具的严格权限控制。一个用于查询订单的工具，其底层数据库账号应只有目标表的 `SELECT` 权限，绝不授予 `UPDATE`、`DELETE` 或 `DROP` 等危险权限。权限控制的粒度应细化到工具级别，甚至参数级别。这遵循了最小权限原则，即使某个工具被意外或恶意调用，其造成的损害也能被限制在最小范围。

二、输入校验：绝不信任模型的输出

LLM 的输出是概率性的，即使它生成了符合 JSON Schema 的格式，其参数内容也可能包含注入攻击代码、非法值或导致后端崩溃的畸形数据。因此，必须对每一个参数进行独立、严格的校验。

- 类型与格式校验：首先要验证参数的基本数据类型是否正确，字符串长度是否在允许范围内，数字是否在合理区间，日期格式是否合法。

- 业务逻辑校验：这是更深层次的校验。例如，`user_id` 参数不仅要是整数，还必须是当前系统中真实存在且用户有权访问的 ID；`quantity` 参数不仅要是正数，还必须小于库存数量。

- 注入攻击防护：对于可能与数据库、Shell 命令交互的参数，必须使用参数化查询或转义处理，严防 SQL 注入、命令注入等安全漏洞。任何来自模型的输入，在真正执行前，都必须经过上述安全白名单的验证和清洗。任何一次校验失败，都应中止调用并返回明确错误，绝不让步。

三、权限控制与人机协同

- 用户身份绑定与权限传递：每个工具调用必须绑定到发起请求的具体用户身上。后端的权限校验模块需要验证，执行此操作的用户是否真正拥有相应的权限。LLM 的身份只是代理，不拥有任何超越用户的特权。

- 高风险操作的人机协同确认：对于支付、删除、发送邮件等不可逆且后果严重的操作，必须设置人机协同的二次确认机制。LLM 的计划会在此暂停，系统生成一个清晰的确认请求（包含即将执行的操作详情）发送给用户，只有在用户明确批准后，才交由后端执行。

通过这层层递进的“沙箱隔离、输入清洗、权限管控”防线，我们才可能将 LLM 工具调用的安全风险控制在可接受的水平。

#### 不同 LLM 提供商（OpenAI, Anthropic, 开源模型）的 Function Calling 实现有何差异？如何做兼容适配？

不同 LLM 提供商在 Function Calling 的实现上，虽然在核心思想（用结构化输出驱动工具调用）上殊途同归，但在具体的 API 格式、参数传递方式、模型提示和功能特性上存在显著差异。这给多模型兼容框架的开发带来了挑战。

一、实现差异

- OpenAI (GPT系列)：是最早将 Function Calling 标准化的厂商之一。其 API 接受一个 `tools` 参数，内包含一个符合特定 JSON Schema 格式的函数列表。模型会返回一个 `tool_calls` 数组，其中包含函数名和一个 JSON 字符串格式的 `arguments`。它原生支持在一次响应中发起多个并行的工具调用。执行结果通过 `role: "tool"` 的消息，并附带 `tool_call_id` 进行回传。

- Anthropic (Claude系列)：Claude 的工具使用模式略有不同。其 API 也接受 `tools` 参数，但定义方式更贴近其内部格式。Claude 强调逐步推理，在决定调用工具时，其响应中的 `stop_reason` 会是 `"tool_use"`，并返回一个包含 `name` 和 `input` 的 JSON 对象。工具返回后，需要以 `tool_result` 的内容块形式传回。其模型训练更侧重于安全、谨慎地使用工具。

- 开源模型 (如 Llama 3, Qwen 2, Mistral等)：开源模型的工具调用能力依赖于其指令微调数据集。它们的实现方式更加多样化。
  - Llama 3：通过特殊的提示词格式（如 `<|start_header_id|>assistant<|end_header_id|>`）和预定义的 `python` 或 `json` 格式输出来实现。其模型本身被训练为直接输出包含工具调用的文本。
  - Mistral：引入了专门的 token 和格式来处理函数调用。
  - 通用适配：许多社区微调的开源模型采用了类似 OpenAI 的 `tool` 消息格式，但具体的提示词模板和特殊 token 各不相同。这导致“即插即用”的通用性较差。

二、兼容适配策略

要构建一个统一的、屏蔽底层差异的工具调用层，推荐采用适配器模式。

1. 定义统一的内部 Schema：在你的应用程序中，定义一套你自己的、与提供商无关的工具定义规范（如标准的 JSON Schema 格式）。这是你系统内部的通用语言。

2. 为每个提供商实现适配器：对于每一个你需要支持的 LLM 提供商（OpenAI, Claude, Llama 3 等），编写一个适配器模块。这个适配器负责两件事：
  - 请求转换：将你的内部 Schema 和对话历史，翻译成该特定 LLM API 所要求的格式。这包括处理提示词模板、特殊 token 的注入和角色定义的映射。
  - 响应转换：将该 LLM 的原始响应（可能是 OpenAI 的 `tool_calls`，也可能是 Claude 的 `tool_use` 结构），解析并转换回你的内部统一格式。这包括提取函数名和参数，并处理多模态或文本格式的差异。

3. 组件化切换：在 Agent 的配置中，通过依赖注入的方式，轻松切换或混合使用不同提供商的 LLM，而无需修改任何上层的业务逻辑代码。这使得你的 Agent 可以在成本、性能、安全等不同维度上自由选择最合适的模型。

通过这种方式，你可以成功地将上层应用的稳定性与底层 LLM 生态的快速变化进行解耦。

#### 工具执行结果的序列化与回传：如何将工具的输出格式化后重新注入对话上下文？

工具执行的结果，往往是一个包含大量元数据、嵌套复杂的数据结构（JSON、XML等）或长文本。如何将这一“原始数据”处理成 LLM 能够高效理解、并用于生成后续答案的“精炼信息”，是决定 Agent 能否有效利用工具的关键。

一、结果处理的三项核心任务

在将结果注入上下文之前，后端需要完成三项任务：清洗、压缩和格式化。

1. 清洗：从工具返回的原始数据中，剔除所有与回答用户问题无关的“噪音”。这包括 API 返回的 HTTP 状态码、无关的响应头、各种技术性元数据。只保留与核心业务语义相关的数据部分。

2. 压缩与信息提炼：LLM 的上下文窗口是昂贵的，而且容易被冗长的数据淹没。因此，不能将整个清洗后的结果直接丢给模型，特别是当结果很大时。需要根据任务进行智能压缩。例如，对于一个搜索列表，可以只返回前 N 条最相关结果的摘要，而不是全部；对于一段长文本，可以先调用一个小型、快速的摘要模型进行总结。

3. 格式化：将清洗、压缩后的数据，转换成对 LLM 最友好的格式。虽然 LLM 能处理 JSON，但信息的呈现方式极大地影响其理解效率和准确性。
  - 信息密度优先：使用结构化的纯文本或 Markdown 列表、表格，往往比一个巨大的嵌套 JSON 对象更容易被模型理解。
  - 结果与参数呼应：在格式化结果时，应附加上本次调用的工具名和使用的查询参数，帮助模型建立起“因”与“果”的联系。
  - 错误格式化：必须将技术性的错误堆栈转换为一条清晰、可执行的文本指令，如“工具调用失败，原因是：权限不足”。

二、重新注入对话上下文的标准模式

一旦完成了格式化，接下来需要将它正确地注入对话历史，确保 LLM 能理解这条消息的语义。

遵循你所用 LLM API 的消息角色规范，使用专门的角色（如 OpenAI 的 `role: "tool"`）来标记这些消息。一条格式良好的工具结果消息应包含：

- `tool_call_id`：与之前模型发起的工具调用请求严格对应，这是 LLM 建立请求与响应之间关联的关键。

- `content`：经过清洗、压缩和格式化后的、信息密度高的文本内容。

将这些消息追加到对话历史末尾后，再次向 LLM 发起请求时，模型就能像阅读一份报告一样，准确地理解工具的执行结果，并基于此完成后续的推理和答案生成。这个“二次生成”过程，是 Function Calling 从“单次调用”升级为“交互式智能”的核心。

#### 在对话中，如何维护工具调用的上下文（即之前调用结果影响后续决策）？

维护工具调用的上下文，本质上就是为 Agent 建立起一个能够跨轮次、跨工具调用的“工作记忆”。这是 Agent 能够执行复杂的、多步规划任务的基础。没有这个能力，每一次工具调用都是孤立的，Agent 就像一条只有七秒记忆的鱼，永远无法将多个工具串联起来解决问题。

一、对话历史是天然的上下文载体

最基础也最关键的方法，就是严格遵循 LLM API 所定义的消息结构，将所有相关信息都保存到对话历史中。这是一个包含所有 `system`, `user`, `assistant` (及其内嵌的 `tool_calls`), 以及 `tool` 角色的消息列表。这个列表本身，就是 Agent 的“记忆链”。每一次向 LLM 发起的新的请求，都必须将这个完整的记忆链发送过去。

二、上下文维护的最佳实践

1. 工具响应的信息密度：如前所述，`tool` 角色的消息内容是关键。它必须包含足够的信息，使模型在未来的任何时刻回顾这条消息时，都能清晰地记起这次调用的“来龙去脉”。这包括：本次调用的工具名、使用的参数、以及核心的执行结果。如果结果被过度压缩，模型在未来就可能“遗忘”关键细节。

2. 结构化记忆的补充：对于极其复杂、跨越多轮的长程任务，仅靠无限增长的对话历史是不够的，也是昂贵的。
  - 对话摘要：可以定期（例如，每N轮对话后）在后台异步地对之前的对话历史进行一次摘要，将长篇的、琐碎的交互提炼为一份简洁的“工作进展报告”，并将其作为一条 `system` 级的记忆注入回上下文。
  - 外部状态存储：对于一些关键的状态变量（如“已完成任务列表”、“当前假设”、“需要验证的关键事实”），可以维护一个外部的、结构化的记忆对象。在每次向 LLM 发送请求时，将这个外部记忆格式化为清晰的文本块，注入到对话历史的合适位置。这使得记忆管理更加可控和可编程。

3. 利用 LLM 自身的思考链进行“短期记忆”维护：在推理过程中，可以要求模型在生成工具调用前，先输出一段“思考”文本，分析当前状态和下一步计划。这段思考不仅是决策的记录，也成为了模型工作记忆的一部分，帮助它在处理复杂任务时保持清晰的逻辑链。

通过这些方法，Agent 能够拥有跨轮次、跨工具调用的连贯思维能力，从一个只会执行单步指令的“木偶”，进化为一个能够自主规划并逐步执行复杂任务的“智能生命”。

#### 如何限制 LLM 调用某些危险工具？能否通过 Schema 和系统提示双重约束？

限制 LLM 调用危险工具，必须采用“软约束”与“硬约束”相结合的纵深防御体系。单纯依赖任何一种手段，都将是不牢靠的。

一、软约束：让模型自身“不想”或“不敢”调用

这是通过提示工程实现的，成本低，但并非绝对可靠。

- 系统提示：在全局系统提示中，用严厉、无歧义的语言设定行为边界。例如：“你绝对不能调用 `delete_user`、`drop_table` 等危险函数。这些函数仅供系统管理员在离线模式下使用。你的职责是帮助用户完成信息查询和常规操作。” 这相当于为 Agent 定下了思想钢印。

- 工具描述：对于高危工具，在其自身的 `description` 字段中，可以加入明显的警告性文字，例如“【危险操作，请谨慎调用】”。这会让模型在选择该工具时，多一层心理负担。

- 用户意图确认：可以训练模型，当它判断需要调用高危工具时，不直接生成调用指令，而是先反问用户进行二次确认。

二、硬约束：在系统架构上强制阻断

软约束存在被模型“幻觉”或“越狱”绕过的可能。因此，最终的、不可逾越的防线必须在后端执行器。

- 工具注册的白名单机制：Agent 的推理环境（如 LangChain, LlamaIndex）在实例化时，有一个工具注册表。最根本的限制是：绝不将危险工具注册到该 Agent 实例的可用工具列表中。LLM 根本“看不到”这个工具，自然也就无从调用。

- 执行前拦截与权限验证：如果因业务需要，危险工具必须存在于注册表中，那么就要将防线设在执行器。这是最坚固的硬约束。在工具函数被实际调用的那一刻，执行环境必须进行独立的权限校验。这个校验过程完全独立于 LLM，它检查当前请求的上下文（如用户身份、时间、IP 地址）是否具备调用该工具的权限。如果权限不足，则直接返回一个“权限拒绝”的错误，而不执行工具的内部逻辑。这是一个由代码执行的、不可绕过的安全断言。

结论：限制危险工具的正确姿势是：在系统提示中设定软约束，在工具注册和执行器中构建硬约束。软约束是预防，硬约束是兜底。两者结合，才能构建起对抗意外和恶意调用的坚固屏障。

#### 工具发现的动态性：如何让 Agent 在运行时发现新工具？通过注册表还是自然语言描述？

工具发现的动态性，决定了 Agent 生态的开放性和可扩展性。在运行时让 Agent 获知并使用新工具，主要有两种路径，它们适用于不同的场景。

路径一：基于中心化注册表的动态加载

这是目前工业界标准的、可控且高效的方式。

- 原理：系统维护一个工具注册中心，可以是一个配置文件、一个数据库，或者一个远程服务。当新的工具被开发完成后，开发者向注册中心注册其元数据（即 JSON Schema）。

- 运行时的工具发现：当 Agent 启动或接收到一个新任务时，它会向注册中心查询当前可用的工具列表。注册中心可以根据任务上下文、用户权限、环境变量等，动态地决定返回哪些工具。例如，一个普通用户的 Agent 实例，注册中心只会向其发放无危险性的只读工具。

- 优势：安全可控，支持权限管理和版本控制。工具的执行逻辑在本地或已知的远程服务器上，延迟低。

- 局限：工具的扩展需要人工（开发者）预先将工具接入并注册。Agent 不能自主发现完全未知的互联网 API。

路径二：基于自然语言描述与 API 文档的即时发现

这是一种更开放、更接近 AGI 想象的路径，让 Agent 能够“阅读文档学习新工具”。

- 原理：当用户或任务提供一个新工具的详细自然语言描述或 API 文档（如 OpenAPI/Swagger 文件）时，Agent 的规划器直接将这些描述文本作为上下文，临时构建出一个“虚拟工具”的 Schema，并尝试生成调用。

- 运行时的工具发现：Agent 接收到的不是预先注册的函数名，而是一段纯文本。例如，用户说：“我找了一个新的邮件 API，文档如下：`POST /sendmail`，参数为 `to`, `subject`, `body`...，请帮我用它发邮件。” Agent 需要在这个元信息的指导下，生成一次 HTTP 调用。

- 优势：极具灵活性，可以即时接入海量的、标准化的互联网 API，无需人工编写代码。

- 局限：存在巨大的安全风险和不确定性。LLM 对 API 文档的理解可能出错；无法进行严格的 Schema 和权限校验；API 调用的延迟不可控；容易受到中间人攻击。

实践中的选择：目前，在生产系统中，以注册表为基础、以自然语言描述为补充的混合模式是主流。核心的、需要高安全性和高性能的工具通过注册表管理；同时，为 Agent 提供一个“通用 API 调用”工具，可以接受自然语言描述的请求，但该工具本身在沙箱中执行，且权限受到严格限制。这使得 Agent 在安全的前提下，具备了初步的开放域工具使用能力。

#### 工具使用的粒度：应该提供少量强大工具，还是大量细粒度工具？各自的利弊。

工具粒度是 Agent 系统设计中的经典权衡，很像软件工程中的“单体架构 vs 微服务架构”之争。

一、少量强大工具——多功能瑞士军刀

- 设计：提供少数几个功能覆盖面广、参数复杂、带有条件逻辑的工具。例如，一个名为 `manage_database` 的工具，包含 `operation` 参数，其值可以是 `query`, `insert`, `update`, `delete`。

- 优点：对 LLM 的决策压力小，因为可选工具列表短，选择工具本身不容易出错；数据流更集中，便于维护。

- 缺点：工具的 Schema 极其复杂，LLM 需要面对高度嵌套、包含大量可选参数和条件逻辑的参数结构，在参数提取时极容易出错。复杂的工具内部逻辑像黑盒，使得 Agent 难以诊断失败原因。修改一个功能会影响整个工具的稳定性。

二、大量细粒度工具——单一职责的工具链

- 设计：每个工具只做一件极其微小、定义清晰的事情。例如，`query_database`, `insert_database`, `update_database`, `delete_database` 被拆分成四个独立的工具。

- 优点：每个工具的 Schema 简单、清晰、易于理解，LLM 在参数提取上的准确率极高。工具的独立性使得单个功能的更新和调试变得容易。简单工具更容易被组合，以解决复杂的新问题。

- 缺点：LLM 需要在长工具列表中进行更复杂的“意图分类”，容易出现“工具选择错误”（即本应调用工具A，却选了工具B）。对模型的推理和规划能力要求更高。

三、如何决策与最佳实践

最佳实践是倾向于细粒度工具，但通过“工具组”和“智能路由”来弥补其选择复杂度的问题。

- 细粒度优先：首先根据单一职责原则，将功能拆分为原子工具。这使得每个工具的 Schema 是简单、可预测的。

- 构建工具组：通过注册中心或系统提示，根据任务类型或用户权限，将不同的原子工具组织成“工具包”。Agent 在启动时，只加载与当前任务相关的工具包，而不是全部。这既保留了原子工具的准确性，又缩小了 LLM 的选择范围。

- 引入“智能路由器”工具：设计一个专门的 `choose_tool` 工具，其本身就是用来帮助 LLM 从细粒度的工具集中进行选择的。但这不能替代正确的设计。

总之，信任 LLM 像一个初级工程师，给它简单、明确的指令（细粒度工具）比给它复杂、模糊的指令（庞大工具）要更可靠。将复杂度留给后端的业务逻辑，将简洁留给模型的 Schema。

#### 设计一个工具时，如何权衡通用性和特异性？Schema 如何适应？

工具的设计常常面临一个两难：设计得太通用（如一个 `search` 工具能查所有东西），模型在参数提取时容易混淆意图；设计得太特异（如 `search_products_by_name` 和 `search_products_by_category` 是两个工具），工具数量会爆炸，且模型难以选择。

一、通用性与特异性的权衡法则

核心原则是：以意图的清晰度来决定工具的边界。如果两个操作在用户的自然语言意图上可以被清晰地区分，就应设计为不同的工具；如果区别仅在于某种参数的不同值，就应将它们合并为一个通用工具，用参数来区分。

- 何时倾向于特异性：当不同操作对应着截然不同的后端逻辑或权限要求时。例如，`get_product_details` 和 `purchase_product` 虽然都与产品有关，但一个是纯查询，一个是带有支付副作用的高风险操作。将它们分开，是安全设计的必然要求。

- 何时倾向于通用性：当多个操作只是同一类功能的不同变体时。例如，用户问“最新的华为手机”、“三星平板”或“价格低于2000的耳机”，其意图都是“搜索商品”。应该使用一个 `search_products` 工具，用 `query` 或 `filters` 参数来承载不同的搜索条件，而不是为每个品牌或品类创建一个工具。

二、Schema 的适应设计

为使 Schema 适应这种权衡，需要采用参数化的描述。

- 使用明确的枚举或字符串参数，而非创建大量独立工具。例如，不要创建 `start_charging` 和 `stop_charging` 两个工具，而是创建一个 `control_charging` 工具，其中包含一个 `action` 参数，其 `enum` 值为 `["start", "stop"]`。这既保持了工具的通用性，又通过枚举保证了参数值的特异性。

- 在参数的 `description` 中进行精细化引导。这是平衡通用性和特异性的关键技巧。对于一个通用的 `search` 工具，其 `query` 参数的描述可以写为：“用于搜索的关键词。可以输入产品名称、类别、品牌或任何相关的描述。例如，'华为手机'、'冬季羽绒服'、'促销耳机'。” 这使得一个通用参数，具备了处理多种特定场景的能力。

- 评估 LLM 的理解能力。如果你发现模型在某个通用工具的某个特定用法上频繁出错（例如，总是分不清是要搜索“人”还是要搜索“职位”），那就说明这个工具可能过于通用，需要被拆分为 `search_people` 和 `search_jobs`。以模型的表现为最终裁决依据。

设计工具，就是为模型提供最合适的“词汇表”。词汇不宜过多（工具数量爆炸），也不宜一个词表达所有意思（工具过于通用）。一个精心设计的工具集，应该让模型能够精准、无歧义地表达其操作意图。

#### 参数提取的鲁棒性：用户遗漏必填参数或提供了模糊值时，Agent 应该如何澄清？

用户输入是模糊、不完整、充满歧义的。一个脆弱的 Agent 会在信息不全时“猜测”参数或直接报错，而一个智能的 Agent 则会像一位经验丰富的客服，通过主动澄清来获取必要信息。

一、澄清机制的设计

澄清不是模型的自发善意，而是需要通过精心设计的系统提示和工具 Schema 来引导和约束的行为。

1. 在系统提示中注入澄清策略：必须明确地告诉模型，在某些情况下必须停止生成工具调用，转而生成一个向用户提问的文本回复。核心指令包括：
  - “当需要调用工具时，如果某个必填参数没有被用户明确提供，不要猜测或使用默认值。”
  - “生成一个礼貌的追问，向用户请求这个缺失的信息。”
  - “如果信息模糊（例如，‘查下苹果’），不要自行消歧，而是列出可能的解释，让用户选择。”

2. 在工具描述中标注“必需的上下文”：对于某些参数，即使它不是 Schema 中的 `required` 字段，但如果没有它会导致错误或不精确的结果，可以在参数 `description` 中注明：“如果没有提供此参数，应向用户询问以澄清。”

二、澄清的策略与技巧

- 精准定位缺失项：模型不应笼统地问“您能提供更多信息吗？”，而应精确地指出缺失了什么。例如：“为了帮您预订酒店，请告诉我您打算入住的日期是？”

- 处理模糊值的多选一策略：当值存在歧义时（如“苹果”），模型应能列出几个最可能的选项，并让用户选择。例如：“您是指苹果公司，还是想要找关于苹果水果的信息？”

- 提供带默认值的快速确认：对于可以推断出高置信度默认值的情况，模型可以生成一个带默认选项的确认性问题。例如：“您要查询北京的天气吗？如果是，请确认。或者您也可以告诉我其他城市。” 这比一个完全开放的“你要查哪里”要高效得多。

- 维护澄清状态：在一次澄清后，用户的补充回答可能依然不完整。Agent 必须有能力继续追问，直到信息足够。这要求框架能够处理多轮的“澄清-回答”循环。

通过构建这种主动的、精准的、用户友好的澄清机制，Agent 的交互体验将从“经常出错的命令式工具”进化为“善于沟通的协作助手”。

#### 如何评估 Function Calling 的准确性？定义参数提取准确率、工具选择正确率等指标。

评估 Function Calling 的准确性，需要将其拆解为三个关键环节：工具选择、参数提取和流程规划。每个环节都需要独立的评估指标。

一、工具选择正确率

这是衡量模型能否在正确的时间选择正确的工具。

- 指标：Tool Selection Accuracy
  - 定义：在需要调用工具的场景中，模型选择了正确工具的比例。
  - 计算：`(正确选择工具的调用次数) / (所有应触发工具调用的总次数)`。
  - 细化：对于多工具场景，还可以计算 Precision@K（正确的工具是否在模型的 Top-K 候选里）和 MRR（正确的工具在候选列表中的排名）。

二、参数提取准确率

这是衡量模型在选定工具后，能否为其提供准确参数的能力。

- 指标1：Exact Match (EM)
  - 定义：模型生成的参数键值对，与标准答案（Ground Truth）在所有必填字段和值上都完全一致的比例。这是最严格的标准。

- 指标2：F1 Score for Parameters
  - 定义：将生成的参数看作一个键值对集合，分别计算 Precision（生成的参数中有多少是正确且必要的）和 Recall（标准答案中有多少参数被正确生成），然后取调和平均。这比 EM 更鲁棒，能评估部分正确的调用。

- 指标3：幻觉参数率
  - 定义：模型生成了 Schema 中不存在的参数（幻觉）的调用比例。这是衡量模型对 Schema 遵循能力的重要负面指标。

三、流程规划与鲁棒性

对于需要多步工具调用的复杂任务，评估其整体流程的正确性。

- 指标1：Task Success Rate
  - 定义：Agent 最终成功完成端到端任务的比例。这是最终的、最重要的业务指标。

- 指标2：Planning Efficiency
  - 定义：完成任务所需的最小工具调用步数与实际调用步数之比。评估 Agent 是否存在不必要的、冗余的调用。

- 指标3：Error Recovery Rate
  - 定义：当某次工具调用失败时（如参数错误），Agent 能在一到两轮内通过重试或修正参数成功恢复的比例。

评估数据集的构建：一个高质量的评估基准是核心。它必须包含多样化的查询、每个查询对应的正确工具调用序列的标注、以及针对不同错误类型的对抗性测试用例（如缺少参数、歧义查询、工具混淆等）。通过这套指标体系，可以全方位地诊断一个 Function Calling 系统的是工具选择不准、参数提取不清、还是整体规划逻辑混乱。
