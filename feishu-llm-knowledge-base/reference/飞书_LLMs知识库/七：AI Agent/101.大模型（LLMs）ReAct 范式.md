# 101.大模型（LLMs）ReAct 范式

#### 详细解释 ReAct 的核心循环：Thought → Action → Observation。

ReAct 的核心思想是让大语言模型在解决复杂任务时，不再孤立地进行推理或机械地调用工具，而是将推理与行动紧密结合，形成一个动态的、自我修正的闭环。这个闭环由三个节点组成：思考、行动和观察，它们首尾相连，构成一个持续迭代的循环。

思考是模型在每一轮循环的起点。它不是简单地复述已知信息，而是基于当前全部的上下文——包括原始问题、历史行动和观察——进行主动的分析和规划。模型会在思考中回答几个关键问题：我目前掌握了什么信息？我还缺少什么关键信息？下一步最合理的行动是什么？为什么？思考是 Agent 的“内心独白”，它负责生成下一步行动的战略意图。例如，“要回答这个问题，我需要知道2024年诺贝尔物理学奖得主是谁。我可以通过搜索来获取。”

行动是思考意图的具体执行。它不是一个模糊的指令，而是一个清晰、结构化、可被外部系统解析的操作符。行动通常包含一个动作类型和一个动作参数。例如，`Search[2024年诺贝尔物理学奖得主]`、`Calculator[123 * 456]` 或者 `Finish[答案文本]`。Agent 生成的行动指令，会被应用程序后端拦截，而不是直接返回给用户。

观察是外部世界对行动的反馈。后端执行了模型要求的行动后，会将返回的结果进行格式化处理，然后以观察的形式重新注入到对话上下文中。观察的内容可以是搜索引擎返回的文本摘要、计算器的数值结果、数据库查询的结构化数据，或者一个“行动执行失败”的错误信息。观察是真实世界信息进入模型认知的唯一入口，是打破模型内部知识孤岛的关键。

这个循环会一直持续，直到模型在思考后决定，已经收集到了足够的信息来回答用户问题。此时，它的行动不再是调用外部工具，而是执行一个特殊的停止动作，如 `Finish[生成的最终答案]`。至此，闭环结束，最终答案被返回给用户。

ReAct 的精髓就在于这个循环赋予了 Agent 一种“思考-试验-观察-再思考”的科学探索能力，使其能够在复杂、信息不完整的环境中自主地寻找解决方案。

#### ReAct 如何通过交错推理和行动来解决复杂查询？它与纯推理（CoT）和纯行动（传统工具调用）相比的优势。

ReAct 解决复杂查询的秘密在于它打破了传统范式中推理与行动的严格分离，让两者在微观层面上相互促进。它不是先推理完再行动，也不是行动完再推理，而是在每一个微小的步骤中，都交织着“想”和“做”。

这种交织如何工作？面对一个复杂的、需要多步信息检索的问题，ReAct Agent 首先会进行思考，拆解出第一个需要查询的信息点，然后立即发起一个搜索行动。收到搜索结果后，它不会直接跳到最终答案，而是再次思考，评估搜索结果是否回答了原始问题，信息是否充分，是否发现了新的需要查询的实体。基于这个评估，它可能发起第二次、第三次搜索，或者调用计算器来验证数据。它可以在搜索不到信息时，思考并决定更换关键词重试；也可以在搜索到意外的高价值信息后，临时决定深入探索，而放弃原有的部分计划。这种在每一步都重新评估局势、动态规划下一步的能力，是 ReAct 的核心。

与纯推理（CoT）相比的优势

纯推理方法（如 Chain-of-Thought）是一次性的、线性的。它在内部通过冗长的思维链进行推理，但其知识完全受限于模型本身的参数。当遇到需要实时信息或精确数据的问题时，CoT 只能靠“记忆”或“猜测”，极易产生幻觉。例如，让它比较两款最新发布手机的性能，它的知识截止日期可能使其完全无法回答。而 ReAct 可以主动去搜索这两款手机的最新评测，基于真实的观察来构建答案，从根本上解决了信息过时和幻觉问题。

与纯行动（传统工具调用）相比的优势

传统的单步 Function Calling 往往是“一次性”的。它将用户的整个请求映射到一次 API 调用，然后基于返回结果生成答案。当任务需要多步串联时（例如，“查一下2023年图灵奖得主的博士毕业院校”），单次调用很难一步到位。一个过大的函数会难以设计，而多个函数的组合则缺乏中间的推理来串联。ReAct 则优雅地解决了这个问题：它将任务分解为一系列简单的原子工具调用，并用 Thought 将它们串联起来，形成一条灵活的工具链。

总结优势：ReAct 比 CoT 多了获取外部真实信息的能力，因此更准确；比传统工具调用多了动态的、多步的推理和纠错能力，因此更强大、更鲁棒。它是两者的融合与超越。

#### 写出一个 ReAct 提示的典型模板，包含 Thought、Action、Observation 的边界。

一个高质量的 ReAct 提示模板，其核心是清晰地向 LLM 展示这种交替结构，并教会它何时思考、如何行动。通常，我们会提供一个包含一到多个完整示例的少样本提示词，然后将当前问题交给模型去续写。

通用 ReAct 提示模板

```plain text
你是一个能够通过思考和行动来解决复杂问题的智能助手。你可以使用以下工具：

1. Search[query]: 向搜索引擎发起查询，返回相关结果的摘要。
2. Calculator[expression]: 计算一个数学表达式，返回计算结果。
3. Finish[answer]: 当你认为已经找到问题的最终答案时，将答案写在[]中，结束任务。

请严格按照以下格式进行输出，不要在格式之外添加任何内容：

问题：{用户输入的问题}
Thought: {你的思考过程，分析当前状态和下一步计划}
Action: {你决定执行的动作，必须从上方工具列表中选择}

Observation: {动作执行的结果，由系统自动填入}

... （Thought/Action/Observation 循环重复）...

Thought: 我现在已经有了足够的信息来回答这个问题。
Action: Finish[最终答案]

现在开始：
问题：{用户的问题}
```

一个完整的少样本示例

这个示例被放在提示中，让模型模仿学习：

```plain text
问题：2024年诺贝尔和平奖得主是谁？
Thought: 我需要知道2024年诺贝尔和平奖得主的信息。我首先搜索一下。
Action: Search[2024年诺贝尔和平奖得主]

Observation: 2024年诺贝尔和平奖授予了日本原子弹氢弹爆炸受害者团体协议会...

Thought: 搜索结果已经明确告诉我得奖者是该团体。信息充分，可以给出答案。
Action: Finish[2024年诺贝尔和平奖得主是日本原子弹氢弹爆炸受害者团体协议会。]
```

设计的关键在于格式的严格一致性。`Thought:`、`Action:` 和 `Observation:` 这些关键词是解析器和模型之间的协议。任何边界的不清晰都可能导致解析失败。通过这种方式，我们为 LLM 搭建了一个明确的舞台，让它在一个结构化的沙盒中进行智能的探索。

#### 如何解析 ReAct 的输出以提取动作并执行？常用的正则或有限状态机方法。

ReAct 的输出是一段自由文本与结构化指令的混合体。解析器的工作就是从这段文本中精准地识别出最新的一个“Action”指令，将其提取出来并传递给执行器；同时，当“Finish”动作出现时，能够终止循环。

解析器的核心任务

1. 提取最新的 Action：解析器必须能够从可能包含多轮历史文本的模型中，找出最后一次出现的、符合格式的 Action 行。

2. 提取 Action 类型和参数：将 `Action: Search[2024 Nobel]` 这样的字符串，解析为结构化的数据：`{"action_type": "Search", "action_param": "2024 Nobel"}`。

3. 处理边界情况：模型可能输出格式错误的 Action（如缺少方括号、拼写错误），解析器需要有一定的容错或明确的错误处理机制。

常用解析方法

1. 基于正则表达式的解析

这是最常用、最轻量的方法。编写一个正则模式，去匹配 Action 的格式。例如：

```plain text
Action:\s*([^\[]+)\[(.*)\]
```

- `\s*` 匹配可能的空格。

- `([^\[]+)` 捕获组1：提取 `[` 之前的字符串，作为动作类型（如 `Search`）。

- `\[(.*)` 捕获组2：提取 `[` 之后的内容，作为参数。

解析流程是：获取完整模型输出 -> 用正则匹配所有 Action -> 取最后一个匹配项 -> 提取动作和参数。如果匹配失败，可以返回一个错误观察，要求模型重新输出。

2. 基于有限状态机的解析

当 ReAct 的格式更灵活或更复杂时，可以设计一个简单的状态机。状态机逐行阅读文本，在“自由文本”和“结构化指令”之间切换。

- 状态1：等待Action。逐行扫描，寻找以 `Action:` 开头的行。

- 状态2：读取Action。一旦找到，进入此状态，记录动作类型和参数。

- 状态3：确认结束。检查 Action 是否为 `Finish`，如果是，状态机进入停止状态。

状态机的优势是逻辑更清晰，易于处理多行 Action（如果参数跨多行）等复杂情况。

3. 基于 JSON 模式的直接输出

现代 LLM 已经强大到可以直接输出 JSON 格式的响应。在提示中要求模型输出：

```json
{"thought": "...", "action": {"type": "Search", "query": "..."}}
```

这样，解析器只需一行 `JSON.parse()` 即可。这彻底消除了正则解析的脆弱性，是目前最可靠的方法。如果模型不支持原生 JSON 模式，正则解析依然是健壮的首选。

无论哪种方法，解析器都必须被设计为可容错的。当解析失败时，系统应能将错误信息作为一次观察返回给模型，让模型有机会进行自我修正，而不是直接崩溃。

#### 当动作执行后，如何将 Observation 格式化并注入回提示，以继续下一轮思考？

Observation 是连接外部世界与模型内部认知的桥梁。对其格式化的质量，直接决定了模型能否有效利用这些新信息进行下一轮推理。

格式化的三项核心原则

1. 相关性优先，过滤噪音：工具返回的原始数据（如搜索引擎的 JSON 响应）往往包含大量无关的元数据。格式化器必须从中只提取出核心的、对回答问题有帮助的文本内容，例如，只保留搜索结果的标题和摘要，丢弃时间戳、URL、状态码等。

2. 保持结构清晰，便于模型解析：Observation 必须被清晰地标记，以区别于 Thought 和 Action。使用与提示模板一致的关键字 `Observation:` 开头。如果结果包含多个条目（如多条搜索结果），应使用编号列表进行格式化，使其一目了然。

3. 信息密度与长度权衡：过长的 Observation 会迅速撑满上下文窗口，带来高昂成本。但过度压缩可能会丢失关键细节。格式化器需要根据内容类型做出判断：对于简单的计算器结果，返回精确值即可；对于复杂的搜索结果，保留一个带有原文引用的、适度详细的摘要。

注入回提示的流程

1. 文本构造：将原始的工具执行结果，按照上述原则处理，形成一个纯文本字符串。例如：`Observation 1: 1. 2024年诺贝尔和平奖授予... \n2. 颁奖典礼将于12月10日...`。

2. 追加到对话历史：将这段格式化后的文本，作为一条新消息，追加到与 LLM 的对话历史列表中。这条消息通常被标记为 `user` 或一个特殊的 `system` / `tool` 角色。

3. 上下文组装与重发：将更新后的完整对话历史，再次发送给 LLM。LLM 在接收到这段新的 Observation 后，会像阅读一份刚刚呈上的情报，基于它展开下一轮思考，并生成新的 Thought 和 Action。

这个“执行-格式化-注入-再推理”的闭环，是 ReAct 系统的心脏跳动的节律。

#### ReAct 范式中的“思考”步骤是否必须是自然语言？可否使用隐式内部状态？

ReAct 范式在其经典实现中，Thought 被设计为显式的自然语言，但这并非唯一的可能。是否存在隐式内部状态，是 Agent 架构设计中的一个高级选择。

显式自然语言思考：优势与意义

将 Thought 外化为自然语言，是 ReAct 取得成功的关键设计之一。它带来了几个不可替代的好处。第一，可解释性和调试性。开发者可以清晰地看到 Agent 的推理链路，理解它为何在某一步选择某个 Action，从而快速定位问题。第二，上下文作用。这些自然语言 Thought 本身就是短期记忆的一部分。它们被保留在对话历史中，为后续轮次的推理提供了丰富的背景和逻辑延续。第三，涌现的纠错能力。模型可以通过阅读自己之前的 Thought，发现矛盾，并在后续 Thought 中进行自我修正。

隐式内部状态：可能的形式与代价

理论上，Thought 可以是隐式的。例如，模型可以使用一个无法被人类直接阅读的特殊编码来表示其内部意图，或者用模型某层的隐藏状态向量来表征“思考”。一些研究也在探索将推理过程压缩到连续的向量表示中。

然而，这种做法会带来巨大的代价。首先，它牺牲了可解释性，使得 Agent 的决策过程变成一个黑盒。其次，隐式状态不易被保存和跨轮次传递，需要额外的技术来维护。最重要的是，当前的大语言模型是被训练来生成文本的，显式的文字思考最符合它们的“思维习惯”，也是最能发挥其能力的形式。

结论：在目前的工程实践中，显式的自然语言思考是性价比和可靠性最高的选择。它充分利用了 LLM 的文本生成优势，同时为系统的透明性和可控性提供了保障。隐式状态更多是研究的前沿方向，在追求性能极限和可解释性的生产环境中，显式思考是不可或缺的。

#### ReAct 与常规的单步 Function Calling 有何区别？为什么多步推理需要 ReAct？

常规的单步 Function Calling 和 ReAct 的根本区别，不在于是否使用函数，而在于推理和行动的组织方式。前者是一次性的映射，后者是交互式的探索。

单步 Function Calling 的工作模式

在单步 Function Calling 中，模型收到用户请求后，立即分析出意图，选择最合适的一个工具，并生成一次函数调用。后端执行该工具，返回结果，然后模型基于此结果生成最终答案。这个过程是确定的、线性的：`请求 -> 选择工具 -> 生成调用 -> 得到结果 -> 回答`。

这种模式对于“帮我查一下明天北京的天气”这样简单的、单目标的查询非常高效。但当任务变复杂时，它的局限性就暴露了。例如，用户问“帮我比较一下这两款新发布的手机的性能”，这个任务隐含着多个子步骤：需要先分别搜索手机 A 和 B 的详细性能参数，然后进行对比分析。单步调用无法直接完成，因为它无法在一次调用中同时执行多个搜索，也无法在获得第一个搜索结果后，基于结果去调整第二个搜索的查询。

为什么多步推理需要 ReAct

多步推理任务的核心特征是：任务目标无法通过一次工具调用达成，需要多轮次的、有条件的信息获取和加工，并且每一步的决策都依赖于之前所有步骤的累积结果。

ReAct 正是为此而生。它将一个复杂任务动态地分解为一系列简单的原子操作。在“比较两款新手机”的例子中，ReAct 的流程是：

- Thought: “我需要先分别获取手机 A 和 B 的性能参数。先查手机 A。”

- Action: `Search[手机A 性能参数]`

- Observation: 获取到手机 A 的信息。

- Thought: “已获取手机 A 信息。接下来用同样的方式搜索手机 B 的参数。”

- Action: `Search[手机B 性能参数]`

- Observation: 获取到手机 B 的信息。

- Thought: “现在两款手机的信息都有了，可以进行对比分析并给出答案。”

- Action: `Finish[对比分析结果]`

在这个过程中，ReAct 的 Thought 起到了关键的“逻辑粘合剂”作用，它将多个独立的、被动的工具调用串联成一个智能的、目标导向的行动序列。因此，ReAct 不是 Function Calling 的替代品，而是它的“指挥家”，专为需要多步、动态推理的复杂任务而生。

#### 在 ReAct 循环中，如何防止无限循环？最大步数、停止动作（如 Finish）的设计。

无限循环是自主 Agent 最常见的失败模式之一。当 Agent 陷入无法自拨的困境时，它会不断消耗 Token、时间和计算资源。因此，设计健壮的终止机制是工程实现中的重中之重。

1. 设计明确的停止动作

最优雅、最智能的退出方式是让模型自己按下“停止键”。这就是 `Finish` 动作的作用。我们需要在系统提示中明确定义，当模型认为“我的信息已足够，可以回答用户问题了”，就必须生成一个特殊的、不可被混淆的结束动作，如 `Finish[最终答案]`。

解析器一旦捕获到这个动作，就意味着任务成功完成，循环立即终止。关键在于教会模型何时应该 `Finish`。这需要在少样本示例中，清晰展示“信息足够，可以回答”和“信息不足，仍需探索”的场景对比。

2. 设置硬性的最大步数限制

永远不要相信模型会总是正确地自行终止。必须在系统层面设置一个无法逾越的“安全阀”——最大循环次数（例如，10 或 15 步）。这是一个独立的计数器，与模型的生成行为无关。

当循环计数达到这个上限时，调度器强制终止循环，并接管控制权。此时，它不会直接丢弃所有信息，而是采取一个保底策略：将迄今为止所有的对话历史发送给 LLM，并要求它“根据以上所有信息，给出你当前能得出的最佳答案，并指出还有哪些问题未解决”。

3. 其他辅助终止条件

- 动作重复检测：如果监控到 Agent 在连续几步内，执行了完全相同或高度相似的 Action（例如，连续三次用同一个关键词搜索），这通常意味着它陷入了思维僵局。系统可以注入一条警告 Observation，或者直接强制终止。

- 无效 Action 次数限制：统计返回“错误”或“无结果”的 Action 次数，如果比例过高，说明当前策略失效，应提前终止。

- 时间预算限制：为整个 ReAct 循环设置一个全局的执行时间上限。

通过“模型自我终止”和“系统强制终止”的双层保护，我们可以在充分发挥 Agent 自主性的同时，牢牢将风险控制在可接受的范围之内。

#### ReAct 中的动作空间可以包含哪些？搜索、计算、数据库查询、代码执行等。

ReAct 的动作空间，定义了 Agent 与外部世界交互的能力边界。一个丰富、设计精良的动作空间，能让 Agent 成为超级连接器；而一个匮乏或不清晰的动作空间，则会限制其解决问题的能力。

常见的动作类型

1. 信息获取类：
  - 搜索：最核心的动作。可以是通用网络搜索，也可以是针对特定领域（如企业内部文档、学术论文）的搜索。
  - 数据库查询：通过生成 SQL 或自然语言查询，从结构化数据库中提取精确信息。
  - 文档检索：在 RAG 架构中，直接对知识库进行向量相似度检索。

2. 精确计算与逻辑执行类：
  - 计算器：执行安全的数学表达式，解决模型不擅长的精确算术问题。
  - 代码解释器：在隔离的沙箱中运行 LLM 生成的代码，用于数据分析、图表生成、复杂算法验证等。

3. 事务与操作类：
  - API 调用：与外部服务交互，如发送邮件、创建日程、下单购物、控制智能家居。这类操作通常具有现实世界的副作用，需要权限控制。
  - 数据写入：更新数据库或用户资料。这需要严格的安全和认证机制。

4. 人机协同类：
  - 向用户提问：当遇到信息缺失或指令模糊时，主动向用户发起澄清，获取必要信息。这赋予了 Agent 谦逊和协作的能力。

5. 任务控制类：
  - 完成任务：即 `Finish`，提交最终答案。
  - 放弃任务：在确认无法完成时，优雅地退出并解释原因。

设计动作空间的要点

- 原子性：每个动作应该做一件很小的、定义清晰的事情。一个庞大的、参数复杂的动作会让模型难以驾驭。

- 命名清晰：动作名应直观反映其功能，如 `Search`、`Calculator`。这在提示工程中至关重要。

- 描述精准：在提示中，对每个动作必须提供详细的描述、适用场景和参数格式，特别是要说明其能力边界和限制。

一个精心设计的动作空间，是 Agent 能力大厦的坚实基础。

#### 分析 ReAct 的适用任务：为什么在需要实时信息或多步推理的场景中尤其有效？

ReAct 的架构决定了它在某些任务上拥有压倒性优势，而在另一些任务上则可能显得笨重。它的最佳战场是那些同时需要外部知识、逻辑推理和动态规划的复杂任务。

1. 需要实时或精确信息的任务

这是 ReAct 相对 CoT 等纯推理方法的绝对优势领域。大语言模型的知识是静态的、过时的。对于“今天的天气怎么样？”、“帮我查一下最新的财报数据”、“2024年奥运会首金是谁？”这类问题，模型无法依靠内部知识回答。ReAct 可以主动调用搜索工具，获取最新信息，并基于真实的观察来构建答案，从根本上解决了信息过时和幻觉问题。对于需要精确计算的问题，它也可以调用计算器，确保数字的准确无误。

2. 需要多步推理的复杂任务

这是 ReAct 相对传统单步工具调用的优势领域。许多现实问题无法通过一次 API 调用解决，需要进行“信息检索-分析-再检索-综合分析”的循环。例如，“比较一下2024年诺贝尔物理学奖和化学奖得主的主要贡献”，或者“帮我规划一个去日本看樱花的三天行程，并估算总花费”。这类任务需要串联多个搜索、多个计算，并且每一步都可能根据上一步的结果进行调整。ReAct 的 Thought 步骤使得这种多步的、带有条件逻辑的工具编排成为可能。

3. 需要探索和验证的开放域任务

当用户意图模糊，或者问题的解决方案不唯一时，ReAct 就展现出了强大的探索能力。例如，“帮我找一些关于某A公司最近负面新闻的源头”。Agent 可能需要先进行广撒网式的搜索，发现几个可疑的线索后，再对每个线索进行深入追踪和交叉验证。在这个过程中，ReAct 的 Thought 不断地评估搜索结果、调整搜索方向、摒弃无效线索，最终找到真相。这种“假设-验证”的循环是科学探索的微缩版。

总结：ReAct 不是一把万能钥匙，但对于那些有明确外部信息需求、需要多步逻辑串联的复杂任务，它是目前将 LLM 的强大推理能力与外部世界的真实信息融合得最好的范式之一。

#### 如何处理 ReAct 中的错误动作？Agent 如何恢复并调整后续推理？

ReAct 的核心优势在于其闭环结构，使其拥有在遭遇错误时自我恢复的独特能力。错误不再是致命失败，而是变成了一个可以被分析和应对的“观察”，驱动 Agent 的下一步推理。

错误的类型

在 ReAct 循环中，错误主要有两类。一类是动作执行错误，即工具返回了运行时的错误，如“搜索超时”、“计算语法错误”、“API 权限不足”。另一类是逻辑性错误，即动作本身执行成功了，但返回的结果与预期不符，或是无用的信息，例如搜索返回了完全不相关的内容。

Agent 如何恢复：将错误作为特殊的观察

Agent 的恢复能力，来源于它对观察的智能解读。当后端捕获到一个执行错误时，我们不会直接将其抛给模型，而是将它格式化成一个特殊的、富含上下文的观察文本。例如，对于一次超时的搜索，观察不是 `Error`，而是 `Observation: 搜索操作超时，未能获取到结果。你可以尝试简化查询词或更换搜索源。` 这条精心设计的消息，本身就是一条行动指南。

当 LLM 收到这样的观察时，它在下一轮的 Thought 中就会进行“故障分析”和“策略调整”。常见的恢复策略包括：

1. 重试与参数修正：如果错误是临时性的或参数明显有误，Agent 可能会决定重试，并修正参数。例如，它观察到 `Calculator[10 / 0]` 返回了除零错误，下一轮 Thought 就会分析：“我试图除以零，这是错误的。我需要重新思考这个计算。”

2. 降级与工具替换：如果一个工具反复失败，Agent 会尝试切换到功能相似但更可靠的替代工具。例如，“搜索引擎似乎不可用，我试试查询内部数据库。”

3. 回溯与目标修正：如果 Agent 发现当前错误是因为最初的假设有误，它会执行更根本的回溯。它可能在 Thought 中反思：“看来我假设这个信息是公开的是错误的。我需要调整搜索方向，或者向用户询问更具体的线索。”

工程层面的增强

除了依赖 LLM 的推理能力，我们还可以在系统层面对错误进行预处理。例如，后端可以自动对第一次失败的搜索进行关键词简化后重试，只有在重试仍然失败后，才将“已重试但依然失败”的观察返回给 LLM。这减少了不必要的推理循环。同时，全局步数和时间限制依然是最终的熔断机制，防止 Agent 陷入无限恢复的循环。

ReAct 的这种“观察-反思-调整”的闭环比传统的“调用-返回”模式要鲁棒得多，因为它赋予了 Agent 面对不确定性的弹性和智慧。

#### ReAct 与 Plan-and-Execute 范式的区别：ReAct 是即兴的，Plan-and-Execute 是先计划后执行，何时用哪种？

ReAct 和 Plan-and-Execute 代表了 Agent 在解决复杂问题时两种截然不同的思维模式：一个是即兴的爵士乐手，一个是严谨的建筑师。

核心区别

- ReAct 将规划和执行融为一体，形成了一个“思考-行动-观察”的实时闭环。它不在行动前制定完整计划，而是每走一步，都根据最新的环境反馈来动态决定下一步怎么走。它的强项在于灵活应变，对意外和未知有很强的适应力。

- Plan-and-Execute 则将规划和执行严格分离。它首先进行全局规划，生成一个包含所有步骤的完整计划；然后，再像一个执行脚本一样，逐步执行这个计划。它的强项在于结构性和全局一致性，能保证最终产出符合预期的蓝图。

何时用哪种？

选择哪种范式，取决于任务的特性和对过程的要求。

适合用 ReAct 的场景：

- 信息不全或动态变化的任务：例如，开放域的复杂问答、市场情报收集、交互式调试。你不知道答案会在哪里，需要像探险家一样不断搜索、发现新线索、并根据线索调整方向。

- 需要高度交互和用户确认的任务：例如，与用户协同完成一项预订。每一步都可能需要根据用户的反馈来调整，无法预先规划。

- 目标明确但路径未知的任务：解决问题的过程本身就是探索性的。

适合用 Plan-and-Execute 的场景：

- 步骤明确、结构化程度高的任务：例如，生成一份格式严格的项目报告、遵循标准作业流程的合同审核、执行一个已知的复杂计算。这些任务的步骤是相对固定的，可以被预先定义。

- 对最终产出的结构完整性要求极高的任务：你需要一份包含所有必要章节、逻辑严谨的文档。Plan-and-Execute 能很好地保证这一点，因为它先确立了骨架。

- 需要评估和审批执行计划的高风险任务：可以让 Agent 先生成计划，经人类审核批准后，再无人值守地自动执行。

融合趋势：在实际的复杂系统中，两者常常结合。例如，高层使用 Plan-and-Execute 制定战略计划，然后在执行每个具体子任务时，使用 ReAct 来进行灵活的动态交互。这就像一位项目经理先制定项目蓝图，但在执行每个具体任务时，又会根据实际情况灵活变通。

#### 如何提升 ReAct 的推理质量？比如在提示中加入示例或使用更优的 few-shot 格式。

ReAct 的推理质量，几乎完全由提示词的质量、示例的引导以及底层模型的能力共同决定。提升推理质量，核心在于为模型提供一套清晰、可模仿的“思考范本”。

一、精心设计少样本示例

这是最直接、最有效的提升手段。提供的示例必须覆盖关键的成功模式，尤其是要包含错误恢复的案例。一个绝佳的示例集应包含：

1. 成功的多步推理案例：展示一个复杂问题是如何通过“搜索、分析、再搜索、综合”的标准流程被解决的。

2. 从错误中恢复的案例：这是重中之重。展示当搜索返回无关内容时，模型是如何在 Thought 中分析“这个结果不相关，我需要更换关键词”，然后成功找到信息的。这能教会模型应对不确定性的能力。

3. “不知道”的案例：展示当多次尝试仍无法找到答案时，模型如何优雅地终止任务，并诚实地告知用户。

二、强调“引用事实，杜绝幻觉”

在系统提示中用最严厉、最清晰的语言设定规则。例如：“你的所有答案必须严格基于‘观察’中获得的信息。绝不允许编造、猜测或使用你自身的参数化知识来补充观察中没有的事实。如果在观察中找不到答案，就说找不到。” 这种指令，如果能通过少样本示例中的行为来体现，效果会更好。

三、优化 Thought 的写作风格

引导模型写出高质量的 Thought。一个好的 Thought 不应只是陈述事实，而应是一个“内部对话”，包含对当前状态的评估、对下一步行动的理由、以及对潜在风险的预判。例如，“搜索结果提到了事件A，但并未给出具体的日期。要回答用户，下一步需要专门搜索事件A的日期。” 这种“分析型”的思考，比“描述型”的思考更能驱动有效的行动。

四、技巧性的提示策略

- 区分“思考”与“行动”：在输出格式上，确保 Thought 和 Action 是严格分离的。

- 使用思维链作为思考的延申：允许 Agent 在生成 Action 之前，先输出一段自由文本，深入分析问题的核心和解决方案的优劣。

- 注入元认知指令：在系统提示中加入：“在每一步行动后，请评估你的行动是否让你更接近目标。如果没有，请调整策略。”

通过这些技巧，我们不是在简单地给模型下命令，而是在一步步地教它如何像一个专家一样去思考和解决问题。

#### 在 ReAct 中，外部工具返回大量信息时，如何让 Agent 关注重点？是否需要压缩观察？

外部工具（尤其是搜索引擎）返回的海量数据，是 ReAct Agent 面临的一大挑战。如果不加处理地全量注入，不仅会迅速撑满上下文窗口、推高延迟和成本，更严重的是，会将关键信息淹没在噪音中，导致模型注意力分散，做出错误决策。

答案是需要压缩，而且必须进行智能压缩。

压缩的策略

1. 格式化即压缩：在将工具返回的原始 JSON 注入上下文前，后端必须进行一次格式化处理。这包括：丢弃所有技术性元数据、只保留核心文本字段、对多个结果进行编号列表处理。一个简单的列表比一个冗长的 JSON 结构要友好得多。

2. 语义摘要压缩：当返回的内容过长（例如，一篇超长网页）时，可以调用一个廉价的、快速的 LLM 对内容进行摘要，只保留与当前任务最相关的信息。或者，可以要求模型输出一个“信息点列表”，而非直接保留原文。

3. 分级检索与展示：Agent 在规划时，不应只使用一个宽泛的搜索工具。可以提供更精细的工具，如 `search_titles`（只返回标题）、`search_summaries`（返回带摘要的结果）、`fetch_page`（在需要时获取全文）。这允许 Agent 像人类一样，先浏览标题和摘要，找到最相关的目标后，再深入获取全文。

如何让 Agent 关注重点

压缩只是第一步，还需要通过技术手段引导模型的注意力。

1. 在观察前缀中加入引导语：例如，`Observation: [以下是搜索返回的前3条最相关结果，请重点关注其摘要内容]`。

2. 高亮关键实体：在格式化结果时，自动对与查询高度相关的实体或数字进行加粗或特殊标记。

3. 要求模型进行“信息提取”式思考：在提示中训练模型，使其在接收到大量信息时，其 Thought 的第一句话是：“在以上观察中，最相关的信息是...”，从而强迫它主动进行信息筛选。

通过“智能压缩”和“注意力引导”的双重策略，我们能让 Agent 在信息的海洋中保持清醒，精准地找到航行所需的星辰。

#### ReAct 的提示模板设计技巧：如何强调“不要幻想”和“基于观察事实”？

让 Agent 杜绝幻觉，是其从“玩具”走向“工具”的核心要求。这不能仅靠一句“不要胡编”来实现，而必须通过系统化的提示工程，将“基于事实”内化为模型的底层行为准则。

技巧一：在系统提示中建立绝对的规则层级

在系统提示的开头，使用最强硬、最无歧义的语言设定原则。可以设置一个 `[最高指令]` 板块：“你的所有回答必须严格遵守以下原则：1. 你只能基于‘Observation’中提供的信息来回答问题。2. 如果Observation中的信息不足以回答问题，你必须诚实地说明‘信息不足’，严禁使用你自身的知识进行猜测或补充。3. 你所生成的一切事实性陈述，都必须能追溯到某次具体的Observation。”

技巧二：通过正反示例让规则具体化

抽象的规则不如一个鲜活的例子。在少样本示例中，必须包含两类关键案例。一个是正面案例，展示模型是如何在Observation中找到关键事实后，将其完整、准确地用于最终答案。更重要的是，要提供反面案例，展示模型在Observation信息不足时，是如何放弃编造，转而诚实地告知用户“无法找到”或发起进一步搜索的。这种“知止”的示范，比任何指令都更有说服力。

技巧三：设计强制性的“信息溯源”步骤

在提示模板中，可以要求在生成最终答案时，必须包含一个“信息来源”的附加说明。例如，让模型在 `Finish` 之前，先输出 `Thought: 我的答案基于以下观察：第1轮搜索和第3轮搜索。` 这种强制性的溯源步骤，会迫使模型在生成答案前，必须自觉地与观察内容进行核对。

技巧四：优化观察的注入方式

在格式化Observation时，不要只是提供一个编号列表。可以在其前后加上明确的指示性文本，例如：

text

[系统] 以下是搜索引擎返回的真实信息。请注意，你必须只基于这些信息进行推理。[观察开始]1. ...[观察结束]

这种“标记”强化了观察内容的权威性和边界性，让模型更清楚地认识到，什么是它应该依赖的证据，什么是它不应跨越的雷池。

通过这些层层递进的约束和引导，可以让“基于观察事实”从一句口号，变成模型根深蒂固的行为模式。

#### 如何评估 ReAct 系统的性能？除了最终答案正确率，还看哪些效率指标？

评估 ReAct 系统远比评估一个单轮问答模型要复杂，因为它的性能不仅体现在结果的对错上，更体现在其解决问题过程的智能性和效率上。一个答案正确但绕了无数弯路、消耗了大量资源的 Agent，在生产环境中是难以接受的。

一、任务成功率与答案质量

- 最终答案正确率：在标准测试集上，最终答案与参考答案一致的精确匹配（Exact Match）或 F1 分数。这是最根本的指标。

- 部分正确与完整性：对于复杂任务，即使最终答案不完全正确，也可以评估其正确完成了多少个子任务。

- 忠实度：生成的答案中，有多少比例的信息是可以在其执行轨迹的观察中找到依据的。这是衡量幻觉控制的核心指标。

二、推理与行动效率

- 平均动作步数：成功完成任务平均需要多少次 Thought-Action-Observation 循环。步数越少，效率越高。

- 工具调用正确率：模型在选择 Action 时，选择正确工具的比例。例如，需要搜索时却调用了计算器，就是一次错误。

- 参数提取准确率：在正确选择工具后，其提供的参数是否准确、充分。

- 冗余/无效动作比例：在总动作中，有多少是返回了无结果、错误、或与最终答案无关的冗余操作。一个低效的 Agent 会频繁地做“无用功”。

三、鲁棒性与错误恢复

- 错误恢复率：当某一步动作失败（如搜索超时、返回错误）时，Agent 能在后续步骤中通过修正参数、更换工具等方式成功恢复并最终完成任务的比例。

- 循环/死锁发生率：Agent 陷入无法自拨的重复行为或逻辑死结的频率。

- 抗干扰能力：在工具返回的结果中人为注入不相关的噪音信息后，Agent 答案质量的下降幅度。

四、成本与性能

- 平均Token消耗：完成一次任务所消耗的总输入和输出 Token 数。这是最直接的成本指标。

- 端到端延迟：从用户发起到返回最终答案的时间。对于在线服务，P95和P99延迟至关重要。

- 最大步数超限率：有多少比例的任务因达到预设的最大循环步数而被系统强制终止。

一个全面的 ReAct 评估体系，必须综合考量这些指标，才能精准诊断系统是“决策逻辑混乱”、“工具使用不当”还是“过于谨慎低效”。

#### 在批量推理或在线服务中，ReAct 循环带来的延迟和成本如何控制？

ReAct 的多轮循环特性，使其在延迟和成本上天生就比单次调用要高昂。将其部署到对响应速度和成本敏感的在线服务中，是一项重大的工程挑战。

一、控制成本的核心策略

1. 缓存机制：这是控制成本最有效的手段。建立两级缓存：对同一个用户查询，缓存其 ReAct 的最终答案；更精细地，对同一 `Thought -> Action` 决策，如果上下文相似，可以缓存其观察结果，从而避免重复的、昂贵的工具调用。

2. 模型分层使用：在 ReAct 的不同阶段使用不同成本的模型。用较小、较便宜的模型来执行简单的 Action 解析和常规的 Thought 生成，只在遇到复杂推理或决策时，才调用昂贵的强大模型。这可以极大降低平均成本。

3. 优化提示与压缩上下文：精心设计提示，使其在能完成任务的前提下尽可能简短。对每个 Action 的观察结果进行智能摘要，压缩其长度，减少后续请求的 Token 开销。定期对过期但重要的对话历史进行摘要，替换原始文本。

二、优化延迟的核心策略

1. 并行化执行：当 Agent 在某一轮思考后，决定需要执行多个相互独立的 Action 时（例如，同时查询北京和上海的天气），后端应支持并行工具调用。并发执行可以显著缩短墙钟时间。

2. 流式处理：将 ReAct 的 Thought 和最终的答案通过流式传输返回给用户。用户可以看到 Agent 的实时思考过程，这种持续的反馈极大地改善了感知延迟，虽然总耗时可能不变。

3. 预测性预取：对于常见或可预见的查询模式，可以在后台预先执行一些搜索，并将结果缓存。当用户请求到来时，可以直接命中缓存，延迟极低。

4. 异步化与解耦：将慢速的工具调用与主推理循环解耦。Agent 可以在发出慢速 Action 后，不阻塞等待，而是挂起当前任务，转向处理其他就绪的任务。当观察返回时，再恢复执行。

通过这些策略的组合，ReAct 系统的延迟和成本可以被优化到生产环境可接受的范围内，实现“智能”与“经济”的平衡。

#### 是否存在无需人工设计提示，模型自身就能涌现 ReAct 模式的情况？

答案是肯定的。ReAct 模式在顶级大语言模型上确实可以涌现，但这需要满足特定的模型条件和任务特征，并且其稳定性和可靠性远不如通过显式提示工程引导。

涌现的机制

这种涌现能力，本质上是模型在海量数据预训练期间，无意中学会了推理与行动交织的模式。预训练语料库（尤其是代码库和技术论坛）中包含了大量类似 ReAct 轨迹的文本，例如：开发者在命令行中的操作及其输出（`$ ls` -> 文件列表）、技术博客中“问题-搜索-结果-分析”的写作模式。模型在“阅读”了数以亿计的这种结构化交互文本后，学会了这种模式。当它遇到一个需要这种模式的问题时，即使没有专门的提示，它也可能自发地生成类似 `Thought: ... Action: ...` 的输出。

证据与局限

在 AutoGPT 等早期 Agent 实验中，即使没有显式的 ReAct 提示，GPT-4 在给定工具和任务目标时，也常常会自发地开始生成类似 Thought-Action-Observation 的序列。这证明了它是一种强大的涌现能力。

然而，这种涌现是不稳定的。模型可能会忘记格式，可能会跳过关键的思考步骤，也更容易产生幻觉。它完全依赖模型的“直觉”，无法进行任何工程上的约束和优化。因此，在生产环境中，显式的、精心设计的 ReAct 提示依然是首选。它提供了确定性、可控性和可调试性。涌现模式更多地被视为模型强大能力的证明，以及未来更加通用、无需提示的 Agent 架构的曙光。

#### 对比 ReAct 与 Reflection 机制：能否在 ReAct 中增加自我反思步骤？

ReAct 的核心在于“做中学”，即在行动的当下根据反馈进行调整。而 Reflection（反思）的核心在于“事后学”，即在一段完整的行动序列结束后，对其进行整体回顾，提炼出更深层次的教训。两者不仅不矛盾，反而可以完美结合，形成一种更强大的 Agent 学习模式。

两者的天然差异与互补

ReAct 的反思是即时和局部的。当一次搜索返回了不相关的结果，它在下一轮 Thought 中立即进行分析和调整。这种反思粒度细，但对解决当前问题非常有效。

Reflection 的反思则是延迟和全局的。它在一次完整的任务尝试（可能包含多次 ReAct 循环）失败后，被触发。它会把整个执行轨迹——包括所有 Thought、Action 和 Observation——输入给 LLM，要求它进行深度分析：“这次任务为什么失败了？关键的错误节点在哪里？下次遇到类似任务时，应该采取什么不同的策略？” 它的产出是一段具有持久价值的“教训”。

在 ReAct 中增加自我反思的流程

1. 任务级反思：在一次完整的 ReAct 任务结束后（无论成功或失败），触发 Reflection 模块。其生成的“经验教训”被存入长期记忆（如向量数据库）。

2. 检索与注入：当 Agent 开始一项新的、类似的任务时，它会从长期记忆中检索相关的历史反思。这些反思作为“先验知识”，在任务开始前就注入到系统提示中，指导其初始的规划。例如：“基于过往经验，在搜索此类信息时，应该优先使用XX关键词。”

3. 即时反思：也可以在 ReAct 循环内部，设置一个“阶段性反思”的检查点。例如，每完成 3 个步骤，就强制 Agent 暂停，进行一次简短的内部反思：“我目前的方向是否正确？有没有更高效的途径？”

这种“ReAct 负责在战场上灵活应变，Reflection 负责在战后总结经验以指导下一场战斗”的组合模式，赋予了 Agent 从单次任务到持续进化的学习能力。

#### 在多智能体系统中，ReAct 如何扩展为多 Agent 的协作推理和行动？

将 ReAct 从单兵作战扩展到多智能体协作，核心在于将“思考-行动-观察”的闭环，从单个 Agent 的内部心智过程，外化为多个 Agent 之间的结构化通信与协作协议。

扩展模式一：中心化协调的层级结构

在这种模式下，存在一个“管理者” Agent 和多个“执行者” Agent。管理者负责接收总任务，进行高层规划和任务分解，但它不亲自执行。它的“行动”是向执行者 Agent 委派子任务。管理者的 ReAct 循环变为：

- Thought：“这个任务需要先收集市场数据，再进行分析。我先派 Agent-A 去收集数据。”

- Action：`DELEGATE[Agent-A, 收集市场数据]`

- Observation：Agent-A 完成任务后，将其完整的执行结果作为一条结构化的报告返回给管理者。\
  管理者根据这个报告，再进行下一轮思考，决定下一步是派 Agent-B 去分析，还是自己整合所有信息。

扩展模式二：去中心化的动态协作

所有 Agent 是平等的，共享一个公共的“任务黑板”和“通信通道”。每个 Agent 都是一个独立的 ReAct 循环体，但它的 Observation 不仅来自自己调用的工具，还来自其他 Agent 广播的消息。例如，Agent-A 在搜索中发现了一个关键线索，它可以广播一条消息。Agent-B 在下一轮 Thought 中，会看到这条消息作为其观察的一部分，并决定是否基于此线索调整自己的行动。这种模式更灵活，但需要解决任务分配、冲突消解等复杂问题。

扩展模式三：对话式协作

Agent 之间通过自然语言进行“讨论”。例如，一个“规划者” Agent 先提出一个初步方案，然后以广播的形式让所有“评论家” Agent 观察。评论家们在各自内部经过 ReAct 式的“思考-调取知识-形成观点”后，输出反对或修改意见。规划者根据这些观察（意见），修改方案，再次广播，直到达成共识。

在这些模式下，ReAct 的“思考”和“行动”被赋予了社会性。Thought 变成了“团队内部沟通”，Action 变成了“对队友的委派或请求”，Observation 则同时来自工具和队友。这使多 Agent 系统能够完成远超单个 Agent 能力范围的宏大任务。

#### ReAct 与 RAG 的结合：当检索作为一个 Action，ReAct 如何决定何时检索以及检索什么？

ReAct 与 RAG 的结合，是赋予 Agent 主动获取知识的智慧，解决了传统 RAG 中“检索什么”和“何时检索”的固定化问题。

传统的 RAG 是“被动检索”：系统在收到用户查询后，立即无差别地进行一次检索，然后将检索结果作为上下文喂给 LLM。这种“一次检索，全篇使用”的模式在复杂任务中往往不够。

ReAct 使 RAG 进化为“主动、动态的检索”。在 ReAct 框架中，检索只是一个与其他工具等同的 Action，例如 `Search[query]` 或 `Retrieve[query]`。LLM 成为了检索的决策者，它能自主决定两个关键问题：何时检索，以及检索什么。

决策机制：如何决定

1. 何时检索：这由 ReAct 的 Thought 驱动。Agent 会在推理过程中评估自己的知识状态。当 Thought 中出现“我不确定这个信息”、“我需要核实一下”或“要回答这个问题，我需要更多关于 X 的证据”等分析时，就触发了检索 Action。它可能在一开始就检索，也可能在生成答案的过程中发现信息不足，临时决定补充检索。它甚至可以决定不检索，如果它认为自己已经掌握了足够的信息。

2. 检索什么：同样由 Thought 决定。Agent 不是简单地用原始用户问题去检索，而是会生成一个专门为检索优化的查询。例如，用户问“那件事后来怎么样了？”，Agent 的 Thought 会分析：“用户指的是上一轮对话中提到的 A 公司收购案。我需要检索它最新的进展。” 然后，它会生成 Action `Search[A公司 收购案 最新进展]`。这个查询比原始问题“那件事后来怎么样了”要精准得多。

协同工作的流程

一个完整的 ReAct+RAG 工作流可能是这样的：

1. Thought：“用户问了一个关于最新科技政策的问题。我需要查一下最新的官方文件。”

2. Action：`Retrieve[2024年 人工智能 政策 文件]`

3. Observation：获取到几篇相关政策文档。

4. Thought：“检索到的文档提到了政策A，但并没有详细说明其具体条款。我需要针对政策A进行二次检索。”

5. Action：`Retrieve[政策A 具体条款 实施细则]`

这种交互式的检索策略，使得 Agent 能够像一位侦探一样，根据线索不断调整搜索方向，精准地找到那些埋藏在海量信息中的关键证据。它使得 RAG 从一种信息注入技术，升级为一种由 Agent 智能驱动的信息探索策略。
