# 44.大模型（LLMs）SFT 损失掩码（仅计算回复部分损失）

#### 在 SFT 中为什么通常只对“assistant”部分计算交叉熵损失？写出损失掩码的实现逻辑。

指令微调（SFT）的唯一目标，是让模型学会如何生成高质量的回复。我们只对“assistant”部分计算损失，原因如下：

1. 明确优化目标，避免目标错乱：语言模型的训练目标是“给定上文，预测下一个词”。如果对所有角色（system, user, assistant）都计算损失，模型会被迫同时学习“如何提问”、“如何设定规则”和“如何回答”。这会导致模型在推理时无法确定自己的角色，可能不回答用户问题，而是去续写用户的提问。

2. 只学习有用行为：system prompt 是开发者预先设定的，user 输入是用户给的，都不需要模型去学习生成。如果对它们也计算损失，模型就会浪费大量参数去记忆和复现这些“固定”或“多变”的输入模式，而不是去优化生成回复的质量。

3. 防止有害模仿：如果对 user 输入也计算损失，模型可能会学会模仿用户的攻击性、偏见或恶意提问。这在安全上是不允许的。

损失掩码实现逻辑：

损失掩码是控制哪些位置的输出参与梯度计算的核心机制。在自回归语言模型中，输入序列和目标序列是错位对齐的：输入是 tokens[0:T-1]，目标是 tokens[1:T]。通过构造一个与目标序列等长的掩码向量，将不需要计算损失的位置标记为特殊值（在PyTorch中通常是 -100），损失函数会自动忽略这些位置。

关键点是：掩码必须作用于目标序列（即模型预测的标签），而不是输入序列。掩码与目标序列在维度上严格对齐。

#### 如果对话数据格式为 [User] ... [Assistant] ...，如何构造 labels 张量实现仅对 assistant 部分计算损失？

以最简单的纯文本格式对话数据为例：

```plain text
[User] 你好，请问... [Assistant] 您好！很高兴为您服务...
```

构造步骤：

1. 确定目标序列与掩码的对应关系：目标序列长度 = 输入序列总长度 - 1（每个位置预测下一个词）。因此，掩码长度 = len(input_ids) - 1。

2. 找到所有“非Assistant”部分的 token 位置：定位到`[User]`、`[System]`这些特殊标记，以及它们后面的所有内容，直到下一个角色的特殊标记开始为止。这些位置对应的所有 token 都是需要被掩盖的。

3. 创建与 input_ids 等长的数组：遍历整个 input_ids，根据每个 token 所属的角色段，在数组的对应位置上标记该 token 是否参与损失计算。对于 assistant 部分的 token，设为原始 token ID；对于非 assistant 部分，设为 -100。

具体示例：

假设对话为："[User] 你好 [Assistant] 我很好"

经过 tokenization 后得到 input_ids = [101, 102, 103, 104, 105]。

标签序列（labels）长度 = len(input_ids) = 5。

由于 "[User] 你好" 是用户部分，不需要计算损失，所以 labels 的前 3 个位置设为 -100。

"[Assistant] 我很好" 是助手回复，需要计算损失，所以 labels 的后 2 个位置保持为原始 token ID。

最终 labels = [-100, -100, -100, 104, 105]。

#### 在 HuggingFace 的 transformers 中，如何利用 -100 忽略某些位置的损失？具体写出代码片段。

在 HuggingFace 的 `transformers` 库中，所有模型的损失函数都遵循 PyTorch 的约定：当 `labels` 中的某个值为 `-100` 时，该位置的损失贡献为零。这是内置的、自动处理的行为。

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-2-7b-hf")
model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-2-7b-hf")

messages = [
    {"role": "system", "content": "你是一个有用的助手。"},
    {"role": "user", "content": "你好，请问..."},
    {"role": "assistant", "content": "您好！很高兴为您服务..."}
]

# 1. 使用 chat_template 格式化对话
input_text = tokenizer.apply_chat_template(messages, tokenize=False)

# 2. Tokenize 整个序列，返回 PyTorch 张量
inputs = tokenizer(input_text, return_tensors="pt")

# 3. 构建 labels 张量（与 input_ids 形状相同）
labels = inputs["input_ids"].clone()

# 4. 找到 assistant 回复的起始位置（示例中为固定位置，实际开发中需要根据 tokenized 后的序列自动识别）
assistant_start_pos = 10  # 假设从第10个token开始是assistant回复

# 5. 将非 assistant 部分的所有位置的 label 设置为 -100
labels[0, :assistant_start_pos] = -100

# 6. 前向传播，自动计算损失（只对 labels != -100 的位置计算）
outputs = model(input_ids=inputs["input_ids"], labels=labels)
loss = outputs.loss
loss.backward()
```

#### 多轮对话训练中，如果有多个 assistant 回复，是所有 assistant 回复都计算损失吗？如何设计掩码？

在多轮对话训练中，所有 assistant 回复都应该参与损失计算。因为每一轮 assistant 的回复都是模型在对应的对话上下文中需要学习的目标行为。

掩码设计方法：

1. 将所有轮次的 assistant 回复的 token 识别出来。

2. 所有其他部分（system, user）的 token 的 label 全部设为 -100。

3. 所有 assistant 部分的 token 的 label 保留为原始 token ID。

例如，一个两轮对话的 labels 可能是：

```plain text
System: ... (labels: -100)
User 1: ... (labels: -100)
Assistant 1: ... (labels: token_ids)  <- 计算损失
User 2: ... (labels: -100)
Assistant 2: ... (labels: token_ids)  <- 计算损失
```

这样，模型在每一轮 assistant 回复的位置都会学习“在当前对话历史下，如何生成恰当的回复”。

#### 如果系统提示（system prompt）也参与损失计算，可能会带来什么问题？

1. 目标错乱与角色扮演失败：模型会试图学习如何生成 system prompt，在推理时可能不执行用户指令，而是自己编造一个 system prompt，导致输出混乱。

2. 浪费训练资源：system prompt 是固定的文本模板，信息量低，可预测性强。让模型去优化这些位置的预测，是无效的参数更新，浪费计算资源。

3. 可能放大有害内容：如果 system prompt 中包含安全约束（如“你不能生成暴力内容”），当模型通过学习能够“生成”这些约束时，它可能同时学会了“如何在特定上下文下绕过这些约束”。这类似提示注入攻击，潜在风险巨大。

4. 降低多任务能力：模型会将其重要的模型容量，浪费在记忆 system prompt 这类无关紧要的“格式信息”上，而不是学习更有价值的语言理解和推理能力。

#### 对比仅掩码 assistant 回复，与同时掩码 system prompt 和 user 输入，模型在推理时的行为差异。

| 行为差异 | 仅掩码 assistant | 同时掩码 system 和 user |
| --- | --- | --- |
| 角色一致性 | 稳定扮演助手，只生成回复。 | 可能混乱，不确定自己该扮演哪个角色。 |
| 生成边界 | 知道何时停止生成。 | 可能不会主动停止，倾向于生成完整的多轮对话。 |
| 对话延续能力 | 遵循指令，就当前输入进行回复。 | 可能“抢话”，把用户的提问也生成出来。 |
| 安全性 | 不会主动输出用户/系统内容。 | 可能输出模拟的用户提问，给外界造成信息泄露的假象。 |
| 示例对比 | 用户: 你好。 模型: 你好，有什么可以帮助你的吗？ | 用户: 你好。 模型: 你好，有什么可以帮助你的吗？\n用户: 我想问一下...\n模型: ... |

行为差异的根源：仅掩码 assistant 的模型，其优化目标单一且明确：“给定对话历史，生成助手的回复”。而后者则试图优化整个序列的生成，它模仿的是整个对话过程，而不是对话中的一个角色。

#### 使用 tokenizer 的 chat_template 后，如何自动生成对应的损失掩码？

现代 tokenizer 的 `chat_template` 会为不同角色生成特殊的、可区分的 token（如 `<|im_start|>user\n`, `<|im_end|>`）。这为自动生成损失掩码提供了极大便利。

核心实现逻辑：

```python
def create_loss_mask(input_ids, tokenizer):
    labels = input_ids.clone()
    
    assistant_start_token = tokenizer.convert_tokens_to_ids("<|im_start|>assistant")
    assistant_end_token = tokenizer.convert_tokens_to_ids("<|im_end|>")
    
    in_assistant_section = False
    for i in range(labels.shape[1]):
        token = labels[0, i].item()
        
        if token == assistant_start_token:
            in_assistant_section = True
            labels[0, i] = -100  # 开头标记本身也不计算损失
        elif token == assistant_end_token:
            labels[0, i] = -100  # 结束标记本身不计算损失
            in_assistant_section = False
        elif not in_assistant_section:
            labels[0, i] = -100  # 非assistant部分，掩码
            
    return labels
```

关键逻辑：利用 `chat_template` 生成的特殊 token 作为标记位，通过一个简单的状态机，可以精确地识别出“assistant”角色所在的文本段，并自动将其他部分的 label 设为 `-100`。

#### 在多任务 SFT 中，有些任务可能需要对输入部分也进行学习（如翻译），掩码策略应如何动态调整？

多任务微调中，不同任务的优化目标不同。对于翻译任务，模型需要学习的正是“输入→输出”的映射，因此需要对输入部分也计算损失。

动态调整策略：

1. 在数据样本中添加任务类型标签：为每条训练数据添加一个 `task_type` 字段，如 `"chat"`, `"translation"`, `"code"`。

2. 根据任务类型实现不同的掩码逻辑：
  - `chat`: 仅对 assistant 部分计算损失。
  - `translation`: 对整个序列（source+target）或仅对 target 部分计算损失。

3. 在 Data Collator 中实现动态掩码：

```python
def dynamic_loss_mask(sample, input_ids):
    if sample["task_type"] == "translation":
        # 翻译任务：只对目标语言部分计算损失，或者对整个输入+输出计算损失
        return input_ids.clone()
    else:
        # 对话任务：只对 assistant 部分计算损失
        return create_chat_mask(input_ids, tokenizer)
```

通过这种方式，可以实现在一个 batch 内混合多种任务类型，并且每种任务都采用其最优的掩码策略。

#### 如果对 user 输入也计算损失，相当于让模型学习什么？为何一般避免这样做？

如果对 user 输入也计算损失，相当于让模型去学习 “如何生成用户的提问和指令”。

一般避免这样做的原因：

1. 目标函数错乱：模型的核心任务是“回答问题”，而不是“提出问题”。同时学习两者会导致优化目标冲突。

2. 角色扮演失败：推理时，模型可能会“替”用户说话，或者生成一段包含用户提问和助手回复的完整对话，而不是只扮演助手。

3. 安全风险：这是最致命的问题。如果模型学会了如何生成用户的提问，攻击者可以通过提示词诱导，让模型生成包含恶意、偏见或非法内容的“用户提问”。这为模型被滥用提供了途径。

唯一例外：在训练一个纯粹的“对话模拟器”或“数据增强生成器”时，我们需要模型能够模拟真实的用户行为。此时，对 user 输入也计算损失是合理的，但这并非通用助手模型的训练目标。

#### 损失掩码对训练效率和显存占用有影响吗？为什么？

训练效率：

- 正向影响：虽然损失掩码本身几乎不消耗额外计算，但它通过避免无效的参数更新，使得每个优化步都更有价值，从而间接提升了训练效率。模型不需要浪费时间去拟合那些可预测的格式文本。

显存占用：

- 几乎无影响：`labels` 张量本身是 `int64` 类型，显存占用极小。损失计算本身也是稀疏的：在 GPU 内核中，带有掩码的交叉熵损失计算不会为掩码位置分配额外的计算资源。它对整个计算图的内存占用没有可量化的影响。

总结：损失掩码是 SFT 训练的基石，它以一种极其轻量、高效的方式，精准地定义了模型的优化目标，是保证模型行为可控、安全、高效的关键技术。通过上面的`create_combined_loss_mask`函数，可以将整个流程串联起来，构建出可直接用于训练的数据集。

#### 解释为什么掩码部分对应的 logits 依然需要计算，但损失被忽略，这会浪费算力吗？

要回答这个问题，我们需要先理清 Transformer 解码器的计算范式。

为什么掩码部分的 logits 必须被计算？\
Transformer 的自回归生成是串行的。在训练时，虽然我们可以一次性输入整个序列，但模型内部仍然通过因果注意力掩码确保每个 token 只能看到它之前的上下文。因此，要预测位置 `t` 的 token，模型必须先计算出位置 `t-1` 及之前所有 token 的隐藏状态。`assistant` 回复的第一个 token，依赖于之前 `user` 输入的所有 token。如果不对 `user` 部分进行前向计算，就无法得到 `user` 输入最终的隐藏状态，也就无法为 `assistant` 回复的第一个 token 提供正确的上下文。所以，掩码部分的 logits 作为中间计算的“副产品”，是必须存在的。

这会浪费算力吗？

这确实是一种“算力浪费”，但这种浪费是在当前深度学习框架和 GPU 架构下，为了达到最佳性能而被迫接受的权衡。

具体来说：

- 计算的必要性：`user` 部分的计算是必须的，它为后续的生成提供了上下文。

- 计算的浪费性：`user` 部分对应的 logits 被计算出来，占用了 GPU 算力，但最终被掩码忽略，这确实是浪费的。

如何最小化这种浪费？

- GPU 的并行性要求计算“浪费”：核心矛盾在于 GPU 是为稠密矩阵乘法高度优化的。整个序列（包括 `user` 和 `assistant`）被一次性送入模型，可以充分利用 GPU 的并行计算能力。如果试图跳过 `user` 部分的 logits 计算，就需要实现稀疏或条件计算，这在当前 GPU 上会极大地降低并行效率，得不偿失。

- 低效的替代方案：理论上可以分两次前向传播：先用 `user` 的输入跑一遍模型，得到其最后的隐藏状态，再将其传给 `assistant` 部分进行生成。但这种方式引入了串行依赖，打断了 GPU 的并行流水线，训练速度会慢数倍。

- 工程上的最优解：因此，“一次性计算整个序列 + 损失掩码”的策略，尽管在数学计算上存在浪费，但在工程实践上，它通过最大化 GPU 并行度，实现了最高的训练吞吐量。最终的 logits 计算成本远低于破坏 GPU 并行性的代价，这是一种“以空间换时间”的策略，总体效率最高。

#### 如何在训练代码中实现“分段损失掩码”，对对话的不同段设置不同权重？

在某些高级场景中，我们希望对不同的 `assistant` 回复赋予不同的重要性。例如，某个任务的示例回复比日常闲聊的回复更重要。此时，我们可以对损失进行分段加权。

实现方式：将 `labels` 中的值从简单的 `-100` 或 `token_id`，扩展为可以携带权重信息的结构。

具体代码实现：

```python
import torch

def create_weighted_loss_mask(input_ids, tokenizer, sample_weights):
    """
    sample_weights 是一个列表，元素为 (start_str, end_str, weight)
    start_str/end_str 用于标识重要文本段的起止文本
    weight 是该段的损失权重，默认其他区域的权重为 1.0
    """
    # 克隆原始 input_ids 作为 labels 的基础
    labels = input_ids.clone()
    # 初始化权重张量，默认所有位置权重为 1.0
    weights = torch.ones_like(input_ids, dtype=torch.float)
    
    # 首先，将非 assistant 部分的权重设为 0（相当于原始掩码）
    assistant_start = tokenizer.encode("<|im_start|>assistant")[0]
    assistant_end = tokenizer.encode("<|im_end|>")[0]
    
    in_assistant = False
    for i in range(input_ids.shape[1]):
        token = input_ids[0, i].item()
        if token == assistant_start:
            in_assistant = True
            weights[0, i] = 0.0  # 特殊token本身不计算损失
        elif token == assistant_end:
            weights[0, i] = 0.0
            in_assistant = False
        elif not in_assistant:
            weights[0, i] = 0.0
    
    # 其次，根据 sample_weights 对特定 assistant 回复段调整权重
    for start_str, end_str, weight in sample_weights:
        start_ids = tokenizer.encode(start_str, add_special_tokens=False)
        end_ids = tokenizer.encode(end_str, add_special_tokens=False)
        # 在 input_ids 中定位这些文本段，并为对应位置设置权重
        # （此处为简化示例，实际开发中需要更复杂的序列匹配算法）
    
    # 计算加权损失
    outputs = model(input_ids=input_ids, labels=labels)
    logits = outputs.logits
    shift_logits = logits[..., :-1, :].contiguous()
    shift_labels = labels[..., 1:].contiguous()
    shift_weights = weights[..., 1:].contiguous()
    
    # 逐 token 计算交叉熵
    loss_fct = torch.nn.CrossEntropyLoss(reduction='none')
    token_losses = loss_fct(
        shift_logits.view(-1, shift_logits.size(-1)),
        shift_labels.view(-1)
    )
    token_losses = token_losses.view(shift_labels.shape)
    
    # 应用掩码（权重为0的位置损失为0）
    masked_losses = token_losses * shift_weights
    
    # 应用权重并计算最终损失
    final_loss = masked_losses.sum() / (shift_weights.sum() + 1e-8)
    return final_loss
```

应用场景：

- 课程学习：训练初期，对简单样本的 `assistant` 回复赋予高权重；随着训练进行，逐步降低简单样本权重，提高困难样本权重。

- 多任务平衡：不同任务的数据量差异巨大，对数据量少的任务的 `assistant` 回复赋予更高权重，防止被数据量大的任务淹没。

- 质量导向训练：对经过人工验证的高质量回复赋予更高权重，对自动生成、可能含噪声的回复赋予较低权重。

#### 当 assistant 回复中包含不希望模型学习的部分（如不确定的标注），如何局部掩码？

在实际标注中，某些 `assistant` 回复可能只有部分内容是正确的，其他部分存在不确定性。我们不应直接丢弃整条数据，而是精准地只学习正确的部分。

实现“局部掩码”的方法：

1. 使用特殊标记符标注不确定区域：在数据标注时，用 `[UNCERTAIN]` 和 `[/UNCERTAIN]` 这类特殊标记将不确定的文本片段包裹起来。这些标记符会被添加到模型的词表中。

2. 在构建 labels 时进行精确掩码：

```python
def create_local_mask(input_ids, tokenizer):
    labels = input_ids.clone()
    uncertain_start = tokenizer.convert_tokens_to_ids("[UNCERTAIN]")
    uncertain_end = tokenizer.convert_tokens_to_ids("[/UNCERTAIN]")
    
    in_uncertain = False
    for i in range(labels.shape[1]):
        token = labels[0, i].item()
        if token == uncertain_start:
            in_uncertain = True
            labels[0, i] = -100
        elif token == uncertain_end:
            labels[0, i] = -100
            in_uncertain = False
        elif in_uncertain:
            labels[0, i] = -100
    return labels
```

优势：这种方式保护了数据中的有效部分不被浪费，同时避免了模型学习到错误或模糊的知识。

关键：这需要标注者或自动标注流程具备识别不确定内容的能力，并将其用特殊标记符标注出来。

#### 设计一种方法，对 assistant 回复中的关键信息（如最终答案）赋予更高损失权重。

在某些任务中，`assistant` 回复的某些部分比其他部分更重要。例如，在一个包含推理过程的任务中，最终答案比客套话更加关键。我们希望模型在预测“答案”时更加精确。

设计方法：

1. 在数据标注时标记关键片段：使用特殊标记符 `[IMPORTANT]` 和 `[/IMPORTANT]` 将回复中的关键信息包裹起来。

2. 在损失计算时赋予更高权重：

```python
def create_importance_weighted_loss(input_ids, labels, tokenizer, importance_weight=3.0):
    # 默认所有权重为 1.0
    weights = torch.ones_like(input_ids, dtype=torch.float)
    
    important_start = tokenizer.convert_tokens_to_ids("[IMPORTANT]")
    important_end = tokenizer.convert_tokens_to_ids("[/IMPORTANT]")
    
    in_important = False
    for i in range(input_ids.shape[1]):
        token = input_ids[0, i].item()
        if token == important_start:
            in_important = True
            weights[0, i] = 0.0  # 标记符本身不计算损失
        elif token == important_end:
            weights[0, i] = 0.0
            in_important = False
        elif in_important:
            weights[0, i] = importance_weight  # 关键信息区域赋予高权重
    
    # 结合原始的 assistant 掩码
    assistant_mask = create_assistant_mask(input_ids, tokenizer)
    final_weights = weights * assistant_mask  # 只有 assistant 部分且是关键信息的区域才获得高权重
    
    # 后续损失计算逻辑与分段加权类似...
    return final_weights
```

效果：模型会更加关注 `[IMPORTANT]` 区域内的 token，在预测这些 token 时更加准确，从而提升模型在关键信息上的生成质量。

#### 如果对话数据中 assistant 回复存在严重错误，除了直接丢弃，能否通过损失掩码做部分学习？

直接丢弃数据是一种浪费，我们可以通过损失掩码从错误中学习正确的部分。

场景：`assistant` 回复整体是好的，但某个句子存在明显的事实错误（例如，在介绍北京时，错误地写成了“北京有3000万人口”）。

部分学习策略：

1. 利用强大的裁判模型识别并标记错误片段：使用 GPT-4 等模型作为标注工具，让它找出 `assistant` 回复中存在错误的具体句子，并用 `[ERROR]` 和 `[/ERROR]` 等标记符将其包裹起来。

2. 在构建 labels 时掩码错误片段：

```python
def create_error_masked_labels(input_ids, tokenizer):
    labels = input_ids.clone()
    error_start = tokenizer.convert_tokens_to_ids("[ERROR]")
    error_end = tokenizer.convert_tokens_to_ids("[/ERROR]")
    
    in_error = False
    for i in range(labels.shape[1]):
        token = labels[0, i].item()
        if token == error_start:
            in_error = True
            labels[0, i] = -100
        elif token == error_end:
            labels[0, i] = -100
            in_error = False
        elif in_error:
            labels[0, i] = -100
    return labels
```

效果：模型会学习错误片段周围的正确上下文，但不会学习错误内容本身。这比直接丢弃整条数据要好，因为它保留了数据中的其他有效信息。

更高级的做法：可以将错误片段替换为正确的信息（如果可获取），然后用掩码确保模型只学习替换后的正确内容，不学习原始的错误内容。

#### 如何验证损失掩码实现是否正确？列出测试方法。

损失掩码的实现错误非常隐蔽，因为模型依然能训练，但可能学到错误的行为。必须进行系统性的测试。

测试方法：

1. 单元测试：人工构造小样本并手动计算损失

创建一个只包含2-3个 token 的极简对话。手工计算正确的交叉熵损失值。在代码中运行该样本，对比框架输出的损失与手工计算值。如果完全一致，则掩码逻辑正确。

2. 梯度检查：验证非掩码部分梯度是否为零

```python
# 进行一次完整的前向+反向传播
loss.backward()

embed_grad = model.get_input_embeddings().weight.grad

# 找到 input_ids 中被掩码位置（labels == -100）对应的 token ids
masked_positions = (labels == -100)
masked_token_ids = input_ids[masked_positions]

# 关键验证：这些被掩码 token 对应的嵌入向量的梯度应该全部为零
for token_id in masked_token_ids.unique():
    assert torch.all(embed_grad[token_id] == 0), f"Token {token_id} 的梯度不为零！"
```

1. 生成行为测试：推理时模型是否正确扮演角色\
   用完全相同的 prompt，分别输入给一个未正确施加掩码的模型和一个正确施加掩码的模型。如果正确掩码的模型只输出 `assistant` 回复，而错误掩码的模型会输出 `user` 提问和 `system` 提示，则证明掩码实现正确。

4. 过拟合测试：小数据集上过拟合，检查损失是否降为零

准备一个包含50条固定对话的数据集，反复训练。如果损失能降到极低（接近0），说明掩码正确。如果损失卡在某个非零值无法下降，说明掩码实现可能有问题。

5. 可视化 labels 张量

#### 在序列拼接训练中，多个样本拼接到同一序列时，如何设计注意力掩码配合损失掩码，防止信息泄漏？

为了提高训练效率，我们常将多个短对话拼接成一个长序列。但必须确保不同对话之间不能互相看到，否则会造成信息泄露和错误学习。

关键设计：联合构造 `attention_mask` 和 `labels`

1. 构建 Block-Diagonal 的注意力掩码：

每个对话样本只能看到自己内部的上下文，看不到其他对话的内容。

```python
def create_block_diagonal_attention_mask(input_ids, tokenizer, sample_boundaries):
    """
    sample_boundaries 是列表中每个样本的起止位置
    """
    seq_len = input_ids.shape[1]
    # 初始化一个全 -inf 的注意力掩码
    attention_mask = torch.full((seq_len, seq_len), float('-inf'))
    
    for start, end in sample_boundaries:
        # 每个样本内部，使用标准的下三角（因果）掩码
        for i in range(start, end):
            for j in range(start, i + 1):
                attention_mask[i, j] = 0.0
    
    # 填充位置（[PAD]）也需要隔离
    pad_token_id = tokenizer.pad_token_id
    for i in range(seq_len):
        if input_ids[0, i].item() == pad_token_id:
            attention_mask[i, :] = float('-inf')
            attention_mask[:, i] = float('-inf')
    
    return attention_mask
```

1. 配合损失掩码：\
   对于每个样本的非 `assistant` 部分，同样将其 `labels` 设为 -100。

为什么要两者配合？

- 注意力掩码：保证模型在计算注意力时，看不到其他对话的 token，防止信息泄露。

- 损失掩码：保证模型只学习生成 `assistant` 的回复，不学习 `user` 的提问和 `[PAD]` 等无关 token。\
  两者共同作用，确保训练的正确性。

#### 使用 FlashAttention 等优化时，损失掩码的 -100 机制与标准实现是否兼容？

完全兼容，且无需特殊处理。

- FlashAttention 是一种精确的注意力加速算法。它只优化了注意力计算的速度和显存占用，不改变其数值结果。模型的输出 logits 与标准实现完全一致。

- 损失函数是在模型输出 logits 之后，由 `CrossEntropyLoss` 独立计算的。这一步骤完全不受 FlashAttention 影响。

- -100 掩码是 PyTorch 的标准约定，`CrossEntropyLoss` 在计算时会自动跳过这些位置。FlashAttention 与这一机制完全解耦。

因此，在使用 FlashAttention 等优化时，你完全可以、也应该继续使用标准的 `-100` 作为损失掩码，无需任何修改。

#### 多轮对话中，如果某个 assistant 回复被截断，损失掩码如何处理不完整句子？

这是一个实际的工程问题。处理方式取决于截断点的位置和数据标注的完整性。

最佳实践：丢弃不完整的助手回复片段。

如果 `assistant` 回复在一个句子的中间被截断，这个回复就是不完整的。如果不对其进行掩码，模型会学习生成一个不完整的句子，这会影响生成质量。

实现方式：

```python
def create_mask_with_truncation_handling(input_ids, tokenizer):
    labels = input_ids.clone()
    
    assistant_start = tokenizer.convert_tokens_to_ids("<|im_start|>assistant")
    assistant_end = tokenizer.convert_tokens_to_ids("<|im_end|>")
    
    i = 0
    while i < labels.shape[1]:
        token = labels[0, i].item()
        if token == assistant_start:
            # 找到这个 assistant 回复的结束位置
            found_end = False
            for j in range(i + 1, labels.shape[1]):
                if labels[0, j].item() == assistant_end:
                    found_end = True
                    # 这是一个完整的助手回复，保留其损失计算
                    # 将开始和结束标记设为 -100
                    labels[0, i] = -100
                    labels[0, j] = -100
                    i = j
                    break
            if not found_end:
                # 没找到结束标记，说明这个回复被截断了！
                # 将这个不完整回复的所有 token 都掩码掉
                labels[0, i:] = -100
                return labels  # 直接返回，因为后续都是不完整的
        else:
            # 非 assistant 部分，掩码
            labels[0, i] = -100
        i += 1
    return labels
```

核心原则：只保留完整的、带有明确结束标记的 `assistant` 回复用于训练。任何不完整的片段都应被掩码，避免模型学习到错误的终止行为。

#### 训练代码中，如何根据 token 对应的角色标签动态生成损失掩码矩阵？

在实际训练中，对话数据往往以结构化的角色信息（如 `role: user/assistant`）存储，而不是简单的文本。我们需要根据这些角色标签动态生成损失掩码。

核心思路：遍历整个 tokenized 序列，识别每个 token 所属的角色。可以通过特殊标记（如 `<|im_start|>user`）来区分角色边界。一旦确定了每个 token 的角色，就可以生成掩码：`assistant` 角色的 token 对应的 label 保持为原始 token ID，其他角色的 token 对应的 label 设为 `-100`。

完整代码示例：

```python
import torch

def create_loss_mask_from_roles(input_ids, tokenizer, roles):
    """
    input_ids: [1, seq_len] 的 token ID 张量
    tokenizer: 用于获取特殊标记的 ID
    roles: 一个列表，每个元素为 (start_index, end_index, role)，
           表示 input_ids[0, start_index:end_index] 属于哪个角色。
           例如 roles = [(0, 5, 'system'), (5, 12, 'user'), (12, 20, 'assistant')]
    返回: labels 张量 [1, seq_len]，其中非 assistant 部分为 -100
    """
    labels = input_ids.clone()
    
    # 首先将所有位置初始化为 -100（默认不计算损失）
    labels.fill_(-100)
    
    # 然后只将 assistant 部分的 label 恢复为原始 token ID
    for start, end, role in roles:
        if role == 'assistant':
            labels[0, start:end] = input_ids[0, start:end]
    
    return labels
```

自动化识别角色边界：在实际项目中，我们通常不手动传入 `roles`，而是利用 `chat_template` 生成的特殊 token 自动识别。例如，Llama 的模板会生成 `<|im_start|>assistant\n...<|im_end|>`。我们可以扫描 `input_ids`，找到所有 `<|im_start|>assistant` 和 `<|im_end|>` 对，将两者之间的 token 标记为 `assistant` 角色。

```python
def auto_detect_roles_and_create_labels(input_ids, tokenizer):
    labels = input_ids.clone().fill_(-100)
    
    assistant_start = tokenizer.encode("<|im_start|>assistant")[0]
    assistant_end = tokenizer.encode("<|im_end|>")[0]
    
    seq_len = input_ids.shape[1]
    i = 0
    while i < seq_len:
        if input_ids[0, i] == assistant_start:
            # 找到对应的结束标记
            j = i + 1
            while j < seq_len and input_ids[0, j] != assistant_end:
                j += 1
            if j < seq_len:
                # 将 assistant 部分的 token 恢复为原始 ID
                # 注意：我们通常也把 assistant_start 和 assistant_end 设为 -100
                # 因为它们是格式标记，不是自然语言
                labels[0, i+1:j] = input_ids[0, i+1:j]
            i = j + 1
        else:
            i += 1
    return labels
```

这种方法完全自动化，无需人工标注角色边界，是现代 SFT 训练的标准做法。

#### 损失掩码对困惑度（perplexity）的计算有什么影响？正确做法应只计算有效 token。

困惑度是衡量语言模型性能的核心指标，定义为交叉熵损失的指数：`PPL = exp(Loss)`。如果计算困惑度时包含了被掩码的 token（即 `-100` 的位置），会导致两个问题：

1. 数值扭曲：`-100` 的位置在交叉熵计算中被忽略，但如果手动计算困惑度时错误地将它们包含在内，会导致分母变大，从而低估真实的困惑度。

2. 不反映真实能力：困惑度应该衡量模型在“它需要学习的任务”上的表现。如果包含了 `user` 和 `system` 部分的 token，就等于在评估模型“生成用户提问”的能力，这不是我们关心的。

正确做法：在计算困惑度时，只计算 `labels != -100` 的有效 token 的平均损失，然后取指数。

```python
def compute_perplexity(logits, labels):
    """
    logits: (batch, seq_len, vocab_size)
    labels: (batch, seq_len)，其中非目标位置为 -100
    """
    # 将所有非 -100 的 label 取出
    active_labels = labels[labels != -100]
    active_logits = logits[..., :-1, :][labels[..., 1:] != -100]  # 错位对齐
    active_labels = labels[..., 1:][labels[..., 1:] != -100]
    
    loss_fct = torch.nn.CrossEntropyLoss()
    loss = loss_fct(active_logits.reshape(-1, active_logits.size(-1)), active_labels.reshape(-1))
    return torch.exp(loss)
```

在 HuggingFace 的 `Trainer` 中，如果 `labels` 中包含了 `-100`，损失计算会自动忽略这些位置，因此困惑度计算也是正确的。但如果自定义评估循环，务必手动过滤。

#### 如果微调数据包含图像或其他模态，损失掩码的概念如何扩展到多模态序列？

多模态大模型（如 LLaVA）通常将图像 token 和文本 token 拼接成一个序列。损失掩码的核心原则不变：只对模型需要学习的输出部分计算损失。

具体扩展方式：

1. 图像 token 部分：图像 token 是输入的一部分，模型不需要生成它们。因此，所有图像 token 对应的 labels 都应该设为 `-100`。

2. 文本部分：与纯文本对话相同，`system` 和 `user` 的文本 token 的 labels 设为 `-100`，只有 `assistant` 的文本 token 保持原始 ID。

3. 多模态的特殊标记：例如 `<image>`, `</image>` 等标记，同样设为 `-100`。

```python
def create_multimodal_labels(input_ids, tokenizer, image_token_id, assistant_start_id, assistant_end_id):
    labels = input_ids.clone().fill_(-100)
    
    seq_len = input_ids.shape[1]
    i = 0
    while i < seq_len:
        token = input_ids[0, i].item()
        if token == assistant_start_id:
            j = i + 1
            while j < seq_len and input_ids[0, j] != assistant_end_id:
                j += 1
            if j < seq_len:
                labels[0, i+1:j] = input_ids[0, i+1:j]
            i = j + 1
        else:
            i += 1
    return labels
```

关键：无论输入序列中包含多少种模态，损失掩码的逻辑始终保持一致——只对需要模型自回归生成的部分计算损失。

#### 在 RLHF 的 SFT 阶段，掩码策略与最终偏好对齐效果是否有关联？

有很强的关联。SFT 阶段的掩码策略会直接影响模型的基础行为，而这些基础行为是后续 RLHF 优化的起点。

关联体现：

1. 正确的掩码策略保证了优化的方向：如果 SFT 阶段只对 `assistant` 部分计算损失，模型学习到的是“给定上下文，生成助手回复”的能力。这与 RLHF 阶段优化的目标（生成更好的助手回复）是一致的。如果 SFT 阶段掩码不当，模型学习了生成 `user` 提问，那么在 RLHF 阶段，它会收到奇怪的奖励信号，导致对齐失败。

2. SFT 掩码策略决定了 RLHF 的初始策略质量：RLHF 的 PPO 训练需要一个稳定的初始策略。如果 SFT 模型因为掩码错误而表现出角色混乱，PPO 的训练将极其不稳定，因为奖励模型无法给“时而扮演用户、时而扮演助手”的行为打出合理的分数。

3. 影响偏好数据的有效性：RLHF 的偏好数据通常是人工标注的，标注者看到的是模型的回复。如果 SFT 模型因为掩码错误，经常输出包含 `user` 提问和 `assistant` 回复的混合文本，这些数据会被标注为低质量，导致偏好数据被“污染”。

结论：SFT 阶段的损失掩码是 RLHF 成功的基石。一个干净、一致的 SFT 模型是后续偏好对齐能够有效进行的先决条件。

#### 如果 assistant 回复中包含大量格式化内容（如 markdown 标记），是否需要通过掩码降低其损失权重？

这是一个可选的微调策略，取决于你对模型输出风格的期望。

分析：Markdown 标记（如 `加粗`, `- 列表`）是格式信息。如果大量训练数据的 `assistant` 回复都带有 Markdown 格式，模型会学习到“我应该在合适的场景下使用 Markdown”。这通常是期望的行为，因为用户也喜欢结构清晰的回复。因此，一般不需要对这些格式化 token 进行特殊处理。

但以下情况可能需要降低权重或掩码：

1. 格式错误：如果自动生成的回复中，Markdown 标记使用混乱（如不匹配的 `**`），这些错误会影响模型对格式的学习。此时应将这些错误的 token 掩码掉，或者修正数据。

2. 不希望模型使用格式化：如果应用场景明确不需要 Markdown（如纯文本对话），则可以在构造 labels 时，将 Markdown 标记对应的 token 权重设为 0 或较低，抑制模型生成这些标记。

3. 减少“格式过拟合”：如果担心模型对某种特定格式过拟合，可以对这些 token 施加一个小的权重衰减，但通常不需要。

实现方式：可以在 `labels` 张量中，将对应 Markdown token 的 label 设为 `-100`，或者在计算损失时，为这些 token 分配一个小于 1.0 的权重。

#### 对比“仅计算回复损失”与“对整个序列计算损失但使用不同权重”的梯度流向区别。

这两种策略在数学上和优化行为上有本质区别。

策略 A：仅计算回复损失（标准做法）

- 梯度流向：梯度只会从 `assistant` 回复部分的输出传递回模型。模型参数更新完全由“生成助手回复”的误差驱动。

- 优化目标：最小化助手回复的负对数似然，清晰且专注。

策略 B：对整个序列计算损失，但使用不同权重

- 梯度流向：梯度会从所有位置（包括 `user` 和 `system`）的输出传递回模型。只是不同位置的损失贡献被缩放了。

- 优化目标：变成了一个多目标优化问题：既要生成助手回复（高权重），也要生成用户提问（低权重）。这会导致梯度信号混杂。

关键区别：

1. 梯度冲突：在策略 B 中，`user` 部分的损失会鼓励模型去预测用户提问的模式，而 `assistant` 部分的损失会鼓励模型生成回复。这两种梯度可能在共享的参数层中发生冲突，导致训练不稳定或收敛到次优解。

2. “捷径学习”风险：模型可能会通过直接“记忆”`user` 输入来降低那一部分的损失，而不是学习更深层的语言规律。这会浪费模型容量。

3. 长期影响：策略 B 可能让模型在生成时变得“犹豫”，因为它在训练时被要求同时扮演两个角色。策略 A 则让模型对“自己是助手”这一身份更加坚定。

结论：除非有特殊需求（如训练一个能同时模拟用户和助手的对话生成器），否则策略 A（仅计算回复损失）总是更优、更稳定的选择。

#### 当使用 LoRA 等 PEFT 方法时，损失掩码的策略与全参数微调有何不同？

掩码策略本身完全相同。无论你使用 LoRA、Prefix Tuning 还是全参数微调，训练数据都是一样的，模型的期望行为也是一样的。因此，你对 `labels` 的处理方式不需要任何改变。

但存在一个值得注意的区别：

- 全参数微调：所有模型参数都参与更新。如果掩码策略出错（如对 `user` 部分也计算了损失），整个模型的所有层都会受到错误梯度的污染，影响可能是全局的。

- LoRA 微调：只有 LoRA 的低秩矩阵被更新，原始预训练权重保持冻结。如果掩码策略出错，错误梯度只会影响 LoRA 矩阵，而不会破坏基座模型的语言能力。这使得 LoRA 对掩码错误的容忍度稍高一些。但这并不意味着可以犯错，因为 LoRA 矩阵学到的错误行为依然会影响最终模型。

结论：掩码策略与微调方法无关，但 LoRA 等 PEFT 方法因为参数更新范围小，对掩码错误的“纠错”成本更低（重新训练 LoRA 矩阵即可，基座模型不受影响）。

#### 在指令微调中，是否应该将 EOS token 也包含在损失计算中？为什么？

应该。 EOS token 是助手回复的组成部分，它标志着生成的结束。模型需要学会在何时停止。

原因：

1. 教会模型“闭嘴”：如果 EOS token 不参与损失计算，模型就无法学习到生成结束的时机。它可能会一直生成下去，直到达到最大长度限制。

2. EOS 是自然语言的一部分：对于一个完整的回复，EOS 是最后一个 token。预测 EOS 是语言建模任务的一部分。模型需要根据上文判断“话已说完”，从而输出 EOS。

3. 对 RLHF 的影响：在 RLHF 阶段，奖励模型会根据回复的完整性和简洁性打分。如果模型不知道如何停止，它会生成冗长的回复，从而获得较低的奖励。

实现方式：在构建 labels 时，将 EOS token 像普通的 assistant 回复 token 一样保留，不设为 `-100`。

#### 如何利用损失掩码在训练中同时支持条件生成和无条件生成任务？

在一些高级训练场景中，我们希望模型既能进行“有上下文的对话”（条件生成），也能进行“开放式续写”（无条件生成）。损失掩码可以灵活地区分这两种情况。

策略：

1. 条件生成（对话）：只对 `assistant` 部分计算损失，`user` 和 `system` 部分掩码。这是标准做法。

2. 无条件生成（续写）：数据格式为一段纯文本，没有角色区分。此时，我们希望模型学习生成整个文本。因此，不对任何 token 进行掩码，或者只对一段 prompt 之后的文本计算损失。

实现动态掩码：\
在每条数据中添加一个 `task_type` 字段，指示该数据的类型。在 Data Collator 中，根据 `task_type` 动态选择掩码策略：

```python
def dynamic_loss_mask(sample, input_ids):
    if sample["task_type"] == "dialogue":
        return create_assistant_only_mask(input_ids, tokenizer)
    elif sample["task_type"] == "completion":
        # 假设 prompt 已经包含在 input_ids 中，我们只对 prompt 之后的部分计算损失
        prompt_len = sample["prompt_len"]
        labels = input_ids.clone()
        labels[:, :prompt_len] = -100  # prompt 部分不计算损失
        return labels
    else:
        return input_ids.clone()  # 无条件，全序列计算损失
```

效果：通过这种动态掩码，一个模型可以同时学会“对话”和“续写”两种能力，并且不会互相干扰。在推理时，它可以根据输入格式自动判断应该进行哪种任务。

#### 分析如果忘记设置损失掩码（即对所有 token 计算损失），模型会表现出怎样的行为？

如果忘记设置损失掩码，模型会对整个序列（包括 `system`、`user` 和 `assistant`）的所有 token 计算交叉熵损失。这会导致以下几个严重的后果：

1. 角色扮演混乱\
   模型被训练来生成整个对话，而不是只生成助手的回复。在推理时，给定一个 `user` 的提问，模型可能不会直接回答，而是：

- 生成一段 `system` prompt，然后等待。

- 接在 `user` 提问的后面，把自己当成用户，继续提问。

- 生成一个完整的、包含 `user` 和 `assistant` 的多轮对话，而不是只回答问题。

2. 输出质量下降\
   由于模型被迫学习如何生成 `user` 的提问，它的优化目标变得模糊。它可能学会了模仿训练数据中低质量或有害的 `user` 提问模式，并可能在推理时输出这些模式。

3. 安全性降低\
   如果训练数据中包含恶意或有偏见的 `user` 提问，模型可能会学会生成类似的内容。这违背了安全对齐的原则。

4. 训练不稳定

不同角色的语言分布差异很大，将它们混合在一个损失函数中，相当于让模型去优化多个相互冲突的目标，这可能导致训练损失震荡，收敛缓慢，甚至发散。

5. 对话历史被“污染”

模型可能会认为，在对话中适当地“插嘴”或“抢话”是合理的，从而无法维持正常的一问一答节奏。

总结：忘记设置损失掩码是一个灾难性的错误，它会使 SFT 模型完全不可用。这也是为什么各种训练框架都将损失掩码作为核心功能来强调。

#### 写出一个完整的 PyTorch 示例，实现给定 input_ids 和 assistant_start_pos，生成带掩码的 labels。

下面是一个完整的、可直接运行的 PyTorch 示例。它假设我们已经通过 `chat_template` 将对话格式化，并且已知 `assistant` 回复的起始位置。

```python
import torch
from transformers import AutoTokenizer

def create_labels_with_assistant_mask(input_ids, assistant_start_pos):
    """
    input_ids: Tensor of shape (batch_size, seq_len) 或 (seq_len,)
    assistant_start_pos: int, assistant 回复的起始 token 位置
    返回: labels Tensor，与 input_ids 相同形状，非 assistant 部分为 -100
    """
    # 确保 input_ids 是二维的 (batch_size, seq_len)
    if input_ids.dim() == 1:
        input_ids = input_ids.unsqueeze(0)
    
    batch_size, seq_len = input_ids.shape
    labels = input_ids.clone()
    
    # 在 PyTorch 中，-100 是 CrossEntropyLoss 默认的忽略索引
    IGNORE_INDEX = -100
    
    # 对于 batch 中的每个样本（这里简化为 batch_size=1）
    for b in range(batch_size):
        # 将 assistant 起始位置之前的所有 token 的 label 设为 -100
        labels[b, :assistant_start_pos] = IGNORE_INDEX
        
        # 通常我们也希望将 assistant 回复的起始特殊标记（如 <|im_start|>assistant）设为 -100
        # 因为它是一个格式标记，不是自然语言。
        # 这里假设 assistant_start_pos 已经指向了 assistant 回复的第一个自然语言 token。
        # 如果 assistant_start_pos 指向的是特殊标记，那么需要 +1 或做其他处理。
    
    return labels

# ========== 完整示例 ==========
if __name__ == "__main__":
    # 1. 加载 tokenizer
    tokenizer = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM2-135M")
    if tokenizer.pad_token is None:
        tokenizer.pad_token = tokenizer.eos_token

    # 2. 构造一个简单的对话
    messages = [
        {"role": "system", "content": "你是一个有用的助手。"},
        {"role": "user", "content": "你好，请问北京的首都是哪里？"},
        {"role": "assistant", "content": "北京是中国的首都。"}
    ]

    # 3. 使用 chat_template 格式化对话
    input_text = tokenizer.apply_chat_template(messages, tokenize=False)
    print("格式化后的文本：")
    print(input_text)
    print("-" * 50)

    # 4. Tokenize 整个序列
    inputs = tokenizer(input_text, return_tensors="pt")
    input_ids = inputs["input_ids"]
    print("Input IDs shape:", input_ids.shape)

    # 5. 找到 assistant 回复的起始位置
    # 辅助函数：在 input_ids 中查找子序列
    def find_sublist(seq, sub):
        for i in range(len(seq) - len(sub) + 1):
            if seq[i:i+len(sub)].tolist() == sub.tolist():
                return i
        return -1

    # 查找 "assistant" 标记，例如 "<|im_start|>assistant\n"
    assistant_marker = tokenizer.encode("assistant", add_special_tokens=False)
    # 注意：实际应用中，应使用 chat_template 生成的确切标记
    # 这里简化为直接查找 "assistant" 的 token，但更健壮的方式是查找完整的角色标记
    
    # 假设我们已经知道 assistant 回复的起始位置（实际开发中需要动态查找）
    # 这里我们手动指定（你可以通过查找 "assistant" 相关的 token 来定位）
    assistant_start_pos = 15  # 例如：经过 tokenization 后，assistant 回复从第 15 个 token 开始
    
    # 6. 生成带掩码的 labels
    labels = create_labels_with_assistant_mask(input_ids, assistant_start_pos)
    
    # 7. 可视化 labels
    print("\nToken 与 Labels 对照：")
    for i in range(input_ids.shape[1]):
        token_text = tokenizer.decode([input_ids[0, i]])
        label_id = labels[0, i].item()
        if label_id == -100:
            label_text = "[MASKED]"
        else:
            label_text = tokenizer.decode([label_id])
        print(f"Position {i:3d}: Token='{token_text}' (ID={input_ids[0,i].item():5d}) -> Label={label_text}")

    # 8. 验证非 assistant 部分的 label 是否确实为 -100
    assert torch.all(labels[0, :assistant_start_pos] == -100), \
        "Error: Non-assistant tokens were not correctly masked!"
    print("\n✅ 掩码验证通过！")
```

关键点说明：

1. 在实际项目中，`assistant_start_pos` 应该通过自动查找 `input_ids` 中特定的角色标记（如 `<|im_start|>assistant`）来动态确定，而不是硬编码。

2. 对于多轮对话，需要找到每一个 `assistant` 回复的起始和结束位置，将中间的所有 token 保持为原始 ID，其余位置设为 `-100`。

3. 对于 `assistant` 回复中的特殊格式标记（如 `<|im_end|>`），通常也设置为 `-100`，因为它们不是模型需要学习生成的自然语言内容。
